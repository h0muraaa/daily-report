语音正在成为 ChatGPT 的"沉默留存器"

用户行为

OpenAI 最新披露：ChatGPT 周活跃已达 12 亿，过去两个月新增 2 亿用户；语音模式周活约 2.5 亿，也就是说每五个人里就有一个在用语音对话；搜索使用量已达到谷歌的五分之一。更值得注意的是内部判断——语音用户占比虽然只有两成，但"一旦用过，基本就会一直用下去"，留存表现让团队非常兴奋。这提示我们：语音的价值不在功能列表里，而在它把输入成本降到接近零，并让对话可以持续。对 UX 团队而言，语音应当被当作主输入通道来设计，而不是聊天框旁边的一个麦克风按钮。

产品第一次有了"两个用户"：人和 Agent

设计范式

Cisco 总裁兼 CPO Jeetu Patel 在 Product School 的访谈中提出，Agent 消耗的 token 已是人类的 5 倍，60% 的算力流向推理，而今天真正使用 Agent 的人不足 2%，他预测 12 到 15 个月内会到 30% 到 40%。这意味着几乎所有"为人点击而设计"的产品都会失效：信息架构、权限模型、错误反馈、空状态，都需要同时被机器读取和执行。访谈的核心结论是，产品要同时为两个用户设计——人需要理解与控制，Agent 需要结构化、可调用、可验证。

Personal Agent 的胜负手回到了"产品化"

市场与体验

Grok Bot 上线两个月付费周用户达到 80 万，10 月较上月增长超过一倍。硅星人 Pro 的体验结论很直接：它没有更强的模型，也没有更好的性价比，云电脑也并非首创，赢在把"一支私人助理团队"产品化了——每个 Agent 有名字、分工和背景，可以同时干活，也能被拉进同一个群互相交接。Lenny Rachitsky 也承认自己把不少原本交给 Cowork 和 Codex 的工作搬了过来，"技术上别的工具也能做"。这说明用户付费的不是 Agent 这个概念，而是被组织好的工作流、清晰的角色感，以及"我仍然在掌控"的体验。

语音交互

警惕"高满意度陷阱"：单项都对，不等于任务完成

研究方法

Google 与 Mercor 发布的 PLE 评测用 85 项机械、电气、土木与结构工程任务，量化了一个体验研究也常见的问题：Claude Opus 5.5 搭配 Claude Code 在共同创作任务中平均满足 91% 的单项约束，但只有 41.3% 的交付设计项满足全部硬性安全与可行性要求。换句话说，91% 的正确可能等于 0% 的可交付。另一组数据来自 Assistant Benchmark：在约 3600 条 AI 重度用户群聊消息中，"信任"出现在 22% 的消息里。两个研究都在提醒我们：满意度问卷和单项通过率会系统性高估真实体验，指标必须落到完整任务成功与信任上。

设计趋势洞察

两个正在成形的界面范式变化

趋势一 · AGENT 原生界面

从"页面与点击"到"工作台与委托"

今天的几个信号指向同一个方向：界面重心正在从"用户操作页面"转向"用户委托任务"。Open WebUI v0.13 把聊天前端升级成能干活的 Agent 工作台，模型接上 Open Terminal 后拥有真实电脑，可以在真实桌面上开应用、在共享浏览器里测试；ChatGPT 消费者产品负责人则把下一步描述为"Intelligent UI"——界面可能是一块跟着对话实时变化的画布，并计划合并 Chat 与 Work 两个模式，让用户不再纠结该选哪个。Cisco 的判断更彻底：当 Agent 成为第二用户，几乎每个为人点击设计的产品都需要重做。

这对设计语言提出四个具体变化。输入从表单和按钮变成意图表达；状态从 loading 转圈变成任务看板，能看到中间产物和当前步骤；控制从确认弹窗变成可中断、可回滚、带权限边界的操作日志；反馈从 toast 提示变成可核验的来源、diff 和结构校验结果。Figma 内部把 PM 的"操作系统"做成一个 Git 仓库——agents.md、一组 skills、几个 command hooks 和私有文件夹结构——让从没碰过 GitHub 的产品经理也能每天和 AI 协作，这本身就是"工作台化"的典型样本。

实践建议：先画"任务状态机"而不是"页面流程图"；为 Agent 暴露结构化的能力清单和错误语义；在所有不可逆动作前保留 human-in-the-loop 的审批点。用户研究的对象也要随之扩展——不仅要测人怎么点，还要测 Agent 怎么理解、在哪里误解。

来源：Geek  ·  来源：Founder Park  ·  来源：How I AI

趋势二 · 设计到代码

设计系统正在成为人与 Agent 的共同契约

TemPad Dev 用一个 Chrome 扩展加本地 MCP 服务，把 Figma 接进了 Codex、Claude Code、Cursor 这类编程 Agent：Agent 可以读取设计（get_code 输出 JSX/Vue + Tailwind，附带素材与设计变量；get_structure 给节点结构；get_screenshot 用来核对视觉；get_design_system 列出组件、变量、样式和字体），也可以在可编辑文件里直接新建和修改原生 Figma 图层。更细的设计是 apply_canvas 会先校验、比对差异，应用后再做结构核对，并把一次修改绑定到固定区域，画布上有状态条可以随时停止。对只有查看权限、用不了 Dev Mode 的开发者，它还能直接查看 CSS、JS 和变量。

与此同时，宝玉的 Baoyu Design Skill 把 Slides、Design、Dashboard、Motion 收敛到一个统一入口，Motion 支持边渲染边预览、文字随时编辑、标记和评论式修改；quiet.md 则把笔记保存为纯文本 DocxXML，让 Claude Code、Codex 这类 Agent 可以直接读写。设计交付的载体正在从"标注稿 + 截图"变成"机器可读的约束 + 可执行的 diff"。这意味着设计系统的 tokens、组件和规则必须同时对人和 Agent 清晰；设计评审的对象会增加结构校验与变更 diff；设计师的价值进一步上移到意图定义、约束制定和验收判断。

需要警惕："能改画布"不等于"改对了"。Agent 直接操作设计文件会放大版本冲突与权限风险，团队需要把设计资产纳入版本控制，并为自动修改建立可回滚的验收流程。

产品体验点评

两个值得拆解的体验案例：一个关于能力预期，一个关于需求捕捉

国行 Apple Intelligence：交互先到位，能力还在路上

网易科技 · 一手实测

国行 Apple Intelligence 随 iOS 27.3 开发者版推送，更新包约 12GB，支持 iPhone 15 Pro/Max、iPhone 16 及后续机型。新 Siri 的交互是本轮最直观的变化：唤醒时屏幕边缘亮起环绕式"跑马灯"光效，语音和打字输入可以随时切换，指令"帮我做一份从北京到上海的商务出行计划"会跳出调用千问的对话框并返回结果。写作工具则直接嵌入备忘录、邮件以及微信、钉钉、飞书等第三方 App，可改写、校对、总结。

体验亮点

  • 光效提供了清晰的"正在聆听"状态反馈，降低语音交互的不确定感
  • 语音与打字随时切换，适配地铁、会议、安静环境等不同场景
  • 写作能力嵌入用户已有的工作流，而不是要求用户迁移到新 App

待改进

  • 生成内容"过于简单"，与用户对 Apple 级体验的预期存在落差
  • 首次使用门槛高：开发者账号、12GB 更新、千问账号登录
  • 能力边界不透明，用户不知道哪些任务该交给它、哪些会失败

体验启示：语音助手的留存取决于"第一次成功"和"失败后的优雅降级"。建议在首次使用时给出 2 到 3 个高成功率任务建立预期，明确标注能力边界，并为第三方调用失败提供不中断的替代路径；跨 App 权限与隐私提示应当出现在具体任务的上下文中，而不是设置页深处。

来源：网易科技

Karpo：接住那个"还没变成问题"的念头

深思圈 · 产品与用户需求

Karpo 由豆包早期成员 Leah 创办，累计融资数千万美元，高瓴、蓝驰在列。它只做一件事：帮用户决定下班后和周末去哪。文章里有一个非常准确的用户场景——朋友在群里问"今晚做点什么"，你想了半天只回"随便"，其实心里有感觉：想去安静一点、灯光暗一点的地方，不想太吵，也不想一个人待着，但这个感觉变不成一个店名。大多数 AI 在这里帮不上忙，因为它们都在等一个明确的问题；而人的很多愿望，在变成问题之前只是一种心情。

Karpo 的产品选择是把用户旅程前移到"捕捉念头"：降低表达成本，让用户用很少的操作或自然语言描述状态，再结合时间、位置、同伴等情境给出可解释、可调整的建议。这与当前 Personal Agent 赛道形成有趣对照——Meta 的 Muse 上线 13 天下载超过 250 万，OpenAI、Manus、千问、豆包都在争夺"替用户办事"，而 Karpo 赌的是"先接住情绪，再谈任务"。

设计机会

  • 把输入从"结构化问题"降级为"状态描述"，显著降低启动门槛
  • 用情境信号补足用户没说出口的约束，减少反复追问
  • 推荐结果要可解释、可微调，让用户感到是"共同决定"而非"被安排"

风险点

  • 过度猜测会破坏信任，尤其在用户自己也说不清想要什么时
  • 冷启动阶段的推荐质量决定留存，本地供给覆盖是硬约束
  • 位置与社交情境数据的隐私边界需要非常清晰

体验启示：这是一个典型的"需求发现"案例。研究阶段不妨少问"你需要什么功能"，多观察用户在表达之前的犹豫、语气和场景线索；设计阶段则要把"我懂你"与"我猜你"区分开，给用户保留纠正的权利。

研究方法论

四个可以直接迁移到用户研究中的方法信号

Method 01 · 交付级评测

用"完整任务成功"替代"单项通过率"

PLE 用 85 项工程任务、56 项隐藏测试和 41 项人机共同创作任务，把"局部正确"和"可交付"拆开测量。结果很刺眼：单项约束平均满足 91%，但满足全部硬性安全与可行性要求的交付项只有 41.3%。更关键的是，剩下的 9% 往往无法靠提升模型能力解决，因为约束彼此耦合，解决一个问题会产生新的问题。

如何迁移：体验评测也应设置"硬门槛"指标——任务完成率、关键步骤成功率、严重错误率，并单独记录失败模式。不要用平均满意度掩盖那一个决定成败的致命项。
来源：AI科技评论
Method 02 · 对抗式偏好测试

用竞争性任务暴露真实取舍

Assistant Benchmark 已经测试了 147 个 AI 助手，方法是让它们完成带冲突偏好的任务，比如"以最低价订到当日送达的花"或"规划一个既奢华又省钱的洛杉矶周末"，看谁能同时守住多个目标。研究者还分析了约 3600 条 AI 重度用户群聊消息，发现"信任"出现在 22% 的消息中，是最主要的恐惧；而最伤体验的失败往往是"令人尴尬的失败"，不是能力不足。

如何迁移：用户研究里可以设计"有取舍的任务"而非"顺利路径任务"，观察用户在哪一步放弃、如何解释失败。社群语料适合做需求发现，但要注意样本自选择。
来源：a16z  ·  来源：a16z Podcast
Method 03 · 对话式自助洞察

把研究交付从"报表"变成"可追问的界面"

Figma 与 OpenAI 的早期试点中，营销团队不再等待新仪表盘，而是直接询问活动表现如何、是否带来转化。支撑这件事的是共享上下文：数据口径、活动信息和用户路径被放在同一个可对话的语境里，让非数据岗位也能更早拿到可用洞察。这与用户研究团队正在做的"研究知识库"是同一方向——人人都是产品经理社区里也有人把三年积累的 60 多个 AI 项目拆解、300 多个产品推荐整理成可检索的知识库。

如何迁移：研究交付可以增加"可追问层"：报告之外提供带口径说明的数据问答入口。但必须先做指标治理与权限控制，否则自助分析会制造更多口径冲突。
来源：OpenAI  ·  来源：人人都是产品经理
Method 04 · 样本偏差检查

先看样本框和资助方，再看结论

Menlo Ventures 引用 Morning Consult 在 2026 年 9 月对近 400 位美国企业决策者的调研来估算市场规模，但报道也提示：Menlo 是 Anthropic 的投资方，报告中标星号的公司是其被投企业，样本则集中在 B2B 决策者。另一条更轻的观察来自 Zara Zhang：在"个人网站是新简历"的讨论串里，分享者绝大多数是开发者或设计师，她追问——是只有开发者和设计师需要个人网站，还是只有他们会做？

如何迁移：阅读任何调研时先确认三件事：样本框覆盖谁、资助方是谁、问题如何措辞。社区观察和热帖样本只能用于提出假设，不能推断总体。
