今日要点

Sam Altman 呼吁：是时候重新思考操作系统和用户界面的设计了

OpenAI CEO Sam Altman 在 X 上发文表示，当下是"认真重新思考操作系统和用户界面如何设计"的好时机。他进一步指出，互联网也应该存在一个"对人类和 agent 同样可用"的协议。这意味着 AI 时代的界面设计正在从"人类专属"走向"人机共用"——未来的 UI 不再只是服务于人的视觉系统，而是要同时满足 agent 的文本化、结构化理解需求。

对于 UX 设计师而言，这是一个范式转移的信号：当 agent 成为界面交互的重要参与者，设计的目标用户从"单一人类"扩展为"人类 + AI 协作体"，设计系统需要重新考虑信息层次、反馈机制和可解析性。

[来源: Sam Altman(@sama) on X]
Peter Yang 拆解三大 Agent 产品的 UX 盲区

Product 领域知名博主 Peter Yang 连续发文，对 Claude Code、Codex 和 OpenClaw 三款主流个人 Agent 产品进行了坦诚的体验点评。他指出 Claude Code 每次在移动端与项目对话都需要输入 /remote-control 指令，routine 失败时也没有通知；Codex 缺乏移动端支持，无法成为真正的个人代理；OpenClaw 在人格化方面进步明显，但可靠性不足，许多重度用户需要定期用其他工具来"救场"。

同时，Peter Yang 提出了"优秀个人 Agent"的七条体验标准：跨平台工作、主动可靠、优秀记忆、多端无缝、多模态切换、第三方消息可达、有趣的人格。他直言："三者都还没能全部达标。"这为 AI 产品经理和 UX 设计者提供了一个清晰的体验评估框架。

[来源: Peter Yang on X]
"AI 设计悖论"：越懂设计，越难用 AI 做设计

Linear 联合创始人 Karri Saarinen 提出一个引人深思的观察："当你对某个领域不太了解、不太在意或没有清晰想法时，AI 给人的感觉最惊艳。可一旦你知道某个东西应该是什么感觉、长什么样，引导 AI 到达那里就几乎不可能了。"这个悖论横跨设计、代码、法律等多个领域。

这一洞察对 UX 团队极具价值：AI 工具当前最大的用户并非领域专家，而是"新手"或"执行者"。如何设计出能让专家精确控制输出质量的交互方式，而非仅靠反复试错，是 AI 创意工具下一个需要突破的体验瓶颈。

[来源: Karri Saarinen via X]
GitHub Next 的 Maggie Appleton：Agent 工程需要"多人协作"体验设计

GitHub Next 的 Maggie Appleton 在 AI Engineer 大会上指出，Agent 工程目前还是一个"单人故事"——每个开发者在自己的 CLI 里独自指挥 agent，没有共享上下文，导致重复工作、冲突修改和方向分裂。她强调，严肃软件仍然需要严肃协作，需要多视角和多类型专长的共同参与。

她在演讲中展示了 Ace 项目的 demo，探索如何让多人在同一个 agentic 环境中共同规划、批判性思考和共享上下文。这对设计协同工具的演进具有启示意义：当 AI 介入团队工作流，协作设计的对象从"人与人"变为"人 + AI + 人"的复合网络。

[来源: AI Engineer / Maggie Appleton]
Snap CEO Evan Spiegel：分发是比产品市场匹配更稀缺的资源

在 Lenny's Podcast 的深度访谈中，Snap CEO Evan Spiegel 分享了 Snap 在巨头夹缝中存活 15 年的产品设计哲学。他反复提及的核心判断是：产品会被复制，分发很难复制；功能会被追平，生态更难追平；技术会进步，但用户是否愿意采用，最终是人性问题。

Spiegel 还透露了 Snap 的设计组织方式：一个 9-12 人的设计团队，没有职级和层级，每周与 CEO 一起评审数百个创意。这种扁平化、高密度的设计决策模式，以及以相机为核心入口的交互创新（Stories、AR Lens、Swipe 导航），值得 UX 团队深入借鉴。

设计趋势洞察

Agent 原生界面：从 GUI 到 CLI，再到"AI 优先"交互范式

42章经对 Slock.ai 创始人 RC 的深度访谈揭示了一个正在发生的设计范式迁移：CLI（命令行界面）正在因为 Agent 的崛起而被重新发明。RC 指出，大模型是 text-based 的，相比 GUI，它天然更容易理解 CLI 这种文本化、结构化的形态。

但关键在于，"今天做 CLI"和过去完全不同。以前 CLI 是给人用的，可以做得很花哨；今天 CLI 的目标用户变成了 agent，需要重新设计输入和输出——输入要简洁明确，help message 和 menu 要给出清楚的示例；输出要静态、确定、高信息密度，让 agent 能一眼判断操作是否成功。

这揭示了一个更大的趋势：界面设计正在出现"双轨制"——一条轨道继续为人类优化视觉体验（GUI），另一条轨道专门为 agent 优化可解析性和执行效率（CLI/结构化接口）。未来优秀的数字产品，很可能需要同时设计"人类版"和"agent 版"两套交互界面。

UX 启示：产品经理和设计师需要开始思考"Agent 可理解性"作为新的设计原则。你的菜单结构、错误提示、返回数据格式，是否也便于 AI 解析和决策？
[来源: 42章经]
AI 设计工具矩阵成型：Claude Design 与 Lovart/星流的"一人品牌部"实践

本周 AI 设计工具领域有两个值得关注的动态。Claude Design 被 Matt Wolfe 称为"最被低估的 Claude 功能"，它能够将创意直接转化为精致的视觉产出——包括落地页、mockup、演示文稿、品牌概念和 UI 布局。HeyGen 更是将 HyperFrames 原生集成进 Claude Design，实现了"设计 -> 动画 -> MP4"的一站式工作流。

与此同时，花叔在公众号分享了他使用"星流"（Lovart 的中文替代版）构建"一人公司品牌部"的实践。从橙皮书封面、公众号配图、视频封面到 PPT 动画和活动海报，AI 设计工具已经成为他每周输出的核心工作流。他用 Image-2 模型完成的演讲 PPT 设计获得了上千互动——一个发 PPT 的推文跑出了远超预期的传播效果。

这两个案例共同指向一个趋势：AI 设计工具正在从"尝鲜玩具"进化为"专业工作流组件"。设计师的核心价值正在从"执行产出"向"创意方向 + AI 协作管理"转移。

产品体验点评

Multica：4 个真人 + 十几个 Agent 的"多人多 Agent"协作体验

Multica 是一个上线不到 3 周就斩获 GitHub 1.2 万 Star 的新项目，致敬了 1964 年的操作系统 Multics。它的核心理念是：让人和 AI Agent 在同一个工作空间里协同工作——"Where humans and AI agents work as one team."

从用户体验角度看，Multica 试图解决的是当前 Agent 工具的两个核心痛点：一是个人使用的孤岛化（每个开发者在自己的环境里独自操作 agent），二是团队协作时的上下文断裂（没有共享语境导致重复工作和方向冲突）。Multica 的设计思路是将"多人 + 多任务"的操作系统思想移植到 Agent 时代，让团队可以在同一个空间内与多个 agent 丝滑协作。

创始人张佳圆透露，团队目前只有 4 个真人和十几个 AI Agent，但平台上"平均每 10 秒就有一个 Agent 任务被触发执行"。这种"小规模人类团队 + 大规模 Agent 军团"的组织模式，可能是未来产品设计团队组织形态的预演。

[来源: 十字路口Crossing]
Gemini CLI 的"子代理"机制：任务委派与并行工作流的设计权衡

Google 在 Gemini CLI 中引入了子代理（subagents）功能，允许主代理充当"协调者"，将代码分析、调研或测试等子任务分配给不同的专用子代理。每个子代理在隔离环境中运行，并将汇总后的结果返回主会话，从而减少上下文负载。

从 UX 设计角度，这个功能体现了一个重要的交互设计原则：信息层次的分离。用户（或主代理）不需要看到所有中间步骤的细节，只需要收到汇总后的结果。子代理支持并行运行，可以同时分析代码库的不同部分或并行开展多项调研任务。

但 Google 也在文档中坦诚指出了并行执行的风险：代码修改冲突、并发请求导致的使用额度增加。这种"能力开放 + 风险提示"的设计策略，值得在构建复杂 AI 工作流时参考——不是把能力隐藏起来，而是让用户在知情的前提下自主选择。

研究方法论

"上下文种子"：AI 产品设计中的隐性信息收集策略

宝玉在 X 上分享了一个极具产品思维的设计方法——"上下文种子"。核心思路是：给 AI 工具/系统设计的接口，除了满足当前运行所需的必要参数外，还应该额外携带一些"不需要但未来分析产品时会很有价值"的信息。

他以客户支持系统为例：最原始的工具设计只要求 customer_id、date_range 和 status 三个参数。但产品团队永远不知道 AI 抓取这些工单是为了什么——是处理投诉？做事故复盘？准备周报？还是分析大客户流失风险？

如果在工具参数中加入 purpose（这次操作的目的）、user_goal（用户最终想完成什么）、related_event（是否和某次事故/发布有关）、confidence（AI 对判断的把握度）等"上下文种子"，产品团队就能获得原本只能靠猜的用户意图数据。

研究启示：这个方法本质上是一种"设计即研究"的策略——通过在产品接口中预埋信息收集点，实现用户行为的自动化洞察。对于研究资源有限的小团队，这是一种低成本、高回报的用户研究基础设施设计思路。
[来源: 宝玉(@dotey) on X]
需要为 Agent 单独写一版 PRD 吗？

产品经理社区本周有一个有趣的讨论：写产品需求文档（PRD）时，是否需要单独为 Agent 开一版？宝玉的观点很明确：没必要。他的理由是：如果人能看懂，模型更应该能看懂；如果 PRD 可以直接给 Agent 用了，那大部分场景程序员可能都不需要了。

这个观点背后有一个更深层的 UX 设计趋势：人机可读性正在趋于统一。传统的 PRD 需要人类语言（模糊、依赖上下文、需要面对面澄清），而技术文档需要机器语言（精确、结构化、无歧义）。但在 LLM 时代，自然语言本身已经成为一种"可执行规范"——写得足够清晰的 PRD，对人好理解，对 AI 也好执行。

对于 UX 研究员来说，这意味着"用户研究文档"（如用户画像、旅程地图、洞察报告）也可能需要重新设计格式——不再只是为 human reader 优化，还要考虑 AI 能否从中提取关键信息并转化为设计决策。

[来源: 宝玉(@dotey) on X]
