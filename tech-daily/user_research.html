今日要点

五条最值得带进下一次评审会的用户体验洞察。

01

评测集正在变成一份用户研究：3,995 人决定了「什么任务值得测」

OpenAI 发布 LifeVal，用数千名 ChatGPT 用户的反馈确定个人助理最该帮忙的生活任务。任务清单不是由工程师凭直觉挑选，而来自「人们如何分配时间」的研究，以及一份 3,995 人的问卷，覆盖找托育、办政府手续、管理个人财务等真实场景。 公开结果中，GPT-6 Astra 在 16 项任务里有 10 项拿到 100%，平均 80.6%，其中包括为丢失的订婚戒指找到同款、退订邮件列表、得州食品补助文书（98.7%）、为糖尿病家人做饮食计划（90.4%）和核对 LSAT 答案（88.7%）。

对研究团队而言，这份 benchmark 的价值不在分数，而在抽样逻辑：评测单位从「模型会不会做题」变成「用户生活里最耗时的麻烦」。当任务由时间预算和人群问卷共同定义，用户研究就不只是需求前的洞察，而是直接参与模型验收标准的设计。 需要保留的怀疑是：这些是厂商自报的「最佳记录」成绩，任务如何选择本身，也会决定哪些能力看起来已经被解决。

来源：OpenAI · LifeVal · The Rundown AI · LifeVal 结果表

02

95.9% 的记忆不是用户要求记的：ChatGPT 的「算法自画像」被拆开

一篇被 ACM Web Conference 2026 接收的论文《The Algorithmic Self-Portrait: Deconstructing Memory in ChatGPT》，利用 GDPR 赋予用户的数据访问权，从 80 名真实用户处拿到了完整对话记录与系统存储的全部记忆：1058 段对话、22971 轮交互、2050 条记忆条目。 研究者用「记住 / 注意 / 保存 / 忘记」等触发词逐条比对，发现只有 4.1%（84 条）是用户明确要求写入的，其余 95.9% 由系统自行判断「这对未来对话有用」后单方面写入。

这意味着个性化记忆的默认状态是「系统替你决定什么值得记住」，而不只是「记住你说过的话」。对体验设计的直接要求是：记忆条目要能解释来源——来自哪段对话、为什么判断有用；要能逐条查看与撤销；对敏感推断应设置更严格的默认值。 用户需要的不只是「删除」按钮，而是对「它认为我是谁」的可见性与申诉权。

03

「AI 味」成了可识别的界面缺陷：先给结构，再让 AI 生成

一篇被 1.3 万人收藏的 Vibe Coding UI 避坑清单指出，AI 生成的界面往往「一眼就能认出来」：蓝色渐变、Inter 字体、线性图标、清一色圆角卡片。作者的核心方法不是反复改提示词，而是先改变输入：用 Excalidraw 只画方块和线条的线框图，截图后让 AI「按这个结构实现」； 视觉参考也按组件给——导航栏、价格卡片、首屏、页脚各截一张，而不是整页丢过去。

这背后是一个朴素结论：AI 擅长临摹，不擅长想象。当生成成本趋近于零，界面质量的分水岭前移到「设计意图是否被表达清楚」——信息层级、组件边界、品牌约束，以及明确不要什么。 设计师的交付物因此多了一层：不只是稿子，而是一份能让生成器稳定复现意图的约束说明。

04

注意力成了 Agent 产品真正的界面：TRAE 宝把「项目」从会话里拿出来

TRAE 上线开发者个人助理「TRAE 宝」，分全局与项目两级：全局助理接收需求、跨项目读取历史任务与产物、拆分派活并汇总；项目助理负责具体执行会话。它支持绑定微信、飞书，用户在聊天里就能发起任务、查看进度；单个项目内存在多个 Session 时，也可「打开会话」下钻。体验作者的判断很直接：AI 能并行完成的任务越来越多，但人能跟进的活跃会话通常只有 3 到 5 个。

这类产品真正设计的对象不是「任务列表」，而是「委托关系」：哪些事可以放手、现在进行到哪一步、何时需要我拍板、出了问题如何一键收回。同一时间，腾讯 QClaw 从公测到宣布停服只用 188 天，并把用户数据迁移至 WorkBuddy——个人助理赛道的产品生命周期正在缩短，界面也必须为「迁移与退出」设计一套体面的体验。

05

情绪价值从「角色」走向「被看见」：种花、AI 猫狗与互动叙事

少数派介绍的 Floria 把情绪记录变成「种花」：用户写下心境，可附图片或语音，应用自动回复并总结思绪；经用户授权后，一只「小蜜蜂」会把改写成第三人称的情绪摘要带到别人的花园，可能收到陌生人的回应，也可以选择只留在自己的花园。 与此同时，AI 宠物内容正在成为流量收割机：抖音账号「干嘛猫」5 条视频累计播放超 3000 万，《AI猫咪演绎人生系列》更新 127 集、播放超 4.5 亿，留言者多为 20—30 岁年轻人。

另一条线是互动叙事的代际更替：Character.AI 进入破产重组，而 OOC 以约 7000 万美元 ARR 成为新样本，行业描述的变化是「从用户输入转向 AI 帮用户进入故事」——聊天本身是费力的，产品要把用户送进情境。 三者共同指向一种设计转向：情绪价值不来自更大的模型，而来自被见证、可保持距离，以及明确的分享授权。

02

设计趋势洞察

两个正在发生的转向：生成之前先约束，陪伴之前先授权。

Design Trend 01

从「生成界面」到「约束设计」：AI 味本质上是输入质量问题

Vibe Coding 暴露出的同质化，只是表层。更有价值的信号来自两套已经跑起来的工作流：它们都不再问「AI 能生成什么」，而是先定义「AI 必须在什么边界内生成、又凭什么被验收」。

案例一：Figma 的 PM OS——把流程写成可复用的 skill

Figma 增长产品经理 Ezra Mechaber 把个人 Claude Code 配置扩展成 PM OS：一个共享仓库，沉淀 31 个 skill，供 Figma 约 60 到 70 名产品经理使用。其中最完整的是 AutoXP——三个由 Slack 触发的 Cursor 自动化，分别扮演数据科学家、UX 文案和工程师，自动定位流失点、写文案、提交 PR，并在同一线程汇报。

这套东西的关键不是「Agent 会写 PR」，而是把产品判断拆成了可复用的环节：发现问题的口径、文案的语气约束、实验的分流规则，都被写进 skill。设计经验第一次以「可执行约束」的形式被组织，而不是停留在文档和口头评审里。

案例二：大淘宝 D2C——给 AI 装上眼睛再验收

淘宝 D2C 团队面对的是另一个常见失败：AI 生码后信心满满地报告「卡片已完成」，推到真机才发现布局错位、badge 圆角被截、价格符号与数字没对齐——AI 没有眼睛，看不到真机渲染结果。团队的做法是构建端上 UI Harness，让 AI 走完「生码—编译—三端真机验证—自动修复」的闭环。

他们给出的公式是：质量 = 输入约束 × 生成约束 × 验证闭环。确定性流程下沉到 CLI 骨架，AI 只保留少量推理决策点；验证层融合像素 diff、DOM 树对比，并辅以交叉验证与独立门禁，防止「假交付」。这和 Vibe Coding 的线框图方法指向同一件事：AI 的输出上限，由人给的约束质量决定。

给设计团队的四条可执行建议

  • 先写意图简报：目标用户、核心任务、信息层级、品牌语气、明确不做什么，一页纸即可。
  • 线框图先于提示词：用最粗糙的结构图替代长段文字描述，让 AI 从「想象」切到「临摹」。
  • 参考按组件给：导航、卡片、空状态分别给样例，避免整页信息过载导致的风格漂移。
  • 把验收信号写进需求：像素 diff、DOM 对比、无障碍检查、真机截图，和视觉稿一起交付。
「AI 擅长临摹，但不擅长想象。」——当生成变得便宜，真正稀缺的是清楚的意图与可靠的验收。
对研究员的提示：当设计交付物从「一张稿」变成「一组约束 + 验收信号」，可用性测试也应同步升级——不只测界面，还要测这套约束是否让生成结果稳定复现了设计意图。

Design Trend 02

陪伴式界面的三条设计线：见证、距离与授权

从情绪日记到 AI 宠物，再到互动叙事，产品正在从「帮用户完成任务」扩展到「接住用户的情绪」。但真正决定体验好坏的，不是拟人程度，而是三个更具体的设计变量。

见证：先接住情绪，再给建议

Floria 的第一步不是分析或建议，而是自动回复并总结思绪，把用户散落在几百字里的感受收拢成一个可被看见的形状。用户的原话是：「写完之后还是会陷入一种低迷的状态：我的情绪没有被看见。」这句话点出了情绪类产品的核心任务——不是解决问题，而是提供被理解的证据。

距离：亲密感需要一个安全的缓冲区

Floria 把情绪摘要改写为第三人称，再让「小蜜蜂」带到其他花园；用户也可以选择不发送。AI 猫狗则用动物形象和幼儿声线制造「比现实宠物更可爱」的距离感，让 20—30 岁的年轻人可以安全地投射依恋。两者都在说明：情绪产品不能只有「更懂你」，还要允许「不被完全看穿」。

授权：每一次外溢都应该是可撤回的动作

OOC 的叙事转向提供了另一个参照：聊天本身是费力的，产品要把用户送进故事，而不是要求用户持续输入。但越是被动地被带入情境，越需要明确的边界——用户知道哪些内容会被分享、以什么形式呈现、谁能看到、如何收回。

  • 先反映后建议：首屏先复述用户表达，再提供行动选项，降低「被评判」感。
  • 默认私密，分享显式：任何跨用户的内容流动都应是用户主动触发，并显示对方将看到什么。
  • 改写而非原文外传：第三人称摘要既保护隐私，也降低社交压力。
  • 退出不惩罚：不发送、不连续签到、不公开，都不应触发愧疚式提醒或功能降级。
情绪价值不来自更像人的模型，而来自「我被看见了，同时我仍然安全」。
评审时可以直接问：这个产品在用户最脆弱的时刻，给了他控制权，还是只给了他陪伴？

03

产品体验点评

两个案例：一个在管理人的注意力，一个在把推荐的解释权还给人。

产品体验 Agent / 生产力

TRAE 宝 × Buddy One：当产品开始管理「人的注意力」

用户痛点：不是缺 Agent，而是缺一个能管住 Agent 的人

以 Session 为中心的 Agent 产品把任务越堆越多：置顶、按项目分组、普通任务列表混在一起，用户找一次历史会话就要翻很久。体验作者给出的约束很具体——人的注意力通常只能同时跟进 3 到 5 个活跃 Session。任务并行度可以无限增长，但管理注意力的人没有变。

设计解法：两级助理 + 统一上下文

  • TRAE 宝的全局层：接收一句话需求，跨项目读取历史任务、对话与产物，自行拆分派活、盯进度、主动汇报；用户可在微信或飞书里拍板。
  • TRAE 宝的项目层：每个项目一个专属助理，按依赖拆子任务并行执行，结果汇总回项目层；需要细节时再「打开会话」下钻。
  • Buddy One 的上下文层：腾讯把文档、会议、ima 知识库、网盘与 Agent 串在同一账号下，账号、上下文、积分通用；一次提问可同时检索多处，并标注每项结果的出处。

体验评估：好的部分与真正的风险

好的部分在于「渐进披露」：默认只展示结果与需要拍板的节点，把执行细节折叠到二级会话；IM 入口降低了发起成本，出处标注则缓解了「AI 说的能不能信」。WorkBuddy 团队引用的调研也说明需求真实存在——98 家受访企业中，只有 10.2% 把 AI 用在核心业务流程，37% 计划把四分之一试点推入生产环境，差距正在「上下文」而不在模型。

风险同样明显。委托越深，权限越难解释：Agent 能读哪些项目、能改哪些文件、能花多少额度，必须在任务卡上可见；并行任务越多，通知越容易变成新的噪音；失败时的恢复路径、以及产品停服时的迁移体验（QClaw 的 188 天就是现实案例），都应当作为一等功能设计。 一个可落地的检验标准是：任务卡能否用五个状态说清楚——等待中、执行中、需要你决策、已完成、失败可恢复。

产品体验 推荐 / 内容

HackerTube：当推荐流让人失望，用户干脆自己重做一个

事件：两小时，把「不信任的推荐」换成「可追溯的清单」

周五晚上 11 点，Karpathy 打开 YouTube 想找视频，首页却全是夸张封面和看过无数遍的老话题。第二天，他用 Claude Opus 5.5 的中等推理强度，只花两个小时做了一个 HackerTube：保留 YouTube 的完整网页布局，但推荐源换成了 Hacker News 二十年来 4300 万条评论中反复被推荐的 6,454 个视频。

详情页不只展示视频，还展示来自 HN 的评论、有多少位 HN 用户推荐过、以及在什么时间被推荐。个性化推荐依然存在，但它的依据从「平台的黑箱行为预测」变成了「一群人公开的推荐记录」。

体验解读：四个被重新摆上台面的界面要素

  • 控制感：用户不再只能训练算法，而是可以直接选择推荐语料的来源。
  • 可追溯性：「为什么给我看这个」有了具体答案——因为有多位 HN 用户在多年前推荐过它。
  • 熟悉感：复刻 YouTube 的布局降低了迁移成本，用户无需重新学习一套界面。
  • 反参与循环：静态的、被反复推荐的语料，天然绕开了「越点越极端」的实时反馈回路。

边界与启示

这不是一个可规模化产品：它依赖 YouTube 元数据接口，版权与稳定性都未解决，也没有验证过留存。但它是一个高质量的用户研究探针——当用户宁愿花两小时自己搭一个替代品，说明痛感已经超过了迁移成本。 对做推荐的产品团队，值得问的不是「如何让推荐更准」，而是「用户能否看见推荐的理由，并在不满意时换一套理由」。

研究方法论

两个可以直接借鉴的抽样与取证方法：让用户交出自己的数据，让时间预算决定研究任务。

方法 01 · 记忆审计

把「数据访问权」变成研究工具：一次 AI 记忆审计怎么做

《The Algorithmic Self-Portrait》提供了一套可复制的研究路径：不猜测模型如何记忆，而是让用户行使数据访问权，拿到系统保存的全部记忆，再逐条追问「它是怎么来的」。研究团队用 80 名用户、2050 条记忆做触发词编码，得到了「95.9% 由系统单方面写入」这一结论。

  • 招募数据捐赠者：明确研究目的与数据范围，签署知情同意；样本 80 人属于自选择样本，结论应表述为「在这批用户中」。
  • 合法获取数据：通过 GDPR 数据访问请求导出对话与记忆；在中国语境下可对应《个人信息保护法》的查阅、复制权。
  • 建立编码框架：按来源（用户显式要求 / 系统推断）、内容类型（偏好、关系、健康、工作）、敏感度分别编码。
  • 做成员核对：把系统生成的画像回放给用户，问三个问题：这像我吗？我愿意被记住吗？我希望它怎么改？
  • 安全与退出：本地加密存储、去标识化、允许随时撤回；对外只发布聚合结论与脱敏示例。

这套方法的价值在于把研究单位从「用户说了什么」推进到「系统认为用户是谁」。它同样适用于推荐画像、客服标签、会员分层等任何存在隐性建模的产品。

方法 02 · 任务抽样

用「时间预算」抽样任务，而不是用「好测的任务」抽样

LifeVal 的任务池来自两个来源：人们如何花费时间的研究，以及一份 3,995 人的问卷。这避免了评测中常见的偏差——只测容易打分、容易演示的任务，却漏掉用户真正耗时、真正焦虑的琐事。最终进入评测的，是为丢失的戒指找到同款、退订无尽邮件、填写政府补助文书、为患病家人做饮食计划这类「不酷但真实」的任务。

  • 先画时间地图：用时间使用调查或日记法，找出目标人群在生活行政、照护、财务上实际投入的时间。
  • 再做人群验证：用代表性问卷确认哪些麻烦最普遍、最希望被代劳，而不是由团队内部投票决定。
  • 把任务写成脚本：保留真实约束——截止日期、材料缺失、家人意见冲突、错误信息的干扰。
  • 用 rubric 而非单一对错：分别记录完成度、正确性、可解释性与用户是否愿意再次委托。
  • 报告失败模式：比平均分更有价值的是「在哪一步失败、失败后用户是否知道、能否恢复」。

需要提醒的是，厂商公布的 80.6% 平均分与「最佳记录」并非独立复现结果；任务选择会直接决定分数上限。研究团队若要引用，应优先借鉴其抽样逻辑，而不是把分数当作能力结论。

来源：OpenAI · LifeVal · The Rundown AI · LifeVal 结果表
