◈设计趋势洞察

趋势一：Agent 架构催生"无界面"体验设计

交互范式 系统智能

华为在 HDC 2026 上展示的鸿蒙智能体框架 2.0，让小艺从语音助手升级为"长在操作系统里的智能体"。演示场景中，用户只需说一句"我下午要去会展中心参加会议，需要提前 20 分钟到"，小艺就能自动串联日程、地图、打车、闹钟等多个独立应用完成整条任务链路。这与当前主流"用户打开 App → 寻找服务"的交互逻辑形成鲜明对比。

更具突破性的是追觅旗下 Eclix 品牌预告的"没有 App 的 AI 手机"——Project Quasar 将以 AI Agent 为原生系统内核，主界面不再显示传统 App 入口，用户主要通过语音与系统交互，由 AI 直接调用原子化服务。如果这种形态成真，移动 UX 的核心问题将从"信息架构与导航设计"转向"意图理解、任务分解、反馈透明与信任设计"。

对 UX 研究的启示：研究者需要开始建立"Agent 时代"的用户心智模型研究框架。例如：用户如何感知一个无形的 Agent 在替自己操作多个服务？用户需要怎样的进度反馈与撤销机制？当出错时，用户归因于 Agent、系统还是背后的某个 App？这些问题的答案，将决定下一代操作系统的体验下限。

趋势二：AI 辅助设计从"提效工具"升级为"设计协作者"

AI 设计 设计系统

宝玉在讨论 Claude Design 时指出，AI Agent 辅助设计后，设计师的角色正在从"亲自调像素"转向"用文字指令指挥 Agent 去改"。当设计系统足够完善时，按钮圆角、字号、间距等原本需要反复微调的属性，可以由 Agent 自动遵循规范完成。这不仅改变了设计执行方式，也改变了设计团队的协作结构。

但这种转变有一个关键前提：设计系统必须真正被用起来。否则 AI 会生成 3px、5px 这类随意值，反而增加返工。同时，方向和验收仍然是人的工作——Agent 负责执行，设计师负责判断。这意味着未来 UX 设计师的核心竞争力，可能从软件熟练度转向问题定义能力、审美判断力和对设计系统的治理力。

对 UX 研究的启示：可以开始研究"AI 协作者"场景下的设计师工作流程：设计师如何与 Agent 沟通设计意图？ Agent 的哪些输出会被接受、哪些会被拒绝？设计系统在不同团队中的 AI 可用性差异是什么？这些研究将直接影响设计工具的产品形态与技能培训方向。

◇产品体验点评

案例一：Claude Design 降低原型设计门槛，但需警惕"AI slop"

原型工具 生成式 UI

Claude Design 让用户用一句话描述想要的 App，就能生成交互原型，点哪里都有反馈，乍看像真实应用。这与 Figma 等静态设计工具不同——它直接产出了可感知的行为与反馈，更接近用户研究的"原型测试"场景。对于产品经理和 UX 研究员来说，这意味着可以在需求早期就进行低成本的用户测试。

但风险同样明显。Zara Zhang 在讨论 vibe coding 时专门提到"如何防止 AI slop in design"——AI 生成的设计可能看起来完整，却缺少真正的用户洞察与品牌一致性。当人人都能生成界面时，差异化将来自设计师的品味、对用户的理解，以及对设计系统的坚持。正如 Paul Graham 所预言："在 AI 时代，品味会变得更加重要。"

实践建议：将 Claude Design 类工具用于早期概念验证和用户测试原型，但不要让 AI 替代用户研究。在生成原型后，仍然需要进行真实用户访谈、可用性测试和启发式评估，确保设计解决的是真实痛点而非"看起来对"的问题。

案例二：Zynga 创始人"Proven, Better, New"框架的 UX 价值

产品方法论 用户验证

Mark Pincus 在 Lenny's Podcast 中分享的框架值得所有 UX 从业者回味：先复制已被市场验证的行为（Proven），再把它做得明显更好以至于 10/10 用户都说"f*ck yes"（Better），最后才加入最小的新元素（New）。这与很多团队"先创新再找用户"的路径截然相反。

这个框架本质上是一种用户中心的产品策略：它要求团队先理解用户已经熟悉什么、想要什么，再在熟悉的基础上做可感知的改进。Pincus 的名言"你的直觉在 95% 的时候是对的，你的想法在 75% 的时候是错的"也提醒我们：用户研究的价值不在于验证创始人想法，而在于把直觉和具体想法拆开，把创新区缩小到可被快速验证的范围。

实践建议：在产品规划阶段引入"Proven, Better, New"评估：这个功能对应的是已被验证的用户行为，还是我们假设用户需要的新行为？如果是后者，是否有更小范围的验证方式？同时，把"10/10 用户会说 yes"作为体验改进的验收标准，而不是"比竞品多一个功能"。

◉研究方法论

方法：用 AI 自动抓取与分析 App Store 用户评论

用户反馈 AI 辅助研究

向阳乔木分享了一套实用 workflow：输入任意 App 名称，自动抓取 App Store 用户评价，再用 DeepSeek 做信息挖掘，输出四类对产品团队有用的信息：用户在夸什么、骂什么；哪些问题与版本更新相关；哪些反馈代表产品机会；以及可视化图表。该工具预计下周开源。

这对用户研究的价值在于：它把散落在应用商店的海量定性反馈，快速转化为结构化的产品洞察。传统上，这类分析需要研究者手动抽样、编码、归类，耗时数天；AI 的介入可以把这个过程缩短到小时级。但研究者仍然需要判断：AI 归类是否准确？哪些"骂声"反映的是真实痛点，哪些是噪音？以及如何将洞察转化为可执行的产品建议。

实践建议：将此类工具作为用户研究的"第一站"——在正式访谈前快速扫描评论，识别高频主题与情绪分布；在访谈后用其补充量化视角。但要保持批判性：AI 可能遗漏语境、过度简化情绪，或把 sarcasm 误判为 praise。最终洞察仍需人来做。

方法：LLM 组合与路由可能成为研究质量的新杠杆

模型路由 洞察合成

elvis 提出"LLM Council"概念，认为不同模型各有所长，关键在于如何组合它们。OpenRouter 推出的 Fusion API 也试图通过并行调用多个模型并由 judge 模型合成最终答案，以更低成本达到高端模型效果。

对用户研究而言，这开辟了一条新路径：在做大规模文本分析、情感识别、主题建模时，不必依赖单一模型，而是可以根据任务类型路由到最合适的模型，甚至让多个模型互相校验。例如，一个模型负责提取主题，另一个负责评估情绪强度，第三个负责发现矛盾观点。这种"多模型协作"可能比单模型输出更稳健。

实践建议：在研究工具选型时，不要把"用最贵的模型"当作唯一标准。可以尝试根据任务复杂度设计模型路由策略：简单分类用轻量模型，复杂解读用强模型，关键结论用多模型交叉验证。同时记录不同模型在研究任务上的表现，建立团队自己的"模型使用手册"。
