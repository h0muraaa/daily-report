深度分析

两个会改变技术决策前提的变化
深度分析 01

当 Agent 成为最大开发者，Git 成了新的容量瓶颈

OpenAI 在 11 月 2 日发布 Pando，一套兼容 Git 协议与客户端的新后端。Codex 把 OpenAI 的 monorepo 推到“多分支并发写 + 海量并发读”的极限后，旧系统从 2025 年底开始慢推慢拉、合并失败，可靠性一度低于 90%。Pando 没有改变工程师和 agent 的 git push / git pull 习惯，而是换掉服务端：单条 ref 串行化、全仓只保证因果一致，packfile 进入对象存储并在多个读者之间复用，读侧像 CDN 一样下发。

结果相当具体：中位推送延迟下降约 80%（约 5 倍），日均分发近 1 PB Git 数据；仓库中位 pack 小于 20 KiB、P99 小于 3 MiB，缓存命中率超过 99%，标准机器可以跑满 10 Gbps。OpenAI 称从立项到生产约 10 周，其中大量代码由 Codex 编写，并把部分修复回馈给了 Git 官方。

Anthropic 选了另一条更激进的路：自研 Scion，连客户端和服务器一起替换，提交、合并、代码审查、搜索和 CI 都在新系统上完成。官方口径是 CI 拉代码从分钟级降到秒级，服务器 CPU 与内存占用降到原来的 1/200；代价是必须换掉整套工具链，因此只适合巨型代码仓库，其他公司很难直接复用。

三个判断

  • 瓶颈正在从“运行时”转向“变更吞吐”。 过去十年平台工程优化的是部署、扩缩容和可观测性；当 agent 让代码变更量级上升，最先崩的会是 push/fetch、CI 排队、代码评审队列和制品库。
  • 不必自研，但必须建模。 跟踪单仓大小、分支数、日推送量、P95 延迟、CI 队列深度和评审周期；按 agent 并发提升 3—5 倍做容量规划，而不是按人头规划。
  • 平台团队的 KPI 需要重写。 从“可用性 99.9%”转向“开发者等待时间”“agent 任务吞吐”和“每次代码变更成本”。否则 agent 带来的产能，会被基础设施排队吃掉。
对多数企业的现实动作：先启用浅克隆/稀疏检出、远程缓存、CI 分片和合并队列，对 monorepo 做一次容量压测；只有当日推送量达到万级、单仓达到数十 GB 时，才值得评估后端改造。自研 Git 是 OpenAI 和 Anthropic 这种规模的解法，不是普遍解。

深度分析 02

Anthropic 的 8,954 亿美元账单：AI 单位经济学开始反噬

Anthropic 的 S-1 更新把 AI 行业最敏感的两个数字放在了一起：收入增长与算力承诺。收入仍在高速增长，但环比增速腰斩；算力支出占比上升，经营利润重新转负。这不是一家公司的财务问题，而是企业 AI 采购环境的先行指标。

指标数值含义
2026 Q3 收入169.56 亿美元从 2025 Q1 的 3.76 亿美元增长而来
环比增速47%（Q2 为 144%）增长明显减速
经营利润-5.67 亿美元（Q2 为 +9.74 亿）盈利只维持了一个季度
算力与基础设施支出99 亿美元，占收入 58%环比增长 77%，占比从 48% 上升

价格折让约 6 亿美元竞争性降价侵蚀收入
IPO 募资拟向日本投资者募至多 35 亿美元资本市场继续补充弹药

当模型厂商的算力支出占收入 58%、承诺额又是季度收入的数百倍时，成本一定会以某种形式传导给客户：更高的 token 价格、更严格的限流、更贵的优先级与缓存、或者更激进的私有化部署报价。企业如果把 AI 预算简单建模为“调用量 × 单价”，很容易低估未来的账单波动。

另一方面，开源权重正在给采购方提供议价筹码。Mistral Large 4 以 1.05T 开放权重、100 万 token 上下文进入 Open Math OS；美团 LongCat-2.5 用 1.6T 总参、约 48B 激活的 MoE 架构面向长程 agent 任务，并针对国产算力做了 W4A4 推理优化；Kimi K3 通过 Amazon Bedrock 提供印度境内推理。模型能力差距在缩小，部署形态在分化。

Revolut 的案例给出了一个可参考的盈亏平衡点：约 2,000 名工程师迁移到自托管 GLM，56 张 B200，混合成本约 0.30 美元/百万 token，约为原供应商的十分之一，工程交付周期改善 70%。但这个数字没有计入 GPU 折旧、机房、运维和模型迭代的人力；自托管只在推理量足够大、负载稳定、数据敏感度高时才成立。

推理供给端仍在扩张。Fireworks 宣布 2027 年在欧洲上线 NVIDIA Vera Rubin 与 Grace Blackwell 容量，并推出 1,500+ tokens/s 的 Ultrafast、多日 prompt caching 和后台模式。供给增加会压低单价，但不会自动降低“每任务成本”——后者取决于缓存命中率、模型路由、推理档位和 agent 步数。

CTO 的采购检查清单：
  • 合同：价格调整机制、模型退役时间表、迁移协助、数据可携带。
  • 架构：模型抽象层、路由、缓存、评测集，避免单点锁定。
  • 财务：看 cost per task，而不是只看 per token；把缓存命中率和 agent 步数纳入看板。
  • 风险：至少两家可替换供应商，外加一套开源权重备选。
  • 组织：指定 AI 单位成本的 owner——Uber 已让 Distinguished Engineer 负责 AI spend。

平台工程

大规模 ML 平台的瓶颈从“算得动”转向“改得动”

Meta 的广告排序单次请求需要超过 2 万个特征，F3 把特征编译成单一合并图降低了计算成本，但也让整张图成为发布单元，一处失败就阻塞全链路。F3 Lightning 把特征发布与共享执行解耦，支持每个特征独立编译、验证、部署和回滚，同时保留原先的效率收益。这是“独立可部署性”在超大规模 ML 平台上的又一次胜利。

CTO 视角

本周可以推动的五件事

  1. 给开发者基础设施做一次“Agent 压力测试”

    以当前 agent 并发量的 3—5 倍为假设，压测 push/fetch P95、CI 排队时长、代码评审周期、单仓大小与分支数量。找出最先饱和的环节，优先用远程缓存、浅克隆、CI 分片和合并队列解决，而不是一上来就重写平台。

    衡量：agent 并发提升 3 倍时，P95 延迟不翻倍

  2. 建立 AI 单位经济学看板，并指定唯一 owner

    把 cost per task、缓存命中率、tokens per merged PR、模型路由占比和失败重试次数做成周度看板。Uber 已由 Distinguished Engineer 负责 AI spend，这说明 AI 成本治理需要架构级别的负责人，而不是散落在各团队的账单截图。

    衡量：月度 cost per task 与预算偏差可解释

  3. 启动一次 build vs buy 复算，把开源权重纳入备选

    对高稳定、高敏感、高量的推理负载，评估 Mistral Large 4、LongCat-2.5、Kimi K3 等开放权重方案；以 Revolut 的 56 张 B200、0.30 美元/百万 token 作为参考锚点，但必须计入 GPU 折旧、机房、运维与模型迭代人力。结论不一定是要自托管，而是让采购谈判有真实替代方案。

    衡量：至少一类核心负载具备可切换的开源备选

  4. 把安全左移升级为“每次 push 的自动审计”

    评估推送级安全审查产品，强制 MFA/Passkey 与设备绑定会话，提高内部漏洞赏金，并针对插件/MCP 采用 IdP 托管授权，禁止个人手工 OAuth。微软 Titan 的默认 admin 事件提醒我们：AI 时代最危险的往往不是模型漏洞，而是最老套的身份与配置问题。

    衡量：生产分支每次变更都有自动安全结论

  5. 重写架构与人才的责任边界

    明确“agent 写实现，人负责边界、契约与风险”；把架构评审、领域建模、评测设计和故障归因列入晋升标准。用公开薪酬基准校准 AI 技能溢价，避免为“会用工具”支付长期溢价，而真正稀缺的是能定义问题、设定约束并对结果负责的人。

    衡量：晋升材料中架构与风险责任可被验证
