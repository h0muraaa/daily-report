Kubernetes网络

从零手撸 Kubernetes CNI：理解容器网络的本质

对于大多数开发者来说，CNI 是 Kubernetes 中最熟悉的陌生人：每天依赖它转发 Pod 间的每一个数据包，却很少拆开看过。freeCodeCamp 的这篇长文不依赖 Helm 安装 Cilium 或 Calico，而是直接用 Linux 网络原语（veth、bridge、路由表、iptables/nftables）一步步复现 CNI 的行为。

文章的价值在于建立准确的心智模型：Pod 网络命名空间如何创建、veth pair 如何桥接、SNAT/DNAT 在什么时候发生、为什么跨节点通信需要 overlay 或 underlay 路由。理解了这些，排查 "Pod 能 ping 通 IP 但 DNS 不通"、"Service 负载不均"、"网络策略不生效" 这类问题才会有的放矢。对于想在云原生基础设施上更进一步的开发者，这篇文章比直接背 CNI 配置清单更有效。

实践要点：不要只学 YAML 抽象；用 ip netns、iptables -t nat -L 和 tcpdump 在测试集群里手动复现一次 CNI 行为，网络排障能力会有质变。

RAG检索

HyDE：用"假设文档"弥合查询与文档之间的语义鸿沟

标准 RAG 的流程是：把用户问题向量化，然后去向量数据库里找最相似的文档块。问题是，用户提问的方式和文档里的答案段落往往写法迥异。例如用户问 "为什么我的 AWS Glue job 变慢了"，而文档里对应的章节标题可能是 "Optimizing Spark executor memory"。直接嵌入问题会漏掉这些关键块。

HyDE（Hypothetical Document Embeddings）的做法是：先用 LLM 根据问题生成一段"假想的理想答案"，再用这段假想答案去检索，而不是用原始问题。这样查询向量会更接近目标文档的语义空间，从而显著提升召回率。文章还讨论了 HyDE 的适用场景与陷阱：在事实性要求高的领域，必须对生成的假设文档做后校验，防止幻觉答案污染检索结果。

落地建议：对于技术文档、FAQ 类 RAG，HyDE 是值得优先尝试的低成本优化；同时保留原始查询的并行检索链路，通过重排序把两者结果融合，能兼顾覆盖率和准确性。

04 实践指南

供应链安全

Dependabot 冷却期：给自动更新加一道安全闸门

依赖自动更新工具的核心假设是"新版本更安全"，但供应链攻击正在利用这一假设。GitHub 的应对方案是为 Dependabot 引入冷却期，让恶意版本在自动化流程进入你的仓库前有机会被社区发现并撤回。

对于使用其他依赖管理工具的团队，可以借鉴这一思路：在 CI 中延迟自动合并依赖更新 PR，或对新版本设置最小"存在时间"门槛；对核心依赖启用 lockfile 审计与签名验证；把依赖更新 PR 纳入代码审查流程，而不是完全交由机器人自动合并。

SEO / AI 引用

AI 可提取性审计：让大模型更愿意引用你的网站

当 AI 助手回答问题时，它会从若干页面中抽取句子并标注引用。你的页面是否"可被提取"由 HTML 结构决定。作者通过实践发现，把仅用于 UI 卡片的 <h2> / <h3> 降级为保留 ARIA 语义的段落，能让首页可提取性评分从 65 提升到 100，且视觉和文案完全不变。

对技术博客、产品文档和开源项目主页来说，这意味着：用正确的标题层级表达文档结构、避免把装饰性文本塞进标题标签、保证关键信息出现在清晰的主题段落中。这些做法不仅服务 SEO，也服务 AI 摘要与引用。

Agent 工程

Harness Handbook：让编码 Agent 自己找到该改哪些文件

维护生产级 Agent 时，最大的痛点往往不是生成编辑本身，而是让 Agent 定位到与某个行为相关的所有文件。Harness Handbook 提出了一种三级映射：从运行时行为通过静态分析和 LLM 辅助结构定位到源码位置，再用 BGPD 工作流引导 Agent 从系统概览到相关阶段、函数和文件。

在 Codex 和 Terminus-2 的 60 个修改请求测试中，这种方法把规划胜率从 28.3% 提升到 38.3%，在另一组任务中从 26.7% 提升到 45.6%，同时减少了 planner token 消耗。对于正在构建或维护 Agent 框架的开发者，这提供了一套可复用的"行为到源码"定位思路。
