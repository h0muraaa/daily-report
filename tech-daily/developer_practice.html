SECURITYPHP 修复两个可未授权 RCE 的严重漏洞：8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 已发布

PHP 发布 8.5.12、8.4.27、8.3.36、8.2.35 四个维护版本，修复两个允许未授权远程代码执行（RCE）的严重漏洞。InfoQ 提到，Amazon 在补丁发布前四天就记录到了利用尝试；补丁当天，运维人员集中处理三个问题：自己到底跑没跑 PHP、应该从哪里拿包、以及怎么确认修复已经生效。

NUMERICSPyTorch、JAX、TensorFlow 的标准 Softmax / 交叉熵实现被指存在数值精度 Bug

Google DeepMind 首席研究科学家 Jonathan T. Barron 公布新研究，指出 PyTorch、JAX、TensorFlow 等主流框架普遍采用的 Softmax 与交叉熵标准实现里存在两个容易被忽视的数值精度 Bug。其中一个被命名为 Softmax Collapse：平时很难察觉，却可能在训练特定阶段悄悄改变梯度，造成 loss 突然飙升，甚至让模型已经学到的能力出现退化。

论文《A Fix for Softmax and Cross-Entropy》已于 10 月 22 日提交 arXiv，作者还包括 Dan Gnanapragasam 和 Michael Tschannen。研究称只需调整计算方式即可修复，无需提高浮点精度，也不需要重新设计损失函数；Barron 表示 Gemini 在实验与论文工作中承担了相当多任务。对训练团队而言，最务实的动作是把自己的 loss 异常与框架版本关联起来，并用 float64 参考实现做数值回归（见深读）。

CDNCloudflare 原生支持可配置 HTTP Vary：把内容协商拆成“源站声明 + 边缘规范化”

Cloudflare 在全球边缘网络原生支持可配置的 HTTP Vary 响应头，并通过 Cache Rules 向所有套餐开放。Vary 用来告诉缓存“源站在生成响应前检查了哪些请求头”；如果缓存直接照做，请求头里的空格、大小写、语言优先级顺序差异，就可能把同一资源拆成几十个变体。

Cloudflare 审计了约 5 万个热门域名、超过 1.2 亿条 HTTP 响应，发现近 3000 个源站会根据四个以上请求头生成不同响应，极端情况涉及数十个字段，直接后果是缓存命中率暴跌、源站负载上升。新能力把内容协商拆成两段：源站声明哪些头影响响应，Cache Rules 决定边缘在计算变体键前如何规范化、原样传递或绕过缓存，并可为未列出的字段设置兜底策略。

OBSERVABILITYAdobe 开源多租户 Prometheus 方案：用 prom-label-proxy 强制 namespace 边界

Adobe 工程师介绍了一套面向多租户 Kubernetes 的 Prometheus 自助查询方案：团队可以查看自己的 GPU 利用率、功耗等指标，又不会暴露其他团队的共享数据。难点在于中心化 Prometheus 可能包含数千个命名空间，直接开放查询会泄露数据，大量用户查共享存储又会带来性能与“吵闹邻居”问题。

方案是在用户与中心 Prometheus 之间放一个租户感知代理：请求先经 NGINX 与 kube-rbac-proxy 完成认证授权，代理识别租户、发现可用后端，并把查询限制在该租户命名空间。关键组件 prom-label-proxy 会在查询到达 Prometheus 前改写 PromQL、强制追加 namespace 约束；另有可选的按租户小实例。它解决的是“靠开发者自觉写对 namespace”根本不构成安全边界的问题。

深度技术解读

两条主线：数值正确性，与带权限的检索

当模型“越自信”梯度越错：Softmax / 交叉熵的隐藏数值 Bug

标准实现里的两个精度问题，为什么常规测试抓不到，以及怎么在自己的训练栈里加一条哨兵

这项研究最反直觉的地方是触发条件：问题不在模型“不会”，而在模型“太确定”。Softmax 把 logit 转成概率，交叉熵再衡量预测与标签的差距；当模型对某个类别极其自信时，概率会贴近 0 或 1，梯度计算涉及的两个相近数值相减，float32 的有效位数被迅速吃掉。论文报告的第一个 Bug 因此被命名为 Softmax Collapse——它改变的是梯度，而不只是最终 loss 的显示值。

论文称两个 Bug 都可以通过调整计算方式修复，不需要把整个训练切到 float64，也不需要重新设计损失函数。这很关键：如果修复要求全链路高精度，训练成本会直接翻倍；而“改计算顺序/公式”意味着框架可以在不牺牲吞吐的前提下打补丁。Barron 还提到 Gemini 承担了大量实验与写作工作，这本身也是 AI 参与科学研究的又一个案例。

// 为什么常规单元测试抓不到

大多数数值测试用的是随机初始化的小 logit，Softmax 输出接近均匀分布，数值条件很好，测不出问题。Bug 出现在训练后段：模型已经学会、logit 拉大、预测接近 one-hot，此时梯度里的精度损失才会显形。表现也容易被误判——loss 突然飙升常被归因于学习率、数据脏、优化器状态，而不是框架里的一个基础函数。

现象常见误判更稳妥的排查动作
训练中 loss 周期性尖峰学习率过高 / 数据批次异常固定随机种子，用 float64 参考实现复算同批次 loss 与梯度
模型越训越“自信”，评估反而退化过拟合 / 正则不足检查高置信 logit 区间的梯度误差，而不只看平均 loss
换框架或升级版本后行为变化随机性 / 硬件差异把框架版本写进实验元数据，做同权重前向/反向对账

// 一条可以马上加进训练代码的数值哨兵

下面的脚本不是复现论文 Bug 的完整用例，而是给训练代码加一个“高置信区间”检查：把同一组 logit 分别以 float32 和 float64 走一遍 Softmax + 交叉熵，比较 loss 与梯度的最大绝对误差。误差随 logit 放大而异常增长时，就值得怀疑当前框架实现。

# 数值哨兵：高置信 logit 下的 loss / grad 对账
import torch
import torch.nn.functional as F

torch.manual_seed(0)
target = torch.randint(0, 10, (8,))

# 人为拉大 logit，模拟训练后段“模型很自信”的状态
base = torch.randn(8, 10).requires_grad_(True)
with torch.no_grad():
    base.add_(torch.randn_like(base) * 8)

logits32 = base.detach().clone().requires_grad_(True)
logits64 = base.detach().clone().double().requires_grad_(True)

loss32 = F.cross_entropy(logits32, target)
loss32.backward()
loss64 = F.cross_entropy(logits64, target)
loss64.backward()

print("loss diff", (loss32.double() - loss64).abs().max().item())
print("grad diff", (logits32.grad.double() - logits64.grad).abs().max().item())

把它做成 CI 里的固定用例，比在事故后翻日志更划算：固定随机种子、固定 logit 量表，误差超过阈值就失败。真正需要框架层面修复的部分，等上游版本；但“知道自己的栈在当前版本有没有暴露”是团队自己必须回答的问题。

实践建议：① 在实验元数据里记录框架完整版本，而不只是 torch.__version__ 这类主版本；② 对分类任务增加高置信 logit 的梯度对账；③ 看到 loss 尖峰先别急着调学习率，先排除数值实现问题；④ 关注论文与框架的后续补丁说明，不要自行往生产环境打未经验证的 monkey patch。

带权限的向量检索：post-filter 丢召回、pre-filter 太慢，第三条路是“原生过滤”

Bridgewater 1 亿份带权限文档 + turbopuffer 4 亿向量，P90 约 120ms 的架构拆解

Bridgewater 的 AI 分析师需要检索私有文档，但每封邮件、每份备忘录、每条研究笔记都带着自己的权限。这不是“加一个 WHERE tenant_id = ? 就完事”的场景：权限既细又杂，且必须保证召回质量——漏掉一份该看的文档，分析师可能做出错误判断，比多查一次更危险。他们最初的搜索架构在 1 亿份带权限文档上直接失败。

// 两种直觉方案，各有一个硬伤

  • post-filtering（先检索再过滤）：先取向量近邻 top-k，再按权限剔除。实现简单，但召回不可控——如果前 k 条大多不可见，过滤后结果可能所剩无几；把 k 调大又会放大延迟与下游成本，而且仍然无法保证“该看到的都看到”。
  • pre-filtering（先过滤再检索）：先把候选集限制到用户有权访问的文档，再在子集里做近邻搜索。结果正确，但在大规模、权限组合复杂的场景下，候选集构建与索引遍历都很昂贵，延迟会随过滤条件变复杂而恶化。
  • native filtering（原生过滤）：把权限条件作为索引的一部分，在聚簇向量索引的遍历过程中直接跳过无权节点。它同时保留召回与延迟，这也是 turbopuffer 的方案：约 400 亿级向量规模下，跨 1 亿份权限文档的查询做到约 120ms P90。
# 反例：先取 top-k 再过滤，召回取决于“前 k 条里有多少条可见”
hits = index.search(query, k=100)
allowed = [h for h in hits if acl.can(user, h.doc_id)]

# 目标：把租户与 ACL 条件下推到索引遍历，而不是在结果上做减法
hits = index.search(
    query,
    k=10,
    filter={
        "tenant_id": user.tenant,
        "acl_groups": {"$in": user.groups},
    },
)

// 把“权限”当一等数据建模

真正难的往往不是索引，而是权限模型。文档权限可能来自个人、团队、项目、组织层级，还会随时间和继承关系变化；如果只在查询时临时拼 ACL，既容易漏，也很难做缓存。更稳的做法是在写入/更新时就把可过滤的权限标签算好，与向量一起进索引，并为权限变更设计增量更新路径。

同样的原则在其他系统里反复出现：Kepler 为 30 多万份 SEC 文档建引用注册表，让模型“引用数字但不写数字”，由确定性代码做算术，检索侧做租户隔离；Adobe 的 Prometheus 代理则在查询到达存储前强制注入 namespace 约束。三者都不是在结果返回后“再检查一下”，而是把边界前移到检索/查询入口。

做 RAG + ACL 的检查清单：① 权限标签在入库时生成，不在查询时猜；② 过滤条件下推到索引，不依赖返回后裁剪；③ 用带权限的真实查询集测 recall@k，而不是只看平均延迟；④ 缓存键包含租户与权限版本；⑤ 权限变更要有增量重建与审计日志；⑥ 对“无权访问”的查询做延迟与结果形态上的防侧信道处理。

工具推荐

今天就能装上试用的六项
Google ML Drift
一套引擎跑遍 OpenGL ES / OpenCL / Metal / WebGPU

Google 开源的跨平台 GPU 计算引擎，Apache 2.0 许可，面向端侧 AI 与机器学习推理。它把不同 GPU 硬件和底层图形/计算 API 的差异抽象掉，支持 OpenGL ES、OpenCL、Metal 与 WebGPU。

适合需要把同一份推理代码铺到 Android、桌面与浏览器的团队：过去往往要为 Metal、OpenCL、WebGPU 各维护一条路径，现在可以先在统一接口上做原型，再针对热点算子下探。端侧推理的瓶颈常在内存带宽与算子融合，建议上手先跑自己的模型与输入尺寸，而不是只看示例基准。

CLI-Anything（HKUDS）

01PHP 漏洞响应：先确认运行时，再确认包版本，最后确认进程已重启

未经认证的 RCE 不应进入常规迭代排期。先把“我们哪里在跑 PHP”查清：Web 应用、API、后台任务、容器基础镜像、Serverless 运行时、第三方 vendored 环境都算。然后按 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 或更高版本升级，并注意发行版仓库、Docker 镜像与语言版本管理器可能各自滞后。

  • 升级后重启 php-fpm / Web 服务，确认新进程加载的是新二进制。
  • 用 php -v、包管理器版本与容器镜像 digest 三重确认，不只看 CI 里的声明。
  • 对公网暴露面做一次资产扫描；无法立即升级的实例先加访问控制或 WAF 规则作为临时缓解。
  • 把“补丁发布 → 资产定位 → 升级 → 验证”的耗时记下来，作为下一次安全演练的基线。
📎 来源：InfoQ · PHP Patches Two Critical RCE Flaws That Were Already Under Attack

02给分类训练加一条高置信数值回归

Softmax / 交叉熵的精度问题说明：平均 loss 正常，不代表梯度正确。把深读里的 float64 对账脚本改成参数化测试，固定几组 logit 尺度（例如 ±2、±8、±16），分别比较 float32 与 float64 的 loss 和梯度误差；超过阈值就让 CI 失败，并记录框架版本与硬件。

同时调整排障顺序：遇到 loss 尖峰，先固定种子复算同批次，再查数据与学习率。若误差只在模型高置信阶段出现，优先怀疑基础算子实现，而不是模型结构。

📎 来源：arXiv · A Fix for Softmax and Cross-Entropy · 机器之心 · Softmax 隐藏 Bug

03Agent 架构先做减法：从“多子 Agent”回到“单循环 + skills”

Anthropic 的经验值得当成默认起点：新项目先用单 Agent 主循环，按需加载上下文与工具，把领域知识写成 skills；只有当任务需要并行、独立验证或权限隔离时，才拆子 Agent。拆分要有可量化的理由，而不是“看起来更模块化”。

  • 基线与候选方案用同一批真实任务对比质量、单任务成本与 P95 延迟。
  • 迁移时一次只并回一个负责路由/规划的子 Agent，观察品牌一致性、延迟与失败率。
  • 保留子 Agent 的场景：大规模并行检索、独立评审、需要不同权限边界的操作。

04AI 生成代码的 PR 卫生：把“能生成”变成“能评审”

Linux 基金会的数据说明，代码供给变多之后，维护者的评审带宽就是瓶颈。提交 AI 参与的改动时，至少做到：PR 小而聚焦、说明“为什么改”与验证方式、附带可复现的测试、避免顺手大改格式、不提交未运行的生成代码。对维护者而言，可以在贡献指南里明确 AI 辅助披露与测试要求，并用标签区分“需要设计讨论”的 PR。

衡量团队效率时也别只看 PR 数量：AI 让写代码快了 52%，但如果评审与返工同步上升，交付速度未必提升。更值得跟踪的是“从提交到合并的 lead time”和“合并后 7 天内回滚/修复率”。

05边缘缓存：用 Cache Rules 规范化 Vary，而不是任由源站“自由发挥”

先审计自己的 Vary 头：哪些字段真的影响响应？Accept 的大小写与 q 值顺序、Accept-Language 的优先级排列是否被原样计入缓存键？Cloudflare 提供三种动作——规范化、原样传递、绕过缓存——建议对语言与编码类头做规范化，对不影响内容的头直接忽略，只有确实需要逐字段区分时才原样透传。

验证方式很直接：上线前后对比边缘命中率、源站请求量与 P95 延迟，并抽查不同客户端头的响应正确性。不要为了追求命中率盲目 bypass，绕过缓存会把压力全部推回源站。

06多租户可观测性：隔离要落在代理层，而不是查询规范里

Adobe 的方案可以直接借鉴：在 Prometheus 前放租户感知代理，认证授权后由代理强制注入 namespace 约束，避免租户构造跨命名空间查询。实现上可以复用 NGINX、kube-rbac-proxy 与 prom-label-proxy，不必引入新的指标平台；GPU 团队则能自助查看利用率与功耗，及时处理“空转的昂贵卡”。

落地时补三件事：对代理本身做高可用与限流；记录每次改写后的实际查询用于审计；用压测验证“一个租户的复杂查询不会拖垮共享存储”。同样的模式也适用于日志、追踪与向量检索的租户隔离。
