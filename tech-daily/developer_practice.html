LlamaIndex LiteParse v2：Rust 重写，PDF 解析性能提升 100 倍
Rust / WASM

LlamaIndex 团队发布了 LiteParse v2.0，这是一个从零开始用 Rust 重写的 PDF 解析库。相比前代版本，新版本在解析速度上最高可达 100 倍的提升，同时保持了对 50 多种文档格式的支持。LiteParse v2 的最大亮点是多语言原生支持——除了 Rust 外，还提供了 Python 和 JS/TS 的原生包，以及一个自定义 WASM 包，使其可以在浏览器和边缘计算环境中运行。该库在准确性上也超越了其他开源无模型解析器（pymupdf、pypdf、markitdown、pdftotext 等）。对于需要处理大量文档的开发者而言，这意味着可以在客户端完成原本需要服务端才能胜任的解析任务。

OpenAI 推出 Secure MCP Tunnel：企业内网 MCP 服务器的官方安全接入方案
Security

OpenAI 发布了 Secure MCP Tunnel 功能，填补了企业级 MCP 部署的"最后一公里"安全空白。技术思路上采用了类似 ngrok 和 Cloudflare Tunnel 的"反向隧道"机制：在企业内网部署一个轻量级的 tunnel-client 程序，由它主动向外建立到 OpenAI 的加密 HTTPS 连接。当 ChatGPT 或 Codex 需要调用内部 MCP 服务器时，请求通过这条已建立的隧道传入内网，tunnel-client 将请求转发给本地 MCP 服务并返回结果。整个流程无需开放任何入站端口，也不需要配置 VPN 或防火墙规则，且与 OpenAI 的组织和 Workspace 权限体系打通。另外，tunnel-client 内置了一个名为 Harpoon 的 MCP 服务器，可以把内网的 REST 接口按标签暴露给 Agent 调用，但限制调用方不能随意选择目标。

GitHub Copilot 推出远程会话：从手机继续你的 CLI / IDE Agent 会话
AI Dev

微软开源 Webwright：终端原生的 Web Agent 框架，"代码即动作"
Web Agent

微软开源了 Webwright，一个"终端原生"的 Web Agent 框架。与传统 Agent "观察 → 预测点击 → 执行"的循环不同，Webwright 采用了"代码即动作"的设计哲学：让 LLM 直接编写 Playwright 脚本来操控网页。核心循环仅包含三个模块约 1000 行代码，无隐藏编排层。工作区作为状态容器——脚本、截图和日志保存在本地，浏览器会话可随时重建。这种模式的"副产品"是可复用的自动化程序，而非一次性的交互痕迹。在性能上，Webwright 达到了 SOTA 水平。对于习惯写测试脚本的开发者来说，这种"让 AI 写你本来就要写的代码"的思路可能比纯自然语言交互更可靠、更可维护。

LinkedIn 排查内核锁竞争导致的周期性系统冻结：eBPF off-CPU Profiling 实战
Kernel / eBPF

LinkedIn 工程师遇到了一种棘手的故障模式：用户 Feed 数据库周期性短暂不可用，随后自动恢复，但没有留下有用的日志或追踪信息。常规监控在这种"闪断"场景下完全失效。团队最终采用了一种创新的排查方法——基于 eBPF 的 off-CPU profiling（CPU 外分析）。与传统的 on-CPU profiling 不同，off-CPU profiling 追踪的是进程在等待什么（锁、I/O、调度等），而不是在 CPU 上执行什么。通过这种方法，工程师定位到了内核层面的锁竞争问题，这是导致系统冻结的根本原因。这个案例对于处理类似"幽灵故障"的开发者极具参考价值：当常规监控束手无策时，eBPF 提供的内核级可观测性可能是最后的救命稻草。

CHI-Bench 开源：75 个真实医疗工作流评测，最强 Agent 仅过 28%
Benchmark

AI Coding Agent 如何使用你的技术：Microsoft AX Stack 追踪分析

当你发布了一个 SDK、CLI 或 API，你知道开发者会如何使用它。但现在 AI Coding Agent 也在使用它，而且使用方式与人类完全不同。Microsoft 的 AX Stack 系列文章深入追踪了"开发者输入提示"到"Agent 生成代码"之间究竟发生了什么。

Agent 与技术的三种交互模式

Microsoft 将 Agent 与技术栈的交互归纳为三种路径：

  1. 读文档 — Agent 通过检索增强生成（RAG）读取你的官方文档、README、示例代码，然后基于理解生成调用代码。
  2. 调用 MCP Server — 如果你的工具提供了 MCP 接口，Agent 可以通过标准化的工具调用来使用它，获得结构化输入/输出。
  3. 凭记忆猜测 — 最坏的情况：Agent 既不读文档也不调用 MCP，而是基于训练记忆中的片段"脑补" API 用法，这往往是 bug 的温床。

开发者能做什么

文章提出了 AX Stack 框架，将 Agent 与技术栈的交互分为三层：

  • Model（模型层）：你几乎无法控制，包括模型选择、上下文长度、推理能力。
  • Harness（执行层）：Agent 的运行时环境——IDE 插件、CLI 工具、沙箱等。你可以选择优化自己工具在这些 harness 中的表现。
  • Extensions（扩展层）：你完全可控的层面——提供 MCP Server、优化文档结构、提供清晰的错误信息、确保 API 设计的 Agent 友好性。
实践建议：如果你正在维护一个开发者工具，现在就开始思考"Agent 友好性"——提供 MCP 接口、保持文档的结构化和可检索性、让错误信息包含可操作的修复建议。Agent 不会"像人一样"阅读整篇文档，它们更依赖结构化的快速扫描和精确的 API 契约。

京东 DongSQL V1.2.0：零售数据库内核的六大技术升级

京东自研电商数据库内核 DongSQL 发布了 V1.2.0 版本，这是继 2025 年 9 月 V1.1.0 发布后的重大迭代。新版本在热点行更新、主从复制、执行计划缓存、带量压测、海量表启动、SIMD 加速六个维度实现了突破。

核心优化点解析

1. 组提交单播通知（解决惊群效应）

在组提交过程中，follower 线程需要等待 leader 完成 binlog 刷盘。传统方式使用单一条件变量广播唤醒所有等待线程，高并发下产生严重的锁竞争。DongSQL V1.2.0 为每个线程分配独立的条件变量 THD::COND_wakeup_ready，将广播改为逐个单播唤醒，大幅减少对共享条件变量的竞争。

2. 执行计划缓存

引入 Prepared Statement 级别的执行计划缓存机制，避免重复查询的解析和优化开销，在 OLTP 场景下显著降低 CPU 消耗。

3. SIMD 加速

在数据类型转换、字符串比较等高频操作中引入 SIMD 指令加速，充分利用现代 CPU 的向量化能力。

4. 海量表启动优化

针对电商场景中表数量庞大的特点（数十万张表），优化了数据库启动时的表元数据加载流程，减少冷启动时间。

值得借鉴的思路：DongSQL 的组提交优化展示了经典的"广播改单播"模式——在并发系统中，"通知所有人"往往是性能瓶颈的根源，"只通知需要的人"才是正确的方向。这个思路不仅适用于数据库内核，也适用于消息队列、任务调度等任何需要通知/唤醒机制的系统设计。

基于 Claude AI 三款产品的 Agent 安全实战总结

Anthropic 工程团队分享了在 Claude AI、Claude Code、Claude Cowork 三款产品中积累的安全实践经验，提炼出了一套可落地的 Agent 安全设计原则。

核心设计原则

  • 先环境层，后模型层 — 确定性边界是最后防线。不要指望模型自己判断安全，环境隔离（沙箱、容器、权限控制）才是根本。
  • 隔离强度匹配用户监督能力 — 开发者能理解 bash 命令的输出，知识工作者不能。给不同角色的用户提供不同强度的隔离。
  • 警惕自建组件 — 优先使用久经考验的标准隔离原语（如 Docker、Firejail、seccomp），而不是自己造一个"差不多"的沙箱。
  • 出站白名单是能力授权 — 每个可调用函数、每个可访问的 URL 都是攻击面，不是"目的地过滤"而是"能力授权"。

三种风险类型

  1. 用户误用：用户（有意或无意）指示 Agent 执行有害操作，如绕过检查、执行破坏性命令。
  2. 模型行为失当：Agent 未经请求执行有害操作，如自行访问未授权资源、泄露敏感数据。
  3. 供应链攻击：通过 Agent 使用的工具、依赖库或外部资源引入的间接攻击。
行动项：如果你正在开发或集成 AI Agent，对照上述原则做一次安全审计：检查执行环境的隔离强度、审查所有外部调用的白名单、确认敏感操作是否有人类确认环节。

Bash & Python DevOps 自动化实战手册

freeCodeCamp 发布了一份完整的 DevOps 自动化实践手册，覆盖了五个真实的生产场景。核心观点是：自动化脚本的问题不在于工具，而在于"系统看起来很健康但实际上并不健康"。

五个生产级场景

  1. 异常 AWS 支出检测：在月度账单到达之前，通过 CloudWatch API 监控资源使用率突变，提前发现异常消费。
  2. 跨服务日志关联：使用 trace ID 串联多个微服务的日志，快速定位问题根因。
  3. Terraform 外部漂移检测：定期对比 Terraform state 与实际云资源状态，发现手动修改导致的配置漂移。
  4. 应用层密钥轮换验证：确保密钥轮换后，应用确实在使用新密钥而非缓存的旧密钥。
  5. 金丝雀发布健康检查：不仅检查错误率，还检查响应延迟分布（P99、P999），避免"零错误但每个请求都慢 5 秒"的隐形故障。
关键认知："验证进程完成"不等于"验证系统健康"。一个 Kubernetes pod 可以处于 Running 状态，但内部应用无法连接数据库；一个 Terraform 部署可以返回 clean，但有人已经在控制台手动修改了基础设施。自动化脚本的核心价值在于验证"真实系统状态"，而不是"工具返回的状态码"。
