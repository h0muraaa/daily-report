发布TypeScript 7.0 正式发布：Go 原生编译器带来 8–12x 构建提速

微软正式发布 TypeScript 7.0，核心变化是编译器从 JavaScript 迁移到了 Go 语言实现的原生版本（项目代号 tsgo），在真实代码库上实测构建速度提升 8–12 倍。这是 TypeScript 十年来最大的一次底层重写，对大型 monorepo 的 CI 时间、IDE 冷启动和增量检查都有直接影响。

需要注意的是：7.0 尚没有稳定的编程式 API（计划 7.1 提供），依赖 typescript API 的工具链（如部分自定义 transformer、ts-loader 深度定制）需通过官方兼容包过渡。项目保持开源，现有 tooling 可借助 compatibility package 平滑迁移。

实践建议：先在 CI 中用 tsgo 平行跑一轮类型检查对比耗时；大型项目建议等 7.1 的 programmatic API 稳定后再全面替换构建管线中的编译器。

发布Cloudflare Agents Week 连发四弹：@cloudflare/computer、入站 TCP/gRPC、跨语言 RPC、用量计费 API

Cloudflare 本周围绕"给 Agent 一台电脑"密集更新基础设施：

  • @cloudflare/computer（早期预览）：为每个 Agent 提供持久化"工作空间"——Durable Object 内基于 SQLite 的虚拟文件系统，可在三种 runtime 间动态切换：Container（SQLite 状态经 FUSE 挂载到真实 Linux 沙箱）、Isolate Shell（Dynamic Worker 中跑 just-bash 的轻量假 Shell）、Isolate JavaScript（隔离 Dynamic Worker 中的 JS runtime）。思路是"Agent 需要的是 computer 而不是 container"，重任务用容器、轻任务用 isolate，兼顾性能与成本。
  • Workers/Containers 支持入站 TCP 与 gRPC：新增 connect(socket) API，实时语音等低延迟 gRPC 应用可以直接跑在 Cloudflare 上。
  • Workers RPC 跨 Python/JavaScript：基于 Cap'n Proto，无需定义 schema 或引入序列化依赖，即可跨语言调用方法与流。
  • Billable Usage API：单端点返回账户按产品、按服务周期拆分的用量与成本（Workers、R2、D1、Workers AI、Vectorize 等全覆盖），为"Agent 替你花钱"的时代提供程序化的成本可见性。

训练效率工程：Meta GEM 如何把广告大模型训练效率翻倍，百度百舸 512 卡扩展效率 97.48%

Meta 披露了广告推荐基座模型 GEM（支撑 Instagram/Facebook 广告推荐）在数千张最新一代 GPU 上以 LLM 规模训练的工程细节：12 个月内训练 FLOPs 扩大 4 倍，同时端到端训练效率翻倍，达到 20–25% MFU。方法论是 kernels、精度、并行策略、网络与内存的协同设计——推荐模型混合架构与非典型数据分布让现成的 LLM 训练优化无法直接套用，必须针对 workload 重新做 co-design。

百度百舸团队的实践则回答了另一个问题：没有 NVLink 的通用 GPU 集群能否稳定扩展？他们在无 HPN、无 NVLink 的实例上把 64B 参数的 Cosmos3-Super 世界模型从 4 节点 32 卡扩展到 64 节点 512 卡，扩展效率 97.48%，吞吐从 33.997 提升到 530.227 samples/s，Loss 曲线与小规模完全对齐。此前同平台 16B 模型已做到任务启动提速 89 倍、单机吞吐 +99.3%、MFU 0.42（超过官方基准 0.23–0.3）。

共同启示：大规模训练的效率瓶颈早已不是单点算力，而是"框架 × 通信 × 工程体系"的系统协同。MFU、扩展效率、Loss 对齐这三个指标应成为自建训练平台的验收标准。

AI 写代码的天花板实测：用 Rust 重写 Postgres，过了 4.6 万条官方回归测试，被一行 SQL 送走

工程师 Michael Malis（曾在 Heap 维护 1PB 级 PostgreSQL 集群）与朋友用 AI 在几个月内以 Rust 从零重写了完整的数据库引擎 pgrust——解析器、规划器、执行器、存储层、事务与并发控制全部重建，且与 Postgres 磁盘格式兼容，可直接读取现有数据目录，成本约十万美元。项目通过了 PostgreSQL 官方测试套件的 4.6 万+ 回归查询与隔离测试——这些测试是每个 Postgres 版本发布的把关标准。

但公开亮相后，原本用于给真 Postgres 找 bug 的同一批模糊测试工具对准 pgrust，跑了一个下午就崩溃了。PostgreSQL 背后是约四十年的工程积累：补丁层层叠加、生产灾难驱动的修复、成千上万贡献者对边角案例的打磨——这些"隐性知识"不在任何测试套件里。

对开发者的启示：AI 生成代码能通过"显式规格"（测试套件），但生产级系统的可靠性来自"隐式规格"（历史事故、模糊测试、真实负载）。评估 AI 产出时，回归测试全绿只是入场券，fuzzing 与灰度才是分水岭。这也呼应了本周 DevOps 之父 Patrick Debois 的观点："不要再修 Agent 产出的代码，去修那个产出代码的系统。"

指南Graph Engineering：多 Agent 系统的"形状"设计正在成为新底层能力

Prompt Engineering 解决"一次回答怎么写"，Loop Engineering 解决"一个 Agent 怎么反复做事"，而 Graph Engineering 解决的是：当系统里有多个 Agent、多个工具、多个审批点和长期记忆时，它们应该被组织成什么形状。核心概念：节点负责工作、边负责路由、状态沿边流动、检查点决定是否继续。需要先分清两类图谱——知识图谱（Knowledge Graph/GraphRAG）与任务图谱（Task Graph/Agent 编排），再从建模到融合走 9 个阶段，最后落地企业治理（可观测与审批）。落地路径可以手动白板分道 → LangGraph/n8n 三层渐进。当你的任务变成"调研多源→写稿→事实核查→审批→发布"这类多步流水线时，就别再把所有动作塞进一个 while-loop。
