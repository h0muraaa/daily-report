深度技术解读

两个今天最值得展开的技术话题：TPU 软件栈的开放化，以及 Agent Harness 的工程化。

A. TPU 的「去 JAX 化」：TorchTPU 把整个 PyTorch 生态搬上 TPU

关键词：TorchTPU · vLLM · SGLang · llm-d · Pallas · KV Cache

问题在哪：TPU 在特定负载上的性能和成本一直有吸引力，但软件栈长期围绕 JAX/XLA 构建。对已经沉淀了大量 PyTorch 训练代码、自定义算子和服务链路的团队，迁移意味着重写和重新调优，机会成本极高。TorchTPU 试图消灭的正是这道“语言税”。

四层栈各自解决什么

层次组件今天新增的关键能力
训练 TorchTPU + TorchTitan TPU fork 原生 torch.device("tpu")；SimpleFSDP、Graph Trainer、自定义 Pallas kernel；面向 dense/MoE 提升 MFU；提供 Hugging Face modeling backend
推理引擎 vLLM / SGLang 基于 TorchTPU 的原生 PyTorch 后端；优化的 TPU kernel；TPU Sync 管理 KV Cache；支持 disaggregated serving
分布式编排 llm-d 1.0 Kubernetes 原生分布式推理栈，CNCF Sandbox 项目，500+ 贡献者、25+ 组织；针对 agent 多步调用、长共享前缀与 RL rollout
调试 Model Explorer 支持 TOSA、VGF、PTE 等自定义 IR 适配器；分层图可视化、分屏视图、逐节点 trace 覆盖，用于定位导出回归与硬件 delegate 问题 
# 迁移的核心变化：设备选择，而不是重写模型
import torch

device = torch.device("tpu")
model = model.to(device)

# 训练：TorchTitan TPU fork 提供 SimpleFSDP / Graph Trainer / Pallas kernels
# 推理：vLLM / SGLang 通过 TorchTPU 后端在 Ironwood TPU 上提供服务
# 编排：llm-d 1.0 负责 K8s 上的分布式推理与长前缀调度

为什么值得关注

  • 多供应商议价能力：同一套 PyTorch 代码可以同时跑 GPU、CPU 和 TPU，推理成本终于能做同口径 A/B，而不是靠估算。
  • 推理栈合流：vLLM、SGLang、llm-d、Ray、TorchRec、Hugging Face 被放进同一软件模型，团队不必为 TPU 维护一套独立服务链路。
  • Agent 负载被单独照顾：llm-d 1.0 明确针对多步 agent 和 RL rollout 的长共享前缀，这与传统“一问一答”推理的优化重点不同。
落地建议：先用一个小模型 + vLLM 在 TPU 上跑通吞吐/延迟基线，再评估训练迁移；重点验证自定义算子与 Pallas kernel 的覆盖度。不要为了 TPU 而 TPU，先把数据搬运、算子缺口和运维成本算进 TCO。

B. Agent Harness 正在成为新的「后端框架」：持久化、护栏与外部验收

关键词：Pi Durable · Harness · 崩溃恢复 · 循环上限 · 写审分离 · FPY

问题在哪：写一个 while 循环加几个 tool call 就能做出 demo，但生产环境的问题全在循环之外：工具失败怎么办？谁来校验参数？如何防止无限循环和上下文爆炸？进程崩了任务能不能续？让同一个 Agent 自评，结论几乎永远是“没问题”。这些正是 Agent Harness 的职责——模型与执行环境之间的那层软件。

今天出现的三个工程样本

  • Pi Durable（持久化）：把消息、模型回复、工具结果、任务状态落盘，支持崩溃后从断点恢复与会话分叉。关键设计是重放语义：安全操作可重放，可能产生重复副作用的操作不会盲目重跑。
  • freeCodeCamp 的 TypeScript Harness 教程（可测试性）：强调 provider 无关的执行循环，并逐层加入工具注册、参数校验、失败处理、执行上限；同时把模型响应抽象掉，让 harness 本身可以脱离真实模型做单测。
  • 腾讯云 AI 工程化护栏（安全边界）：把安全边界外置到 Harness，按事前隔离与授权、事中循环封顶/人机分级/哨兵熔断、事后门禁与审计分层设防；并明确指出“写和评不能是同一个 Agent”，以对抗自我确认偏差。

组织层面，货拉拉的实践提供了另一个视角：个人提效不等于组织提效。他们用 AI 代码占比的分层签名、FPY（首次通过率）公式及已知盲区来做度量，用对抗性审查和 SDD 五步产线兜住初级工程师的产出下限，再把散落在个人手里的 AI 配置收编成统一工作台。这些动作本质上都是在补 Harness 之上的流程层。

一个可测试的 Harness 骨架

type Tool = {
  name: string;
  schema: ZodType;                    // 参数必须过 schema，不信任模型输出
  run: (args: unknown) => Promise<unknown>;
};

async function runAgent(task: string, tools: Tool[]) {
  let ctx = createContext(task);

  for (let step = 0; step < MAX_STEPS; step++) {
    const action = await model.decide(ctx, tools);

    if (action.type === "final") return action.answer;

    const result = await execute(tools, action);  // 校验、超时、重试、幂等键
    ctx = ctx.append(action, result).compactIfNeeded();
  }

  throw new Error("step budget exhausted");  // 宁可失败，不要失控
}

JetBrains 今天的两篇文章从不同角度补了注脚：一篇解释为什么仍然需要 IDE——Agent 开始承担跨文件任务后，IDE 的角色从“编辑器”转向工作环境与审查界面；另一篇用 4782 个真实开发会话指出，主流 Coding Agent benchmark 大多是单轮任务，而真实使用是连续多轮、意图不断演化的，评测与用户任务流存在结构性偏差。这也提醒我们：Harness 的验收标准，最好来自真实工作流，而不是单一跑分。

落地建议：把 Harness 当后端服务来设计——有状态、有预算、有审计、有幂等、有外部验收。最小可用清单：工具 schema 校验、循环与 token 双预算、写审模型分离、崩溃恢复、浏览器/测试门禁、全链路 trace。

实践指南

可以明天就落到代码里的 6 条建议，每条都对应今天的一条具体动态。

01把 12 小时缓存用起来：重构请求前缀

既然 OpenAI API 现在可以缓存 12 小时，请求结构就应该围绕“稳定前缀 + 动态尾部”来设计。把系统指令、工具 schema、few-shot 示例、长期记忆放在最前面，且保证逐字节稳定；把用户输入、时间戳、本轮检索结果放到后面。时间戳、随机 ID、动态排序的工具列表都会让缓存失效。

  • 工具定义按固定顺序序列化，避免 JSON key 顺序抖动。
  • 不要把“当前时间”写进 system prompt，移到 user message 或工具返回值里。
  • 监控 cached tokens 比例，把它当作和延迟同级的指标。
📎 OpenAI Developers

02给上下文做显式预算，而不是“能塞就塞”

上下文是稀缺资源。Transformer 的注意力是 n² 关系：1 万 token 是 1 亿对关系，10 万 token 是 100 亿对，100 万 token 是 1 万亿对；token 涨 10 倍，注意力被摊薄 100 倍。更直接的是成本：10 万 token 的上下文，Agent 跑 20 轮就是 20 倍重复付费。建议为系统提示、工具定义、对话历史、检索结果分别设定 token 配额，超过阈值就压缩或摘要，而不是等窗口溢出。

📎 架构师之路

03让 Agent 在浏览器里自证，而不是只看测试绿灯

Coding Agent 说“已实现并验证”，通常只代表格式化、类型检查和单测通过。前端改动仍然可能出现控件重叠、选中态没高亮、某个重置路径失效等人类三秒就能发现的问题。把浏览器行为纳入 Agent 的验收闭环：打开页面、执行关键路径、断言可见结果、收集 console error，再配合截图留档。

const errors: string[] = [];
page.on("console", (m) => {

await expect(page.getByText("保存成功")).toBeVisible();

📎 AWS Machine Learning Blog

05按“寿命”给代码定质量标准

Capital One 首席软件工程师 Max Kanat-Alexander 提出的判断框架很实用：不是所有代码都值得同一套质量标准。先问四个问题——这段软件准备活多久？坏掉会伤到谁？有多少人和系统依赖它？重写是否真的更便宜？半小时用完的 CSV 清洗脚本和每天处理资金交易的账户系统，不应该共享同一套评审强度。AI 把代码生产成本压低之后，“可抛弃软件”会越来越多，但前提是明确它真的可抛弃。

06用 fetch + 薄封装替代 axios 前，先看自己的真实需求

一篇在掘金引发讨论的团队规范解释了禁 axios 的动机：原生 fetch 已覆盖超时、取消、拦截器等核心能力，而流式响应（SSE、大文件流）反而是 axios 的短板；多层拦截器嵌套还会变成调试黑洞。更稳妥的做法不是一刀切，而是盘点项目是否真的需要拦截器链、进度监控和上传能力——如果只是发 JSON 请求，一个 10 行左右的 fetch 封装就够了；如果需要 SSE，原生方案反而更直接。
