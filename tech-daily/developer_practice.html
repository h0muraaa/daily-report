01 今日技术热榜

#1Perplexity 用 4 万行 Rust 写出 CobbleDB，把 DynamoDB 换掉了

Perplexity 把核心搜索服务层的持久化从 Amazon DynamoDB 迁到了自研的 Rust 分布式键值存储 CobbleDB。动机非常具体：面向 LLM 的检索每次查询要取回 100–120 个页面的完整分块段落和稠密向量嵌入，平均记录载荷约 50 KB，在每秒 20 万+ 请求下，DynamoDB 按字节计费的模式在经济上不可持续；而且它是个黑盒，分区位置、缓存策略、副本路由都不可见，工程师无法定位未缓存读取或跨可用区跳转造成的尾延迟，分块算法/嵌入模型更新触发的重处理写入还会和实时请求形成噪声邻居争用。

为什么值得看：他们的解法是把存储拆成三个专用系统——Pillar（持久状态，跑在大容量机械盘上）、Lorry（批量聚合）、CobbleDB（低延迟服务），把持久化文档存储与热数据检索解耦。结果批量读取延迟降低 5 倍、整体存储费用至少下降 20%。这是一份"什么时候该自研存储"的判据样本。
📎 来源：InfoQ（作者 Olimpiu Pop / 译者 田橙）

#2谷歌开源 AX：面向自主 Agent 的 Kubernetes 风格编排器

谷歌发布 AX（GitHub google/ax，托管于 agentexecutor.io），Apache 2.0 许可的开源编排器兼声明式运行时，用于执行和扩展自主 Agent 工作负载。它基于 Agent Substrate 运行，把每个 Agent 会话当作有状态的 Actor 沙箱而非微服务或批处理任务，支持亚秒级任务暂停/恢复，提供四种声明式原语：Task、Workspace、Gateway、Model。

为什么值得看：它针对的正是传统编排的痛点——Agent 具有"突发计算 + 长时间空闲等待模型/API/人工"的特征，在 K8s 里维持常驻沙箱会浪费算力，容器冷启动又会拖慢交互循环；AX 用 Actor 多路复用执行运行时来平衡。自建 Agent 基础设施时值得逐条对照它的取舍。
📎 来源：InfoQ（作者 Olimpiu Pop / 译者 平川）

React 19.3（9 月 9 日发布）引入 react-dom 的 browser() API，允许组件显式退出服务端渲染。它解决的是依赖客户端专有数据的组件在 SSR 下的 hydration mismatch 问题，并支持条件式数据获取。此前这类需求通常靠 useEffect + 挂载标记或 typeof window 之类土办法绕过，现在有了框架层的第一等公民表达。

为什么值得看：如果你在维护依赖大量浏览器 API 的组件库，这个 API 能让代码意图更清晰、水合失败更少——升级时优先检查那些"靠副作用才敢渲染"的组件。

02 深度技术解读

解读 A · Perplexity 如何为 Agent 重造基础设施：CobbleDB 与"面向 Agent 的 Git forge"

Perplexity 这一周同时放出了两个基础设施层面的设计，合起来看是一条清晰的思路——把 Agent 当成主线用户来重造底层系统。

第一层 · 存储：为什么 DynamoDB 撑不住了

AI 答案引擎的读取模式与传统搜索完全不同：每次查询生成 100–120 个目标页面键，检索服务拆成 10–20 键的批次并行处理，而 LLM 需要的是完整段落 + 稠密向量（平均 50 KB/记录），远超搜索引擎返回的元数据片段。在 20 万+ QPS 下，三个问题同时爆掉：

  • 成本——AWS 对传输的每个字节计费，50 KB 的载荷放大后不可持续；
  • 尾延迟不可观测——DynamoDB 是黑盒，分区位置、内存缓存策略、副本路由都不可见，无法定位未缓存读取与跨 AZ 跳转；
  • 噪声邻居争用——分块算法或嵌入模型更新触发的重处理写入，会和实时请求抢同一张表。

他们的解法是三系统拆分，把读写路径彻底解耦：

// 迁移前后：读写路径解耦
Pillar    →  持久状态管理（大容量机械盘，成本优先）
Lorry     →  批量聚合 / 重处理写入（隔离噪声邻居）
CobbleDB  →  低延迟服务层（Rust，面向热数据检索）

效果：批量读取延迟 ↓ 5×   整体存储费用 ↓ ≥20%

第二层 · 文件系统：一个没有 PR 审批的 Git forge

Perplexity Projects 的底层文件系统被设计成"没有 GitHub 冗余"的 Git forge——因为这里没有人类来审批 PR。每个 Agent 在自己的短生命周期沙箱里工作，再提交到 S3 上共享的仓库；由于彼此隔离，冲突率低于 2%。Git 提供原子多文件提交、作者归属和可查询历史；forge 提供托管与写权限控制；而 PR review 这一环被替换为"每次提交对照仓库契约做校验"。项目不需要为峰值负载预置长寿沙箱——仓库在 S3 上、Agent 在临时沙箱里跑，崩溃只丢失未提交的工作。

反直觉结论：给 Agent 一个真实文件系统去 grep

他们用一次内部基准测试（150 道金融文档问答）说明了一件重要的事：

// 检索方式对答案准确率的影响（150 题金融文档）
朴素 ls / grep 在真实 checkout 上  →  0.627
语义检索（semantic search）        →  0.37

也就是说——给 Agent 一个真实的文件系统去 grep，胜过喂它一套语义搜索。因为每个沙箱里是一份真实 checkout，Agent 可以用标准文件工具做精确检索，而不必依赖宽泛的语义匹配。

实践建议

  1. 读写模式分离后，热路径与冷路径应当用不同系统承载，别让重处理作业与在线查询共用同一张表。
  2. 给 Agent 提供真实文件 + grep，在结构化/高精度检索场景往往比向量检索更准。
  3. Agent 协作的核心原语是提交（commit），而非会话（session）——让工作能跨沙箱存活、让历史可查。
📎 来源： InfoQ · CobbleDB| Aravind Srinivas| Perplexity · grep vs 语义检索

解读 B · 沙箱不是可选项：隔离编码 Agent 的四种真实方案

在笔记本上以 --dangerously-skip-permissions 跑编码 Agent，等于把手上的每一个文件、密钥和生产凭据都暴露出去。OpenHands 联合创始人 Robert Brennan 在 AI Engineer NY 的分享里，把"给 Agent 做隔离"落成了四种可对照的实现方案，并按本地/远程、扩展性、隔离度、持久性和触发方式五个维度评估：

  • 笔记本上的 Docker——最轻量，适合个人实验；隔离边界取决于容器配置，共享宿主内核。
  • GitHub Actions 里的 Claude Code——天然远程、有 CI 触发；适合把 Agent 接进既有自动化流水线。
  • 专用 VM / Mac Mini——隔离度高、可持续运行，适合小团队常驻 Agent。
  • 每会话一个 Kubernetes Pod——扩展性最好，适合大规模并行 Agent 集群。

Brennan 的核心原则是最小权限，并强调沙箱也不是万灵药。与之呼应，AWS Bedrock AgentCore 工程师 Kevin Orellana 做了一项"破坏性测试"：把 AgentCore 的代码沙箱和云浏览器包成 MCP server，让编码 Agent 在 10 个领域写了并运行 1000 个测试、日志写入 SQLite，从中暴露了图片编码 bug、空字节（null bytes）、不可读文件、浏览器内存耗尽等问题，并进一步把故障区分为接口层 bug（如沙箱内存、文件权限、seccomp、eBPF 等底层限制）。这类"用 Agent 测 Agent 基础设施"的实践，正在成为沙箱工程的标准动作。

可落地的检查清单

  1. 先设边界：从"每会话一个隔离边界"开始，把凭据从 Agent 可达范围内移出。
  2. 给硬限制：为沙箱设定内存、文件权限、seccomp 等底层约束，别只靠"提示词里叮嘱它别乱来"。
  3. 主动压测：用大批量任务（数百上千次）跑破坏性测试，把故障按"接口层 / 沙箱层"分类，别等生产环境来告诉你边界在哪。
  4. 只给最小权限：能从只读开始就别给写权限，能限时就别常驻。
📎 来源： AI Engineer · OpenHands：4 Ways to Isolate Coding Agents| AI Engineer · AWS：1,000 Agent Tasks in a Sandbox

04 实践指南

指南 1 · 把"验证闭环"当成核心产出，而不是逐行审代码

Addy Osmani 与 lauren（分别来自 Anthropic 与 SpaceXSI）在一次分享中给出了一致判断：当 AI 让验证变便宜，工程师的核心工作就从"逐行写好 / 逐行审查代码"转变为设计验证闭环，并把个人品味沉淀为可复用的规则。lauren 的论证值得记住——所谓 "slop" 一直存在，人类写了几十年的代码也充满瑕疵；大部分人对 slop 的真实定义其实是"不是我写的代码"；好代码 = 正确、无 bug、运行快且成本高效，而它之所以昂贵，是因为这三条过去无法被廉价地形式化保证。Addy 补上机制：agent 让测试、基准、规格说明、端到端运行的边际成本趋近于零，于是"规模上的平均更好"成立。

  1. 为每类任务写死验收条件：能跑的命令、期望的测试输出、要通过的用户流程。
  2. 把检查交给 Agent 自己执行，通过了才允许它宣称完成。
  3. 把 review 从"人肉逐行把关"转向"可自动校验的契约与门槛"——当前研发 pipeline 里 code 与 review 两个节点的速率已经倒挂，逼着团队重建流程。
📎 meng shao · 代码质量是验证出来的 · yan5xu · code review 之争

指南 2 · AI Evals 口袋指南：什么时候该写评估、怎么写才不浪费

Hamel Husain 把 "Applied AI Evals" 课程浓缩成 13 张信息卡，几条落地规则：

  • 先做误差分析再写评估：收集 100+ 条多样 trace → 开放式编码写非结构化笔记 → 聚类 → 按频次排优先级，循环到"理论饱和"；trace 要标注 pass/fail 和失败模式。
  • 拒绝通用指标：ROUGE、BLEU、"有用性/忠实度"应替换为应用专属指标，如"日历排期失败""邮件收件人错误"。好指标应符合：对应观察到的错误、聚焦具体失败、结果是二元的（pass/fail 而非 1–5 分）、可验证。
  • 评估是有 ROI 的：先问"误差分析里是否观察到该失败"，没观察到就别写；需要大量迭代修复的失败才值得上昂贵的 LLM 裁判。
  • 三种自动化评估按需分工：代码断言（快、便宜、确定、可解释，能用则用）→ LLM 裁判（处理主观/细微标准，需对照人类标签校准）→ 护栏。
  • 全绿不是好消息：100% 通过往往说明评估已饱和或太简单，要持续补困难用例。
📎 meng shao · Pocket Guide to AI Evals

指南 3 · 老系统接入 AI 的三条路径：API 封装 / CLI 包装 / RPA 兜底

腾讯技术工程的一篇文章用一张概念图讲清了 Model / Agent / Skill / MCP / CLI 五个概念的关系（类比成一支数字化团队：Model 是大脑、Agent 是数字员工、Skill 是岗位技能手册、MCP 是万能转接头），并给出老系统接入 AI 的三条路径：优先 API 封装（有接口时最干净）、其次 CLI 包装（把已有命令行能力暴露给 Agent）、最后 RPA 兜底（完全没有接口时）。文章还系统梳理了 MCP 的实现形式分类，并给出 BS/CS 两种架构的实战案例。

  1. 盘点手里老系统的接口形态：有 API 走 API、只有命令行走 CLI 包装、什么都没有才上 RPA。
  2. 用统一协议层（如 MCP）把内部系统对 Agent 的暴露方式标准化，避免每接一个系统就改一次 Agent。
  3. 把流程与经验封装成 Skill，而不是散落在每个 Agent 的提示词里。
