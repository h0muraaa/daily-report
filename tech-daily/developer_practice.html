2. 深度技术解读

2.1 从 AWS 迁到 PaaS：先算清“运维税”

一支 7 人的内部工具团队通过复盘 sprint、事件日志和日历，发现大量时间被基础设施运维吞噬，而非用于构建产品。迁移到 PaaS 的核心不是“追新”，而是用平台托管服务器、补丁、扩容等运维工作，让团队回归业务价值。

实现细节：先用“功能开发时间 / 基础设施运维时间”量化隐性成本，再列出最痛的运维任务（如证书管理、数据库补丁、自动扩缩容）。然后评估 PaaS 是否能覆盖这些任务，并制定分阶段迁移计划：先迁非关键服务，再处理有状态组件。迁移后持续对比故障恢复时间、部署频率和团队满意度，确保 PaaS 真的在还“运维税”。

实践建议：不要一开始就全量迁移；选一个没有复杂遗留依赖的服务做试点，记录迁移前后的工程时间分配，用数据说服团队和组织。

来源：freeCodeCamp

2.2 给 AI 代理上“笼子”：为什么隔离是刚需

AI 编码代理的能力边界正在快速扩展：写代码、运行测试、安装依赖、调用 API、修改文件系统。这些操作如果直接在开发者的本机执行，就相当于给一段由模型生成的代码 root 权限，风险随着能力线性增长。

技术方案：Docker Sandbox（sbx）把 AI 代理放进一个可丢弃的沙箱 + microVM 组合环境中。每次任务启动一个干净容器，执行完毕后销毁；网络、文件系统、系统调用都受到限制。这样即使代理被提示词注入或产生幻觉，破坏范围也被锁定在沙箱内。

落地思路：在 CI/CD 中为 AI 生成的补丁先跑一遍沙箱测试；本地开发时，把 agent 的“执行模式”默认指向容器，只允许显式授权的操作突破沙箱。这类似于给 LLM 加上最小权限原则。

来源：Docker
