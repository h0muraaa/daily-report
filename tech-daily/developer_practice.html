#02 深度技术解读
今天最值得钻进去的两个话题：一是 Agent 的复杂度如何在模型外面一层层长出来（以及 Harness 该怎么配），二是"文档即代码"被推到极致——代码库干脆不存代码。
// DEEP DIVE 01 · FROM LLM CALL TO HARNESS

从一次 LLM 调用到完整 Harness：Agent 的一层层"补丁"，就是一套小型操作系统

腾讯技术工程这篇长文的起手式很适合当心智模型：Agent 的复杂性不是一次设计出来的，而是每次模型想越过某条边界、系统就在模型外补一个新部件。最初的 LLM 只是一个"token 进、token 出"的函数——它把世界知识编码进参数，却不记得用户上一轮说了什么，也不知道自己刚输出的命令到底执行没有。于是：模型不记得历史 → 补上下文；模型无法改变世界 → 补工具；一次调用完不成任务 → 补循环；上下文装不下 → 补记忆；循环开始产生真实副作用 → 补权限与沙箱；一个循环不够并行 → 补子 Agent。

# 从一次调用到 Agent，复杂度在"模型外"逐层补齐 model: tokens_in -> tokens_out # 纯函数：无记忆、无副作用 #1 context # 模型不记得上一轮 -> 拼历史 #2 tools # 模型无法改变世界 -> 开放函数调用 #3 loop # 一次调用完不成任务 -> agent loop #4 memory # 上下文放不下 -> 长期记忆文件 #5 policy # 循环开始产生副作用 -> 权限/沙箱/审核点 #6 sub-agent # 一个循环不够并行 -> 进程/编排

到最后，今天的 Agent 系统"看起来很像一套小型操作系统"：管理子 Agent 进程、维护长期记忆文件、通过工具驱动接触外部世界，还要处理权限、隔离、恢复与观测。这也是为什么本文档的另一半（见实践 P3）会把 Claude Code 的 Harness 拆成七件套——CLAUDE.md、Skills/Commands、Subagents、Agent Teams、Dynamic Workflow、Hooks、MCP——本质都是在给"模型外那层"补确定性。今天热榜里 Anthropic 访谈的"删掉 80% 系统提示词"并不是要拆掉 Harness，恰恰相反：模型越强，越要把提示词这种"软约束"换成 Hooks 这类"确定性质量门"，把精力沉淀在可复用的外壳上。一句话总结两篇文章的共识：提示词是一次性的，Harness 是可沉淀的。

⚠ 读懂所有 coding-agent 新闻的框架：先问"这是在换更强的模型，还是在加更厚的 Harness"。今天的 GitHub、AWS、字节跳动 Agent Plan 大多属于后者。
↳ 来源：腾讯技术工程·架构师之路·meng shao(Anthropic 访谈)
// DEEP DIVE 02 · DOCS AS THE ONLY SOURCE OF TRUTH

"Design Docs Are All You Need"：一个主分支几乎没有代码的仓库，靠子 Agent 按文档重新生成实现

Google DeepMind + MIT 的这篇论文被 elvis（@omarsar0）称作"奇怪又有趣"。它的做法非常激进：他们维护一个 performance-modeling 库，主分支上几乎没有代码；仓库本体是一张由自然语言设计文档组成的有向图（DAG）。每次版本更新，编码子 Agent 根据这些文档重新生成整个实现；人类唯一的改动方式，就是去改某份设计文档。背后的判断是：ML 性能建模的抽象每隔一代硬件/模型就会被推翻，与其"打补丁式"维护一套不断失真的代码，不如在 Agent 足够便宜的今天"整库再生成"。

# 文档 DAG = 事实源；src/ 只是可丢弃的"构建产物" repo/ docs/ 00_overview.md 01_kernel_model.md # 逐行 worked example + 边界条件 02_memory_model.md # 让子 Agent 能照着"算一遍" ... # 发版时： agents: parse(DAG) -> for node in nodes: regenerate_impl(node) -> run(worked_examples) # 示例即校验 -> write src/*.py human_change = edit(doc) # 不直接改代码

它为什么可靠？关键在于设计文档围绕一步步可执行的 worked example 来写——这些例子既当规格又当上下文校验，让子 Agent 生成的不是"猜出来的代码"，而是能对着示例逐步验证的代码。Amjad Masad 今天的另一条高赞推文其实点出了同一个时代前提："我们没到 AGI，但已经拥有一个不知疲倦的程序员——任何能被表述成编码问题的任务，几乎都被解决了。"当"写实现"的成本趋近于零，"表达意图（写文档）"就取代"维护代码"成为主要工程活动。

对普通团队，这不是让你明天就把代码全删了，而是给"文档驱动开发"指了一个更极端的方向：文档与示例要写得足够精确，精确到能作为 Agent 的生成规格；同时要在 CI 里保留"从文档再生成一遍"的演练，验证文档没有和实现脱节。反过来，这也解释了为什么越来越多团队抱怨"文档没人写"——当 Agent 能读文档并生成实现时，写文档第一次成了高杠杆的开发行为。

↳ 来源：elvis(@omarsar0)·Amjad Masad(@amasad)

#04 实践指南
六条今天就能用上的实操经验：评审分流、LLM 错误处理、Harness 配置、长任务 Agent、Agent 交付上架，以及一份学习路线。
PRACTICE 01 · CODE REVIEW ROUTING

Addy Osmani：代码越多，人越要"选择性"评审——Agent 做首轮，人盯爆炸半径

Addy Osmani 回应"还要不要做人工评审"给出了自己的分流方案：① 每个 PR 先跑一个多 Agent 首轮评审，负责找 bug、验证、按严重度排序、给修复建议，但"批准权"仍然留给人；② 低爆炸半径、非敏感路径的改动，在 agent 首轮干净的前提下可以跳过深度人工评审，否则 PR 洪峰会压垮团队；③ 核心 / 敏感路径必须有 owner 和人工签字，人的时间应该花在验证、约束和建立"哪些能安全交给 agent"的信任上。

# 评审分流（示意） review = multi_agent_first_pass(diff) # 找 bug、验证、按严重度排序 if review.blast_radius == "LOW" and not core_path: auto_merge(review) # 低风险：agent 首轮干净即放行 else: human_signoff(review) # 高风险：人看验证/约束/信任

核心思想一句话：Agent 做第一遍全覆盖，人类按爆炸半径做选择性深挖，同时保持"可恢复性"。

↳ 来源：Addy Osmani(@addyosmani)
PRACTICE 02 · LLM APP RESILIENCY

ByteByteGo：给 LLM 应用做错误处理，先把失败分成"技术性"和"语义性"两类

LLM 应用除了普通软件的故障，还多出"语义失败"——调用技术上成功了，但结果不对、不安全、不可用。ByteByteGo 给出了一张完整故障清单：无效输入要前置校验省钱省时；网络/超时可重试（交互式约 20s、后台任务可以放宽到分钟级）；429 限流要退避+削峰或换模型；401/403 不要重试，直接告警；上下文超长要在发送前算 token，做裁剪/摘要/分块；输出格式错乱要用 structured output + schema 校验；最难的"幻觉"无法靠异常捕获，要靠可信数据源与人工兜底。工具调用要重点防"成功但确认丢失"——盲重试可能重复扣款。

# 失败三分类 -> 处理策略 TRANSIENT : 网络/超时/429/部分5xx -> 指数退避 + 抖动重试（限次数） PERMANENT : 401/403/参数错误 -> 不重试，告警 + 安全返回 SEMANTIC : 幻觉/格式错/结果不可用 -> schema 校验 / 回退 / 人工兜底 # 带副作用的工具调用必须幂等 call(payment, idempotency_key=req_id) # 重试安全，防重复扣款

工程上再叠加三层：回退链（主模型 → 更小备用模型 → 缓存/预置响应 → 人工）、熔断器（closed / open / half-open 三态）、限流与队列。想让 LLM 应用在线上"稳"，这些是比 prompt 更值得先做的功课。

↳ 来源：ByteByteGo Newsletter
PRACTICE 03 · PERSONAL HARNESS SETUP

同一个 Claude Code，为什么别人是 10 倍生产力？差距在 Harness：七件套配置清单

架构师之路这篇文章点破了普遍困惑：Agent = Model + Harness，模型大家都一样，真正拉开差距的是模型外那层。作者给出 Claude Code 个人 Harness 的七件套：CLAUDE.md（固化项目事实与约束）、Skills/Commands（固化可复用工作方法）、Subagents（固化专业执行角色）、Agent Teams（固化多 Agent 分工）、Dynamic Workflow（固化任务依赖/状态/恢复）、Hooks（固化确定性质量门，让格式化/Lint/测试自动发生）、MCP（固化授权外部连接）。

# Prompt / Context / Harness 的分工 prompt : 这次做什么 # 一次性 context: 完成任务需要知道什么 # 一次性 harness: 怎样稳定、受控、持续地完成 # 可沉淀、每次都在 # 七件套（配置顺序建议） 1. CLAUDE.md -> 2. Skills/Commands -> 3. Subagents -> 4. Agent Teams -> 5. Dynamic Workflow -> 6. Hooks（先上确定性质量门）-> 7. MCP

一句话：提示词是一次性的，Harness 是可沉淀的——它让 Code Agent 从"偶尔成功"走向"稳定交付"。搭配今天热榜里 Anthropic 的访谈结论（提示词删减、示例瘦身、测试加量），配 Harness 的正确姿势是：把软性规则尽量下沉成 Hooks 之类的确定性检查，而不是堆砌提示词。

↳ 来源：架构师之路
PRACTICE 04 · LONG-HORIZON GUI AGENT

把"深度调研"丢给云电脑：Agent 拆任务、跨网页与桌面执行、人只验收结果

字节跳动「Agent 云电脑」展示了一条可复制的长任务玩法：接到"做一份股市大盘深度研究"这类要查行情、翻研报、对数据、写分析的活，传统做法是开十几个标签页手动切换；现在可以让一台 24 小时在线的云电脑自己拆解任务。关键设计是 CUA 能跨网页与桌面应用操作（站内搜索、滚动、切换标签、处理需交互的页面），并且一次委派、持续观察——监控中断不影响任务执行，可随时停止/恢复。
