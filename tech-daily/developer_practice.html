# 深度技术解读

Claude Code

驾驭 Claude Code 的七种上下文注入方式

Claude Code（以及 Codex）提供了多种超出普通对话的上下文控制方法，包括 CLAUDE.md、Rules、Skills、Subagents、Hooks、Output Styles 和 System Prompt Append。理解它们的加载时机、会话压缩后是否保留、以及 token 消耗差异，是高效使用 AI 编码工具的关键。

CLAUDE.md 是项目根目录的 Markdown 文件，会话开始时全程驻留上下文，压缩后重新读取；子目录的 CLAUDE.md 只在访问该目录时按需加载。官方建议控制在 200 行以内，并指定负责人像审查代码一样审查变更，否则容易变成无人维护的配置垃圾堆。Rules 存放在 .claude/rules/，最有价值的是路径作用域：通过 paths 字段只在触碰特定文件时加载，例如只对 src/api/** 注入"所有 API 处理器必须用 Zod 验证输入"的规则，避免全程占用 token。Skills 是复用的任务模板，Subagents 可以并行处理子任务，Hooks 则用于确定性执行特定事件。Dynamic Workflows 是 Claude 较新的能力，允许它自己编写编排脚本、协调多个 agent 并行工作。

实践建议：不要把所有规则都塞进 CLAUDE.md。按作用域拆分到 Rules，把可复用的操作抽象成 Skills，把需要确定性触发的事情交给 Hooks，这样才能在控制 token 成本的同时保持 AI 的执行力。

Agentic Engineering

Factory Model：Coding Agent 如何改变软件工程

谷歌工程师 Addy Osmani 提出的 Factory Model 认为，当 Coding Agent 从补全、对话式协作走向长时间自主执行任务时，软件工程师的工作重心从"亲手写代码"转向"设计一个能产出软件的系统"。这个系统由规格说明、智能体、工具链、测试、反馈循环和人工评审组成。编码方式虽然发生了巨大变化，但软件工程的核心要求并没有消失，反而架构理解、规格说明、测试、验证和判断力变得更加重要。

这与国内开发者宝玉提出的实践相呼应：让 Agent 生成更好的代码，需要从需求分析、系统设计、拆分里程碑、代码审查到自动化测试形成完整闭环。Agent 不怕你啰嗦，怕你不说；你觉得显然的东西对它一点都不显然。每次提交只做一件事，便于审查；单元测试给 Agent 即时反馈，集成测试验证模块组装，CI 自动跑测试减少人工触发。当错误根因是项目特有的约定或上下文缺失时，才应该更新 AGENTS.md；如果是边界条件没覆盖，就应该加测试；如果是架构缺陷，就应该重构。

Workflow

AI 驱动开发的 7 阶段工作流

Matt Pocock 提出了 AI 驱动开发的七个阶段：Grill（让 AI 疯狂拷问细节直到清晰）、Research（针对难点单独分析并生成研究文档）、PRD（生成详细需求文档）、Issues（把 PRD 拆成带依赖关系的独立 tickets）、Implement（分 ticket 独立实现）、Review（验证）。独立开发者 Viking 表示这正是他开发新功能和新点子的主要流程。

这个流程的核心思想是：在进入高保真实现之前，先弄清楚设计树的形状。把大问题拆成小任务，每个任务独立完成和验证，避免一次性给 AI 太多上下文导致失控。对于使用 Claude Code、Codex 或 Cursor 的开发者，可以尝试用 /grill-with-docs 或类似的 plan 模式来结构化前期工作。

Security

防范 AI 投毒：当 Agent 自己下载了木马

开发者 Barret 李靖分享了一次真实经历：电脑中了 AMOS Stealer 恶意软件家族的 macOS 变种，潜伏一个月后才被发现。溯源发现，木马是在使用 Claude Code 的 bypass 模式执行软件安装/更新时，AI 从互联网找到不安全的资源并下载执行的。Claude Code 长期开启 bypass 模式，所有命令直接放行，导致恶意脚本获得了执行机会。

这次事件给 AI 编码工具用户敲响了警钟：AI 会从网络搜索资源并执行命令，如果缺乏人工审核，就可能引入供应链攻击或恶意软件。建议为 Agent 设置最小权限，避免长期开启自动执行模式；对于涉及 curl | bash、brew install 第三方 tap 等操作，务必人工确认来源；同时保持系统日志和进程监控，便于事后溯源。
