浏览器Codex / Claude Code 双双上线多标签浏览器：Agent 从"写代码"进化到"接管桌面操作"

Grok Build CLI 被曝上传整个代码库事件持续发酵。xAI 的回应是：禁用 ZDR（Zero Data Retention）后即可同步删除已上传数据。但社区迅速指出两个关键问题：(1) ZDR 只对企业用户开放，个人开发者无法用；(2) "已删除"这件事无法被外部证伪——xAI 说删了，但你无法验证。Sam Altman 在 X 上用一个词评论："Concerning."。Amjad Masad（Replit CEO）也公开声讨。有开发者在 12 GB 测试仓库上验证：5.1 GB 数据被上传到 grok-code-session-traces 桶，而实际编码任务只需 192 KB。

框架Google Genkit Agents API 预览：一个 chat() 接口搞定消息历史、工具循环、状态持久化

Google 发布了 Genkit Agents API 预览版，覆盖 TypeScript 和 Go。核心设计是把 Agent 应用最常见的四件事——消息历史、工具循环、流式输出、状态持久化——打包到单个 chat() 接口后面。两个值得关注的差异化能力：(1) Detached turns 让 Agent 在客户端断开后继续工作；(2) Interruptible tools 提供人在回路控制，resume 时带防伪验证。

// TypeScript 示例
const agent = ai.defineAgent({
  name: 'support',
  tools: [lookupOrder, refund],
  detached: true,     // 客户端断开也继续跑
  humanInLoop: ['refund'],  // 退款需要人工确认
});

const { response, resume } = await agent.chat({
  messages, sessionId,
});
为什么值得你看：(1) Genkit 是 Google 的官方 Agent 框架，和 LangGraph、OpenAI Agents SDK 是同一层级的产品；(2) Detached turns 是 Agent 工程里一个常见但少有人解决好的问题——用户在手机上关掉 App 后，Agent 还应该跑完后台任务；(3) 如果你正在评估 Agent 框架，值得花 30 分钟看看 Genkit 的状态持久化模型和 LangGraph 的差异，尤其 "interruptible tools + 防伪验证" 这套设计。

🔬深度技术解读

长上下文Context Rot：1M Token 上下文的真相 —— GPT-5.5 在 256K 检索 80%，1M 掉到 36%

Prime Intellect 一位工程师的演讲片段被广泛传播："everyone's bragging about a million-token context. here's what they don't tell you."他给出了一个让很多人不舒服的数字：GPT-5.5 在 256K tokens 时检索准确率 80%，拉到 1M tokens 直接掉到 36%。模型"接受"了上下文，但已经无法跨越上下文做有效推理——社区开始把这种现象称为 Context Rot（上下文腐烂）。

这个观察和 Andrej Karpathy 同日的另一个观点形成呼应："Context windows are a cheap way to manipulate AI"——上下文窗口是操纵 AI 的廉价方式，但真正的定制需要微调或专门训练，那要困难得多。Prime Intellect 工程师给出的解法是三件事：continual learning（持续学习）+ training on your own traces（在你自己的轨迹上训练）+ real environments（真实环境），而不是指望上下文窗口无限制扩大。

实践建议：(1) 如果你的 Agent 工作流依赖"把所有历史塞进上下文"，现在就该重新设计——检索、摘要、外部记忆都应该是首选方案；(2) 评测 Agent 时把"上下文长度"作为变量，不要只看峰值上下文能塞多少，而要看"在 X K tokens 时准确率是多少"；(3) 如果你在做企业 Agent，认真考虑 continual learning 路线——把 Agent 的工作轨迹当作训练数据回流，这是 Prime Intellect、Meta 都在押注的方向；(4) Karpathy 那句"上下文窗口是廉价操纵"值得记下来——它解释了为什么 RAG + 微调往往比纯 prompt 工程更有效。
📎 来源: X / AI Will — Prime Intellect 工程师演讲  |  No Priors — Karpathy on Context Windows

路由DeepMind 模型路由论文：如果你所有模型回答都一样，路由器就是个摆设

Google DeepMind 发布了一篇关于 LLM 路由策略的研究论文，提出两个被主流评测忽视的指标。当前 LLM Router 普遍只用"准确率 + 成本"来评估，但论文指出这是不充分的——如果你池子里所有模型对同一个 query 的回答都一样，路由器选谁都无所谓，它的"准确率"再高也没意义。论文提出两个正交于任务准确率的关键属性：(1) Behavioral differentiation（行为差异化）——池子里模型之间必须有真实差异；(2) Stability under surface-form rewrites（在表面形式改写下的稳定性）——同一个 query 的不同表述应该被路由到同一个专家。

实践建议：(1) 如果你正在用 mixture-of-agents 或 model routing（比如 OpenRouter、自己的路由层），先做个体检——随机抽 100 条 query 看不同模型的回答差异度，如果差异小于 10%，你的路由器就是装饰品；(2) 路由稳定性这个指标很新但很重要——它直接影响用户体验（用户换个问法不应该得到截然不同的答案）；(3) 同日 Arena.ai 的 Melissa Pan 公布了他们的研究：通过优化完整系统配置（不只是 LLM 选择），可以削减 89% 的 agent 成本，同时保持 100% 的最佳静态配置准确率。这和 DeepMind 论文是同一个方向——路由只是表面，系统级配置才是关键。
📎 来源: X / elvis — DeepMind model routing paper  |  X / Arena.ai — 89% cost cut via full config

责任Addy Osmani：Don't Build Agents You Can't Answer For —— 工程师的新角色是"可解释性"

Addy Osmani 在 AI Engineer 大会闭幕演讲中讨论了 LLM Agent 时代工程师角色的演变。他的核心论点是：随着编码任务被自动化，工程师的真正价值正在从"代码生产"转向"问责、判断和系统所有权"。他给出了几个关键概念：(1) Harnesses 与 Loop Engineering——Agent 的工作流需要被设计为可控的循环，而不是无限自动运行；(2) Answerability as an engineering requirement——"能为你的 Agent 回答"是一种工程要求，不是道德表态；(3) Reviewing AI-assisted code 是组织瓶颈——AI 写得越快，人类的 review 瓶颈越严重；(4) Alpha 与 decay——工程师的优势来自"taste"和判断力，而不是打字速度。

实践建议：(1) 检查你团队的 Code Review 链路——如果 AI 把代码产出速度提升了 3 倍，你的 review 能力是否也跟上了？这是大多数团队当前的最大瓶颈；(2) 把"Answerability"作为 Agent 设计的第一原则——任何 Agent 行为都要能回答"谁决定的、为什么这么做、出了问题谁负责"；(3) 如果你正在做 Agent 平台，把 Loop Engineering 作为核心抽象——明确"什么时候 Agent 该停、什么时候该升级给人类"比"让 Agent 跑得越久越好"重要得多；(4) 重读 IBM 1979 年那句"A computer can never be held accountable"——这是 47 年前的智慧，今天依然是 Agent 工程的地基。
📎 来源: AI Engineer — Don't Build Agents You Can't Answer For

视频claude-video：让 Claude Code 看懂 YouTube 视频的开源 Skill，6.8K Star

Brad Bonanno 开源的 claude-video 给 Claude Code 增加了一个 /watch 能力——可以处理 YouTube 链接和本地视频文件，让 Agent 真正"看懂"视频而不仅仅是读字幕。用法非常直观：/watch https://youtu.be/xxx 总结这个视频 或 /watch ~/Movies/screen-recording.mp4 这个视频哪里有 xx 的画面？。它会先获取字幕，根据需要下载视频并抽取关键帧，然后基于多模态理解给出回答。目前 GitHub 上约 6.8K Star。

适合谁：(1) 经常需要让 Agent 处理视频会议、产品 Demo、技术演讲录像的团队；(2) 做技术教育内容、需要批量分析视频素材的创作者；(3) 想把"看视频学新框架"自动化的开发者。之前这类需求只能用 Whisper + 多模态模型手工拼，现在一个 Skill 搞定。注意目前主要在 Claude Code 生态，Codex / Cursor 用户需要等社区适配。

视频BaoCut：把 Agent 字幕转录+翻译+剪辑打包成 Mac 应用，带 GUI 二次编辑

宝玉开源的 BaoCut 是一个 Mac-only 的字幕转录翻译剪辑 Skill。它的差异化设计在于解决了"Agent 处理完字幕后无法可视化二次编辑"的问题——Agent 通过 CLI 完成转录、Speaker 识别、错别字润色、翻译，进度实时同步到 GUI；用户在 GUI 里预览和人工编辑。安装后，从 Codex / Claude Code 直接触发：/baocut 转录并翻译视频：<视频 url 或路径>。

为什么推荐：(1) "Agent 处理 + GUI 二次编辑"是一个很值得参考的产品设计模式——纯 CLI Agent 对最终用户不友好，纯 GUI 又不能利用 Agent 自动化，BaoCut 把两者结合得很好；(2) 如果你也在做"Agent 干脏活 + 人工精修"类的工具，BaoCut 的 Skill + CLI + GUI 架构值得参考；(3) 已知问题：仅支持 Mac、翻译速度略慢，但质量较高。对非 Mac 用户可以等社区移植，或者参考它的设计思路。

观测Mindwalk：单文件 Go 程序，把 Claude Code / Codex 会话日志变成 3D 代码地图

cosmtrek 开源的 Mindwalk 是一个 单文件 Go 程序，读取 Claude Code 和 Codex 的本地会话日志，在浏览器里把整个仓库铺成一张 3D 夜景地图——文件被搜索、读取、修改得越频繁，亮度越高。提供地形和树两种视角、回放拖拽、时间轴标记、点击文件查看详情。所有处理在本地完成，日志不会外发。

为什么推荐：(1) 这是"Coding Agent 可观测性"的一个有趣视角——不只是记录 Agent 改了什么，而是可视化 Agent 的"探索路径"；(2) 单文件 Go 程序 + 本地处理是隐私敏感场景的正确选择，尤其对比本周 Grok Build 的丑闻；(3) 适合做 Agent 行为分析、团队培训（"看看 Agent 是怎么读懂这个项目的"）、Code Review 复盘；(4) 对比 LangSmith / Vercel Agent Runs 的云端方案，Mindwalk 是本地优先的互补方案。
