Microsoft for DevelopersVS Code 1.147 Insiders：把「Agent 会话管理」做进编辑器

VS Code Insiders 更新到 1.147，这一版的重点不在编辑器本身，而在 AI 工作流：新增 Agent 会话管理、Chat 资源（resources）与 Markdown 编辑改进。所谓「会话管理」，指向的是多轮、长程 Agent 交互里绕不开的痛点——多个会话如何切换、上下文如何组织，而不是把每一次提问都当成一次性请求。

对每天把编辑器当 Agent 工作台用的开发者，这类更新比新语法高亮更值得关注：它决定了你能否在一个窗口里稳定跑长任务、并在多个任务之间保持隔离。Insiders 渠道意味着功能还会变，但方向已经明确——IDE 正在从「写代码的地方」变成「编排、观察、复盘 Agent 的地方」。

📎 来源: Microsoft for Developers — Visual Studio Code Team

meng shao / Berryxia腾讯开源 LoopForge：让 Coding Agents 按 SOP 交付，而不是靠提示词碰运气

腾讯开源了 LoopForge（MIT 协议），定位不是「再做一个编程助手」，而是给 CodeBuddy、Codex、Claude Code、Cursor CLI、OpenCode、Kimi Code、DeepSeek Harness 等现有 Agent 套一层「组织交付流程」。核心判断很反直觉：代码从来不是瓶颈，交接才是——让 Agent「修个 bug」，跑一次靠运气，可能跳过计划、忘测试、自己审自己、跑到一半停了没人发现。

LoopForge 把计划、写代码、审代码、测试拆成四个不同角色（写的人不审），用脚本退出码裁决编译/测试是否通过，关键节点停下等人签字，并在运行结束后用 runeval 给整条流程打分、提出改进建议。仓库和密钥留在自己的服务器，也提供了本地模式，一行命令即可在 Claude Code 里试：npx -y loopforge-cli@latest install claude，然后用 /start-devflow 起流程。目前是 v0.3，平台版需要 Docker、模型 key 自理。

📎 来源: meng shao (@shao__meng) · Berryxia.AI (@berryxia)

The JetBrains BlogTeamCity 实验性 AI Agents 插件：在 CI 构建里直接跑 Codex / Claude Code

JetBrains 发布 TeamCity 的实验性 AI Agents 插件，让编码 Agent 不再只跑在开发者本机，而是进入 CI/CD：可以用来审查代码、排查失败构建、更新文档。插件会把 Codex 或 Claude Code 安装到 TeamCity 构建代理上，在构建期间安全地注入凭证，并收集用量统计与 Agent 轨迹（trajectories）。

用法很直接：构建开始时插件检查客户端是否可用、缺失则安装；之后就能像普通 Command Line 构建步骤一样调用 codex 或 claude，LLM 供应商可自选。对想把「AI 做事」纳入可审计流水线的团队，这是把 Agent 变成标准构建步骤的信号——凭证生命周期跟着构建走，轨迹可回看，而不是散落在每台开发机上。

InfoQAWS 开源 Emulator：不用云账号，本地就能测 200+ 个 AWS 服务

AWS 开源并正式可用了一套本地 Emulator：一个本地 HTTPS 端点，由公开的 Smithy API 模型生成，让开发者和编码 Agent 在没有 AWS 账号的情况下，对 200 多个 AWS 服务做本地测试。它公开了各服务的「保真度分数」（fidelity scores），并明确记录了在 IAM、region、内存态（in-memory state）等方面的限制。

这条对两类人价值最大：一是写集成测试不想每次打真实云、也不想维护 Moto 之类手写 mock 的团队；二是让编码 Agent 在完全离线、可重复的环境里自验证代码——不用给它真实云凭证。需要留意的是，保真度分数和局限是官方自己标注的，涉及 IAM 鉴权语义、跨 region、持久化状态的用例，仍要回到真实环境验证。

InfoQGitHub 重建 Copilot App 的 Diff 视图：2200 文件、百万行 PR 不卡顿

GitHub 工程师重写了 Copilot App 的 diff 视图，目标是一个极端 PR：2200 个文件、超过一百万行改动、400 条行内评论。设计上的关键取舍是把「固定高度的代码行」和「可变高度的评论块」分开处理——评论块只在视口附近分批测量，从而避免一次性布局整个百万行文档。

性能不是靠感觉，而是靠约束：通过 CI 性能预算（budgets）和自动化 App 运行来卡回归。对做大型列表/虚拟滚动的前端团队，这是很典型的「混合高度虚拟化」范式——难的不是渲染代码行，而是夹在代码之间、高度不定的注释/评论块，如何在不全量测量的前提下保持滚动稳定。

Microsoft ResearchTokenEconomizer：复用历史会话，让编码 Agent 少花 18.4–30.9% 的 token

微软研究院开源了 TokenEconomizer 插件：因为开发者天天在同一个代码库里用编码 Agent，而 Agent 每次都从零开始——重新发现熟悉的事实、加载用不到的工具、重复失败过的尝试。这个插件从仓库里过去的会话中学习，在不修改 Agent 或其底层模型的前提下，减少未来会话的浪费。

在 277 个真实 bug 修复任务上，它在多个 AI 编码 Agent 上把成本降低了 18.4%–30.9%，所测每个仓库成本都下降，而任务成功率总体稳定。这条的价值在于它承认了一个现实：Agent 的浪费很大一部分来自「不记得上次学过什么」，而这件事可以在模型之外、用一层可插拔的记忆/经验来治。

DockerDocker Sandboxes + Firecrawl kit：给沙箱里的 Agent 一条受控的上网通道

Docker Sandboxes 里的编码 Agent 跑在隔离 VM 中，沙箱控制它能访问哪些主机，凭证留在宿主机、经由代理注入。问题也随之而来：这层控制同时挡住了 Agent 去读文档、看 changelog、查训练截止之后才发布的 API，于是它只能照着记忆里的旧版本写代码。常规「放开白名单」的解法，又把沙箱的安全收益还了回去。

Firecrawl kit 给出一条更收敛的路：只新增一个出口主机 api.firecrawl.dev，Agent 便获得网页搜索、页面抓取、站点爬取能力，且每个页面都以干净的 Markdown 返回。这是一个值得抄的模式——不是把整个互联网放进来，而是把「读网页」抽象成一个受控服务，用单点出口换取可审计与可限流。

LoopForge：把「团队交付流程」编译成 Agent 能执行的 SOP

// 关键词：角色分离 · 退出码裁决 · 检查点 · runeval 两层循环

大多数「AI 写代码」的方案都在优化模型这一步，LoopForge 反过来假设模型会犯错、会偷懒，于是把可控性放到模型外面。它的核心对象是「流程」：由 Agent 节点、脚本节点、人工审批节点、子流程节点组成一张有向图，按依赖推进，支持并行分支。规划、开发、测试、评审因此从「提示词里的提醒」变成「流程里的硬步骤」。

四条硬约束

  • 角色分离：计划、写代码、审代码、测试是四个不同的 Agent，写的人不审自己。
  • 脚本说了算：编译和测试过没过，看退出码，而不是听 Agent 自己说「好了」。
  • 人来签字：关键检查点停下来等人批准，可以打回到任意一步重做。
  • 沙箱与留痕：每个任务在 Docker 沙箱里跑，全过程有运行记录，可追溯。

两层循环：先修好这次，再改进下次

第一层在任务执行中发生：脚本和检查节点根据执行结果判断是否通过，失败后可以定向修复或重跑，并受最大尝试次数、返工次数限制；人也可以补充信息、批准结果或退回指定步骤。第二层在运行结束后发生：runeval 把运行轨迹整理成结构化事实，再由模型从控制流、耗时、工具浪费、Token 效率、错误恢复、交付完整性六个维度打分，并给出「流程补丁」——比如调整重试策略、增删角色检查规则、补充角色提示词。

# 概念上的执行循环（非官方伪代码）
for task in tasks:
    plan  ← agent_plan(task)
    code  ← agent_code(plan)            # 写的人不审
    review← agent_review(code)
    ok    ← run_tests(code).exit_code == 0  # 退出码裁决
    if not ok: retry_or_human(code, max_retry)  # 定向修复/返工
    if checkpoint: wait_for_human_approval()      # 关键节点签字

score, patches ← runeval(run_trace)   # 6 维打分
propose(patches); # 补丁待人工应用，不自动改 SOP

边界要说清楚

官方口中的「自进化」，主要是根据执行反馈改进流程和角色规则，不是训练模型，也不等于系统会无人干预地持续变强——提示词明确禁止整份重写 SOP、修改连线或删节点，建议先以「待应用」状态存在，由人审后再生效。仓库的验收文档记录了一次真实用例：CodeBuddy 配合 deepseek-v4.1-flash 跑通了规划、编码、测试。对想给团队 Agent 加「流程护栏」的人，这是目前少见的、把「谁来验收」讲明白的开源实现。

📎 来源: meng shao (@shao__meng) — 机制拆解 · Berryxia.AI (@berryxia) — 上手与限制

百万行 PR 怎么不卡：GitHub Copilot App 的混合高度 diff 渲染

// 关键词：固定行高 · 可变高评论块 · 视口批测 · CI 性能预算

一个有 2200 个文件、超过一百万行改动、400 条行内评论的 PR，会同时击穿两类假设：一次性布局整个文档会爆内存；而简单的固定行高虚拟滚动，又容不下夹在代码之间、高度不定的评论块。GitHub 团队的做法是承认这两种元素性质不同，分开处理。

核心取舍

  • 代码行固定高度：可预测，适合虚拟化——只渲染视口内的一小段，滚动位置直接算偏移量。
  • 评论块可变高度：内容长度不定，无法预先算总高度；只在接近视口时分批测量（batched measurement），把测量成本摊到滚动过程中，而不是一次性全量。
  • 性能写成预算：把渲染耗时、滚动帧率等指标做成 CI budget，回归即失败；配合自动化 App 运行，防止「本地看着还行」蒙混过关。
# 混合高度虚拟滚动的心智模型
rows   = pr.diff_rows              # 固定高度，可预算偏移
blocks = pr.inline_comments        # 可变高度，需测量

visible = viewport_range(scrollTop)
for block in near(visible, margin): # 只测视口附近的评论块
    block.height ← measure(block)     # 分批，不阻塞首屏
render(visible_rows + measured_blocks)
assert perf ≤ ci_budget             # 性能预算卡回归

为什么值得借鉴

这套模式适用于任何「大小元素混排 + 超长列表」的场景：日志查看器（固定行 + 可展开的堆栈）、聊天记录（消息 + 可变附件卡）、文档（段落 + 代码块 + 图片）。要点不是某个库，而是三条工程纪律——按可预测性给元素分类、把不可预测的测量推迟并批量化、把性能指标固化进 CI。三者缺一，百万行级别的输入就会把「看起来的流畅」打回原形。

// 可直接落地

把 Agent 当「会话」，而不是「请求」来分配资源

Google 的 GKE 实践给出一个反直觉结论：AI Agent 会话一天里大部分时间既在活动、也在空转，传统「一个 Pod 一个会话」的分配方式极度浪费集群资源。做法是用 Agent Substrate + AX on GKE，把空闲会话「停泊」到对象存储里释放算力，需要时再恢复会话状态。结果是 Kubernetes 节点成本最高可降 40%。落到你自己的部署上：先统计会话的活跃/空闲比例，再决定是常驻还是可挂起/恢复，别默认「一直开着」。

📎 来源: Google Developers Blog

沙箱 Agent 联网：单一出口 + 凭证留宿主

不要让「能读文档」变成「能访问一切」。参照 Docker + Firecrawl 的做法：只放行一个受控出口主机（如 api.firecrawl.dev），由它代理搜索/抓取并返回干净 Markdown；凭证留在宿主机、经代理注入，不进入沙箱环境。这样既让 Agent 拿到训练截止之后的新文档，又保留了可审计、可限流、可一键关停的边界。凡是需要「更宽的网」，优先加一个受控服务，而不是加一条通配白名单。

📎 来源: Docker

在 CI 里跑编码 Agent 的正确姿势

TeamCity 的插件示范了三个要点，可迁移到任何 CI：① Agent 客户端装到构建代理上，构建开始前检查、缺失则安装，保证环境可复现；② 凭证只在构建期间注入，用完即失效，不落到镜像或日志；③ 采集用量统计与 Agent 轨迹，让「AI 在流水线里做了什么」可回看、可审计。适合先从不写回主干的任务切入——代码审查、失败构建排查、文档更新。

📎 来源: The JetBrains Blog

本地集成测试别再依赖真实云账号

AWS 开源 Emulator 提供本地 HTTPS 端点、覆盖 200+ 服务、无需账号，由公开 Smithy 模型生成，并公开了每个服务的保真度分数。落地建议：先在 CI 和 Agent 自验证环节用它替代「必须连真实云」的集成测试；同时把它文档化的限制（IAM、region、内存态）当成边界——鉴权语义、跨区、持久化这类用例仍回真实环境验证。收益是测试可离线、可重复，Agent 也拿不到真实云凭证。

📎 来源: InfoQ

让 Agent 复用「上次学到的东西」来省 token

成本优化不一定靠换更便宜的模型。TokenEconomizer 的思路是：把同一仓库历史会话里的经验沉淀下来，在后续会话中提前告诉 Agent「这个代码库里已经确认过什么、哪些工具用不上、哪些路子试过失败」。实测 277 个 bug 任务、多个 Agent 上省 18.4%–30.9% 且成功率稳定。自己实现时，从「仓库级事实 + 失败尝试记录」两类最小经验做起，注意及时失效，避免把过时结论当事实喂回去。

📎 来源: Microsoft Research Blog · Microsoft Research

工具定义塞满上下文时，让 Agent「写代码」来编排

AI Engineer Code Summit 上，mitsuhiko（@earendilworks）主张：与其在上下文窗口里塞几千条工具定义、让模型逐个挑，不如给 Agent 一个能跑 JavaScript 的沙箱，让它把多次工具调用编成一段工作流。好处和 Claude Code 的 Code Mode 一脉相承——独立调用可并行、上一步结果在代码里直接传给下一步不必绕经模型、中间输出先在代码里过滤再回传以省 token。适用信号很明确：工具数量爆炸、且经常需要「连续调好几个再汇总」的场景。

把 Traces 当成和 Git 同级的新原语来「拥有」

Vercel 的 Guillermo Rauch 提出：Git 用「代码增量」让人类协作，而 Traces 更强——它记录了上游意图、提示词、推理、用到的技能与工具，是团队的「智能资产」。可落地的动作：① 先安全地采集并自持 traces；② 基于其中的摩擦、延迟、结果反馈，搭建递归自我改进的回路。配合「开放 SDK/harness → 用网关掌控模型选择 → 拥有 traces 与数据并强制 ZDR → 私有推理拥有模型」这条路线，避免把最关键的过程数据留在别人手里。
