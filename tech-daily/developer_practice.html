安全xAI Grok Build CLI 被曝静默打包整个仓库上传云端，含 .env 密钥

社区对 Grok Build CLI 的逆向分析发现：每次 session 开始和结束时，CLI 会把当前工作目录的完整状态（含 git 历史和所有文件）打包成 tar.gz，静默上传到 xAI 控制的 gs://grok-code-session-traces 存储桶。即使用户在配置里关闭改进选项，上传仍然继续，而且会跨项目抓取 .claude 配置目录里的 API 密钥。Reddit 上有开发者用合成仓库验证后确认了该行为，并给出了关闭方式。

# ~/.grok/config.toml
[features]
telemetry = false          # 关闭 trace_upload
remote_fetch = false       # 阻止远程配置下发

[telemetry]
trace_upload = false       # 直接禁用 session trace
mixpanel_enabled = false

[harness]
disable_codebase_upload = true  # 禁止代码仓库上传
为什么值得你看：这不是"模型读取你代码"的正常行为，而是绕过 Agent 视野的独立通道。在你允许任何 CLI Agent 接触生产仓库前，先确认它的数据外发策略。同样的检查应该应用到 Claude Code、Cursor、Codex CLI 等所有同类工具——任何能访问 $HOME 的 CLI 都可能"顺手"带走不该带走的东西。如果你已经在用 Grok Build，建议立刻执行上述配置并 rotate 所有暴露过的 API Key。

内核Meta 用 sched_ext BPF 调度器把广告系统 p99 延迟压低 28%，省电 3.28 MW

Meta 工程博客披露了他们在 Linux 内核升级时遇到的一个隐性回归：广告系统整体 p99 延迟被新调度器拖累。团队最终选择 sched_ext —— Linux 上游的 BPF 可扩展调度框架，为广告检索工作负载定制了一个调度策略。结果：广告检索阶段 p99 延迟下降 28%、能耗降低 3.28 兆瓦、广告排名条数提升 1.1%。该系统日均处理 4000 亿次请求、峰值 500 万次/秒，每个毫秒都很值钱。

为什么值得你看：sched_ext 是这两年 Linux 内核最值得关注的方向之一——把 CPU 调度从"内核编译期决定"变成"运行时 BPF 程序决定"。Meta 的案例证明，对于高吞吐、对延迟极度敏感的业务，通用调度器往往拿不到最优，按工作负载定制是值得的。如果你在维护大规模低延迟服务，值得花时间了解 sched_ext 的编程模型，尤其它和 cgroup、CPU isolation 的组合用法。

🔬深度技术解读

长文PostHog：用并行 Claude Code 会话重写 SQL 解析器，16K 行代码 + 70x 性能

PostHog 工程师 Robbie Coomber 分享了他们迁移 SQL 解析器的完整过程。背景是 PostHog 给用户提供 SQL 接口，但底层数据存在 ClickHouse 里——他们需要一个解析器把用户 SQL 转成 AST，再翻译成 ClickHouse SQL。原解析器是 Python 写的，性能瓶颈明显。Coomber 用多个长时间运行的并行 Claude Code 会话，重写出一个 16K 行的手写解析器、5K 行工具代码、几千行测试代码，整体性能提升约 70 倍。

最关键的方法论是"搭建验证闭环而不是写代码"——他花在写"如何验证新解析器和旧解析器等价"的工具上的时间，远多于让 Claude 写解析器本身。最终新解析器在所有真实业务查询上都和旧解析器等价，只在极少数"SELECT SELECT FROM FROM WHERE WHERE AND AND"这种刻意构造的边缘案例上有差异。文章给出了完整的 harness 设计：每个 Claude 会话负责一个独立模块、共享一个回归测试集、每次改动必须让所有测试通过才能合并。

实践建议：(1) 当你要用 Agent 重写一个有存量行为的系统时，先建一个"双跑对照"的测试框架，让新旧实现同时处理同一输入，diff 输出；(2) 把 Agent 的并行度提上去的关键不是开更多会话，而是把工作拆到 Agent 能独立验证的粒度；(3) 保留边缘案例库——Coomber 提到的"恶作剧之神"测试用例，是验证解析器鲁棒性最有价值的资产；(4) 70x 性能提升的核心来源是 Python → 原生代码 + 重写 AST 结构，不要把 Agent 当成性能优化的银弹，它只是一个高水平的执行者。

方法Simon Willison：Agent 不该是 DRI —— Directly Responsible Individual 必须是人类

Simon Willison 在新博文里展开讨论了 DRI（Directly Responsible Individual）这个概念在 LLM Agent 时代的适用边界。这个源自 Apple、后被 GitLab 等公司沿用的管理术语，指"对一个项目、倡议或活动的成败承担最终责任的人"。Willison 的论点非常明确：Agent 永远不应该成为 DRI。因为 DRI 的本质是"对结果承担 accountability"，而机器无法承担责任——责任必须落在能解释自己决策、能承担后果的人类身上。他引用了 IBM 1979 年培训幻灯片里那句著名的话："A computer can never be held accountable, therefore a computer must never make a management decision."

这个观点值得和门罗社区里另一个热议对照——当 Anthropic 把 Fable 5 订阅延到 7 月 19 日时，有用户为了"用满" Fable 5 不眠不休，最后压力过大进了医院。当事人自己发帖说："FYI my conclusion was that I am the idiot"——这是把 Agent 的能力边界和自己的身体边界都搞错了。Agent 越强，人类作为 DRI 的角色就越重要，包括决定什么时候该停。

实践建议：(1) 在你的项目里明确每个 Agent 工作流的"DRI 是谁"，写到文档里；(2) 任何对外可见的决策（合并 PR、部署生产、发送邮件、修改客户数据）都必须由 DRI 明确签字确认，Agent 只能起草不能拍板；(3) 把"Agent 产出需要人类 DRI 复核"这条作为团队规约，而不是依赖个人自觉；(4) 当你自己开始像那个进医院的用户一样"为了用满额度拼命"时，停下来想想谁是 DRI。
📎 来源: Simon Willison's Weblog — Directly Responsible Individuals (DRI)

哲学antirez：Control the ideas, not the code —— 程序员角色的根本转变

Redis 作者 Salvatore Sanfilippo（antirez）发布了一篇长文，标题是《Control the ideas, not the code》。文章背景是他 2024 年 1 月就开始写"AI 编程"相关的博文，最近重新加入 Redis 同时还在做一个本地 LLM 推理的开源项目。作为" relatively well regarded programmer"，他的核心论点是：程序员的核心价值正在从"写代码"上移到"控制想法"——架构、抽象边界、问题分解、取舍。代码本身已经是 Agent 的执行层，程序员不再是打字员，而是系统设计师。

他特别提到自己为什么持续说"人们不想听的话"："I feel the urge of lowering the impact for people less prepared to the change than me, often younger than me, and that, unlikely me, didn't see many of those things coming." 这篇文章和 Lenny 的年度调查形成呼应——调查显示 50% 的技术从业者觉得 AI 放大了自己的能力，27% 觉得角色正在重写，14% 感到失去稳定。这两种情绪的同时存在，恰恰说明"控制想法"的能力正在替代"执行能力"成为分水岭。

实践建议：(1) 回顾你过去一周的代码，统计有多少时间是"想"出来的、有多少是"敲"出来的——如果敲的比例还在 80% 以上，你已经在贬值通道里了；(2) 把"控制想法"具象化：画架构图、写 ADR、做技术预研、跟用户聊需求，这些活动的权重应该在你的时间表里上升；(3) 不要试图和 Agent 比打字速度，要和你自己比"判断力提升速度";(4) 如果你带团队，开始把"想法清晰度"纳入工程师考核——能不能用一段话讲清楚为什么这么做，比代码行数重要得多。

🛠工具推荐

测试Skillgrade 2.0：给 Agent Skills 写单元测试的开源框架

Minko Gechev 开源的 Skillgrade 2.0 是一个"Skills as Tests"的工具。核心理念是 "Don't ship skills without evals"——Skills 也需要测试，不要发布没有评估的 Skills。它的前身是 Skill Eval 框架，2.0 版本彻底重写：从"你在框架之上搭建项目"变成"一个全局安装、指向 Skill 目录即可运行的工具"，所有配置收敛到单个 eval.yaml 文件，零脚手架、零项目结构学习成本。

# 三步即可运行
npm i -g skillgrade
cd my-skill/ && skillgrade init
skillgrade --smoke

# 评分器设计
1. Deterministic Grader (70% 权重)
   bash/TS 脚本输出 {score, details, checks}
   用于回答"结果对不对"

2. LLM Rubric Grader
   把会话记录交给另一个 LLM 评审
   评估"过程是否合理"
为什么推荐：Skills 在 Codex / Claude Code 里越来越像"配置即代码"，但大多数团队发布 Skills 靠的是"我跑了一下觉得行"。Skillgrade 把 Skills 的发布标准拉到了和代码同一水平——每个任务跑多次 trial 统计通过率，而不是一锤定音。如果你团队已经积累了 10+ 个生产 Skills，引入这个工具能避免"改了 A 没想到弄坏了 B"的回归问题。
📎 来源: GitHub — mgechev/skillgrade  |  X / meng shao — 给 Agent Skills 写单元测试

CLIOfficeCLI：让 AI Agent 操作 Office 文件的命令行工具，1.3 万 Star

iOfficeAI 开源的 OfficeCLI 是一个 单文件二进制、不需要安装 Microsoft Office 的 Office 自动化工具，让 AI Agent 能读取、编辑、生成 Word、Excel、PowerPoint 文件。之前 Anthropic 官方提供了 PowerPoint/Excel/Word/PDF 的预置 Skills，MiniMax 也开源过 minimax-xlsx 等办公文档 skill，但路线都偏"封装 Python 库"。OfficeCLI 选择了更工具化的路径——把所有 Office 操作统一收进一个 CLI，Agent 只需要调命令就能完成"读取 Excel → 修改某列 → 生成图表 → 导出 PPT"的完整流程。

质量百度 Geek 说：AI Coding 下的质量关卡 —— 把验证流程左移

百度团队分享了他们在 AI Coding 大规模落地后建立的质量保障体系。核心思路是 "把验证流程左移"——传统质量保障依赖提交后的人工 CR 和 QA 测试，但在 Agent 高频产出代码的场景下，所有问题都等后面环节才发现，协作成本只会更高。他们的链路是：Agent Operating Rules → Code Validation → Runtime Verify → Figma To Verify → Pipeline Code Review → 问题结构化 → Agent 辅助修复 → 重新验证 → 沉淀为 Skill/Rules。

身份AWS Bedrock AgentCore：多租户 Agent 的 on-behalf-of Token Exchange 实践

AWS ML 博客发布了一篇针对多租户 Agent 部署的深度指南。核心问题：当 Agent 调用下游 API 时，应该带谁的身份？用 Agent 自己的服务身份会让审计追踪崩溃（下游系统必须无条件信任 Agent）；直接转发用户 Token 又会让每个下游工具变成"困惑的代理"（confused deputy）。这两种方案在一个 Agent 服务多租户、用户不在场的场景下都不可扩展。

解决方案是 OAuth 2.0 Token Exchange（RFC 8693）——Amazon Bedrock AgentCore Identity 原生支持这种 grant type。流程：用户登录后 IdP 颁发 Token → Agent 收到 Token 后，不直接使用，而是向 AgentCore 发起 Token Exchange → AgentCore 验证后颁发一个新的"代理 Token"，里面携带原始用户身份 + Agent 身份 + 授权范围 → Agent 用这个新 Token 调用下游服务 → 下游服务可以独立验证 Token 并做出授权决策。

什么时候用：(1) 你的 Agent 要替用户调用多个下游 API（邮件、日历、CRM、内部系统）；(2) 你面临合规审计要求，需要知道"哪次调用是哪个用户的哪个 Agent 发起的"；(3) 你不能让下游服务盲目信任 Agent。如果你正在做企业级 Agent 平台，这一篇是绕不开的标准参考——即使你不部署在 AWS 上，Token Exchange 的设计模式可以直接搬到你的身份系统里。
