DeepSeek Harness + Cordis：为什么「一切皆插件」不是营销口号

DSH 那句「Everything is a plugin」容易被当成宣传话术，但看完源码级拆解和那篇 88 页的 Cordis 论文，会发现它是有实底子的。整套架构建立在北大 & DeepSeek-AI 的元框架 Cordis 之上——这是一个与 LLM/Agent 无关的通用插件框架（Shigma 系聊天机器人框架 Koishi 就是它的用户），负责依赖注入、作用域服务与生命周期清理。DeepSeek 把 Cordis 直接 vendored 进来，把模型适配器、工具注册表、会话、存储、沙箱、Agent Loop、Web UI、四种运行模式全部插件化。腾讯技术工程的实测指出，Cordis 同时解决五个通常彼此分离的问题：插件在当前位置能看到哪些能力；依赖能力缺失时是否启动；同名 service 能否在不同作用域解析到不同实现；插件退出时注册项/监听器/进程由谁收拾；静态配置怎样变成可热更新的运行时插件树。

  • 插件的「装卸」是有纪律的： 论文《A Programming Paradigm for Spatiotemporal Composability》的要点是插件不仅要装得上，还得拆得干净——一个 Agent 连续工作两三个小时后，旧插件留下的监听器、定时器和服务必须按依赖顺序正确关闭。这一点直接回应了「插件化不就是浏览器扩展吗」的质疑。
  • PTC 模式才是隐藏大招： 社区实测发现「PTC（程序化测试）模式」和 Cordis 插件系统才是 dsh 真正区别于其他 CLI 的点——工具执行默认走独立沙箱式 Code Mode，把风险边界与审批策略做成可替换插件。
  • 生态已经长出来： 桌面端（anywhere-labs，免 Node.js）、Web UI 皮肤/侧边栏工作台、终端 TUI 插件（Claude Code 风格全屏交互）、dsh-attachments（补上官方缺失的上传文件功能）、dsh-inspector 等社区项目 2 天冲到 4K+ star。官方 dsh 仓库 Star 数从 50k 迅速逼近 100k。

对想基于 DeepSeek 模型搭内部 Agent 平台的团队，DSH 提供了比「从零写 harness」低得多的起点；对只想用它的开发者，先跑 npx @deepseek-ai/dsh web 或 ollama launch dsh，理解标准 / PTC / 极简 / 创造四种模式是上手关键。

Vercel Zero 语言：当编译器的主要读者变成 AI，工具链该怎么重新设计

Zero 的核心假设很颠覆：过去编译器把源码编译给人看（可读的报错、符号化的调试信息），而 Vercel 赌的是未来的主要「阅读者」是 AI 智能体。它把这一假设贯彻到了工具链的每一个角落——所有子命令统一 --json 输出，错误码是 NAM003 这种稳定的机器可读代码，修复建议是带类型的元数据；zero fix --plan --json 把「修复计划」本身当成一等公民返回，智能体可以接受、编辑或拒绝，而不是盲目应用。这实际上是在给 LLM 写「编译器级 API」。

  • 副作用显式化： 任何与外部世界交互的函数都必须接受一个 World 能力参数，由编译器强制执行。只看函数签名就能判断代码能否访问网络、文件系统或标准输出——这对让 AI 安全地操作代码是巨大的可审计性提升。
  • 图优先（graph-first）创作： v0.3.0 起 zero.graph 二进制存储才是编译器的输入，.0 文本文件只是供人类阅读的投影，智能体通过 zero query 直接查询图结构。语言不再是「写给编译器的文本」，而是「智能体可操作的图 + 给人看的投影」。
  • 工程数据： v0.3.4，GitHub 5200+ star；Hello World 一毫秒构建、16.2 KiB 二进制。关注体积/速度的团队可以把它当作一个「AI 时代系统语言」的方向样本，短期不必替换任何现有语言。

对开发者来说，Zero 现在还不是生产选项，但它值得当作「AI-first 语言/工具链设计」的参照系：稳定错误码、机器可读修复计划、能力边界签名化，这三条几乎是任何「让 Agent 安全地写代码」方案的共同归宿。

吴恩达团队发布「AI Engineering 技能图谱」：四种核心能力拆解

DeepLearning.AI 分析了超过 1 万份 JD，并对 AI 专家、招聘经理与猎头做了数十次结构化访谈，得出 AI Engineering 的四个核心技能。其一，构建与部署 AI 应用——核心是「纪律严明的评估与错误分析闭环」，因为 LLM 输出不可预测，必须用统计方法度量、引导、治理。其二，软件工程基本功——不懂基本功的开发者做 vibe coding，往往不知道给编程智能体提供什么上下文，也无法察觉智能体在替自己做糟糕的架构决策；基本功的价值正从「亲手写代码」转移到「用精确的工程语言驾驭智能体」。其三，使用编程智能体——对智能体能力与局限的心智模型、管理上下文、提供验证器让智能体自主闭环、编写清晰规格说明、编排多智能体。其四，塑造构建方向——当智能体能「按规格交付」，工程师的价值重心上移到「决定规格里该写什么」，需要产品 Sense 与商业上下文。这份图谱可作为团队能力建设和个人学习路线图。

运行时无关的 AI 工作流：生产稳定性和快速评估迭代，如何同时要

InfoQ 这篇文章给出 Brex AI 工作流平台（TypeScript，5 人团队维护，跑在 K8s + Temporal Cloud 上）的取舍模式。矛盾在于：生产环境的持久性需要一个重量级、分布式的持久化运行时；而 LLM 输出的质量会随每次 prompt 微调或模型变更漂移，必须靠评估——即「在标注数据集上离线跑工作流并打分」——来做回归验证，这需要一个轻量、可在几秒内重跑的进程内循环。大多数技术栈只围绕其中一种运行时构建。Brex 的解法是把「工作流协调逻辑」与运行时解耦，让同一套工作流既能在 Temporal 上持久运行、也能在进程内快速评估。对正在用 Temporal / AWS Step Functions 之类编排 Agent 且被「评估跑不起来」困扰的团队，这是一个值得复制的模式。
