eBPF

GitHub 如何用 eBPF 提升部署安全性

GitHub 的一个独特挑战是：github.com 托管着自己的全部源码，而为了部署 GitHub，又需要 GitHub 本身可用。这就形成了一个危险的循环依赖。除了代码镜像和回滚资产外，部署脚本本身也可能引入对内部服务的新依赖。

GitHub 的解决方案是使用 eBPF 在部署过程中实时监控和拦截系统调用。eBPF 程序可以在内核态运行，无需修改应用代码或重启服务，就能检测部署脚本是否尝试访问尚未声明的依赖服务。这种"部署时安全网"让团队能够在 CI/CD 流程中尽早发现循环依赖和配置漂移问题，而不是等到生产环境才暴露。

对于运维大规模系统的开发者来说，这个案例展示了 eBPF 不只是可观测性工具，它还可以作为部署防护机制嵌入到发布流程中。

[来源: The GitHub Blog]

Architecture

Cloudflare Artifacts：为 Agents 打造的 Git 原生版本化存储

Cloudflare 提出了一个新的基础设施原语：Artifacts。他们认为，未来 5 年生成的代码将超过人类历史上所有编程的总和，而现有的源代码控制平台是为人类设计的，无法应对 agents 10x 规模的增长。

Artifacts 被定义为一个"分布式、版本化的文件系统"，原生为 agents 设计。它保留了 Git 的语义（分支、提交、合并），但针对 agents 的无睡眠、多任务并行特性做了优化。对于正在构建 agent 工作流的开发者来说，这预示着一个新的底层存储范式可能出现——不再仅仅是"给 agent 一个 repo"，而是"整个版本控制系统为 agent 重新设计"。

[来源: The Cloudflare Blog]

AI DevMem0 发布 token-efficient memory 算法：降低 3-4 倍成本

Mem0 的新算法在 LoCoMo、LongMemEval 和 BEAM 基准上取得了与全上下文方法相当的成绩，但平均每次检索调用仅消耗约 7000 token（全上下文方法通常超过 25000 token）。核心变化是从之前的"两阶段识别+调和（ADD/UPDATE/DELETE）"改为"单遍 ADD-only 提取"。

实践启示： 当信息变化时，新旧事实同时保留，系统推理的是"事物如何演变"而非"最终状态是什么"。这带来了约 50% 的提取速度提升，同时大幅降低成本。对于在自己的 agent 中实现长期记忆的开发者，这是一个值得借鉴的设计思路：减少状态机的复杂度，用追加式存储换取性能和成本的优化。

[来源: mem0]
