LiteRT 是一个面向移动端开发者的生产级 AI 推理框架，核心卖点在于通过统一 API 屏蔽底层 NPU（神经处理单元）的硬件差异。相比传统的 CPU/GPU 推理方案，NPU 在执行视频实时处理、动画生成、语音识别等任务时能显著提升能效比并降低电池消耗。Google Meet 和 Epic Games 已经在生产环境中使用 LiteRT 部署 AI 模型。框架内置了基准测试工具，且支持跨平台部署——从手机到 AI PC 再到工业物联网设备。对于需要在端侧运行 AI 但又不想陷入硬件适配泥潭的开发者，LiteRT 提供了一个值得评估的方案。

训练优化

连续检查点：Orbax + MaxText 的可靠性新方案

在大规模分布式模型训练中，检查点（checkpoint）策略一直是一个需要权衡的难题：保存太频繁会拖慢训练速度，保存太稀疏则在故障时丢失大量进度。Google 在 Orbax 和 MaxText 中引入了连续检查点（Continuous Checkpointing）机制来解决这个矛盾。与传统的固定间隔保存不同，连续检查点采用异步流水线——只有当上一次保存操作成功完成后，才会启动下一次保存。这种方式最大化利用了 I/O 带宽，同时将故障时的数据丢失窗口缩到最小。基准测试表明，在大规模训练任务（MTBF 较短）中，该方法显著减少了检查点间隔并节约了大量计算资源。如果你正在使用 JAX/Flax 或 PyTorch 进行大规模训练，且当前采用固定间隔检查点策略，建议评估 Orbax 的连续检查点功能。特别是对于租用抢占式实例或者训练任务持续数天以上的场景，这个优化可以显著降低因故障导致的重复计算成本。

Agent 优化

生产环境 Agent 的持续进化：Pydantic AI + Logfire 实践

Pydantic 创始人 Samuel Colvin 在这个工作坊中展示了如何在 Agent 已经上线运行后持续优化它，而无需重新部署或重启服务。核心思路是将提示词（prompt）、模型选择和其他参数抽象为可管理变量（managed variables），支持在运行时热更新。关键实践点包括：用真实数据集对比不同 prompt 变体的效果进行 A/B 评估；以及 GEPA（进化式 Prompt 优化）——从生产环境的 trace 和用户反馈中自动进化出更优的 prompt。这套方法的本质是把"上线即结束"转变为"上线只是开始"——Agent 的 prompt 和配置应该像传统软件的 feature flag 一样可以被动态管理和回滚。如果你正在用 Pydantic AI 或类似框架构建生产级 Agent，建议参考 Logfire 的观测方案来实现这套闭环优化流程。

扩散式投机解码：TPU 上实现 3 倍 LLM 推理加速

UCSD 研究团队在 Google TPU 上成功实现了 DFlash——一种基于块扩散的投机解码方法，突破了传统自回归草稿生成的顺序瓶颈。与逐 token 预测不同，DFlash 在单次前向传播中"绘制"整块候选 token，平均加速达到 3.13 倍，峰值性能几乎是现有 EAGLE-3 方法的两倍。该开源实现已集成到 vLLM 生态中，通过利用 TPU 硬件的"免费"并行验证能力和高质量草稿预测，对复杂推理任务的优化效果尤为显著。对于在 TPU 上运行大规模推理服务的开发者，这是一个可以直接接入的性能提升方案。

构建生产级 AI Agent 的 5 条经验

如何测试非确定性的 Agent 行为

GitHub Copilot Coding Agent 的团队写了一篇关于 Agent 测试的深度文章。当 Agent 开始与真实环境（UI、浏览器、IDE）交互时，"正确"不再是单一确定的——加载时间可能变化、多个操作序列可能达到同一结果，传统的断言式测试会产生大量"假阴性"。解决思路包括：用结果导向的验证替代路径导向的验证——验证最终状态是否满足目标，而不是强制 Agent 走特定路径；为测试环境引入可控的随机性来验证 Agent 的鲁棒性；以及使用 GitHub Actions 的重试机制和超时配置来减少 flaky test 的影响。对于正在构建需要与外部环境交互的 Agent 的开发者，这套测试策略值得直接借鉴。

JetBrains 插件开发：适配远程开发新模式

JetBrains IDE 的远程开发模式正在改变插件的架构假设：IDE 不再是一个单一的本地进程，而是前端客户端与后端服务的分离架构。后端可以运行在 Docker、云端或其他远程机器上。对于插件开发者来说，这意味着需要重新考虑哪些逻辑应该运行在前端、哪些应该在后端。关键适配点：UI 相关功能和延迟敏感的功能（如代码补全、实时错误检测）如果放在后端运行，可能会因为网络延迟导致体验劣化。JetBrains 建议将计算密集型任务放在后端，而将需要即时响应的交互逻辑保留在前端。
