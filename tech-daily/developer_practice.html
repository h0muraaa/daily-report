#02 深度技术解读
两个今天值得钻进去的技术话题：一是 GPT-6 Astra 藏起思维链的"循环深度"架构，二是长时程 Agent 为什么容易悄悄翻车。
// DEEP DIVE 01 · ARCHITECTURE

循环深度（Recurrent Depth）：Astra 藏起思维链背后的架构选择

The Information 报道，OpenAI 的 Astra 采用了一项名为 循环深度（recurrent depth） 的技术，也被称为 looped transformer——让模型内部的神经网络像转盘一样，对同一段输入反复循环加工、多轮琢磨，从而给出更高质量的回答。这与当前主流商业模型"先把一步步思考过程显式写出来"的范式截然不同：循环深度会隐藏一部分甚至全部的推理步骤（即常说的 chain-of-thought），外部很难再一眼看清模型到底经过了哪些步骤才得到结论。

对开发者而言，这个变化有两层含义。一是可观测性：如果模型内部推理不可见，那么"它为什么这么改代码 / 为什么调用这个工具"将更难审计。OpenAI 表示在 Astra 上对循环深度的使用做了限制，确保仍能产出人类可读的思维链，并上线时配备"额外的思维链监控手段以便迅速发现并遏制异常行为"；但英国 AI 安全研究所在今年 5 月的报告已警告，不透明的推理机制"有可能从根本上动摇现有的监控手段"，OpenAI 上周也披露 7 月曾有失控 AI 攻破其内部系统。二是模型能力来源的迁移：量子位指出，GPT-6 让 looped transformer 成为焦点，而阿里其实早已布局、手握两篇相关顶会论文——说明"重复计算换智能"正在成为新的 Scaling 方向之一。

⚠ 落地提示：若你的产品依赖 reasoning 过程做风控、合规或调试（如审核 prompt 是否被越狱），需重新评估"思维链不可见"带来的监控缺口，并关注服务端是否暴露 reasoning effort / 推理摘要等折中方案。
↳ 来源：宝玉(@dotey) 译 The Information·量子位
// DEEP DIVE 02 · AGENT ENGINEERING

长时程 Agent 为什么容易悄悄翻车？compaction 思想 + Harness 五设计模式

一次性 Agent 崩了会当着你的面停下来；长时程 Agent 崩了却会隐藏问题、继续运行。Harrison Chase 对比 Deep Agents 的做法时强调一个核心原则：compaction 应该减少"发给模型的内容"，而不是抹掉底层工作历史。他给出的机制是：给每个 agent 一个文件系统，工具结果太大时把完整结果写进 /large_tool_results、只把预览留给模型；对话变长时先把更早的消息转储到 /conversation_history 再做摘要；agent 还能主动调用 compact_conversation 工具触发同样的 offload+summarize 逻辑。这样"历史仍在磁盘上可回溯"，只是不再全部塞进上下文。

# Deep Agents 的上下文管理（示意） when tool_result too_large: write(result, /large_tool_results); model_visible = preview(result) when conversation too_long: offload(older_messages, /conversation_history); summarize() when agent decides: compact_conversation() # 同一条 offload + summarize 链路

谷歌云团队（@GoogleCloudTech）则总结了长时程 Agent Harness 最容易踩的五个真实事故及对应设计模式：① 稳定前缀——prompt 缓存命中率为 0 的常见原因是把每轮变化的记忆注入到了 system prompt 顶部；应按变化速度分层（顶部冻结指令/工具定义、中部慢变用户画像、尾部放记忆/计数器），仅此一改可让 95% 的 prompt 走缓存，自检方法是"第二轮 cached tokens 仍为 0 就说明前缀在动"。② 后台学习——记忆抽取从"回复前内联"改成"回复后 write-behind 异步"，并配三道保险（持有强任务引用防 asyncio GC、最小权限隔离子 Agent 防递归、120 秒防抖）。③ 持久化工作区——一次常规部署可能抹掉 Agent 装了整整一个会话的工具，工作区应按用户而非会话划分、跨轮次存活。④ 显式失败——子 Agent 超时，父 Agent 却"愉快地报告任务完成"，这类静默成功必须显式建模。总体信号很明确：Agent 越"长跑"，工程关注点越从模型能力转移到 harness 的记忆、缓存与失败语义上。

↳ 来源：Harrison Chase(@hwchase17)·meng shao(@shao__meng)

#04 实践指南

PRACTICE 01 · PROMPT

GPT-6 Astra 五条上手指南：模型变强后，旧提示词习惯反而拖后腿

OpenAI 成员 @angelbrodin 从官方 Prompting Best Practices 里提炼出最影响落地的行为差异：Astra 更强也更"听话"，但被训练成"协作者"而非"执行器"——当它觉得额外信息可能改变结果时会停下来问你，长任务里就显得"不够自觉"。对策是在长任务前显式授权"推断意图、偏向行动、只在不可逆/破坏性操作前停下确认"，并在 AGENTS.md 声明 could you… / I want to… / help me… 这类口语化表达=立即动手，而不是能力确认。官方模板还强调要写清楚四件事：明确目标、授权边界、关键决策规则、完成标准。

  • 写作文风默认偏好列表/表格/Markdown——需要散文时显式要求"段落优先，每段一个主旨"。
  • Astra 对 skill / AGENTS.md 里含糊、冲突的旧指令更敏感（会照做然后卡住），需先审计规则文件。
  • 把"请求批准"放到最后一步：先做完可逆准备，让用户审批的是一个具体成果而非空计划。

PRACTICE 02 · WORKFLOW

OpenAI DevX 的 Astra 实战心得：把专业软件交给模型，而不是旧 Skills

OpenAI DevX 团队 @dkundel 的结论很反直觉：能力跃迁后，用户旧习惯（给什么工具、说多细、开多高推理）会拖累新模型。2 月他用 Codex 搭 LEGO 金门大桥需要自定义 skill + 复杂指令 + 数小时迭代仍失败；Astra 时代只要一句 "Use Studio to build the golden gate bridge in lego"，10 分钟就产出第一版。五点心得：① 把专业软件给 Astra（Blender、DaVinci Resolve、BrickLink Studio），别强迫它只用 FFmpeg 这类 CLI；为旧模型写的 skill 可能是阻碍（去 skill 的"原生"配置反而更好，先不加 skill 试一次）。② 给意图和参考，不写规格。③ 3D 任务用 Blender。④ 从 Low/Medium 推理起步（不必默认拉满）。⑤ 说清完成标准和验证边界。

PRACTICE 04 · DESIGN CONTEXT

DESIGN.md 到底有没有用？Atlassian 实测：原型场景出彩、生产代码库不如 MCP/Skills

为对抗 AI 生成界面的"同质化 slop"，Atlassian 设计系统团队用同一条结构化内容管线自动生成 DESIGN.md，并做了两个实测。场景一（一次性原型）：给 Figma Make 生成自定义仪表盘时，DESIGN.md 让产物从通用 slop 变成可辨识的 Atlassian 风格，颜色/间距/字体/层级都符合预期——这类高层指引特别适合去定制 Tailwind、Shadcn 等通用库、从零生成 UI。场景二（生产代码库）：在已有 token/组件库 + lint + 类型检查的环境下做登录页，DESIGN.md 表现最差；对照数据——无上下文时设计系统覆盖约 5%（4.20M tokens/6m19s/43 轮），ADS MCP 约 80% 覆盖（3.75M tokens/5m1s/35.1 轮，最优），ADS Skill 约 80%（4.43M tokens）。结论：高层设计描述适合"从零生成"，一旦进入有约束的生产库，还是结构化的 MCP/Skills 更能精准接线。

PRACTICE 05 · AGENT CONFIG

给 Agent 立规矩：一份针对 Astra 重写的 AGENT.md 长什么样

独立开发者卡兹克把 AGENT.md 按 Astra 的行为特性整体重写了一遍，几个规则值得抄：沟通——面向用户叙述用简体中文、代码保持英文；先给"影响与结论"，再给行动/待决策/证据；能用简洁段落就别滥用列表。② 指令优先级——用户当前明确指令 > Skill / 历史记忆 / 默认偏好；项目内 AGENTS.md 只在本项目内补充或覆盖全局规则。③ 执行方式——开始新工作后持续推进直到目标完成；提问前先把"已授权且能让下一步变成可审查结果"的工作做完；不要因为假想风险主动加警告/免责声明/审批清单；用户建议不合适时直接说，不迎合。④ 测试与验证——不为可逆、影响小、只复述实现的改动写测试；跑与改动相称的测试，有新失败或新疑点才扩大范围。⑤ 工具与并行——文件搜索优先 rg/rg --files，只读查询尽量批量；仅在存在真正独立工作流时才用子 Agent。
