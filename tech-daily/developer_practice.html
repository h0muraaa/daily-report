协议MCP 最大更新：砍掉握手、废除会话粘滞，重回无状态 HTTP 时代

Model Context Protocol 迎来了官方口中"发布以来最大的一次更新"——方向却是出人意料的"复古"：移除初始化握手、废除会话粘滞，每个请求必须独立携带完整的上下文信息。最终版规范已于 7 月 28 日发布，候选版 5 月 21 日冻结，核心功能随之全面无状态化。

对运维和平台工程师来说，这解决了一个长期痛点：远程 MCP 服务器从此可以像传统无状态 HTTP 服务一样用轮询调度横向扩展，无需配置会话亲和性。但代价也很明确——状态迁移到客户端，每个请求都要带上全部上下文；且新旧协议共存期"故障率可能比现在还要高"（AgentStatus 创始人 Román Moskalenko 的直言）。如果你在维护 MCP 服务端或依赖粘性会话的 Agent 中间层，这次迁移值得排进近期技术债清单。

开源Rust 项目为 AI 编程立新规：能帮你看，不能替你写

本周，Rust 项目五个团队（编译器、标准库、类型系统、rustdoc、bootstrap）正式采纳一份 LLM 使用准则，为向 rust-lang/rust 提交代码时如何使用大语言模型立下成文规矩。核心一句话：可以用 LLM 回答问题、分析、提炼、检查、提建议和审查，但不能用它来创造。

Loop 还是 Graph？Graph Engineering 的 14 步实操判断框架

继 Loop Engineering 之后，"Graph Engineering"成为新一轮热词——7 月初 OpenClaw 创始人发问"我们还在聊 loop，还是已经切到 graph？"，随即有人跟帖"Loop Engineering 已死，Graph Engineering 永生"。Datawhale 整理的这份由 Codez 总结、全网 570w 人看过的 14 步手册，核心观点很冷静：Graph 不是 loop 的升级版，而是 loop 的组织方式。它烧更多 token、协调开销更高，出了问题你要 debug 的是一整张你没亲眼看着跑的路由图。

动手前先自问四个问题：① 任务能否拆出清晰的"谁负责什么"（拆不出角色就还是 loop，加节点只是加成本）；② 有没有真正能并行的子任务（没有独立并行，图比循环贵却不比循环快）；③ 单个 agent 的上下文是否装不下全部背景（装得下就别拆，拆分是为了腾上下文）；④ 失败后能否承担跳转分支的成本（没想清楚重试耗尽后去哪，图会在你看不见的地方卡死）。

同方向的一线观点来自宝玉：他认为像视频转录剪辑这类 App 未来应"被 Agent 调用"，App 只负责确认结果和微调，因此他砍掉了内置 Harness、只保留复制 prompt 让 Agent 去操作。两篇合看，指向同一个判断——决定要不要上 Graph 之前，先确认你已经有一个跑得稳的单体 loop，图是循环的组织方式，不是循环的替代品。

  • 先单后图：没有跑稳的 loop 就别建图，图只解决"并发/上下文不够"这两类真实问题。
  • 拆角色要能落地：调研、撰写、复核这类明确角色才值得拆成图节点，否则只是增加协调开销。
  • 接受更高 token 成本：Graph 用更高成本换质量与并行度，评估时把 token 预算写进方案。

编码 Agent 的度量与"速度病"：AI Engineer World's Fair 一线话题

AI Engineer World's Fair 2026 的 Agentic Engineering Track 主题是"写代码已经不再是难的部分"，多场演讲围绕一个核心问题：Agent 变快了之后，瓶颈和风险在哪里？其中 Matt Dailey 的"Velocity Sickness（速度病）"尤其锋利：当一个团队整体 10 倍速产出时，输出的增长会先于影响——PR 太多合不完、方向太多冲刺、最终"宣布 agent 破产"，第二天早上回到 12 个终端、谁也不认识，全部推翻重付一遍钱。他最担心的不是写不出代码，而是关键决策正被没有上下文的人/模型快速做出。

Denys Linkov（Wisedocs）的演讲则给"新旧代码库基准"提供了硬数据：他们的重构任务，o3 在 Cursor 里往返三小时仍带 10 个重大错误；而新模型 Sonnet 4.6 只需多一次迭代，Opus 4.8 基本一把过，成本约为原先 1/5。但反向警告同样存在——把整个任务交给 GPT-5.5，它曾宣称完成一个全仓库重构，实际写的是 2000 行脚手架、没有任何真模型。另一组来自会场的数字更冷：一个自信说谎的 AI 被盲从率近 80%，人在 AI 犯错时的核查兜底，并不像你以为的那么可靠。

实践要点：给团队引入编码 Agent 时，同时盯两个指标——产出速度（PR 吞吐）和"可回滚性"（每段输出是否可独立验证）。速度病的最优解不是更快，而是给每段自动产出配一个便宜的校验闭环。

文档LiteParse：毫秒级 PDF 结构化数据提取，开源免费

LlamaIndex 开源的 LiteParse 能"毫秒级"从 PDF 提取结构化数据：支持复选框状态、标注、矢量图形、词级边界框，是当前最全面的免费/开源文档处理器之一。它定位为"不需要视觉模型就知道 PDF 里有什么"——接进编码 Agent 处理数字 PDF 时，既能给到正确上下文，又能把结果反锚定到源文档位置。

AgentPi：极简 system prompt 的 Agent harness，被真实基准验证

AICodeKing 的评测视频把 Pi 推为"目前用 AI 模型的最佳方式之一"——尤其适合 DeepSeek 这类便宜开源模型。核心理念是极小的 system prompt：让模型不被多余指令过载，反而表现更好。佐证数据很有说服力：Claude Code 据报道把 system prompt 缩减了约 80% 且性能无损失；Composio 基准显示基于 Pi 的 harness Oh My Pi 在成功率上超过 Claude Code、Codex 和 OpenCode（配合 DeepSeek 时）。

Pi 还支持会话中途切换模型。对在意"每任务 token 成本"和"换模型自由"的开发者，这是与"喂大量系统提示词"完全相反的一个设计哲学——值得在自建 agent 时对照验证。

实践指南

AgentLinear 的生产级 Agent 三条经验：少给指令，多给工具

Peter Yang 采访 Linear 的 Nanyu 与 Delashum，从"初始 memo 到上线"完整拆解了一个生产级 agent 的构建过程。最反直觉的一条是："给你的 agent 尽可能少的指令，给它加载上下文的工具，而不是把上下文写死在提示词里。"其余两条同样直接：先钉死一两个用例跑通，再根据真实使用方式扩展；先用最好的模型证明核心工作流，再优化成本。

这套"基础 prompt + 工具加载上下文"的做法，与上面 Pi 的极简 system prompt 哲学互相印证——今天多个成功案例都在朝"少提示词、多工具"收敛。对正在设计内部 agent 的团队，这是一份可以照抄的三步清单。

评测Intercom 给内部 Agent 跑 evals：像对待客户产品一样对待内部 bot

Intercom 的做法是"把你在客户面 AI 产品上用的评测纪律，用到内部 agent 上"——他们对 agent 产出的每一次 PR review 都打日志，并让工程师复查评分是否正确。这样内部 bot 长期可信任，而不是上线后放任自流。

同理，Jerry Liu 预判 FDE（Forward Deployed Engineer）类工作的未来与 evals / post-training / RL 环境强绑定：把业务问题编成 eval 评分卡和环境，再通过自动优化流程跑出解决问题的 agent。这给做内部工具平台的人一个方向：给 agent 建立持续评测闭环，是让它长期可信的唯一办法。

SREStripe 用图搜索 + 状态机自动恢复数据库事故

踩坑供应链安全提醒：伪装 OpenAI 的钓鱼邮件与恶意 agent 工具

社区连续出现两条安全踩坑通报。其一，有伪装成 OpenAI 官方的钓鱼邮件，域名三天前刚注册，打开链接就引导授权 X 账号——典型的授权劫持（OAuth phishing）。其二，Mirasim 这款被推荐的工具被扒出"不止偷 Skills"：官方回复称"统一 Skills 是产品需求，默认关闭"，但使用者发现目录被改动、会话被扫描、代码具备 MITM 与 Blob 上传能力，质疑"功能开关被偷换成安装时无需授权"。

对开发者，这两条都指向同一习惯：装 agent 工具前先看它的权限清单和网络行为，尤其警惕"扫码/粘贴一段命令就装"的闭源工具；官方渠道下载、最小权限授予、事后审计日志，是这三周内值得固化下来的默认动作。
