Google AI Edge：边缘 AI 的瓶颈不是算力，而是内存

Cormac Brick 在 AI Engineer 会议上指出，边缘设备上部署模型的真正约束是 RAM，而且情况还在恶化：手机厂商今年甚至在减少内存配置，6GB 树莓派的价格已是发布时的 2.5 倍。Google AI Edge 的应对思路是把模型做到足够小。20 亿参数的 Gemma 量化到 2.9 bits/weight 后，能在树莓派上以约 8 token/s 运行；在 Qualcomm NPU 上则快到足以每秒处理几帧视觉任务。更小的模型从 5 亿参数一直下探到 5000 万，覆盖老旧笔记本和廉价设备。这些超小模型通常需要微调而非提示工程，但回报明显：一个微调后的 Gemma 能把自由文本转成跨 10 个动作的正确函数调用，准确率超过 86%。

深度解读一：AI 根因分析正从"模型推理"转向"上下文工程"

越来越多的工程师认为，现代 LLM 已经能够在给定正确上下文的情况下完成根因分析，真正的难点变成了如何把日志、指标、链路追踪关联成模型能用的上下文。Coroot 在 11 个模型上做的实验为这一观点提供了早期证据。

Arize 的 Jason Lopatecki 从另一个方向给出了落地方案：与其让工程师半夜被叫醒后手工翻 dashboard，不如让 Agent 直接拿到生产 trace 文件——把相关 trace 和日志作为文件写入代码仓库旁边，让 Claude Code 等编码 harness 去处理。因为编码工具擅长处理文件，但不擅长处理 dashboard。Agent 拿到的是软件实际走过的精确代码路径，而不是在数百万分支中猜测，从而能产出真正可合并的修复 PR。

对开发者的启示：RCA 的瓶颈不再是模型能不能推理，而是你的遥测数据能不能被方便地装进模型上下文。下一步应该投资的是 trace→文件→Agent 的管道，而不是再买更强的模型。

深度解读二：Agentic Context Management 的五个原语

生产环境中的 Agent 失败，原因往往不在推理能力，而在于上下文不断膨胀：对话历史、大提示词、庞大的工具定义、膨胀的工具输出，每一轮都在累积。常见的应对是存储与检索，但新的研究认为这个视角太窄，提出了更完整的 Agentic Context Management 框架，包含五个原语：architecting（架构）、ingesting（摄入）、scoping（范围）、anticipating（预判）和 compacting（压缩）。

朴素的累积会让 token 成本随对话长度平方增长；粗暴的摘要能把成本降到线性，但会撞上准确性悬崖。只有经过保真度验证的压缩，才能在控制成本的同时不丢失关键信息。对构建多轮 Agent 的开发者来说，这意味着上下文管理需要成为一级架构问题，而不是事后加一层记忆存储。

让 Agent 理解业务：意图识别演进路径

Datawhale 的这篇文章梳理了意图识别从规则到统计模型再到大模型的演进路径。业务早期用规则最实用：出现"退款""取消订单"等关键词就路由到对应流程，几乎无推理成本且可解释。当标签稳定、有标注语料时，TF-IDF/FastText + 轻量神经网络是高并发场景的高效选择。当表达越来越口语化、上下文变长、意图组合复杂时，才需要引入更强的模型。

文章给出了选型前需要回答的四个问题：意图数量有多少、标签是否频繁变化、标注数据是否充足、一次判断需要理解多少轮上下文。答案基本决定了技术路线。对正在设计 Agent 意图系统的开发者来说，这是一条避免"一上手就写 Prompt"的务实路径。
