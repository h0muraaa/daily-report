meng shaoClaude Code 实验功能 Code Mode：从「一次调一个工具」到「写段 JS 批量调工具」

Claude Code 上线默认关闭的实验特性 Code Mode。开启后，模型不再逐个调用 Bash / Read / Edit，而是先写一段 JavaScript，在本地会话里一次性编排多个工具调用。官方示例是「把重试上限从 3 改成 5」：先用 rg 定位文件、改参数、跑相关测试，最后只把文件路径和测试输出回传给模型——原本需要四五轮往返的操作一步完成。

价值有三点：独立命令可以并行；上一步结果直接在代码里传给下一步，不必绕经模型；中间产生的大量输出先在代码里过滤，只把需要部分放进上下文，直接省 token。典型适用场景是「同一改动批量改多文件」「搜索结果先过滤再读」「多个独立命令并发」。开启方式是设置环境变量 CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1（shell 或 ~/.claude/settings.json，写在项目设置里不生效，克隆的仓库无法替你偷偷开启）。限制也很硬：仅支持终端交互会话，不支持 -p、Agent SDK、VS Code 面板、桌面端与云端会话，也不能走网关 / Bedrock / Google Cloud / Microsoft Foundry 或纯 API key 模式。

📎 来源: meng shao (@shao__meng)

yan5xuGoogle Antigravity Dynamic Workflows：让 Agent 写 Python 脚本编排子 Agent

Antigravity 推出 /run-workflow：Agent 用 Python 脚本编排并行与串行的子 Agent，并做结构化交接（structured handoffs），用确定性的控制流替代「prompt 漂移」。脚本在运行前可以人工审阅，也可以保存下来重复执行同一流程。

开发者反馈的关键点是：这相当于在 Python 脚本里提供了一个「agent 函数」，返回值遵循 schema 定义，脚本后面可以继续做 if/else 分支判断。有人评价，和早期 CrewAI 相比，如今的差别在于真正具备可编排的大模型和能干活的小模型，同一套形态因此才「回春」。对需要稳定复跑的流水线而言，把编排逻辑从自然语言挪进代码，是可控性的关键一步。

InfoQCloudflare Workers KV Instant：读取 p99 1.62ms，但写入一次约 0.1 美元

Cloudflare 首次把内部配置存储 Quicksilver 以 Workers KV 新模式「KV Instant」对外开放。在 300+ 边缘节点测得：p99 读取延迟 1.62ms，而经典 KV 为 287ms；Instant 模式 p95 读取为微秒级。Quicksilver 自 2020 年启用，几乎每个进入 Cloudflare 的请求都会从中读取至少一个键，但此前从未作为客户产品开放。

同一套 API，却有三处行为差异：模式必须在创建命名空间时通过 "mode": "instant" 设定且此后不可更改；不支持元数据，getWithMetadata 恒返回 null；list 返回所有匹配键且不分页。配额也更紧（单命名空间最多 1 万个键）。结论很工程化：它适合「读多写少、要求全球低延迟」的配置类数据，而不是通用存储；写入成本高（约 $0.1/次 量级），写放大敏感的业务要绕行。

「Always-on Agent」的参考架构：把「像一直在线」拆成五个组件

// 关键词：Event Inbox · Timers · Memory · Permissions · Outbox

Anthropic 的《Building always-on agents》给出的核心判断是：所谓「始终在线」是一种使用体验，不是进程一直开着。Agent 大部分时间在休眠，收到事件或到点才醒来跑一次，做完把状态存下来继续睡。单次 run 很短，但循环一直在转——真正的区别不在 Agent 主循环，而在外围架构。

五个关键组件

  • Event Inbox：用户消息、webhook、定时任务产生的事件，先写入一张持久化表，再由 worker 领取。不让每个来源直接调用 Agent。同一收件箱同时只允许一个活跃 worker；按事件来源的唯一标识去重；用户连发的多条消息合并成一次运行——这样才扛得住重试、并发和崩溃。
  • Timers：分两类——Agent 给自己定的跟进时间（如过一阵看对方是否回复），以及固定节奏任务（如每日简报）。计时器单独存放，到期后不直接启动运行，而是往 Inbox 投一条事件，走同一套流程。
  • Memory：只存「下次查不到的东西」——对 Agent 行为的指令、关于用户的笔记、已经说过的话、每项任务的进度；外部系统能查到的只存指针。因为每次运行都要先加载这部分上下文，所以要精简，并配合提示缓存压成本。
  • Permissions：权限是最大风险。凭证放在 Agent 环境之外，由代理注入请求；高风险动作交给分类器审查，最关键的决定仍由人做。需要审批时延期该次工具调用、结束当前运行，等用户回答作为事件回到 Inbox 再继续——Agent 不卡住。
  • Outbox：结果通过发件箱交给用户，节奏上「先少说话」，再逐步争取注意力，避免打扰。

主循环

# 一次 run 的生命周期（伪代码）
event  ← inbox.claim(worker)          # 去重 + 合并 + 单活跃 worker
session ← session.load_or_create(event)
mem    ← memory.load(session)         # 指令 / 用户笔记 / 历史 / 进度
action ← agent.step(mem, event, perms) # 在权限范围内行动
memory.update(mem, action)
outbox.push(action.user_facing)
if needs_approval: defer_toolcall(); return   # 等用户回答回流 inbox
timer.schedule(action.followup)            # 到期再投事件

为什么值得借鉴

这套设计把「可靠性」从模型能力里剥离出来，交给经典的后端模式：持久化队列、幂等去重、单写者、状态外置、权限代理、异步审批。即使模型不变，只要外围架构照此搭建，Agent 就能在崩溃、重试、并发下保持一致行为。评论者认为，这基本就是 Grok Bot 与 Meta Muse 这类产品的设计蓝图。对自建 Agent 平台的团队，这是目前最完整的一份「可抄」参考架构。

📎 来源: meng shao (@shao__meng) — 五个要点 · Viking (@vikingmute) — 架构摘要

「All Code Is Slop」：一个月 1.1 万个 PR、0.5% 回滚率的工程做法

// 关键词：lint 而非文档 · 干净代码库 · 禁用易错 API · AI 自验证

SpaceXAI 负责 Grok Bot 桌面版的 Lauren Tan（@poteto）在 AI Engineer Code Summit 的演讲《All Code Is Slop (Except Mine)》里，真正想论证的是软件工程师工作方式的变化：在大幅提高产出的同时，维持甚至提高代码质量。团队上个月合并了约 1.1 万个 PR，回滚率约 0.5%，应用比刚发布时还快（数据来自演讲自述，无独立审计；她在访谈中还提到每月约合入 4000 个 PR 的个人节奏）。

八条可落地做法

  • 把每次纠正写成 lint 规则，而不是往 agents.md 里加一段说明。违反 lint 的代码直接报错、提交不上去；文档里的话模型不一定照做。
  • 代码库是模型最主要的学习材料。里面的坏写法、临时补丁会被下一个 AI 当惯例照抄，像杂草一样越长越多，所以要保持干净。
  • 容易用错的东西直接禁掉。React 里有个功能人常用错、AI 更用不好，他们在产品代码里禁用后，这类问题不再出现。
  • 禁掉 99% 的代码注释。AI 爱在注释里给自己走的捷径找理由，后来的 AI 就照着学；她在 Cursor 时，这类「有理由的补丁」扩散开来，把应用拖得很卡。
  • 让 AI 自己检查自己的活：把程序跑起来像用户一样点一遍，交上录屏和截图，人审代码变成看这些材料。她的 token 大部分花在这一步。
  • 以前用不起的严格验证现在用得起：用数学方法证明程序没问题这类手段，过去太费人力，AI 把成本降下来了。
  • 先打好地基，再谈全自动。如果 AI 写代码这一步本身就出烂代码，全自动化只会产出更多烂代码，还更费钱。
  • 质量靠约束下沉，不靠提示词。把规则放进可执行的检查里，比写进自然语言说明更可靠。

这套做法的本质，是把「人类老工程师的口头规矩」翻译成机器可强制的约束：lint 规则、禁用清单、无注释规范、自动化验收。它解释了为什么同样的模型，有的团队产出高质量 PR，有的团队只能不断回滚——差别在工程基建，而不在模型。

实践指南

// 可直接落地

把「纠正」沉淀成可执行约束，而不是散文

每次你纠正 AI 的一次错误，优先把它写成 lint 规则、类型检查或 CI 卡点，而不是往 agents.md 里追加一段话。可执行约束会在提交时直接报错，自然语言说明模型不一定遵守。长期看，前者是资产，后者是负债——文档会越写越长，约束会越跑越稳。

📎 来源: 宝玉 (@dotey) — Lauren Tan 演讲要点

把代码库当成模型的训练集来治理

代码库是 AI 最主要的学习材料：坏写法、临时补丁会被下一个模型当惯例照抄。可落地的三件事：清理长期存在的 hack 与死代码；对「人都会用错」的 API 直接在产品代码里禁用；大幅削减注释，尤其是「为捷径找理由」的注释。目标不是洁癖，而是切断错误模式的自我复制。

📎 来源: 宝玉 (@dotey)

让 Agent 自证：跑起来、点一遍、交录屏

把「验证」也交给 Agent：让它把程序跑起来，像用户一样操作一遍，提交录屏和截图。人工审查从「逐行读代码」变成「看它是否真的工作」，这是 Grok Bot 团队 token 花得最多、也最值的一步。配套做法是：先打好地基（lint、测试、验收脚本），再谈全自动，否则自动化只会放大烂代码。

📎 来源: 宝玉 (@dotey)

代码审查分层 + 基于风险的人工审批

照 Anthropic 的做法把审查拆成三层：自动化验证（lint、类型、测试、构建）兜住机械问题；AI 驱动审查兜住模式与上下文问题；人工只审「按风险分级后剩下的部分」。这样在不增加回归与事故的前提下压缩人工时间。关键是明确每一层「谁负责、卡什么」，而不是把所有东西都丢给最后那个人。

📎 来源: InfoQ — Anthropic 的 Claude Code 审查流程

Agent 安全底线：出网管控 + 最小权限 + 凭据外置

即便用自托管开源权重，也要假设模型可能外传数据（Qwen3.8 的探针文件案例）。落地清单：默认拒绝出网、按域白名单、记录所有出站请求；Agent 权限按单次动作判断是否恰当，而不是静态授予；凭证放在 Agent 环境之外由代理注入；高危动作交分类器或人工审批。别因为「权重在本地」就省掉这些。

选模型：先把 effort 拉满，再考虑换模型

基准数据给出一个朴素结论：Claude Code 2.1.322 上 52 个编码任务，Fable 5.2 解决率 82.7%、Opus 5.5 为 84.6%，但前者每解决一个任务成本是后者的 2.80 倍。实践建议（Addy Osmani）：Opus 5.5 medium 是很好的日常主力，遇到瓶颈先抬高 effort，再换模型；Fable 5.2 留给真正困难的任务（大迁移、长时间无人值守）。先算「每解决成本」，再谈「谁更强」。

SDD：难点在 spec 基线，不在工具集

引入 openspec、speckit 之类工具不等于落地了规范驱动开发（SDD）。真正的门槛是每个公司自己的 spec 基线建设，以及「人与 AI 配合 + 人与人配合」的研发流程升级。人的价值会从「交付」转向三件事：审美（判断好不好，spec 基线由人产出）、判断（多个技术方案之间做权衡）、兜底（AI 不为质量负责，得人来）。别指望把通用架构原则直接内置进模型。
