Claude Code 团队删掉 80% 系统提示词，Coding 评测无明显损失

Anthropic 的 Thariq 发文复盘 Claude 5 时代的上下文工程。核心结论是：面对 Opus 5 和 Fable 5，Claude Code 的系统提示词被删掉了超过 80%，但 Coding 评测没有可测量的损失。背后的判断是，新模型推理能力变强后，过多的防御性规则反而会限制它——旧规则曾经用来避免最坏情况，现在却成了「抢方向盘」。

文章把 Claude Code 收到的上下文拆成 Prompt、参考材料、系统提示词、CLAUDE.md、Skills 和 Memory 等部分，并给出六组具体变化：什么时候该少写规则、为什么示例可能限制模型、不同上下文组件如何分工。对正在维护 CLAUDE.md 或 Agent 系统提示词的开发者来说，这是一份可直接落地的重构 checklist。

阿里云发布千问AI平台：一个 API Key 调用百余模型，Agent 可自主切换

阿里云把 Qwen、Kimi、DeepSeek 等一百多个系列模型聚到一个平台，并提供统一 API Key。发布同时开源了两个官方 Skill，让 Agent 能够根据任务自动选择、调用、切换模型。Datawhale 的实测显示，让 Agent 基于 qianwen-ai Skill 把一段小水豚的故事做成 15 秒短片时，Agent 自动调用了 wan2.6-i2v-flash、qwen3-tts-flash、wan2.6-t2i 等模型，跨越文本、图像、视频、语音四类能力。

这件事的关键不在于「一个 Key 调多模型」——聚合网关已经做了这件事；而在于把「选模型、比价、切换」从人工决策变成 Agent 可调用的能力。如果你正在构建需要多模型协作的 Agent 工作流，这种「模型平台即 Skill」的范式值得参考。

Ruff v0.16.0 默认启用规则从 59 条增至 413 条

Astral 的 Ruff Python linter 发布 v0.16.0，这是自 v0.1.0 以来首次修改默认规则集，默认启用规则从 59 条大幅提升到 413 条。新增规则涵盖语法错误、运行时错误等更严重的质量问题。Simon Willison 反馈，升级后他的多个项目 CI 直接变红，仅 sqlite-utils 就报出 1618 个问题。

如果你在 CI 里用了未固定版本的 ruff，这次升级大概率会触发破坏性检查。建议的做法是：要么固定版本，要么专门抽时间用 uvx ruff check . 跑一遍，评估新增规则的修复成本再决定是否跟随默认。

EvoX：蜂群式自进化的多 Agent 协作框架

多 Agent 项目的失败率很高：德勤 2026 年报告称 86% 的多 Agent 试点无法规模化。EvoMap 团队提出的 EvoX 没有采用「主 Agent 拆活、子 Agent 执行」的主从架构，而是让每个 Agent 独立工作、自主进化，最后像蜂群一样汇合结果。测试显示系统容错率翻倍，长周期任务完成率提升，同时显著降低 token 成本。

对开发者来说，这个案例说明多 Agent 的瓶颈不是「有没有一个更聪明的总管」，而是角色协作、多轮汇合和错误恢复。如果你正在设计 Agent 系统，可以先问自己：任务能否被拆成多个可独立验证的子目标，而不是一条必须全程由主节点理解的流水线？

2. 深度技术解读

上下文工程进入「少即是多」阶段

Claude Code 团队的经验不只是「提示词越短越好」，而是重新梳理了上下文各组件的职责。Prompt 针对具体任务；系统提示词和 CLAUDE.md 提供通用指导；Skills 封装可复用的工具能力；Memory 沉淀项目特有知识；参考材料则提供当前任务所需的代码、文档、测试和截图。

当模型能力较弱时，开发者倾向于用规则把每一步都写死；但当模型能基于周围代码做判断时，过多规则会抑制其主动性和探索能力。Jerry Liu 也指出，他过去习惯写覆盖所有边界情况的超长提示词，结果模型只按字面回应，反而不会独立提供新视角。更好的做法是：给足完整上下文，但减少「该怎么做」的约束。

实践建议：定期审计你的 CLAUDE.md 和 Agent 系统提示词。把「因为某次错误而加的一条规则」翻出来，问自己：这条规则现在是在帮助模型，还是在替它做它本可以做得更好的判断？

机器人不是浏览器：腾讯具身智能的「三层脑」架构

腾讯 Robotics X 实验室在把通用智能体框架 OpenClaW 移植到机器人后发现效果很差——因为这类框架服务的是数字智能体，「操控的身体相当于浏览器」，可以等待；但机器人不能等，任务下达到响应必须控制在几秒内。于是他们设计了原生框架 TairosAgent，把响应时间压到 2-3 秒，并将具身智能拆成三个不同频率的层级：

  • Hy-Embodied-VLM-1.0：空间与场景理解
  • Hy-Embodied-RxBrain-1.0：认知规划与未来状态想象
  • Hy-Embodied-VLA-0.5：高层目标到连续动作的转化

这套架构提醒我们：把大模型直接套到物理世界时，不能简单复用数字 Agent 的假设。延迟、实时控制、力觉反馈和身体安全都是新的约束。做机器人、IoT 或任何涉及物理交互的开发者，都需要重新思考模型分层和响应边界。

4. 实践指南

Agent 使用 Skills 不是「先选再调」的两段式调用

宝玉解释了一个常见误解：Agent 使用 Skills 时，并不是先调一次大模型选 Skill，再调一次执行工具。Skills 的元信息（name 和 description）在对话开始时就作为系统提示词的一部分加载进上下文，大模型可以在同一轮调用中判断该用哪个 Skill、读取 SKILL.md、决定是否调用工具。

token 成本方面，系统提示词（包括所有 Skill 描述）会被 Prompt Caching 缓存，多轮对话中不需要重复处理。设计 Skill 时，重点应放在让 description 足够清晰，让模型一次就能判断适用场景，而不是依赖冗长的内部文档。

来源：宝玉 (@dotey)

「软件工厂」比单次 Agent 提示更可持续

Guillermo Rauch 提出，eve.dev 这类框架的核心理念是：工厂即产品。与其每次有新想法就临时 prompt 一个 Agent，不如搭建一套能自动启动、维护、演进想法的系统。Rauch 自己的研究流程也很简单：一个 research/ 文件夹、一个 AGENTS.md 描述格式和最佳实践，然后让 Agent 基于文件系统持续积累和关联知识。

对开发者来说，这意味着 Agent 时代的产品力不再只是「会不会写 prompt」，而是能不能设计出可复用、可验证、可维护的自动化流程。分享结果也可以让 Agent 渲染成 HTML 并部署到 Vercel。

来源：Guillermo Rauch (@rauchg)、 Guillermo Rauch (@rauchg)

Loop Engineering：用控制论设计 Agent 开发循环

Kyle Mistele 在 AI Engineer 的分享中指出，Coding Agent 最大的风险不是写不出代码，而是给你一份 4 万行、没人能 review、还悄悄做错事的 PR。解决方案不是更好的 prompt，而是更好的循环。他借用控制论的框架设计 Agent 循环：

  • Sensor：感知当前状态（如 lint、grep、结构搜索）
  • Controller：决定下一步最小增量改动
  • Actuator：执行改动（如代码迁移一个 procedure）
  • Disturbance Dampening：严格检查防止偏离

每个迭代只做一个可读、可验证的小改动，而不是一次性交付巨大 diff。这是把 Agent 从「黑箱生成」变成「可审计工程」的关键。

来源：AI Engineer、 AI Engineer (@aiDotEngineer)

为演进式架构构建上下文存储库

InfoQ 的一篇文章讨论了 AI 加速开发的同时如何隐藏架构隐患。METR 的实验发现，使用 AI 工具的开发者完成任务耗时反而增加 19%，而他们主观上却认为效率提高了 20%。落差来自：AI 在前 80% 环节很快，但最后 20% 的集成、边界处理、调试和历史兼容才是真实耗时所在。

作者建议建立统一的「上下文存储库」，把架构决策、设计文档、TDD 测试和自动化架构校验工具整合进代码仓库，实现人与 AI 的安全协同迭代。对正在引入 AI 编码的团队来说，这比追求代码生成速度更重要。
