GitHub 内部实践：Agent 工作流 Token 成本降低 62% 的方法

GitHub 公开了其在 CI 环境中优化 LLM Agent 工作流 Token 消耗的实战经验。团队设计了"等效 Token（ET）"统一指标来跨模型对比成本，并通过三个关键动作实现优化：精简未使用的 MCP 工具、将部分 MCP 调用替换为 GitHub CLI 命令、引入每日审计和优化 Agent。整个优化闭环由两个 Agent 驱动："每日 Token 使用审计器"负责汇总资源消耗并标记异常，"每日 Token 优化器"则自动读取源码和日志，创建 Issue 并提出优化建议。这对于任何在持续集成中运行 LLM Agent 的团队都有直接参考价值。

深度技术解读

从 Chrome DevTools MCP 学到的 Agent 接口设计教训

Google 的 Michael Hablich 在 AI Engineer 大会上分享了 Chrome DevTools MCP 的开发历程——一个把同样的事情做错三次才做对的诚实故事，值得每个正在构建 Agent 工具的开发者仔细品味。

第一次尝试：只提供了一个 debug_webpage 工具。Agent 因为无法组合行为而静默失败——功能太粗粒度，Agent 不知道该怎么用。

第二次尝试：将工具拆分为 25 个专注的小工具。结果 Agent 有了 25 个选择却没法可靠地选出正确的——粒度太细，决策负担过重。

第三次（正确的做法）：三个关键改进让接口真正可用：

  • 语义摘要替代原始数据：不再把 50,000 行的 JSON trace 文件扔给 Agent，而是提供结构化的语义摘要
  • Agent 可自修复的错误信息：将错误提示从 "Unable to navigate back in currently selected page" 改为 "Cannot navigate back, no previous page in history"——后者包含足够信息让 Agent 自行决策下一步
  • tokens per successful outcome 指标：用"每个成功产出消耗的 token 数"来衡量接口的"燃油效率"

核心启示：设计 Agent 接口时，工具粒度不是越粗越好也不是越细越好，关键在于接口是否具备"可组合性"和"自解释性"。同时，错误信息的设计要假设没有人类在循环中——Agent 必须能从错误本身推断出下一步行动。

OpenClaw 的"暗工厂"实践：一晚 2700 次 commit 的 Agent orchestration

OpenClaw 的 Vincent Koc 分享了如何用 Agent 在一夜之间完成 2700 次 commit、近百万行代码变更、触及 82% 核心代码库的真实案例。这不是炫技，而是一套可复制的规模化 Agent 工作流方法论。

关键组织方式——泳道（Swim Lanes）：将 60-70 个并行 Agent 会话按类型组织成每组 15-20 个的泳道。不同类型的任务（如重构、测试、文档）分到不同泳道，避免互相干扰。

核心技能——读懂推理 token：Koc 强调"2025 年是 token maxing，2026 年是不浪费 token"。真正的技能不是写 prompt，而是判断 Agent 是否在"胡说"。这需要开发者养成阅读 Agent 推理过程的习惯，理解它的思考路径是否合理。

决策原则——何时终止会话：当 Agent 开始循环重复相同错误、或偏离目标太远时，果断终止比让它继续消耗 token 更划算。这需要为每个泳道设置清晰的终止条件和检查点。

两个字符让 Django 接口快了 8 倍：一次险些翻车的线上性能排查

腾讯云开发者社区分享了一个真实的生产环境性能排查案例。某个使用 Python 2.7 + Django 1.11 的老旧服务在直播高峰期出现响应抖动，接口一次可能返回 10000+ 台设备信息、响应体达 7MB。问题根源在于 Django ORM 的查询方式：使用 Server.objects.filter(...) 一次性查出大量 Model 对象，再通过列表推导逐个转成字典。解决方案只需两个字符的改动——将列表推导改为生成器表达式（把 [] 改成 ()），利用 StreamingHttpResponse 的流式特性避免内存中堆积全部数据，响应时间从数秒降至毫秒级。这个案例提醒我们：老代码的性能陷阱往往藏在最基础的语法选择中。

阿里云：用 Claude Code 搭建 Harness 工程评测业务 Agent

阿里团队提出了一种"Harness 工程搭建式评测"方法，用 Claude Code 作为 Harness 搭建者，系统性地评测业务 Agent 的效果。传统评测的问题在于启动成本高、人力密集、迭代慢、可复现性差。Harness 式做法的思路是：让顶级 Agent（Claude Code）搭建完整的评测骨架（包括评测方案、数据集、评测逻辑和分析流程），人只需提供被测对象和做关键决策。Claude Code 在 Harness 中的核心能力包括：深度理解 prompt、自动生成测试用例、执行评测并分析结果、持续迭代优化评测方案。这种方法把评测工程的搭建时间从周级压缩到天级。
