AWS

Amazon S3 Annotations：把元数据直接挂在对象上

AWS 新推出的 S3 Annotations 允许把摘要、分类、合规标签、AI 生成洞察等富上下文直接绑定到 S3 对象，而不需要再维护一套独立的元数据系统。注解可以独立于对象更新，也能跨数据集被检索。

Agent Workflow

Claude Code 团队：为什么用 HTML 而不是 Markdown 做智能体输出

Claude Code 工程负责人 Thariq Shihipar 发文指出，随着 Agent 工作流越来越长、输出越来越复杂，Markdown 的可读性成了人类复核的瓶颈。HTML 的可视化、色彩和交互能力反而更适合人类跟进。

这不是格式之争，而是协作效率问题：当 Agent 输出上百行文本时，Markdown 很难快速定位关键信息；HTML 可以直接折叠、标色、嵌入表格。建议在设计 Agent 输出时，默认按"人类可读"而非"模型易生成"来选格式。

Cloudflare 宣布从 9 月 15 日起，所有使用其服务的网站默认屏蔽"混合用途"的 AI 爬虫（Training + Agent）。网站主可以分别对 Search / Agent / Training 三类爬虫设置允许或屏蔽，逻辑从"默认允许、手动封禁"翻转为"默认拒绝、手动放行"。

Deep Dive

Fable 5 实战心法：地图不是领地，开工前先找 Unknowns

Claude Code 团队成员 Thariq Shihipar 提出了一套 Fable 5 使用框架，核心是把 prompt / skills / context 比作"地图"，把真实代码库、业务约束、运行环境比作"领地"，两者之间的差距就是 unknowns。Fable 越能跑长任务，就越容易在这些空白处替你"合理猜测"，等看到 diff 时问题已经绕了好几层。

他把 unknowns 分成四类：

  • Known knowns：你明确写进 prompt 的东西，比如目标文件、兼容要求。
  • Known unknowns：你知道自己没搞懂、需要进一步确认的部分。
  • Unknown knowns：你潜意识里知道但没写下来的业务约束或代码历史。
  • Unknown unknowns：你压根没想到、只有看到结果才会意识到的点。

实践建议分三段：实施前做盲点排查、头脑风暴和参考收集；实施中让 Fable 记录偏离原始计划的决策；实施后让 Claude 反过来解释和测试你。这不是更复杂的 prompt，而是把"隐性假设"显式化。

Deep Dive

上线后的 Agent 运维：模型不是产品，运营 Agent 的也得是 Agent

来自 Wandero AI 的 Raphael Kalandadze 在 AI Engineer 大会上指出，运营 Agent 产品不像运营传统软件：失败发生在对话里，而不是 stack trace 里。Dropped constraint、stale price、自信的错误答案都不会触发告警，但会真实伤害客户。

他们的解法是用 Agent 来运营 Agent：

  • 一个 Agent 监控生产对话，判断 Agent 在哪里让客户失望。
  • 一个 Agent 看日志和系统健康，把真实问题追溯到代码。
  • 一个 Agent 写测试并运行，因为"CI 全绿"对非确定性 Agent 没有意义。
  • 一个 Agent 审查每份 PR，无论作者是人还是 Agent。

这与 RELAI 的 Soheil Feizi 提出的"可验证持续学习"方向一致：把生产失败变成可回放的学习环境，在保留旧能力的前提下做回归感知的修复。对开发者来说，这意味着 Agent 项目不能只盯着 prompt 和模型，还要建设从失败到改进的闭环。

Troubleshooting

Redis 内存没告警、key 却离奇失踪？一次生产排查复盘

vivo 互联网技术团队分享了一次凌晨两点的生产故障：应用报错获取不到 Redis key，但监控显示内存使用率不高，也没有收到内存告警。最初怀疑是 key 批量过期，但 TTL 显示还有 5 天，而且连续两天在同一时间点复现。

排查思路值得学习：先看淘汰策略和过期时间，排除批量过期；再结合内存监控和 key 过期曲线，发现是大量 key 在同一时间点被集中淘汰；最后定位到业务代码在某个逻辑里对大量 key 设置了相同过期时间，导致 Redis 在该时间点触发集中清理。优化方法是打散过期时间、合理评估存储性能，并调整告警灵敏度。

关键启示：Redis 内存告警≠不会丢 key。volatile-lru 等策略在内存压力或集中过期时都会触发淘汰，监控覆盖不了所有 corner case，设计 key 过期时需要避免"脉冲式"集中失效。

AI Engineering

当模型变强，工具调用反而变差：Better Models, Worse Tools

Simon Willison 转发了 Armin 的一个观察：更新更强的 Claude 模型（如 Opus 4.8、Sonnet 5）在调用 Pi 的编辑工具时，反而比老模型更容易在 tool schema 里发明不存在的字段，导致调用被宿主拒绝。编辑本身往往是对的，但参数不合法。

这对开发者有两个警示：一是不要默认"新模型在所有任务上都更好"，工具调用这种对 schema 严格遵从的任务需要单独回归测试；二是 Agent 宿主端要做好参数校验和重试，不能假设模型永远遵守 JSON schema。
