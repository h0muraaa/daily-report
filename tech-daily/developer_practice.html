Gemma 4 发布 MTP Drafter：本地推理速度最高提升 3 倍，输出质量零损失
Release

Google 为开源模型 Gemma 4 推出了 Multi-Token Prediction (MTP) Drafter，基于 speculative decoding（推测解码）机制实现高达 3 倍的推理加速。核心思路是用一个轻量级小模型预先"猜"出接下来多个 token，再由主模型并行验证，验证通过的部分一次性输出。

这套机制对本地部署场景尤其有价值：LLM 推理的瓶颈通常不在算力而在内存带宽，speculative decoding 能把闲置算力利用起来。实测在 Apple Silicon 上跑 26B MoE 模型，批量大小 4-8 时可获得约 2.2 倍提速。Drafter 采用 Apache 2.0 协议，权重已上传 Hugging Face 和 Kaggle，transformers、MLX、vLLM、SGLang、Ollama 均已支持。

来源: [Google Blog] [Google AI Developers]
Google 发布 Code Wiki：让任何 GitHub 仓库瞬间拥有智能文档
Tool

Google 推出 Code Wiki，目标直指"读代码"这个软件开发中最大、最贵的瓶颈。它能为任何公开 GitHub 仓库自动生成结构化、实时更新的 Wiki 页面，核心能力包括三项：自动扫描仓库并在代码变更时实时同步文档；Gemini 驱动的智能聊天，回答问题时可直接超链接到具体代码行；自动生成架构图、类图、时序图，实现从解释到源码的一键跳转。

对于接手遗留项目的新手、或是需要快速理解大库的老开发者，这意味着文档永远与代码同步，不再需要靠 grep 和猜测来理解系统。目前公共仓库已开放预览，地址：codewiki.google。

Google DFlash：扩散式推测解码在 TPU 上实现 3.13 倍无损加速
Research

Google 与 UCSD 合作推出 DFlash（Diffusion-Style Speculative Decoding），从根子上改变了自回归解码的串行限制。不同于传统的逐词生成，DFlash 用扩散式推测一次性生成多个 token，在 Google Cloud TPU 上实现了 3.13 倍推理加速且完全无损。

这种硬件+算法联合优化的思路正在重塑 LLM 推理的成本曲线。当推理速度提升 3 倍以上，实时 Agent、长上下文处理、复杂工具调用等场景的可行性大幅提升，本地部署门槛也被显著拉低。对于关注推理性能优化的开发者，这是继 speculative decoding 之后又一条值得跟踪的技术路线。

深度技术解读

Speculative Decoding 正在成为 LLM 推理的标配技术

今天有两条相关新闻指向同一个趋势：Gemma 4 的 MTP Drafter 和 Google 的 DFlash，本质上都是 speculative decoding 的变体。这项技术的核心洞察是——大模型推理时，处理器大部分时间都在等内存带宽，而不是计算单元满载运行。

传统自回归生成每次只产出一个 token，然后等待下一次前向传播。Speculative decoding 引入一个小型草稿模型来并行预测未来多个 token，主模型只做验证。验证通过的 token 可以直接输出，不通过的再回退修正。因为草稿模型极小，验证可以批量进行，整体吞吐量显著提升。

对开发者的实践意义：

  • 本地部署开源模型的可用性正在大幅提升，Apple Silicon + MLX + Gemma 4 drafter 已经能跑出接近云端的速度
  • 如果你在做 AI 应用的产品化，推理成本曲线正在变得更友好
  • Ollama、vLLM、SGLang 等推理框架都已支持 drafter，集成成本很低

预计 2026 年下半年，主流开源模型都会标配 drafter，这会成为推理 infra 的标准配置而非加分项。

来源: [Google Blog]

AI Coding Agent 的"长时运行"工程实践

宝玉在 X 上分享了一套让 Codex 等 AI coding agent 长时间自主运行的方法论，核心是把"人怎么带新人"的经验迁移到 agent 管理上来：

  • 目标不是为了时间长而时间长——要有清晰的问题定义和验收标准
  • 任务文档化——把计划和验收标准写成 Agents.md，让 AI 清楚知道做什么、怎么验证、什么时候算完成
  • 分阶段执行——长时间任务要拆成阶段，每个阶段都有明确的中间产物和检查点
  • 提供样板——当 AI 第一次输出不符合预期时，手动写一个样板文件，明确告诉它"这是我期望的结果"
  • 进度可视化——要求 agent 维护进度条、checklist 等中间状态辅助

这套方法论的本质是：不要把 agent 当成一个会自动搞定一切的魔法黑盒，而是当成一个需要 onboarding、需要清晰需求、需要持续 feedback 的"虚拟团队成员"。

来源: [宝玉]

JetBrains 调查：别让 AI 产生的 IDE 可捕获错误流入 Code Review

JetBrains 在 2025 开发者生态调查（24,000+ 受访者）中发现，AI 编码工具显著增加了 PR 量和 code review 负担。关键数据：约 20%-25% 的 AI 代码幻觉可以通过自动化的结构化和静态分析检测。建议将这类检查前置到 IDE 或 pre-commit 阶段，而非让它们在 review 中消耗人力。

来源: [JetBrains Blog]

Andrew Ng：AI 编码加速程度因领域而异

Andrew Ng 给出了 AI 编码对不同软件工作的加速排序（从高到低）：前端开发 > 后端开发 > 基础设施 > 研究。原因是前端有成熟的框架生态和浏览器可视化反馈闭环，而基础设施和研究需要更深入的领域知识和创新探索。在组建团队或分配项目时，可以据此设定合理的效率预期。

来源: [Andrew Ng]

CMU 顶会论文：GitHub 上 600 万颗星可能是刷出来的

ICSE 2026 论文《Six Million (Suspected) Fake Stars on GitHub》揭示了 GitHub 虚假星标灰产。 researchers 发现大量"热门项目"实为伪装成盗版软件、游戏外挂、加密货币机器人的钓鱼仓库。开发者选用依赖时的"先看 star 数"直觉正在失效，建议结合代码审查、commit 历史、issue 响应质量等多维度判断项目可信度。
