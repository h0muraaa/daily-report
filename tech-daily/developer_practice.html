🧠 深度技术解读

话题一：Serverless 大规模实战——100 万 Lambda 背后的工程决策

AWS 架构博客中 ProGlove 的案例非常典型：一个面向制造业可穿戴设备的 SaaS 平台，最终运行了超过 100 万个 Lambda 函数。这不是炫技，而是真实业务规模下的架构演进。

核心经验：
  • 真正的 scale-to-zero 很关键：不只是函数不跑时不花钱，而是整个事件链路（API Gateway、SQS、DynamoDB 等）都要按实际调用计费，避免常驻资源。
  • 配额管理是生产事故高发区：Lambda 并发、SQS 吞吐量、DynamoDB 读写容量都有账户级限制，提前规划并设置 CloudWatch 告警。
  • 提前联系 AWS 服务团队：大规模场景下，AWS 可以提前调整限制、给出架构建议，避免上线后被动救火。

对于国内使用阿里云函数计算、腾讯云 SCF 或华为云 FunctionGraph 的开发者，同样适用：Serverless 的“免运维”是有条件的，容量规划、成本监控、冷启动优化一样不能少。

话题二：AI 编码工具的“局部优化陷阱”

GitLab 的研究揭示了一个反直觉现象：AI 让开发者写代码更快，但软件交付整体没有变快。原因是代码生成后，测试、代码审查、合并、部署这些下游环节没有同步提速，反而因为 AI 生成的代码量增加而变得更拥挤。

给团队的实践建议：
  • 把审查和测试自动化前置：用 lint、类型检查、单元测试、安全扫描在提交前拦截问题，减少人工审查负担。
  • 建立 AI 生成代码的规范：例如要求 AI 生成的代码必须包含测试、注释和变更说明，否则不予合并。
  • 度量端到端交付周期：不要只看“代码行数/天”，而要关注从需求到上线的 lead time，找到真正瓶颈。

AI 是杠杆，它放大的不只是个人效率，还有流程中的薄弱环节。团队需要同步升级治理和工程实践。

📋 实践指南：为 AI 生成代码建立“可合并”标准

结合 GitLab 的研究和当前 AI 工具的普及，建议团队为 AI 生成代码制定明确的提交标准，避免审查环节成为瓶颈。

推荐的最小可合并清单（AI 生成代码版）：
  • 变更必须附带清晰的提交信息，说明哪些部分由 AI 生成、哪些经过人工修改。
  • 新增功能必须包含对应的单元测试或集成测试，且测试由开发者验证通过。
  • 运行静态分析和类型检查，确保无 lint 错误、无类型报错。
  • 复杂逻辑需要添加注释，解释“为什么这样设计”，而不仅是“做了什么”。
  • 涉及安全、权限、数据处理的代码必须经过人工二次审查。

可以在 CI 中强制这些检查，例如通过 pre-commit hook 或 GitHub Actions：

# .github/workflows/ai-code-check.yml 示例片段 - name: Run lint and tests run: | npm run lint npm run typecheck npm run test:ci - name: Require AI-generated code label uses: actions/github-script@v7 with: script: | // 检查 PR 是否标注了 ai-generated 或 human-reviewed

关键是把“AI 生成”当作一种需要额外标注和验证的变更来源，而不是默认可信的代码。
