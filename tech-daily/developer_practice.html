01Node.js 26.10.0 把 debounce / throttle 和 PKCS#12 解析搬进核心

Node.js 26.10.0 新增 util.debounce() 与 util.throttle()，以及 util.markPromiseAsHandled()，直接进核心库；同时引入 crypto.parsePKCS12() 用于读取 .p12 / .pfx 证书包，并把实验性的 Virtual File System 扩展到了 node:ffi。

对一线开发者的意义很直接：debounce/throttle 几乎每个项目都在手写或用 lodash 顶一下，如今可以少一个依赖、少一类"每个库实现边界不一致"的坑；PKCS#12 解析进核心则让证书链/客户端证书的加载不再依赖 OpenSSL 命令行或第三方包。Node.js 26 现已进入 Active LTS，适合新项目起步。

03Google Cloud Compute Engine API 改为不可变的日期版本

Compute Engine API 的日期版本化正式 GA：用不可变的季度快照（如 2026-09-01）取代单一可变的 /v1 面，调用方可通过请求头或查询参数按请求选择版本。

02 深度技术解读

Anthropic 的"常驻 Agent"架构：把 always-on 拆成五个部件

Anthropic 发布了一份可以照着搭的架构说明，讲的是"始终在线"的 Agent 到底由哪些核心原语组成。按社区提炼，它把常驻能力拆成几块各自职责清晰的部件：事件收件箱（inbox）负责接收外部事件，计时器（timers）提供主动触发能力，记忆（memory）保证跨会话的连续性，再加上权限（permissions）与发件箱（outbox）。

这份文档真正有价值的地方不在"这五样东西有多新"——收件箱、计时器、记忆、权限、发件箱单独看，很多团队早用"队列 + 定时任务"拼出过类似结构。它的价值在于把每个部件的职责边界划清楚，并明确一个容易被误解的点：

"始终在线"是一种使用体验，不等于让模型一直挂在线上烧 token。常驻 Agent 大部分时间应该在睡觉、等待 inbox 事件或 timer 唤醒，只在真正有活时才调用模型。

给一线开发的落地建议：照这份文档搭骨架时，先落"事件驱动的空转循环"——inbox 收事件、timer 兜底、状态写进 memory，模型调用放在被事件唤起的分支里；权限做成显式的 gate，而不是散落在 prompt 里。配套工程上，记住另一条同日的观点："没有 eval factory，就没有 software factory"——常驻 Agent 的行为一旦上线就长期运行，没有可回归的评测集，你无法判断某次"记忆写入"或"权限放宽"是否让整体质量退化。

📎 来源：elvis (@omarsar0) · Anthropic always-on agents guide · meng shao · Claude 团队架构说明 · elvis · eval factory

Shopify Cyber Chaos Monkey：用 AI Agent 在生产环境"打自己"

Shopify Engineering 公开了内部系统 Cyber Chaos Monkey（CCM）：把攻防模型、源码、基础设施知识和真实测试店铺的凭证交给 AI Agent，让它们在生产环境里主动寻找绕过防护的新方法。名字致敬 Netflix 2011 年的 Chaos Monkey——思路是把混沌工程（主动制造故障来检验系统韧性）迁移到安全领域。

动机来自一个现实压力：前沿模型让"发现漏洞"的成本越来越低，全行业收到的漏洞报告都在猛增。Shopify 称自家漏洞赏金计划的报告量自 2024 年以来增加了近 300%。他们的判断是——同样的模型也能帮防守方，且 Shopify 比外部研究者更了解自家系统，应该抢先找到影响最大的问题，抬高外部挖到漏洞的难度。攻击者瞄准生产环境，测试也就必须对着生产环境做。

  • 先定方向再动手：CCM 像一名赏金研究员，手里有源码、威胁情报、历史漏洞报告、部署记录，还能用真实测试店铺调用线上接口。
  • 两段式结构：系统分"发现模块"和"沙箱"。一个想法先进发现模块，由最新攻防模型缩小范围，有价值的线索才交给沙箱。
  • 任务来源多样：可来自安全工程师、上游的其他安全 Agent，也可以来自发现模块自身的反馈。
  • 硬约束：不能影响服务可用性，也不能危及商家数据。

对工程团队的启发不在于"照抄一个红队"，而在于它示范了一种把第二个 Agent 当裁判的闭环：让 Agent 去试探，再让另一个 Agent 判定结果是否成立，从而把"AI 找漏洞"这件高风险动作约束在可控沙箱里。想落地的话，第一步不是接模型，而是先把"测试凭证的隔离"和"允许触碰的边界"定义清楚。

📎 来源：meng shao · Shopify Cyber Chaos Monkey 解读

03 工具推荐

Kiri Rust

Rust 写的容器运行时，主打一个"快"：启动 Docker 容器约 22ms，对比 OrbStack 的 279ms、Docker Desktop 的 178ms，快了十几倍。VM 空闲 60 秒自动关机并有唤醒机制，适合本地开发省资源。

目前是 beta，可能有些 bug；作者已用它替换 OrbStack。适合愿意尝鲜、对本地容器启动速度敏感的后端/DevOps 同学。

📎 来源：Viking

Mole CLI 跨平台

Tw93 的电脑清理工具近期大幅更新，Mac / Windows / Linux 三端同步。Mac 端补齐了约 900 款软件的卸载残留清理，开发工具与编译过期内容、iOS/Android 模拟器缓存都能清；Windows 补上 360、夸克、QQ、飞书、剪映、Trae 等常用软件缓存，卸载时保留游戏存档、Epic 游戏与 WSL 磁盘，并新增 mo installer 挑出久置安装包。

04 实践指南

① 多模型分工的 CLAUDE.md：Claude 规划、Codex 干重活、Codex 交叉审查

数字生命卡兹克分享了一套自己长期在用的多 Agent 协作分工：跟 Claude 对话做规划与前端，把成块的后端/算法/数据处理/性能活派给本机的 Codex（GPT-6.1 Sol），再让 Claude 收尾，最后启动 Codex 做最多三轮审查。核心是把"你定接口和验收标准、Codex 写实现"这条边界固定进 CLAUDE.md。

## 派活
- 成块的后端、算法、数据处理和性能活（不是一两行的修补）
  交给本机的 Codex（GPT-6.1 Sol）写，你定接口和验收标准；
  前端、视觉、文案、拆解和验收自己做。
- 用 `codex-worker <工作树> "任务"` 派；
  追加用 `codex-worker --resume <会话ID> <工作树> "追加"`，
  放后台跑，会话 ID 在输出最后。
- 它只能写工作树和临时目录，提交不了、联不了网：
  装依赖、联网测试、提交推送由你做。
  它只看得到任务和工作树，接口、验收标准、要一起改的同类都写进任务。
- Codex 交回后你读 diff、自己跑测试（合并前的审查也是 GPT，
  你这步才是换家模型的交叉检查）。PR 里有 Codex 写的代码就是混合来源，交付不带 --agent。

这套流程有两个值得抄的设计点：权限最小化（worker 只能写工作树、不能联网/提交，装依赖和推送由人来做，天然把"不可逆动作"留在人手里）和交叉检查（写代码和审代码用不同家的模型，避免同一模型的盲区）。作者也坦言用的是自建 codex-worker 脚本而非官方插件，因为官方插件"有点麻烦，问题也有点多"。

📎 来源：数字生命卡兹克

② 换模型后跑一遍 prompt-audit：审计 CLAUDE.md / skills / commands

Peter Yang 给了两个可以直接用在新模型上的审计提示词：

  • /doctor prompt-audit：审计你的整个 Claude Code 配置（CLAUDE.md、skills、commands），并给出修复建议。
  • /claude-api prompt-audit [skill name]：对单个 skill 做深度审计。

他的建议是"每次 Anthropic 发布新模型都应该跑一遍"——新模型的理解力和指令遵循方式可能变化，旧 prompt 里为迁就旧模型写下的大量补丁，往往在新模型上要么冗余、要么反而拉低效果。把这一步固化成"换模型后的 checklist"，比拍脑袋重写整个 CLAUDE.md 更省事。

📎 来源：Peter Yang

③ 主会话 + 任务双层设计：让"老板"能越过总监看细节

宝玉抛出了一个很实际的 Agent 交互设计问题：只盯主会话，你就无法干预子任务细节、看不到执行过程、不方便补上下文；而像 Claude Code 那样开一堆 Session，管理起来又很累，人得自己记住每个 session 在干什么。他给的比喻很到位：前者像"老板只能通过部门总监了解情况"，后者像"老板自己当每个项目的项目经理"。

理想形态是两者结合：人只盯主对话，每次发消息时由会话的协调器判断这是普通对话、还是属于某个任务；对具体任务能点开去干预——既能透过主会话看任务细节，又能直接指挥。同一天他另一条补充指出：从主会话里应当能"沉淀"出两样东西——任务（让 Agent 去做的某件事）和成果（这件事做完产生了哪些结果），否则主会话会退化成"微信群"，有价值的话题和文件都难找。

📎 来源：宝玉 · 主会话与 Session · 宝玉 · 沉淀任务与成果

④ 当 Agent 写 PR 比你看 PR 快：把重要 PR 做成带旁白的分镜短片

Matt Pocock 预告了一个 /animatic Skill，解决他自己遇到的瓶颈："Agent 写 PR 的速度已经超过我审 PR 的速度，大段 diff 也读得很慢。"他的办法不是全程录屏，而是做成 animatic（分镜短片）：每一帧一张静态画面、配一句旁白，由 Agent 做好贴回 PR。整个流程由一条构建命令串起来：

  • 先写一份 JSON 格式的分镜脚本，每一拍对应一句台词和一帧画面；
  • 用 Playwright 渲染画面，代码直接取自 diff，并保留真实行号；
  • 用选定语音逐句朗读，最后用 ffmpeg 合成 MP4，并逐帧检查画面与音频；
  • 生成后按仓库配置贴回 PR（GitHub、GitLab 或本地目录均可）。

工程优化也有参考价值：同一支视频的优化前后对比，总耗时从 397 秒降到 96 秒，模型耗时 244s→85s，对话轮次 27→12，费用 $1.38→$0.49，每轮脚本处理时间从约 50s 降到约 6s，并改为逐帧检查；平均完成约 4 分钟。/setup-animatic 负责逐项只问一次工具选择（语音可选 ElevenLabs / OpenAI 等），把答案存进文档，避免重复配置。

📎 来源：meng shao · Matt Pocock /animatic Skill

⑤ 成本工程：按"每个解决任务的成本"选模型，而不是按每 token 价

同一天有两条互相印证的观察。AWS 博客在介绍用 NVIDIA NeMo Switchyard 给编程 Agent 做模型路由时指出：开发者真正为"任务"付费，而不是为单次调用付费；一个任务可能要几次到几十次模型调用，总成本取决于需要多少轮、每轮重放多少历史、以及任务是否反复重试或永远不完成——没做完的任务你也一样付费。因此模型路由应当用 cost per solved task（总成本 ÷ 测试通过的任务数）来衡量，而不是只看 token 单价。

另一条来自 Google Antigravity 的 Orchestrator：它让一个前沿模型（Carbon）出计划，把代码编辑与测试交给快速执行模型（Hydrogen），遇阻时前沿模型再回来修计划；官方称在 Terminal-Bench 4.0 上接近 Carbon 的任务成功率，同时少消耗 24% 配额、平均快 19%。这类"规划模型 + 执行模型"的分层，本质上也是在优化同一个指标。

实践提醒：在成本报表里，把"平均 token 单价"换成"每个通过测试的任务成本"，你会立刻发现哪些重试、长历史重放和未完成任务正在悄悄吃掉预算。

⑥ SDD 规范驱动开发：用"约束"压住 AI 产出的方差

58 沈剑在《代码都被 AI 写了，那人的价值在哪里》里给了一个清晰的问题拆解。传统研发是"人驱动、流程为人设计"，前半段（需求→设计→架构→用例→开发联调→测试→上线）最花时间；AI 时代这些步骤的时间被极大缩短，如果流程不变，人与人之间的沟通反而成了瓶颈。

但直接把流程丢给 AI 会出问题：AI 不知道你公司的具体业务、不知道团队的设计约束与规范、不知道特定技术栈的架构约束——不是能力不行，而是知识太广、幻觉太多，不约束就会让产出质量的"方差"特别大。他的解法是 SDD（Specification-Driven Development，规范驱动开发）：让研发流程从"人工驱动"进化到"约束与规范驱动"，AI 不再只是执行，而是在约束与规范的范围内执行。他建议把研发生命周期拆成四个阶段，第一阶段是"需求约束（需求结构化）"。

对想落地 AI 编码的团队，这条的实用价值是把"写更好的 prompt"升级成"建更好的约束"——把业务规则、设计规范、架构约束显式化、结构化，才是压低 AI 产出波动的根。这在思路上和上文的 eval factory 是一对：约束管输入端，eval 管输出端。
