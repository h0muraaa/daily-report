协议MCP 规范转向「无状态核心」：水平扩展、Serverless 与 MRTR 一次到位

2026-07-28 版 Model Context Protocol（MCP）规范把旧版"状态化约束"替换为完全无状态的协议核心，直指 Agent 基础设施的规模化痛点。无状态化让 Agent 应用可以像普通 HTTP 服务一样做云原生水平扩展、部署到 serverless 平台，并且能用标准的 round-robin 做负载均衡——这在此前的状态化设计下很难实现。协议层还新增了标准化的 HTTP 头，用于在不做深度包检测（DPI）的情况下高效路由请求，并提供了缓存控制能力。

另一个值得关注的新机制是 Multi Round-Trip Requests（MRTR）：交互式、长耗时的任务可以跨多次往返继续，而不必长期占用连接。官方同步放出了 Python、TypeScript、Go、C# 四个语言的 beta SDK，已经在跑 Agent 的团队可以立刻开始迁移。对做 MCP server / client 基础设施的开发者来说，这是一次需要跟进的协议级变更。

MCP 无状态化解读：从"连不上"到"秒级扩容"，以及云端 Agent 怎么访问本地 MCP 工具

MCP 是 Anthropic 在 2024 年 11 月提出的开放标准，用来统一"AI 模型如何连接外部数据与工具"。它的架构是 client-server：MCP host（一个 AI 应用，比如 Claude Code）去连接一个或多个 MCP server。这次规范升级之所以重要，是因为旧协议把会话状态绑在连接上——server 端必须记住每个连接的进度，导致它没法被当作无状态服务水平扩展、也没法用普通的 HTTP 负载均衡。

  • 无状态核心：新版把状态约束从协议核心移除，server 可以在任意节点之间自由调度，云原生水平扩展、serverless 部署、round-robin 负载均衡成为开箱能力——对要做多实例 Agent 网关的团队是直接的架构红利。
  • 标准 HTTP 头路由：路由信息从"需要深挖连接状态"变成"读标准头"，网关不用做 DPI 就能把请求导向正确的后端，缓存控制也顺势得到标准化。
  • MRTR（Multi Round-Trip Requests）：交互式/长任务不必独占一个长连接，可以跨多次请求往返继续推进，配合无状态化让"长时间运行的 Agent 任务"也能跑在普通负载均衡后面。
  • 落地时机：Python / TypeScript / Go / C# 四个 beta SDK 已经可用，官方明确说"可以立刻开始迁移"。

配套的一个典型工程难题来自 AWS 博客：Agent 跑在云上，但用户的 Excel 在本地笔记本上。MCP 的两种传输——stdio（本地进程间通信）和 streamable HTTP（远程通信）——都解决不了"server 在本地、client 在远端"这个反向缺口。AWS 的解法是搭一个 MCP bridge：在用户本地跑一个持有 MCP server 的桥接进程，云端 AgentCore 托管的 Agent 通过 HTTP 连到这个桥，从而拿到本地 MCP 工具能力。对金融、财务这类"数据不出本地"的场景，这个"本地桥接 + 云端大脑"的模式直接可抄。

实践要点：升级到无状态 MCP 不只是改 SDK 版本号——它意味着你的 MCP server 可以拥抱 serverless 与标准负载均衡，但需要处理 MRTR 的进度状态存储（比如挪到外部 KV/DB）；而"云端 Agent + 本地 MCP 工具"的桥接，是把 MCP 能力扩展到用户设备资产上的关键模式。

让大模型输出确定的结果：为什么 Temperature=0 + 锁 Seed 还不够

做强化学习（RL）的读者都清楚，Rollout 的确定性是实验可复现的基石。腾讯技术工程这篇文章用一个非常具体的实验戳破了常见误区：同样的硬件、同样的提示词，把 Temperature 设为 0、关掉随机采样，甚至把随机数种子锁死——结果"是也不是"。实测环境是 vllm serve Qwen/Qwen3-8B：

  • Run-to-run 确定性是有的：同一时刻、没有其他并发请求时，多次同样提示词的回答完全一致。
  • Batch Invariance 做不到：一旦同时有别的请求进来，同样的提示词回答就会不一样。不同请求间的注意力机制是物理隔离的，不存在上下文污染——波动来自更深层。
  • 根因是浮点加法顺序：推理引擎底层的动态组批与算子调度策略，改变了浮点加法的执行顺序。浮点加法不满足结合律：(a + b) + c ≠ a + (b + c)。系统为了掩盖访存延迟，触发了非确定性的硬件级并行优化（Non-deterministic Hardware-level Parallel Optimization），这才是结果波动的真正来源。

这个结论的工程含义很重：如果你在跑需要严格可复现的实验（RL rollout、批量评测、回归测试），只靠"调低 temperature + 锁 seed"是不够的，还要考虑固定组批策略、关闭或显式控制硬件级并行、在部署层做确定性约束。反过来，如果只是面向用户的产品交互，这种"同样的输入偶尔给不同输出"在统计上无伤大雅，但做测试的同学要警惕——它意味着"重跑一次测试通过/失败"可能根本不是代码变更导致的。

可复现性清单：① 确定采样（temperature=0 或固定 seed）；② 锁定组批与调度（避免动态组批改变 FP 结合顺序）；③ 在关键路径上做确定性校验而非相信"重跑即真理"。

解析Firecrawl anydoc：Rust 写的文档转 Markdown 引擎，中位 4.7ms 覆盖 14 种格式

Firecrawl 开源了 anydoc——一个纯 Rust 实现的文档解析引擎，把 Word、PowerPoint、Excel、OpenDocument、RTF、EPUB、CSV、PDF 等 14 种办公格式统一转成干净的 GitHub 风格 Markdown（GFM）。官方 benchmark 对比 6 个竞品（libreoffice、unstructured、markitdown、pandoc、docling、mammoth）：中位转换 4.7ms，比第二快的 mammoth（52.5ms）快一个数量级，比 LibreOffice（1129ms）快约 240 倍；格式覆盖 14/14 是唯一全覆盖；综合质量分 80 为最高。

架构上它采用"统一文档模型 + 单一序列化器"：先按内容特征（而非扩展名）做格式探测，各格式专属解析器输出共享的 Document 模型（块、行内元素、表格、脚注、内嵌资源），最后走唯一的 GFM 序列化器，保证输出一致性。没有 ML 模型、没有外部服务依赖，同时提供 Rust crate、Node.js 包和 Python 包三种形态——对要本地批量喂文档给 RAG / Agent 的团队，这是可以直接内嵌的解析层。

交付大淘宝技术的 AI Coding 交付：分层知识库 + 文件化 RD 流程 + 质量门禁

复杂业务场景下，AI 研发交付要先打底。大淘宝技术团队把流程分为三阶段，重点打造第一阶段"底座"：分层知识库（main 全局业务 / applications 应用知识 / candidate 候选知识 / personal 个人经验 / template 模板），确保 AI 拿到正确上下文、减少返工；文件化 RD 流程——用 Markdown 承载需求分析、拆解、实现校验全过程，让研发状态可接续、可 review；质量门禁——在 PRD 验证、需求澄清、方案设计等关键节点设置人机协同 review 点，把返工成本挡在后期之前。

一个值得记住的原则是"不追求 100% 全 AI 交付"：AI 负责分析实现、人聚焦关键判断，通过知识沉淀与流程规范提升整体交付质量与稳定性，为后续自动化和多 Agent 协同打基础。对"多业务域、多应用、多模块"的复杂后端团队，这篇文章给了一套可直接落地的分工与门禁设计。

技巧烧了 5 亿 token 后：给 Codex / Claude Code 的 Skill 上下文瘦身经验

卡尔的AI沃茨分享了一个具体的踩坑与解法：因为 Fable 5 / GPT 5.6 Sol 越来越聪明，很多以前需要写死在提示词里的规则，模型自己就能判断，塞一大堆 Skill 指令反而占上下文窗口。他甚至观察到"10 天前 Claude Code 把自己的系统提示语删了 80%"。但他也踩了"一口气全删"的坑——删完才发现有些 Skill 在特定项目里仍然有效，又花时间一个个装回来。

他因此做了一个"Skill 瘦身的 Skill"（github.com/LearnPrompt/carl-skills），专治选择困难症。一个触目惊心的量化数据：装了 300 多个 Skill 之后，一个全新会话还没说话，光是 Skill 列表就占了约 9.9k token（启动上下文 10.1k）——也就是说近 98% 的上下文预算被"还没用上的 Skill"吃掉了。用 npx skills add LearnPrompt/carl-skills --skill skill-slimming -g 可以在 Codex 里直接配置。

可复用清单：① 定期审视 Skill 列表，删掉"模型已能自己判断"的规则型 Skill；② 保留在特定项目里仍会生效的 Skill；③ 量化启动上下文占用，别让 Skill 清单吃掉大部分预算。

安全给 Agent 设计权限模型：Cloudflare 的 Agent Access Model 与 WriteGuard

Cloudflare 用两篇博客点出了 Agent 时代的安全盲区。其一，过去 12 年企业安全从"信任网络"转向"信任身份与设备健康"（BeyondCorp 模型），但它假设的主体是"人"——任务级 Agent 运行是短暂的一次性过程，而长生命周期 Agent 服务会以远超人速的速度处理数据，"为人设计的控制，指向 Agent 时会安静地失败，而不是响亮地报错"。其二，WriteGuard 讲了一个具体事故："无限关票事件"——一个提示词写得太宽的清理任务，在三个并发会话里跑，几小时内把几千张工单全关了，而系统把所有变更都记在 Joe 名下，人肉排查了半小时才找到肇事 agent。

这两个案例对任何在生产环境跑 agent 的团队都是硬提醒：给 Agent 的权限要做最小化，对输出到共享系统的变更做审计与限额，把"任务范围过宽"当作一等风险对待。Cloudflare 开源的 Cloudflare OS（本期热榜）里的 Gatekeepers 框架，正是这套治理思路的工程化落地。
