02MCP 发布以来最大更新：砍掉握手与粘性会话，走向无状态 HTTP

MCP 官方口中的「发布以来最大一次更新」方向出人意料：无状态化移除初始化握手、废除会话粘滞，每个请求必须独立携带完整的上下文信息。这意味着远程 MCP 服务器从此可以像传统无状态 HTTP 服务那样运行，采用轮询调度即可，无需配置会话亲和性。

对运维来说这解决了运行远程 MCP 服务器时长期存在的会话管理痛点；但开发者社区意见分裂，有评价认为「刚从蹩脚的 SSE 迈向成熟的 WebSocket，又被拽回上古世界观」。AgentStatus 创始人直言：现代协议与旧版协议共存阶段会非常混乱，故障率可能更高。新旧协议共存是接下来要面对的迁移难题。

03AWS 开源 Dogwood：用「时序」策略治理 Agent 的连续工具调用

AWS 开源了 Dogwood，一个扩展 Cedar 的策略语言，新增时序条件，让策略规则可以基于 Agent 先前的工具调用历史做判断，而不只是孤立地看单次请求。覆盖审批、限流、累计配额等场景——比如「同一会话内连续调用超过 N 次某工具则拦截」。

协议为 Apache 2.0，已获 AgentCore Policy 支持；不过参考解释器（reference interpreter）尚未达到生产就绪。对正在构建 Agent 权限层的团队是一个值得跟进的方向。

深度技术解读

深度 01 DeepSeek Harness：「一切皆插件」的 Agent 操作系统

架构理念。「Harness」原义是马具、缰绳，引申为让模型能当 Agent 干活的那套外壳。DSH 的设计核心是「一切皆插件」：模型、工具、技能、会话、沙箱、UI 全部可替换重组，插件甚至可以调用竞对模型。这与 Harrison Chase 描述 deepagents 的架构同源——agent 运行的「backend」只暴露文件系统类操作（read/write/edit/execute），backend 本身可以是数据库、对象存储或真文件系统；backend 与 agent loop 分离，实现「separate the brains from the hands」，并可经 MCP、A2A 等标准端点部署。

# 安装（Node.js 运行时） npx @deepseek-ai/dsh # 常用插件示例（聚合站 dsh.so） dsh plugin --profile web add @liustack/modlens@latest # 识图/读截图 dsh plugin --profile web add github:dsh-external/dsh-at-file # @ 引用工作区文件 dsh plugin --profile web add dsh-paste-input # Ctrl+V 粘贴文件 dsh plugin --profile web add dsh-cc-tui # Claude Code 风格终端

插件生态爆发。上线当天 dsh-plugin 话题下出现上千个插件仓库，贡献者里大量 B 站 UP 主——发布当天热榜第一的 colleague-skill、第三的 OpenBiliClaw 都出自 B 站创作者。生态周边也迅速跟上：DSH Desktop（MIT 协议社区桌面客户端，双击即用，支持 macOS/Windows）、Windows 启动器（用轻量 WebView2 小窗口代替浏览器）、一套 runtime 覆盖 Desktop/Web/TUI 三种体验、消息队列增强面板（编辑/删除/插话/排序，误删 10 秒内可撤销）。

对开发者的意义。DSH 刻意不把「开箱即用」当作目标——它更像一个可组合的 agent 平台层。如果你正在做 Agent 相关产品，这套「模型 / 工具 / 技能 / 沙箱全可插拔」的分层值得借鉴；其插件生态的演进方式（聚合站 + 社区规范）本身就是一种分发模式的样本。

深度 02 Claude 文本水印原理：不改变选词的「统计指纹」与社区反制

机制。Anthropic 发布官方技术说明，解释 Claude 文本水印的工作方式。方案并非自研：Claude 用的是 Google DeepMind 2024 年发表在《Nature》上的 SynthID-Text，可上溯至 Scott Aaronson 2022 年的提案。这一脉方案的共同特征，是在模型选词时用「密钥」改变随机数的来源，从而在输出中留下统计痕迹。

Anthropic 举的例子很直观：模型写到「今天天气很冷，而且___」，下一个词可能是「阴沉」也可能是「灰蒙蒙」，对读者意思差不多。正常情况下模型用随机数在这些候选里选；加水印后选词过程仍随机，但随机数的来源变成由密钥和前文共同决定——文本读起来完全一样，事后拿密钥核对选词序列，就能算出这段话出自 Claude 的概率。

两个关键设计。① 水印不会让模型选它本来不会选的词（不会为了打标而硬塞「nubilous」这种生僻词），只在模型本就犹豫的选择上起作用；② Anthropic 内部测试未观察到对内容质量、创意水平或可读性的影响，并援引 Google 在 Gemini 上的数据佐证。

社区反应两极。一篇 MIT 协议的「脱水平印」开源仓库在 Anthropic 公布技术细节后数天内冲上 10,000 stars，同时针对 Claude / SynthID-Text / OpenAI 标记以及图片 PDF 中的 C2PA / EXIF 元数据。另一边也有工程视角的文章冷静指出：AI 文本水印影响有限——文本质量无损、实践中并非那么容易检测、不侵犯隐私，且到 2027 年各厂商大概率都会这么做。

实战 01 让 Agent 输出「简单格式」来省 Token：BaoCut 的真实调优

宝玉排查 BaoCut 转录慢的真实经历很有启发：让 Fable 5 / Codex 分析瓶颈，得到的都是「多开 workers、预热 workers」这类看起来靠谱但实际无效的建议。最后自己抓数据包才发现——耗时的根因是输出 JSON 格式太长，导致生成与校验时间都长。

改成纯文本 / 简单 HTML 输出后效果立竿见影：调用次数从 33 次降到 12 次，时间从 31 分钟降到 18 分钟；近 7 小时的访谈完整润色也只需 42 分钟。若走 Cloud 模型，1 小时视频完整翻译校对成双语字幕用 DeepSeek v4 Flash 成本约 ¥0.4。

# 核心 trade-off 让程序简单 → 模型输出复杂 → 费 token 让模型输出简单 → 程序解析复杂 → 省 token （如字幕润色需 diff 比对、把变更重新对应到原文单词）

关键教训：把「让模型输出结构化 JSON」当成默认答案之前，先算一笔 token 账——结构化的代价最终由你的调用次数和等待时间买单。

实战 02 SQL 优化：为什么「先聚合再 JOIN」更高效

数据量上来之后「查个统计结果要等半天」，往往是因为把聚合放在 JOIN 之后。JOIN 的计算复杂度与两张表行数的乘积相关（Nested Loop / Hash Join / Merge Join），数据量越大越慢；而聚合能把订单表从 N 行压缩到 M 行（M ≪ N）。

-- 先 JOIN 再聚合：先拼大表，慢 SELECT u.name, SUM(o.amount) FROM orders o JOIN users u ON o.user_id = u.id GROUP BY u.name; -- 先聚合再 JOIN：先缩行数，快 SELECT t.name, t.total FROM (SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id) t JOIN users u ON u.id = t.user_id;

优化思想一句话：尽早减少数据量，避免在大数据集上做 JOIN。小表测试和千万级数据下都成立。

实战 03 平台团队：用「接口与契约」替代「开会协调」

KubeCon 欧洲大会上的一个平台团队经验：把平台从「项目思维」转向「产品思维」。做法是引入生产者—消费者模型——提供某项能力的团队是生产者，使用方是消费者；生产者定义清晰的接口，交互走契约而不是临时协调。

一条可操作的经验法则：如果两个团队需要定期开会来协调工作，说明它们之间的接口很可能没被明确定义。同时「完成」的定义从「按范围和期限交付」改为「当一项能力能被其他人可靠地使用」——有文档、易理解、可运维、真正被目标消费者使用。评估就两个问题：「有人用它吗？」「它减少了用户的阻力吗？」
