▚把一个 7B 模型服务的冷启动从 2 分半压到 12 秒

场景 / 问题

客户要在同一平台托管 OCR、图像识别、内容审核、信息抽取、公式处理等大量模型，却是典型的「稀疏流量」——模型很多，单个却很闲，冷门的一天只被调用几次。若每个模型都常驻一张 GPU，几十上百个模型就是几十上百张卡，账算不过来。于是走 scale-to-zero：无人用时彻底退出，把 GPU 还给资源池，下一条请求到来再临时拉起。

实现细节

用官方 vLLM，7B 模型冷启动约 2 分半。先做最容易的优化：镜像提前拉到节点、模型文件缓存到本地、权重页读热，耗时降到 43 秒。真正难啃的是剩下的 43 秒——镜像和权重都已在本地，为什么还慢？作者把优化思路归为三类：「少做一点、并行做一点、做过的事情尽量别重来」，把一次「7B 启动 + 短回答」从 43.12s 压到 11.74s。

实践建议

冷启动优化没有「一键加速」的魔法开关。先分清哪些是加载耗时、哪些是初始化 / 图编译耗时，再针对性地做缓存与并行；对稀疏流量场景，scale-to-zero 能显著提升 GPU 利用率，但必须接受冷启动延迟，并把它挡在用户体验之外（预热池、请求排队或降级）。

来源：阿里技术

▚Sub-100ms 分布式 API 设计：把延迟预算拆到每一跳

场景 / 问题

InfoQ 演讲，作者基于 eBay 的实战规模，讲如何在分布式系统里设计稳定、低延迟（100ms 以内）的 API。难点不在单点提速，而在复杂调用链里「谁吃掉了延迟、尾延迟为什么压不下来」。

实现细节

核心是 hop-by-hop 的延迟预算——把总预算拆到每一次网络跳转，避免某一跳偷偷吃光全部额度；再配合异步 fan-out 的取舍、线程池容量规划、缓存与熔断器，专门治理 tail latency（尾延迟）瓶颈。

实践建议

「性能优先」应作为工程习惯而非事后补丁。设计时就把 P99（而非均值）当目标，逐跳设预算、按跳定位瓶颈；对扇出高的接口，优先评估异步化与并行化的收益边界，再用熔断保护下游。

用 AI 接老代码、开发新功能：高手的 4 步流水线

把老项目直接扔给 AI 读，几乎必然踩三个坑：定位慢（一个功能横跨页面/接口/逻辑/数据访问，无关代码占满上下文）、装不下（几十个模块塞进去烧 token 还跑偏）、换会话从头再来。可落地的流水线是：

  • ① 了解项目资料：别裸读源码，先建「项目 Wiki（干什么、模块分工、主流程、数据关系）」+「代码地图（功能入口、关键代码、调用路径）」；
  • ② 明确需求与方案：拒绝一句话需求，需求没说清楚，一行代码都别开始写；
  • ③ 实现与 Review：写代码的 AI 和查代码的 AI 必须换模型、开新会话，交叉审查；
  • ④ 测试与验收：AI 做完 ≠ 能上线，人来兜底。

关键纪律：每一步的产物都作为下一步的输入——Wiki/CodeMap → 需求 → 方案 → 实现，形成可追溯的链，而不是每次重新「喂」一遍背景。

来源：架构师之路

腾讯 Octop Memory：光有 RAG 不够，Agent 长期记忆要「记得住、查得准、改得对」

把人聊过的话放进向量库确实能检索到相关片段，但要变成长期可用的项目记忆，还得回答三个问题：找到的是「用户的明确要求」「助手的临时建议」还是「工具当时返回的结果」？结论能不能回到存留的对话 / 结果去核对？只适用于一部分的条件，有没有在整理时被丢掉？新旧决定冲突时，下次该沿用哪一条？Octop Memory 的做法是「先按策略留下可回看的材料，再提炼和核验值得长期使用的内容」，并允许宿主按实际任务调整写入方式、提炼节奏、审核规则和召回时机。对自建 Agent 记忆层的团队，这套「材料 → 提炼 → 核验」的分层思路比直接堆 RAG 更能应对记忆的准确性与时效性。

来源：腾讯技术工程

JetBrains 扩展了 CLion 对 SEGGER J-Link 的集成：一键打开 Ozone 和 SystemView，同一套调试器也能给 AI Agent 使用。在 CLion 里即可覆盖写码 → 构建 → 烧板 → 目标调试全流程，调试器旁直接显示 RTT 输出、实时变量值和 RTOS 状态；需要更深分析时再跳转到 Ozone / SystemView。对嵌入式开发者，这是把「断点调试」和「系统级可视化 / AI 辅助」串进同一个 IDE 的实用升级。
