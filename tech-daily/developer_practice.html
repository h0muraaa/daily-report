DeepSeek Harness 架构深挖：为什么「一切皆插件」不是营销口号

DSH 官方宣传的"Everything is a plugin"容易被当成噱头，但看了多篇源码级拆解后你会发现它是有实底子的。整套架构建立在 Shigma 的开源元框架 Cordis 之上——这是一个与 LLM、Agent 无关的通用插件框架（QQ/Discord 聊天机器人框架 Koishi 就是它的用户），负责处理依赖注入、作用域服务与生命周期清理。DeepSeek 直接把 Cordis 源码 vendored 进来，把"模型适配器、工具目录、会话、存储、沙箱、Agent loop、Web UI、四种运行模式"全部插件化。腾讯技术工程的分析指出，Cordis 同时解决五个通常彼此分离的问题：插件在当前位置能看到哪些能力；依赖能力缺失时是否启动；同名 service 能否在不同作用域解析到不同实现；插件退出时注册项/监听器/进程由谁清理；静态配置怎样变成可热更新的运行时插件树。

  • 两套并行的系统： 山行AI 的拆解把它概括为 Cordis 维护的"运行时插件图"（谁依赖谁、在哪个作用域生效、卸载时清理什么）+ 会话/事件溯源层（模型所见皆可回放，便于调试与恢复）。
  • 工程取舍很激进： 全仓库工具 schema 从 52 个砍到只剩 1 个，目的是减少上下文占用；测试代码与生产代码接近 1:1；整个产品 65 天产出 84 万行、1 万多个 commit，Codex 署名的主干 PR 占 21.2%。
  • Code Mode 隔离： 工具执行默认走一个独立沙箱式 Code Mode，不是"听起来更安全"的简单子进程，而是把风险边界与审批策略一起做成可替换插件。

对想基于 DeepSeek 模型搭内部 Agent 平台的团队，DSH 提供了一套比"从零写 harness"低得多的起点：模型、工具、会话存储、执行循环都是可替换插件。对只想用它的开发者，先跑 npx @deepseek-ai/dsh web 启动 Web UI 即可，四种模式（标准 / PTC / 极简 / 创造）对应不同的工具暴露程度——理解这四种模式是上手的关键。

上下文与成本工程：从「无脑上旗舰」到「按任务配模型」

这周的新模型发布把"Agent 成本控制"推到了台面上。OpenAI 发布的 GPT-5.6 构建者指南给出一个很有冲击力的实证：同样效果，账单从 33 美元降到 1.33 美元。核心结论是"中小型号多想一会儿就能顶到上一代旗舰的水平，价钱只是零头"——不再需要无脑上最贵旗舰 + 推理拉满，通过型号搭配、推理档位、三个新的 API 开关，6 家已上线 Agent 的公司各给出了一条实测数字。这个趋势与本地开源模型相互印证：Qwen3.8-27B 在 17GB 内存即可本地运行、单张 RTX 5090 跑出 206 tok/s，能力追平六个月前的最强旗舰；GLM-5.3 用 7.5 万 token 达成 34.5% 完成率，比 5.2 少花 22% token 还高出 11 个点。

  • 上下文才是真正的成本杠杆： InfoQ 上那场《The Right 300 Tokens Beat 100k Noisy Ones》演讲直指 Agent 失败的主因是上下文窗口臃肿、prompt 塞太满，给出的工程化手段是 lazy-loaded skills、版本化 context artifacts、外部化 memory banks、LLM-as-a-judge 评测。
  • 企业侧已有落地模板： 腾讯云开发者的实践文章把生产级 Agent 归结为三个基础问题——一次任务可以访问什么、领域经验如何进入 Agent、长任务状态保存在哪，答案是统一 harness + skill 分发 + 虚拟文件系统管理上下文/证据/产物。
  • 别让评测失真： Meta 的 Wiggle 框架论文提醒，LLM judge 在"被追问"时会大幅摇摆（25%-71%），验证评测基准本身的稳定性与基准一样重要。

一句话给实践者的建议：把"贵模型 + 长上下文"当作默认方案的年代已经结束，先想清楚任务需要多少上下文、该用哪个档位的模型，再决定要不要上旗舰。

写一个 DeepSeek Harness 最小插件：理解「工具即插件」

Datawhale 的教程把 DSH 插件开发拆成"写最小插件理解机制 + 装现成插件用于日常"两部分。写插件的路径：clone 源码仓库、corepack enable && pnpm install && pnpm run build（注意要求 Node.js ^22.19.0 或 ≥24，build 一步不能省），然后在 scratch-plugin/src/ 下新建工具文件，导出名字与 apply 逻辑即可注册一个新工具。下面是一个 greet 工具的示意结构：

// scratch-plugin/src/greet-tool.ts
export const name = 'greet';

export function apply(ctx) {
  ctx.tool('greet', {
    description: '向用户打招呼',
    input: { name: { type: 'string', required: true } },
  }, async ({ name }) => {
    return `你好，${name}！你的第一个 Harness 插件已经运行。`;
  });
}

写完 build 后，插件的调用日志会在 Web UI 出现——这一步能直观理解"一切皆插件"里模型→工具注册表→执行回调的链路。

Redis Cluster 为什么只能用 0 号库：一个把无数 Java 工程师绊倒的「常识」

Redis 单机默认 16 个数据库（0-15），但集群模式下基本只能用 0 号库。根因在分片机制：Redis Cluster 全局只有一张槽位映射表（0-16383，共 16384 个槽），每个 key 通过 slot = CRC16(key) % 16384 落到节点。数据库号（DB index）是"同一实例内分隔数据空间"的概念，与跨节点的槽位分片天然冲突——若集群支持多 DB，同一个 key 的数据会因为 DB 不同而无法用槽位唯一定位，迁移、重分片都会乱套。文章还覆盖了键槽、迁移、为什么线上 RedisCluster 只有 0 号库的完整推导。想在线面试里不翻车的后端同学，值得一读。
