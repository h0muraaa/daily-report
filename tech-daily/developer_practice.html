按对一线开发的影响排序

CI/CDVercel CI 进入 Beta：只跑受影响任务，push 到“CI 通过”快 2–6 倍

Vercel 发布 Vercel CI Beta，核心思路是复用 Turborepo 的任务图：它读取 turbo.json，只运行被本次改动影响的任务，并且只为这些检查启动所需算力。官方称在其内部仓库里，从 git push 到 “CI passed” 的等待时间比之前缩短 2–6 倍，目标正是跟上越来越多由编码 Agent 提交的 PR。

配套能力包括：只跑受影响任务、使用 Vercel Remote Cache 做任务缓存、每次运行只安装一次依赖、在代码更新之间复用依赖缓存。对已有 Turborepo 的项目几乎零额外配置，每个带 ci 标签的任务都会在每次 push 时运行。

这项更新真正解决的是“Agent 把 PR 数量拉高之后，CI 成为评审前的排队瓶颈”。值得先量三个数：push→CI 通过的 p50/p95、每次 CI 实际执行的任务数、缓存命中率。如果任务图划分得粗，只跑“受影响任务”仍然会把整块工作全部拖进来。

来源：Vercel News · Vercel CI is now in beta · Vercel Blog · Introducing Vercel CI

FRONTENDNext.js 推出 next-bundle-optimizer：让 Agent 帮你删掉多余的 JavaScript

Next.js 官方发布 next-bundle-optimizer Agent Skill，用于分析并优化应用的 bundle；同时更新了 Bundle Analyzer 工具，让开发者可以直接查看产物体积构成。官方给出的使用方式是“让 AI Agent 调用这个 Skill 来定位并削减不必要的 JavaScript”，而不是手工逐个模块排查。

在此之前，bundle 优化依赖开发者阅读构建产物、判断哪些依赖被误引入，经验门槛较高。把它做成 Agent Skill 后，优化动作可以被重复调用，也更适合放进日常的“体检”流程。建议先建立基线：首屏 JS 体积、路由级分包大小、重复依赖数量，再让 Agent 在受控分支上提交改动并跑性能回归。

K8SKubernetes 1.37 “Garhwal” 发布：Metrics API 转正，Pod 检查点进入 Alpha

CNCF 发布 Kubernetes 1.37，代号 Garhwal，重点放在稳定性、安全性与 AI/ML 工作负载优化。最重要的变化是 metrics.k8s.io Metrics API 正式 GA，为节点与 Pod 健康度提供统一度量方式，也是 HPA、VPA 与 kubectl top 等能力的基础。

Alpha 特性同样值得关注：工作负载感知调度通过 InPlacePodVerticalScalingSchedulerPreemption 特性门控，让调度器抢占低优先级工作负载、为高优先级应用腾出资源做原地规格调整；新增 Pod 级检查点与恢复，可对运行中容器的内存与进程树做快照，便于调试与安全分析；StatefulSet 滚动更新新增 Recreate 策略。Rootless Kubelet 进入 Beta——标题里的“Rootless Kubelet”正是本轮安全增强的一部分。

升级前先做两件事：用 kubectl 的弃用 API 检查扫一遍清单；确认 HPA/VPA 在 Metrics API GA 后行为没有变化。AI/ML 团队则可以评估 Pod 检查点是否能降低长任务重跑成本，但 Alpha 特性不要直接上生产。

EDGECloudflare 开放 Quicksilver：Workers KV Instant 把 p99 读延迟从 287ms 打到 1.62ms

Cloudflare 把支撑其绝大多数请求的内部键值存储 Quicksilver，以 Workers KV 的新模式 “Instant” 开放私有 Beta。官方数据是：读请求 p99 延迟 1.62ms，而经典 Workers KV 为 287ms。差异来自数据放置位置与读取路径，而不是简单的缓存命中。

限制同样明确：每个 namespace 最多 10,000 个 key、总容量 1MB、每秒最多 1 次写入。这决定了它适合配置、功能开关、边缘路由表、小型白名单等“读多写少、体积很小”的场景，而不适合用户数据或需要高频更新的计数。经典 KV 的最终一致性模型在 Instant 模式下依然是设计前提。

如果你的边缘函数每次请求都要读一份配置，且能接受秒级写入频率，这个模式值得申请试用；但先算清楚 namespace 的 1MB 预算，别把“KV 是无限容量”的习惯带过来。

FRAMEWORKSpring AI 2.1 重构消息模型：推理块要在多轮往返中“原样带回”

Spring AI 2.1 把消息内容从“一段文本 + 附属的工具调用列表”改为有序的 message parts 列表。变化的原因是推理模型会把一部分“思考过程”交还给调用方，并要求下一次请求原样带回：Claude 会签名 thinking block，Gemini 在函数调用上附加 thought signature，OpenAI Responses API 则返回加密的 reasoning item。

官方明确提示：如果丢弃、重排或编辑这些块，轻则 HTTP 400，重则模型静默丢失此前的推理并从头开始。这不是某个框架的兼容性问题，而是所有多轮工具调用应用的共同契约——消息的“顺序”和“完整性”本身就是状态。

升级时重点检查三处：持久化层是否保存了 parts 的顺序与类型；网关或日志中间件是否在转发前“清洗”掉了不认识的字段；重试逻辑是否会重新组装消息。用一次带工具调用的多轮对话做回归，比只看单轮问答更能暴露问题。

ANDROIDLiteRT 进入 Google Play services：GPU 推理快 1.4 倍，安装包小约 8MB

Google 宣布 Google Play services 中的 LiteRT 支持由 ML Drift 驱动的 GPU 推理，并引入新的 CompiledModel API，官方称性能约提升 1.4 倍。相比把运行时二进制打包进应用，改用系统内置版本可让安装包减小约 8MB，同时获得跨数十亿设备的自动运行时更新。

迁移路径也被工具化：更新依赖即可接入，并可使用新的 Android Studio LiteRT Skill 做自动化迁移。对 Android 端侧模型应用来说，这解决的是“每个应用各自打包推理运行时、版本碎片化、包体膨胀”的老问题。

上线前仍需验证 GPU delegate 的回退路径：不同 SoC 与驱动对算子支持不一致，CompiledModel 编译失败时应有 CPU 回退，并记录首次编译耗时——它通常发生在用户第一次打开功能时。

Agent 质量的评测闭环，与 Agent 凭据的边界

Agent 质量不是“感觉变好”：把评测做成一条可以爬的坡

从 Agents CLI 的评测循环、Google 的 Skill 质量门禁，到阿里策略 Agent 的“谁更值得上线”

Agent 的退化往往不是一次大爆炸，而是许多小漂移：改了提示词、换了模型后端、加了一个工具、调了检索参数，单看每次都“差不多”，合起来却让通过率慢慢滑下去。Google 的 Agents CLI 把这件事拆成一个可重复的评测循环：持续测试与打分、捕获提示词回归、在切换模型后端时做并排 trace 对比、自动化评测执行，并接入夜间定时运行与基于阈值的告警。

这套循环里最关键的不是“跑分”，而是“可比较”。同一个用例在旧后端与新后端的完整 trace 要能并排看：模型在哪一步选了哪个工具、参数是什么、哪一步开始偏离、耗时与 token 花在哪里。只看最终答案的对错，无法定位是检索、工具还是生成出了问题；只有 trace 级对比，才能把“换模型”从赌博变成决策。

// 规模化的 Skill 需要产品级门禁

Google 的 Agent Skills 仓库在两个月里从 1.5 万 Star 涨到 2.1 万，收录了 170 多个来自 Google 各团队的 Skill，并分发到多个 AI 平台。官方第二篇复盘的重点不是“怎么写 Skill”，而是“怎么保证 170 个 Skill 不腐化”：每一次变更都必须通过自动质量门禁，另有一个 AI 审查 Agent 检查 Skill 质量，团队也总结了一套可以复用到自家 Skill 仓库的规则。

这提示了一个常被忽略的事实：Skill 不是提示词的别名，而是有接口、有依赖、有失效条件的“软件资产”。它需要版本、需要测试、需要审查，也需要在底层模型或工具变化时被重新验证。小项目写一个 SKILL.md 很容易，难的是让它在大规模分发后仍然可靠。

// 当输出没有标准答案，评测就变成“谁更值得上线”

阿里云开发者分享的策略效果类 Agent 是个更难的样本：商品营销场景里，Agent 输出的是补贴、投放、素材策略，没有静态正确答案；输入每天在变（业务效果、预算约束、帕累托最优策略、实验桶数据、人工规则）；离线看起来合理的策略，上线后还会受环境、货盘、周期与流量影响，线上指标变化也不能直接归因为策略质量。

更现实的约束是反馈信号稀缺且延迟：每天只能跑 3 组对照实验，T+1 才拿到业务效果数据，半个月大约积累 100 组。于是评测问题从“这条输出对不对”变成“多个可接受策略里，谁更值得上线”。这要求评测体系同时处理三件事：用少量高价值实验做在线验证、用离线回放与模拟扩大样本、把人工经验变成可复用的判断规则。

// 好 Agent 的“骨架”本身就在定义评测点

Arize 的产品内 Agent Alex 从 2023 年“50% 幻觉”的原型，演进为单个具备规划、记忆与按需技能（skills）的 Agent，且用自研 harness 代码而不是框架。它的几个决策恰好对应可测的边界：把计划移进 harness；把“结束”做成显式 gate；把大的工具结果当文件处理；每个用户一份 8,000 字符的记忆文件，效果胜过向量库与知识图谱；把 10 个专家 Agent 合并成 1 个；用生产会话当测试集。

Anthropic 关于“何时把 subagent 折回主循环”的讨论则给出另一条经验：不要照搬组织架构去拆 Agent，拆分会增加成本与延迟、降低质量；应该先用一小套 golden examples 度量，再逐个折叠；只有少数理由（如需要独立上下文、独立权限、独立生命周期）才保留独立 subagent。

评测层要回答的问题信号典型失败
单步 / 工具该不该调这个工具、参数对不对工具选择准确率、参数校验、trace检索到了但没用、参数幻觉
会话 / 任务多步之后是否完成任务任务成功率、轮数、成本、延迟中途放弃、死循环、提前结束
回归 / 变更换模型或改提示词后是否退化golden set 分数、trace diff静默退化、只在边缘用例上崩
业务 / 上线多个可接受方案谁更值得上线在线实验、离线回放、人工复核离线合理、线上无效

// 一个最小可用的评测配置

不必一开始就搭平台。先从生产 trace 里挑 20–50 个代表性用例，固定输入与判定标准，每次提示词或模型变更都跑一遍，并把结果写进版本库。下面的配置是示意，重点是把“阈值”和“对比基线”写死，避免每次靠人眼看：

# 示意：agent-eval.yaml，不是某个工具的官方格式
suite: checkout-assistant
cases:
  - id: refund-eligibility
    input: "我 15 天前买的鞋能退吗？"
    expect: {tool: order_lookup, contains: "可退"}
  - id: address-change
    input: "还没发货，改一下地址"
    expect: {tool: update_address, approval: true}

run:
  baseline: main
  compare: [trace, tool_calls, latency, cost]
  repeat: 5                 # 非确定性任务，取分布而不是单次

gate:
  min_pass_rate: 0.90
  max_cost_usd: 0.02
  max_p95_latency_ms: 4000

schedule:
  nightly: true
  alert_on_drop: 0.05       # 通过率下降 5 个百分点即告警
落地建议：① 评测用例从真实失败案例里长出来，不要凭空编；② 生成器与评分器分离，尽量用不同模型或规则评分，避免“自己批自己”；③ 对非确定性任务重复跑并看分布，单次通过不代表稳定；④ 每次模型切换必须做 trace 并排对比，而不是只看总分；⑤ 把成本与延迟纳入门禁，质量提升不能以 10 倍账单为代价；⑥ 保留人工抽检，尤其是“看起来对但理由错”的样本；⑦ Skill 仓库同样要门禁，变更必须可回归。

Agent 的凭据不该交给 Agent：从身份、网关到供应链签名

OAuth 只是起点，SDK 与网关都有边界；Chainguard 说补丁已经追不上利用

Keycard 的 Agent Auth 101 把现状说得很直白：今天大多数 Agent 拿到凭据的方式，是个人访问令牌、静态 API key，或者权限过大的服务账号。问题在于一次 Agent 请求往往横跨多个步骤、多个工具，当 Agent 用“你的令牌”发出一个操作时，系统很难回答“到底是谁发起的”。

合理的 Agent 鉴权需要几件东西：每个 Agent 有独立身份；支持委托（delegation）而不是共享人类账号；凭据短期有效且按需缩小 scope；能与遗留系统做联邦；有集中策略与审计。演讲还比较了 SDK 与网关两条路径——SDK 把凭据交给进程内代码，网关把凭据留在 Agent 够不到的地方，但网关本身也有取舍，比如额外的跳数、单点与策略复杂度。

// 补丁追不上利用，30 天窗口已经失效

Chainguard 的 Patrick Smyth 给出一个更不乐观的背景：前沿 AI 让攻击者整体更强，平均而言利用已经先于补丁落地，传统的 30 天修复窗口不再成立。他列出四类攻击面：恶意软件、已知 CVE、零日，以及“侧门”——CI/CD、开发者笔记本、Agent Skill。对应的动作是：设置依赖冷却期、加快 CVE 修复、用 SLSA 与 Sigstore 给所有产物签名。

微软 10 月的补丁数据是一个具体注脚：一次更新修复 1415 个漏洞，85 个严重，其中 1 个已被在野利用。这并不意味着“补丁没用”，而是说明“以月为单位”的节奏已经跟不上，尤其是面向公网与开发者工具链的组件。

// 社区信任也是供应链的一部分

Reddit 的 r/opensource（近 40 万成员）宣布不再接受任何使用 AI、由 AI 制作或专为 AI 打造的项目，并要求项目至少维护一年、拥有多名贡献者、发布者账号注册满一年。公告获得约 2800 条评论、净投票为 0，争议很大。版主的理由是：AI 降低了生成代码与创建项目的门槛，但不代表项目值得推广，“Token 很便宜，我们不在乎你花了多少 Token”。

这条规则是否合理可以讨论，但它反映了一个真实问题：当生成变得廉价，维护者的审查带宽成为稀缺资源，社区只能用“可验证的投入”来筛选。对 Agent 工具链而言，这意味着 Skill、MCP server、插件这类“看起来很小”的依赖，同样需要来源、版本与签名，而不能因为“只是一个配置文件”就跳过审查。

凭据模式典型风险改进方向
个人访问令牌无法区分人与其 Agent；离职/轮换困难per-agent 身份 + 委托链
静态 API key长期有效、易泄漏、权限过大短期凭据 + 按需 scope
共享服务账号审计只剩一个名字，无法归因一 Agent 一身份，账号与策略绑定
进程内 SDK 注入凭据进入 Agent 可读内存/上下文网关代持，Agent 只拿能力不拿密钥
无签名依赖CI/CD、笔记本、Skill 成为侧门SLSA/Sigstore、锁版本、冷却期

// 一次受控调用的形状

目标不是“让 Agent 拿到 token”，而是“让 Agent 发起一次可归因、可限制、可审计的请求”。一种常见做法是：Agent 用自身身份向令牌服务做交换，拿到 audience 与 scope 都收窄、TTL 很短的凭据，再由网关在出口处注入真实密钥并记录审计。示意流程如下：

# 示意：token exchange + 网关代持，不是某产品的真实配置
agent(identity=pr-reviewer)
  → token_service.exchange(
      audience="github",
      scope="repo:read pull_request:comment",
      ttl=300s,
      on_behalf_of=user_42
    )
  → gateway.call(
      tool="comment_pr",
      credential="<short-lived>",   # 网关校验后注入真实密钥
      args={pr: 123, body: "..."}
    )
  → audit(session_id, agent, user, tool, args_hash, result)

# 默认拒绝：没有对应 scope 的工具不出现在 Agent 的工具列表里
# 写操作需审批；只读操作也按数据域收窄
上线前的最小检查单：① 每个 Agent 有独立身份，不共用人类账号；② 凭据短期有效、audience 与 scope 收窄；③ 真实密钥由网关代持，不进入 Agent 上下文；④ 所有工具调用记录会话、调用链与参数哈希；⑤ 不可信输入（邮件、网页、PR 评论、外部文档）显式标记，写操作默认审批；⑥ Skill、MCP server、插件固定版本并做代码审查；⑦ 产物用 SLSA/Sigstore 签名，依赖设冷却期；⑧ 把补丁 SLA 从 30 天压到与暴露面匹配的节奏。

实践指南

六条可以排进本周工单的动作

01先建 20–50 条 golden case，再谈 Agent 升级

Agents CLI 的评测循环可以直接借用：固定一组代表性用例、每次变更都跑、对比 trace、夜间定时执行、按阈值告警。不必等平台化，先把“可比较”这件事做出来，模型切换和提示词调整才不再是拍脑袋。

  • 用例从生产失败样本里挑，覆盖工具选择、参数、多轮终止与拒答。
  • 每次跑 5 次取分布，非确定性任务不要用单次结果下结论。
  • 门禁同时约束通过率、成本与 p95 延迟，避免“质量换账单”。
参考：Google Developers Blog · Agents CLI Evaluation

02给 Skill 仓库加自动门禁与 AI 审查

Google Agent Skills 在 170 多个 Skill 的规模上，靠“每次变更必须通过自动质量门禁 + AI 审查 Agent”维持质量。小团队也可以从两条规则开始：Skill 必须有可执行的示例与期望输出；任何修改都要跑一遍关联用例，失败则阻断合并。

  • 把 Skill 当代码管理：版本、依赖、变更记录、负责人。
  • 底层模型或工具升级时，触发相关 Skill 的回归。
  • 对第三方 Skill 固定版本并审查，不因为“只是提示词”跳过。
参考：Google Cloud Blog · How we ship Google Agent Skills like products

03AI Coding 冷启动：先沉淀项目级 Skill，再按闭环交付需求

vivo 在 SmartFlow 项目上的结论值得直接抄：AI Coding 的瓶颈已经从模型逻辑能力转向上下文管理与开发意图表达。他们用两条循环主线落地——从存量代码与历史需求中提炼项目级 Skill，把隐性架构知识显式化；新需求则走“需求规格化 → 规格评审 → 受控实现 → 验证联调 → 知识回写”的闭环。最终交付时间比原计划减少 2/3。

  • 先做知识沉淀，不要一上来就让 Agent 改核心链路。
  • 每次需求结束把新知识写回 Skill，让下一次少踩坑。
  • 跨服务、跨机房、跨前后端项目收益最大，也最需要规格先行。
参考：vivo互联网技术 · 从知识沉淀到编程范式：AI Coding 项目冷启动落地实践

04高频“分类/选择”任务，交给轻量决策层

得物技术在测试域的三个场景——用例打标、UI 自动化操作选择、知识库召回精排——共同点是最终只需要一个明确的分类或选择。用通用大模型也能做，但高频执行时响应时间、调用成本与输出处理都会拖后腿。他们引入 Jev 作为轻量决策层，工程化地承接这类任务，整体流程获得约 10 倍提速。

  • 先盘点工作流里“只需要选一个答案”的节点，这些是决策层的候选。
  • 把决策层与生成层分开：生成负责内容，决策负责路由、筛选与判定。
  • 用固定评测集验证准确率，再谈替换通用模型。
参考：得物技术 · Jev 实战：为 AI 工作流引入轻量决策层 x10 倍提速

05把“一个人 + AI”拆成 Spec、Skill、Test Asset 三件套

腾讯云开发者沈淦把 AI Coding 的现状概括为“欺骗性失望区”：看起来没那么神、处处是坑，跨过去靠的不是换方向，而是把工程细节做扎实。他拆出上下文工程的五个环节——知识库、工具调用、对话历史、项目记忆、现场清理——并给出“个体团队”的黄金三件套：Spec（规格）、Skill（可复用能力）、Test Asset（可复用的验证资产）。

  • 没有 Spec 的 Agent 任务，等于让它在模糊需求上自由发挥。
  • Skill 负责“怎么做”，Test Asset 负责“怎么证明做对了”，两者都要版本化。
  • “现场清理”常被忽略：会话结束前清理临时状态，避免污染下一次任务。
参考：腾讯云开发者 · 一个人+AI就是一个团队？拆开“个体团队”的黄金三件套

06存量迁移用四条标准验收，而不是“看着差不多”

百度好看视频把鸿蒙端存量功能迁移拆成四个问题：迁什么、怎么迁、怎么证明迁得对、怎么持续迁移，并对应四条标准——完整（行为建模保完整）、正确（语义映射保正确）、可验证（分层测试保可验证）、可持续（迁移飞轮保可持续）。配合源码行为建模、需求矩阵对账、多设备适配、质量门禁与状态落盘，形成一套不依赖个人经验的交付流程。

  • “完整”先做行为清单，再谈代码：未文档化的预期行为要从源端代码里界定。
  • “可验证”靠分层测试与需求矩阵对账，避免只测主路径。
  • “可持续”靠迁移飞轮：每次迁移沉淀规则与用例，下一批直接复用。
  • 真实案例（随听频道）用 52 个行为点、65 条用例验证了这套机制。
