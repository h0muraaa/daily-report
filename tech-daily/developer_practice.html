Vercel 软件工厂：把开源库维护交给 Agent，人只负责 merge

AI SDK 是 Vercel 最热门的开源项目（每周 2000 万+ npm 下载、26K stars），维护它等于同时盯四个移动靶：模型供应商（新 provider/新能力/新 bug）、UI 框架绑定（React/Next.js/Svelte/Vue）、沙箱执行环境、以及 Codex/Claude Code/Pi 等 harness 适配层。多年增长后仓库每月涌入 100+ 新 issue，在 Opus 4.6 发布后 PR 达到拐点，6 月底累计了 1000+ 个未关闭 issue。Vercel 的解法是给 AI SDK 建了一条"软件工厂"：流水线里每一步都是一个 Agent，人类只负责合并变更。

运行四周后的数据相当有说服力：

  • 合并 PR 占比： 工厂产出了多达 35% 的已合并 PR。
  • Issue 清理： 7 月关闭了 70% 的 issue，未关闭 bug 总量下降 25%。
  • 流水线设计： 每个步骤是独立 Agent，质量与自治之间靠"人最后 merge"来平衡——机器负责生成、人负责把关，正好落在 Guillermo Rauch 所说的"self-maintaining software"愿景上。

对维护开源库或大型 monorepo 的团队，这套"Agent 分工 + 人审 merge"的架构是一个可复制的参考：它没有追求全自动（人在环路），而是把 Agent 放在最擅长的高吞吐重复劳动上，同时保留质量闸门。这是 2026 年开源维护模式演进的代表性案例。

MCP 无状态化：去握手之后，是更简单的路由，还是又变回 REST？

MCP 2026-07-28 规范做出了一次方向性改动：删除 initialize 握手与 session header，改为强制要求 method 和 tool-name header。动机很工程化——网关/路由层要在不解析 JSON body 的情况下对 agent 流量做转发与鉴权，靠 header 就能低成本路由，而握手状态对无状态网关是额外负担。这个变化本质上是把"会话状态"从协议层上移到应用层，与 HTTP 无状态的哲学一致。

  • 为什么争议大： 批评者认为这等于"重新发明 REST"——MCP 最初的价值之一就是给工具调用定义清晰语义，去掉状态后与普通 HTTP API 的边界变模糊了。
  • 支持者观点： 标准的存在价值不在于"多一套状态机制"，而在于统一的工具发现、描述与调用约定；无状态反而让 MCP 更好嵌入现有网关与中间件。
  • 对开发者的实际影响： 现有 MCP server/client 的握手代码需要适配新规范；对做 MCP gateway、工具路由、团队级 MCP 平台的人，这是接口变更，需要同步升级。

站在工程视角看，这其实是"协议演进到一定阶段必然走向简化"的又一例：当生态足够大，无状态、可路由、可观测成为刚需，标准就会朝 HTTP 的成熟形态靠拢。值得每个接 MCP 的团队读一遍差异说明再决定升级节奏。
