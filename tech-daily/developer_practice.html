DeepSeek Harness 架构拆解：为什么「一切皆插件」值得开发者关注

DeepSeek Harness 今天开源后，社区讨论最多的不是"又一个 coding agent"，而是它背后的架构选择。Harness 由 Cordis 元框架驱动，把 Agent 的每一个组成部分——模型、工具、技能、会话、沙箱、文件系统、循环、编排和 UI——都实现为插件。这意味着什么？官方给的一句话是："Everything is a plugin"。对照 Codex 这类把主循环、权限、工具调用写死在产品里的 harness，DSH 更像一个可组装的积木底座：你想换模型就换模型插件，想改主循环就改循环插件，想加沙箱机制就加沙箱插件。

  • 安装与上手： 官方命令 npx @deepseek-ai/dsh web，一个 Web UI 工作台；也可以让 Codex 等 agent 直接执行该命令完成安装。
  • 与 Codex 的定位差异： 爱范儿首发体验指出，DSH 具备管理项目、长任务协作、多 Agent 编排、上下文管理、联网搜索和 Skill 等本地 Agent 工作台该有的功能，但可自定义 Agent 预设、可重建会话、可插拔插件，让它和传统 Codex 类产品拉开差距。
  • 生态响应： 发布一小时内 Star 近 2 万；Geek 玩家已在做"毛坯房 + 宜家家具"式的自定义组装；社区还涌现了基于 Pi 的极简 Harness——DSCode 桌面版（适配 DeepSeek V4 Pro/Flash，主打缓存命中与便宜）。

从工程视角看，这套设计的价值在于把"Agent 框架的定制成本"从改写产品代码，降到了"写/换一个插件"。对想基于 DeepSeek 模型做自己内部 Agent 平台的团队，DSH 比从零搭 harness 省掉大量工作；对纯用户，它则是一个值得持续关注的"半成品"——正如社区所说，很多 Geek 就喜欢这种能自己动手组装的毛坯房。

[来源: DeepSeek] [来源: Berryxia.AI] [来源: 爱范儿] [来源: 小互(@imxiaohu)]

Cloudflare 六周追查：hyper HTTP/1.1 竞态条件如何「200 OK 却截断响应」

Cloudflare 记录了团队定位并修复 Rust 常用 HTTP 库 hyper 中一个罕见漏洞的全过程：在特定时序下，hyper 返回 200 OK 成功状态，但大型 HTTP 响应会被悄然截断。这个 bug 存在多年，直到 Cloudflare Images 重构 Workers Images 绑定时才暴露——上线后，部分大型图像转换请求间歇性返回截断数据，尽管响应报告为成功。团队花了六周时间追踪一个几乎不可见的竞态条件，最终只用了四行代码在上游修复。问题根因是 HTTP/1 实现中特定时序下的并发状态竞争，InfoQ 也做了中文编译，并指出该事件引发了 Rust 从业者对大型网络库中"只在特定时序触发"的深水区 bug 的讨论。

  • 定位方法： 从"响应成功但数据变短"这一矛盾信号出发，逐步排除中间件/缓存层，最后锁定 hyper 内部状态竞争。
  • 修复成本： 四行代码；但排查代价是六个星期——这类时序 bug 的最大成本从来不是修，而是"看见它"。
  • 对开发者的启示： 任何"偶发、间歇、成功但残缺"的网络问题，都值得怀疑底层库的边界条件，而不是先怀疑自己的业务代码。

hyper 从 2014 年至今被大量 Rust Web 框架依赖，这次修复已合入上游。对正在用 Rust 写网络服务的团队，这是一次难得的"大型底层库故障排查"公开课。

[来源: InfoQ]

阿里技术：把「改 Skill」变成可重复流程——评测 + 轨迹闭环

一个经典的 agent 维护痛点：skill 干着干着就在某些 case 上稳定翻车，改好一个又弄坏另一个，像打地鼠。阿里的解法是把"改 skill"流水线化，五步闭环：跑一批测试任务找出错 case → 按规则自动分析失败原因（不是瞎猜）→ 自动生成 patch 改 SKILL.md → 改完再验证"修好这个、没弄坏那个" → 通过就接受、不通过就丢进黑名单。跑几轮后 agent 处理该类任务的能力逐渐稳定。作者特别澄清这并非"AI 自己教自己"，而是用评测结果驱动的一版版迭代。想给自家 agent 建立可持续维护机制的团队，这套方法可以直接借鉴。

[来源: 阿里技术]

LangChain × Unify：两个工程事实——prompt cache 上限、Agent 降本 95%

Unify CTO Connor Heggie 分享了把 GTM agent 做成"给每个销售配一个工程师"的工程细节。两个数字最值钱：团队在发布前两周把成本砍掉 90-95%；以及 OpenAI prompt cache 存在约 15 requests/秒 的天花板——这决定了长会话 agent 的缓存命中设计必须考虑并发上限，而非无脑堆缓存。核心思路是让 agent 尽可能复用已缓存上下文，减少重复的 token 消耗，从而在销售对话这种高并发场景里跑出可接受的单位成本。LangChain 的延伸观点是：改进 agent 本质上是个数据挖掘问题——环境与评测是 agent 进步的货币，而评测数据要从生产轨迹里挖。

[来源: LangChain] [来源: LangChain(@LangChainAI)]

宝玉的跨平台 App 迁移实录：Electron → CLI → Rust + GPUI

宝玉分享了自己把视频编辑 App 从 Electron 迁移到跨平台方案的完整决策链。Electron 在"视频一长、字幕一多"时很卡、内存占用夸张；先做 Mac 版（Swift + AppKit）效果极好，但跨平台还要再想办法。关键路径是：先用 Rust 做了跨平台 CLI 的 PoC，音频转录和视频导出性能反而比 Swift 还好，且天然支持 Mac/Windows 多平台；再基于 CLI 接上 Rust 的 GPUI 做桌面 UI。他的判断很有参考价值——"AI 让写代码成本变低，但测试和验收成本还在那里"，跨平台的价值在于核心逻辑只需测一遍，剩下只有少量兼容性问题。他还对比了 Fable 5 与 GPT-5.6 Sol 写的 PoC 还原度。

[来源: 宝玉(@dotey)]

Grok 4.6 实战笔记：验收标准 > 提示词，措辞几乎没用

Cursor 团队 eric zakariasson 把 Grok 4.6 当几周主力模型后，写下最有价值的三条结论。第一，措辞几乎没用："努力工作、一直做到完"这类话对 4.6 基本加不上分，它自己就会撑相当久。第二，长 prompt 有用，但买的是"具体性"而不是"更长就更好"——你已经知道要什么，就写下来。第三，最高杠杆是验收标准，不是提示词写法。他还做了多组压测：浏览器帮走供应商控制台点出 API key、对跑着的应用做功能和视觉 QA、把收件箱压到只剩真正要回的几封，以及电子表格、浏览器版帝国时代 2、MSN Messenger 等一长串应用。他特别看重模型"何时说话、何时闭嘴"的分寸——小改动时安静，动很多文件才开始叙述，这个节奏比想象中难调。

[来源: meng shao(@shao__meng)]

AWS：参数化查询模板把 Text2SQL 端到端延迟砍掉 80%

Text2SQL 系统如果响应要 25-30 秒，用户流失会非常明显；而每次问答都调 LLM 生成 SQL，带来响应时间不可预测、限流和随流量线性增长的 token 成本。AWS 的解法是参数化查询模板：作为一层智能缓存，把高频问题模板化，只替换参数，避免重复的 LLM 调用。在生产部署里，这层缓存把端到端延迟降低了 80%、token 消耗削减超 50%，把"能跑的 demo"变成"可上线的生产系统"。对任何在做 Text2SQL、NL2Query 或同类 LLM 代理查询层的团队，这是一套低成本高收益的架构参考。

[来源: AWS Architecture Blog]
