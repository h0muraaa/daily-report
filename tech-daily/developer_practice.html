# MCP 走向无状态：移除协议会话，开发者追问"这不就又变回 API 了吗？"

MCP 2026-07-28 规范做了一次大改：从协议层移除会话。这对 Agent 基础设施的横向扩展是实打实的利好，但也引发了一场"这还是不是 MCP"的争论。

旧模型为什么是瓶颈

  • 早期传输以 initialize / initialized 握手开始，之后每个请求都要携带 Mcp-Session-Id 找到关联会话状态。结果：自动扩缩基础设施必须保留会话、部署时必须排空或迁移会话、负载均衡几乎不可行——客户端会被钉在持有其会话的那台实例上。
  • 新协议从核心请求路径移除握手、会话标头与协议会话。每个请求自带协议版本、客户端身份与能力，任何请求都可以落到任意实例。

被低估的改动：两个新 HTTP 标头

  • MCP 消息本质是 HTTP 上的 JSON-RPC，过去网关想知道请求是"列工具 / 调工具 / 读资源"必须解析 JSON 正文。现在 Streamable HTTP 请求必须携带 Mcp-Method 与 Mcp-Name 两个标头，例如 Mcp-Method: tools/call + Mcp-Name: search。
  • Cloudflare 的 Matt Carey 点出价值：网关、速率限制器、WAF 无需打开请求正文，就能按方法/工具对 Agent 流量做路由、限流与计量——复用它对其他 API 已有的那套机制。
实践要点：无状态化让 MCP 服务终于可以无脑横向扩展，但"状态"并没有消失——会话状态被上移到网关/外部存储，Agent 长任务的状态管理仍然是你的设计责任。

# DeepSeek Harness 的新范式：一切皆插件，让 Agent 为自己造工具

字节跳动技术团队与多家媒体的深度文章，把 DeepSeek Harness（DSH）的架构逻辑讲透了：把模型之外的一切都做成可插拔的插件，Harness 本身退到最薄。

Harness 只做三件事

  • 在 DSH 中，Model、Tool、Memory、Sandbox、Agent 都是可组合、可替换、可扩展的插件；Harness 本体只负责：调度模型与工具、在高危操作前请你审批、维护一份任务计划。
  • 启动方式极轻：npx @deepseek-ai/dsh web，默认访问 http://127.0.0.1:3080/。

关键心智：Agent 会话不再是"密闭盒子"

  • 过去 Agent 会话一旦启动就不能往里塞工具，客户端也不允许改核心逻辑与主流程。DSH 的"一切皆插件"打破了这一点：Agent 循环、Tool、Hooks、记忆管理全部可替换，官方提供 100+ 插件，也可以随时"Vibe"一个更趁手的插件替换实现。插件既能常驻，也能作为"轮抛"的临时工具。
  • 字节方舟把这一思路产品化为 Agent Plan：按 Agent = Model + harness，把"能干活、能记事、能成长、能出产品"所需的模型与 harness 组件打包，一次订阅、AFP 额度统一抵扣；DSH 提供插槽，Agent Plan 提供经过验证的"优选插件组合"（豆包搜索、记忆、Sandbox 等）。
  • 一个直观的例子：像"开会时临时要一个内容运营"，过去要招人、开会、且裁不掉；现在可以直接"捏"一个带技能的 Agent 加入会议，讨论完"优化掉"——能力边界随任务动态伸缩。
实践要点：DSH 的激进在于把"Agent 运行时的可修改性"当作第一公民。自建 Agent 平台时，与其把 harness 写成黑盒，不如把循环、工具、记忆、审批全部插件化，让它能被替换和扩展。

React 高频实时数据：Ring Buffers + OffscreenCanvas，把主线程让出来
