#02 深度技术解读
两个今天值得读透的底层真相：一个关于 coding agent 该怎么被评测与改进，一个关于自回归推理为什么"慢在等待而不是计算"。
// Harness 工程

"Agent 的进步 = Harness 的进步"：把评测从"最终结果"下沉到"工具边界"

今天至少有四个独立信源指向同一个结论：coding agent 的瓶颈正在从模型本身，转移到模型外围的 harness——编排逻辑、上下文传递、工具提供、失败恢复与评测方式。Google 开发者博客这篇《The Anatomy of Harness Engineering》直接点题：端到端基准（如 SWE-bench）贵、慢、且缺乏根因诊断，无法告诉你 Agent 的逻辑到底在哪一步断掉。解法是引入行为评测（behavioral evals）：快速、本地、单元测试式，断言离散的中间动作——例如"是否调用了某个工具""是否修改了某个文件"，而不是最终字符串是否相等。用这些廉价微检查撑起日常迭代，再配合宏观基准做发布门禁，团队就能放心升级模型、改 system prompt 而不怕回归。

LangChain 创始人 Harrison Chase 转发的 EMNLP'26 论文《Beyond Prompts: Measuring and Optimizing LLM Tool-Agent Harnesses》把这个直觉形式化：固定模型下的 harness 优化是一个"预算内选择"问题——harness 的编辑是发生在工具边界的守卫式拦截（guarded intercept），而不是重写执行逻辑。其 PRISM 方法对失败聚类，把每个修复路由到 prompt、middleware 或联合表面，再用 gate 挑选候选。AI Engineer 大会上还有一个成本佐证：Laurie Voss 重跑了一个一年前"200 条指令就能难倒所有模型"的基准——现在所有模型满分，上限逼近 2000 条指令，整场研究只花了 $29。评测的边际成本正在趋近于零，把它做进日常迭代完全可行。

// 行为评测：断言"工具边界发生了什么"，而不是最终输出
test("update_ticket 之前必须先 search 定位到目标单", async () => {
  const ctx = await runAgent(prompt, { tools });
  const names = ctx.toolCalls.map(t => t.name);
  expect(names).toContain("search_tickets");
  expect(names.indexOf("search_tickets"))
    .toBeLessThan(names.indexOf("update_ticket"));
  expect(ctx.toolCalls.find(t => t.name === "update_ticket").args.status)
    .toBe("resolved");
});
  • 对自建 Agent 的团队：把"调了哪些工具、以什么顺序、传了什么参数"落成可断言的 trace，比只看 pass@k 更容易定位回归。
  • 对选型/买工具的团队：优先选那些把评测与可观测性做进 harness 的平台（Deep Agents + LangSmith、Codex 内部同类闭环都是这个方向）。
  • 参考学习：CMU 26 秋季新课「AI Agents」（Graham Neubig / Daniel Fried）28 讲全公开，从零搭 harness、建评测、用 RL 训 Agent，是系统补课路径。
一句话：想加快 Agent 迭代，别只盯着最终结果。把"工具边界上发生了什么"变成可断言的单元测试，才是低成本、可解释的回归网。
// LLM 推理内核

Cohere 开源 Megakernel：decode 慢在"等待"而非"计算"，一个常驻 kernel 把 H100 顶到 62% 理论带宽

自托管 LLM 服务时，我们常默认算力（FLOPs）是瓶颈——但低 batch 的自回归解码是典型的显存带宽受限：每生成一个 token，都要把模型权重完整读一遍。以 Cohere 的 North Mini Code（约 30B 参数、每 token 激活 3.3B）为例，BF16 下每步解码要流过约 6.6 GB 权重，加 8K 上下文约 0.5 GB KV cache；H100 的 HBM 带宽 3.35 TB/s 对应理论极限约 470 tok/s，而 vLLM 只跑到 185 tok/s，仅利用理论的 39%。差距不在 kernel 本身，而在 kernel 之间：传统引擎把 QKV 投影、attention、MoE、RMSNorm 切成独立 kernel，彼此隔着全 GPU 的隐式同步与启动开销——对 memory-bound 负载，SM 在算子边界空转一拍，就是带宽利用率的直接损失。

Megakernel 的思路是把整个 decode 阶段的前向计算融合成一个常驻 GPU 的持久 kernel，消除算子之间的启动与等待。实测单张 H100、BF16、batch size 1 下达到 292 tok/s，即理论带宽上限的 62%，是 vLLM（185 tok/s）的 1.58 倍；端到端服务（batch 8）在真实基准上快 1.25–1.41 倍。Cohere 已把这一推理服务系统开源。

  • 自建推理 / 低延迟场景：把"kernel 启动开销"也放进选型指标，融合 kernel（如 Megakernel、FlashInfer 类路线）在低 batch 下收益显著。
  • 容量规划：当服务跑在带宽受限区，加 GPU 数量不如提高单卡带宽利用率；先看 SOL% 再谈扩展。
  • 对框架开发者：这是"持久化 kernel + 显式调度"路线可参考的完整开源样本。
一句话：自回归推理的优化哲学不是把单个 kernel 变快，而是让 GPU 别在 kernel 与 kernel 之间闲着。

#04 实践指南
五条今天就能落地的经验：一条大型成本治理打法、两条 Agent 稳定性/编排架构、一条成本权限治理反思、一条系统性学习路径。
PRACTICE 01 · AI 工程成本

Uber "AI 软件工厂"：请求量 ×9.4，总账单却能稳住——先把"成本优化"和"模型升级"两个变量拆开

Uber 在 2026 AI Engineer 大会上公开数据：超过 70% 的合并请求由本地或云端 Agent 生成，全司已构建 3600+ 个 Agent 技能、每天执行 3 万+ 次技能调用；从 2026 年 2 月到 8 月，周活跃用户 ×7、周 Agent 请求 ×9.4，但 AI 总支出自 4 月起基本平稳。关键方法论是"固定同一模型做对照"：由于工具采用率、负载构成与模型版本一直在变，想单独衡量优化收益就必须锁住模型。对照结果是每 1000 次请求成本较峰值下降约 34%，单会话成本较 6 月峰值下降 52%。落点：技能复用、缓存与 prompt 精简才是杠杆，别把成本波动简单归因于模型涨价或用量增长。

↳ 来源：AI前线（UberEng）
PRACTICE 02 · Agent 稳定性

大淘宝：长程任务断点续传的"框架 Checkpoint + 上层任务调度"两层架构

直播技术团队梳理了生产环境的三类中断：用户主动中断、工具执行中断（协作式）与系统级中断（机器重启/发布），长程任务、A2A 协同与人机协作场景都依赖恢复能力。方案在不修改 Spring AI Alibaba 框架源码的前提下做了两层：框架层扩展 InterruptableAction、用 Hook 注入关机信号检测、消息顺序修正、多工具调用 Mock 返回与子图会话 ID 记录，实现进程内状态保存/恢复；上层调度用 MQ 摘流阻止关机机器消费新消息，再靠任务表 + MQ 协调跨进程恢复。设计要点是给每一类中断一条显式的恢复路径，而不是统一"从头再跑"。

↳ 来源：大淘宝技术
PRACTICE 03 · MultiAgent 编排

得物：把 ReAct 换成"Plan 模式"——Plan 是一个有状态、可持久化、可被前端观察的运行对象

得物在基于 AgentScope Java 的企业级 MultiAgent 平台上总结：只用 ReAct 循环会遇到"前置步骤缺失到最后才发现、过程藏在 prompt 里无法审计、token 消耗难预估、工具失败后没有稳定恢复路径"四个问题。Plan-and-Execute 把"要做什么"与"怎么做"拆开：Plan 生命周期覆盖创建、Hint 注入、持久化与断点恢复、SSE 过程可见；主 Agent 与子 Agent 声明式配置与调用，跨服务用 A2A Agent Teams；企业级配套包括多租户隔离、双模式认证、全链路调用树、SSE 分层消息协议与"四道异常防线"。结论：复杂任务编排优先考虑 Plan-and-Execute，把 Plan 当"一等运行对象"而不是备注。

↳ 来源：得物技术
PRACTICE 04 · Agent 成本治理

腾讯云：一次需求触发数百次付费决策——"消费权限"要和"执行权限"一样被治理

一次真实事故：产品同学用 DeepSeek Harness 分析一个插件需求，输入只有几十 token，5 分钟内烧掉 1000 元。展开执行链路后发现后台实际输入约 1964 万 token、输出约 13 万，而用量记录里 cacheReadTokens 每次都是 0——缓存完全没生效；过程中启动了 12 个 subagent、反复检索、上下文被反复携带。文章点出更本质的产品命题：用户只提了一次需求，Agent 却在后台自主完成了数百次付费决策，用户既看不见也无从在成本扩张时确认。落点：给 Agent 设"消费权限"——预算上限、缓存策略、subagent 数量、关键确认点，与执行权限同等对待。

↳ 来源：腾讯云开发者
