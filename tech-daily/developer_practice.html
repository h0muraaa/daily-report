Bun 创始人 Jarred Sumner 宣布，用一批并行运行的 Claude 智能体，仅用 11 天就把 Bun 从 Zig 移植到 Rust，按 API 定价约花费 16.5 万美元。这表明过去被认为"规模太大无法实施"的软件重构，如今借助 AI 已变得可行——Sumner 称此次移植势在必行，源于 Bun 用户发现的漏洞数量日益增多（包括一个与近期 Claude 源码泄露相关的漏洞）。但 Zig 创始人 Andrew Kelley 强烈回击：这与语言差异甚至 AI 使用无关，而是"两个项目截然不同的价值观体系"，他质疑"测试套件连 Zig 代码的 Bug 都无法完全发现，凭什么能发现 100 万行未经审核的粗制滥造代码里的 Bug"。

# 上下文工程：压缩可能是个陷阱，提示词缓存才是成本主战场

在一场面向开源 AI Tutor 项目的实测中，Towards AI 团队跑了 11 种上下文处理预设，结果出乎意料："对上下文什么都不做"（原样保留历史）在召回、成本、延迟三项指标上同时打败了所有压缩技术，他们自己的生产默认配置甚至比"完全不动历史"更差。结论的关键在于提示词缓存。

为什么压缩会"亏钱"

  • 该场景下 97% 的 token 从缓存读取，而缓存 token 在某些 API 上价格便宜最多 50 倍。
  • 只要对上下文做任何改写（summarize / compact / truncate），就会使请求前缀变化、缓存整段失效，下一轮全部按全价 prefill 计费。
  • 因此压缩必须把上下文缩小超过约 50 倍才能覆盖缓存失效的成本——大多数场景根本做不到。Louis-François Bouchard 的结论很直接：summarization 可能是一个陷阱。

Claude Code 的成本模型（来自社区优化指南）

  • 单 token 价格三大决定因素：模型（更大模型更贵）、输入 vs 输出（输出约为输入的 5 倍，thinking token 占大头且由 /effort 控制，可用 MAX_THINKING_TOKENS=0 关闭）、提示词缓存（读 0.1×，写最高 2×，写入只发生一次）。
  • 以下行为会击穿缓存、导致整段会话重新全价 prefill：切换 /model、切换 /effort、开启 Fast mode、执行 /compact、缓存超时（订阅约 1 小时，API key 约 5 分钟，可设 ENABLE_PROMPT_CACHING_1H=1 延长）。
实践建议：常规体力活用小模型；保持会话前缀稳定、避免频繁切模型/切思考档位；轻易不要 compact；恢复旧会话基本必然全价 prefill；把"缓存友好"作为长会话的设计目标。

# Agent Harness 工程化：从"一切皆插件"到企业级 Skill 资产治理

这一轮最值得关注的基础设施变化，是 Agent 运行层（Harness）从"个人玩具"走向"企业治理对象"。三篇国内一线实践可以连起来看。

DeepSeek Harness：Cordis 微内核 + 三层组装

  • 底层 Cordis 只管"插件何时加载/卸载、如何协作"；产品的每个部分都是插件，连驱动 Agent 的主循环本身也是。
  • 中间三层组装：Profile（本地组装方案，列出要叠放的组合包与用户配置补丁）→ Bundle（组合包）→ 运行时叠加。换模型提供方不改源码、换沙箱后端不重启、换 agent loop 不动框架。

阿里技术：Skill 工程化，从 Prompt 工程到 Skill 工程

  • 传统 Prompt 工程把领域知识全部塞进提示词，项目越复杂 Prompt 越臃肿、上下文被撑满、复用性差。
  • Agent Skill 把领域知识与工作流封装为可移植、可版本控制的文件夹（类比"新员工手册"），Agent 按需加载。文章结合真实工程化项目 trade-ab-skill，讲结构规范、触发机制与作用域优先级。

百度 Geek 说：商业客户端 Harness 资产治理

  • 多产品线、多 Agent、多台 Mac 本地部署下，Rules / Skills / Hooks / MCP / 配置文件散落，配置漂移、规则冲突成为隐性技术债。
  • 方案从"单文件同步"演进到"ACX 仓库整体插件化"：ACX 唯一事实源 + 三层资产治理 + 每日自动同步，为规模化落地 Agent 研发模式提供可复制的资产管理范式。

一条主线：当团队把 Agent 当"一线生产力"时，资产的版本管理、分发、灰度、回滚会成为和代码资产同等重要的工程问题。

Agent 上下文CLAUDE.md

管理 Codebase 上下文文件，拿到更好的 Agent 输出

freeCodeCamp 的文章点破一个常见痛点：Agent 写出来的代码"能用但都得重写"，原因往往不是模型推理不行，而是"没人告诉它这个代码库怎么工作"。一个请求 90 秒出端点的背后，可能混入了 package.json 里没有的校验库、用了团队早已放弃的 Jest、在 route handler 里直连数据库——因为团队的约定都写在评审记录里而不是 Agent 能看到的地方。解法是把团队规范固化成上下文文件（如 CLAUDE.md / AGENTS.md），让 Agent 一进仓库就"知道规矩"。这是当前 ROI 最高的 Agent 提效手段之一。

成本优化Codex

在 Codex 中为 GPT-5.6 Sol 开启 1M 上下文窗口（配置逐行抄）

在 ~/.codex/config.toml 顶部（任何 [section] 之前）写入三行即可：

model = "gpt-5.6-sol"
model_context_window = 1000000
model_auto_compact_token_limit = 900000

更大的窗口让 Codex 在压缩旧材料前保留更多代码、工具输出与会话历史。但注意：宝玉的补充观点是官方已经为性能/成本调优过，只要压缩得当，上下文短一些反而更快更便宜——建议先保持默认，确有大仓库需求再开。

Agent 设计框架

"AI Agent 五要素测试"：判断什么业务该做成 Agent，而不是自动化

一个实用的判断框架：① 重复的触发器（高频重复才摊得平构建成本）；② 稳定的输入（输入越结构化，解析越可靠）；③ 明确的工具集（行为可控、结果可验证）；④ 可衡量的终点（没有验收标准就无法闭环迭代）；⑤ 中间需要判断力（每次运行有差异、要当下做真实决策）。关键洞察：前 4 条回答"这件事能不能被自动化"，第 5 条才是分水岭——规则驱动、路径完全相同的场景用 Automation（if-then），需要理解上下文、权衡选项、处理例外的场景才值得用 Agent（LLM 相对传统脚本的本质增量）。
