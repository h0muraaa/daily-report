X 重写 Web：流式 SSR + 首条帖子前零 JS，弱网首屏 22 秒降到 2.7 秒

X 的 Web 重写把首屏路径改成了服务端流式渲染：先把 HTML 流给浏览器，在第一条帖子出现之前不加载任何 JavaScript。效果是弱网下展示首条帖子的时间从 22 秒以上降到 2.7 秒，帖子与个人页加载快 8–13 倍，目前按国家逐步放量。这个案例的价值不在“又一个性能优化”，而在于它验证了一个常被前端架构忽视的顺序：关键内容先由服务端直出并流式送达，交互所需的 JS 延后水合。对内容型页面、控制台首屏、SSR 框架选型都有直接参考意义。注意测量必须在真实弱网与低端设备上做，本地 localhost 的 Lighthouse 分数说明不了这个问题。

Vercel Workflow SDK：start() 原子化，重复启动从竞态变成可预期的失败

Vercel Workflow SDK 的 start() 现在可以在一步内完成“准入运行 + 占用 hook”，重复启动会安全失败。此前常见写法是先 getHookByToken() 再 start()，两次调用之间的窗口存在官方文档承认的重复启动竞态。新模型下，hook 从运行被准入的那一刻起就存在，所以 resumeHook 可以在工作流真正开始执行前调用，提前到达的 payload 会按顺序缓冲；工作流内部用同一个 token 调 createHook({ token }) 会 guaranteed 绑定到已占用的 hook，不注册新 hook、不新增 step，getConflict() 返回 null。最关键的是 token 本身就是幂等键，并且来自你自己的业务域，比如订单号——不需要额外维护一张幂等表。

// case study · agent harness

天猫国际建场 Agent：用确定性外壳包住 ReAct 内核

需求是一句话：“帮我搭一个七夕轻奢箱包会场。”对人来说这是一个完整业务目标，对系统来说却远不是可执行指令：商品数量、选品条件、模块结构、素材尺寸、文案要求都可能缺失；执行链路还要跨 U+ 圈品、图片生成、文案生成、页面装配和人工修改，其中既有秒级同步调用，也有靠 MetaQ 回调完成的分钟级异步任务。天猫国际的做法不是“让大模型直接吐一份页面 JSON”，而是把系统拆成一个 ReAct 驱动的生产 Agent，外加一层确定性机制来约束边界。

架构：模型决定“做什么”，系统决定“写到哪、怎么恢复”

前端 SSE / AG-UI：文本 + 工具事件 + 业务卡片

为什么这层“确定性外壳”是必要的

  • 授权边界。模型可以提出“修改这个模块”，但不能绕过状态机直接写生产数据；每个阶段允许哪些动作由状态机裁决，而不是由 prompt 自觉遵守。
  • 写入边界。字段级生产计划与业务坐标把“改哪个会场的哪个字段”变成可定位的坐标，避免模型生成看似合理但落错位置的 JSON。
  • 恢复边界。任务账本记录已完成的步骤与外部副作用，长流程中断后可以续跑；异步圈品在对话结束后仍能通过回调更新任务事实，而不是把结果硬塞回已关闭的会话。
  • 交互边界。前端通过 SSE/AG-UI 同时消费文本、工具事件和业务卡片，用户能看到“正在圈品/正在生成图片”，而不是一个长时间无响应的 loading。

可复用的部分比“建场”本身更值钱

项目沉淀出的流式执行、AG-UI 事件协议、会话任务模型、工具执行与日志、异步任务续跑、Trace 和场景扩展点，都不绑定“会场”语义。换一个复杂 Agent 场景，比如 AI 设计或投放素材生成，可以直接复用同一套底座。这提示了一个很实际的架构判断：Agent 项目的第一次投入应该放在 harness，而不是 prompt。Prompt 会随模型升级重写，状态机、任务账本、事件协议和可观测性却会留下来。

给工程团队的检查清单：在接入第一个生产 Agent 前，先回答四个问题——失败后从哪里恢复？外部副作用如何幂等？模型能做哪些动作由谁裁决？前端如何展示中间过程？四个答案都没有，说明还停留在 demo。

// reliability · evaluation

91% ≈ 0%：Google PLE 揭开的“可行域瓶颈”，对代码 Agent 同样致命

Google 与 Mercor 发布了 Physical-Engineering's Last Exam（PLE），用 85 项机械、电气、土木与结构工程任务量化一个工程 Agent 的真实交付能力。结果很刺眼：在 56 项隐藏测试中，Claude Opus 5.5 搭配 Claude Code 得分 48.3%；在 41 项人机共同创作任务里，它平均能满足 91% 的单项约束，但只有 41.3% 的交付设计同时满足全部硬性安全与可行性要求。换句话说，模型把绝大多数题都“做对”了，却只有不到一半的方案能真正交付。

为什么剩下的 9% 不是“再强一点就能补上”

因为工程约束是耦合的。一条电缆桥架穿过消防管线，载流量算对、电压降达标、设备选型有依据都不够——几套系统争同一段净空，方案就得推倒重来。解决一个约束，可能触发另一个约束失效；刚核验过的结果也会随修订作废。PLE 把这种失败称为“可行域瓶颈”：局部能力已经足够强，难的是同时落在所有硬约束的交集里。

指标数值说明了什么
隐藏测试得分48.3%单题能力尚未过半，且这是较强组合的成绩
平均单项约束满足率91%“看起来快成了”的错觉来源
全部硬约束通过率41.3%真正可交付的比例
任务规模85 项 / 56 项隐藏测试覆盖机械、电气、土木、结构

迁移到软件工程：PR 的 91% 通过率也可能是 0%

同样的陷阱在代码 Agent 上天天发生：单元测试过了九成，但一个硬不变量被破坏——权限校验被绕过、幂等键冲突、迁移不可回滚——这个 PR 依然不可合并。用“平均通过率”做 Agent 评测，会系统性高估能力，因为它把“决定性失败”稀释成了几个百分点。更合理的做法是把硬约束做成 gate：全量测试、类型检查、安全扫描、数据迁移演练，任何一项失败即零分；再在 held-out 任务上测，避免 Agent 针对公开用例过拟合。模型侧也应接入约束检查器或求解器，让“检查是否满足全部约束”成为生成循环的一部分，而不是交付后的抽查。

一句话结论：Agent 的评分体系要从“做对了多少”改成“有没有一项没做对”。前者适合 demo，后者才适合上线。

今天就能改的 5 件事

分清 Playwright 的两种浏览器：测试用 Chrome for Testing，访问不可信页面用正式版 Chrome

最近流传“Playwright 自带漏洞浏览器，应该删掉”，官方说明这是一个误解：Playwright 的任何安装包里都不带浏览器。真正的区别在于使用方式。

  • 用 Playwright MCP 或 CLI 的 Agent：调用的是你电脑上的正式 Chrome/Edge，正常接收安全更新，沙箱默认开启，无需改配置。
  • 用测试运行器跑 npx playwright install：下载的是 Chrome for Testing，版本固定在当前 Playwright 验证过的那一版，且默认关闭沙箱。这是为了让开发机和 CI 跑同一个浏览器、避免自动更新搞挂测试。
  • 直接调库 API：chromium.launch() 的默认行为与测试运行器一致——固定版本、沙箱关闭。

因此，爬虫或 Agent 脚本一旦会访问不受你控制的页面，就应该改用正式版 Chrome 并显式打开沙箱：

const browser = await chromium.launch({
  channel: 'chrome',        // 用系统安装的正式版 Chrome
  chromiumSandbox: true     // 显式开启沙箱
});
→审计现有脚本：凡是 chromium.launch() 后访问第三方站点的，补上 channel 与 chromiumSandbox；测试用浏览器只用于可信应用的 E2E，并保持 Chrome 本身更新，因为部分漏洞可以突破沙箱。
来源: meng shao(@shao__meng)

工作流幂等：把“先查再启动”改成原子 start，用业务 ID 当幂等键

重复启动是工作流系统最常见的线上事故之一。旧写法 getHookByToken() 再 start() 在两次调用之间留下窗口，同一订单可能被准入两次。Vercel Workflow SDK 的新语义值得作为通用设计模板：

  • 一步原子化。准入运行和占用 hook 在同一步完成，重复启动安全失败，而不是靠分布式锁临场补救。
  • token 即幂等键。token 由业务域生成（订单号、工单号、支付流水号），不额外维护幂等表；同一个 token 天然指向同一次运行。
  • 提前消息可缓冲。hook 在运行被准入时就存在，resumeHook 可以在执行开始前调用，早到的 payload 按顺序排队，不会丢。
  • 重复 createHook 不新增 step。工作流内部用同一 token 绑定已有 hook，getConflict() 返回 null，重试不会把 step 数量越滚越大。
→检查你的事件驱动系统：入口是否用业务 ID 做幂等键？启动与资源占用是否原子？早到消息是否有缓冲队列？三者缺一，就该在下一版补上。
来源: Vercel News

上下文工程：把脚本执行移出上下文，把技能改为按需加载

AWS 的参考实现给出了两个很直观的数字：一个 write-and-execute 工具，让每段脚本进入上下文的 token 减少约 95%；按需加载 skills，让系统提示词缩小约 97%。背景是 200K 窗口在数据分析、报告生成这类任务里几分钟就会被烧穿，随后出现中途失败、准确率下降和成本上升。可操作的层次：

  • 工具输出整形。不要在上下文里塞完整脚本和完整日志；让工具在沙箱执行，只回传摘要、退出码和必要片段。
  • 技能按需挂载。常驻系统提示只保留路由信息，具体 skill 在被选中时加载，避免几十个技能把每轮请求都撑大。
  • 状态外置。把中间结果写进任务账本或文件，上下文只保留“去哪取”，而不是“全部内容”。
  • 分层而不是堆技巧。单独一个技巧容易看，组合起来才有可测量的收益；用同一任务对比改前改后的 token、时延和成功率。
→先做最小改动：把最耗 token 的那个工具改成“执行后只回摘要”，再记录一周的平均输入 token。通常这是收益/风险比最高的一步。
来源: Artificial Intelligence / AWS ML Blog

.NET 并行循环在单 CPU 容器里会退化成串行：别让默认值替你做并发决策

Stack Overflow 的文章指出一个很典型的容器化坑：Parallel.For/Parallel.ForEach 默认按 CPU 数量决定并发度。容器只分到 1 个 CPU 时，并行度就是 1；如果循环体是 I/O 密集型（调下游服务、读写队列），整个循环就退化成一条一条处理，吞吐骤降。解决不是简单把数字调大：

  • 显式设置 MaxDegreeOfParallelism，按 I/O 并发能力而不是 CPU 核数来定。
  • 给每个下游服务单独设并发预算：连接池大小、限流阈值、超时和重试要一起算，否则只是把瓶颈推到下游。
  • 在容器限制 CPU 的环境里做压测，别在 8 核开发机上得出结论。
→搜索代码库里的 Parallel.For、Parallel.ForEach 和 Task.WhenAll 批次循环，确认它们是否依赖 CPU 核数；I/O 循环补上显式并发度和下游限流。
来源: Stack Overflow Blog

Agent 产出的合并门禁：用“全部硬约束通过”替代平均分

PLE 的 91% 与 41.3% 说明，平均分会把决定性失败稀释掉。对代码 Agent 来说，一个 PR 即使 90% 的测试通过，只要一个硬不变量被破坏，就仍然是不可合并的 0%。建议把评审门禁写成可执行的规则：

  • 硬门禁全量执行。全量测试、类型检查、安全扫描、迁移可回滚演练，任一失败即阻断，不参与“打分平均”。
  • 隐藏用例。保留一组 Agent 不可见的 held-out 测试，防止针对公开用例过拟合。
  • 记录违规类型。不只记“通过率”，还要记违反了哪条约束、耦合关系如何，方便定位是模型能力问题还是 harness 缺检查。
  • 把检查放进生成循环。让 Agent 在提交前自己跑约束检查器；能自动验证的约束不要留到人工 review。
→给现有 Agent PR 流程加一个“零容忍清单”（安全、数据迁移、权限、幂等），先跑一周，统计被这个清单拦下的 PR 比例——这比看平均通过率更能说明 Agent 是否真的可交付。
