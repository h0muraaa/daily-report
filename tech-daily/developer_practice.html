🔬 深度技术解读

向量检索不够了：Neo4j 的上下文图（Context Graphs）实践
[AI Engineer / Neo4j]

Neo4j 的 Stephen Chin 在一个演讲中用医疗场景完美诠释了为什么"检索"（Retrieval）不等于"理解"。当你问一个向量 RAG 系统关于患者肺气肿护理计划的问题，它返回的是通用建议：呼吸治疗、深呼吸练习。但如果你给它一张基于该患者真实病史的图——知道他吸烟、做过手术——系统给出的建议就会完全个性化。

关键洞察：信息本身存在于两种系统中，区别在于系统是否能遍历连接这些信息的关系。对于构建复杂 AI Agent 的开发者，这提出了一个重要的架构选择：当业务实体之间存在丰富关系时，图数据库（Graph DB）+ 向量检索的混合方案可能比纯向量 RAG 更适合。

实践建议：如果你的 Agent 需要处理"这个用户的上次订单""这个项目的依赖关系"这类需要关系遍历的查询，考虑在向量相似度搜索之外引入图遍历能力。Neo4j 的 GDS 库或 Amazon Neptune 都提供了与 LLM 集成的方案。

Julia Evans：认真对待 CSS，而不是贬低它
[Simon Willison's Weblog]

Julia Evans（以技术漫画闻名）分享了她对 CSS 的态度转变：从"CSS is hard"的抱怨者，变成真正尊重这门技术的实践者。她发现很多 frustration（比如"居中不可能"）其实在 CSS 中早已被优雅解决，而且"居中"本身就不是一个简单的问题——不同场景下有不同的语义和实现方式。

这个观点与最近"逃离 Tailwind"的讨论形成呼应。Tailwind 的 utility-first 方法在快速原型阶段很有价值，但当项目进入维护期，内联的 utility class 会让 CSS 的语义层完全消失。Julia 的做法是：花时间去学习 CSS 的现代特性（Grid、Flexbox、Container Queries），你会发现原生 CSS 的能力远比你想象的强大。

给前端开发者的建议：如果你还在用 !important 和负 margin 做布局，值得花一个周末系统学习现代 CSS——这会从根本上提升你的布局效率和代码可维护性。

Netflix 的模型生命周期图：企业级 ML 系统的元数据架构
[InfoQ / Netflix]

Netflix 分享了一种基于图（Graph）的机器学习系统管理架构——"模型生命周期图"（Model Lifecycle Graph）。在大型组织中，ML 资产（数据集、特征、模型、实验、工作流）呈指数级增长，传统的元数据管理工具越来越难以回答"这个模型依赖哪些上游数据集""某个数据集的变更会影响哪些下游模型"这类问题。

Netflix 的解决方案是将 ML 资产及其关系作为一等基础设施关注：用图结构建模数据集→特征→模型→评估→部署的完整链路。这种以元数据为中心的 ML 平台设计正在成为行业趋势，Google 的 Vertex AI、AWS 的 SageMaker Lineage 都在走类似路线。

对 ML 工程师的启示：如果你的团队已经开始为"模型版本混乱""实验不可复现""特征来源不明"头疼，引入一个支持血缘追踪（lineage tracking）的 ML 元数据平台（如 MLflow、KubeFlow Pipelines 或自研图系统）是架构升级的关键一步。

📋 实践指南

AI 产品中如何利用领域专家：三种组织模式
[AI Engineer / Notius Labs]

Chris Lovejoy 分享了 Granola 团队组织 AI 产品开发的三种模式，对正在构建 AI 应用的团队非常有参考价值：

Oracle（神谕模式）：领域专家拥有完整闭环——既评估质量，又直接改进 prompt。适合创意类输出（如会议记录），因为没有"客观完美"的标准，需要有人用品味做判断。

Evaluator（评估者模式）：领域专家定义质量标准并度量，工程师负责迭代实现。适合有明确评估指标的任务（如准确率、召回率）。

Architect（架构师模式）：构建能从使用数据中自动改进的系统。适合大规模、高频场景，系统通过用户反馈自学习。

关键教训：引入领域专家但不给 ownership 是最大的浪费。无论选择哪种模式，专家必须对输出质量有真正的决策权。

8 维度 Skill 量化评估框架：你写的 Skill 及格了吗？
[dbaplus社群 / 百度Geek说]

Skill 是 Agent 能力的最小封装单元，但现在所有人都在写 Skill，质量参差不齐。百度团队提出了一套 8 维度评估框架：元数据质量、执行引导清晰度、领域知识密度、错误处理完备性、输入输出规范度、可复用性、文档完整性和安全性。

实践要点：description 写得太宽泛，Agent 根本不会触发；工作流缺少分支处理，遇到异常就崩溃；没有示例输入输出，Agent 难以正确使用。框架还设计了多模型交叉验证流程，通过不同模型对同一 Skill 打分取均值，降低评估偏差。

如果你正在为自己的团队或开源社区编写 Skill，建议先用这套框架自评——"能跑"和"好用"之间确实隔着十万八千里。
