01.NET 11 正式发布：C# 15 联合类型、Native AOT CLI 宿主、MAUI 默认 CoreCLR

微软发布了 .NET 11，这是一个标准期限支持（STS）版本，提供两年支持周期。语言层面最大的变化是 C# 15 引入联合类型（union types）与封闭层次结构（closed hierarchies），让类型系统能更精确地表达互斥的数据形态；工具链上新增 Native AOT CLI 宿主，并带来 Runtime Async 预览。

06Amazon SageMaker 实时端点支持 KV cache 感知路由

SageMaker AI 为实时端点新增 KV cache-aware routing：路由策略会读取模型容器上报的缓存状态，把每个请求发给已持有长缓存匹配、且当前不太繁忙的实例。它专为多轮对话、长共享 prompt、高负载这类 LLM 服务场景设计。

启用方式很小：给模型加一个环境变量让容器上报缓存内容，并在端点配置里把 RoutingStrategy 设为 KV_AWARE，客户端 API 完全不变。对已有 RAG / Agent 服务的团队，这是几乎零改造的延迟优化点。#inference#performance

Deep Dive · 01

给 Coding Agent 的代码上沙箱：external sandbox 模式

Simon Willison 与 Prime Radiant 合作，提出了 external sandbox（外部沙箱）模式：Agent 本身运行在你的主机（如 Mac）上，但它生成并执行的代码运行在一个专用沙箱内。这样可以在试用本地模型时不必担心模型出错或遭遇 prompt injection 而在机器上造成破坏性操作。该模式已开源出三个沙箱服务器实现用于演示。

三种沙箱实现

  • external-sandbox-v86：跑一个 Node.js 服务，再用 v86 在 WebAssembly 中运行 Alpine Linux——纯用户态虚拟化，跨平台、无需内核权限。
  • external-sandbox-container：基于容器（Container）隔离，贴近生产环境。
  • 第三个实现（QEMU / Apple Container 路线）：在 macOS 上借助系统级虚拟化运行完整隔离环境。

文中还给出了对 Claude Code、Codex 与 Pi 的接入 demo，说明这个模式不是绑定某一家 Agent，而是可复用的执行层抽象。

安全边界：出网白名单 + 凭据替换

三个沙箱服务器都带一个可选的 HTTP/HTTPS allow-list 代理，让你精确控制 Agent 代码能访问哪些主机；更进一步，它还提供凭据替换机制——Agent 可以在不持有真实密钥的情况下发起需要鉴权的 API 调用，真实凭证由沙箱侧注入。这两点合起来，直接对应 prompt injection 最常见的两类危害：数据外泄与密钥滥用。

为什么这种设计值得借鉴

核心思想是把"思考"与"执行"分成两个信任域：Agent（可能被注入、可能出错）只负责产出代码；执行发生在权限受限、默认断网、凭证隔离的沙箱里。相比"给 Agent 一台完整的开发机再祈祷它别乱来"，external sandbox 用很小的接入成本换来了可审计、可回滚的安全边界。对任何要在 CI 或本地跑自动化代码生成的团队，这都是一套可以直接照搬的架构范式。

Deep Dive · 02

LLM 成本与延迟工程三件套：规则优先、载荷瘦身、缓存路由

今天有三条来自 AWS 的实践恰好构成一条完整的成本-延迟优化链路，串起来看很有价值。

① 能用代码就别调模型

AWS 在《Cut generative AI costs: Code for rules, models for judgment》中给出的核心判断是：生成式系统里最大的成本杠杆，是"到底要不要调模型"本身。很多团队把输入校验、格式化、路由全部交给 LLM，单次看似便宜，规模化后会成为架构中最大的一笔开销。正确做法是按步骤做决策：

  • 确定性规则能完成的 → 用普通代码，省钱、降延迟、去除非确定性；
  • 需要判断但选项有限 → 用受约束的决策调用；
  • 确实需要生成/理解 → 选合适尺寸的 Bedrock 模型，而非默认上最大模型。

② 大 JSON 载荷会反复撑爆上下文

《Reducing token costs and latency in Amazon Bedrock AgentCore JSON workloads》指出一个隐蔽陷阱：Agent 每调用一次工具，就把整份载荷重新注入 LLM 上下文。当载荷是 20MB+ 的 JSON 且多轮对话时，token 与延迟会被成倍放大。文中用三种可组合策略为 Flightscape 的生产 Agent 处理 20MB+ JSON，把上下文压力压了下来——这类"工具调用 = 全量重放"的成本，是很多 Agent 上线后才暴露的。

③ 让请求落到"缓存热"的实例上

前面热榜提到的 KV cache-aware routing 是同一思路的服务侧延伸：多轮对话/长共享 prompt 的 KV 缓存若落到不同实例就被浪费，按缓存状态路由能把命中率最大化。启用只需一个环境变量加 RoutingStrategy=KV_AWARE。

落地上按顺序排查：先砍掉不必要的模型调用 → 再压缩工具载荷与上下文 → 最后用缓存路由榨干已有算力。前两步是纯代码改造，收益通常最大。
📎 来源: AWS (规则优先) · AWS (JSON 载荷优化) · AWS (KV 缓存路由)

工具推荐

rust-anything AI 编码助手 · 迁移工具

把一个跑得慢的老项目（TypeScript / Python / Go / Java 均可）逐步改写成 Rust，最大风险是"改完行为变了"。rust-anything 的思路很工程化：先给老程序喂一批输入并记录全部输出，形成黄金基准；AI 每改写一块，就把同一批输入重放到新代码，逐条对比输出。它本质上是给 AI 编码助手用的"改写说明书 + 验收工具"，把"行为不变"从口头承诺变成了可执行的回归校验。

📎 来源: Geek(@geekbb)
skwir Rust · 跨平台文件管理器

当人和 AI Agent 同时操作同一批文件时很容易互相踩。skwir 把每个文件操作都建模成可撤销、可审核的"计划"，人和 Agent 都从同一命令入口下发，从而避免并发冲突、并让每一步都能回溯。用 Rust + GUI 构建，适合把"Agent 参与文件操作"纳入可控流程的场景。

📎 来源: Geek(@geekbb)
开源加密邮件客户端 Rust + React + Tauri

一个用 Rust 写引擎、React 写界面、基于 Tauri 的跨平台桌面邮件客户端：邮件全部加密存储于本地（SQLite + SQLCipher），支持把 Gmail 与任意 IMAP 账号合并到一个收件箱，自带全文搜索、追踪器清除与钓鱼预警。免费开源，卖点是数据不经过任何第三方服务器——也是学习 Tauri 本地加密存储实践的好样板。

📎 来源: Geek(@geekbb)
Datasette Lite（重写版） Python · Pyodide · Service Worker

Simon Willison 用 Service Worker + Pyodide 彻底重写了 Datasette Lite——把完整的服务端 Python 应用搬进浏览器，如今"几乎与真正的服务端版本无法区分"。你可以在浏览器里浏览任意 SQLite / JSON / CSV / SQL 文件，从 PyPI 选择 Datasette 版本、从 GitHub 加载指定 commit/tag/branch、在 100+ 个 SQLite 版本间切换，还能从 PyPI 或 wheel URL 安装插件。它是理解 WASM 里跑 Python 应用的一座极佳参考实现。

📎 来源: Simon Willison's Weblog · Simon Willison
Vercel AI 组件库 (ui-sdk.dev) 设计 · Prompt 生成

Vercel 出了一套专门给 AI 用的设计组件库：点选技术栈即可生成对应的 UI Prompt，也可以直接让 Agent 访问该站点获取。社区经验是——想让 AI 生成的界面不像 "Slop"，最稳的配色是学 Vercel 的黑白灰风格，并避免让模型随意发挥或使用系统默认的丑组件。适合把"AI 生成前端的审美约束"标准化。

📎 来源: 向阳乔木(@vista8) · 配色实践
SqlPackage 170.6 预览版 .NET · 数据库部署

数据库部署应当可重复：SQL 项目构建出 .dacpac，SqlPackage 再与目标库比对生成变更。问题是即便"无变化"，重复发布也要做一次完整 schema 比对。新预览版带来两项能力：Deployment history（LogDeployment，把部署记录写进目标库）与 fast comparison（EnableFastComparison，借助兼容的部署历史跳过全量比对）。对反复发布同一模型的 CI 流水线，能明显省下时间。

📎 来源: Microsoft for Developers
Vercel Blob TTL 存储 · 自动过期

Vercel Blob 现在支持自动删除：写入时传 ttlDays（1–730 天，从上传日算起），到期自动删除。它适用于原本要自己清理的会话记录、导出文件、临时上传。覆盖 put()/copy()/putImage()/分片上传/预签名上传 URL，写入结果与 head() 都会返回 expiresAt；setTtl() 可批量修改已有 blob（一次最多 1000 个）。CLI 65.16.0+ 支持 --ttl-days 与 vercel blob set-ttl。

📎 来源: Vercel News

实践指南

AI 省时在缩水：瓶颈已从"写代码"转向"管理 AI"

Atlassian 的《2026 年开发者体验现状报告》给出一个反直觉的数据：过去一年，每周靠 AI 节省 10 小时以上的开发者比例从 68% 暴跌至 26%；而 AI 的渗透率已接近饱和——95% 的开发者、96% 的工程负责人称组织已在工程中积极使用 AI。该报告基于 1,155 名个人贡献者与 405 名工程负责人的调查，Atlassian 也明确提示这些是自报告的体验数据、相关性不等于因果。

局部收益仍在：87% 的开发者称 AI 让他们更快交付，80% 称在不延长工时的情况下完成更多工作。但只有 28% 觉得摩擦明显减少，50% 认为摩擦与之前持平——报告称之为"不同类型的摩擦"。一部分摩擦恰恰来自 AI 本身：49% 的开发者现在每周要花 4 小时以上管理 AI 工具。Atlassian AI 与协作部门 CTO Taroon Mandhana 的结论是："瓶颈已经转移到管理 AI 的工作上。"

别只统计"AI 帮我们省了多少"，要开始度量"管理 AI 本身花了多少"。把 prompt/工具/权限的维护成本当成真实的工程开销来优化，而不是默认它免费。
📎 来源: InfoQ

阿里 Qoder 的 AI Native 研发流程：SPEC 先行 + 团队级 Harness

阿里巴巴 Qoder 高级技术专家宋文龙（闻可）在 AICon 2026 的分享，讨论了 Coding Agent 从"个人工具"走向"团队级生产系统"必须跨过的坎。其路径可归纳为：SPEC 先行（先写清规格再让 Agent 动手）、团队级 Harness（统一的执行/约束/评测框架）、Agent team 与组织转型，从"许愿式编程"迁移到 on the loop 的研发范式。

一个值得注意的方法论前提来自他们自己的实践——用 Coding Agent 开发 Coding Agent，并分享了高德、闪购以及 Qoder 内部的一手案例。"Agent 越强，人的重要性不是降低，而是重要性的方式发生了改变。"

团队引入 Agent 时，先补 SPEC 和 Harness 这两块基础设施，再谈扩大使用范围；否则规模一上来，产出会因缺乏约束而变得不可控。
📎 来源: InfoQ

Vercel 两个待处理的流水线变更（含硬性截止日）

1）原生 lint / typecheck Deployment Checks 即将下线。这些检查原本在 Vercel 侧与部署构建并行运行；2026-11-30 之后将被移除，新检查已无法再添加。受影响项在项目的 Build & Deployment 设置里显示为 provider 为 Vercel 的 Lint / Typecheck 条目。迁移方式是把命令挪到 Vercel CI 或自有 CI 工作流；对于会阻断生产发布的检查，需确认新流程如何传递失败。

2）新增"仅对 PR 构建预览"预设。这是 Ignored Build Step 的新预设：没有打开 PR 的分支跳过预览构建，生产部署与有 PR 的分支照常构建；被跳过的预览会在消耗 Build CPU 分钟之前就被取消。在 GitHub/GitLab 项目上通过 Deployments > Configuration 启用。

把 11-30 这个日期加入日历：在此之前把 lint/typecheck 命令搬进 CI，并顺手用 PR-only 预设砍掉无谓的预览构建成本。
📎 来源: Vercel News (下线公告) · Vercel News (PR-only 预设)

Shopify 的 Remote Dev：让 AI Agent 在远端跑移动端开发

AI 开发工作流很容易把开发者机器的资源耗尽。Shopify 构建了 Remote Dev——一个远程移动开发环境，使 AI Agent 能独立地、并行地构建、测试与维护 iOS 和 Android 应用，而不占用本地机器。这是"把 Agent 的重活挪到远端"这一思路的典型落地。

如果你在本地跑移动端 Agent 流水线频繁遇到机器过热/资源争抢，考虑把构建与测试迁到远程开发环境，让本地只保留编辑与轻量交互。
📎 来源: InfoQ

把 LLM 排序塞进 P99 SLA：LinkedIn 的延迟工程清单

LinkedIn 的分享讲的是如何在严格的 P99 延迟 SLA 下生产化 LLM 排序。几条可直接复用的技巧：把 7B 模型蒸馏到 400M 参数；把职位上下文压缩成单 token embedding，换来约 10x 吞吐；以及消除各种"隐藏瓶颈"——自定义 flash attention mask、Python GIL 绕行、gc.freeze、非阻塞 CUDA 显存拷贝。

延迟优化往往不在模型本身，而在这些"看不见"的运行时与拷贝开销上。做 LLM 服务时，把 GIL、GC、显存拷贝、attention mask 逐项列入排查清单。
📎 来源: InfoQ
