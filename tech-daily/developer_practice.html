深度技术解读

两个今天值得手抄进团队 wiki 的话题：Agent 的上下文该怎么管，以及推理性能到底该从哪里抠。

上下文工程：为什么 800 行规则，反而不如一套可执行的体系

// context engineering · agent harness · prompt vs tooling

腾讯云开发者团队分享了一次很典型的翻车：他们把开发流程写成 Skill，让 AI 按清单执行。AI 总是漏步骤，于是团队不断加规则，不到一个月从 500 多行涨到 800 多行，开头还加了五条“违反任何一条即为失败”的铁律，第一条就是“逐步执行，禁止跳步”。结果规则越多，AI 反而越不听话。作者的判断是：上下文里塞进的东西越多，每条规则分到的注意力就越少，最重要的几条被埋掉了。

这不是孤例。Every 的评估负责人 Mike Taylor 把同类现象称为 Context Rot：同一个会话里，旧架构、失败方案、错误结论和纠正意见会持续累积，模型不会因为需求变了就自动降低旧信息的权重。他的做法很简单——每接到一项新任务就新开一条对话，因为旧要求已经不再适用。LangChain 的 Deep Agents 则把处理方式做进了 Harness：超过约 20,000 token 的工具结果和长消息会被 offload 到虚拟文件系统，不留在上下文里；当 token 使用量达到阈值（默认 85%）时触发摘要压缩，并用 keep cutoff 决定哪些内容保留原文。注意摘要触发前 token 可能已经超过阈值，所以不能把 85% 当成精确水位线。

把“流程”从提示词里拿出来

腾讯团队最终的解法是搭一套工程化体系，并把经验归纳为三根支柱：流程让 AI 可控，知识库让 AI 能积累，工具让 AI 能接触真实环境。翻译成工程语言就是：能由脚本、lint、hook、CI 强制执行的约束，不要写成自然语言请求模型遵守；需要长期积累的经验，放进可检索的知识库，而不是每轮全量塞进上下文；当前任务的真实状态（报错、文件、测试结果）通过工具读取，而不是靠人复制粘贴。

# 反模式：把流程和纪律都写进 system prompt
RULES = open("rules.md").read()   # 500 → 800 行，继续膨胀
prompt = RULES + task

# 推荐：流程由工具阻断，知识按需检索，上下文只装当前任务
run_step("lint")        # 失败即返回非零，模型无法跳过
run_step("test")        # 结果写入文件，而不是全部回灌上下文
state = load_task_state()  # 只加载当前步骤需要的最小状态
context = retrieve(state.query) + state.diff
做法放在哪里为什么
“必须先跑测试”CI / pre-commit hook / 脚本退出码机器执行，不消耗注意力，无法被跳过
“遵循团队的修复规范”仓库内的规范文档 + 可检索知识库按需加载，避免每轮全量注入
“记住上周的踩坑”带索引的决策记录 / memory 文件跨会话可复用，且不污染当前上下文
当前报错、文件内容工具读取的实时状态避免人工转述导致的信息失真

还有一个容易忽略的工程细节：长上下文模型并不等于可以放弃上下文管理。阶跃星辰今天开放权重的 Step 5 Preview 已经把窗口做到 100 万 token，总参数 600B、每 token 激活 27B，主打跨文件代码修改与多轮工具调用；但官方技术博客讨论的重点仍然是上下文管理、训练系统和运行时状态，而不是“窗口大所以随便塞”。窗口变大只是延后了问题，成本、延迟和注意力稀释依然存在。

实践结论：先问“这条规则能不能变成一次工具调用或一次失败退出”，不能的再考虑写进提示词；能写进知识库的，不要写进 system prompt。上下文预算要和 token 成本一样被监控。

推理提速的三条路线：国产 NPU 调参、稀疏注意力索引器、线性注意力

// inference optimization · ascend 910c · dosa · linear attention

今天有三篇来自不同层面的推理优化实践，放在一起看很有信息量：它们分别从运行时、算法和模型结构下手，但共同点是都先做 profile，再决定改哪里。

路线一：昇腾 910C 上把 Qwen3.5-35B-A3B 提速 40%

得物技术公开了国产算力适配的完整过程：先建立 Qwen3.5-35B-A3B 在昇腾 910C 上的性能基线，用 MindStudio 做 profile 定位瓶颈，再按“镜像与版本升级 → 参数与环境变量调优 → vllm-ascend 源码修改 → 算子层融合 → MTP 投机解码”五层推进，累计落地 20 余项有效优化，最终提速 40%。文中最有价值的部分不是成功项，而是十余项实测无效或负向的尝试清单。具体手段包括把集合通信下沉到 AI Vector（HCCL_OP_EXPANSION_MODE=AIV）、静态 kernel 预编译、HBM 分配器调优、用 jemalloc 替换 glibc malloc、MoE 权重预取、HCCL 通信参数与 CPU 绑定、cudagraph 捕获尺寸与 warmup 等。对做国产卡推理的团队，这是一份可以直接对照复用的工程记录。

路线二：小红书 DoSA 把首 token 延迟砍掉 37%–48%

稀疏注意力本来是为了减少主注意力计算，但负责筛选 token 的 Indexer 自己成了瓶颈。在约 1M 上下文的测试里，Indexer 占预填充 GPU 时间的 73.0%–90.8%。DoSA 的思路是利用分数的上下界，提前排除不可能进入 Top-K 的候选，再配合 GPU kernel 优化减少实际耗时；它保持原始评分函数下的精确 Top-K，不牺牲结果质量。在 GLM-5.2 上，约 97% 的查询—key 候选组合无需全头精算；在约 1M token 的测试中，Dots3-Note-preview、GLM-5.2、DeepSeek-V3.2 的首 token 延迟相对各自 SGLang 基线分别下降约 37%、46%、48%。

路线三：Laplace 3B 用线性注意力摆脱 KV cache 增长

i14 的 Laplace 3B 采用 Gated Linear Attention，推理时的循环状态固定为每序列 29.5 MB，不随上下文长度增长，直接绕开了 KV cache 限制并发和成本的问题。团队与 AWS 合作，用 TorchNeuron Native 的原生 PyTorch 支持把这一自定义架构搬到 Trainium2，同时保留 GLA 设计和 Muon 优化器。在一台 trn2.48xlarge 上，训练吞吐约 120,000 token/s，服务侧可在 1,280 并发下输出 11,544 token/s。这条路线说明，当模型结构允许时，“换一种注意力”可能比在 KV cache 上继续做工程优化更彻底。

路线先定位到的瓶颈关键手段结果
昇腾 910C推理栈适配与内核效率镜像/参数/算子/MTP 五层调优提速 40%，20+ 项优化落地
DoSAIndexer 占预填充 73%–91%分数上下界剪枝 + GPU kernelTTFT 降低 37%–48%，精确 Top-K
Laplace 3BKV cache 随上下文增长GLA 线性注意力 + Trainium2 原生 PyTorch29.5 MB/序列，1,280 并发下 11,544 tok/s
共同经验：不要先抄参数。先建立基线、用 profiler 找到真正占时间的那一段，再决定是改运行时、改算法还是改模型结构；同时把无效尝试记录下来，避免团队重复踩坑。

实践指南

今天就能在团队里落地的四件事，按优先级排列。

0124 小时内完成三类安全处置：PHP、Node.js、信任库

这不是“下个迭代再排”的级别。php2shell 已有在野利用，Node.js 的 Brotli 漏洞可致 RCE，CA 泄露则影响所有 TLS 校验。建议按下面顺序处理：

  • PHP：升级到 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12；RedHat 系使用 Remi 仓库的，临时切换到官方仓库完成升级。
  • Node.js：升级到 26.12.1 / 24.22.1 / 22.23.4，并确认部署环境没有继续使用 EOL 分支。
  • 信任库：更新 Python 的 certifi（≥ 2026.10.19）、uv（≥ 0.13.4）、pip（≥ 26.2.2）和系统 ca-certificates；所有自带 CA bundle 的容器镜像都要重建，而不是只重启。
  • 验证：升级后跑一遍 TLS 连接测试、依赖安装和镜像构建；检查是否有固定在旧版本的基础镜像或 SDK 缓存。

02容器构建报错“vite: not found”，先查第一个失败而不是最后一个

freeCodeCamp 记录了一个很典型的排查误区：应用在浏览器开发环境里正常，迁到 Azure Container Registry 构建后报 sh: 1: vite: not found。团队一开始怀疑 devDependencies 被裁剪或 NODE_ENV 设置错误，但真正的原因是更早的一次失败——npm ci 从只存在于浏览器开发环境的包源下载 tarball，失败后构建却继续走到了下一步，最后才以“找不到 vite”暴露出来。落地建议：

  • 构建脚本开启 set -euo pipefail，或在 CI 中检查每一步的退出码，避免上游失败被下游错误掩盖。
  • 检查 lockfile 中的 resolved URL 和 npm registry 配置，确保 CI 环境能访问同一来源；不要依赖开发环境里的本地代理。
  • 用与 CI 一致的干净环境复现，开启详细日志（如 npm ci --loglevel verbose），先定位第一条 error，再谈修复。

03给 Agent 立规矩：把流程交给工具，把知识交给检索，把上下文留给当前任务

腾讯云团队 800 行规则的教训值得直接写入团队规范。具体可以这样做：

  • 能由 lint、测试、pre-commit、CI 或脚本退出码强制执行的约束，不要写进提示词；模型无法“跳过”一个返回非零的步骤。
  • 项目规范、历史决策、踩坑记录放进可检索的知识库或带索引的 memory 文件，按需加载，不要每轮全量注入。
  • 长任务启用 offload 与摘要：大块工具结果落盘，只把摘要和当前 diff 留在上下文；监控 token 水位，而不是等模型开始“忘事”。
  • 需求切换时新开会话，避免旧方案和错误结论继续影响新任务；需要跨会话保留的偏好，显式写入 memory。

04模型可以换，外围别锁死：给 LLM 调用加一层薄适配

Stacklok 对 520 位技术负责人的调查显示，团队已经在频繁更换模型，真正担心的是模型之上那层“胶水”被锁死。工程上的应对不是造一个庞大的抽象框架，而是把变化点收敛：

  • 模型调用统一走内部适配层，隔离 SDK、鉴权、重试和流式协议差异；业务代码不直接依赖某家的专有对象。
  • 提示词、工具定义、评测集都版本化，换模型时用同一套回归用例对比，而不是凭感觉判断“更聪明了”。
  • 谨慎使用只有单一供应商支持的记忆、文件或 Agent 托管格式；至少保留可导出的原始数据。
  • 把模型选择和路由做成配置，而不是散落在代码里的硬编码；这也为“主模型 + 便宜模型”的分工留出空间。

05别再往计算节点里塞长期凭据：用工作负载证明换短期证书

Netflix 公开了其在 Amazon EMR 上为 Spark 作业做工作负载证明（workload attestation）的设计：把 AWS IAM 身份与控制面签发的签名声明结合，校验通过后才签发短期内部 X.509 证书，让托管计算任务访问内部服务时不需要直接注入长期凭据。对自建平台，可以借鉴的原则是：用平台身份 + 运行时声明做双向校验，凭据短 TTL、可轮换、可审计，应用侧不再持有静态密钥。
