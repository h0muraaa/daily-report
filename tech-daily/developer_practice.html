协议OpenAI 联合六家推出 Agent Plugins 开放标准，Cursor 已原生支持

由 OpenAI 与 AWS、Cursor、GitHub、VS Code、Vercel 共同制定并推动的 Agent Plugins 开放标准正式落地：把 Agent Skills 与 MCP 服务器配置打包成一种共享格式，做到"一次构建、多个兼容 Agent 客户端通用"。首批支持该格式的客户端包括 Codex、ChatGPT、Cursor、GitHub Copilot、Kiro 和 VS Code。

平台Cloudflare 发布 Kitesurf：为 AI Agent 打造的浏览器引擎，跑在 Workers V8 上

Cloudflare 终于自己造了浏览器，但不是给人用的——Kitesurf 是专门为 AI Agent 设计的 agent-first 浏览器，完全运行在 Cloudflare Workers 的 V8 隔离环境之上（已集成进 Browser Run 产品，beta 期免费）。官方表示相比 Chromium，CPU 和内存占用省 3 到 7 倍。

核心理由是资源开销错配：Agent 不需要标签页、主题、扩展、跨设备同步、60fps 渲染，只关心 token 数、上下文窗口、可扩展性和成本；威胁模型也不同，prompt injection 与工具安全才是头等大事。Chromium 的开销大到"给每个 Agent 配一个实例在经济上不可行"，Kitesurf 的目标就是"Agent 浏览民主化"，让大量 Agent 应用跑得起。

数据库Qdrant 1.19 引入 Turbo4 数据类型：向量坐标从 36bit 压到 4bit

Qdrant 1.18 曾引入 TurboQuant——内存里保留 4-bit 压缩副本、磁盘存原始 float32 用于 rescoring，效果好但要存两份向量。刚发布的 Qdrant 1.19 推出 Turbo4 新数据类型：只存 4-bit 表示、彻底去掉 float32 副本，单坐标存储从 36 bit 降到 4 bit，实现约 9 倍存储压缩，读写数据量更小、搜索吞吐也随之提升。

取舍很直白：没有原始向量就无法 rescore。存储效率优先选 Turbo4；对召回率要求苛刻、预算允许的场景，TurboQuant + 全精度存储仍是更稳妥的选择。对正在压向量库成本/规模的团队，这是一个值得在选型清单上打勾的新选项。

Agent Harness 工程：模型能力是概率的，真正"可控可用"的是外面那层骨架

今天多篇一线工程文章不约而同指向同一个主题：模型能力是概率的、会漂移的、偶尔会失控的，真正让 Agent 可用、可控、可演化的是模型外层那套工程化"骨架"（Harness）。大淘宝技术团队给淘宝主播 Agent 做的 Harness 实战，把这件事讲得最完整。

他们定义了 Harness 的六元组：执行循环、工具注册、上下文管理、状态存储、生命周期钩子、评估接口；并确立分层架构——框架层兜底安全与状态、业务层专注技能开发，用 MySQL / Hologres / GitLab 分别存会话、记忆与技能，做到"逻辑统一、物理分治"。细节上的工程取舍相当硬核：用分层压缩 + Reducer 模式优化上下文、用 Schema 强约束 + 幂等设计 + 五层纵深防御保障工具调用、用沙箱隔离执行风险、用 DAG 全局规划替代 ReAct 单步决策来提升长程任务的恢复性与效率；记忆体系则基于会话/事实/行为三层，配合记忆对账机制与信任度演化算法，让 Agent 逐步理解主播偏好。

腾讯技术工程的文章给出了一个具体转折点：在背负沉重历史债务的项目里，AI 之所以"胡言乱语"，根本原因是上下文知识不够——给项目搭建"AI 上下文工程"后，AI 才能高效定位问题、给出贴合项目的方案。奇舞周刊收录的"Violin"项目则从零演示了 Coding Agent 的架构：Agent Loop（问模型 ↔ 执行工具），加上模型适配层（统一 OpenAI/Anthropic 接口）、工具系统（内置 6 个基础工具）、产品层（会话管理、上下文压缩）与网络层——印证了现代 Coding Agent "并非全知全能，而是有状态、有工具、有边界的执行循环"这一本质。

  • 上下文是瓶颈：AI 与资深开发者的差距往往不在模型，而在"能否拿到正确上下文"。老项目重构成 AI 可维护项目，第一优先级是搭上下文工程。
  • 用约束换取可控：Schema 强约束、幂等设计、沙箱、DAG 规划，都是把"自由发挥的模型"装进"确定的流程"。
  • 分层架构：框架层管安全与状态、业务层管技能，物理分治（不同存储）与逻辑统一并存，才扛得住生产。
  • 别当甩手掌柜：腾讯云开发者分享的"省钱流 Agent 驾驭学"提醒——设好多智能体任务就出门，Agent 会在沙箱里为纠错和对齐 Schema 反复推理、一晚烧光积分；多智能体任务需要分阶段、设检查点、控制上下文预算。
实践要点：如果你的 Agent 在多步任务中"答非所问"，先别换模型。检查检索/上下文是否完整、工具协议是否有强约束、是否有 DAG 级规划和状态恢复——Harness 的投入产出比往往高于换一个更贵的模型。

Cursor 开源 MoK：把 token 调度、跨卡通信和专家计算塞进同一个 GPU 内核

Cursor 开源了 Mixture-of-Kittens（MoK）——一个反直觉的 MoE 性能优化内核。它没有去折腾更快的矩阵乘法，而是直接重写了一层 MoE 的执行方式：把 token 调度、跨 GPU 通信和专家计算放进同一个 GPU 内核。背景是英伟达 GB300 NVL72 已把 72 张 GPU 放进同一个 NVLink Domain、机架内带宽高达 130 TB/s——按说传数据已经够快，但大规模 MoE 训练里通信依然拖住专家计算。

问题出在 MoE 的数据流：Router 每一步都重新决定 token 去哪个专家，而专家分散在不同 GPU 上，token 要先跨卡送过去、算完再传回来；发送前要整理位置，到达后要等待数据完整。当 MXFP8 和 Blackwell Tensor Core 把专家计算压得越来越短，这些原本藏在计算后面的等待就越来越显眼。MoK 的核心不是把单次 Dispatch 传得更快，而是重新安排 token 怎么到达专家、什么时候开始计算，以及让通信与计算同时占用 GPU。

这篇文章的结论对工程师很有启发：在算力被 Blackwell 和 NVLink 堆到极致的今天，"硬件跑得再快，也救不了低效的软件编排"。MoK 的开源不只代表一个内核的胜利，更被看作"应用层定义算子"时代开始的信号——为了压榨最后 30% 的算力，模型框架层开始直接控制 GPU 内核行为。

值得思考的方向：当通信-计算重叠成为瓶颈，训练/推理框架的"算子编排"会取代"更快内核"成为主要优化杠杆。MoK 展示了把调度逻辑下沉进内核的具体路径。

实践指南

CI/CD给 GitHub Actions 上最小权限：按 workflow/job 级别收紧默认权限

freeCodeCamp 这篇教程讲透了 CI 安全里最常被忽视的一环：workflow 拥有的权限超出实际所需时，一个简单的 build job 就可能成为通往仓库改动、token 滥用或更大爆炸半径的路径。问题很难被发现，因为 workflow 依然通过，多余访问往往要等到 review、事故或发布失败才暴露。

做法分三步：识别 workflow 真正需要的权限 → 降到最小可行范围（workflow 与 job 级别）→ 验证收紧后流程依然工作。GitHub Actions 处在代码、secrets、发布与部署自动化的交汇点上，收紧权限范围能显著降低某个 step/action/依赖被攻破时的破坏力。对任何维护 CI 的团队，这是一份值得对照执行的清单。

[来源: freeCodeCamp — Harden GitHub Actions Permissions]

Agent给 Agent 设边界：质量来自约束，自主性靠验证循环赢得

Addy Osmani 这条被广泛传播的判断值得放进工程原则："质量存在于你给 Agent 设的约束里；自主性是靠通过验证循环赢来的。"他给出的框架是三档：high autonomy（高自主）、gated autonomy（有闸门的自主）与 human as a must（必须人参与）。

对应到实践：新功能 / 低风险任务放开高自主；涉及写文件、部署、发布的高风险操作设闸门（审批点）；某些环节强制人工。同时他强调当 Agent 写出第一稿成为常态，code quality、taste 与 judgment 反而更重要——质量门禁（如 SonarSource 类工具）要内建进流程，而不是依赖事后 review。

前端用 Baseline 重新审计依赖：中型应用里 60–90KB 的 JS 其实浏览器已经内置

Smashing Magazine 这篇文章点出一个大多数团队没意识到的账：中型 JS 应用里通常有 60KB–90KB（min+gzip）的依赖是浏览器现在原生支持的——日期/数字格式化、HTTP 请求、模态框、tooltip、深拷贝、数组分组，几年前这些确实是缺口，现在大多不是了。

依赖留存的真正原因不是懒惰，而是团队很少按 Baseline cadence（浏览器能力基线节奏）重新审计 package.json。对追求体积与首屏性能的团队，这是一条"零重构就能省几十 KB"的路径：把已内置进平台的能力从 bundle 里摘出去。

安全Anthropic 详解 Claude 安全隔离架构：Agent 的边界由运行环境决定

Anthropic 详细披露了 Claude 在 Web、开发者和桌面产品中的安全隔离架构。核心观点是：分类器、系统提示词与模型训练能影响模型行为，但无法提供绝对保证；真正决定 Agent 能访问什么、能向外发什么数据的，是运行环境本身施加的限制。风险被归纳为三类：用户误用、模型自身错误行为、以及通过文件/工具/网络内容发起的攻击。

具体落地很有参考价值：Claude.ai 的代码执行跑在隔离基础设施上的临时 gVisor 容器，完全无法访问本地文件系统；Claude Code 一开始用"逐项授权"，结果用户批准了约 93% 的权限请求，人工确认的价值大打折扣——于是转向操作系统级沙箱（macOS 用 Seatbelt、Linux 用沙箱机制），把安全边界从"靠用户点确认"变成"基础设施强制"。对做 Agent 平台的团队，这是"安全不能依赖概率性机制、要靠确定性边界"的权威案例。
