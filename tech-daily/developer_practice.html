04npm 正式上线分阶段发布：软件包开放安装前必须经维护者人工审批

npm供应链安全

# 深度技术解读 (Deep Dives)

AAgent Harness 的演进：模型在吸收底座，剩下的 harness 是给"人类注意力"用的

架构Agent Harness开源

Latent.Space 的《Evolution of the Agent Harness》给出了一个观察框架：大约 2025 年圣诞节前后，agent 突然"开始能用了"，原因是 模型与 harness 两条改进曲线在同一时刻交汇。由此推导出的下一步是——模型持续把 harness 的行为吸收进自己的权重，工程师持续删掉那些已被吸收的部分，最终留下的 harness 不是给模型用的，而是给"人类注意力"用的：让人类在环上确认、审查、干预。这个视角解释了当下社区的两个动作：elvis 在推特上说"Own your harness"，他尤其希望 Claude Code 的 harness 开源，现在已在 Pi 与 Hermes Agent 之上构建；并把为 eval、RL 环境、编码、营销等定制 harness 的现象称为 Harness Engineering，正整理最佳实践与工具指南。AI Engineer 频道上 Rémi Louf 的分享《Agent Frameworks Considered Harmful》则展示了"不用框架自己造运行时"的极端版本：重复推送变成带计数的队列、丢失的语音备忘变成因果链上的 append-only log、无法追溯的 prompt 变成 content-addressed store——system message、每个 skill 描述、每个工具定义、用户问题分别哈希存储，一个 prompt 是哈希列表而非渲染字符串，diff 两次运行就能看到哪个组件变了。另外 Orange AI 的实测提醒：同一模型在不同 harness 上的体验差异巨大——ox 在 opencode 里频繁中断，在 hermes 与 cola 里则稳定很多。结论：harness 正在成为比模型本身更值得投入的工程对象。

BLLM-as-a-Verifier：不换参数不微调，自验证采样让 DeepSeek V4 Flash 反超 Fable 5，成本不到 1/11

评测Test-time Scaling开源框架

一个已训练完成的大模型还能榨出多少性能？Jacky Kwok 联合斯坦福、UC Berkeley 与英伟达研究院的 LLM-as-a-Verifier 开源框架给出答案，并冲上 GitHub 热榜第二。做法是：每个任务采样 5 条候选轨迹，再用模型自己作为 Verifier 从候选里挑最优解（Best-of-5）。在极具挑战的 Terminal-Bench 2.1 上，DeepSeek V4 Flash 的系统成功率从 79% 涨到 88%，超越闭源前沿模型 Claude Fable 5。成本更具冲击力：DeepSeek 自验证单任务约 $0.11，Fable 5 约 $1.3，不到后者的十分之一；作者回应质疑称公布成本已包含生成 N 条候选轨迹与后续验证的全部开销，虽然 token 消耗更多，但开源模型极低的单价让"单任务总成本"依然碾压。对做 Agent 评测与推理优化的团队，这是把"验证"从昂贵的外部裁判变成廉价的自引用过程的一次重要示范。

# 实践指南 (Best Practices)

01Claude Code 多 Agent 省 Token 42%：用一份共享文件替代重复沟通

成本优化多 Agent

伦敦大学学院团队用 Claude Code 做了 1902 次实验专门算 token 账，结论反直觉：省 token 的办法不是更聪明的协调 Agent，也不是复杂调度框架，而是建一个文件。在多 Agent 参与、消息密集的任务里，把重复沟通换成共享文件后，输出 token 少了约 42%。原因在于：Agent 数量一多，点对点确认消息迅速铺开（改个接口要通知前端、后端、测试，三方各自回复）；而专门设置协调 Agent 并没有稳定提高成功率，它只是给团队多加了一层汇报。实操建议：在项目根目录建 AGENT_STATUS.md，把任务目标、验收标准、Agent 交接结果集中写入，搜集→分析→执行→验收各环节只读需要的部分。论文见 arXiv:2608.16801。

02LinkedIn 的多 Agent AI Code Review：把代码审查当成生产基础设施来建

Code Review多 Agent

在 LinkedIn 的规模下，只靠人工审查或把现成 AI reviewer 怼到 GitHub 前面都不可行。LinkedIn 工程师自建了一套 多 Agent AI Code Review 平台：它理解组织的编码上下文（而不是泛泛的通用规则），把代码审查当作"生产基础设施"来运营，并刻意压低幻觉和低信号反馈（避免 AI 在 PR 里刷一堆无关紧要的评论）。对准备在公司内铺 AI Code Review 的团队，这条"理解组织上下文 + 基础设施化 + 信号质量治理"的三件套是很好的架构参考。

03验证 Agent 代码的正确姿势：Simon Willison 的"不止 Code Review"与 Uncle Bob 的约束框架

工程实践质量保障

Simon Willison 在博客《More than just code review》里点出：用好编码 Agent 的核心技能是"自信地下达改动指令 + 自信地验证改动被正确应用"。验证并不总是逐行审查——逐行看代码从来不是验证软件改动的最高效方式。InfoQ 同日报道的 Uncle Bob 正是这套思路的极端践行者：他已放弃对 AI 代码的逐行人工评审，转而给 Agent 套上强约束体系——单元测试、Gherkin 验收测试、QA 流程、圈复杂度阈值、模块大小限制、依赖结构分析、变异测试与覆盖率要求，靠确定性检查建立"很高信心"。但他也因此遭 UML 之父 Grady Booch 反对："信任但要核验"，Booch 认为指标无法发现安全漏洞、侵蚀可维护性的死代码或性能逻辑缺失。两条立场放在一起的启发是：约束与指标是下限保障，但领域判断仍需人类兜底。

05后端实战两则：MySQL 执行计划救分页 SQL + Milvus 3.0 让 regex 安全扫过百万行

数据库性能排查

生产环境一页分页 SQL 从 200ms 飙到 3.5s，同事说"加个索引"，一线 DBA 说"先看执行计划"——结果发现索引加了反而更慢、或只用了部分字段、或明明有索引 MySQL 却视而不见。这类"加索引救不了"的问题，根因都在没读懂 EXPLAIN。执行计划不是 DBA 专利，它是每个写 SQL 之人的"X 光机"，能透视数据库到底怎么执行你的查询。另一边，Milvus 3.0 新增 =~ 与 !~ 正则过滤器，并把"百万行安全扫描"当成工程问题处理：先用 RE2 校验（线性时间匹配，非法 pattern 提前拒绝），再把简单模式重写为等值/前缀/后缀检查，对 sealed segment 复用编译后的 pattern、先查必选字面量，最后在可并行处用 NGRAM 剪枝。两条经验都指向同一件事：别靠猜，去读执行计划与执行路径。
