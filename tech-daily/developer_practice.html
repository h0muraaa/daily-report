Vercel 内部实践：给 Agent 一个文件系统，它就能完成长任务

📎 来源: AI Engineer Summit - Nico Albanese, Vercel

Vercel 内部 Agent 工程的一个关键发现是：给 Agent 提供文件系统不仅仅是增加存储能力，而是从根本上改变了 Agent 的行为模式。当 Agent 拥有了持久化的文件系统后，它开始能够执行需要持续跟进的长任务、保持工作轨迹、进行自我纠错，甚至在多次会话之间保持工作连续性。

这一发现对 Agent 架构设计有重要启示：传统的"一问一答"式 Agent 架构受限于无状态设计，而给 Agent 一个"工作空间"（workspace）的概念——包含文件系统、执行环境和状态持久化——是实现真正自主 Agent 的关键前提。开发者在设计 Agent 系统时，应该优先考虑为 Agent 提供可持久化的工作环境，而不是仅仅优化 prompt 或增加工具数量。

💡 构建可落地的 AI Agent：从免费CodeCamp教程看工程实践

基于 freeCodeCamp - How to Build Optimal AI Agents 的核心要点

  • Agent ≠ 简单的 LLM 调用链：真正能完成任务的 Agent 需要具备规划、记忆、工具使用和错误恢复四个核心能力，缺少任一维度都会导致"玩具级"Agent
  • Harness（马具）比模型更重要：同样的模型，放进聊天框只是"给建议"，放进 Claude Code / Codex / OpenCode 就能读文件、改代码、跑测试——差异在于外围工程系统
  • 从具体业务场景出发：技术上搭建 Agent 工作流并不难，难的是对业务和技术都有深入理解，设计出 AI Native 的工作流而非"原流程+AI点缀"
  • 评估体系先行：没有评估标准的 Agent 就是不可控的黑盒，上线前必须建立任务完成率、错误率、成本等多维度指标

🛡️ AI 编码时代的安全防护：攻击者正在利用 Agent 信任的文件

基于 Google Cloud 安全博客 的分析

  • 攻击面扩大了：AI Agent 不仅信任源代码，还信任配置文件、环境变量、文档和注释——攻击者可以通过污染这些非代码文件来操纵 Agent 行为
  • CI/CD 成为关键防线：在 Agent 自动提交代码的场景下，传统的 Code Review 流程可能不足以发现问题，需要在流水线中增加静态分析、依赖扫描和行为检测
  • 最小权限原则：给 Agent 的权限应该遵循最小权限原则，特别是写入权限和 secrets 访问权限，避免单点被攻破后的连锁影响
  • 建议措施：启用 npm provenance 验证、锁定依赖版本、对 CI secrets 进行最小化配置、定期审计 Agent 的权限范围
