架构HubSpot 200 亿向量语义搜索：VaaS 平台从 PoC 到内部服务的演化

深度DoorDash 的 Ask DoorDash：Agent 落地的四层架构与"业务逻辑不放 Prompt"原则

DoorDash 自 2026 年 6 月起连续发布三篇工程博客，详解其新上线的 AI 购物助手 Ask DoorDash 的运行时架构、记忆系统与评测框架。核心设计原则：不是从零搭一套系统，而是在现有 DoorDash 平台之上加一层 Agent。整个架构分为四层——业务逻辑只住在其中一层，不写进 Prompt。用户用一句自然语言描述想吃什么、想买什么，Agent 就能搜餐厅、规划三餐、建好购物车。关键抓手是工具调用和记忆系统，而非模型本身的"聪明"。

为什么重要：这是企业级 Agent 落地最具参考价值的范式之一：①把 Agent 当成"薄薄一层"，复用现有微服务和数据；②业务规则留在代码里、Prompt 只做意图理解和调度，大幅降低 Prompt 漂移风险；③评测框架要跟上，否则无法上线。任何在做 Agent 产品的团队都值得读原文三篇。

深度Simon Willison 披露 Claude web_fetch 数据外泄漏洞与"致命三合一"攻击

Simon Willison 详述了 Ayush Paul 发现的一个 Claude 数据外泄漏洞。背景：常规 Claude 聊天天然处于"致命三合一"（lethal trifecta）风险中——它同时拥有你的私有数据（历史记忆）和访问在线内容的工具（既可读取恶意指令也可通过 URL 外泄数据）。Anthropic 的防御是 web_fetch 只能访问用户明确输入或 web_search 返回的 URL。Paul 的绕过思路：让 LLM 把"最近的回答"拼接到 https://evil.example.com/log?answers=... 这样的 URL 后面——而 web_search 返回的 URL 是可以被攻击者污染控制的。文章详细分析了攻击链条和 Anthropic 的缓解方案。

为什么重要：任何在 Agent 中接入 web_fetch / 浏览器 / RAG 的开发者都该读这篇。核心教训：①"只允许 LLM 访问用户直接输入的 URL"这种约束在搜索场景下会被间接攻破；②URL 白名单必须与"URL 内容拼接"分开审计；③Agent 的 memory + 网络访问组合是天然的高危面，需要在架构层面做隔离。

数据库Postgres for Production Agents：JSONB + HNSW + 向量量化的组合拳

Gwen Shapira 在 InfoQ 分享：团队如何用 PostgreSQL 支撑企业级 Agent 的关键应用。要点：①利用 Postgres 的多模态能力——JSONB 处理结构化上下文，HNSW 向量索引处理语义检索，两者联合为 LLM 提供确定性 + 语义双重上下文；②使用向量量化可将查询速度提升 4 倍；③Agentic memory 的管理策略（写入、过期、命名空间隔离）需要单独设计，不能简单等同于 chat history。

落地建议：如果你的 Agent 需要长期记忆 + 结构化数据 + 语义检索，先评估 Postgres 而非引入独立的向量库。单系统意味着一份运维、一份备份、一份权限模型。量化带来的 4x 提速对成本敏感场景非常关键。

数据库用 AlloyDB AI 解决 PostgreSQL 中日韩多语言全文搜索

Google Cloud 发布新能力：AlloyDB 新增 RUM 索引支持，并通过 Gemini 多语言能力解决 PostgreSQL 在中文、日文、韩文等表意语言上的分词难题。传统基于空格的 tokenization 在 CJK 语言下失败，Gemini 可以做智能分词和停用词去除。文章详述了如何避免"对海量数据做行级 API 调用"的性能陷阱，把分词能力下沉到索引层。

安全 exposed Cloud Functions：LFI/RFI + 命令注入的攻击面与加固清单

Google Mandiant 威胁情报团队发布报告：大量"因业务需要而公开"的 serverless 函数缺少身份验证，成为攻击入口。由于 serverless 通常运行自定义代码 + 第三方包，常见应用层攻击包括本地/远程文件包含（LFI/RFI）和命令注入。一旦被利用，攻击者可完全控制底层容器实例，作为跳板进一步攻陷整个云环境。文章给出了真实客户案例和详细的加固清单。

落地建议：立即审计你账号下所有"公开访问"的 Cloud Functions / Lambda / Azure Functions。即使业务需要公开，也必须：①输入严格校验（拒绝文件路径、shell 元字符）；②最小权限服务账号；③单独的 VPC + egress 限制；④开启云厂商的入侵检测。Mandiant 的加固清单可直接抄作业。

📎 [来源: Google Cloud Blog / Mandiant]

工程为什么 AI 应用在生产环境会挂：Google 总结的"5% 生存率"原因

Google Cloud 博客：得益于 Agentic engineering 和 LLM，从空白 IDE 到本地可用原型已经从"几个季度"缩短到"几小时"。但在企业环境里，Vibe Coding 会撞上一堵"看不见的墙"——只有 5% 的 AI 原型能走到生产环境，其余 95% 死在"验证深渊"。主要杀手：企业网络限制、级联错误、领导层对运维波动的恐惧。

落地建议：文章给出的路径是把"原型到生产"拆解为可观测性、评估、灰度、回滚四个独立工程问题，而不是期望 Agent 一次性搞定。对每个 LLM 调用增加 tracing，对关键路径做离线评测，对发布走 canary。这些都不新鲜，但在 AI 应用场景被普遍忽视。

评测Stripe Benchmark：AI Agent 能搭集成但难过验证关

Stripe 发布基准测试套件，评估 AI Agent 在真实 Stripe 集成任务上的表现，覆盖后端、前端、浏览器 Checkout 流程。研究聚焦端到端软件工程能力，特别是执行、测试、验证三个环节在生产级约束下的差距。结论：Agent 能搭建集成框架，但在"验证自己的产出是否真的工作"这一环普遍表现不佳。

落地建议：这印证了 DoorDash、HubSpot 等团队的实战经验——Agent 的最大瓶颈不是"写代码"而是"验证代码"。团队引入 Agent 时，最该投入的是自动化验证基础设施（集成测试、e2e、沙盒环境），让 Agent 能自己跑验证、看结果、再迭代。

方法论FactoryAI 的激进选择：从 ban useEffect 到 ban SDKs

FactoryAI 团队继"禁止 useEffect"之后，又宣布"禁止官方 SDKs"——已经把所有第三方服务的官方 SDK 全部迁移走，转而让 AI Agent 直接为具体使用的 API endpoint 生成调用代码。核心理由：许多官方 SDK 质量差、更新滞后、代码臃肿；当 Agent 能力足够强时，"自己造轮子"反而更靠谱。Viking 评论：这很可能是未来趋势——前端框架和基础架构层面的"内容"影响力正在下降，可能回归"html + js 一把梭"的极简形态。

落地建议：这个判断有争议但值得思考：①SDK 的价值在"封装好的最佳实践"和"类型安全"，放弃意味着要自己维护；②但在 Agent 时代，"读懂 REST API 文档并生成调用代码"的成本已经极低，确实可以重新评估引入 SDK 的 ROI；③更稳妥的做法是"核心服务仍用 SDK，长尾服务让 Agent 直调 API"。
