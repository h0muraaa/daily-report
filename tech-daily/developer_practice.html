llama.cpp 发布 v1.0.0 —— 本地推理的里程碑

维护者 Georgi Gerganov 正式发布 llama.cpp v1.0.0，Hugging Face 同步发布了配套博客。这个以纯 C/C++ 实现、几乎零依赖著称的推理库，长期是本地跑大模型、量化部署、边缘设备落地的首选底座。

冲到 1.0 意味着 API 与工程成熟度进入"可长期依赖"的阶段。对一线开发者而言，做端侧推理、私有化部署、或给工具链嵌一个轻量推理后端时，可以更放心地把它当作稳定依赖，而不是需要频繁跟 breaking change 的实验性项目。

开源 / 推理 📎 来源：Thomas Wolf(@Thom_Wolf)
02

Cloudflare Kitesurf 开源（Apache 2.0）—— 跑在 Workers 上的 Agent 浏览器

Kitesurf 是 Cloudflare 为 AI Agent 打造的无状态浏览器，完全运行在 Workers 之上：它自己解析 HTML、应用 CSS、执行页面 JavaScript 并渲染截图，不需要浏览器容器。现在已按 Apache 2.0 协议在 GitHub 开源，可本地运行、修改，并部署到自己的 Cloudflare 账户。

关键点在于它支持 Chrome DevTools Protocol（CDP）。这意味着你在 Agent 里常用的 Playwright/Puppeteer 风格自动化可以对接，但底层是边缘无服务器运行，冷启动和运维成本显著不同。做网页 Agent、抓取或自动化测试的团队值得评估。

开源 / Agent 📎 来源：The Cloudflare Blog

DeepSeek 开放"全家桶"应用 API —— 一个接口复刻完整 App

DeepSeek 把 App 里的联网搜索、深度思考搜索、文件输入、阅读链接、语音交互（含 OCR/ASR/TTS）等能力整合进原有 API，开启对应参数后，工具调用与上下文拼接由服务端自动完成。开发者不必再自己对接一堆外部工具和调用衔接。

目前 deepseek-flash（V4.1-Flash）已在 Messages、Responses、Chat Completions 三类接口下支持上述能力，语音与底层能力也可独立或组合调用。官方称可 1:1 复刻出完整的 DeepSeek App 对话体验，做 RAG、文档问答、语音助手的团队可直接省掉大量脏活。

Google Antigravity 推出 Dynamic Workflows —— 让 Agent 写脚本编排自己

在 Antigravity 里输入 /run-workflow，Agent 会写一个 Python 脚本来编排并行与串行的子 Agent，并通过结构化 handoff 传递结果，从而用确定性的控制流取代 prompt 漂移。脚本在运行前可人工审阅，并保存下来重复执行同一流程。

Google 工程师 Varun Mohan 补充：动态工作流内部使用极多，核心价值是"给 Agent 写程序来编排 Hydrogen 和 Carbon 的能力"，甚至无需显式触发，模型可像 swarm 一样自行决定。这是把"编排逻辑"从自然语言 prompt 下沉到可审查代码的一个明确信号。

Agent / 编排 📎 来源：Google Antigravity(@antigravity) · Varun Mohan

深度技术解读

Deep Dive 01 / Agent 工程

Harness 比模型更关键：Agent 工程化的三个硬信号

今天有两条独立消息指向同一个结论：在 Agent 里，围绕模型的那层"脚手架"（harness）决定成败，往往比换模型更有效。

第一是 Browser Use 的对照实验。他们用同一个模型（gpt 6.1 terra medium）、同一批 200 个超难长程任务、同一个裁判，只更换浏览器 harness：codex 内置的 6 个浏览器工具得分 62.4，而 Browser Use 1.0 agent 达到 77.5。进一步，他们发现缓存命中率只有 78%，修好 harness 后升到 96%，结果每任务成本从 $0.67 降到 $0.45（省 33%）、耗时从 5.0 分钟降到 4.6 分钟，分数不变。一行 uv add "browser-use==1.0.4" 即可复现。

第二是"验证"问题。Stack Overflow 直接发问：编码 Agent 能写设计文档、搭前端、端到端实现项目，但它能可信地验证自己的代码真的能跑吗？言下之意是不能——自评会产生盲区。与之呼应，Google 开源了 AQuA（Ambient Quality Agent），专门分析线上 Agent 会话、验证重复出现的失败模式、并对部署源码快照做根因分析；在一组 32 次会话回放中，把"选座流程被绕过"从 15 次降到 2 次，"饮食偏好遗漏"从 7 次降到 0 次。

第三是组织层面的证据。JetBrains 对 9 个真实案例的研究发现：某组织 AI 采用率高达 95%，开发者速度却没有提升；另一家却把 PR 吞吐翻了三倍、缺陷积压下降 54%。差别不在"用没用 Agent"，而在是否有配套的流程、验证与度量。

落地要点：把"模型选择"降级为可替换变量，把投入放到 harness 上——缓存策略、工具封装、结构化 handoff、以及一套独立于生成方的验证/评测回路。Agent 自评不可信，评测必须由外部裁判或真实回归来兜底。

Deep Dive 02 / 性能优化

性能优化的另一半：不改算法，只消除"核心操作周围的冗余"

MongoDB 团队给了一个反直觉但很实用的经验：最大的性能收益，常常来自干掉核心操作周围那些不必要的工作，而不是把核心本身做得更快。他们在优化 Atlas Search 与 Vector Search 的文档查找链路时，没有改动底层搜索算法，只是去掉了冗余的查询计划与执行开销，就让 $search / $vectorSearch 查询最高快了 5 倍。

理解这条链路是关键：mongot（基于 Apache Lucene）先执行搜索、找出并排序最相关文档，然后 mongod 再用这些文档的 _id 回表 join 出完整 BSON 文档。冗余就藏在这两步的衔接里——重复的查询规划、重复的执行开销。删掉它们，端到端延迟直接受益。

同样的模式在今天的其它更新里反复出现：Vercel Sandbox 不是把镜像加载做得更快，而是把镜像数据缓存到离沙箱更近的区域，避免回源，启动时间降约 75%；Vercel 把构建缓存上限提到 5 GB，本质是让下一次构建少做重复安装。三者都是"减少无谓工作"而非"加速必要工作"。

方法论：做性能剖析时先画清"必要工作"与"周边开销"的边界。优先问三个问题——这段查询计划是否重复计算？这份数据是否在跨区回源？这次构建是否在重复安装？往往比换更快的硬件或重写算法更省力、见效更快。

实践指南

▸ 给 Agent 建一条"不自评"的验证回路

编码 Agent 能端到端实现功能，但让它给自己的产出打分会产生系统性盲区。把验证从生成流程里拆出来：

  • 用独立的外部裁判或真实回归 / 集成测试作为最终判据，而非模型自评。
  • 对线上 Agent 做会话回放，像 AQuA 那样把失败模式量化（本次案例：选座绕过 15→2、饮食遗漏 7→0）。
  • 把评测脚本固定下来、可重复执行，分数变化才是可信的改进信号。
📎 Stack Overflow · InfoQ

▸ 先调 Harness，再考虑换模型

同一模型只改 harness 就能大幅提升得分与成本效率。上线前按这份清单过一遍：

  • 测缓存命中率：Browser Use 从 78% 修到 96%，直接省 33% 成本、快 ~8%。
  • 统一评测口径：固定模型、任务集与裁判，只变 harness，否则无法归因。
  • 把编排逻辑从 prompt 下沉到可审查脚本（如 Antigravity 的 /run-workflow），用确定性控制流替代 prompt 漂移。
📎 Browser Use · Google Antigravity

▸ 性能剖析：先找冗余，再谈加速

MongoDB 不改算法靠"删除周边开销"拿到 5 倍提升。做性能优化时优先排查三类冗余：

  • 重复的查询规划 / 执行：搜索与回表衔接处是否被计算了两遍？
  • 跨区回源：缓存是否离计算更近？Vercel 靠区域缓存把启动降 ~75%。
  • 重复安装 / 重复构建：缓存上限是否限制了复用（Vercel 提到 5 GB）？
📎 MongoDB Blog · Vercel News

▸ 用 Playwright 做跨区域合规巡检（可复用的测试模式）

Dropbox 用一个基于 Playwright 的 Cookie 审计器，在 200+ 个 Web 界面验证同意行为：每页跑 US 访客、EU 访客、Global Privacy Control 三个用例，规则留在代码之外，配套工具自动发现活跃 URL，周报区分疑似违规与误报。这套"规则外置 + 多身份用例 + 定期报告"的模式，可直接迁移到任何需要跨环境校验的自动化巡检。

📎 InfoQ

▸ 给 AI 工具做"零埋点"成本归因

AI 工具规模上来后，"每个用户真实花多少钱、哪个团队在烧钱"是绕不开的问题。Amazon Bedrock 提供内置、零埋点的成本归因：每次推理调用都能追溯到发起它的 IAM principal，身份与组织标签一起流入 CUR 2.0 与 Cost Explorer，数据不出 AWS 安全边界。自建 AI 平台可借鉴这个"身份即成本维度"的设计。

📎 Artificial Intelligence (AWS)

▸ 流处理选型：多数团队先用 Spark，再按场景引 Flink

Databricks 的选型建议很务实：对大多数团队，Apache Spark 是更合适的选择，它覆盖批处理 ETL、SQL 分析等主流场景；真正的实时流处理需求再考虑 Apache Flink。别为了"架构先进"提前引入两套引擎，运维和一致性成本往往被低估。
