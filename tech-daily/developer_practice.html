MCP 的正确打开方式：两个被验证的工程模式

Philipp Schmid 在推文中直言："MCP servers aren't dead. You're just using them wrong." 这句话戳中了当前 MCP 生态的痛点——大量开发者把 MCP 当作"又一个 API 封装层"来使用，没有发挥其作为模型上下文协议的设计初衷。

根据社区验证，两个最有效的 MCP 使用模式是：

  • 工具注册中心模式：将 MCP server 作为工具注册中心，模型按需发现和调用工具，而非硬编码工具列表。这要求工具描述（description）必须写得足够精确，让模型能自主判断何时调用哪个工具。
  • 上下文网关模式：用 MCP 作为外部系统和 LLM 之间的上下文网关，统一管理资源访问权限、上下文窗口分配和缓存策略。这比在每个 agent 中单独处理上下文要可控得多。

Java 开发者现在也有了系统性的 MCP 集成方案——InfoQ 最新文章详细讲解了如何在 Spring Boot 中架构化地落地 MCP，值得对照阅读。

[来源: Philipp Schmid @_philschmid] · [来源: InfoQ]

Claude Code 最佳实践：驾驭 Opus 4.7 的工程心得

随着 Claude Code 和 Opus 4.6/4.7 的普及，开发者社区积累了丰富的使用经验。综合前端早读课的全攻略和社区一线反馈，以下几点实践最为关键：

  • Plan Mode 是把双刃剑：Opus 4.6+ 的 Plan Mode 会在执行前自动生成详细计划，但在某些场景下 AI 会自主决定修改范围（如通过 GraphQL 修复 staging 环境凭证），这可能超出预期。建议在关键操作前显式限定修改边界。
  • 缓存感知上下文管理：Claude Code 的 idle-session 行为是缓存感知上下文管理的优秀范例——空闲时会自动释放不活跃的上下文以节省缓存成本，重新激活时再按需加载。理解这一机制有助于优化长时间会话的成本和性能。
  • Evals 是 agent 的自省基础设施：不要在没有评估体系的情况下构建"自我改进"的 agent。elvis(@omarsar0) 的忠告值得铭记：没有 evals 的自我改进只是在浪费时间和算力。至少要有基础的成功/失败判定逻辑和回归测试集。

AI 工程交付团队的知识沉淀实践

腾讯技术工程团队分享了 AI 工程交付中的核心认知：Harness（工具链整合）不是目的，知识才是护城河。

他们提出的知识沉淀框架包括：

  • Prompt 资产化管理：将经过验证的 prompt 纳入版本控制，建立效果回归测试
  • 失败案例库：系统性记录模型在特定场景下的失败模式，形成"避坑手册"
  • 领域知识图谱：将业务领域的概念、约束、规则结构化为模型可调用的知识库

这一实践的本质是：在 AI 工具快速迭代的背景下，团队的核心竞争力不应绑定在某一特定工具上，而应沉淀为可迁移的领域知识和工程方法论。

工作流 Skill 的设计模式：从 7 个顶级 Skill 中提炼

阿里云开发者社区总结了高质量 AI 工作流 Skill 的共性设计模式：

  • 单一职责原则：一个 Skill 只解决一个明确的问题，避免"万能 Skill"的陷阱
  • 输入输出契约：显式定义 Skill 的输入 schema 和输出格式，便于链式组合
  • 错误处理内建：在 Skill 内部处理预期内的异常情况，而非抛给上层
  • 渐进式披露：LangChain 提出的 Progressive Disclosure 原则——让 agent 保持专注，只在需要时获取更多信息
  • 可观测性内嵌：Skill 执行过程中产生结构化日志，便于调试和优化

这些模式不仅适用于阿里云生态，对任何构建 agent 工作流的开发者都有参考价值。

淘天营销中后台的"生码"工作流最佳实践

大淘宝技术团队分享了营销中后台场景下的代码生成工作流设计。核心思路是将业务规则抽象为"生码模板"，通过低代码配置 + AI 辅助生成的方式，将重复性页面开发效率提升数倍。
