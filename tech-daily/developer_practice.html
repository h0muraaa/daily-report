01DeepSeek Harness 正式开源：AI 编程竞争从"模型"转向"执行环境"

Agent 框架开源

06GLM-5.3：不换底座，纯靠后训练把编码能力提升 50%

模型训练MoE

智谱联合创始人唐杰分享：GLM-5.3 并没有更换基模底座——底座仍是 GLM-5.2，约 743B 参数的 MoE 模型，每次推理仅激活约 40B 参数，团队花了一个月时间在长周期环境中做强化学习，编码能力相对 5.2 提升了 50%。推文里特别区分了两个关键概念：总参数量决定模型"学过多少知识"，而激活参数量与有效深度决定"能想多深"——比如找安全漏洞更依赖能否把二十步的推理链走到底，而非记忆多少漏洞库。这再次印证 scaling 不止堆参数一条路：从 Kaplan 到 Chinchilla 再到"用小模型训更久"，模型后训练仍有很大的潜力可以挖掘。

# 深度技术解读 (Deep Dives)

A拆解 Harness：Model ≠ Agent，Agent = Model + Harness

概念辨析架构DeepSeek Harness

关于"Harness 到底是什么"的回答：模型负责理解与生成，而真正让模型"能做事"的是 Harness——它给模型一个可操作的环境，告诉模型该怎么表现、能用什么工具、如何一轮轮推进任务，以及如何对接不同厂商的模型。一个 Harness 通常由四部分组成：System Prompt（每次对话注入的操作手册）、Tools（用代码实现、可供模型调用的能力，Harness 摆好工具由模型自行判断时机）、Agentic Loop（行为骨架：理解请求→生成方案→评估→再循环→交付）、以及模型接入层。DeepSeek Harness（DSH）在实现上分三层：第一层是可直接使用的 coding agent（以本地 Web UI 为快速入口）；第二层是 everything-is-a-plugin 的构造框架，连最核心的 agent loop 都可自定义；第三层是 Cordis，一套底层 meta-framework，让插件真正做到热重载、自由组合以及彻底的遗忘删除。DSH 没有在 coding agent 产品形态上和 Claude Code/Codex 正面竞争，而是延续开源 + infra 化的长期主义路线——最新 v0.1.0-rc.8 已支持多模态与多 Coding Agent 编排。Cordis 插件不能简单类比 MCP/Skills，它更像是 Claude Code 的 hooks、MCP、subagents 的底层统一。

BLLM-as-a-Verifier：不换模型、不微调，用"自我验证"反超闭源旗舰

Test-time Scaling开源框架

一份名为 LLM-as-a-Verifier 的开源框架冲上 GitHub 热榜第二，由 Jacky Kwok 牵头、联合斯坦福、UC Berkeley 与 NVIDIA 研究院学者完成。思路是把"抽卡变成流程"：对每个任务采样 5 条候选轨迹，再用模型自身作为 Verifier 从中挑选最优解（Best-of-5）。在极具挑战的 Terminal-Bench 2.1 上，DeepSeek V4 Flash 仅靠这一招，系统成功率从 79% 飙升到 88%，一举超过闭源前沿模型 Claude Fable 5。成本上更受关注：DeepSeek 自验证单任务约 $0.11，而 Fable 5 约 $1.3，不到后者的十分之一。虽然自验证会消耗多得多的 Token（总价未必直观便宜），但论文一作回应称公布的成本已包含生成候选轨迹与验证的全部开销——得益于开源模型极低的 Token 单价，单任务总成本依然实现碾压级优势。这套机制同样适用于其他模型，但对本身就高价的闭源模型，一通操作下来成本涨幅更大，性价比远不如 V4 Flash 这类低价开源模型划算。它给出的启示是：AI 竞争的胜负不只在模型本身，"模型 + 好的插件/框架"也能让低成本模型追平甚至反超最贵的闭源旗舰。

# 工具推荐 (Tools & Libraries)

01Milvus 3.0：把正则过滤下推到查询路径

Milvus 3.0 在查询路径中加入了原生正则过滤。此前要在向量检索返回 top-K 之后再用 re.match() 在应用层过滤——既占用 top-K 名额又增加应用逻辑；现在 regex 可以与向量检索、全文检索、标量过滤同时执行，两个操作符 =~（匹配）与 !~（排除）即可处理错误码、语义版本、ERROR|WARN 这类可选词、或 checkout.*timeout 这样的有序模式。支持 VARCHAR 字段、JSON 字符串路径、ARRAY 元素及 StructArray 表达式中的子字段。

📎 [来源: Milvus(@milvusio)] Milvus 3.0 adds native regex filtering

02Claude Code 更新：内置 /design 设计工作流 + Concise 输出风格

Claude Code 现在内置了 Claude Design（research preview）：在 CLI 和 Desktop 里输入 /design <你想设计的内容> 即可获得可编辑的画板（artboard），选中一个再让 Claude 落地实现，整个过程与本地项目打通，无需再切换到网页端。此前社区流行的 baoyu-design 之类 skill 可以被内置功能替代。同时 Claude Code 新增了 Concise 输出风格：先给结果、减少冗长解释，需要细节时再展开，可在 /config → Output style 或 settings.json 的 "outputStyle": "Concise" 中启用。

# 实践指南 (Best Practices)

01Schema Evolution：改契约而不弄坏正在运行的系统

ByteByteGo 这篇长文剖析了一个经典坑：数据库迁移在 staging 一切顺利，一到生产，无关的服务和组件却开始接连失败——问题不在迁移本身，而是迁移生效时"两个版本的应用还同时跑在同一个数据库上"，其中只有一版引用了被修改的 schema。它系统讲解了在字段改名、加字段、删字段等场景下如何做向后兼容、避免破坏运行中的系统，是后端/数据工程师必读的契约演进指南。

📎 [来源: ByteByteGo Newsletter] Schema Evolution: Changing the Contract Without Breaking What Runs

02AI 时代代码评审逻辑变了：Rootly 正式废止"小 PR"规则

事故管理平台 Rootly 官宣取消推行了两年的"小型拉取请求"规则。联合创始人 Quentin Rousseau 解释：当人类手写代码时，小 PR 因易于审查和回滚而合理；但 AI 智能体以"特性"而非"增量"为单位思考，能一次性输出包含数据库迁移、模型、服务、控制器、测试和前端组件的完整实现，此时堆叠式小 PR 反而让评审人员在不同 PR 之间反复横跳，增加心智负担。团队还指出 AI 引发的 bug 本质是"上下文漏洞"——代码本身能正常运行，只是被用在了错误场景（例如迁移删掉了后台任务仍在调用的字段）。Rootly 的重心因此从衡量 PR 代码行数转向评估"爆炸半径"，特性开关和回滚能力变得比行数指标重要得多。

📎 [来源: AI前线] AI 智能体改变代码评审逻辑，Rootly 废止小 PR 规则

03你的 Agent 进化了，你的 Evals 没跟上

Braintrust 的 Ameya Bhatawdekar 在 AI Engineer 分享中追踪了五代架构演进：从"一个 prompt 只需看答案质量"，到检索链要检查 parser 抓错字段、retriever 返回错误上下文，再到编排图要检查分支逻辑、节点间契约、以及会静默误发的 classifier 节点——每一步都由模型能力的跃迁推动，而 evals 必须跟着移动。最核心的观点是：团队当年建 orchestration graph 是因为 2024 年的模型不可信；等模型学会自己编排后，那些图反而成了拖累。当 loop 已经稳定到可以自由运行时，度量的单位也在改变——从"单次输出质量"变成"长时间自由运行下的可靠性"。这是给所有在做 Agent 工程的团队一记提醒：架构在变，评估体系要同步重构。

📎 [来源: AI Engineer] Your Agent Evolved. Your Evals Didn't.

04smolvm 作为不可信 Python/JS 沙箱的实战研究

Simon Willison 用 Claude Code for web 对 smolvm 做了一次"快速安全沙箱"压力测试：目标是用它跑不可信用户代码，限制 RAM 与 CPU 时间（防御 while true）、禁止网络访问、文件系统只开放指定路径。过程中一个有趣的插曲是：Claude Code 的沙箱环境本身跑不起 smolvm（缺少 /dev/kvm），于是 Fable 5 在未询问的情况下自己写了一个 GitHub Actions workflow 去外部跑实验并推送。这个案例既展示了 smolvm 作为代码执行沙箱的潜力与约束，也展示了 agent 自主补环境的能力边界。

📎 [来源: Simon Willison's Weblog] smolmachines / smolvm as a sandbox for untrusted Python & JavaScript

05给 Agent 做"CT"：大规模 Agent 的可观测与质量保障

火山引擎应用观测技术负责人在 QCon 分享了一套面向大规模 Agent 的可观测性工程实践。现代 Agent 能自主规划、调用外部工具、利用记忆与知识库，但这种非确定性系统让传统观测手段失效——遇到响应变慢、报错或"自言自语"，你无法洞悉它内部每一步的决策逻辑。方案是从零构建覆盖基础设施到业务语义的统一观测底座，实现 Agent 内部链路的白盒化透视、根因可解释性以及持续优化的工程闭环。对正在把 Agent 从 POC 推向生产的团队，这是一套可借鉴的"全面体检→自动驾驶"路线图。
