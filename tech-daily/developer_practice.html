Google 发布 Gemini 3.6 Flash、3.5 Flash-Lite 与 3.5 Flash Cyber

Google 一天内连发三款 Gemini 新模型，核心目标非常明确：让生产级 AI Agent 跑得更快、更省、更可控。Gemini 3.6 Flash 是这次的主角，输出 Token 消耗比 3.5 Flash 降低约 17%，部分编程场景甚至减少 65%，定价为输入 $1.50/百万 Token、输出 $7.50/百万 Token。它在 DeepSWE 代码任务上的得分从 37% 提升到 49%，Computer Use（OSWorld）成功率达到 83%，并且更少出现乱改代码和死循环的问题。

3.5 Flash-Lite 则是高吞吐场景的选择，输出速度接近 350 Token/秒，价格压到输入 $0.30/百万、输出 $2.50/百万，适合批量文档处理、并行子 Agent 等重复性工作。专门面向网络安全的 3.5 Flash Cyber 将通过 Google 的 CodeMender 平台提供，定位是自动发现与修补关键漏洞。三款模型已上线 Gemini API、Google AI Studio、Android Studio 和 GitHub Copilot。

来源：[Google DeepMind News] · [The Keyword] · [@GoogleDeepMind]

Claude Code 团队自曝：系统提示词砍掉 80% 后反而更强

Anthropic 的 Claude Code 负责人 Cat Wu 与工程师 Thariq Shihipar 在 AI Engineer World's Fair 上与 Simon Willison 对谈时透露，Claude Code 的系统提示词近期减少了 80%，而效果反而更好。他们总结了三条反直觉的提示工程经验。

第一，删掉 few-shot 示例。Thariq 直言，过去 Opus 4 时代需要大量示例，但现在模型比人类给的示例更有创造力，删除示例反而有效。第二，少用“不要做 X”的硬禁令。禁令对 Claude 是“很强的冲动”，一旦与后续用户指令冲突，模型会陷入困惑，方向应转向更多上下文、更少硬约束。第三，每条指令都要“100% 成立”。Cat 建议逐句审视提示词，问自己是否存在例外场景，把措辞软化到在任何善意误读下都成立为止。

这场对话还提到，Claude Tag（Slack 集成）已经承担了 Claude Code 团队 65% 的产品工程 PR，说明 Agent 工作流正在从实验走向真实研发主路径。

来源：[Simon Willison's Weblog] · [@simonw] · [@meng shao]

JetBrains Context：给 coding agent 的代码库智能层

同一天，JetBrains 还发布了 RubyMine 2026.2（Agentic Debugging、原生 GitHub Copilot、symbol-based code insight）和 PyCharm 2026.2（Rust 插件开发 Python 扩展、debugpy 默认调试器、uv/Poetry/Hatch workspace、Pyrefly 类型引擎、编辑器 minimap）。IDE 厂商的竞争焦点已经从“谁补全更好”转向“谁能帮 Agent 真正理解复杂代码库”。

GitHub Copilot Canvases：把对话做成交互式画布

GitHub 官方发文介绍如何用 Copilot Canvases 构建交互式体验。思路很直接：有些任务（比如整理 backlog、可视化复杂信息、聚合多源数据）不适合纯对话流，画布能让我们直接拖拽、筛选、编辑信息，而不是在一长串 prompt/response 里来回找。

对开发者来说，这意味着 Agent 的输出形态正在从“文本流”扩展到“可交互界面”。如果你在做内部工具或 Agent 产品，值得思考：哪些场景给 user 一个 canvas 会比给一段回答更高效。

Google Tunix：消除 TPU 空闲的 Agentic RL 训练框架

Google 开源了 Tunix，一个面向多轮、工具调用型 LLM Agent 的后训练库。核心痛点很真实：训练 Agent 时，模型经常要等网络 I/O 或环境步骤，导致 TPU 大量空闲。Tunix 用 高并发异步 rollout + 解耦的生产者-消费者流水线 把 TPU 喂满，并提供即插即用的抽象和宏观级 profiling，方便集成自定义开源环境。

如果你在做 Agent 后训练或 RLHF，这类基础设施会是接下来“卷完模型卷工程”的关键战场。

来源：[Google Developers Blog]

AWS：用 Amazon Nova 做自蒸馏推理，降低 SFT 数据成本

AWS 机器学习博客分享了如何用 Amazon Nova 2 做“自蒸馏推理”来生成 SFT 所需的 chain-of-thought（CoT）推理轨迹。传统上，给训练数据写高质量 CoT 又贵又慢，很多团队直接跳过推理步骤，但这样会损失模型在代码、数学等硬任务上的表现。

自蒸馏的思路是让模型自己生成、筛选并精炼 reasoning traces，再用这些轨迹做监督微调。对想在私有数据上复刻 o1 风格推理能力的团队，这是一条更可控、成本更低的路径。

🔍 深度技术解读

React Server Components 的 Flight 协议安全边界

React Server Components（RSC）不会把 HTML 或 JSON 发到浏览器，而是使用一种叫 Flight 的自定义流式协议。Smashing Magazine 的这篇深度文章指出，大多数 React 开发者从未打开 Network 面板看过 Flight payload——它是一系列 JSON 片段、$ 前缀引用和模块指针的混合体，由 React 运行时静默重组为客户端组件树。

文章的核心警示是：Flight 是一种带类型系统和引用解析的序列化协议，存在反序列化 sink。如果服务端渲染的输入能被攻击者污染，客户端可能在重组过程中执行恶意模块或构造危险对象。作者建议团队把 Flight payload 当作不可信输入来审计，而不是因为“框架处理了”就默认信任。

实践建议：审查 RSC 服务端渲染的数据来源、限制可序列化的模块范围、在边界处做输入校验，并在安全 review 中把 Flight 协议纳入攻击面分析。

来源：[Smashing Magazine]

从“代码生成”到“验证与Harness工程”：Martin Fowler 的软件 Retreat 观察

Martin Fowler 汇总了第二届 Future of Software Development Retreat 的五条核心发现，其中最扎眼的一条是：代码生成不再是瓶颈，验证才是。当 AI 能快速产出大量代码后，人类工程师的时间会越来越多地花在“这堆代码对不对、安不安全、能不能合入”上。

围绕这个变化，Fowler 提出了几个值得关注的趋势：

  • Harness engineering 正在成为一个独立的工程学科——给 Agent 设计工具、约束、评估和回退机制。
  • 学徒危机：初级岗位被 Agent 替代后，高级工程师从哪里来？
  • 高管与工程师的预期鸿沟：C-suite 看到的生产力承诺与一线工程师遇到的验证成本之间存在真实差距。
  • 遗留系统现代化 是最清晰、最可辩护的近期价值池。

Weaviate 向量搜索新增 per-query profiling

Weaviate 推出 per-query profiling，只需一个 opt-in 标志，就能把一次向量搜索的耗时拆成 filter evaluation、HNSW traversal、向量 rescoring、BM25 打分、对象 hydration 等阶段。协调节点会汇总所有参与 shard 和 node 的 profile，一次请求拿到集群级视图。

这对调试 RAG 延迟非常有用：以前只知道“慢”，现在能定位到是磁盘 IO、HNSW 参数还是结果限制导致的慢。

🚀 实践指南

12-Factor Companies：AI Native 团队的组织原则

Chroma 创始人 Jeffrey Huber 提出的 12-Factor Companies 框架，把 AI 时代公司的核心假设从“人类执行力是瓶颈”切换为“人类品味与判断力是瓶颈”。关键原则包括：

  • 拥有上下文，租用智能：不要把核心数据交给“上下文吸血鬼”型供应商；同时保持模型供应商的可替换性。
  • 自建工具，外购底座：承载业务上下文的内部工具应该自建；数据库、训练基础设施等通用底座应该买。
  • 先招 Agent，再招人：任何新任务先尝试教会 Agent，教不会再招聘。
  • 写下来的组织惯例：AI 时代逼迫企业把隐性知识文档化，让组织对人和 Agent 都可读。

这套框架适合正在从“人写代码”转向“人指挥 Agent 写代码”的团队做组织设计参考。

来源：[@meng shao]

Gumroad 的 AI 客服实验：报 bug 奖 $25

Sahil Lavingia 分享 Gumroad 的 AI 客服实践：用户报告 bug 并被修复后，自动获得 $25 账户积分，整个流程 100% 自治，每月预算上限 $5,000。他同时提到，2026 年 6 月是 Gumroad 首次 AI token 支出与人力工资支出持平的月份。

对开发者来说，这个案例展示了 AI 自动化的边界设计：给 Agent 明确的预算上限、把奖励机制与真实价值（修复 bug）挂钩、保留人类在异常场景的介入能力。不是“替代客服”，而是“把客服的反馈循环自动化”。

来源：[@shl]

Andrej Karpathy：先掌握模型，再堆 Agent

Andrej Karpathy 在一段被广泛转发的讨论中提醒开发者：现在 AI 领域最大的错误，是人们还没真正掌握底层模型，就开始强迫 Agent 工作。他回顾 2016 年 OpenAI 的类似错误，代价是五年时间。

他的三条建议很直接：第一，停止强迫 Agent 包办一切，先理解它背后的模型；第二，做 Demo 容易，做产品可能需要十年，自动驾驶已经证明跳过基础最终一切都会崩溃；第三，Agent 不是产品，底层模型才是，先把基础打牢，Agent 会自然涌现。

这条建议对当前“所有团队都在上 Agent”的风气是一剂冷却剂：在把 agentic 工作流铺到生产之前，先确保你对模型能力、失败模式和评估方式有扎实理解。
