🔍 深度技术解读

话题一：AI 编码的"边界"在哪里？——从 db9 项目看技术栈锁定的瓦解

PingCAP CTO 黄东旭用 AI 完成了 100 万+ 行代码的数据库项目 db9，最终结论是："我没看到边界"。这不仅是能力惊叹，更揭示了一个结构性变化——技术栈选型这个曾经"以年为单位"的重决策，正在被 AI 压缩到以天为单位。

对比数据极具冲击力：

  • Meta Java → Kotlin：4.5 年
  • 微软 TypeScript 编译器 → Go：14 个月
  • Bun Zig → Rust：6 天

开发者实践视角： 当技术栈迁移成本趋近于零，"选型"的核心考量应从"长期维护成本"转向"当前 AI 的理解和生成质量"。建议团队建立技术栈实验机制：用 AI 快速原型验证替代冗长的技术评审，关注 Agent 对特定框架的代码生成准确率而非社区热度。

话题二：Agent 可观测性——Vercel 的实战方案与通用启示

Guillermo Rauch 指出 Agent 调试的三大难点：模型非确定性、分布式计算链、外部 API 故障。Vercel 为 eve.dev 内置的观测方案值得借鉴：统一追踪模型调用、工具执行、运行时错误和 token 消耗。

可落地的实践建议：

  • 日志结构化： 参考 Codex 用量分析工具，将本地 JSONL 日志索引到 SQLite，通过 MCP 工具暴露查询接口
  • 分层监控： 业务层（任务完成率）、模型层（token 消耗/延迟）、基础设施层（API 错误率）
  • 确定性注入： 对关键路径设置 temperature=0，非创造性任务强制结构化输出

📋 实践指南

Prompt 工程：四层语音架构替代单条语气指令

Isadora Martin-Dye 的生产经验：品牌语音不是"写一次"的指令，而是分层架构。将语音拆解为四个层级，可让 prompt 在 21 轮对话后仍保持稳定：

层级 1: Immutable Identity（不可变身份）— 品牌核心人格 层级 2: Situational Mode（情境模式）— 当前场景适配 层级 3: Example-Anchored Voice（示例锚定）— 具体语料参照 层级 4: Deterministic Post-Generation Veto（确定性后验过滤）— 规则硬约束

落地建议： 在构建 AI 产品的系统 prompt 时，将"语气要求"从单一 system prompt 抽离为配置化的层级结构，便于 A/B 测试和版本管理。

LLM 默认技术栈的微妙变化

Simon Willison 观察到一个趋势：当前 LLM 不再像去年那样"默认一切用 React"。这意味着prompt 中的技术约束可以减少，但也需要更精确的上下文引导。

实践建议： 在 AI 编程工作流中，尝试移除"不要用 React"这类否定式指令，改为正面指定技术栈（如"使用原生 Web Components"或"使用 Vue 3 + Composition API"），观察生成质量变化。
