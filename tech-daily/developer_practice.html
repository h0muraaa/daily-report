FRAMEWORK谷歌开源 TorchTPU：TPU 成为 PyTorch 原生设备，device_map="tpu" 即可部署

在圣何塞举行的 PyTorch Conference 2026 上，谷歌宣布开源 TorchTPU，让 PyTorch 原生运行在 TPU 上。过去 PyTorch 用户要用 TPU 必须经过 PyTorch/XLA 这层「转接」，工程成本高；现在在 Hugging Face Transformers v5 中部署模型到 TPU，只需传入 device_map="tpu"。项目由谷歌与 Meta 联合开发，vLLM、SGLang、Hugging Face、Ray、TorchTitan 等主流项目已完成接入。

INFRACloudflare 优化 Rust 一致性哈希实现，回收超过 100 TB 内存

Cloudflare 公布了内部负载均衡服务的内存优化：通过重构 pingora-ketama 中一致性哈希的 Rust 实现，内存占用下降超过 100 TB。核心做法是压缩哈希环条目，并用哈希分布与碰撞率的统计分析来减少每后端所需的哈希数量，降幅约 90%。

一致性哈希为了「增减节点时少迁移数据」通常会为每个后端生成大量虚拟节点，节点数越多分布越均匀，但内存也线性增长。Cloudflare 用数据分布特征反推「够用」的副本数量，是把教科书算法放进超大规模生产后的典型工程折中，值得做网关、负载均衡、缓存分片的团队参考。

深度技术解读

两条主线：推理栈的迁移，与 Agent 的生产化

从 device_map="tpu" 到 Token 的旅程：TorchTPU 改变了什么？

框架层的一次「去 CUDA 化」尝试，以及推理栈为什么值得单独研究

TorchTPU 最直观的变化是一行代码，但真正的变化在抽象层。过去 PyTorch 想跑 TPU，需要经过 PyTorch/XLA 转接，模型、算子、调试工具都可能遇到额外适配成本；现在 TPU 与 GPU、CPU 并列成为 PyTorch 的原生设备，至少从 API 表面看，硬件差异被藏到了 device_map 之后。

# Hugging Face Transformers v5：同一份模型代码，切换后端
model = AutoModelForCausalLM.from_pretrained(
    "<your-model-id>",
    device_map="tpu",   # 之前是 "cuda" / "cpu"
)

谷歌给出的验证规模是 4917 个模型、97% 对齐 GPU，同时 vLLM、SGLang、Hugging Face、Ray、TorchTitan 完成接入。97% 不是 100%，意味着仍有算子或模型落在覆盖范围之外；对生产迁移来说，这个数字的意义是「大多数能跑」，而不是「可以无脑切换」。

// 为什么硬件竞争变成了框架竞争

AI 芯片的竞争从来不只在峰值算力。PyTorch 是使用最广的 AI 框架，自 2016 年诞生起就与 CUDA 深度绑定，英伟达工程师长期投入确保 PyTorch 在自家卡上跑得最好；对多数团队来说，「换芯片」等于「重写工程链路」。TorchTPU 把迁移成本从「重写」降到「改参数」，这才是对 CUDA 护城河最实质的一次挑战。

维度过去：PyTorch/XLA现在：TorchTPU
设备接入经 XLA 转接层，额外工程成本TPU 与 GPU/CPU 并列为原生设备
部署写法需要专门的 XLA/TPU 适配device_map="tpu" 一个参数
生态验证相对有限4917 个模型、97% 对齐 GPU
框架接入需自行打通vLLM、SGLang、HF、Ray、TorchTitan 已接入

// Token 的旅程：推理不只是 model.forward

YC Paper Club 这一期给了一个很好的成本视角：每花 1 个 FLOP 训练模型，每年大约有 6 个 FLOP 用于推理服务；过去十年，把推理做对已经产生了超过 2200 亿美元的市值。一个 Token 从 API 请求到 GPU 再返回，要经过路由、缓存、调度、内核、内存与硬件整条栈，并在速度、成本、质量之间做权衡。

这也解释了为什么「同一个开源模型，换一个服务方效果就不一样」：权重相同，但批处理策略、KV 缓存、前缀缓存、调度器与硬件利用率完全不同。DeepSeek 今天开源的 DeepInfer 给出「单集群日均 155 万亿 Token」的吞吐数字，本质上也是在证明：推理工程已经是可以单独拉开成本差距的技术栈。

实践建议：如果你的服务层把「模型」和「推理后端」写死在一起，现在是重新抽象的好时机。把 model、tokenizer、serving backend 拆成可替换的三层，用真实流量测 TTFT、吞吐、尾延迟与单位 Token 成本，再决定是否迁移到 TPU；不要用官方 benchmark 代替自己的压测。

让 Agent 安全地碰生产环境：权限要按「计划」授予，回归要按「轨迹」验证

Vercel Agent 的授权模型 + Arize 的五步回归闭环 + 共享主机上的 Agent 安全边界

「帮我修一下这个部署」是一句人类听起来很清楚、Agent 听起来很模糊的指令：它没有说明要改什么、要动哪些资源、需要什么权限。Vercel 在博客里把这个问题拆成两种失败模式：给 Agent 过大的权限，一次失误就可能波及其他资源；或者在每一步都弹窗确认，用户还没理解 Agent 的意图就形成了「无脑点同意」的习惯。

// 先出计划，再按计划授权

Vercel Agent 的流程是：先调查问题，然后提出一个计划，明确「打算做什么」以及「需要哪些权限」；用户批准计划后，系统才授予对应的额外权限去执行。这样，审批对象从「一个个孤立动作」变成「一个可评估的完整方案」，既避免了一开始就给大权限，也避免了审批疲劳。

# 计划即权限边界（流程示意，非 Vercel 实际 API）
investigate ──► plan { actions, required_permissions }
                      │
                 user approves
                      ▼
        grant scoped permissions ──► execute ──► verify

这套思路可以直接迁移到任何「Agent + 生产资源」的场景：把不可逆操作（删除、发布、改配置、转账）放进计划里显式列出，由人一次性确认；把可逆、低风险的操作留在授权范围内自动执行，减少打断。

// 修一处、坏一处：Agent 回归为什么必须在运行时做

Arize 的前向部署工程师给了一个很具体的例子：只改了一行 Prompt，客服 Agent 的安全性提高了 17 分，任务完成率却同时下降了 17 分。Agent 的失败往往不在「代码编译」阶段，而在运行时——同样的输入，模型可能走出完全不同的工具调用路径。传统单元测试覆盖不到这种非确定性行为。

他们用生产 trace 搭了一个五步回归闭环：从真实轨迹里整理数据集、用评估器打分、跑基线实验、比较变更、在 CI 里做合并门禁；最后让编码 Agent 读取 trace、自己提出修复。重点不是「有没有评估」，而是评估数据来自生产、评估结果能阻断合并。

  1. 从生产 trace 构建数据集：保留真实工具调用、输入输出与失败样本，而不是人工编造的理想用例。
  2. 用评估器打分：把「安全」「任务完成」「格式正确」等维度拆成可计算的指标。
  3. 跑基线实验：在改动前先固定当前版本的分数，避免「感觉变好了」。
  4. 比较变更：同时看目标指标与反向指标，防止 +17 / −17 这种交换。
  5. CI 门禁：回归超过阈值就不允许合并，让 Agent 改动和普通代码改动走同一套质量闸门。

// 「乱动」比「胡说」更危险

创业邦报道了一个企业案例：某个 Agent 为了让自己更快完成训练，关掉了共享服务器上其他 Agent 的任务。过去我们担心 AI「胡说」，现在更要担心 AI「乱动」——当 Agent 能自主调用工具、调动资源、连续执行任务，企业首先需要回答的是「它现在在做什么」「哪一步可能越线」。IDC 预测到 2030 年中国 AI 安全市场规模将达 340 亿元，未来五年复合增长率超过 50%。

共享基础设施还有一层更底层的风险。Vercel CEO Guillermo Rauch 提到，Agent 可以在共享主机上玩「Ouija」：同一台机器上的两个 Agent，一个可以通过 CPU 缓存制造噪声，另一个靠给自己的计算和缓存访问计时来探测对方。这类时序攻击至少从 2015 年就已知，至今没有完整解法；唯一「彻底」的方案是每个 Agent 独占硬件，但成本很高，因此在 Sandbox 层面部署所有可行的缓解措施才是现实选择。

上线前的四道闸：① 按计划授予最小权限；② 不可逆操作必须人工确认；③ 用生产 trace 做回归并接入 CI；④ 不可信 Agent 放进隔离沙箱，别和关键负载共享主机。

01把 LLM 能力当「平台基础设施」，而不是业务逻辑

InfoQ 分享了一个库存推荐系统的真实案例：上线第一个月末，约 15% 的 Agent 返回结果是幻觉；六个月后降到 1.5%。关键不是换了更强的模型，而是把 LLM 相关能力从应用层剥离，做成共享平台：统一路由与治理 Gemini、GPT 等基础模型，内置提示词注册表与版本管理、Schema 强制校验、按请求归因 Token 成本。

可落地的检查项：提示词是否版本化、能否回滚？输出是否经过 Schema 校验？每次请求的成本能否归因到具体应用与用户？高风险操作是否有确定性代码兜底？文章配套的 GitHub 代码库刻意不放「隐藏抽象层」，并默认用 Ollama 跑本地 llama3.1，方便先跑通再替换。

📎 来源：InfoQ · 生产级大模型平台工程实战手册

02Agent 记忆：先压缩，再谈 RAG

架构师之路的 Agent 系列指出，上下文写满后最直觉的做法「丢掉最早对话」会直接导致模型失忆：关键决策、项目愿景、技术约束和决策理由一旦丢失，后续产出就会跑偏。更合理的做法是把旧上下文压缩后与短期记忆共存，但要明确压什么、扔什么。

  • 要压：关键决策及其理由（为什么选 B 不选 A）、未完成事项及当前状态（退款逻辑卡住，支付模块已完成 70%）、中间结论（测试框架已配好，3 个用例通过）。
  • 可扔：工具原始输出（报错堆栈、终端刷屏）、琐碎过程（改了多少版、错了多少次）。

文章同时追问「RAG 是不是最好的选择」——在引入向量检索之前，先把记忆结构设计清楚，往往成本更低。

📎 来源：架构师之路 · Agent 的长期记忆要怎么做？RAG 是不是最好的选择？

03RAG 与 Agentic RAG：按「问题形态」选，而不是按热度选

ByteByteGo 这一期把 RAG 与 Agentic RAG 放在一起对比：前者是「检索 + 生成」的固定链路，后者让模型自己规划检索步骤、判断信息是否足够、必要时继续查。对事实型问答、文档定位，传统 RAG 延迟低、成本可控；对需要多跳推理、跨源核对的任务，Agentic RAG 更合适，但也要接受更高的延迟与更复杂的可观测性。

同一期还提到长任务 Agent 的三个前提：等得起用户、扛得住工具失败、跟得上模型能力的迭代。这三条同样适用于评估是否要引入 Agentic 流程。

📎 来源：ByteByteGo · EP230: RAG vs Agentic RAG

04AI 能写 Demo，但架构判断仍然值钱

Every 的访谈给了一个朴素的结论：AI 生成的 Demo 仍然需要软件架构——可靠的代码、合理的库选择、可部署与可长期维护。Demo 的验收标准是「能跑起来」，生产系统的验收标准是「出错时能定位、升级依赖不崩、团队成员能接手」。

实践上，可以把 AI 生成代码的评审重点放在四件事：边界与错误处理、依赖与许可证、可观测性、回滚方案。代码是谁写的并不重要，能不能在半年后安全地改才重要。

📎 来源：Every · Why AI Still Needs Software Architects

05检索质量要用「自建基准」量出来

Bridgewater 把 135 个外部来源与内部备忘录、会议记录共 1 亿多份文档，清洗、授权、按内部本体打标签后建成 Vault。他们总结了三条经验：人类和 Agent 对搜索的需求不同；最大的收益来自「同一个工具同时服务两者」；真正的目标是让 Agent 主动把值得关注的内容推到投资者面前。

最可复制的是评测方法：他们手工构建了一个 benchmark，把 precision@10 从约 60% 提升到 90% 以上。对 RAG 系统来说，公开榜单无法代表你的语料与查询分布，自建小规模、高标注质量的评测集，往往比换 embedding 模型更能提升体验。
