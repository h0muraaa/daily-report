01. DeepSeek V4.1 Flash 静默换模型：能力更强，工程治理却翻车

9 月 9 日 DeepSeek 把发往 V4 Pro 的请求全部路由到 V4.1 Flash，按 Flash 价格计费。公告与邮件都有，但距离切换只有一天左右，没有新旧模型并行的迁移期，不少开发者是刷到那条 70 万浏览的推文才知道自己调用的模型要换掉。争议点不在能力：V4.1 Flash 是 763B-P8B-D16B 的新因果编码器-解码器结构，原生多模态，性能、费用、速度、总用时全面超过 V4 Pro，在 OpenRouter 上 24 小时就跑了 1T tokens。真正的问题是「被固定版本号依赖的线上行为」被单方面改变——评测基线、成本模型、prompt 调优都可能一夜失效。

技术报告 5.3.4 节「Performance across agent scaffolds」值得一读：同一模型在 Claude Code（69.8）、Codex、OpenCode、mini-SWE（74.2 最高）、DSH 等不同 Harness 上分数差异明显，且 DSH 内部工具越多的 PTC 模式（67.6）反而低于 Minimal（72.6）——工具更丰富的 Harness 不一定更好，简单接口有时更稳。对开发者的直接教训：把模型版本 pin 死，把模型当成一个需要灰度、需要迁移窗口的依赖来升级，别让应用行为绑死在「最新模型」上。

02. GPT-6 Astra 的 Computer Use 被逆向工程：代码模式 + 无障碍树，浏览器操作提速 2 倍

Browserbase 团队发现 Astra 的 Computer Use 之所以快，秘诀是「让模型写代码」而不是「输出坐标点击」，并用浏览器天然的无障碍树（a11y tree）替代像素截图作为观察界面。他们把默认的 Playwright 换成自家 Stagehand 框架，加上「批处理式动作预测」，在仍使用 Astra 模型本身的前提下把浏览器操作速度提升约 2 倍，行为质量常常还更好。

三条可直接复用的结论：其一，写代码是 LLM 后训练中被强化最多的能力，让模型用它最擅长的动作形式控制环境，各领域表现全面优于坐标点击；其二，a11y tree 带有 role / name / 可操作性等语义信息，比截图信息密度更高、更结构化，模型定位元素不必做视觉推理；其三，Astra 是针对 Playwright 做过后训练的，顺着模型的训练偏好选框架，比自造抽象层更省事。做浏览器 Agent 的话，这是今天最该抄的一条作业。

03. Uber GitFarm：把 Git 操作做成中心化服务，客户端资源直降 80%

Uber 的自动化系统每天在支撑 Go / Java / Python / Web / Android / iOS 的巨型单体仓库上调用数百万次 Git。此前每个服务都维护完整检出副本：克隆 Go 单体库要约 15 分钟、6 个 CPU 核、32 GB 内存、40 GB 以上磁盘。GitFarm 通过高性能 gRPC API 暴露标准 Git 操作，网关做认证授权后路由到后端集群，命令在隔离的临时沙箱中执行；后端维护裸克隆（推送式更新 + 定期拉取）以及预热的检出和沙箱容器池，请求到达时直接挂载预热检出。

效果：完整 Git 检出从 15 分钟降到 500 毫秒，消除了 10~15 分钟的主机级冷启动，客户端资源占用降低 80% 以上。对维护 monorepo / 大型 CI 的团队，这是「把昂贵的一次性环境准备变成共享服务 + 池化」的一个完整范例。

04. FreeToken：伯克利 + MIT 开源推理引擎，让 RTX 4060 跑 35B MoE

稀疏 MoE 每个 token 只算一小部分参数，但解码时仍要在数千亿未激活权重间路由；数据中心有 NVLink 掩盖开销，消费级硬件只有 PCIe（16~64 GB/s）和主机内存延迟，传统「静态专家卸载」一旦缓存未命中就让整个执行停顿。FreeToken 用名为 q* 的动态协同调度替代僵化卸载：缓存未命中时不让 GPU 停摆，而是按实时互连吞吐在 CPU 核心与 GPU 张量核心之间分配 token 计算；配合快速权重格式（FTW）与整层双缓冲，让 PCIe 权重传输和活跃层计算完全重叠，弹性内存管理器还能在运行时动态调整 KV 缓存。

作者阵容包括 Databricks 联合创始人 Matei Zaharia、Ion Stoica 与 Song Han、Kurt Keutzer 等。演示里 RTX 4060 跑 35B 模型达到约每秒 39 token。它改变了边缘 AI 的思路：不再把个人电脑当成资源受限的数据中心节点，而是可弹性调度的异构计算资源。

06. pnpm 12.4：一个 install 同时管 npm、Python、Cargo

一个仓库同时包含前端、Python 服务和 Rust 模块时，装依赖只是第一步，之后还要安排构建顺序、跑测试、处理缓存，再搬进 CI。pnpm 12.4 在工作区启用 python.enabled 与 cargo.enabled 后，一条 pnpm install 就能安装 npm、Python、Cargo 三套依赖，共用网络请求、鉴权、制品校验和内容寻址存储。各语言规则保持独立：Python 依赖仍写在 pyproject.toml，锁文件用标准的 pylock.toml；pnpm 负责管理 .venv，并在 pnpm run / pnpm exec 时把对应可执行文件目录放到 PATH 前面。

新增的 pipeline 负责处理安装之后的构建与验证顺序，可选服务 pnpr 把共享缓存和制品托管延伸到团队环境。目标是减少多语言项目里需要额外维护的「连接代码」：哪些目录要初始化、任务之间如何衔接、已有结果能否复用、本地和 CI 如何执行同一套流程。

深度技术解读

A. Harness 该变轻还是变重？Codex 与 Claude Code 的分歧，以及 Uncle Bob 的自我修正

模型变强之后，Agent 的 Harness（把模型包起来干活的脚手架）应该越来越轻，还是越来越重？OpenAI 与 Anthropic 两家给出了截然相反的公开判断，而这背后其实是同一个问题的两面。

两种立场

Codex 团队（Tibo）主张「越来越轻」：随着模型进步，系统里的 developer message 会越来越短，Harness 本身也趋于简化。他解释 Codex 的 Harness「通常会比模型领先一点」——当模型已具备某种潜在能力但还无法稳定发挥时，Harness 先用额外指令和控制机制给它加「拐杖」；新模型更准确地理解用户意图、会主动反思任务是否完整，因此过去靠 developer message 强制约束的行为可以逐步交还模型。工程判断因此变成一个明确的取舍：新能力应该由 Harness 还是模型解决？如果预计很快能在模型层修复，团队甚至会选择完全不写临时补丁，直接等下一版模型。

Anthropic Claude Code 团队（Thariq Shihipar）主张「越来越复杂」：模型越强，Harness 反而要越复杂，因为你要让模型能够做更多事情。两者其实不矛盾——Codex 在「约束」维度变轻，Claude Code 在「能力边界」维度变重。

Anthropic 内部怎么做：分层 + 升级阶梯

Claude Code 核心开发者 Boris Cherny 给出一手经验。核心是「分层」：一次性代码可以完全黑箱（反正要扔、出错影响小），但生产代码的标准要高于人写的。Anthropic 内部的实际护栏包括：大量 lint 规则、大量测试、Claude 驱动的端到端测试、每天运行的 Claude 驱动模糊测试、自动化代码评审与安全评审、自动化重构。他的升级阶梯也很具体：换最新前沿模型 → 调高 effort（high / xhigh）→ 用 CLAUDE.md 和 Skills 教会 Claude 在你的代码库工作 → 更强的人工引导 / 让 Claude 偿还技术债、重写代码库 → 等下一个模型。

Addy Osmani 把它落成四个可执行动作

  • 先对齐结果与约束：定义「完成」长什么样、划定不可触碰的区域、判断复用是否优于新写，然后放手。最新的模型不需要冗长的规划仪式，但你需要在坏改动变成 PR 之前拒绝它。
  • 给 AI 自检手段：把确切的 build / test / lint 命令写进配置，把评审中反复拒绝的问题变成 Skills（/verify、e2e、schema 检查），开 PR 前先跑。
  • 按 blast radius 分配审查深度：影响范围决定你读多少代码；涉及 money、auth、用户数据的代码，标准要高于人写的。
  • 出错不要悄悄手动修：让模型把教训写进 CLAUDE.md 或 Skills。这是最反直觉、也最重要的一条。

Uncle Bob 的公开自我修正

《Clean Code》作者 Uncle Bob 花了几周时间构建一套 Harness，用门禁、测试、工具、协议把 Agent 的行为牢牢约束在他规定的流程里。但等他埋头其间，底层模型进步飞快，抬头时这套精心打造的框架已经多余——他甚至提出：除了最宽松的框架之外，任何框架可能都不再需要。他的三层观察是：Agent 已具备「资深工程师」级别的对话能力（能与他长时间辩论系统结构，甚至说服过他）；交付能力达到「可委托」水平（给一个重大任务和几条指导原则，离开 40 分钟回来，覆盖率、变更风险度量、变异测试、架构都达标）；但工程约束并未失效——单元测试、变更风险度量和变异测试依然能发现 bug、提供有效反馈。

实践结论：流程资产的折旧极快。针对旧模型短板做的重度工程投入，会被下一轮模型能力提升直接「蒸发」。因此——验证型工具比控制型工具更持久：测试与变异测试是质量信号，价值不依赖模型强弱；而门禁和协议是行为枷锁，模型一强就成了多余的摩擦。把工程预算优先投给 eval、测试、变异测试和可观测性，把行为约束写成可版本化、可随时删除的配置；模型升级时，主动删掉那些为了补偿旧模型弱点而写的提示词。人的角色正从「过程的控制者」退到「意图的定义者 + 最后的审查者」。

B. 2 名工程师 + Codex 的 Rust 重写：OpenAI 存储平台 Habitat 的极限扩展史

Habitat 是 OpenAI 内部的在线存储平台，为从 ChatGPT 到 Codex 的一切提供服务。2024 年中它只是一个连接单个数据库的 Python 客户端库，两年后成长为横跨约 40 个地理区域、服务超 10 亿周活用户、承载 500+ PB 数据、7000 万+ QPS 的分布式系统。重写前 Python 版本峰值扛住了 2000 万 QPS，如今 Rust 版本已承接 95% 的生产流量。这是一份少见的、把「何时该重写」讲清楚的工程复盘。

三个阶段，每一步都有明确触发条件

  • Python 库（2024 年中）：对产品工程师屏蔽 schema 查找、路由、鉴权、加密、序列化、连接池，底层数据存在 Azure Cosmos DB。因为不强制推，靠口碑在内部迅速流行。
  • Python 服务（2025 年中）：库的致命伤是升级需要协调几十个业务方滚动部署。文章给了一个很有说服力的案例——一次为缩小单区域故障影响面的路由变更，功能开关推了几天、影子流量验证又几天、修 bug 又几天，最后正要开启时，某个团队因无关原因回滚到了旧的有 bug 的客户端，恰好造成了那次本想避免的宕机。于是把 Habitat 抽成独立服务，换来部署、可观测性、安全策略（访问控制、审计日志）的单一控制点。
  • Rust 服务（2026 年 Q2）：由 2 名工程师 + Codex + GPT-5.5 完成全量重写。结果：CPU 效率提升 6 倍、内存效率提升 15 倍，平均延迟和尾延迟均显著下降，几周内 Python 版将完全下线。

Python 撑到 2000 万 QPS 的三堂课

官方提到，Python 让平台得以快速原型化以支撑 OpenAI 所有产品的用例，但要在这个规模上工作，必须解决事件循环管理与连接池的问题。其中最值得记住的一条是：asyncio 的调度延迟是尾延迟的主导因素——asyncio 解决了 I/O 并发，但不解决 GIL 下的 CPU 并行。这正是「Python 能扛到多大规模」的物理边界所在。

可迁移的判断框架：① Python（或任何高生产力栈）适合快速原型，产品早期应优先速度；② 当出现「一次改动要协调几十个团队滚动部署」时，就是抽取独立服务的信号；③ 当 CPU 密集或尾延迟成为 SLO 瓶颈、而非功能问题时，才考虑重写。编码 Agent 把重写成本从「团队 × 月」压到了「2 人 × 周」，但前提是你已经有一套强测试 / 评测护栏，否则重写只会把 bug 换个语言重演。

实践指南

01. 为新模型重新设计 Skills 和提示词：别再「硬教」模型做事

为旧模型辛辛苦苦、修修补补积累的指令，正在成为新模型的负担。GPT-6 Astra 能力提升后，过去用来「补偿模型弱点」的提示词约束（skills、AGENTS.md、任务提示）反而过度约束了它——模型本可以做得更好，却被过时的指令拉低表现。因此，新模型发布不应只是「换个模型名」，而应是一次清理提示词债务的机会。官方博客给出的方向是：从「教它怎么做」转向「告诉它边界在哪、完成标准是什么」，把方法论的自主权还给模型，自己只保留意图和约束的定义权。

  • Skill 描述要精准触发。坏例：Use when working with databases, queries, models, or persistence——凡是沾数据库边的任务都会加载它。好例：Use when adding or changing a migration, or reviewing its rollout——只在真正相关时触发。
  • 别装太多 Skills。描述列表过长会被截断，且不同 skill 的描述可能互相矛盾。描述要在「足够简短」和「能准确信号何时使用」之间取平衡。
  • 渐进式披露。读取 skill 会消耗上下文、加速触发上下文压缩；多工作流的 skill，根文档应该是一个最小化的路由器，只告诉模型「去哪找」，不强迫它读完全部内容。
📎 来源：meng shao

02. 用前缀缓存把 Agent 循环的成本压下来

理解一次请求在推理引擎里经历了什么，是优化的前提。Together AI 工程师梳理的「一个请求的一生」：一次前向传播产一个 token，prefill 吃算力、decode 吃显存，KV 缓存、连续批处理层层接力，Agent 循环再把 GPU 榨干。关键的工程杠杆是前缀缓存（prefix caching）——它能把 100 轮 Agent 循环的计算量从 55 倍降到 10 倍。

可落地的做法：保持 prompt 前缀稳定。把 system prompt、工具定义、长上下文这些不变的部分放在最前面并尽量不改动，把每轮易变的内容（用户输入、工具返回值）放到后面。这样多轮 Agent 循环才能命中缓存，否则每轮都在为同样的前缀重复付费。同理，动态拼接工具列表、每轮重排消息顺序，都会让缓存失效。

📎 来源：meng shao

03. 代码审查正在改变——但别掉进「AI 写、AI review」的闭环

Gergely Orosz 观察到几个值得对照自身团队的行业趋势：IDE（VSCode / IntelliJ）使用频率越来越低；不再追求 Token 消耗排行榜；代码审查名存实亡——AI 生成的代码多到没办法逐行审查；开源模型能力追上商业模型，既能省钱又能避免数据安全问题；中层管理大幅减少；工作反而比以前更累；优秀工程师依然难招。

其中「更累」值得警惕。有观察指出，代码审查正在演变成「AI 写 → AI review → 作者把评论发给 Agent 改 → 再让 Agent review」的闭环，而最累的是 loop 中的那个人；更糟的是，大公司里会有人故意用特别挑刺的 prompt 来 block 同事的 PR——你无法完全说服 Agent，因为你也无法说服那个故意挑刺的人。结果是在更累的同时浪费大量 token，效率并没有提升。工程上的解法是把审查的「标准」显式化、可复用化：用 Addy Osmani 的四步法把反复出现的评审意见固化成 Skill，让 blast radius 决定阅读深度，而不是让 Agent 的无差别挑刺替代人的判断。

📎 来源： 宝玉 · 马东锡 NLP

04. 给 Agent 执行的代码做沙箱：Landlock，无需 root

当你让 Agent 生成并执行代码时，隔离是绕不开的问题。Linux 的 Landlock（内核 2021 年就有，但大多数人没注意到）提供了一个极轻量的答案：无需 root、无需容器、无需配置文件、无需守护进程，程序可以主动请求内核剥夺自己对大部分文件系统的访问权限——内核会照办。文中演示的程序在没有 Landlock 时能读 /etc/hostname 和 /tmp/secret.txt，加上只允许 /etc 的规则后，后者返回 Permission denied。

实现只需三个系统调用、不用额外库，但有四个容易踩的坑，其中最关键的是：no_new_privs 是必须设置的，且 rulesets 之间是「交集」关系而非叠加。对跑不可信 Agent 输出的场景，这是比「上容器」成本低得多的最小权限方案。

📎 来源：freeCodeCamp

05. 竞态条件：Django 里「最后一次额度」的正确写法

场景很典型：你的 AI 应用只剩一次生成额度，用户在两个标签页里几乎同时提交，两个请求都通过了额度检查，应用接受了超过余额能支付的活儿。开发者的两个问题随之而来——为什么两个请求都能通过检查？如何阻止它们花掉同一份额度？

文中用一个小的 Django 额度系统完整走了一遍：先复现 bug，再用数据库事务 + 行锁（select_for_update）修复，最后写测试验证两个请求争抢最后一个额度时的行为。这是任何「先查后写」的计数 / 扣减逻辑都必须做的处理，也是让 AI 写这类代码时最容易漏掉的点——建议在 code review 时把「是否存在 check-then-act」作为固定检查项。

📎 来源：freeCodeCamp
反向观点：别急着「为 AI Agent 造工具」。很多人主张停止为人类用户做软件、转为给 AI Agent 做软件。但 seangoedecke 给了三条反驳：① 对 Agent 友好的工具对人类也友好——把 Jira 重做成「给 Agent 用的 Jira」，结果你还是得到 Jira；② Agent 用电脑的方式和人一样（输入文本、调 API）；③ 它们吸收信息的方式也和人一样（读文本、看图）。因此多数「为 AI Agent 重做 X」的尝试会失败。真正该做的是让现有工具可被 Agent 调用（稳定的 API、清晰的结构化输出），而不是另造一套只给 Agent 用的东西。
📎 来源：seangoedecke.com
配置提醒：用 OpenRouter 记得锁 provider。OpenRouter 的卖点之一是「自动 fallback、为每个请求挑最划算的后端」，但不同 provider 跑着不同的 serving 软件、优化和配置，同一个 endpoint 可能返回行为不一致的结果——有的 provider 甚至对视觉模型不支持视觉，reasoning effort 的处理方式也会不同。用 provider.only 显式限定路由、或者用 /endpoints 方法先查清可用后端，能避免「同一次调用时好时坏」这类难排查的问题。

· 两个值得收藏的架构话题

  • 代码助手的记忆层：代码图谱 + RAG + MCP。编码 Agent 越来越会写代码，却仍在大仓库里「失忆」：能解释当前文件，说不清一次改动会影响哪些模块；能搜到相似片段，不知道两个函数之间隔着几层调用。问题不只是上下文窗口不够大——传统向量 RAG 擅长「语义相似」，代码工程还需要回答「结构上相关」「最近发生了什么」「证据来自哪里」。文章把 Code-Graph-RAG（跨语言代码图谱）、code-review-graph（面向评审的增量结构索引）、RAGFlow（企业 RAG）拼成三层记忆架构：图谱回答「谁调用谁、改动会波及哪里」，RAG 回答「规范怎么写、当初为什么这样决定」，Agent 通过 MCP 在任务中调用二者。
  • 生产级 Agentic AI 的知识图谱模式。InfoQ 演讲给出四个可复用的架构模式：context bundling（上下文打包）、decision provenance（决策溯源）、code as truth（以代码为唯一事实源）、agent visibility（Agent 可见性），并演示了一个基于知识图谱构建的 engineering harness，用于缩短反馈回路、优化 token 用量、维持系统可靠性。
📎 来源： 山行AI · InfoQ

· 关于「工程师还剩什么」

吴恩达基于 1 万+ 职位分析与数十次专家访谈，用五封公开信画出一张「AI 工程技能地图」，答案分四层：构建与部署不可预测的 AI 应用、守住软件工程根基、高效驾驭编程智能体，最终上移到「塑造构建」——决定该做什么，并对结果负责。另一个角度来自 Paul Ford：「AI 能写出非常好的软件，但它也让人们更容易把别人的工作做砸，这也是很多项目失败的部分原因。当人人都能写代码之后，我们反而更清楚为什么很多人不该写。」对一线开发者而言，这两段话指向同一个结论：把精力放在判断力和验证能力上，而不只是代码产出速度。
