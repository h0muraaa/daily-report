Anthropic Advisor Tool：小模型干活、大模型当军师的架构革新

ARCHITECTURE

Anthropic 最新发布的 Advisor Tool 代表了 Agent 架构设计的重要思路转变。传统多 Agent 模式是大模型当指挥官、拆解任务分配给小模型执行；而 Advisor 策略正好相反——Sonnet 或 Haiku 作为执行者全程跑任务、调工具、处理结果，遇到难题时才"请教" Opus 获取指导。

核心机制：在 Messages API 的 tools 中添加 advisor_20260301 类型，设置 advisor 模型（通常是 Opus）和最大调用次数。Opus 全程不碰工具、不直接输出给用户，只充当幕后军师提供计划、纠正或停止信号。

实测数据显示，Sonnet + Opus Advisor 在 SWE-bench 多语言测试上比 Sonnet 单干提升2.7个百分点，同时每个任务成本降低11.9%。更值得关注的是 Haiku 的表现：配上 Opus 顾问后，Haiku 在 BrowseComp 测试上从19.7%跃升至41.2%，成本仅为 Sonnet 的15%。

这种架构的优势在于：不需要任务拆解逻辑，不需要 worker pool，不需要复杂的编排框架——所有切换在一个 API 请求内部完成。对于需要平衡成本与性能的开发者，这是一个立即可用的优化策略。

来源: @AnthropicAI / @dotey 类型: 架构设计 / 成本优化

实践指南

如何设计 Agent 友好的 API 和工具接口

BEST PRACTICE

随着 AI Agent 的普及，API 设计范式正在发生转变。传统的 API 为人类开发者设计，强调简洁和一致性；而 Agent 友好的 API 需要考虑机器理解、错误恢复和上下文传递。

设计原则：
  • 自描述性：参数和返回值的语义应清晰明确，减少 Agent 的猜测
  • 错误信息丰富：提供可操作的错误提示，帮助 Agent 自动修复问题
  • 幂等性：Agent 可能重复调用，确保相同输入产生相同结果
  • 分页与流式：大结果集应支持分页或流式传输，避免上下文溢出

Google 发布的 Skill 工具体系和微信支付的 AI 友好接入方案都是这一趋势的典型代表。开发者在设计新 API 时，应开始考虑 Agent 作为一等用户。

RAG 系统优化的三个关键阶段

BEST PRACTICE

基于大淘宝技术团队的实践经验，构建生产级 RAG 系统需要关注三个关键阶段：

1. 意图识别阶段

传统向量检索对提问方式高度敏感，同义改写、口语化表达会导致召回不稳定。建议采用思维链（CoT）驱动的意图识别，将用户问题分解为多步逻辑查询并行检索。

2. 检索架构选择

GraphRAG 虽然效果好，但构建成本高、维护难度大。LightRAG 通过实体关系抽取与双层检索范式，在保留图结构优势的同时实现秒级响应与增量更新，是更务实的选择。

3. 评测闭环建设

建立多维度评测体系，克服模型"过度自信"。人工校验必不可少，通过数据驱动的方式持续提升上下文构建能力。
