Agent隔离

Docker Sandboxes 与容器不是一回事：自治 Agent 需要 microVM 级隔离

普通容器只是共享宿主机内核的隔离进程；Docker Sandboxes 则是拥有独立 Linux 内核、文件系统、网络和 Docker Engine 的专用 microVM，面向需要完整开发环境的自治编码 Agent。Sandbox 内部还能再运行容器，所以两者很容易被混为一谈。选择原则可以很直接：执行不受信任的 Agent 代码时优先 microVM，构建可信工作负载时继续用容器。

深度技术解读

23 倍内核提升与被揪出的 Bug：AI 能写补丁，但不能替代最后一道审查

case study · linux kernel / claude code / human review

Linux 创始人 Linus Torvalds 使用 Anthropic 的 Claude Code 处理了一个困扰社区两年多的页缓存性能问题：folio 引用计数争用。在 Core i7-8565U 的 8 线程测试中，这类争用曾占到跨核 HITM 开销的 99.92%。Linus 的代码树中出现了名为 noref-filemap-read-with-llm 的分支，他提交的一组补丁在 Ryzen Threadripper 的合成基准上把吞吐量提升了 23 倍。

但故事没有停在“AI 赢了”。补丁正式合入主线前，社区维护者发现了一个连 Linus 和 AI 都没抓到的 Bug。引用计数、对象生命周期和并发路径本来就是内核中最难通过“跑分”证明正确的部分；合成基准能证明快，却不能证明在所有竞态窗口下都安全。AI 降低了生成候选补丁的成本，也把瓶颈进一步推向了审查、复现和边界测试。

对一线团队的启示

把 AI 产出当作候选补丁，而不是最终补丁。 性能类改动至少要通过目标硬件复现、并发/生命周期测试、维护者交叉审查和可回滚发布四道门；基准结果只回答“是否更快”，不回答“是否仍然正确”。
review checklist · performance patch
# 1. 先证明问题，再证明修复
$ reproduce_benchmark --before baseline.json --after patch.json
# 2. 在目标硬件上重复，不只看单次最优值
# 3. 跑并发、生命周期、压力与错误注入测试
# 4. 让不写这段代码的人做 adversarial review
# 5. 保留独立回滚路径，灰度后再合入

Agent 上下文的两条路线：少塞一点，或把稳定事实写进权重

context engineering · retrieval · weight memory · model routing

Optiver 的工程分享给出了一个很有代表性的数字：用户还没提问，上下文里已经塞进了 200K tokens。他们的处理方式不是继续扩上下文窗口，而是通过 tool search、缓存和更好的默认值削减 context bloat。LangChain 则把检索型 Agent 的典型故障拆成三类：笨拙的搜索、过大的结果、过期的文本。这三点指向同一个工程问题：Agent harness 需要主动管理“什么进入上下文、以多大粒度进入、什么时候失效”，而不是把检索结果原样倾倒给模型。

另一条路线是把稳定知识写进模型权重。Amazon 的一项工作对比了权重记忆与检索：在相同模型和用户数据下，普通微调存储用户事实的准确率为 36.9%，on-policy self-distillation 达到 59.9%。后者在 8 个 HaluMem-Long 用户上、不提供检索上下文时，也超过了 MemOS 风格检索（47.8%）、抽取上下文（51.9%）和原始对话（51.3%），并且在 4B、9B、27B 三个规模上都成立。方法上，教师模型读取用户记忆，学生模型必须在没有记忆上下文的情况下作答。

这并不意味着“检索已死”。权重记忆更适合变化慢、需要即时召回的用户偏好与事实；检索更适合项目状态、代码库、工单和今天刚发生的变化。更现实的架构是分层：稳定事实进权重，动态状态走向量库或工具查询，再用路由层按任务选择模型。OpenRouter 的新一代 router 提供了一个旁证：其 beta 数据显示无效工具调用降低 4 倍、Agent 响应截断减少 50%、延迟降低 3 倍；Auto Code 在基准上接近 Opus 5.5，但成本低 74%，p90 延迟 0.65 秒。

可以落地的上下文预算

先量后调：记录每次请求的 prefill tokens、检索命中率、结果长度和工具调用失败率。把“加载全部工具”改为“先搜索工具”，给检索结果设长度上限与 TTL，对稳定前缀做缓存；再用评测集验证记忆分层是否真的减少重复问答。

实践指南

把今天的新闻转成明天就能执行的检查项。

给 Agent 划清执行边界：不可信代码进 microVM，密钥不进沙箱

Docker Sandboxes 与容器的差异说明，共享宿主内核的容器并不适合承载任意自治 Agent 代码。执行边界应包括独立内核或 microVM、最小化出站网络、短期凭证和独立文件系统；长期云密钥不要挂进 Agent 环境，改用短 TTL 的委托令牌，并记录每次工具调用。

为 AI 生成的性能补丁建立“四道门”

  • 目标硬件复现：记录基线、补丁后数据和波动范围，不只看最佳值。
  • 并发与生命周期测试：引用计数、锁、对象释放路径必须有专门用例。
  • 交叉审查：让未参与生成的人做 adversarial review，重点看边界条件。
  • 可回滚发布：灰度、开关、独立回滚路径，避免一次性合入主线。

把 CI/CD 依赖从“隐式最新”改成“显式锁定”

GitHub Actions lockfiles 已 GA，建议把第三方 action 的版本升级纳入 code review：锁定解析结果、保留可读引用、限制 workflow token 权限、对外部 action 做来源审查。对安全修复则要保留快速升级通道，避免“锁死”变成“永不更新”。

建立上下文预算，而不是不断加大窗口

统计每次 Agent 请求的 prefill tokens、检索结果长度、工具定义数量和失败率。优先做四件事：按需搜索工具而不是全量注入；给检索结果设长度上限；对稳定前缀做缓存；为文档和记忆设置 TTL 与失效策略。每项优化都应在固定评测集上对比成功率、延迟和成本。

运行时升级要分三条线验证

  • TypeScript 7.1：先验证编辑器问题与 Compiler API 消费方，必要时保留 TS 6 双版本过渡。
  • Node.js 27 Alpha：只用于库作者和测试环境，不进入生产；关注破坏性变更与 V8 15.6 行为。
  • Go 1.27：用真实数据测试 encoding/json/v2 对重复键、非法 UTF-8 和错误路径的处理变化，再评估 10 倍反序列化收益。
