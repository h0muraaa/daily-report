Weight-Space Programming：让前沿模型直接读写另一个模型的权重

MIT CSAIL 的 Rikiya Takehi 团队提出 Weight-Space Programming：GPT-6 Astra 不经过梯度下降或训练循环，直接阅读并修改神经网络权重。最受关注的实验里，Astra 只动了 Qwen3.5-0.8B 约 0.016%（131,072 个）参数，就把 MATH-500 从 7.9% 提到 48.1%、GSM8K 从 13.8% 提到 67.1%，指令遵循也明显改善；它还能仅凭 17,253 个权重数字，以约 99% 置信度认出四个同构 PPO 策略网络分别在玩 Breakout、Pong、Pac-Man 还是 Freeway。保留意见同样重要：Qwen 原本就有严重重复推理问题，这次涨幅里有多少是“修 Bug”、多少是真正的新能力，社区仍有争议。

// deep dive 01 — infrastructure

Pando：当 Git 成为 Agent 时代的瓶颈，该改客户端还是改后端？

OpenAI 和 Anthropic 遇到了同一个问题：Agent 写代码太快，代码管理系统反而成了公司开发速度的瓶颈。两家都把全公司代码放在一个 monorepo 里，也都把 Codex / Claude Code 推到“多分支并发写 + 海量并发读”的极限。旧系统从去年底开始慢推慢拉、合并失败，OpenAI 的可靠性一度低于 90%。

两家解法方向相反。OpenAI 选择保留 Git，只替换服务器后端，工程师和 Agent 的肌肉记忆、脚本、CI 全都不用改；Anthropic 选择替换 Git，自研客户端和服务端 Scion，提交、合并、代码审查、代码搜索、CI 全部自己写。对绝大多数团队来说，OpenAI 这条路更近，因为改动不会外溢到开发者工作流。

Pando 到底改了什么

Pando 的关键不是“更快地跑 Git”，而是放松了两个过去被默认成立的假设：

  • 全仓某一时刻一致 → 改为单条 ref 可串行化，跨 ref 只保证因果一致。推不同分支可以并行，推同一分支仍然有序。
  • 按客户端现算专用 pack → 改为把 packfile 作为不可变对象存进对象存储，元数据记录 tip、依赖和包指针；读侧把 have/want 映射到已存 ref version，用 packfile-uri 下发可缓存包。

数字与代价

生产数据：中位推送延迟约降到原来的 1/5（官方口径为降低约 80%），日均可吐近 1 PB Git 数据；仓库中位 pack 小于 20 KiB，P99 小于 3 MiB；读侧 Express 缓存命中率超过 99%，标准机器能跑满 10 Gbps。代价是“叠分支”时可能多传一些对象，因为服务端默认只广告主干作为基，避免 pack 广告随百万级分支膨胀。后台用 LSM 思路把 L0 合并到更高等级，既压缩又当跳跃索引，规划复杂度约 O(log Δ)。

对普通工程团队的启发

  • 不要轻易自研。Pando 是约 10 周用 Codex 从立项到生产的产物，但前提是 OpenAI 有专门的存储/基础设施团队和极端规模。中小团队先看供应商是否开放，或先优化 CI 的 fetch 策略。
  • 把“一致性”拆开看。很多系统慢，是因为默认要求全量快照一致。Pando 的经验是：单条 ref 有序、跨 ref 因果一致，已经够用，还能换来并行。
  • 不可变对象 + 可缓存 URI 是通用模式。不只是 Git，制品库、模型权重、构建缓存都可以借鉴“内容不可变 + 元数据指针 + CDN 复用”的结构。
  • 上游回馈是长期红利。OpenAI 把修过的 Git 问题提交回官方，部分进了正式版；这类基础设施改造如果能反哺上游，维护成本会低很多。

// deep dive 02 — model internals

Weight-Space Programming：把“解释权重”变成“编辑权重”

这篇论文之所以炸裂，不是因为“0.016% 参数换 6 倍成绩”这个标题，而是因为它把机制可解释性的输出从“解释”推进到了“可执行的编辑指令”。过去四十年，想改模型行为基本只有两条路：改输入（提示词）或改数据（微调/RL）。Weight-Space Programming 主张第三条路：让一个足够强的前沿模型直接读权重数字，定位问题，然后改权重。

实验里到底做了什么

实验输入结果
游戏识别4 个同构 PPO 策略网络，各 17,253 参数约 99% 置信度识别 Breakout / Pong / Pac-Man / Freeway
形状识别3 个小扩散模型（圆 / 方 / 三角）不跑前向，从权重画出轮廓，更像在读几何结构
语言识别3 个 7.2M 字符级 LM，仅保留中间 4 个 Transformer 块区分 Python / 罗马字日语 / 英语
从零写网络全零权重写出小型 Breakout 策略网络，得分 517.4，远高于 PPO 训练 5 亿步的基线
修 QwenQwen3.5-0.8B，改 0.016%（131,072）参数MATH-500 7.9% → 48.1%；GSM8K 13.8% → 67.1%；指令遵循约 3x

Qwen 的例子最能说明问题：这个 0.8B 模型做数学题时经常花掉 32K token 还在重复相似推理，最后交不出答案。Astra 把循环追踪到两层，改了约 0.016% 的权重，在固定采样参数的前提下把 MATH-500 从 7.9% 拉到 48.1%。对维护小模型的人来说，这更像一次“外科手术式排障”，而不是重新训练。

为什么值得认真看

  • 解释结果变成编辑指令。可解释性不再是给人看的热力图，而是可以直接改参数的操作步骤。
  • 模型维护可能绕过重训。修死循环、修指令遵循、移植控制策略，理论上不必再走完整的梯度训练。
  • 小模型先受益。参数规模越大，权重文本越长、定位越难；但 0.1B–few B 的开源小模型，可能是第一批被“权重编程”改造的对象。
  • RSI 叙事又多了一条短路。Latent.Space 把它放进“AI 改进 AI”的语境：以前要跑完整的 autoresearch 实验，现在可能直接改权重。
// 冷静视角
第一，Qwen 本身就有严重重复推理问题，数学成绩暴涨里有多少是“修 Bug”、多少是“新能力”，需要更干净的基线才能判断。第二，论文主要在小网络上展示读写能力；有评论（seangoedecke）认为这更像人类专家也能做的逆向分析，“超人类”说法被夸大。第三，这不是完整的 Transformer 白盒化，距离“随便改大模型”还很远。把它当成一个有潜力的研究方向，而不是明天就能上生产的工具。

给工程师的实践建议

  • 先建立可复现评测。任何“改权重后变强”的结论，都要固定采样参数、固定评测集、保留失败样例；否则很容易把修 Bug 误判成能力跃迁。
  • 把它当排障工具观察。如果你在维护开源小模型，关注后续是否出现权重检查/编辑的工程化工具；短期内仍以微调、提示词、约束解码为主。
  • 安全边界要提前想。直接改权重意味着绕过训练阶段的对齐流程；一旦工具化，模型发布、审计、回滚都需要新的治理机制。

Next.js 发布 2026 年 11 月安全版本，使用 App Router / Server Actions 的项目应尽快升级并复测。TeamCity 发布 2026.2.2 与 2026.1.6 修复版，包含安全与性能问题；同时 eMudhra 的 8 个中间 CA 私钥被发现在公开数据中可恢复，虽然 eMudhra 称未签发终端证书，但 TeamCity 依赖的 Java 信任库可能仍信任这些证书，新版本会给出健康报告和修复步骤。Vercel Security Review 进入公开 beta：每次 push 到关联 GitHub 仓库都会自动扫描漏洞，包括直接 push 和 force push 到生产分支，发现项会带修复建议和 AI 严重度评级。

  • 盘点 Next.js / TeamCity 版本，排升级窗口。
  • 检查 TeamCity 所在 Java 运行时信任库，移除受影响的 eMudhra 中间证书。
  • Pro / Enterprise 团队评估开启 Vercel Security Review，至少覆盖生产分支。
  • 高 stakes 的模型路由/代理场景，关注 Anthropic FlashProve：它用密码学方法证明“某个响应确实来自某个模型”，比此前开源方法更高效，可用于防聊天劫持、让安全评估者确认被测模型与线上模型一致。
→优先级：Next.js 与 TeamCity 补丁今天处理；Vercel 扫描本周开启；FlashProve 先做技术调研。

API 迁移日历：Gemini 2.5 系列 12 月 1 日自动重定向

  • 更新计费与限流假设，特别是长上下文和批量任务。
→本周完成模型 ID 盘点，11 月中旬前跑完评测，不要等到 12 月 1 日被动切换。

Vitest 5 升级：先修“浮动 Promise”，再谈提速

Vitest 5 的性能收益很诱人，但默认值变化会直接让老测试变红：clearMocks 默认开启，未 await 的异步断言现在会失败。升级前先确认 Vite 6.4+ 与 Node.js 22.12+；升级后先跑 vitest doctor 看环境，再用 Browser Mode Trace View 定位失败的浏览器测试。共享 Vite Server 对大型测试套件收益最大，小项目可能感知不明显。

  • 在 CI 单独开一条 Vitest 5 分支，先观察不稳定用例，不要一次性全量切。
  • 修复所有 fire-and-forget 异步断言；需要显式等待的用 vi.when。
  • 审计依赖“上一个测试的 mock 状态”的用例，必要时显式重置。
  • 对比升级前后的 CI 墙钟时间，重点看 VM 池场景是否吃到 50% 级别的收益。
→本周开分支试跑；先修测试正确性，再量化性能收益。

Agent 成本与上下文：别只盯 token 单价

Artificial Analysis 的拆解很直接：一个 Agent 任务的成本由输入 token、缓存命中率和步数共同决定；同一个任务，有缓存约 $21，没有缓存超过 $200。Google 的建议是用便宜的分类器把请求路由到不同 Gemini 模型和思考等级，用少量分类成本换大模型调用量下降。检索侧同样有杠杆：Mixedbread 的案例里，替换掉“OCR + 分块 + embedding + 向量库”的拼装栈、改用多模态 late-interaction 检索后，客户答案准确率从 36% 提到 98%。另外，Google Cloud 提醒不要“把三页 CLI 文档粘进 SKILL.md、跑通一次就 merge”，没有评测循环的 skill 只会把上下文窗口撑爆。

  • 成本指标从“每百万 token 价格”改成“每个成功任务成本”，同时记录缓存命中率和平均步数。
  • 对高频、低难度请求加分类器路由；把最强模型留给真正需要的任务。
  • 为检索单独建评测集，比较“换更大模型”与“换更好的检索”哪个更划算。
  • 每个 SKILL.md 控制长度，配 3–5 个真实场景的回归用例，再进主干。
→本季度建立“每成功任务成本 + 缓存命中率 + 检索准确率”三张看板，按周复盘。
来源: AI Engineer / Artificial Analysis · Google Developers Blog · AI Engineer / Mixedbread · Cloud Blog

团队级 Agent 落地：从“能答”到“可评测、有边界”

三个国内团队的实践可以拼成一张落地路线图。字节 Storage Agent Family 建立了离线回归 + Trace 定位 + 线上真实对话沉淀评测集的闭环，覆盖任务、行为和安全三类指标，解决“改一处提示词/技能/CLI 就破坏另一场景”的问题。小红书 SDBP 上线两个多月服务千余名内部用户，独立解决数千个问题，日均解决量达到单名专家的 5 倍以上，约三成问题在非工作时间解决；关键建设点是共享执行资源、知识获取、访问边界和群聊协作。腾讯观察到 Agent 产品从 Bot 走向桌面/IDE，再走向“两边互相补”，本质是两个需求：Agent 要更接近真实工作环境，人要能随时找到它并把能力交给别人用。

  • 先把真实工单/对话转成可复现评测集，再做 Prompt / Skill / Harness 的快速迭代。
  • 为 Agent 定义清晰的访问边界和共享执行资源，避免“能干活但不敢上线”。
  • 用任务完成率、独立解决率、非工作时间解决占比衡量价值，而不是只看回答是否通顺。
  • 把 Agent 当团队成员管理：有身份、有权限、有交接记录、有回滚方案。
→本季度先做“评测集 + 访问边界”两件基础设施，再扩 Agent 的场景覆盖。
