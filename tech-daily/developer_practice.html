SECURITYPHP 紧急发布四个安全版本，修复两个未认证 RCE 漏洞

PHP 项目于 10 月 21 日同步发布 8.5.12、8.4.27、8.3.36、8.2.35，修复 CVE-2026-109618 与 CVE-2026-109619，两者 CVSS v4.0 均为 9.2。漏洞位于核心引擎的内存管理与错误处理路径，攻击者无需认证、在应用代码执行之前就能触发，影响 PHP-FPM、mod_php、php-cgi、FrankenPHP 与 LiteSpeed，其中 mod_php 风险最高；回溯发现最早受影响路径可到 PHP 5.4.0。

按 W3Techs 口径，约 70% 可识别服务端语言的网站使用 PHP，这意味着补丁窗口极短。更值得工程团队注意的是：这批漏洞最先由前沿 AI 模型发现，攻击侧已经进入"机器速度"，而多数团队的资产盘点和补丁流程还停留在人工节奏。

SECURITYLinux 内核多个高危漏洞疑似被误发到公开邮件列表，最高 9.0

Trend Micro 旗下 ZDI 疑似把多份 Linux 内核漏洞报告发到了公开的 LKML，而不是私有安全列表；内核维护者 Greg Kroah-Hartman 逐一追问原因，但未得到准确回复。泄露的漏洞覆盖网络协议、SMB 服务、显卡驱动等组件，其中 SMB Direct 的整数下溢（ZDI-CAN-33549）和 KSMBD 的竞争条件（ZDI-CAN-33774）均被评为 9.0，可能导致远程代码执行或本地提权。

部分补丁已进入 Linux 7.5 开发分支，但尚未全部合入主线。对于运行 KSMBD、暴露 SMB 或依赖特定网卡驱动的生产环境，这相当于漏洞细节提前公开、补丁却未完全就绪，应尽快评估暴露面并准备临时缓解措施。

INFRACloudflare 重写 Range 缓存，Origin Range Requests 全量开放

视频播放器拖动进度条只请求几 MB，但在旧的 Range 缓存实现下，Cloudflare 可能从源站拉取 128 MiB 并在数据中心之间搬运，甚至发生在用户已经离开之后。新实现针对性地重构了缓存对大文件分段请求的处理方式：R2 的 p99 首字节时间下降约一半，分层缓存（tiered cache）流量再降约 6%。

该能力现以 Origin Range Requests 的形式在所有套餐自助开放，不需要调优 Range 大小，也不需要源站特殊配合。对自建大文件分发、视频点播或对象存储网关的团队，这是一个可以直接对照的实现范式：缓存粒度应围绕"实际请求的字节区间"设计，而不是围绕整个对象。

来源：The Cloudflare Blog · Origin Range Requests: Serving large files without range-request tuning

SERVERLESSAWS Lambda Web Functions：Express / Hono 可直接跑在 Lambda 上

AWS 推出 Lambda Web Functions，允许开发者把基于 Express、Hono 等框架的 Node.js Web 应用直接部署到 Lambda，并支持并发请求与流式响应。过去这类应用通常需要适配层或第三方方案来桥接请求/响应模型，现在由平台原生承接。

实际落地时仍要关注冷启动、数据库连接复用和流式响应的超时语义；"能直接跑"不等于"适合所有场景"，高并发、长连接或大量小请求的服务仍需对比 API Gateway + 容器方案的延迟与成本。

两条主线：安全左移与 Agent 可靠性

当漏洞发现进入"机器速度"，防御体系该补哪几块？

从 PHP 未认证 RCE、Linux 内核报告误公开，到 Anthropic OSS Scanner 与 MCP 供应链风险

今天三条安全新闻可以拼成一条完整的攻击链路：发现更快、披露更乱、供应链更宽。PHP 的两个 9.2 漏洞由前沿 AI 模型率先挖出，影响跨度超过十年；Linux 内核报告被误发到公开邮件列表，细节提前曝光而补丁未齐；与此同时，Anthropic 推出 OSS Scanner，用自家最强模型（包括 Claude Mythos）定期扫描开源项目并直接生成报告。

// 发生了什么

  • PHP：漏洞藏在核心引擎的内存管理与错误处理路径，一次未认证请求即可在应用代码执行前触发。mod_php 风险最高，因为攻击面在应用启动之前；回溯到 PHP 5.4.0，意味着"很多年没升级"的遗留系统同样在射程内。
  • Linux：ZDI 疑似误将报告发到 LKML，涉及 SMB Direct 整数下溢、KSMBD 竞争条件等 9.0 级问题。部分补丁在 7.5 开发分支，主线未完全修复，维护者只能公开讨论。
  • OSS Scanner：免费、按项目 opt-in，报告由模型生成且不经过人工审核即发给维护者，维护者自行验证并决定接受哪些修复建议。这降低了发现成本，也把"验证负担"转移给了开源维护者。
  • MCP 供应链：任何人都能发布 MCP Server，Agent 一旦接入就能读邮件、发消息、操作环境；盲目集成会把权限直接交给未经审计的第三方代码。

// 工程含义

攻防的不对称正在扩大：AI 可以在很短时间内扫描海量代码并给出候选漏洞，而企业的资产清单、补丁验证、灰度发布仍按人力节奏运行。真正的瓶颈不是"有没有扫描器"，而是从发现到修复的流水线是否可自动化、可审计、可回滚。另一个容易被忽视的问题是误报：模型报告不经人工审核，直接进入维护者邮箱，若团队没有可复现的验证流程，就会被大量线索淹没。

注意：AI 生成的漏洞报告应视为"高优先级线索"，而不是"已确认漏洞"。对外暴露系统的关键补丁，仍需要复现、影响面评估和人工签字。

// 可执行清单

php -v

开源维护者可以评估 OSS Scanner 这类 opt-in 服务，但应把它接入现有的 issue/CI 流程，由自动化做去重与复现，而不是直接消费报告结论。企业侧更现实的动作，是把 AI 安全扫描纳入 CI 与依赖治理，同时保留人工对高危修复的最终决策权。

Harness Engineering 的 11 个坑：Agent 可靠交付靠的是工程系统

从 "Agent = Model + Harness" 到 "Harness 管完成、Loop 管进化"，以及 Meta / Anthropic 的两种架构纠偏

2026 年，Harness Engineering 取代 Prompt Engineering、Context Engineering 成为硅谷流行的 AI 工程范式，公式也很简洁：Agent = Model + Harness。模型提供智能，Harness 让智能变得可用。问题在于，很多团队把它当成"高级 Prompt"来用，结果模型一换效果归零，或者代码生成率上去了、总成本反而转移到测试和线上。

// 原文指出的典型误区

  • 认知层：把 Harness Engineering 当成"更高级的 Prompt"。这是腾讯云开发者文章列出的第一个坑，也是最普遍的误判——Harness 包含工具、上下文组织、执行约束、验证与反馈，不只是提示词。
  • 系统层：只追求代码生成率。QCon 圆桌嘉宾指出，代码生成率做到 90% 并不解决问题，成本只是从开发转移到测试与线上；模型决定能力上限，工程化体系决定交付下限。
  • 架构层：子 Agent 拆得过细。Anthropic 观察到，一件事转手太多次，用户刚说过的条件就丢了；有客户把多 Agent 流程合回主循环，运行时间缩短约一半。
  • 架构层：单个 Agent 承担过多领域知识。Meta 最初让一个 Agent 负责推荐系统的数据列接入，演示正常，生产却开始混用不同数据源规则；后来拆成瘦编排器（thin orchestrator）+ 14 个专业 Agent。

// 从 Harness 到 Loop：静态系统 vs 进化系统

圆桌对两个概念做了清晰区分：Harness 解决"Agent 怎么把任务完成"，是一个静态系统；Loop 解决"Agent 怎么越变越强"，是一个进化系统。最本质的变化是生产关系——人从执行职责里解放出来，变成 AI 干完活来找人做决策。但能自动化的是执行，不能自动化的是决策与验收，最终仍需人拍板；当前离真正的自进化还很远，最大缺口是 Agent 不具备人的上下文。

// 一个可借鉴的权限模式

Vercel Agent 在生产环境中的做法值得参考：先调查问题，再给出包含"将要做什么、需要什么权限"的计划；用户批准计划后，才授予执行该计划的增量权限。这避免了两个极端——一上来给宽泛权限（误操作会波及无关资源），或每一步都弹窗（用户很快养成无脑点"同意"的习惯）。

# 伪代码：计划先行的最小权限授权
plan = agent.investigate(issue)
plan.actions   = [...]          # 将要执行的具体动作
plan.permissions = derive(plan.actions)  # 由计划推导所需权限

if human.approve(plan):
    token = grant(scope=plan.permissions, ttl=short)
    agent.execute(plan, token)
else:
    agent.revise(plan)          # 不执行，回到调查/规划

// 落地建议

  • 定义上下文契约：主 Agent 与子 Agent 之间传递什么、哪些状态必须保留，写成 schema 并测试；交接丢上下文是可靠性的头号敌人。
  • 优先瘦编排器：流程控制、可靠性检查留在编排层，领域知识下沉到专业 Agent；不要在一个 Agent 里塞多套互相冲突的规则。
  • 权限跟着计划走：不要让 Agent 长期持有宽泛生产权限；按任务签发、短期有效、可撤销。
  • 评测要像做实验：Omni Analytics 的 Stephanie Jarmak 指出，只替换 Harness 就能让评测结果偏移 30%；公开基准只适合初筛，自建评测要用真实任务、重复运行、完整 trace，并设置真正能阻断发布的 quality gate，生产是最终测试。

实践指南

本周可落地的工程动作

01把补丁窗口写进值班流程，而不是文档里

PHP 9.2 与 Linux 9.0 的案例说明，漏洞细节可能在任何时刻公开，补丁速度就是暴露时长。建议按可达性分级：对外暴露且可未认证触发的 9.0+ 漏洞走 24 小时通道；内部服务走 7 天通道。每个通道都要有"谁批准、谁验证、如何回滚"的具体责任人，并在金丝雀环境验证后再全量。
