DeepSeek-V4.1-Flash 开源：552B MoE，非对称 Causal Encoder–Decoder open weights

DeepSeek 正式发布并开源 V4.1-Flash，这是一个 552B 总参数的 MoE 多模态模型，原生支持图文输入，最长上下文 100 万 token。最值得开发者关注的是它全新的 非对称 Causal Encoder–Decoder（CED）架构：处理输入时每个 token 只激活 8B 参数，生成输出时激活 16B——这是为「输入重、输出轻」的长程 Agent 场景专门做的成本设计。官方给出的缓存数据更直观：相比上一代，KV Cache 的 HBM 占用降到 1/4、SSD 持久化占用降到 1/8，而相对初代模型累计缩小了 437 倍。模型权重与技术报告已在 ModelScope 开放，API 端价格为每百万 token 0.30 美元输入 / 1.20 美元输出，在 Code Arena: WebDev 上以 1620 分落到约第 14 名、开源模型约第 4 名，且与前 13 名差距不足 5 分。

深度技术解读

DEEP DIVE 01

CED 架构怎么把 KV Cache 压到 1/4：拆开 DeepSeek-V4.1-Flash 的「预算再分配」

常规 Transformer 里，每一层的 K/V 都由「进入本层的 hidden states」生成。这意味着要拿到某一层的 KV，历史输入必须先一路算到那一层——对一个已经累积了几万 token 消息、代码、工具结果和日志的长程 Agent 来说，这段历史每次都要重走完整主干，prefill 成本随上下文线性膨胀。V4.1-Flash 的 Causal Encoder–Decoder（CED）改变了这个依赖方向：decoder 的 global KV 直接由 causal encoder 最后一层的输出经投影产生，因此为历史位置构造 decoder 的 global KV 时，不必先完成这些位置在 decoder 各层中的全部计算。

具体结构上，模型的 40 层主干被切成两半：前 20 层是 causal encoder，后 20 层是 decoder。生成新 token 时它仍然完整经过 20 层 encoder + 20 层 decoder，并利用已有历史 KV 做注意力；变化的是「读历史」这条路径被大幅缩短。这就解释了官方那组看起来矛盾的数字：

552B
语言主干总参数（另有 196B Engram 条件记忆参数）
8B
prefill 阶段每 token 激活参数
16B
decode 阶段每 token 激活参数
1/4 · 1/8
运行时 KV Cache / 持久 KV Cache（相对前代）

省下来的历史计算并不是孤立的技巧，它和跨层缓存共享、低精度存储、会话恢复组合成一套面向「输入占主导」任务的系统设计——沿着「读入历史 → 继续生成 → 暂停后恢复」这条链，每一环都在压同一份预算。对开发者的实际含义是：如果你的 Agent 是典型的「长历史 + 短输出」形态（读大量代码/日志/对话再给一个决定），那么在你为模型能力付钱之前，成本结构其实主要由历史 KV 的存储与搬运决定。选模型时把「prefill/decode 激活比例」和「KV 缓存压缩比」放进评估表，比只看 benchmark 分数更能预测真实账单。

DEEP DIVE 02

Harness Engineering：模型一个参数没动，通过率 67% → 86%

当 Agent 表现不好时，团队的第一反应通常是「换更大的模型」。adaption.ai 在 Harvey 法律 Agent 基准（LAB）上的实验给出了相反的结论：在 140 个与训练集不重叠的留出任务上，只改包围模型的 Harness（工具设计、上下文管理、执行循环、交付校验），Qwen3.6-27B 的通过率就从 67.10% 提到 85.92%，随后再加上后训练才推到 88.03%。在 GLM-5.2 上同一套 Harness 把成绩从 88.39% 提到 90.64%。团队对两种增益做了明确区分：「Harness 恢复的是基座模型已具备但被埋没的能力，而后训练增加的是模型原本不具备的能力。」

轨迹分析把丢分点定位得很具体，也基本可以直接抄作业：跑完却没有可用文件、工具调用格式错误导致死循环、读取大文件后指令丢失。对应的四类修复是——有界文件读取、可操作的工具报错、上下文压缩时保留关键状态、退出前校验交付物。其中「因路径缺失导致的写入失败」从 120 次直接降到 0。更值得注意的反例来自 Salesforce 的一篇论文：他们先围绕一个弱模型进化出 Harness，再用强专家在同一 Harness 下的完整轨迹去微调这个弱模型，结果 7 个企业 Agent 任务的表现全部下降 4 到 30 分（Qwen3-Coder 与 Gemma 4 上均如此）——原因是弱模型学到了专家的规划策略却没有执行能力，同时又不再匹配原本为自己的规划风格进化出来的 Harness。同一份微调在未进化的 Harness 下反而有效，说明决定结果的是模型与 Harness 的匹配度，而不是把两边的「最优」拼在一起。

工程启示可以浓缩成一句：把 Harness 和模型当作一对共同优化的变量来对待。先设计适配任务的 Harness，再在 Harness 内部调模型（model-harness co-optimization）；而在 Harness 层面可动的东西远比大多数人以为的多——Browserbase 复盘浏览器 Agent 三年路线时，最终放弃了「给模型预设工具」的思路，全面转向「让模型直接写代码控制浏览器」，并给出判断：做好 Agent 是 Harness 问题，不是模型研究问题，最好的 Agent 本质上都是换了外衣的 Coding Agent。同类信号还有百度团队的做法：把一个需求拆成需求澄清、方案设计、编码实现、审查验收、提交归档的固定流水线，每阶段交给只干一件事的 Sub-Agent，配合状态落盘与人工门禁，目的同样是让 AI 写代码从「碰运气」走向「可交付」。

📎 来源：meng shao（adaption.ai 实验解读） · elvis（Salesforce 论文） · Browserbase 三代路线复盘 · 百度 Agentic Harness Workflow · dbaplus 企业 Agent 落地实践

TOOL 03

Mem0：结构化记忆 vs 非结构化记忆，实测差 6 倍

mem0 公布了一组很有说服力的默认流程对比：同一个系统里，稳定偏好（「我偏好深色模式」）在 12 次测试中被完整保存了 12 次，而临时工作进展（「迁移被阻塞了」）只保存了 2/12 次；把同样的阻塞信息写成结构化字段后，变成 12/12。他们给的经验法则是：只为「会被过滤、校验或聚合」的东西建字段，其余保持文本——这是写入时灵活性 vs 查询时可靠性之间的取舍。最实用的结论是不要二选一：非结构化记忆捕获快，结构化记忆便于代码查询，好的 Agent 会有意地两者并用。

TOOL 04

Milvus External Collection：让权威数据留在 Parquet / Iceberg 里

Milvus 官方给出了一个清晰的选型判据。用普通 collection：应用会持续 insert/upsert，删除必须能通过在线写路径被检索到，serving 数据要保持最新——这种情况下 Milvus 存储并管理源记录。用 External Collection：权威数据集已经以 Parquet、Iceberg、Lance 或 Vortex 形式存在时，Milvus 只在其上建索引并通过同一套 search/query API 服务，新鲜度由显式的 Refresh 控制。两者不是互斥的：一个产品可以同时把快速变化的库存放在普通 collection、把批量产出的目录放在 External Collection。对已经有数据湖、又不想把数据复制一份进向量库的团队，这能省掉一整条同步链路。

实践指南

GUIDE 01

Agent 代码评审提示词：先让它自己实现一遍，再对比

宝玉分享的 Agent Review 提示词只有三步，但顺序是关键：

  • 先搞清楚这个 PR 解决的问题是什么——脱离意图的 review 只会挑风格。
  • 如果不看这个 PR 的实现，你会怎么实现？——逼模型先形成独立方案，避免被现有实现锚定。
  • review 代码后对比你自己的方案给出审查结果——此时差异点是真正有信息量的地方（更好的抽象、漏掉的边界、多余的复杂度）。

第 2 步是这套提示词的价值所在：直接让模型审查代码，它容易变成「解释这段代码在做什么」；先让它独立设计再对比，它才有可能指出「你这样做解决不了原问题」。这条 32K+ 浏览、300+ 收藏的提示词可以直接复制到自己的 PR 流程里。

📎 来源：宝玉 @dotey
GUIDE 02

Frontier Engineering：手写代码不足产出的 1%，那你在做什么

Kiro 团队把「人定方向、Agent 执行」的工作方式总结为 Frontier Engineering，并反复强调它不是 vibe coding。十条原则里信息量最大的几条：

  • 你是架构师，不是打字员。 前沿开发者手写代码占产出不到 1%，其余来自其「指导、引导和审查」的 Agent。工作压缩成两件事：定义「完成」是什么（需求、约束、验收标准），以及验证产出是否符合意图。
  • 最大化 Agent 时间，最小化你的介入。 反模式是「发一条提示 → 等 60 秒 → 拿回代码 → 手动测试 → 把报错贴回聊天窗」。正确做法是给带内置验证的长任务，例如「实现这个功能，写测试，跑测试，确保通过，新代码达到 90% 测试覆盖率」，让 Agent 持续工作 30 分钟以上并自我收敛。此时瓶颈不再是打字速度，而是你同时能让多少个 Agent 保持有意义的工作状态。
  • 为 Agent 构建你的代码库。 人类新成员只需入职一次，Agent 每次会话都要重新「入职」一遍，因此文档和规范的 ROI 被放大了无数倍。

配套的还有 DeepLearning.AI 的 AI Engineering Skills Map（Pillar 3: Using Coding Agents），把技能拆成「主导工作流 / 启用 Agent 自主性 / 审查产出」三类——方向一致：开发者的核心动作正在从写代码转向定规格、设计架构、评估 Agent 产出。

📎 来源：meng shao（Kiro 原则整理） · DeepLearning.AI
GUIDE 03

AI 生成代码之后，瓶颈已经移到「验证」这一侧

InfoQ 的文章《When Spec-Driven Development Pays Off》给了一个值得记住的判断：AI 编码助手已成开发核心，生成侧确实有生产力收益，但同时在引入安全弱点和熟悉的 bug 模式——瓶颈已经从代码生成转移到了代码验证。文章的落点是如何检测并缓解「AI 生成行为偏离意图」的情况。结合前一节 Harness 的结论，可以拼出一条完整的实践链：规格（spec）定义意图 → Harness 保证执行可复现可校验 → 测试与 Agent Review 承担验证 → 交付前校验产物存在且正确。三层缺一层，前面省下的时间都会在返工里还回去。美团的《Agent 评测白皮书》提供了一个佐证：过去三年绝大多数 Agent 项目都死掉了，共性死法是停在 Demo、卡在扩量、说不清业务价值——三者本质上都是评测缺位。

GUIDE 04

用故障注入验证「假设」，而不是验证「服务可用」

当 SQS 队列收发失败时，下游处理会停摆——原因可能是 IAM 配错、网络分区、一次坏部署或瞬时服务事件，但应用侧看到的都一样。你的服务如何应对（对不会成功的快速失败、打开熔断、生产者侧缓冲）决定了这是短暂扰动还是级联故障。AWS 的建议很直接：如果从没在故障下测过这些机制，你就是在依赖假设；用 AWS Fault Injection Service 先把结果跑出来。同类思路还有两个可参考的架构实践：用 DynamoDB lease 协调数百条长连 WebSocket 的归属，worker 挂掉时可让健康 worker 自动接管，避免「一个 worker 失败丢掉 100+ 连接、每条连接 2–3 分钟数据丢失」；以及 Athenahealth 在 2025 年 10 月 us-east-1 区域服务事件后，为单区域的 Terraform Enterprise 做多区域 DR 并用 AWS FIS 验证。三者共同点：把故障当作需要被工程化验证的输入，而不是需要祈祷的意外。

📎 来源：AWS Architecture Blog（SQS + FIS） · DynamoDB leases · Terraform Enterprise 多区域 DR
GUIDE 05

不想重写就用 PyO3 增量换 Rust；顺手关注三个语言/协议更新

InfoQ 的演讲《Accelerating Performance by Incrementally Integrating Rust Into Existing Codebase》讲的是一个很实际的路径：用增量 FFI 重构避免高风险的整体重写，通过 PyO3 把 Python 热点逐个换成 Rust，获得函数级的速度提升、无缝的集成测试，以及可观的基础设施成本下降——而且不需要引入微服务的额外开销。适合「服务跑得动但单点太慢、又不敢停业务重写」的团队。同一批更新里还有三个值得排进 backlog 的变更：CPython 正式把 RISC-V 列为 Tier 3 平台，并继续往 Tier 2 推进，反馈需要 RISC-V 硬件的开发者参与；IETF 发布 RFC 10008，为 HTTP 新增 QUERY 方法——这是 2010 年以来第一个新的标准 HTTP 动词，允许在请求体里传更丰富的查询过滤条件，同时保持可缓存、安全、幂等的语义，直接解决 GET 表达力不足和 POST 语义错配的老问题；以及 Turbopack 的 chunking 策略——Next.js 官方用自家站点的实测数据说明「请求数更少」与「代码量更小」之间存在真实取舍（8 个 chunk 居然比 355 个还重），结论都有数据支撑，值得在调打包配置前先读。

📎 来源：InfoQ（Rust 增量重构） · InfoQ（CPython RISC-V） · InfoQ（RFC 10008 QUERY） · JavaScript 中文周刊 #252
GUIDE 06

Codex 团队的真实经验：维护是一笔「税」，本地开发正在被重新定义

OpenAI Codex 负责人 Tibo Sottiaux 在 The Pragmatic Engineer 的访谈里给了几个值得内化的判断。他说 「Maintenance is a tax」——功能上线是一次性开支，之后的每一次修改维护都是持续账单，而 Coding Agent 正在打掉这笔账，程序员最费时间的维护工作正在被改变。在 OpenAI 内部，新人提问常被反问「你问过 Codex 了吗」。另一个技术细节是 Codex 用 Rust 实现（相关访谈有专门一期讲为什么），而「本地开发是否正在因 Agent 消失」也成了被正式讨论的话题——这些问题背后是同一个变化：当 Agent 能连续数小时自主写代码、跑测试、修 bug，开发者的时间分配、代码库的组织方式、乃至「本地环境」的意义都需要重新设计。
