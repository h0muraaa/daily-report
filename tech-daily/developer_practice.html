Agent = Model + Harness：为什么底层模型相同，Claude Code、Cursor、Codex 表现却截然不同

meng shao 深入分析了 AI 编码工具的核心架构差异。Claude Code、Cursor、Codex 和 Aider 可能使用完全相同的底层模型，但它们的 Agent 行为差异巨大，根本原因在于 "Harness"（驾驭层）的设计不同。Harness 决定了工具如何调用模型、如何管理上下文、如何编排工具链、如何处理错误和重试。这解释了为什么同样是 Claude 3.7 Sonnet，在 Claude Code 和 Cursor 中的表现会有明显差异。理解这一架构分层，有助于开发者在选择工具时做出更理性的决策，也为构建自己的 Agent 系统提供了设计思路。

行业洞察

TypeScript 之父 Anders Hejlsberg 谈 AI 与 Coding 的未来

Delphi、C#、TypeScript 核心设计者 Anders Hejlsberg 分享了他对 AI 编程的深层看法。核心观点：AI 永远不会取代程序员，而是成为加速器。原因在于三点：一是 AI 自身依赖代码而存在——编程语言、编译器、框架、操作系统都需要人去设计；二是 AI 擅长重复模式但不擅长创新，业务逻辑和深层架构决策始终来自人类；三是行业进步来自"洗澡时冒出的疯狂想法"，AI 不会那样工作。他对 "vibe coding" 持高度怀疑态度——代码总得来自某处，并不全由 AI 生成。对初学者的建议：绝对值得学编程。编程语言是 AI 表达自己的方式；不懂代码就无法理解 AI 在生成什么。最常见的错误是停留在语法层而不真正理解变量、数组、数据结构、指针的工作原理。

🔍 深度技术解读

Agentic AI 工作流的可扩展模式

除了上下文工程，我们应该在 Agent 周围投入更多的系统工程精力。一个常被忽视的事实是：Agentic RAG 管道的性能瓶颈几乎从来不是 LLM 调用本身，而是底层的数据平面——预处理、嵌入和向量检索之间的序列化开销，以及分布式服务之间的协调开销。

这篇研究展示了一个典型案例：通过系统层面的优化（而非模型层面的改进），将端到端延迟降低了数量级。关键洞察包括：

  • 数据平面优化优先于模型优化：在大多数生产场景中，数据流管道的效率提升带来的收益远超换用更强的模型
  • 序列化是隐藏杀手：预处理 → 嵌入 → 检索之间的数据转换往往消耗大量时间和内存
  • 分布式协调开销不可忽视：多服务架构中的网络往返和同步点常常是延迟的主要来源
实践建议：在优化 Agent 性能时，先用 profiling 工具定位真正的瓶颈。先用 perf 或 jaeger trace 整个调用链，再决定是否值得升级模型或增加上下文长度。

从"能跑就行"到"能上线"：Granola 工程师的一课

具体踩过的坑：

  • Web Search 看起来只是一行代码的 tool call——直到它爆掉上下文窗口、每次聊天收费 10 便士、专业用户一次会话触发 30+ 次搜索

为什么大应用选择 Web 而非 Native

freeCodeCamp 的一篇文章分析了大型应用（如 Figma、Notion、Slack、VS Code）选择 Web 技术栈而非原生开发的核心原因。这不是技术宗教之争，而是基于实际工程考量的理性选择：

  • 跨平台一致性：一套代码覆盖 Web、Desktop（Electron/Tauri）、Mobile（PWA/Capacitor），维护成本大幅降低
  • 迭代速度：Web 的热更新能力让功能发布周期从天级缩短到小时级
  • 人才池：Web 开发者数量远超任何单一平台的原生开发者
  • 性能边界在移动：WebAssembly 和 WebGPU 正在模糊 Web 与原生的性能边界
选型建议：如果你的应用需要极致的硬件性能（如 3D 游戏、视频编解码）或深度系统集成（如系统级快捷键、文件系统监控），原生仍有优势。但对于大多数生产力工具和内容平台，Web 技术栈已经足够，且生态红利不可忽视。

UI Bug 调试古法：录屏慢放法

Tw93 分享了一个在"古法代码阶段"常用的 UI bug 调试技巧——录屏慢放。核心思路：当遇到 UI 闪动、布局错位或动画异常时，用录屏软件捕捉整个操作过程，然后以 0.25x 或 0.5x 速度回放，定位到出问题的那一帧。找到问题帧后截图给 AI，比打日志和猜测的排查效率高出很多。

这个方法的价值在于：AI 很难直接理解"某个动画中间态出了问题"，但人眼可以通过慢放快速定位异常。将定位结果（截图）作为输入给 AI，AI 就能精准分析原因并提出修复建议。这是人机协作排查的经典范例。

一条命令让 CDN 视频带宽成本降低 90%

转转技术团队分享了一个真实案例：一个 1GB、30 分钟的培训视频推送给 2500 人观看，CDN 监控显示消耗了 120TB 流量——远超理论值。经过排查发现，问题的根源在于 MP4 视频的元数据（moov atom）位于文件尾部。

当浏览器/播放器请求视频时，如果 moov atom 在尾部，播放器必须先下载整个文件才能获取时长、编码等元信息，导致大量不必要的流量消耗。移动端的 seek 行为更是加剧了这个问题。

解决方案极其简单：

ffmpeg -i input.mp4 -movflags faststart -c copy output.mp3

这条命令将 moov atom 从文件尾部移到头部，播放器可以在只下载极小数据量的情况下获取元信息并正常播放。实施后该域名的 CDN 带宽从 120TB 骤降至约 12TB，降幅约 90%。

最佳实践：所有面向 Web 的 MP4 视频，上传 CDN 前都应该执行 -movflags faststart 处理。可以集成到 CI/CD 流水线中自动处理。
