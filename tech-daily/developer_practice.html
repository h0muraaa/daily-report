AGENT60 人公司跑 300 个 Agent：一次模型切换让成本涨了 100 倍

Runlayer 创始工程师 Aiden Sochowski 在 AI Engineer 分享了他们的内部实践：公司约 60 人，但每天有 300 多个 Agent 在跑。他们做的第一件事是在所有 Agent 前面放一个网关，并记录每一个会话与每一次工具调用——在此之前，公司对自己有多少 Agent、它们能访问什么，几乎没有可见性。

有了日志之后暴露的问题相当具体：通过邮件内容实施的提示注入；PR 评审 Agent 被说服批准变更；权限过大的机器人账号；一个被污染的 Agent 影响其他 Agent；以及“vibe coding”出来的 MCP server 反复烧 token。还有一个容易被忽视的运维风险：一次模型切换，让一周内的成本上涨超过 100 倍。

他们的结论是，会话级数据不只是审计材料，更是缩小权限的依据——看清某个 Agent 在一次会话里实际调用了哪些工具，才能把权限从“能访问一切”收窄到“只访问需要的”。这与 Meta 同一天公布的 PrivacyLib 思路一致：把访问控制放在数据访问边界，而不是依赖每个调用方自觉。

MODEL文心 Unlimited OCR 2 开源：任意页数文档解析，峰值 KV 缓存从 47GB 降到 1.77GB

百度发布并开源文心 Unlimited OCR 2，号称首次实现任意页数文档解析，把 OCR 的处理上限从数十页推到“无限”。实测中，模型连续识别 7 部《哈利·波特》共 3600 多页、《三体》全集 1200 多页，在文档长度大幅增加时仍保持精度与效率。

长文档推理的内存账本，与 Agent 的权限边界

把 KV 缓存从 47GB 压到 1.77GB：长文档 OCR 真正要算的是显存账

Unlimited OCR 2 的 SR-SWA 为什么有效，以及自建文档流水线该怎么验证“无限页数”

长文档解析的瓶颈通常不在识别单页，而在“记住前文”。Transformer 推理时，每一页的视觉 token 都会在 KV 缓存里留下记录；页数越多，这份“边读边记的小抄”越厚。在百页级单序列测试中，标准解码把所有页面的视觉缓存同时保留在显存里，峰值达到 47GB——比不少笔记本的整机内存还大，而这还只是 KV 缓存，模型权重与激活另算。Unlimited OCR 2 把这个数字压到 1.77GB，减少约 96%。

// SR-SWA 做了什么

核心机制叫稀疏参考滑动窗口注意力（Sparse Reference Sliding Window Attention，SR-SWA），灵感来自人抄书的过程：抄当前页时主要看当前页，只有需要核对前文或查跨页信息时才回看相关页，而不是每写一个字都把整本书翻一遍。落到模型里分两步：

  • 页面门控（Page Gate）：把每个查询的视觉参考范围从整篇文档缩小到相关页面，同时建模跨页的位置关系，避免“只看当前页”丢失跨页上下文。
  • 视觉 token 桶：在筛出的页面范围内，只把得分最高的视觉 token 桶送入注意力计算，其余稀疏跳过，从而让计算量与页数解耦。

再配合持续解码（continuous decoding），模型可以连续处理超长文档，且单步解码开销不会随文档变长而线性上涨。这是“页数无上限”在工程上成立的前提：不是把窗口调大，而是让每一步只看该看的。

// 自建流水线怎么验证

“峰值 1.77GB”是 KV 缓存口径，不等于整机显存占用，也不代表你的输入（扫描质量、版式、表格密度）会得到相同结果。更靠谱的做法是把显存与延迟当成一等信息记录到每次跑批里，并与现有的“分块 + 拼接”方案做同集对照。下面是最小化的实测骨架：

# 给文档流水线加显存与延迟账本，而不是只看吞吐
import torch, time

torch.cuda.reset_peak_memory_stats()
t0 = time.perf_counter()

result = pipeline.run(pages)          # 你的 OCR / VLM 流水线

elapsed = time.perf_counter() - t0
peak_gb = torch.cuda.max_memory_allocated() / 2**30

print(f"peak_gb={peak_gb:.2f} sec_per_page={elapsed/len(pages):.3f}")

对照时至少覆盖四类样本：纯文本书页、带跨页表格的财报、双栏排版、低质量扫描件。评估指标不要只有字符准确率，还要看跨页表格是否被切断、页眉页脚是否被误合并、页码与目录引用是否对得上。这些恰恰是“分块拼接”最容易出错、而长上下文模型最该赢的地方。

落地建议：① 先估算目标硬件的 KV 预算，再决定单次送入的最大页数，别按“模型说无限”就无限灌；② 把失败重试粒度从“整本重跑”改成“按页/按段重跑”，否则长文档一次失败代价极高；③ 保留分块方案作为降级路径，长文档模型输出异常时可回退；④ 记录 peak_memory_allocated 与每页耗时，作为容量规划输入；⑤ 关注上游对 SGLang 等推理框架的适配，部署方式会直接影响实际收益。

Agent 的权限不该靠自觉：从 300 个 Agent 的事故清单反推网关设计

邮件注入、评审 Agent 被说服、模型切换 100 倍成本——这些都能在网关层拦住

Runlayer 的分享之所以值得细读，是因为它给的不是“最佳实践清单”，而是真实事故清单。60 人的公司跑 300 多个 Agent，在装上网关、记录每个会话与每次工具调用之前，团队对自己有多少 Agent、它们能碰什么数据基本没有概念。可见性一旦建立，问题就变得具体：

事故类型触发路径网关层能做什么
提示注入Agent 读取邮件正文，正文里藏着指令标记不可信输入；对同一会话内的写操作强制人工确认
评审 Agent 被说服PR 评论里嵌入诱导内容，Agent 点了批准评审 Agent 只给建议，批准权限不授予 Agent
权限过大机器人账号能访问超出职责的数据按会话日志收敛工具与数据范围，最小权限
交叉污染一个被污染的 Agent 影响其他 Agent会话隔离；共享记忆写入需审核
MCP server 缺陷随手生成的服务反复调用、烧 token限流、超时、成本预算；上线前代码审查
成本暴涨一次模型切换让周成本涨 100 倍按会话/按 Agent 的成本熔断与告警

这些攻击的共同点在于“跨步骤展开”：单看某一次工具调用可能都合理，但把一次会话串起来看，就能看到数据从不可信输入流向高权限工具。所以只做单点过滤不够，必须有会话级身份与完整调用链。Runlayer 的做法是先记录、再收权——用真实会话数据决定某个 Agent 到底需要哪些工具，而不是一开始就按“可能会用到”授予。

// 网关策略长什么样

下面是示意配置，重点不在具体字段，而在四类约束：工具白名单、不可信输入标记、写操作审批、成本上限。

# 示意：Agent 网关的一层策略，不是某个产品的真实配置
agents:
  pr-reviewer:
    tools: [read_file, list_pr, comment_pr]
    deny: [merge_pr, push]              # 评审 Agent 不给合并权
    approval_required: [comment_pr]
    budget_usd_per_session: 0.50

  inbox-triage:
    tools: [read_email, label_email]
    untrusted_inputs: [email_body]      # 读入即标记不可信
    approval_required: [send_email, forward_email]
    budget_usd_per_session: 0.20

audit:
  log: [session_id, agent, tool, args_hash, tokens, cost]

这份策略能拦住表格里的大部分问题：邮件正文被标为不可信，那么从“读邮件”到“发邮件”的动作就需要人工确认；评审 Agent 没有合并权，被说服也无济于事；每个会话有成本上限，模型切换导致的价格变化会立刻触发熔断而不是等到月底账单。真正难的是运营：权限要随职责持续收敛，MCP server 要像生产服务一样做代码审查与版本固定，日志要能支撑事后追溯。

上线前的最小检查单：① 每个 Agent 有独立身份，不共用人类账号；② 所有工具调用经网关，记录参数哈希与成本；③ 不可信输入（邮件、网页、PR 评论、外部文档）显式标记；④ 写操作默认需要审批，读操作按数据域收窄；⑤ 按会话设成本与调用次数上限；⑥ MCP server 固定版本并做代码审查；⑦ 用真实注入样本做一次红队演练。

来源：AI Engineer · 300 Agents, 60 People: How We Secured Our Own AI Agents · Engineering at Meta · PrivacyLib

tsrs
用 Rust 重写 TypeScript 类型检查的实验中坚

Cloudflare、VoidZero 与 Max Schwenk 推出的实验性 Rust 版 TypeScript 编译器，TypeScript 团队参与共建。官方称对比 TypeScript 7.0 检查速度最高 8 倍、内存减少 70%，但与 7.1 beta 对照时只有 2.7 倍，说明收益随版本与代码库差异很大。

适合先在 CI 里做“只检查、不开发”的加速尝试：它没有 watch 模式与语言服务器，类型错误时退出码为 2（而非 tsc 的 1），接入脚本时要注意。先在单体大仓库跑一次全量基准，再决定是否作为并行门禁，而不是直接替换现有工具链。

值得注意的是位级确定性：相同请求不受并发、批处理与 GPU 数量影响，输出概率逐位一致，7 个评测集共 12351 次决策上准确率 92.94%（BF16 原始精度 92.97%）。如果你的场景是分类、打分或路由而非生成，值得拿自己的评测集复现一遍。

六条可以排进本周工单的动作

01给 Next.js 预留 11 月 3 日的安全升级窗口

先把“有哪些 Next.js 服务、分别什么版本、谁负责”列清楚，再决定升级路径。安全版本发布当天，公告会给出影响范围与修复版本，提前准备好预览环境比当天现搭要快得多。

  • 梳理所有仓库的 next 版本与锁文件，确认没有被 overrides 钉死。
  • 确认构建产物与镜像会随依赖重建，避免只改版本号不重新打包。
  • 在预览环境跑一次现有测试与关键路径回归，记录基线。
参考：Next.js Blog · Upcoming November Security Release

02Python 类型检查：接受“多 checker 并存”，但把版本写进 CI

调查显示一半用户同时使用多个 checker，且不同 checker 的结论并不总是一致（多 checker 用户里 33.3% 报告过不一致，多 checker 用户中为 42.7%）。与其争论“哪个才对”，不如把两者都当信号：主 checker 做门禁，副 checker 做增量提示。

  • 在 CI 里固定 checker 与插件版本，避免升级后门禁结果漂移。
  • 优先补齐第三方库的类型信息（65.1% 的首要痛点），给内部公共库发布 stub 或 py.typed。
  • 如果已用 AI 写类型，确认它是否真的调用了 checker（仅 24.4% 如此），并在错误修复环节保留人工复核。
参考：Engineering at Meta · Python Typing Survey 2026

03把 AI 代码评审当“信号”而不是“门禁”

Laurie Voss 用四款 AI 代码审查工具检查同一份代码，它们都找出了问题，但指出的位置并不相同。这意味着任何单一工具的“通过”都不能作为合并依据；Atlassian 的数据也提示，管理者花在修正 AI 产出上的时间反而更多。评审流程要按“多信号 + 人工判定”设计。

  • 至少运行两类检查：静态规则类与语义评审类，输出分歧单独列出。
  • 用变更前置时间、评审排队时长、回滚率衡量收益，而不是“生成了多少行”。
  • 别把新人练手的小工单全部交给 Agent，资深工程师的成长路径需要保留。
参考：InfoQ · Atlassian State of Developer Experience 2026 · 51CTO · npm 创始人谈 AI 改写工程师工作

04Agent 上线前，先过一遍网关与成本熔断

Runlayer 的清单里，最容易被低估的是成本：一次模型切换就让周成本上涨超过 100 倍。权限问题往往在事故后才被发现，而成本问题会直接体现在账单上，两者都应该在网关层设硬约束。

  • 每个 Agent 独立身份；写操作默认需要审批，读操作按数据域收窄。
  • 记录会话 ID、工具名、参数哈希、token 与成本，作为收敛权限的依据。
  • 给每个会话设预算与调用次数上限，超限熔断并告警。
参考：AI Engineer · 300 Agents, 60 People

05训练与批处理任务：用 SOCI 把镜像下载移出关键路径

AWS 为 SageMaker AI 的训练与处理任务推出 Seekable OCI（SOCI）索引：容器镜像改为懒加载，只取启动所需文件，其余在代码运行时后台流式传输，任务从“分钟级启动”变为“秒级启动”。对深度学习镜像来说，下载时间既是计费时间，也是团队等待时间。

  • 给常用基础镜像建 SOCI 索引，并指向预索引的 AWS 深度学习镜像。
  • 记录任务启动的 p50/p95 与计费分钟数，对比启用前后差异。
  • 镜像层不要过度拆分，懒加载收益取决于启动路径所需文件的比例。
参考：AWS ML Blog · Announcing SOCI-indexed images for faster SageMaker AI jobs

06tsrs 只做并行基准，不要急着替换 tsc

8 倍与 2.7 倍的差距说明基准高度依赖版本与代码库。更稳妥的用法是在 CI 里并行跑一次全量检查，记录耗时与内存，作为未来迁移的决策依据；日常开发仍用支持 watch 与 LSP 的现有工具。

  • 选一个真实的大仓库，分别用 tsc 与 tsrs 全量检查，记录 wall time 与峰值内存。
  • 注意退出码差异：tsrs 类型错误时返回 2，脚本判断要相应调整。
  • 没有 watch/LSP 意味着编辑器体验不变，不要向团队承诺“更快的类型提示”。
参考：InfoQ · Cloudflare and VoidZero Introduce tsrs
