Vercel Services：把前后端真正装进一个项目

Vercel Services 让开发者可以在同一个 Vercel Project 里运行多种框架，例如 Next.js 前端 + FastAPI/Express 后端。核心收益是原子化部署：前后端共享一次构建、一次回滚、同一个预览 URL，并通过内部网络互相通信，不再需要在不同云之间拼接基础设施。对于习惯全栈开发但不想自己维护容器编排的团队，这意味着可以用 `vc dev` 本地启动完整栈，再一键部署到生产。

[来源: Vercel News]

Claude Sonnet 5 发布：更像一个能自主干活的编码搭档

Anthropic 发布 Claude Sonnet 5，官方将其定位为迄今最具 agentic 能力的 Sonnet 模型。它能在没有持续人工干预的情况下制定计划、调用浏览器和终端等工具并自主执行，水平此前往往需要更大的 Opus 模型才能达到。对开发者而言，这意味着在代码迁移、批量重构和复杂调试等任务上，可以用 Sonnet 的价格获得接近旗舰模型的完成度，同时 Vercel AI Gateway 等平台已同步上线。

[来源: Claude(@claudeai)]

Google ADK Go 2.0：用图编排构建可靠的多 Agent 应用

Google 的 Agent Development Kit (ADK) for Go 升级到 2.0，首次引入原生的图化工作流引擎，帮助开发者把复杂多 Agent 应用表达为节点和边。新版本内置了 human-in-the-loop 编排、用普通 Go 代码实现的动态执行，以及指数退避等自动韧性机制。单 Agent 和复杂图现在跑在同一运行时上，telemetry 和部署模型也更加统一，适合已经在使用 Go 技术栈的团队。

[来源: Google Developers Blog]

AWS Lambda MicroVMs：给 Agent 和用户代码加一道硬件级隔离

AWS 推出 Lambda MicroVMs，这是一种新的无服务器计算原语：每个用户会话或 AI Agent 在独立的 Firecracker 虚拟机里运行，具备硬件级隔离、基于快照的秒级冷启动，以及最长 8 小时的状态保持。它把 Lambda 的隔离粒度从函数调用下沉到会话/Agent 级别，适合执行不可信或高风险的代码。不过 Reddit 上的成本测算显示，最小配置每天约 3.03 美元，大约是 Fargate Spot 的 9 倍，选型时需要权衡隔离性与成本。

GitHub Copilot 以原生 Agent 身份进入 JetBrains IDE

JetBrains 与 GitHub 合作，把 Copilot 从 ACP Registry 中的第三方扩展变成 IDE 内置的 Agent。现在可以直接在 Rider、IntelliJ IDEA、PyCharm 等 JetBrains IDE 的 Agent 选择器里调用 Copilot，获得更稳定、经过深度测试的体验。对习惯 JetBrains 工具链的开发者来说，这意味着不必在 IDE 和单独的 Copilot 客户端之间切换，Agent 交互与代码补全、重构等工作流更顺滑。

[来源: The JetBrains Blog]

.NET 8 / 9 将于 2026 年 11 月结束支持

微软宣布 .NET 8 和 .NET 9 将在 2026 年 11 月 10 日同时停止支持，此后不再提供安全补丁、服务更新或技术支持。虽然 .NET 8 本身是 LTS 版本，但 .NET 9 的同步退役让仍在 9 上的团队需要特别注意迁移窗口。官方建议升级到 .NET 10（LTS，支持至 2028 年 11 月），以获得持续的安全更新。这条信息对维护 .NET 后端或桌面应用的团队是明确的升级提醒。

React Native Windows v0.84：输入处理与主题适配再进一步

React Native Windows 0.84 与 React Native 0.84.1 对齐发布，主要改进集中在 Fabric 组件的输入处理、主题感知默认值和命中测试语义。新版本为标准点击事件引入了 `onClick` 和 `onAuxClick`，并支持命令式焦点控制。需要留意的是，0.84 要求 Visual Studio 2026，升级前需确认构建环境。

AI Agent 的安全防线：别只关注提示词，还要看 ReAct 循环

Sriram Madapusi Vasudevan 在 QCon 风格的分享中指出，AI 加速开发的最大风险不在模型本身，而在 Agent 的 ReAct 循环：上下文、推理和工具执行三个环节都可能被污染或劫持。他提出的防护思路包括防御纵深、用 LLM-as-a-judge 作为批评家持续审计输出，以及用 MAESTRO 威胁建模梳理攻击面。对开发者来说，这提供了一个可落地的检查清单：除了写好系统提示词，还要给 Agent 的内存、工具和推理边界加护栏。

Java 实时系统的事件驱动架构：80k BHCC 案例里的隐藏取舍

这篇实战文章基于一个处理 80k BHCC（忙时呼叫量）、覆盖 10k 客服坐席的 Java/Kafka 联络中心平台，剖析了事件驱动架构在真实生产中的坑：状态管理复杂、分区上限、重复消费、JVM 调优和级联消费者故障。作者不仅列出问题，还给出了用 Redis 支撑的针对性模式，比如幂等键、状态快照和限流。对于在高并发 Java 系统里引入 Kafka 的团队，这是比"事件驱动能扩展"更有价值的反面教材。

给 Agent 写代码的能力越强，安全越不能松懈

LangChain 团队近期分享了他们在让 Agent 生成并执行代码时遇到的安全挑战。能力增强的同时，不可信代码的执行、沙箱逃逸和工具滥用风险同步上升。文章建议的做法包括：限制执行环境、使用容器或临时虚拟机、对 Agent 生成的代码做静态检查，以及最小权限原则。这与 AWS Lambda MicroVMs 的发布形成呼应：Agent 时代，隔离和审计应成为默认设计，而不是事后补丁。
