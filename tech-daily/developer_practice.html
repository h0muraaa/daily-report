深度技术解读

1. 从“一个聊天框”到“多 Agent 协作”：多 Agent 编程正成为工程现实

今年的主线已经很明显：AI 编程工具不再只是帮你补全一行代码，而是像一支小队一样分工处理整个代码库。GitHub Copilot 的并行会话、Rider / ReSharper 的 Agent Skills、Trae IDE 的 multi-agent 协作，都是为了让一个 Agent 做测试、一个做重构、一个写业务代码成为可能。

为什么现在需要多 Agent？ 单个大模型在长上下文、多任务切换时容易“顾此失彼”。把任务拆成多个专注的小 Agent，每个只负责一个子目标，能显著降低上下文噪声，也更容易做权限隔离。例如 monday.com 的实践中，每个 Agent 提交的 PR 都要进入统一的人类审核与置信度评分流程，最终靠“confidence-scored merge”逐步接近自治。

对开发者的建议： 如果你的团队准备引入多 Agent，不要一开始就让它们直接提交主分支。建议先从以下三层落地：

  • 任务拆分：用主 Agent 做需求拆解，子 Agent 负责测试、文档、重构或模块开发，避免所有改动堆在一个会话里。
  • 共享上下文：建立统一的工具注册表（Tool Registry）和项目知识库，避免每个 Agent 都重新“发现”数据源和 API 规范。
  • 人工守门：Agent 的输出必须经过 CI 流水线、代码审查和自动化测试，而不是“跑通就合并”。

InfoQ 演讲中提到的“virtual tools”和中间协议层也值得参考：把 Agent 的接口映射、schema 投影和运行时污点追踪（taint tracking）封装成可版本化的组件，可以在不拖慢速度的前提下降低数据泄露风险。

2. 为什么 95% 的 AI 原型死在生产门口？

Google 的文章指出， weekend AI 项目可以在几小时内从 0 到 1，但进入企业环境后却只有 5% 能真正上线。问题往往不是模型不够聪明，而是原型缺乏企业网络兼容性、错误处理、可观测性和治理机制。

生产化的核心不是“让 AI 更聪明”，而是“让 AI 系统更可靠”。 以 Pelago 两周内上线的 serverless AI 助手为例，他们用 Amazon Bedrock + Lambda 构建事件驱动架构，并保留了 care team 的人类审核环节。 healthcare 场景下的 human-in-the-loop 不是妥协，而是对高风险的必要控制。

落到工程实践上，建议大家把 AI 应用当作分布式服务来管理：

  • 可观测性：记录每个 Agent 的输入输出、工具调用、失败路径和 token 消耗，方便复盘和调优。
  • 护栏与重试：对工具调用、外部 API 和代码生成结果加输入校验、超时和重试策略，避免级联错误。
  • 评估流水线：把“任务完成率”作为 CI 指标，用真实数据集跑回归测试，而不是只看模型在本地跑不跑得通。
  • 安全左移：参考阿里 Qoder Security 的思路，在 Agent 生成代码、依赖构建和发布产物阶段分别做扫描，防止 source map 或敏感文件被误打包。

实践指南

把 AI 原型稳定推向生产的 5 个步骤

  1. 先定义“完成”：不只是功能跑通，而是明确任务完成率、延迟、错误率和人工介入比例。把这些指标写进需求文档。
  2. 建立沙箱评估：用真实输入数据构建回归测试集，每次模型或 prompt 变更后都跑一遍，避免“本地 magic，线上 crash”。
  3. 加入护栏代码：对 LLM 输出做结构化校验、敏感信息过滤、工具调用权限控制。例如： 
    const result = await agent.run(userQuery);
// 验证输出 schema、过滤危险字符、限制可访问路径
validateSchema(result);
sanitizePaths(result.files);
  4. 人类审核渐进放权：初期所有 Agent 输出必须人工 review；当置信度评分和测试通过率稳定后，再逐步放开低风险操作。
  5. 持续监控与回滚：把 Agent 的调用链接入现有的 tracing 和日志系统，保留快速回滚到上一版 prompt 或模型的能力。

多 Agent 项目的最小结构建议

project/
├── agents/
│   ├── planner-agent/      # 需求拆解
│   ├── test-agent/         # 测试生成
│   └── refactor-agent/     # 重构与优化
├── shared/
│   ├── tool-registry.json  # 可用工具及 schema
│   └── context-store/      # 共享记忆与项目知识
├── ci/
│   └── agent-eval.yml      # Agent 输出评估流水线
└── guardrails/
    └── policy.ts           # 权限与输入输出策略

这个结构不是唯一答案，但它体现了“把 Agent 当软件工程对象管理”的核心思路：拆分职责、共享上下文、统一治理、可评估、可回滚。
