Codex 内存占用优化：从 5.7GB 降到 3.4–4GB

有开发者总结了 Codex 重度用户遇到的内存膨胀问题：日常 6GB 起步，高负载时容易卡死。核心原因是后台积累了多套 MCP 工具进程，仅关闭窗口不一定会退出后台进程。最有效的优化是彻底退出并重启 Codex，然后默认关闭高占用 MCP（XcodeBuildMCP 约 0.84GB、Blender MCP 约 0.3GB、安全扫描和数据分析类工具），只在需要时临时启用。保持 active 任务控制在 1–2 个，每隔几天完整退出一次，常态内存可以从 5.7GB 降到 3.4–4GB。

[来源: Berryxia.AI (@berryxia)]

Claude Code 团队谈 /loop、/goal 和 workflows 的用法

Claude Code 团队 Thariq Nazeem 在播客中分享了三种长时运行能力的设计差异：/loop 让 Agent 按固定节奏持续检查、/goal 让 Agent 朝目标自主推进、workflows 则是把重复模式固化成可复用流程。他还提到，随着模型变强，Claude Code 的系统 Prompt 已经缩减了 80%，因为模型需要更少的约束和示例。对开发者来说，这意味着在使用 AI 编程助手时，应该更关注如何清晰地表达目标和验收标准，而不是堆砌详细的执行步骤。

Lyft 如何构建真正有用的 Agent 评估：对抗式用户模拟器

Lyft 的分享指出，很多 Agent 在离线评测中得分 90%，但一上线就暴露出评测没覆盖到的失败模式，因为评测里的“用户”是听起来不像真实用户的通用 LLM。Lyft 的做法是构建对抗式用户模拟器：用真实客服对话微调一个 LLM，让它能扮演沮丧、困惑、故意刁难的乘客和司机。这个模拟器找到了合成测试集没发现的回归问题。对开发者来说，这是评估 Agent 时的一个重要提醒：评测集必须反映真实用户的分布，而不是只追求高分。

接受“代码即弃件”的新常态

Zara Zhang 提出一个值得开发者思考的观察：在 AI 时代，越来越多的代码或软件可能变成一次性使用的——比如为调试设计临时弹出的设计 playground、为理解代码生成的 HTML 页面、为排查问题搭建的临时 dashboard。这些代码用完即弃，价值在于加速当下的判断，而不是长期维护。对团队来说，这意味着需要区分“生产代码”和“探索性代码”的治理标准，不要让临时脚本的维护成本侵蚀核心系统的稳定性。
