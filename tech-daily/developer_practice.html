🔍 AGENTS.md 的悖论：更多上下文 ≠ 更好性能

Philipp Schmid 分享的研究揭示了一个反直觉的发现：LLM 生成的 AGENTS.md 上下文文件实际上会降低任务成功率 0.5-2%，同时推理成本增加超过 20%。

核心发现：
  • 自动生成的上下文文件使成功率下降约 3%，推理成本增加超 20%
  • 人工编写的文件仅略微提升基准性能（约 4%）
  • 更强的模型并不能生成更好的上下文文件
  • 代码库概览并不会帮助 Agent 更快导航

技术解读：这个发现对"上下文工程"提出了根本性质疑。当前流行的做法是向 Agent 灌输尽可能多的项目信息，但研究表明这可能导致"指令过载"。Agent 会过度遵循这些指令，使用指定工具的频率增加 1.6-2.5 倍，但这反而损害整体性能，需要多消耗 22% 的推理 token。

实践建议：

  • WHAT：说明技术栈、项目结构、各部分职责——这对 Agent 理解边界至关重要
  • WHEN：明确何时使用特定工具/模式——减少错误触发
  • FOCUS：避免冗余文档，保持精简——不要让 Agent 在噪声中寻找信号

"Less is More" — 在 AI 时代，约束比无限上下文更有价值。

🔍 多 Agent 工作流的工程化挑战

GitHub 博客分享了他们在构建多 Agent 系统时的关键洞察：当 Agent 开始处理相关任务时，如果没有明确的指令、数据格式和接口定义，事情不会按预期发展。

典型失败模式：

  • 一个 Agent 关闭另一个 Agent 刚打开的 Issue
  • Agent 提交了未通过下游检查的代码变更
  • Agent 对状态、顺序和验证做出隐性假设

工程化解决方案：GitHub 在 Copilot 和内部自动化系统中的经验表明，成功的多 Agent 架构需要：

  1. 显式状态管理：每个 Agent 必须清楚了解当前系统状态
  2. 标准化接口：Agent 间的通信需要严格的数据格式约定
  3. 顺序约束：定义清晰的执行顺序和依赖关系
  4. 验证机制：每个 Agent 的输出需要经过明确的验证步骤
