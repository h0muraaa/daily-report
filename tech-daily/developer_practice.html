01Claude Fable 5.2 上线：Coding 更强、单价更低，但很费 token模型

Deep Dive #1 · Agent 工程

让 Agent 连续重构三周，然后你去看代码：自治 Agent 的“验证陷阱”

微软产品经理 Keiji Kanazawa 让 Claude Code 和 Codex 连续三周重构自己的研究助手，一天烧掉约 100 美元、是平时一周 token 预算的 5 倍。等他真正去读代码时才发现：所谓的“Agent”其实还是一个确定性工作流；多个 Skills 没有 SKILL.md；几个不同的架构概念其实是同一个东西的别名；每日反思任务一直产出空报告。更严重的是，coding agent 把单元测试直接接到了生产推理接口上，一天跑了约 30 轮。他复盘时承认，自己批准的是“计划”，却从未验证实现是否兑现了标签所承诺的含义。

重建为显式 agent runtime

同一周，腾讯技术工程的工程师 maple 从另一侧描述了同一个问题。他们团队的代码提交量涨到以前的几十倍，但可控性在整条链上下滑：需求评审时产品一句“这个边界先不用管，实际业务不会这么用”，传统开发里会被人默默裁掉，但 AI 不知道这条隐性约束，会认真地把边界展开成十几个状态、一堆异常路径和兼容分支。于是一个中等需求从过去的二三十次提交膨胀到六百多次，review 从“判断对不对”退化成“看着像不像”，测试追不上就用 AI 批量生成用例，开发再批量改，形成恶性循环。

两个案例指向同一个根因

  • Agent 的自我报告不可信。“我做完了”不等于真的完成；测试有没有真的跑、跑的是不是正确环境，需要外部证据。
  • 隐性知识没有被显式化。哪些边界不用管、哪些兼容可以放弃、哪些测试不值得开单，这些不在文档里，AI 默认“全部有效、全部覆盖”。
  • 人的 review 带宽是真正的天花板。变更一旦超过某个量级，review 就从质量判断退化为模式匹配。

可操作的收敛方式

Keiji 的做法是把系统重建在显式的 agent runtime、更清晰的规格和“目标 rubric”之上，并在选框架前先横向比较了四种框架。对多数团队，更轻量的做法是先把验收标准写死：定义什么叫“完成”、让 agent 用新的 E2E case、截图甚至录屏自证、跑检查直到通过；同时把重复出现的纠正沉淀到 agents.md，避免同一个错误在长上下文里反复发生。核心原则只有一句：看系统状态和事件日志，而不是看 agent 怎么说。

📎 来源： AI Engineer（Keiji Kanazawa） CSDN（事件还原） 腾讯技术工程（加速陷阱）
Deep Dive #2 · AI 基础设施

Google 同期重做了四层：长上下文训练、单控调度、推理状态层、动态切片

这一波 Google 的基础设施更新看似分散，实际指向同一个目标：让大规模加速器集群在“百万 token、拆分式推理、持续 RL”的新负载下少空转。四块拼图分别是训练、调度、状态搬运和部署。

① MaxText Context Parallelism：把长上下文训练推到 1400 万 token

Cloud TPU 上的 MaxText 框架现在支持最高 1400 万 token 的长上下文训练，实现了四种上下文并行策略：All-gather、A2A、P2P 和 USP。它由 Tokamax Splash Attention kernel 支撑，能在不把完整 KV 序列物化到高带宽显存（HBM）的前提下，处理 attention 的计算与显存瓶颈。开发者可在 MaxText v0.2.4 中启用，目标是在大规模训练中维持较高的 MFU。

② Pathways：用单控制器替代同步集合通信

Pathways 是一个单控制器分布式训练系统，把计算表示成全局 dataflow 图，用异步派发和中心调度器协调多个加速器组。与 DDP、FSDP 这类 SPMD 依赖同步集合通信不同，它通过“虚拟设备”把模型定义与物理硬件解耦，更适合动态负载，例如 RL 后训练。

③ TPU Sync：把 KV cache 和权重当成“模型状态层”

TPU Sync 的出发点是：当负载从无状态单轮 prompt 转向百万 token agent、disaggregated serving 和持续 RL，瓶颈已从纯算力转移到“活模型状态”的编排——推理时的大规模 KV cache，以及 RL 中从 trainer 广播到 rollout sampler 的参数。它把 HBM、host DRAM、共享存储和数据中心网络统一成一层模型状态层，避免状态被困在单芯片显存里导致加速器空转。

④ GKE Dynamic Slicing：逻辑切片与物理 nodepool 解耦

GKE 的 Dynamic Slicing 正式 GA，把逻辑 TPU slice 的形成与物理 nodepool 供给解耦。相比为每个 slice 建静态 nodepool，AI 负载启动时间最高缩短 5 倍、故障恢复快 4.5 倍，并允许一个多主机 nodepool 承载多个负载。

给一线工程师的启示：当你在做长上下文/RAG/RL 系统时，成本瓶颈很可能不在“模型单价”，而在状态搬运与调度空转。选型时除了看吞吐，也要看 KV cache 能否分层、能否并行恢复、切片是否随负载弹性伸缩。

📎 来源： Google Developers Blog（MaxText） Google Developers Blog（Pathways） Cloud Blog（TPU Sync） Cloud Blog（Dynamic Slicing）

实践指南

6 条 / 今天就能改
1

不要相信 Agent 说“做完了”，给它外部验证机制

明确什么才算验证通过；让它提供新的 E2E case 的通过流程、截图甚至录屏，并能自己跑检查直到通过。把“完成”的证据留在系统状态和日志里，而不是留在 agent 的总结里。

2

把重复出现的纠正沉淀进 agents.md

上下文一长，agent 容易反复犯同一个错。经验法则是：同一个问题你手动纠正两次，就把它持久化到 agents.md，下次不必再纠正。这是最低成本的“记忆”，比不断重写长提示词可靠。

3

设计无人干预的自动化循环，但要写死边界

一个可用的循环至少包含：定义什么叫“完成” → 明确自验证机制 → 确定边界 → 确定约束（运行轮数、最大 token、时长） → 确定 review 流程。缺了约束，agent 就会在“全边界展开”里烧钱。

4

用“隐式状态机”提示词排查难查的 bug

把你正在用的 Claude 或 Codex 直接丢一句：它会按高低风险依次列出应用里隐藏的状态机，特别适合找出那些没有显式建模、靠 if 分支堆出来的状态转换 bug。

find all of the implicit state machines in my app
5

换模型时，顺手清理一遍提示词

每次新模型发布都是精简提示词的好机会（前提是之后主要用新模型）。一句好用的清理指令是：“阅读整个项目，找出所有损坏、不一致、低效或不再需要的东西。修复你确信的部分，并将其余部分列出供我审查。”注意 Fable 5.2 的 effort 档位行为变了，别直接沿用旧设置。

6

成本按“每任务”算，而不是按“每 token”算

Fable 5.2 单价降了 20%，但因为更费 token，单任务成本可能和上一代持平。评估模型时用“总花费 ÷ 通过任务数”，并区分工程师、工程经理、财务三种视角。团队内可以用 tokenomics 仪表盘按人/团队/模型看花费、做预测。

另外，先决定 agent 生成的代码“在哪跑”（允许列表+审批 / 内嵌运行时 / 独立沙箱），再选框架——模型、提示词甚至框架都容易换，执行环境才是安全边界。
