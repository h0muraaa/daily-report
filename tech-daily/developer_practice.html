VercelAPIMCP

AOx Alpha 实测：传闻 80% 的 DeepSWE 通过率是错的，真实 58.4%——但多模态/WebGL 生成确实惊艳

基准实测DeepSWE多模态

Ox Alpha 上线后社区很快进入实测环节。Berryxia 在 ox-alpha 上跑完了完整 113 项 DeepSWE 基准，指出此前流传的"约 80% 通过率"完全不实，实际结果是 58.4%，与 Claude Opus 4.8 的 59% 几乎打平。这个数字放在"1M 上下文 + 13 万输出 + 免费"的定位下其实是相当能打的长 Agent 模型——DeepSWE 是综合软件工程基准，能摸到 Opus 4.8 的水平，说明它不只是"上下文大"。更让人意外的是多模态侧的演示：归藏给 Ox Alpha 一张图片，让它用 WebGL 还原这个网页，它真的做出了 3D 玻璃材质的质感和透视，连文字位置、排版细节都和原图一致，动态版本还能交互；和 DeepSeek-V4-Flash-Vision-EXP、Claude Fable 5 同题对比时，Ox Alpha 在代码还原上表现突出。至于它到底是谁——谷歌的人疯狂暗示"是我们"，但智谱血缘论、小米 MiMo V3、腾讯混元的猜测也都没被证伪。对开发者而言，一个神秘、免费、能写代码又能做前端还原的 1M 上下文模型，值得放进日常编码工具链里实测一轮。

BNetflix 的 LLM 推理平台实践：Triton 管服务、vLLM 管推理，版本兼容是最大的坑

推理平台TritonvLLM

Netflix 公开了把 LLM 推理引入内部服务平台的生产经验，核心是把"模型周边"和"推理本身"拆给两个引擎。整个平台基于 Netflix 现有的 JVM 服务层构建，路由、特征获取、候选生成、后处理与日志仍由它负责；小模型直接在 CPU 进程内跑，大请求委托给 MSS，由 Triton 负责模型加载、批处理、GPU 调度和多框架服务。GPU 路径里 Netflix 选择 vLLM 来满足运营适配性与可扩展性，但保留 Triton 的模型管理与调度职责——即 Triton 负责服务环境，vLLM 负责执行推理并提供自定义扩展点。文章里有两个特别实用的踩坑点：一是 Triton 与 vLLM 版本不匹配会导致部署无法加载，必须一起测试并固定兼容版本；二是 vLLM 对 Hugging Face 的兼容性对部分 Netflix 自研模型不足，需要走 vLLM 扩展点实现自定义架构与解码行为。最后它比较了 Triton 的 Python backend 与 vLLM backend 两种打包方式。对任何自建 LLM 推理服务的团队，这套"双引擎分工 + 版本锁定 + 扩展点兜底"的架构是很有价值的参考。

# 实践指南 (Best Practices)

01Codex 省钱教程：主模型负责想清楚，便宜模型负责把事情做完

成本优化Codex模型路由

Datawhale 的文章拆解了 Codex 背后的模型调用链：一次任务并不只调一个模型，主对话、代码 Review、子 Agent、上下文压缩承担不同工作，而这些环节的模型是可以单独配置的——配置一次，之后每个任务都按这套"默认分工"运行，在后台把成本降下来。关键分工：主模型是大脑，负责理解需求、规划、协调执行，判断错了后面全跑偏，不能省太狠；子 Agent 负责写代码、改文件、跑测试，任务已拆得比较清楚，不需要和主模型同等的推理能力；Review 模型检查代码、找问题，大多数情况下可以用便宜一档的模型。唯一例外是 Compact（上下文过长时的压缩），目前不能单独指定模型，消耗仍跟随主模型。核心结论一句话：好模型负责想清楚，便宜模型负责把事情做完。

📎 [来源: Datawhale] Codex 省钱教程：模型调用链配置

02吴恩达 AI 工程技能图谱第一篇：构建和部署 AI 应用的六项子技能

AI 工程技能图谱Agent

吴恩达 AI Engineering Skills Map 系列开始逐篇展开，第一篇讲"构建与部署 AI 应用"。核心论点是 AI 应用的本质区别在于"输出不可预测"——传统软件输出可预先确定，AI 应用不行，因此 AI 工程是高度迭代的，靠"构建 → 观察 → 决定下一步"的循环，能否在每步聪明地决定下一步，决定了能否用"不可靠的 AI 组件"造出"可靠的软件系统"。六项子技能：1) LLM 基础——理解 tokenization 与生成机制，掌握多模态使用时机、context window 取舍、缓存命中、reasoning effort、采样参数、tool calling；2) 用数据为模型提供 Grounding——RAG 只是早期尝试，要判断什么放 prompt、什么按需检索，选向量索引/知识图谱/结构化语义层，工程化数据管道保持数据干净新鲜；3) 构建 Agentic 系统——从预定义 LLM 调用序列到 Agent harness 反复自决下一步，决定串行/并行、何时用代码何时用 LLM、带 fallback。这是当前 Agent 工程师最值得对照自检的一份技能清单。

03AI evals 的正确姿势：从真实数据出发，让 Agent 帮你归类而不是发明

评测EvalsClaude Code

Peter Yang 的新一期播客请到了 AI evals 领域最有名的 Shreya 和 Hamel，他们教过 4500+ 工程师和 PM 做评测。核心方法论没有变："先从真实数据出发"，变了的是"让 agent 帮你以更聪明的方式看数据"。他们现场审计了 Peter 为 creator skills 建的 evals，并演示了一个免费的 skill，可以直接在 Claude Code 或 Codex 里从你的反馈构建可复用的 evals。两个关键判断："Bottom-up evals 来自看大量样本输出并把它们变成评测标准，AI 在这方面很差，这全靠你"；"Agent 的职责不是发明新反馈，而是帮你把反馈分组、蒸馏成可执行的评分标准"——也就是 agent 做归纳与整理，标准定义与判断仍由人来定。

04长文档 RAG 的新趋势：轻量解析一遍 + 按需 VLM 精读一遍

RAGVLM文档处理

LlamaIndex 创始人 Jerry Liu 总结了当前 Agent harness（Codex、Cowork 等）处理文档型知识工作的最新 RAG 做法：两遍式处理。第一遍用免费/开源的轻量文档解析工具，廉价地扫过 10–1000 个文件，让 Agent 先通过 grep、语义检索找到相关子集；第二遍才是"just-in-time"的 VLM 精读——找到相关页后，截图文档调用自己的 VLM（或写代码）去解剖这些页面。为什么不能只依赖 VLM OCR？因为对海量临时客户文件全程 OCR 又慢又贵。他另一条实测也印证了这一点：在 schema-guided 的复杂文档抽取上，他们对比了 Claude Code、Codex、专门的 OCR 工具（含 LlamaParse）和裸 VLM——短文档时专用 OCR 工具成本只是 coding agent 的零头、准确率持平或更高；但长文档时 coding agent 明显更接近成本/准确率的 Pareto 曲线，因为复杂抽取本质是推理任务，而 coding agent 就是泛化推理 harness，还有更多空间用分页、并行等工具手段。

05调试新姿势：遇到 Bug 时，让另一个 Agent 并行去 GitHub 搜参考实现

调试AgentGitHub

Suhail 分享了一条最近帮他省了很多痛苦的提示词："Moving forward, when you encounter a bug or issue, search GitHub PRs, issues with another agent in parallel to see if you can find a reference solution."——遇到 Bug 时，并行开一个 Agent 去搜 GitHub 的 PR 和 issue，看有没有参考解法。他由此感慨：GitHub 正在成为 Agent 之间"彼此交流"的主要场所。对正在排查诡异 Bug 的开发者，与其自己翻 issue，不如把它变成 Agent 的并行任务；同类思路还包括 Boris Cherny 的"用 Opus 做 hill climbing"——把任何"用 profiler + 数据集迭代 X 直到达到 Y"的问题（优化 CPU/内存、优化 CI 时间、提升帧率、降低延迟）交给 Opus，社区普遍认为这条路径被严重低估了。

06让 Agent 抓取"抓不到"的网页：冒充官方 AI 爬虫身份

网页抓取UAAgents.md

一条被广泛转发的免费技巧：让 Agent 抓网页时获取更多信息，办法是把网站请求身份模拟成 OpenAI、xAI 等官方 AI 公司的爬虫。实测用抖音视频验证——普通 curl 请求完全抓不到相关内容，但冒充官方 AI 爬虫 UA（如 OAI-SearchBot、Claude-User、Bytespider）就能拿到更完整且更 AI 友好的数据。推荐直接写进你的 Agents.md："当抓取公开网页时，如果默认 curl 得到空白或明显不完整的内容，请尝试使用搜索/AI 爬虫 UA 重新请求以尝试获取完整信息"。对做 RAG、网页抓取、Agent 数据采集的开发者，这是一行成本几乎为零但收益明显的配置。
