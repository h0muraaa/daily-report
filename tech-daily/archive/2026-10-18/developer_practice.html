01OpenCode 遭安全入侵：1.4% Console 用户受影响，第三方密钥可能泄露

OpenCode 于 10 月 17 日发帖确认，前一晚发生了一起安全事件，与一次大规模“蒸馏攻击”有关，受影响的是 1.4% 的 OpenCode Console 用户。影响范围限定在 Console 中绑定了外部服务商的那部分用户，官方当天上午已向所有受影响用户发送邮件——没收到邮件即代表未受影响。据 OfficeChai、Notebookcheck 等媒体转述，邮件提示工作区内保存的第三方服务商密钥（如 OpenAI、Anthropic）可能已经泄露，要求用户到各服务商后台作废旧密钥、更换新密钥、更新相关程序，并检查近期用量是否异常。OpenCode 表示正在与 Anthropic、OpenAI、Google 一起处理事件。 对使用 AI 编码工具的团队，这是一份直接的行动清单：轮换所有曾存放在该工作区的 key、审计调用量和账单、检查 CI 与本地配置中的 secret，并把“Agent 平台持有第三方凭据”纳入供应链风险面。公开帖没有给出更多技术细节，后续值得关注官方复盘。

03Google 用 Pyrefly 替换 Pytype：更快、更准的 Python 类型检查，且开源

Google 已将沿用多年的 Python 类型检查器 Pytype 替换为 Pyrefly——一个最初由 Meta 开发并开源的静态类型检查器。官方给出的迁移理由包括：更快的检查速度、更高的类型推断准确率，以及更低的运行基础设施成本。对 Python 团队来说，这条新闻的实际含义是：在大仓库上做类型检查时，旧一代工具的性能与维护成本已经成为瓶颈，而开源实现让你可以在 CI 中自行评估和替换，不必绑定单一厂商。 建议的验证路径是：在分支上对同一份代码分别跑 Pytype/Pyrefly，对比检查耗时、误报率和漏报率，再决定是否纳入 CI 门禁；对使用 mypy 的团队，也可以把 Pyrefly 作为第二意见跑在关键模块上。

05Google Research 开源 Harness²：没有标准答案时，用 A/B 行为对比递归优化 Agent Harness

Google Research 开源了 Harness²，一个递归式 Agent Harness 优化框架，针对两个开放世界难题：其一，测试时遇到没见过的任务、没有 ground-truth 验证器，无法用“分数涨没涨”指导 harness 修改；其二，递归自我改进（RSI）通常任务特化，换个任务就失效，难以泛化积累。 它的核心机制是两层递归。任务级采用 Propose–Probe–Compose：先跑一次当前 harness 得到参考轨迹，再提出两个候选 harness（一个针对规划、工具使用、上下文管理、委派等通用代理性缺陷，一个针对当前领域知识与约束），在同一任务、同一模型、同一环境下 A/B 执行并对比行为差异，最后依据证据组合出后继 harness，每个决策都必须绑定具体观察而非假想的分数增益。harnessing 级则对完整改进记录做反思，持续优化“改进器”本身。对自建 Agent 平台的团队，这提供了一条在没有评测集时也能迭代 harness 的可行路径。

[来源: meng shao(@shao__meng)]

06字节 Athanor：4 个 Agent 自主做后训练，104 小时追平官方指令版

字节跳动、杜克大学等团队让 4 个 Claude Agent 各自分到一台八卡机器，共同完成一个研究任务：把 Qwen3-4B-Base 训练成通用模型。选数据、写训练代码、分析结果、决定下一步实验，全部由 Agent 自主决定。104 小时后，它们交出的模型在开发集均分 67.3（官方 Qwen3-4B-Instruct-2507 为 66.5），隐藏集 48.2（官方 47.9），其中隐藏集多步行动任务达到 74.7，明显高于官方的 66.8，数学与逻辑仍有差距。 论文保留的过程记录同样有价值：模型答题卡死、队友接手有效改法、机器被回收后恢复实验——说明长程多 Agent 自主研究已经具备工程可行性，但瓶颈在评测设计、状态恢复和过程可观测性。想做类似系统的团队，应先把实验追踪、检查点与失败恢复做扎实。

[来源: AINLP]

07Anthropic 公开 Dynamic Workflows：让 Claude 写编排程序来管理子 Agent

Anthropic 于 10 月 9 日为 Claude Managed Agents 上线 Beta 版 Dynamic Workflows：由 Claude 根据任务需求生成一段编排程序，程序负责启动子 Agent、衔接不同阶段、处理返回结果，再把执行情况交回主 Agent。它解决的是多 Agent 协作里最费上下文的环节——主 Agent 逐一处理每个子 Agent 的结果，任务一多就把主对话塞满。 在 AI Engineer New York 2026 的工作坊上，Anthropic 工程师用 Unix/Linux 从个人开发走向大规模协作的历史做类比：随着参与开发的 Agent 越来越多，任务组织与协调本身会成为瓶颈。把编排逻辑从自然语言对话下沉为可执行程序，意味着流程可以复用、并行、审计，也更容易在失败时定位到具体阶段。

[来源: InfoQ]

08AWS 预览 Well-Architected Agent：部署前审查 IaC，按成本/安全/性能/可靠性给出优先级建议

AWS 发布 Well-Architected Agent 预览版。这个 Agent 会对照 AWS Well-Architected 最佳实践分析环境，围绕成本、安全、性能、可靠性给出按优先级排序的建议，并能提出修复步骤；它还可以在部署前审查基础设施即代码（IaC）。本质上，它把原本依赖人工评审的架构检查变成了一条可自动化的前置门禁。 实践建议：先把 IaC 审查接入 PR 流水线，把它当作“不会阻断、只出报告”的观察模式跑一段时间，统计有效建议率与误报率，再逐步升级为阻断规则；同时给 Agent 的 IAM 权限做最小化，避免审查工具本身成为新的高权限入口。

[来源: InfoQ]

02深度技术解读// 纵向拆解

Agent 写得越快，“证明它做对了”越值钱 / deep-dive #1

Addy Osmani 今天给出了一组很有冲击力的观察：在 Claude Code 团队把验证流程做扎实之后，Claude Code 能够自己写出 90% 以上的代码；当生成速度超过人类审查速度，瓶颈就从“写”转移到“证明它能工作”[来源: Addy Osmani(@addyosmani)]。同一天，WorkOS 与 Langfuse 在 AI Engineer 大会上的两场分享，恰好把这个结论拆成了可执行的工程方法。

1. “Done”必须是一个可执行契约

WorkOS 的分享标题就是 Teach Your Agent to Prove It's Done：Agent 说完成了，并不等于完成。他们给出的做法是给 Agent 设定它自己能检查的目标——CLI 健康检查、浏览器快照、E2E 测试、LLM judge 与 eval 基线，让失败自动驱动下一轮修复，而不是把问题留到人这里[来源: AI Engineer]。关键转变是：验收条件不再是 PR 描述里的一句话，而是 Agent 在循环中能够调用的命令或断言。

2. 代码评审要升级成多层验证系统

Addy 的判断是，代码评审不会消失，但“一个人逐行读完再点通过”已经不适合作为唯一门禁；它需要演化成多层验证体系：快速的确定性反馈、E2E 测试、feature maps、property tests，以及多 Agent 对抗式评审[来源: Addy Osmani(@addyosmani)]。这套组合的价值在于分层拦截：确定性检查负责低成本回归，property test 覆盖边界，对抗评审负责发现“测试没写到”的设计问题。

3. 把 eval 接进 CI，而不是留在演示里

Langfuse 的实操工作坊用银行助手做例子，把高 stakes Agent 的评测闭环完整走了一遍：带 PII 脱敏的 tracing、数据集构建、把领域专家意见转成 failure modes、LLM-as-judge 与代码评估器，最后是当分数下降时阻断 prompt 变更的 CI[来源: AI Engineer]。这套流程的重点不是追求一个漂亮的平均分，而是让每一次 prompt、工具或模型变更都经过同一组回归检查。

4. 验证要从“生成之前”开始

首席架构师 Carlos Kelkboom 的 5 条反常识原则，把验证前移到了生成阶段：亲自搭代码骨架，提前确定目录、关键文件和函数签名；禁止主 Agent 直接改代码，理解需求后才启动执行 Agent；看不懂的生成代码直接扔，结果隔离在 Git worktree 中，偏离预期结构就重来；尽量让 Agent 一次性完成较大任务，避免反复打补丁；让多个 Agent 并行探索，再由另一个 Agent 比较并只合并好的部分[来源: InfoQ]。

综合来看，Agent 时代的“完成”定义正在变成一份可执行契约：骨架由人定，任务由 Agent 做，验证由机器跑，人负责判断值不值得做。谁先把这套契约固化成工具链，谁就能在代码量继续增长时保持稳定。

Claude 把 Git 写崩之后：Agent 时代的版本控制与编排 / deep-dive #2

Anthropic 的一篇工程复盘提供了目前为止最直观的“Agent 规模”数据：今年 5 月他们平均每天合并约 2,500 次代码变更，9 月已超过 30,000 次，四个月增长 12 倍以上。Monorepo 主分支历史接近 100GB，压缩后的工作副本超过 25GB，仅 CI 每天就需要约 2,500 万次代码检出；如果采用朴素 Git 获取方式，每天可能产生超过 600PB 的数据传输[来源: InfoQ]。

1. 自研 Scion：7 个人、5 个月重建版本控制

在浅克隆、稀疏检出、内部镜像、对象存储快照、数百台 Git 镜像服务器等手段都逐渐失效后，Anthropic 决定重写版本控制系统：一个 7 名工程师的团队用五个月做出 Scion，并完成整个 Monorepo 的迁移，同时开发了代码审查工具 Antique、代码搜索、权限管理等配套基础设施。迁移后，基础设施的 CPU 与内存占用相比原有 Git 镜像方案显著下降。这里最值得复用的信号是：当日合并量进入“万”级，版本控制、CI 检出和合并队列都会成为需要容量建模的系统，而不是默认“够用”的底座。

2. 编排逻辑下沉为程序

Anthropic 的 Dynamic Workflows 则从另一个方向回应规模问题：与其让主 Agent 在对话里逐条协调子 Agent，不如让 Claude 生成一段可执行编排程序，由程序负责启动子 Agent、衔接阶段、处理结果，再把摘要交回主 Agent[来源: InfoQ]。这既减少主上下文被中间结果污染，也让流程可复用、可审计、可在失败时定位到具体阶段。

3. Harness 本身也可以被递归优化

Google 的 Harness² 说明了下一层：不仅流程可以程序化，“如何改进 harness”本身也可以程序化。在没有 ground-truth 的任务上，它用同任务、同模型、同环境下的 A/B 行为对比代替分数反馈，再依据证据组合出新的 harness，并对改进记录做二次反思[来源: meng shao(@shao__meng)]。字节的 Athanor 则把自主性推到研究流程：4 个 Agent 在 104 小时内自主完成数据选择、训练、评测与下一轮决策，最终追平官方指令版[来源: AINLP]。

把三条线合起来看：Agent 规模化之后，竞争点正在从“模型能不能写”转向“基础设施能不能承载、编排能不能复用、改进能不能自我循环”。对工程团队而言，值得现在就开始测量的指标包括：每日合并量、CI 检出延迟、单次会话上下文大小、eval 成本，以及失败恢复所需时间。

document.currentScript 内联渲染技巧 // 一个极小的前端模板方案

Simon Willison 分享了一个巧妙的原生技巧：利用 document.currentScript 在页面加载时把当前 <script> 元素替换成渲染结果，从而在纯 HTML 里实现内联模板： 

The year is <script>document.currentScript.replaceWith(new Date().getFullYear())</script>

// 定义快捷函数后，得到极简模板语言：
$=(...n)=>document.currentScript.replaceWith(...n)
The year is <script>$(new Date().getFullYear())</script>

适合静态站点、文档片段或服务端渲染之外的轻量动态内容，不需要引入任何框架。

[来源: Simon Willison's Weblog]

04实践指南// 可落地的最佳实践

OpenCode 事件后的 24 小时安全检查清单

第一步永远是轮换：作废所有曾保存在受影响工作区的第三方 key（OpenAI、Anthropic 等），更新 CI、本地环境变量和服务器配置，再检查各服务商的用量与账单是否有异常峰值。第二步是缩小爆炸半径：不要让 Agent 平台长期持有高权限长期密钥，改用短期凭据、按项目分 key，并给每个 key 设置预算与告警。第三步是确认边界：既然“没收到邮件 = 未受影响”，就保留好通知记录，并关注官方后续复盘。对任何托管式 AI 编码平台，都应默认假设“平台侧凭据可能泄露”，提前准备轮换流程。

[来源: 宝玉(@dotey)]

给 Agent 一个它自己能跑的“完成定义”

不要只对 Agent 说“实现这个功能”。把验收条件写成可执行命令：npm test、make check、健康检查脚本、Playwright 快照、性能阈值，甚至一个 LLM judge 加 eval 基线。WorkOS 的经验是，当失败能自动驱动下一轮修复时，Agent 才会真正闭环；否则它会在“看起来完成了”的地方停下，把验证成本转移给你。对每个任务，至少准备一条确定性检查 + 一条端到端检查。

[来源: AI Engineer] [来源: Addy Osmani(@addyosmani)]

骨架由人搭，执行放 worktree，看不懂就丢弃重来

Carlos Kelkboom 的实践可以压缩成三条：先由人确定目录、关键文件和函数签名；主 Agent 不直接改代码，只负责理解和规划，执行交给隔离环境中的 Agent；生成结果放进 Git worktree，一旦发现结构偏离预期或代码难以理解，直接丢弃重来，而不是在错误基础上继续打补丁。此外，尽量让 Agent 一次性完成较大任务，并用多个 Agent 并行探索、由另一个 Agent 比较结果，只合并好的部分。

把 eval 变成 CI 门禁，而不是季度汇报

Langfuse 的流程值得直接照搬：给关键 Agent 建立 tracing（含 PII 脱敏），沉淀一组代表性数据集，把领域专家的评论归类成 failure modes，分别用 LLM-as-judge 和代码评估器打分，最后在 CI 中设定阈值——分数下降就阻断 prompt 变更。这样每次改提示词、换模型、加工具都有统一回归基线，避免“这次感觉更好”式的上线。

语言选型要算上 Agent 的反馈延迟

宝玉的观察很具体：Rust 适合核心组件，但大项目编译慢会导致 Agent 得到反馈的速度变慢，资源消耗也大，普通机器并行几个任务就吃不消，因此他只在局部核心组件使用 Rust，其余回归 Electron。反过来，动态语言把原型成本降到极低，却把并发、内存和边界 bug 的“暗税”推迟到运维期。给 Agent 选语言时，除了性能，还要把编译时间、反馈循环长度和并行资源成本纳入决策。

给 Agent 发“预算”和“任务”，而不是只给速率限制

一个 Agent 为订餐厅在 90 分钟内发起 200 次调用，最终导致用户被 Resy 封号。Keycard、JPMorgan Chase 与 OAuth 共同创建者 Dick Hardt 在讨论中给出的方向是：把 Agent 当新员工入职，给它明确 mission；用预算而不是单纯的 rate limit 控制行为；把“大脑”和“手”分离，让高权限操作经过确定性策略审批；OAuth 的 scope 对 Agent 来说太粗，需要更细粒度的授权模型。另一个分享则强调把执行者与监督者分开，对明确规则使用确定性策略，而不是让 Agent 自己批准自己的动作。
