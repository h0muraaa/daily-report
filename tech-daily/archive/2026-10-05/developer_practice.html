01Cursor SDK 一次性放出四项 agent 能力：运行时 steering、可替换系统提示词、MCP 注解、后台子 agent 回传

Cursor 今天为 SDK 连发多条更新。最值得一线开发者注意的是 run.steer() —— 你可以在 agent 执行过程中往“下一轮”注入消息来纠偏，而不必中断重来；如果此时某个子 agent 正忙，它会被自动挪到后台继续干活。配套的还有：允许把 Cursor 的系统提示词整段替换成你自己的（rules/skills/tool schema 仍会加载，按账号逐步开启）；自定义工具现在可以携带 MCP 注解，例如 readOnlyHint、destructiveHint，让模型在调用前就能分清“这是查询”还是“这是删除”；后台子 agent 的结果会作为父 run 的后续轮次回传，stream()/wait() 会一直等到所有子 agent 结束。

为什么重要：这四条合起来，等于把“长任务 agent 的可控性”从黑盒变成了有明确 API 的编排能力——可打断、可换 prompt、可标注危险工具、可等待异步子任务，是构建生产级 agent 循环的基础设施。

06HuggingFace 把 Claude Code / Codex / OpenCode 等“编码 harness”变成 RL 训练环境

HuggingFace 的 Clement Delangue 展示了新做法：不改 harness、不改训练代码，就把 Claude Code、Codex、Hermes、Pi、opencode 等编码 harness 直接变成 RL 环境，任意开源模型、任意任务集，全开源。关键洞见是：训练通常意味着把 harness 重写成 env，于是大多数模型都在“一个没人真正部署的脚手架”里被训练——但同一个模型、同样的权重，在 Mini-SWE-Agent 下能到 62%，换到 Claude Code 下只有 33%。他们的解法是用一个代理（proxy）替代重写：harness 以为自己在和模型 API 对话，实际连的是一个捕获代理，它支持编码 agent 常用的四种格式（OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini），转发到 vLLM，记录下 vLLM 采样的精确 token ID 与 logprobs，再把序列交给 TRL。

② 深度技术解读

解读一：Coding Agent 的评估与调试闭环——从“凭感觉发布”到可度量

今天多条内容不约而同指向同一个工程命题：agent 写得越来越多，人 verification 的带宽成了新瓶颈。有开发者直言“我现在花在验证 agent 写的代码上的时间，比我自己写还多”，并称这是所谓 software factory 的核心堵点。围绕这个堵点，今天出现了几条互补的实践信号：

1) Eval 的四要素：dataset / task / scorer / experiments

Braintrust 的 Jess Wang 在一场分享里把 eval 拆成四部分（数据集、任务、评分器、实验），并强调 observability 与 eval 构成飞轮、而非两件事。她做了一个真实对照实验：用微软 TypeScript Go 仓库的 fix PR，让 Claude Code 分别用 agentic search（grep、find、读文件）和 vector search（embedding 检索）去定位 bug 代码，再交给仓库自带测试套件评分。结果是两者准确率相同，但 vector search 的成本约为四倍——因为向量 chunk 缺少上下文，agent 只好反复搜索。

2) LLM-as-judge 会“凭空评分”：要把上下文喂给评审器

Arize AI 的 Laurie Voss 复盘了一个经典失败案例：一个 LLM 正确性评审器把财务分析 agent 的 13 份报告全部判为不合格。原因是 agent 基于实时网络调研写作，而评审器只依据自己脑中的知识评分，完全没有看到调研上下文。把收集到的来源一并提供给“faithfulness evaluator”后，结果变成更合理的 6 份忠实 / 7 份不忠实。他们用 Claude Agent SDK 构建 agent，并用 OpenTelemetry + OpenInference 把 trace 送入 Arize AX，从 trace 中读出了文件写入失败、报告内容缺失、过度网络搜索等问题，还加了一层便宜且确定性的 ticker 检查作为第一道评测。同一批内容里还有一个更极端的例子：语音 agent 的转写文本看起来“已自我纠正”，但音频里是 2.4 秒静音、一次打断、以及对错误订单的退款——纯文本日志根本看不到这些失败。

3) 让 agent 自己“能验证自己的活”

Addy Osmani 给出一套测试策略：写模拟真实用户流的端到端测试作为 ground truth；用 property-based testing 声明“绝不允许发生什么”，让工具生成成千上万个用例去打破这些约束；替换旧系统时用随机输入对比新旧实现；并要求测试跑得又快又确定——否则 agent 可能学会的是“重试”而不是“修问题”。他的总结很精炼：示例测试说的是应当发生什么，性质测试说的是绝不能发生什么。freeCodeCamp 的文章则从反面给出“打破 AI 编码 agent 修复循环”的具体步骤，指出 Lovable、Replit、Cursor、Claude Code、Base44 都会陷入同一模式，因为这是结构性问题、不是某个产品的怪癖。

4) 反直觉发现：上下文压缩≠更快

UT Austin 对编码 agent 的上下文压缩做了一项大规模研究，在 SWE-bench Verified 与 Terminal-Bench 上跑了近 35,000 次 agent run，分别变化三个决策：怎么压、何时触发压缩、压掉多少。结果发现按 token 量调优的压缩策略可能让 agent 变慢：在 Terminal-Bench + Qwen 上，只用到约三分之一 token 的策略，耗时会比保留完整上下文多 20%–80%；step-triggered 策略每步省 token 最多，但模型调用次数要多 10%–27%；threshold-triggered 则能省 22%–55% 的 token 且调用次数接近全上下文。结论因模型而异，因此不能用单一压缩策略一刀切。

此外，ByteByteGo 回顾了经典的“中间遗忘”盲点——把信息放在长 prompt 中部时模型仍可能无法正确使用；Yugabyte 则区分了“单 agent 的记忆已解决”与“多 agent 之间仍无法共同学习”两个问题：一个 agent 把活交给另一个时，只传了输出、丢了推理过程与死路，下一个 agent 得重新烧 token 把它们推导出来；他们靠逐个变量地修 RAG 管线，把 faithfulness 从 14% 提到 82%，上下文却只用约七分之一。

解读二：MCP 正在成为 Agent 接入企业能力的“连接组织”

如果说上半年的 MCP 还停留在“给 agent 接几个工具”，今天的内容显示它已经开始承担企业级基础设施的角色。

Uber：控制平面 + 数据平面的 MCP 网关

Uber 把全公司数千个存量 API 用一套“控制平面 + 数据平面”的网关体系自动转译成 MCP 工具，让 agent 不改动任何后端服务就能调用公司能力，目前已托管 800+ MCP 服务器、5000+ 工具。他们判断，缺的不是更聪明的模型，而是一套统一的“连接组织”——发现、安全、可靠性这些让 agent 值得信任的基建。架构上：MCP Registry 作为控制平面，是全公司工具的目录与唯一事实来源；Proxy Gateway 作为数据平面，在运行时于 MCP 协议与 HTTP/gRPC/TChannel 之间双向转换。最有工程价值的三点里，AutoCrawler 基于 Cadence 工作流引擎持续扫描内部 IDL 注册表（Protobuf/Thrift），对每个新服务执行“建虚拟服务器 → 解析 schema 与文档注释 → 用 LLM 生成对 agent 友好的工具描述 → 转成 JSON-RPC 2.0 schema → 注册”五步流水线，服务团队一行代码都不用写；安全模型上则强调“发现 ≠ 暴露”，把可见与可调用拆开。

工具侧：MCP 正在向垂直场景铺开

同一天里还能看到 MCP 的多个落点：Replit 上线 TikTok Ads MCP，把广告工作流搬进创作工作区；开源本地工具 Precis 把 Excel/CSV/TSV 的“数据质量”编排成可视画布 + 命令行 + HTTP API + MCP 接口，让 AI 助手负责解释需求、生成规则草稿和触发校验，而确定性的规则执行仍落在可复现的本地引擎——作者的核心判断是MCP 对表格质检的价值，不是让模型替代规则引擎，而是让规则、数据和报告变成 agent 可发现、可调用、可复盘的基础设施；Cursor 则让自定义工具携带 readOnlyHint/destructiveHint 注解，把“危险工具”的语义前置给模型。

检索侧：向量检索仍是 agent 的地基

配套的基础设施也在演进。Databricks 提出 NEAREST BY Join，把向量检索从“服务问题”重新放回 runtime 内的 join 语义来做扩展；Milvus 讲清了 HNSW 的三种压缩取舍——SQ 按维度量化（SQ8/SQ6/SQ4U）、PQ 切子向量用码本索引、PRQ 在 PQ 基础上分阶段编码残差、保留更多信息但增加训练/构建/距离计算成本；AWS 则展示了用 LangChain + Bedrock Knowledge Bases 做 agentic retrieval：面对“跨三个维度对比两款产品”这类多意图问题，单向量相似度检索只会返回所有意图的“平均值”，chunk 看似相关却只覆盖问题的一小部分。这些都在提醒：agent 的可靠性上限，往往由检索层的质量决定。

④ 实践指南

✅ 给 agent 装上“能验证自己”的测试

  • 写模拟真实用户流的端到端测试，作为 ground truth；
  • 用 property-based testing 声明“绝不能发生什么”，自动生成成千上万用例去破坏它；
  • 替换系统时，用随机输入对比新旧版本；
  • 要求测试快速且确定——慢或不可靠的循环会教 agent 学会“重试”而不是“修问题”。

一句话记忆：示例测试说“应当发生什么”，性质测试说“绝不能发生什么”。

📎 [来源: Addy Osmani(@addyosmani)]

✅ 打破 AI 编码 agent 的“修复循环”

当 agent 改一次、坏一次、再改再坏时，这不是某个产品的怪癖，而是跨 Lovable / Replit / Cursor / Claude Code 共性存在的结构性问题。freeCodeCamp 的文章给出一条可复用的处理序列，适用于上述任意工具：先让工程状态可回退（回到可工作的 commit），再缩小复现范围，最后把问题交给 agent 时附上明确的复现步骤与验证方式，而不是一句“还是不行”。

✅ 写一个好 Skill 的五条标准

架构师之路以 Anthropic 官方 skill internal-comms 为样本，总结出评审 skill 的五个维度：① Description——能力清单、触发场景、用户关键词是否齐全，是写给人还是写给模型；② 触发策略——自动还是手动（disable-model-invocation），策略是否与 description 的写法匹配；③ 正文——是路由器还是仓库，语气是否祈使句，有没有 Gotchas（坑），有没有过度限制（Don't railroad）；④ 第三层——细节是否放进 references、正文是否有指针、是否有可复用组件；⑤ 一致性——说的和做的是否一致（最高阶）。作者还现场用这套标准给官方示例“挑刺”，是一份上手 skill 工程的实用清单。

✅ 向量检索压缩选型：SQ / PQ / PRQ 怎么选

HNSW 召回率高，但全精度向量 + 分层图很吃内存。Milvus 提供三种压缩：SQ 逐维度量化（SQ8/SQ6 用 8/6 bit 且范围独立估计，SQ4U 用 4-bit 无符号 + 单一统一范围）；PQ 把向量切成子向量，每个用码本索引表示；PRQ 在 PQ 基础上分阶段编码残差，保留更多信息，但训练、构建与距离计算成本更高。选型时按“内存 vs 精度 vs 构建成本”三角做取舍即可。

✅ 上下文压缩的反直觉结论：省 token 可能更慢

UT Austin 在近 35,000 次 agent run 上验证：调优 token 量的压缩策略可能反而变慢。Terminal-Bench + Qwen 上，约三分之一 token 的策略耗时增加 20%–80%；step-triggered 每步最省 token 但调用次数多 10%–27%；threshold-triggered 省 22%–55% token 且调用次数接近全上下文。结论因模型而异，不要用单一压缩策略一刀切，而应先测量“压缩触发点”对调用次数与延迟的实际影响。

✅ 设计 MCP 网关：把“发现”和“暴露”拆开

Uber 的企业级 MCP 网关给出三条可复用的工程经验：① 用两层平面解耦——registry 做目录与唯一事实来源（发现、所有权、启停），proxy gateway 在运行时做协议翻译与转发，配置热更新无需重启；② 用工作流引擎做存量 API 的自动“MCP 化”，从 IDL 注册表出发，用 LLM 生成对 agent 友好的工具描述，服务团队零改代码；③ 安全模型坚持“发现 ≠ 暴露”，把工具可见与可调用分离。规模数据：已托管 800+ MCP 服务器、5000+ 工具。
