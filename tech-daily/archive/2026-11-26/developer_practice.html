Rust 1.100 稳定 never 类型：十年磨一剑，Infallible 成为其别名

11 月 12 日发布的 Rust 1.100.0 终于稳定了讨论十年的 never type（即 !），并把标准库里的 Infallible 正式设为它的别名，这意味着 ! 与 Infallible 可以在类型系统里互换使用，大幅简化了"永不返回"函数的类型推导。never type 此前经历了五次失败尝试才走到稳定，是 Rust 类型系统里最曲折的落地之一。该版本还稳定了 allocator API 的核心部分、新增 DropGuard，并给 Cargo 增加了可选的依赖冷却（dependency cooldown）设置，用来缓解上游 crate 刚发布即被引入的供应链风险。不过也有批评者指出，allocator 设计仍缺乏 inline storage 支持，对嵌入式等场景还不够友好。

📎 来源：[InfoQ] Rust 1.100 Ships the Never Type After Ten Years and Five Failed Attempts

GitHub 弃用 CSS-in-JS 迁向 CSS Modules：SSR 快了 55%，组件初始化快 25%

GitHub 用三年时间把 github.com 从 styled-components 迁移到 CSS Modules，最终报告服务端渲染（SSR）时间下降 55%、组件初始化快 25%。迁移策略非常值得借鉴：Primer 设计系统组件先在 feature flag 后面分批转换，约 7,760 处 sx prop 用法通过 codemod 加 Copilot agent 批量改写完成。这是"大仓库渐进式重构"的典型案例——用开关隔离风险、用代码生成工具摊平人力成本。不过评论区也对用户侧的实际收益与哈希类名的可读性提出质疑，提醒大家性能指标之外还要评估维护成本。

2深度技术解读

① 重写一个扛生产流量的大服务，怎么证明"新的和旧的一样对"？

以 Anthropic 把 Messages API 从 Python 迁到 Rust 为例：迁移的难点不在"重写"，而在"证明等价"。

按 The Pragmatic Engineer 访谈里 Katelyn Lesse（Anthropic 平台工程负责人，曾供职 Stripe）的说法，她的团队负责 Claude API 以及 Claude Code、Claude Desktop 背后的基础设施，而这次改造的对象是"每一个 Claude token 都要经过"的 Messages API。Rust 带来的是更低的内存开销与更可预测的尾延迟，但把一个产生真实收入的在线服务整段重写，风险极高——任何一个边界行为的偏差都可能变成线上事故。

他们的核心做法可以拆成三步，对任何"重写存量服务"的场景都适用：

  • 旧服务当 oracle（真值对照）：新 Rust 服务上线过程中，用仍在运行的 Python 服务作为参照系，对相同输入比对两边的输出。等价性不是靠"我觉得写对了"，而是靠差分对比验证。
  • 用智能体团队做差异收敛：成队的 Claude agent 专门负责追踪新旧两版之间的差异，定位后逐条修复。把"海量、琐碎、需要读懂两套代码"的对拍工作交给 agent，人则把精力放在判断"这个差异该不该修"。
  • 先隔离、再切流：旧服务继续接新请求、处理完在途请求后安全退出，新实例经过预热验证才承接流量——这套"蓝绿 + 在途请求收敛"的发布哲学，也正是下文 vivo 推理服务不停服升级所强调的。

实践启示：当你面对一次高风险重写，与其追求"一次写对"，不如搭一套可以在线并跑、逐字段/逐请求 diff 的对照机制。LLM / 大模型服务尤其适合这种"shadow traffic + 差异回放"的验证，因为输出是结构化的、可比对的，且异常样本可以自动收集成回归用例。

📎 来源：[The Pragmatic Engineer] How Anthropic builds software in 2026 with Katelyn Lesse · [Anthropic] Messages API Python→Rust

② 让 AI 写代码不难，难的是给"自我改进 Agent"装上刹车

三个一线案例（百度 Loopy、Gas Town 作者、大淘宝需求 Agent）指向同一结论：全自动不可信，护栏才是工程重点。

百度在 AIGC 视频产线上做了一个反直觉的消融实验：让 Agent 不受约束地递归改进自己的 Harness，它在"演化用的那批题"上拿到所有版本最高分 92.8，可换一批题，平均分就从 43.6 掉到 40.3，每次试验的 Token 还多花一半以上。结论很尖锐——不加约束的自我改进，学会的只是"在这场考试里拿分"，而非真正变强。

于是他们做了 Loopy，把产线和裁判拆成两条"双螺旋"：

  • 效果螺旋：在冻结的标准下修复产线，负责"把事做好"。
  • 标准螺旋：从真实的 Good Case / Bad Case 中长出下一版标准，负责"把评判尺子做好"。
  • 关键约束：两条螺旋共享证据，但不共享写权限；标准可以跨轮成长，但单轮之内一字不改——这就堵死了"修复 Agent 去放宽标准"这条最省事的作弊路径。效果是可量化的：早期 Demo 综合视频可用率从 92% 提升到 100%。

这和 Gas Town / Beads 作者 Steve Yegge 的踩坑经历互为印证：他反复遇到"模型先做出很棒的东西，后来整个系统却变成一座垃圾山"，不得不推倒重来好几次——因为每句话都被记录、但只往里加没人清理，历史决策越堆越多；而且部署的 Agent 越多，需要的人（管理员、会计、律师）反而越多，他自己成了瓶颈。

大淘宝的"端到端业务需求专家 Agent"则给出了正向解法：四层架构（上下文输入 → 业务专家编排 → 工具执行 → 反馈学习），设置三道质量门禁（需求澄清、技术方案、内部质量），用 TDD 驱动实现、强制反馈留痕、真实环境验收，并在结项时把过程经验蒸馏成长期知识。人在关键节点确认，而不是全自动。

实践启示：搭 agent 工作流时，把"干活"和"评判"拆成两个权限隔离的回路；标准要能演化但单轮冻结；反馈要留痕并能沉淀成下次的上下文。别把"能全自动跑"当成终点，能可控地停下、可回滚、可解释才是。

4实践指南

▸ 升级到 Ubuntu 26 前，先回归测试交互式提权（sudo-rs）

Ubuntu 用 Rust 重写了包括 sudo 在内的一批系统工具，26.04 的 sudo-rs 与旧 sudo 在提权提示（privilege escalation prompt）的交互上存在差异。如果你的 Ansible / 自动化脚本依赖"密码提权"，升级后会遇到 Timeout (12s) waiting for privilege escalation prompt。

  • 升级前在预发环境跑一遍所有 become: true 的 playbook；
  • 优先切换到免密 sudo（sudoers NOPASSWD）或基于密钥的提权，减少对交互提示的依赖；
  • 对关键自动化加超时与重试，并监控提权失败告警。
📎 来源：[Jeff Geerling] Ansible Fails waiting for privilege escalation on Ubuntu 26

▸ CI/CD 去密钥化：用 OIDC 换短期凭证替代长期 Access Key

在流水线里长期存放 AWS_ACCESS_KEY_ID/SECRET 是常见的高危面。标准做法是让 GitLab（或 GitHub Actions）通过 OIDC 与 AWS 建立联邦身份，任务运行时临时换取 STS 凭证。

  • AWS 侧建 IAM OIDC Identity Provider，信任你的 CI 平台；
  • 角色信任策略里用 sub 条件限定到具体仓库 / 分支，防止被别的仓借道；
  • 权限按最小化授予（如只允许目标 S3 前缀的 s3:PutObject）；
  • 删除旧的长期密钥，审计历史泄露面。
📎 来源：[freeCodeCamp] Deploy to S3 with GitLab CI/CD and AWS OIDC

▸ Lambda 超时翻倍到 30 分钟后，要连带调整的三处配置

函数最长可跑 30 分钟（无需 opt-in、无新增计费），但放宽上限会牵动周边组件，务必同步检查：

  • 并发：相同请求速率下，长任务会让并发量翻倍，核算预留并发与下游承载；
  • SQS 可见性超时：需拉到 3 小时量级，避免消息在函数跑完前被重复投递；
  • Kafka 映射：部分事件源映射需要重建才能匹配新上限。

同时反问："这任务真的该进 Lambda 吗？"长时任务迁往 Step Functions / 容器往往更省钱可控。

📎 来源：[InfoQ] AWS Lambda Doubles Its Timeout to 30 Minutes

▸ Rust 1.100 never type（!）怎么用：表达"永不返回"与更干净的泛型

never type（!）稳定后，Infallible 成为它的别名，二者可互换。典型收益：

  • panic!、loop {}、process::exit() 这类"永不正常返回"的表达式，类型上就是 !，能自动强制转换为任意类型，让你在 match 分支里少写 unreachable!() 之类的占位；
  • Result<T, !> 与 Result<T, Infallible> 等价，方便在无需处理错误的 API 里统一签名；
  • 顺带关注 DropGuard 与 Cargo 的依赖冷却设置（缓解上游供应链风险）。
📎 来源：[InfoQ] Rust 1.100 Ships the Never Type

▸ 大模型推理服务"不停服升级"：蓝绿 + 在途请求收敛

vivo 在 KCD 杭州分享的实践值得参考：在 Kubernetes 上用 SGLang 的 P/D（prefill/decode）分离架构，配合 RBG（RoleBasedGroup）生命周期钩子与推理网关，实现平滑升级。

  • 旧实例：先停止接收新请求 → 处理完在途请求 → 完成 KV 传输后安全退出；
  • 新实例：预热验证通过后再承接流量；
  • 灰度策略：区分蓝绿与灰度升级的适用条件，准备好"旧请求超时 / 新实例启动失败 / 接流后性能异常"三类暂停与回滚预案；
  • 验收指标：请求成功率、首 Token 延迟、流式输出停顿。
