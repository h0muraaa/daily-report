什么是 Agentic Engineering？ AI工程

来源: Simon Willison's Weblog | 2026-03-16

Simon Willison 提出了 "Agentic Engineering"（智能体工程）的概念，定义为"在编码智能体辅助下开发软件的实践"。编码智能体是指能够同时编写和执行代码的 AI 工具，如 Claude Code、OpenAI Codex 和 Gemini CLI。

核心定义是：智能体通过循环运行工具来实现目标。你给编码智能体设定一个目标，它会生成并执行代码，循环往复直到目标达成。代码执行能力是区分智能体与传统代码补全工具的关键特征。这一概念正在重塑软件开发的范式，开发者从"写代码的人"转变为"定义目标、设计环境并构建反馈循环的人"。

来源: InfoQ | 2026-03-15

AWS 在 Lightsail 上推出了托管 OpenClaw 服务用于 AI 智能体部署，但与此同时安全担忧正在加剧。这个拥有 25 万 Star 的 GitHub 项目受到 CVE-2026-25253 漏洞影响，该漏洞可导致一键远程代码执行（RCE），目前有 17,500 多个易受攻击的实例暴露在外。

Bitdefender 研究发现 ClawHub 上 20% 的 Skill 存在恶意代码。虽然 AWS 的蓝图提供了自动加固功能，但并未解决架构层面的安全限制。这一事件提醒开发者：在追求 AI 自动化的便利时，必须重视安全基线的配置和持续监控。

深度技术解读

Agentic Engineering：从"写代码"到"定义意图"的范式转移

随着 Claude Code、Codex 等编码智能体的成熟，软件开发正在经历一场深刻的范式转移。传统开发模式中，工程师的核心价值在于将需求转化为可执行的代码；而在 Agentic Engineering 模式下，工程师的核心价值转向"定义目标、设计环境并构建反馈循环"。

关键转变：当 Codex 可以在 5 个月内生成 100 万行代码、完成 1500 个 PR 时，人类工程师的角色从"代码生产者"转变为"意图定义者"和"质量守门人"。

这种转变对开发者提出了新的能力要求：

1. 意图表达能力：清晰、无歧义地描述需求变得至关重要。提示词工程（Prompt Engineering）正在进化为意图工程（Intent Engineering），需要开发者具备将模糊需求结构化、可验证化的能力。

2. 环境设计能力：为智能体创造良好的工作环境，包括仓库结构、CI 配置、测试框架、文档规范等。正如实践所示，AGENTS.md 文件的质量直接影响智能体的产出质量。

3. 反馈循环构建：设计有效的验证机制，让智能体能够从错误中学习。这包括单元测试、集成测试、代码审查流程等。

实践建议：如果你还没有尝试过让 AI 智能体独立完成一个完整功能，现在就是最佳时机。从简单的工具脚本开始，逐步建立对智能体能力的信任边界认知。

百万 Token 上下文：RAG 的终结还是进化？

Claude Opus 4.6 和 Sonnet 4.6 正式上线百万 Token 上下文窗口，且不再收取长上下文附加费。这一技术突破引发了关于 RAG（检索增强生成）架构未来的广泛讨论。

传统 RAG 的核心假设是：模型上下文有限，必须先从海量文档中检索出相关片段，再输入给模型。这一架构带来了额外的复杂性和失败点：分块策略的选择、嵌入模型的质量、检索排名的准确性等。

百万 Token 上下文改变游戏规则：对于许多企业应用场景，百万 Token 足以容纳完整的知识库。这意味着：

  • 简单场景可以直接"把整个文档库塞进上下文"，省去 RAG 的复杂性
  • 复杂场景可以将 RAG 作为第一层过滤，再用长上下文做精细推理
  • 需要精确引用来源的场景，RAG 仍有其价值
架构师思考：不要急于抛弃 RAG。评估你的场景是否真的需要百万 Token，以及成本和延迟是否可以接受。对于大多数生产环境，混合架构可能是最佳选择。

实践指南

OpenClaw 生产环境部署的安全检查清单

随着 OpenClaw 在企业中的普及，安全事件也在增加。根据工信部、CNCERT 等机构发布的预警，以下是生产环境部署的安全检查清单：

高危风险：CVE-2026-25253 漏洞可导致一键 RCE，17,500+ 实例暴露在外；Bitdefender 发现 ClawHub 上 20% 的 Skill 存在恶意代码。

基础安全配置：

  • 禁止在内部网络使用未审批的 OpenClaw 智能体终端
  • 严禁与工业控制网络直接连通，部署于独立隔离区
  • 原则上禁止向 OpenClaw 提供系统级权限
  • 代码、密钥等敏感信息禁止明文发往模型服务商

企业级管控建议：

  • 建立 Skill 审核机制，仅允许使用白名单内的 Skill
  • 实施行为审计，关键任务失败可复盘
  • 敏感操作需要人工审批，避免自动化误操作
  • 定期轮换 API 密钥，限制密钥权限范围

AI 辅助开发的最佳实践：从 1500 个 PR 中学到的经验

基于 Codex 驱动开发百万行代码的实践，总结以下可复制的方法论：

1. 从空仓库开始，让 Agent 定义结构

不要预设项目结构，让 Codex 根据需求生成初始脚手架。这包括仓库结构、CI 配置、格式化规则、包管理器设置等。人工干预越少，Agent 的"一致性"越好。

# AGENTS.md 示例 - 由 Codex 生成 project: "my-service" language: "TypeScript" patterns: - 所有 API 端点必须包含 OpenAPI 注解 - 数据库操作必须使用事务包装 - 错误处理必须使用统一的 AppError 类

2. 建立快速反馈循环

Agent 的优势在于速度，人类的价值在于判断。设计一个让 Agent 快速试错、人类快速纠错的流程至关重要。每次迭代周期应控制在 5-10 分钟。

3. 用测试定义"完成"

不要依赖 Agent 自我判断任务完成度。为每个功能编写明确的测试用例，测试通过即视为完成。这既是质量标准，也是防止过度工程化的约束。

效率数据：实践表明，这种开发模式的耗时仅为手动开发的 10%。3 人团队在 5 个月内完成了传统模式需要 30 人月的代码量。

MCP 的替代方案：什么时候应该选择 CLI 而非协议？

Perplexity 和 YC 的实践经验表明，MCP 并非连接 AI 与工具的唯一选择。以下是决策框架：

选择 CLI 的场景：

  • 工具调用频率高，MCP 的上下文开销成为瓶颈
  • 需要精细控制工具的生命周期（启动/停止）
  • 身份验证逻辑复杂，MCP 的标准方案无法满足
  • 团队有能力维护轻量级包装器

选择 MCP 的场景：

  • 需要跨多个模型/平台复用同一套工具集成
  • 工具生态丰富，希望直接使用社区 Skill
  • 团队希望最小化集成工作量
  • 对延迟和上下文开销不敏感

Garry Tan 的 100 行 CLI 方案核心思路：

用简单的命令行包装器替代 MCP 服务器，通过标准输入输出与 Agent 通信。这种方式避免了 MCP 的臃肿，同时保留了灵活性。对于内部工具集成，这可能是更务实的选择。
