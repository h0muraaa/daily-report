01Anthropic 重造版本控制系统：Git 顶不住 Agent 的代码产出速度

Anthropic 的 Monorepo 主分支历史已接近 100GB，压缩后的工作副本超过 25GB，CI 每天要做约 2500 万次代码检出；若用朴素 Git 拉取，每天可能产生超过 600PB 传输。合并量从 5 月的日均约 2,500 次涨到 9 月的 3 万次以上（4 个月增长 12 倍），浅克隆、稀疏检出、镜像和对象存储快照等优化已难以维持。最终一个 7 人团队用 5 个月写出了新版本控制系统 Scion，并配套了代码审查工具 Antique、代码搜索与权限系统；迁移后其基础设施 CPU 和内存占用约为原 Git 镜像方案的 1/200。

同一时间，Claude Code 约 90% 的代码由 Claude 自己编写，6 月到 9 月合并的 PR 数量翻倍以上，回滚率反而下降超过 40%。当“写代码”不再是瓶颈，版本控制、CI、审查和权限这些支撑系统就成了新的上限——这是所有重度使用 Coding Agent 的团队都会遇到的结构性问题。

02JDK 28 定稿 JEP 543：Structured Concurrency 结束七轮预览

JEP 543 在 JDK 28 中正式定稿结构化并发（Structured Concurrency），相比 JDK 27 的 API 没有变化：已经在 JDK 27 上使用的团队只需去掉 --enable-preview 并重新编译。从 JDK 25/26 迁移的代码则需要适配三处：异常类型参数 R_X、ExecutionException 的包装方式，以及 joiner 上抽象的 timeout() 回调。

结构化并发把一组子任务绑定到同一个作用域，父任务统一等待、取消和传播异常，配合虚拟线程可以显著降低并发代码的泄漏与取消难题。建议在升级 JDK 28 前，先把现有 StructuredTaskScope 用法跑一遍编译与超时路径测试，尤其是自定义 joiner 的实现。

07Cloudflare Containers 跨租户数据泄露：问题出在存储分配器，不在 VM 边界

Cloudflare 披露并修复了 Containers 平台（也为 Cloudflare Sandboxes 提供支撑）的跨租户数据泄露漏洞：Workers 付费账户的客户可能恢复同一主机上其他客户容器遗留的磁盘块，官方表示未发现被恶意利用的证据。根因不在 Firecracker 虚拟机边界，而在底层存储分配器：受影响的资源池使用 64 KiB 精简块并配置了 skip_block_zeroing，一次 4 KiB 写入只覆盖自身空间，剩余最多 60 KiB 仍可能保留前一个容器的数据。

02深度技术解读// 从数据到实现细节

01 · Cloudflare 如何把 AI Code Review 成本砍掉 68% // 不是换更便宜的模型，而是重做上下文与调用链

Cloudflare 的 AI code reviewer 在 4 月平均每次审查花费 $1.19，到 8 月底涨到约 $2.46，而架构没有大改：仍是 coordinator 把任务分给同一组 specialist reviewer，仍由同一套风险分级决定审查强度。真正变化的是 token 量——每次审查从约 0.91M tokens 涨到 2.99M tokens；其中 code-quality reviewer 平均每次审查要发起 16.6 次 LLM 调用，每次调用都重发整段对话，写出 72k tokens 缓存、读取 1.08M tokens。成本结构为：输出 23%、缓存写入 43%、缓存读取 34%。即使缓存命中率从 85.7% 升到 97%，一个更大的上下文仍然更贵。

第一步：测量“第一个请求”，而不是只看总命中率

他们给每个 reviewer 的首次 LLM 调用埋点，记录 token 用量和 system block 的哈希，发现首次请求的缓存命中率只有 14–26%，尽管各仓库共享的 tools 与 agent instructions 有 11k–21k tokens 完全一致。原因是 OpenCode v1 把唯一的缓存断点放在包含仓库特定环境数据的块之后，共享前缀从未被单独缓存。修复方式是把 system prompt 拆成两个 block，在共享部分之后加断点，并把仓库路径、变量化 skill 列表、工具描述等移到断点之后——首次请求命中率升到 91–99.5%。

第二步：减少调用次数，而不是先压单价

  • 把 Codex reference index 直接放进 prompt，省掉初始三轮文件读取：调用数从 15.9 降到 9.6，成本从 $1.12 降到 $0.72。
  • 首轮并行读取共享上下文与全部 patch（最多 150KB），替代“一次读一个文件”的串行工具循环。
  • 三个 reviewer 发送完全相同的首个请求：code quality、security、performance 共享 tools 与规则，之后才加各自指令。一个 reviewer 写缓存，另外两个最多等 20 秒读取流式结果，每个 reviewer 省约 9 美分。
  • 删掉用不上的工具：57–76% 的会话会尝试调用最终评论工具、被拒后再花一次调用恢复；移除后还减少约 2.9k tokens 的工具定义。
  • 跳过空转：复审时没有新内容就跳过对应 reviewer（AGENTS.md 跳过 56%、performance 23%、docs 13%）；审查发布后立即停止，不再生成没人看的总结，每次省约 $0.07。
  • 区分超时与供应商故障，并把取消检查改为每 15 秒轮询——此前抽样的 446 个已取消 GitLab job 中有 358 个仍跑到了结束。

第三步：用数据路由模型与 effort，而不是假设“越贵越好”

同一模型下，full-tier medium effort 比 high effort 快 20%，两组 coordinator 配置被淘汰。Opus 5.5 medium 与 Opus 5 在结果上没有可测差异，但更便宜；Opus 5.5 的单价下降只解释了约 $0.20 的节省，其余来自更少的 token。Sonnet 5 与 Sonnet 5.5 单价相同，但 5.5 在 code quality、performance、security 上分别便宜 62%、58%、47%，原因完全是 token 用量更少：Sonnet 5.5 medium 每次 code-quality 运行平均 1.7 次调用（此前 6.2 次），超过一半一次调用完成。high effort 则需要 3.4 次调用、贵 61%，但多产出 58% 的 critical/warning findings，折算约每次审查 2 美分，因此 code quality 最终保留 high effort。

结果与质量校验

平均每次审查成本$2.43$0.77-68%
中位延迟4m 09s1m 32s更快

成本下降的构成也值得注意：代码/工作流改动贡献 $0.65，模型与 effort 路由贡献 $1.06；缓存读取下降 82%、缓存写入下降 54%、输出下降 67%。但便宜并非对所有 reviewer 都安全：performance reviewer 在 medium effort 下丢失约 64% 的重要 findings，security 下降约 25%，code quality medium 的已采纳 findings 只有 high 的四分之一。Cloudflare 因此保留 code quality high，其余继续测试。

可复用的检查清单

  • 分别监控 output / cache write / cache read 三项成本；高命中率不等于低成本。
  • 对首次 provider 请求做 token 与 system prompt 哈希埋点，验证共享前缀真的被缓存。
  • 先减少调用次数与上下文体积，再谈模型单价；重发增长中的对话是最大的成本乘数。
  • 删除不可用工具、跳过无新内容的复审、任务完成后立即停止、强制执行取消。
  • 用“被采纳的 finding”和盲评来验证质量，而不是只看成本或 token 单价。

02 · Meta 的 Thin Orchestrator：把路由交给代码，把推理留给专家 Agent // 1,300 行编排器，20+ 工作流，14 个专家

Meta 最初用一个“全能 Agent”自动完成推荐系统的数据列接入：把所有 schema、代码生成规则、流水线路由、校验要求和数据源模式都塞进同一个上下文。上线后它开始幻觉并串味——把某个子系统的命名约定或代码模式套到另一个子系统上。于是他们把架构改成 1,300 行的薄编排器，将 20+ 工作流路由到 14 个领域专家 Agent，编排器本身不做任何领域工作。

确定性边界：七步里只有一步用 LLM

编排器负责：识别意图、收集字段、执行可靠性检查、委派、处理结果、暴露错误、确认成功。它不推理代码、不生成配置、不碰代码库。具体七步协议中，第 1–5 步和第 7 步都是确定性的，只有第 6 步“委派给子 Agent”使用 LLM 推理，而且发生在隔离的、领域受限的上下文中。

  1. 读取相关子 Agent 的 instruction 文件。
  2. 检查目标是否已存在，避免重复创建。
  3. 从用户处收集必填字段。
  4. 自动发现可推断的信息，如仓库类型、已有配置。
  5. 执行可靠性门禁：活动告警、必需 reviewer。
  6. 带着完整上下文委派给子 Agent。
  7. 处理结果、暴露错误并确认成功。

用工作流模板复用专家，而不是不断加 Agent

Column Onboarding:  Schema → Validation → Population → Testing
Event Onboarding:   Schema → Population → Validation → Testing → Event Processing
Pipeline Migration: Assessment → Planning → Population → Validation → Monitoring

三条模板复用同一组 14 个 Agent，只是阶段顺序不同。Pipeline Migration 只需要新增模板，没有新增任何 Agent 代码。每个子 Agent 结构统一：运行时知识源、前置收集清单、执行工作流、代码发现模式、故障排查映射；知识从 25+ 个文件按需加载，每个通常几千 token，更新后立即生效，不需要改编排器或重新部署。

结果与设计取舍

数据列配置准备时间从手工 3–4 天降到 1 小时以内，约三分之二的变更无需显著人工修改。Meta 还引用了一项预印本结果：在 80 个任务的批次上，编排式多 Agent 达到 65.3% 准确率，单 Agent 为 16.6%，token 用量最多降低 65 倍；单 Agent 只有在逐任务手工调 prompt 时才能到 70–80%，不调则只有 10–20%。

核心取舍是“没有 Agent 看到全貌”。这牺牲了全局上下文，换来了故障隔离：子 Agent 失败时，编排器可以重试或升级，而不会污染自身状态或其他 Agent 的上下文；由于路由和可靠性检查不是 LLM 驱动，编排层几乎没有幻觉空间。

给生产团队的 5 条经验

  • 路由与推理分离：路由用关键词、意图分类、字段收集等确定性逻辑，领域推理放在隔离子 Agent。
  • 标准化子 Agent 结构：统一模板让新增专家变成填模板，而不是改架构。
  • 用工作流模板扩展：先问现有 Agent 能否重新排序，而不是先加新 Agent。
  • 运行时加载知识：别把领域知识写进编排器，否则每次更新都要重新部署。
  • 显式画出确定性/概率性边界：不要把路由决策和推理任务混在一起。

Pele — 从零重写的 Mermaid 渲染器

Obsidian CEO kepano 开源了 Pele，用一套完全自主实现的解析与渲染管线替代 mermaid.js，支持 Mermaid 12.1.0 的全部内置图表语法并输出 SVG，零运行时依赖、同步渲染，采用 MIT 协议。它没有 fork mermaid.js，而是为约 30 种图型各自实现 lexer → parser → model → render 管线，并用 Mermaid 官方 parser spec 与差分模糊测试验证语法兼容性；布局层也是自研的分层（约 78KB）、泳道和复合嵌套三个引擎。

公开对比数据很夸张：gzip 后 230 kB vs 1.6 MB（约 6 倍），渲染耗时 0.05–0.3 ms vs 6–82 ms（最高约 500 倍），直接依赖 0 vs 23。同步渲染能成立的关键是文本测量：浏览器端用 canvas，Node 等无 DOM 环境用内置字符宽度表，也可注入自定义 measurer。

npm install pele

import { render } from 'pele';

const { svg } = render(`flowchart LR
  A[Mermaid text] --> B[SVG]`);

document.querySelector('#diagram').innerHTML = svg;

注意：这是较新的项目（GitHub 约 2.4k stars），接入前请用自己文档里的图表类型做一轮兼容性与安全验证；Pele 会转义图表文本、过滤链接与样式，并限制输入/输出大小。

OpenGCUA — 通用计算机使用智能体的完整开源栈

阿里通义 MAI-UI 团队开源了 OpenGCUA，包含 harness、跨设备 SDK、原生 macOS 应用、评测轨迹和参考 Agent 实现。它把传统“看截图点按钮”的 GUI Agent 扩展为 GCUA（generalist computer-use agent）：模型自主决定观察什么（按需调用 screenshot()，而不是每步强制截图）、如何行动（输出一段带循环和条件的 Python 程序，编排 GUI 操作、API 调用和 shell 命令）、如何组织工作（自己维护 todo 列表，每步声明 intent）。

两个设计支柱是 code execution 与 harness-to-model decision transfer：复用模型已有的编程能力，循环内中间结果直接决定下一步代码，不必每步回模型，从而提升效率。对正在做 computer-use Agent 的团队，这是一份可以直接跑、可以对照评测轨迹的完整参考实现。

Harness² — 不改模型权重，递归改进 Agent Harness

Google Research 开源了 Harness²（Recursive Agent Harnessing for an Open World），Apache 2.0 协议，支持 OpenCode 和 Codex（默认 OpenCode，可切换）。它把可修改的 Harness 拆成 8 类组件：系统提示词、护栏、记忆、工具指导、子智能体、Skills、脚本和插件，让 Agent 通过持续调整这些外部组件实现递归式能力提升，而不修改模型权重。

核心是两层递归：任务级递归在遇到未见过的任务时执行“提出—探测—组合”，先产生多个 Harness 变体再选择；更高层则从执行经验中提炼可复用的组件更新。国内开发者 Joseph Zhou 称接入 Jev 1.14 后，在不调整权重的情况下显著提升了视觉任务表现。官方明确这是研究项目、不是受支持的产品，适合做实验和借鉴设计，不建议直接压生产。

04实践指南// 可以放进团队规范的做法

把 Code Review 从“有人看过”改成“每一层拦住它该拦的问题”

Anthropic 的 Claude Code 团队在约 90% 代码由 Claude 编写的情况下，6 月到 9 月合并 PR 数量翻倍以上，回滚率反而下降超过 40%；内部 PR 获得实质性审查评论的比例从 16% 升到 54%。他们的结论是：人工是否逐行读过代码，是一个不准确的替代指标。真正要问的是“这次变更有哪些失败模式，应该由哪一层检查来抓”。

  • PR 之前：Claude 必须运行测试、构建和 linter，并展示真实输出，而不是口头声称完成；另起一个全新上下文的 subagent 独立审查 diff。
  • PR 上：必需 CI 阻塞合并；多个 AI reviewer 并行找 bug，由“验证者”投票过滤误报；安全审查走独立流程。
  • 风险分级审批：由分类器而非作者判定风险。低风险（文档、flag 后的增量改动）零人工，中风险一人，高风险（计费、自动更新等敏感路径）两人；AI 的审批永远不能占用人工名额。
  • 合并之后：flag 灰度内部先行，出问题可不部署直接关闭；每周 on-call，事故复盘追问“哪一层本应拦住它”。
  • 事故转化为 eval：把历史上导致事故的 PR 收集成每日评测集，让审查系统持续针对真实失败模式回归。

不要只抄“AI 审 AI”这个结论。真正可复用的是分层验证、风险分级、可回滚发布和事故回归这四件事；没有它们，90% 自动生成就是风险放大器。

[来源: 新智元] [来源: meng shao]

用七级成熟度模型给生产 Agent 做一次自检

Stack Overflow 的 field guide 把 LLM/Agent 的生产化分成 7 级。核心观点不是“让模型更确定”，而是把模型限制在最小的判断点上，用可测试、可门禁、可审计、可观测的确定性组件把它包起来。

级别你拥有的能力危险信号
L0 Notebookprompt、模型、happy-path demo“在我的例子上能跑”
L1 确定性Agent 只提出动作；每个能力有固定步骤；模型只占一个节点；循环有界Agent 能改业务状态，或行为随路径变化
L2 评测eval 进入 CI；发布对比基线；用生产流量做 shadow eval改 prompt 后只能“祈祷”，eval 还在 notebook 里
L3 置信度组合且校准的置信度；阈值分离自动与人工；抽样 LLM judge直接用模型原始置信度；没有弃权路径
L4 安全治理分层护栏；边界处处理 PII；只追加的审计账本；有作用域的记忆只有一个 moderation filter；记录原始输入；审计可篡改
L5 可运维决策可观测；成本控制；模型路由与降级；kill switch通过账单和客户投诉才发现质量/成本问题
L6 生产级构建有纪律的构建流程；面向 Coding Agent 的操作系统；并行 Agent 基于决策日志工作靠口口相传的知识；同一决策反复争论

按依赖顺序爬级：确定性 → 评测 → 置信度 → 自动化 → 安全 → 规模化 → 可观测。自检里若不足一半为真，系统的成熟度就低于 demo 给人的印象。先修最弱的那一级，不要跳级。

[来源: Stack Overflow Blog]

把“运维漂移”当成一等监控对象

系统在部署后立刻符合规格，不代表几小时后仍然符合。freeCodeCamp 的文章把运维漂移（operational drift）定义为“运维规格与持续观测到的状态之间的偏离”，它比配置漂移更宽：流量变化、依赖劣化、证书过期、配置被改、feature flag 移动、数据增长、人工变更、Agent 执行动作、基础设施替换，都会让系统偏离规格。

可落地的做法是：先写清楚可观测的运维规格（SLO、依赖版本、证书有效期、关键配置、容量阈值），再用持续采样去比对，发现偏离时在变成事故前告警。特别注意把 Agent 的动作也纳入观测面——Agent 能改配置、发请求、动数据，它本身就是漂移源。

[来源: freeCodeCamp]

LLM-as-a-judge 不是客观裁判：先做四项偏差校准

Google Cloud 的文章指出一个常见误区：人类有主观性，所以用 AI 做客观评估。实际上 LLM judge 也有偏差：冗长偏差（偏爱更长、更自信的答案，即使事实错误）、位置偏差（交换两个选项的顺序，判词翻转率可超过 75%）、光环效应（干净的语法和格式会让 judge 给准确性高分）、顺从偏差（擅长认可正确工作，却容易漏掉错误、bug 或不正确的实现）。

实操上至少做四件事：随机化候选顺序并多次评估；控制答案长度与格式差异；用人工标注样本校准 judge 的阈值与偏差；对关键决策保留抽样人工复核。把 judge 当成“一个会给出有用信号的评审”，而不是“客观真值”。

接入 DeepSeek Search / Fetch 时，先把限流、缓存和计费日写进设计

Search / Fetch 是原始 JSON API，沿用 Bearer 鉴权，适合直接给 Agent 或 RAG 管道加“实时网页”能力。落地时要注意四点：

  • 限流：每账户两类接口各 5 QPS，批量抓取要自己排队或并发控制。
  • 计费：每 1000 次成功请求 5 元，空结果不收费；当前在 Harness / Claude Code / Codex 中的 Server 端调用免费，但 11 月 1 日 00:00（北京时间）起收费。
  • 缓存：搜索结果和抓取正文按 URL/query 做短 TTL 缓存，既省成本也降低上游压力。
  • 格式：Fetch 返回 Markdown（标题+正文），适合直接进上下文；但仍要做长度截断和内容清洗，避免把整页噪声塞进 prompt。

设计时先问：哪些需求是你“没有”的？

seangoedecke 的文章提出一个很实用的架构视角：设计软件时，你没有的需求和你有的需求同样重要。优雅的设计往往来自主动放弃某些需求——Unicorn 这类 preforking server 不支持进程间共享可变状态，因此可以让每个 server 跑在独立进程里，免费获得隔离；它明确不处理慢客户端，因此可以直接把请求排在 Unix socket 上，大幅简化实现；S3 不支持多 key 原子更新，因此可以按 blob 存储，避免复杂的跨对象事务。

下次做架构评审时，除了列“必须支持什么”，也列一列“可以慢、可以旧、可以不灵活、可以最终一致”的部分。你愿意放弃的约束，往往就是复杂度的来源。
