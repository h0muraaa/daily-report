02深度技术解读

▍Code Mode 与 Agent Harness：为什么把工具调用写成代码？

传统 Agent 的循环是"模型 → 一次工具调用 → 结果回灌 → 模型再决定下一步"，每一步都是一次往返（round-trip），工具返回的原始大块内容还会全量塞进上下文。Code Mode 换了个思路：让模型直接写一段程序去编排工具。这带来三个直接收益：

  • 并行：一段 JS 里可以同时发起多个互不依赖的工具调用，而不是串行等一轮又一轮。
  • 先过滤再入上下文：在代码里先对工具输出做筛选，只把需要的部分返回给模型。工具吐出一大段内容时，context 只吃到筛过的结果，既省 token 又更聚焦。
  • 确定性控制流：循环、条件、聚合这些逻辑交给代码执行，而不是让模型用自然语言"想"出来，减少不确定性。
// 概念示意：把多步工具调用写成一段并行 + 过滤的 JS
const [issues, ci] = await Promise.all([
  tools.fetchIssues({ label: "bug" }),
  tools.ciStatus({ repo: "acme/api" }),
]);

// 只把关键字段放进上下文，而不是整个返回体
return issues
  .filter(i => i.severity === "high")
  .map(i => ({ id: i.id, title: i.title }))
  .concat({ ci: ci.status });

这与 Armin Ronacher（Earendil）在 AI Engineer 分享里的观察一脉相承：Pi 这个 coding agent 一年前和现在用的是同一套核心工具，但"能做更多事"，因为模型变强了。他公布自己的会话数据——纠正次数变少、单个任务从 2.5 分钟跑到 14 分钟、开启过 141 个项目但只留下 10~15 个常驻。核心结论是：人类的注意力仍然是瓶颈，所以要先做一个能产出优秀软件的"工坊（workshop）"，再去建一个批量生产的"工厂（factory）"。Code Mode 这类让工具调用更高效、更省上下文的设计，本质就是在为这个"工坊"降噪。

📎 来源：AINLP · Code Mode ；AI Engineer · Build the Workshop Before the Software Factory — Armin Ronacher

▍Lean 形式化验证：1700 万行证明如何一天内被机器核验

本周最热的"技术事件"其实是黎曼猜想的形式化证明获得 Lean 与 Mathlib 社区认证——但对开发者真正有价值的，是它背后的工程机制：一个 1700 万行的 Lean 库，是怎么在一天内被全球社区独立核验的？

Lean 是什么？可以把它理解成"一套写数学证明的语言 + 一个检查证明的工具"。数学家或 AI 把命题、条件和推理写进去，系统告诉你还差什么没证，最后检查这些步骤能否推出结论。核心理念是"信任小内核"：找证明可以用各种聪明办法，但负责最后检查的程序要尽量简单——否则一份复杂证明通过了复杂检查器，你又得去相信另一套同样复杂的程序。Lean 由 Leonardo de Moura 于 2013 年在微软研究院启动，2014 年 6 月发布 0.1，2023 年发布 Lean 4.0，Mathlib 也随之完成迁移。

验证是怎么做的？社区并没有"相信作者"，而是用一组硬标准逐条核查：

  • 确认被证明的命题本身就是 Mathlib 里那条 RiemannHypothesis（经数论专家审校）；
  • 库能无错误编译，数十人复现出同一份原始证明导出文件；
  • 专门加一个只导入 Mathlib 的文件把命题隔离出来，用两个独立工具比对，确认"证的就是它"；
  • 导出的证明再经 Lean 官方内核、con-leche、con-ron 以及多个第三方独立检查器核验；con-leche / con-ron 还附带了相对集合论的形式化证明，论证它们"不可能接受一个错误的证明"。
给开发者的启示：这不是"AI 单枪匹马证出来了"，而是一次典型的可复现、可独立核验的工程实践——多检查器交叉验证、命题隔离、导出文件可复现。形式化验证的这套"不信任作者、只信任内核 + 多方复核"的思路，和我们在代码世界里追求的可重复构建、独立审计、最小信任面完全是同一套工程哲学。

04实践指南

① 写好代码的秘诀：先别犯低级错误

Sean Goedecke 的观点很反直觉却很实用：写出好代码的秘诀是避免灾难性错误，而不是追求"天才洞见"。他用棋类和网球类比——如果你下棋从不随手送子，几乎能赢所有人；如果你只是很擅长把球回过去，即便从不打出制胜分也能赢大多数人。很多工程师误以为"写好代码"等于"发现漂亮的新抽象"，但这些是加分项，不是主线。

别为了炫技引入新抽象。把"不犯大错"刻进肌肉记忆：不乱改边界、不吞异常、不引入难以回滚的耦合。

📎 来源：seangoedecke.com · To code well, avoid blunders

② 验证被高估了：测试通过 ≠ 代码可靠

InfoQ 报道了 Flask 作者、Pi 开发者 Armin Ronacher 讲的一个真实场景：系统崩了，一屋子工程师开会，没人说得清故障在哪一层、哪段代码出了问题，所有人都在向 Claude 提问。Pi 每天收到约 40~50 个新 Issue，Agent 已接手判断 Bug 是否存在、复现、写测试、生成修复、分配优先级，甚至在某些任务里"只要测试证明修复有效、工程师确认就直接合并"。但 Pi 创始人 Mario Zechner 反问得很直白："如果你什么都不需要理解了，那你还有什么用？公司为什么还需要你？"

让 AI 写测试、找 Bug 可以，但别把"理解系统"也外包出去。测试通过是必要条件，不是可靠性的充分证明——尤其当测试也是 AI 写的时候。

📎 来源：InfoQ · Pi 创始人曝现代开发奇观：系统崩了，一屋子工程师都在问 Claude 怎么修

③ REALCLI：任务成功 ≠ 协作合格

北航、人大与 IQuest Research 的论文 REALCLI（arXiv:2610.22507）指出一个被现有 Benchmark 忽略的维度：当 Agent 在长任务执行中需要与人协作时，它表现如何？现实任务不是"接收完整需求 → 自主执行 → 交付"的线性流程，用户会中途补充信息、修改需求，高风险操作还需授权确认。REALCLI 用成对评测——同一任务在"自主执行模式（REALCLI-EXEC）"与"协作模式"两种条件下运行，共享目标、环境和验证器，从而同时考察任务效果与人机协作质量。

评估自己团队用的 CLI Agent 时，别只看它能不能把任务做完，也要看它中途如何追问、如何请求确认、如何响应需求变更——这才是生产环境里的真实分。
