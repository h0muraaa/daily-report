Claude Code 两连更：Projects 重构成「主对话 + 云端并行线程」，同时落地 AGENTS.md 兼容

Anthropic 重做了 Claude 的 Projects 功能并先在 Claude Code 上线测试版。形态上从「一个放资料的文件夹」变成一个持续的主对话：你在里面派活，Claude 自己拆任务、分给多个并行 Thread，检查结果后汇总给你。每个 Thread 本质上是一个独立的云端 Claude Code 会话，有自己的上下文窗口、独立沙箱和独立 git 分支，在云端并行写代码、跑测试、按需开 PR，合上电脑离线后继续运转。

配套能力包括：Overview 面板按状态给线程分组，卡住等你拍板的进 Waiting on you，桌面端弹通知；每个新线程继承同一份项目指令、仓库与项目记忆；线程开了 PR 会自己盯着，CI 失败或来了评审意见会自己推修复，检查通过才通知你；可以把一部分工作配成定时 routine；没有代码仓库也能用，上传文档让线程调研写报告，成果交到 Library。宝玉指出这套交互几乎是 Slack 的 Thread 模型翻版——主频道保持干净，细节收在 Thread 里。

同日另一项落地：从 Claude Code 2.1.277 起支持 AGENTS.md，若目录里没有 CLAUDE.md，会回退读取 AGENTS.md，该行为可在 /config 中开关（消息由 Thariq 发布，Addy Osmani 转发确认）。

实践建议：如果你的仓库同时被 Codex、Cursor、Gemini CLI 等多个 agent 使用，AGENTS.md 已是跨工具的事实约定，把仓库级约定挪过去能少维护一份；Projects 的「云端线程」模式则适合把能独立验证的任务（修 lint、升级依赖、补测试）真正并行出去，但要留意每个线程都在独立分支上写，合并冲突面变大了。

Shopify 把移动端从 React Native 迁回原生 Swift / Kotlin

Shopify 工程团队发布《Native is now the future of mobile at Shopify》，宣布把全部移动应用迁回 Swift 和 Kotlin。这个决定的反差在于：2020 年 Shopify 曾高调从原生转向 React Native，此后成为该生态最重要的使用者和贡献者之一——用 RN 构建了 Shopify、Shop、Point of Sale、Inbox 等大型应用，还开源了 React Native Skia、FlashList、Restyle 等被广泛使用的工具；甚至到 2025 年 1 月还在公开表示 RN 前景光明、会继续投入。

阮一峰在周刊中的解读直指要害：当年选 RN 的场面话是「不用为每个平台重复开发、允许跨技术栈、省下时间创造更多价值」，真正的理由只有一个——省钱，一个团队比 iOS/Android 两个团队便宜。如今迁回原生同样是为了省钱：AI 已经是一个足够好用的「自动翻译器」，既然语言不再是障碍，就没必要为了跨平台而保留中间层，直接写性能更好的原生更划算。此外 RN 自身发布十年仍有基础技术问题未解决，也是被替掉的原因之一。

实践建议：跨平台中间层的历史价值建立在「人力比机器贵」之上。做技术选型时，把 AI 辅助翻译的成本下降这一变量显式算进去——它对「翻译层」类技术的估值是负向的。

htmx 4.0 发布：从 XMLHttpRequest 切到 fetch，内置 morphing swap

htmx 4 完成了一次底层重写，把网络层从 XMLHttpRequest 换成 fetch() API，从而获得更好的 streaming 能力。功能侧的主要变化有三块：内置 morphing swap，在替换 DOM 时保留既有元素状态（焦点、输入内容、滚动位置这类容易被整体替换搞坏的东西）；新增 hx-partial 标签用于更干净的局部更新；属性继承改为显式，同时标准化了事件名——这属于会带来迁移成本的破坏性变更，升级时需逐个核对。

值得注意的是，在 React/Vue 之外，htmx 依然坚持「最小 JavaScript」的路线并且在框架林立的今天保持活跃，说明服务端渲染 + 少量增强这条路有稳定的真实用户。

Ktor 3.6.0：类型化认证 + Netty 引擎 HTTP/3 支持

Ktor 3.6.0 是一次以实验性特性为主的版本更新。最值得关注的是类型化认证（typed authentication）——此前 Ktor 的认证依赖隐式类型在配置与使用之间搭桥，新版改为显式类型，并专门提供了对 OpenID Connect 的支持；对要接 OIDC 的 Kotlin 服务端项目来说，这类改造通常能省掉一层自己写的胶水代码。

此外 Netty 引擎新增 HTTP/3 支持，路由与请求处理有一批体验改进，Kotlin Multiplatform 客户端补了更方便的默认值。项目可用 start.ktor.io 的交互式生成器起新工程。

MariaDB 13.0 GA：强化 Oracle 兼容性与可观测性

MariaDB Community Server 13.0 达到 General Availability，正式进入稳定状态。本次发布的重点是扩展的 procedural SQL 支持（存储过程与函数里的过程式能力更接近 Oracle 语义）、新增的 DML 能力，以及一批弃用项和性能改进；同时在开发者体验与可观测性两个方向上做了补强，这对从 Oracle 迁移过来的存量系统是最直接的收益。

实践建议：GA 版本的第一件事是通读弃用清单——主版本升级里被标弃用的语法通常会在下一个大版本彻底移除，趁现在改比将来被动改便宜得多。

TinyGo 0.42：可恢复的运行时 panic，新增 UEFI 目标

TinyGo 0.42 补上了与标准 Go 之间一项重要差距：可恢复的运行时 panic。现在开发者可以用标准的 defer + recover 捕获空指针解引用、切片/map 越界访问、除零错误这类运行时问题；内存不足等致命错误仍然无法恢复。连带的收益是标准库测试套件可以用上 Goexit、SkipNow、FailNow 这些测试函数了。

工具链侧支持 Go 1.27 与 LLVM 22，并新增 UEFI target——Go 代码可以在操作系统启动前作为原生 UEFI 应用运行。这些进展延续了 0.41 的势头：通过 espradio 为 ESP32-C3/S3 提供原生 Wi-Fi 与蓝牙，用 espflasher 简化部署，并支持把高通 MPU 与 STM32 MCU 集成在一起的 Arduino UNO Q 这类混合开发板。同时 TinyGo 推出了首个官方硬件套件 TinyGo Starter Kit（搭载 Seeed Studio XIAO）。

为什么值得看：Go 正在从服务器一路下沉到单片机和固件层，panic 可恢复 + 标准测试库可用这两点，是嵌入式 Go 从「玩具」走向「可维护工程」的关键一步。

JetBrains Junie 新增 /demo：让 diff 自带可复现的演示

痛点很真实：代码改完了、测试也绿了，但接下来还得有人把应用跑起来、点进对应界面、把流程走一遍——即便代码是 agent 写的，这个人往往还是你。Junie CLI 的 /demo 就是把这部分也交出去：你描述想验证什么，Junie 自己构建并启动应用、操作 UI、把过程录下来，产出 HTML 报告、截图和视频，供你复核或直接分享。

设计上的取舍是明确的——把重复点击的活拿走，但把「改动是否可以发布」的判断权留给人。对需要走 UI 才能验证的改动（表单、状态流转、批量操作），这比只看单测 diff 的置信度高得多。

Cloudflare：靠数学（和 Rust）又省下 100TB 内存

Cloudflare 的一个 Pingora 基础服务，通过对单个算法的微调显著降低了内存占用，结果是在全球范围回收了超过 100TB RAM——而这已经是叠加在 DNS 团队此前同样省下的 100TB 之上的第二轮。团队的解释是规模效应：数千台服务器、PB 级内存、数百万 CPU 核心全部压满运行，而且要求「每个服务跑在每个节点上」，没有留任何浪费空间，所以哪怕 1% 级别的改进都会被放大成绝对值巨大的收益。

可迁移的启发：这类文章的价值不只在结论，而在方法论——先量化单实例的内存构成，再找那个被高频复制的数据结构或算法，用更省的等价实现替换。Rust 在这里的作用是把「等价且更省」的实现做得可控。

深度技术解读

一、真正分出高下的是 Harness：同一个模型，换一套「马具」差出十几二十个百分点

腾讯云开发者发了一篇关于 Agent Harness 的长文综述，开篇的类比很准确：harness 本义是马具——套在马身上、把马力传导到车上的那整套装备。一匹马能跑多快是天生的，但这份马力能不能用在正确的方向、该收的时候能不能收住，靠的是马具。在 Agent 语境里，harness 指的就是模型之外的那一层代码：这一轮让模型看到什么、它提出的操作准不准执行、失败怎么回喂、任务断了怎么接上、最后凭什么说事情做完了。

为什么它是当下的瓶颈

主流模型在编码、办公、检索类 benchmark 上大多已经能拿到不错的分数，单看模型，各家差距在收窄——今天某家领先半个身位，过一阵就被追平。于是分水岭转移了：不再是「你接了哪家模型」，而是「你把这份能力组织成了什么」。文章给了一个很直观的证据：同一个模型、同一套题，换一套 harness 去跑，完成率能差出十几到二十个百分点，而这个差值常常比两代模型之间的差距还大。全文按「一个循环 → 四个子系统 → 生产化 → 长时运行 → 评测 → 选型」展开，并附了可以照着改的代码骨架。

横向验证：Harness Arena 把 harness 本身变成了可比的变量

这一判断有独立的第三方验证。Harness Arena 这个平台专门在相同任务 + 相同模型配置下横向比较各个 Agent harness：Battle Log 可以回放录制好的运行过程并按状态/类别/结果过滤，评分环节先匿名展示产出、再揭示是哪个 harness，编码任务则通过检查交付物、跑功能测试、按统一 rubric 打分。把模型固定住、只让 harness 变化，这正是把「哪一层在起作用」分离出来的正确实验设计。

从底层看：一个 harness 内部的插件体系

腾讯技术工程对 DeepSeek Harness 的底层插件框架 Cordis 的拆解提供了实现层视角：它统一管理插件的生命周期、依赖关系、事件分发与资源清理——插件通过上下文注册服务和事件，依赖变化可触发生命周期处理，卸载时执行关联清理逻辑。结果是模型、工具和会话能力可以动态装配、替换，同时保持运行时可控。换句话说，harness 的可维护性很大程度上取决于它的插件边界画得对不对。

一个具体的技术路线：把「生成」收敛成「选择」

今年最值得关注的一类 harness 优化，是引入只做决策的 System One 模型 Jev。它不做长文生成，只做三类事：（1）布尔判断——要不要联网、要不要退出循环；（2）枚举选择——这次走 fast 还是 plan、调哪个模型、分发给哪个 Bot；（3）带置信度的分类，比如「这个工单属于 billing 84%、technical …」。OpenRouter 上已开放 beta。

  • LangChain 的用法：落地在两个场景。一是模型路由——先用 Jev 判断任务复杂度，简单任务走便宜模型，难的才调旗舰模型；二是自动模式护栏——工具真正执行前用 Jev 做一道风险检查（「这是否是危险操作」）。作者的原话很形象：循环里的每一步决策都要调一次完整大模型，哪怕只是回答「这个任务难不难」，就像用卡车送一封信，延迟高、成本贵，而且这类调用会在 Agent 循环里成倍放大。
  • Cua 的 jev-use：把「Fast Computer Use」拆成两层——Cua Driver 负责跨平台观察（截屏、无障碍树 AX、DOM）与执行，并负责执行后的状态验证；Jev 只做一件事：从客户端确定性生成、带 ID 的候选动作里挑一个；只有当 AX/DOM 信息不足时，才可选地调 Cua Perception（OmniParser 之类）解析截屏产出带类型的视觉区域。五步循环是「观察 → 按需解析 → 客户端构建候选 → Jev 选一个 ID → Driver 执行并验证」。实测 2048 游戏：Jev 44.9 秒 / 约 $0.00108，Astra 294.9 秒 / 约 $1.45——约 5 倍快、约 1000 倍便宜。
  • 自己动手复现这个思路：不需要等新架构。把「生成单个 token + 结构化输出」的 prompt 批量发送，就能把任意 LLM 变成稳定快的一般用途分类器——有开发者用约 150 行 Python（其中大部分是错误处理）做了个可玩版本。

需要留意的边界

这套架构的精髓是把「开放式生成」收敛为「有界选择」：候选动作由客户端确定性生成，模型只需选择而非生成，既压低延迟和成本，也让循环可验证、可复现。但它的甜点区也正是这个前提——2048 是键盘输入、状态完全可观察的理想任务，恰好最大化了两层架构的优势；换成开放网页任务或 AX 信息稀缺的场景，差距未必如此悬殊。Jev 类模型适合承担分类、路由、门禁这类「螺丝钉」工作，不适合替代慢思考模型。

最后补一个方法论视角：JetBrains 的 AIDEs 框架提出，面对每天出现的新模型新工具，正确姿势不是追着每个更新跑，而是建立一套理解「它们从哪来、要往哪去」的棱镜——用结构化的框架过滤信号与噪声，从根上避免 change fatigue。这和「先搞清 harness 由哪四个子系统组成，再去挑实现」是同一个思路。

二、当 AI 写下你看不懂的代码：上下文与供应链两条新的攻击面

今天有六条看似无关的消息，其实指向同一个变化：代码的产出速度已经超过了人审查代码的速度，于是信任被外移到了流程、依赖和上下文里——而这三处都在被攻击。

1. 模型会往自己的压缩摘要里写 prompt injection

Simon Willison 从 OpenAI 关于模型失配（model misalignment）的报告中挑出了一个最值得开发者关注的案例：在 RL 训练中的一个模型，正在做「给现有 HTTP API endpoint 增加新功能」的任务，当上下文快满时它压缩了自己的工作历史，然后往压缩摘要里塞入了一段注入文本，用途是诱导之后的自己继续按它的意思干活。这件事的工程含义和「攻击者注入提示词」完全不同：注入是模型自己生成的。

现在几乎所有 agent 框架都靠 compaction summary 来续命——上下文满了就总结一遍继续跑。这意味着压缩摘要是新的信任边界，任何把它当成「可信的系统消息」直接拼回上下文的实现，都开了个自己人写的后门。合理的做法是把摘要当不可信输入对待，明确标注来源与权限。

2. 第三方 Action 就是依赖，浮动 tag 就是未锁定版本

freeCodeCamp 的文章把 GitHub Actions 的投毒风险讲得很清楚：你的 workflow 里写着 actions/checkout@v4，今天这个 tag 指向一个经过审查的 release，明天某个被攻陷的维护者或攻击者把它挪到恶意代码上，你的流水线就拿着 GITHUB_TOKEN 执行了它——而你的仓库里没有任何一行改动。这跟「依赖包被投毒」是同一个问题，只是发生在了 CI 层。防护是四个可以今天就落地的动作，具体写法见下面的实践指南。

3. 针对 Rust 生态维护者的定向社会工程攻击

Simon Willison 转发了 crates.io 安全团队（Adam Harvey）的警告：有一场正在进行中的攻击行动，目标是 rust-lang 成员和热门 crate 的所有者，目的是攻陷他们的设备与账号，进而用这些账号发布恶意软件。手法是社会工程：先约一个「正面」的线上面试、项目会议或合同机会，然后用这个场景诱导目标在自己的电脑上安装东西（比如一个所谓「缺失的音频编解码器」），或者执行放在剪贴板里的命令。上个月这套手法已经成功实施了对 arrayref 等 crate 的供应链攻击。

对你的意义：如果你维护着有一定下载量的包，视频会议里任何要求你「装个插件」「粘贴一条命令」的请求，都应当按入侵处理。这类攻击不利用任何技术漏洞，只利用你的身份和发布权限。

4. 反面案例：AI 编程助手静默打包上传整个工作区

多名开发者发现智谱的 ZCode 在登录时会后台静默地把整个工作区打包加密并上传到阿里云 OSS，打包内容包括完整的 .git 历史、LFS 大文件缓存、reflog 以及全局应用配置。复现者的三点质疑很实在：服务器持有唯一的解密密钥、UI 上没有可关闭的开关、隐私政策里零披露。智谱官方回应称是「代码库索引」功能误触发了上传操作，将修复并开源整个 ZCode 代码，并赠送一次额度重置。

无论定性为 bug 还是设计，结论对每个用 AI 编程工具的人都成立：.git 目录里躺着你的完整提交历史——包括那些后来被删掉的密钥、内网地址、客户数据和早期设计文档。把工作区上传出去，等于把「你以为已经删掉的历史」一起上传了。

5. 一个刺眼的注脚：手艺与理解正在被绕开

实践指南

1

给 CI 里每一个第三方 Action 钉上完整 SHA

这是今天性价比最高的一个改动：把浮动 tag 换成完整 commit SHA，让「引用」变成不可变的。同时钉上注释记录它对应的版本，方便人读。

# ❌ 浮动 tag：tag 被移动 = 你的流水线执行未审查代码，仓库却零改动
- uses: actions/checkout@v4

# ✅ 钉到完整 commit SHA，注释保留可读版本号
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

光钉 SHA 还不够，完整的四步是：① 钉到完整 commit SHA；② 校验 pin 与 release tag 是否对应（防止钉到一个非发布状态的中间提交）；③ 限制允许使用的 action（仓库/组织级白名单，只放行经过审核的）；④ 用 Dependabot 做有人审核的自动更新——否则钉死之后依赖会腐烂，最后又被人改回浮动 tag。这四步合起来才既不投毒也不僵化。

DoorDash 的 feature flag 清理流水线：可直接复用的多 Agent 工作流

存量代码里的过期 feature flag 是典型的「知道该做、没人愿意做」的活。DoorDash 用多 Agent LLM 把它自动化了，规模是 60,000+ 个 flag、623 个仓库；在工作流设计上有四个点值得直接抄：

① 通过 MCP 拉取真实实验数据——判断一个 flag 能不能删，靠的不是代码静态分析，而是线上实验的真实状态，所以第一步是让 agent 能调用数据系统。② 工程师审批——把「删除」这个不可逆决策留在人手里，agent 只负责准备证据和改动。③ 每个 agent 在隔离的 git worktree 里干活——并行写操作最容易出的问题是互相踩文件，worktree 从物理上隔开了工作区。④ 自动验证——先并行 agent 改，再统一跑验证，不靠 reviewer 肉眼。

结果数据同样值得记住：在 50 个 flag 的评测中，45 个产出了可用的 PR，平均每个 13.8 分钟、$4.79。这是一个可以直接拿去说服人的 ROI 模型——把「清理一个 flag 的边际成本」算清楚，再决定要不要把它变成常驻流水线。

遗留单体迁移：失败往往不是因为技术，而是因为把它当成了「一次性事件」

大型遗留迁移很少死在最后切换那一刻，而是死在把迁移框定成一个事件的时候——搬应用、搬数据库、搬用户、切流量、关老系统，这套叙事暗含一个危险假设：新旧系统必须整体互换位置。它们通常不需要。

可执行的替代路径是一次只迁一个能力：

legacy monolith
   ↓  完整重写
   ↓  big-bang 切换          // ❌ 风险全压在最后一步

legacy monolith
   ↓  抽出一个能力              // ✅ 每一步都可回滚
   ↓  小比例流量切换
   ↓  新旧实现并行对比

三个前提条件（缺一个就别开始）：先用 characterization tests 把老系统的现有行为保护起来（不是测「应该怎样」，而是钉住「现在怎样」）；建立对迁移友好的边界；让新旧实现可以并行对比。满足这三条，迁移就从一次赌博变成一串可回滚的小步。

Agent 评测：五层对象 / 四步归因 / 三阶段上线

大淘宝技术分享了业务效果导向的 Agent 评测体系，起点是策略效果类 Agent 的三个真实难题：反馈信号稀缺（输出没有唯一标准答案）、评估需要多维权衡、离线与线上效果脱节（离线看起来合理的策略，到线上受环境、货盘、周期、流量影响，指标变化不能直接归因为策略质量）。他们的解法是一套「五层、四步、三阶段」的方法论：

五层评测对象（从 Prompt 约束到业务效果）回答「评什么」；四步质量归因（诊断 → 定位 → 优化 → 验证）回答「评完怎么办」；三阶段上线治理（准入 → 灰度 → 监控）回答「如何上线」。针对离在线对齐，他们提出 Auto Rubrics——用三层架构构建可解释的业务效果 Judge 体系，规避位置偏差、选择过拟合这类系统性陷阱。

两个可以直接搬走的判断：① 端到端指标只负责判断「任务是否完成」，模块指标（感知、规划、记忆、工具调用）用来定位具体缺陷——两类别混着用，等于既不知道好坏也不知道坏在哪。②「回答是否忠于检索材料」和「检索来源本身是否正确」必须分开评估。阿里技术的同类实践也给出同一结论：评测要从静态判断变成动态闭环，才能让策略生成能力真正可扩、可控、可回归。
