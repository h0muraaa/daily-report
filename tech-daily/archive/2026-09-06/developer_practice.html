#02 深度技术解读
今天最值得钻进去的两个技术话题：一是把 Agent 当分布式系统来设计，二是厘清模型与 Harness 的分工边界。
// DEEP DIVE 01 · DISTRIBUTED SYSTEMS

超时不是失败，是"未知"：AI Agent 说到底就是分布式系统（TikTok SRE）

TikTok SRE 负责人 Salman Munaf 的演讲被 InfoQ 系统整理。他给出的起点问题非常尖锐：你的 Agent 去调用退款接口，网络超时了——那这笔退款到底成功没有？结论是超时从来不等于失败，它等于"未知"。而 Agent 面对失败的默认反应是重试；如果没有请求标识符（request identifiers）、幂等键（idempotency keys）和状态查询（status lookup），这种"先重试再说"的本能会让同一笔退款被执行两次。一旦模型开始调用外部服务、产生副作用，问题就不再只是模型问题，而是分布式系统问题——会遇到这个领域几十年来已被反复命名和研究的故障模式。

# 副作用操作：先查状态、再决定是否执行/重试 request_id = new_uuid() st = lookup_status(refund_endpoint, request_id) # 状态查询 if st == "UNKNOWN": # 超时 -> 未知，不是失败 res = call_refund(order, idempotency_key=request_id) # 幂等键 log_audit(seen=snapshot(order), did="refund", why=...) # 记"看到了什么"

演讲给出几条可直接落到工程里的原则：① 上下文能影响行动时，它就是状态——而状态会过期、会和权威数据冲突、会污染 Agent 后续行动，因此记忆要当缓存来设计：可失效、必须带来源信息。② 一个无害的模型，一旦能执行不安全的操作就会变危险，权限边界和审核点是安全设计的一部分。③ 普通日志不够用了，你必须记录 Agent 每一步看到了什么、据此做了什么、为什么认为这样做是对的，否则事后无法定位它的一次错误决策是怎么来的。

这条主线最近已经有真实案例印证：Anthropic 在费马大定理形式化项目里透露，最初的 Claude 集群失败恰恰不是败在数学上，而是"几十个 agent 跟丢了共享项目状态"，直到迁移到 Prove2Me 那种"命题—证明"的外部结构化 DAG 才跑通。换句话说，到了这个规模，"记忆"必须是外部、结构化、可失效的基础设施，而不是塞进 prompt 里的字符串。这与 TikTok SRE 的判断完全同构。

⚠ 落地清单：给 Agent 要调用的外部副作用接口统一加 idempotency_key；重试前先做 status lookup；把"记忆"做成带来源、可失效的缓存而非无限累积的对话；为每次工具调用落审计日志（所见 / 所为 / 所据）。
↳ 来源：InfoQ（TikTok SRE）·Gary Marcus 引 Chi Wang（Prove2Me）
// DEEP DIVE 02 · MODEL vs HARNESS

模型能内化"怎么用工具"，但内化不了"工具"：Astra 为什么离不开 Codex 这类 Harness

这几天满屏都是 GPT-6 Astra 操作 Blender 的演示，宝玉（@dotey）却从工程角度给了一个更清醒的判断：这恰恰证明不是 Codex 驾驭不了 Astra，而是 Astra 离不开 Codex 这个 Harness。模型每一轮训练确实会把很多"策略与判断"写进权重——什么时候该调工具、怎么拆任务、失败怎么回退、什么代码风格更好，所以 Astra 不需要你写一大段提示词教它操作 Blender，它自己"知道"。但模型本身能做的只有一件事：根据输入的 prompt 输出 token。它说"我要在 (x, y) 处画一条线"，那只是一段文本。

# 分工：模型出"策略"，Harness 出"执行" model: "在 (x,y) 画一条直线，然后截图给我确认" # 仅 token 输出 harness: apply_blender_op("stroke", x, y) # 真去执行并回读结果 harness: screenshot(); append_to_context() # 管理上下文窗口 harness: sandbox(allow_delete=false) # 权限兜底 / 恢复现场

真正去执行命令、把结果喂回给模型、管理上下文窗口、决定哪些操作需要用户确认、把它关进沙箱防止误删文件、任务中断后恢复现场——这些全部是 Harness 在干。可以内化的是"如何操作工具"，而"工具本身"无法被内化，就像一个人驾驶技术再好，把车拿走他也只能在原地比划方向盘。模型越强，对 Harness 的影响是两面的：一方面 Harness 可以变薄，少管"该怎么想"、多管"怎么执行"；另一方面模型想用的工具越多、想干的事越复杂，对 Harness 的执行能力、权限控制与状态管理要求反而更高。

这个框架能帮你读懂今天的很多新闻：GitHub HydraFusion、AWS Kiro Crew、Spotify Portal 本质都在加强 Harness/编排层，而不是换更强的单模型；"Skill 规则反而束缚模型"的讨论（下文实践 P4）其实也在说同一件事——策略正在下沉进模型，外壳层的规则要跟着瘦身。对要自建 agent 产品的团队，结论是：把工程重心放在外壳的执行、权限、记忆与可观测性上，那才是模型给不了你的部分。

↳ 来源：宝玉(@dotey)

show-me Skill：教 Agent 用图说话，而不是大段散文

↳ meng shao(@shao__meng)
# cleanbranch / /cleanbranch

cleanbranch Skill：自动提取"最小特性分支"

一段可直接注册进 agent 的 Skill：从当前杂乱的改动里推断真正的 feature，基于你选的 base（当前 PR base 或仓库默认分支）开一条干净分支，只把该特性端到端需要的东西带过去（含必要集成与测试），主动排除无关重构，并优先用独立 worktree 保护原分支与未提交文件。适合"一个分支干到一半变成一团乱麻"的开发日常。

#04 实践指南
六条今天就能用上的实操经验，覆盖 agent 自主度校准、token 成本控制、安全补丁评审边界、规则文件瘦身与学习路线。
PRACTICE 01 · AGENT AUTONOMY

Andrew Ng：别再让 Coding Agent 无人值守地跑几小时——校准自主度才是核心技能

DeepLearning.AI 转述 Andrew Ng 对一线 AI 工程工作流的拆解：让 coding agent 自主跑数小时既贵又常常无效。真正被顶尖实践者使用的工作流是"熟练的人工判断 + 高度迭代的计划 + 频繁的输出验证"。你的时间重心正从"一行行写代码"转移到"做架构与写规格"，同时必须学会三件事：指挥 agent 的工作流、校准它的自主度（多少步可以自己走、哪些点必须停下确认）、建立健壮的测试机制。Ng 把这归纳为使用 coding agent 的五项基础技能，原文以公开信形式发布。

↳ 来源：DeepLearning.AI(@DeepLearningAI)
PRACTICE 02 · COST ENGINEERING

Spotify Portal：AI Coding 的钱大多花在 I/O 上——把"体力活"路由给小模型，token 直降 90%

Spotify 工程团队发现 Claude Code 的 token 大量烧在几乎不需要推理的杂活上：为回答一个方法的问题读五个文件、照着旁边二十个测试文件"模式套娃"再生成一个测试、开完会更新文档——这些用前沿大模型属于"严重高配"。解法是让声明式 Agent 跑在临时运行时上（作者类比"给 agent 用的 AWS Lambda"），只写一份 YAML 声明指令/模型/温度/MCP 工具即可。作者建了两个都用 Gemini 2.5 Flash 当廉价工作模型的 Mode：

  • 批量读取器：替 Claude 读多个大文件并作答，指令要求只输出结构化要点、每条以确切名称/类型/行号开头、不要寒暄——本质是把大语料压成 Claude 能直接消费的摘要。
  • 样板代码生成器：生成可从现有模式预测的测试/脚手架/类型桩，指令要求严格模仿参考文件的模式与风格、只输出代码（否则模型会包上 markdown 围栏让 Claude 再花 token 解析）。

路由最初写在 CLAUDE.md 里，但那是"建议性"的、模型可以无视，且每个项目都要复制一份；于是改成名为 shunt 的插件做三层强制路由。效果：Claude Code 的 token 消耗下降约 90%。

# portal mode —— 声明式"体力活"agent（示意） agent: bulk-reader model: gemini-2.5-flash instructions: | 只输出结构化要点；每条以 名称/类型/行号 开头； 不寒暄、不铺垫；禁止 markdown 围栏。 mcp: [read, glob]
↳ 来源：meng shao(@shao__meng) 译 Spotify Engineering
PRACTICE 03 · TRUST BOUNDARY · SECURITY

1Password 实测 6000+ AI 生成补丁：安全修复只有 26% 成功率，4.5% 引入新漏洞

1Password 的研究人员用 Claude 与 ChatGPT 对真实漏洞跑了 6000+ 个 AI 生成的补丁，结论相当不客气：AI 只有约 26% 的几率真正修好漏洞；约一半情况下它根本没修掉原始 bug；4.5% 的情况下反而引入了一个此前不存在的新漏洞。更反直觉的是，审一个 AI 生成的安全补丁所花的力气，往往比自己直接写修复更大。原话结论是："一个完全由 LLM 生成、未经人工 review 的补丁，期望值在大幅为负。"对把 AI 接进安全修复管线的团队，这是一个必须正视的信任边界——自动补丁至少要过独立的验证与人工评审，而不是直接合入。

↳ 来源：Gary Marcus(@GaryMarcus)
