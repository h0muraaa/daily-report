01Pi 的爆火真相：只给模型一个 bash 的极简 Harness，一次次赢过 Claude Code 和 Codex

AGENT2025 年底在圣诞前后突然走红的 Pi，没有塞满几十个工具、没有复杂的记忆系统、没有云端方案，基本上只给模型一个 bash，却在各种 Benchmark 与 Harness 横向对比中反复胜过 Claude Code 和 Codex。作者 Mario Zechner 是欧洲资深开源开发者，曾创建跨平台游戏框架 libGDX。

动机值得每个依赖现成 Agent 的人对照：Mario 最初很喜欢 Claude Code 简单可预测的工作方式，但随着 Anthropic 不断加功能、修改系统提示词和工具定义，他的工作流被动地反复受影响；更让他不满的是，许多 Harness 会在用户无法感知的情况下向模型注入额外上下文，开发者很难真正掌握模型看到了什么、调用了什么工具、为什么做出某个决定。Pi 的更大关注度还与 Flask 作者 Armin Ronacher、后来开发 OpenClaw 的 Peter Steinberger 有关——三人 2025 年 5 月在维也纳共同开发 VibeTunnel，逐渐形成一套让模型通过写代码、执行代码来完成任务的设计思路，被社区称为"维也纳 Agent 编程学派"。

02MIT CSAIL 的 JAZ：只有 invoke 一个原语，没有记忆系统，用一半成本胜过 Letta 8%

PAPER一篇来自 MIT CSAIL 的论文给出了"我的 harness 到底该多复杂"的实证答案。JAZ 是一个只暴露一个原语 invoke 的 agent 框架：LLM 写代码，可以在代码里递归调用 invoke，并把所有输入和历史当作代码环境里的变量直接访问。

结果相当反直觉：仅靠 prompting、完全没有记忆系统，它在 StuLife 的 recall-heavy 部分比 Letta（MemGPT）高 8%，成本只有一半；在 AppWorld 上比自改进方法 ACE 高 4%，成本更低。关键的设计取舍是：记忆与自改进不再做成独立子系统，而是 agent 在循环内部自己写的代码；需要强制的约束与监控则交给 hooks。对正在给 Agent 堆记忆层、堆工具的团队，这是一份值得精读的反向证据。

04100 万行数据实测：PostgreSQL 里 JSON 与 JSONB 的查询性能差 7 倍

DATABASE一篇基于100 万行真实数据的基准测试把 PostgreSQL 的 JSON 与 JSONB 之争讲清楚了：查询速度差 7 倍、存储空间差 26%、写入速度差 31%。差别来自存储格式——JSON 是纯文本原样保存（保留空格、键顺序、重复键），JSONB 是解析后的二进制（去掉空格、键顺序不保证、重复键去重）。

功能上的硬边界更关键：只有 JSONB 支持 GIN 索引，也只有它支持 @>（包含检查）、?（键存在性）、?&（多键同时存在）这些高级运算符；JSON 只有 -> 和 ->>。一句话总结原文的取舍：JSON = 懒模式（存得快、查得慢），JSONB = 认真模式（存得慢一点、查起来飞快）。结论很直白——别为了省那 31% 的写入时间，在查询时付出 7 倍的代价。

05typesafe/jev-router：缓存感知的模型路由器，实测多解 82% 任务

INFRAOpenRouter 推出 typesafe/jev-router，由 TypeSafe 的决策模型 Jev 驱动。每一轮开始前，Jev 读取你的 prompt，对难度和精度要求打分，并判断四件事：更大的模型或更多 effort 是否有帮助、更便宜的模型是否够用、任务本身是否已经变了。

真正的差异化在功能表之外：多数 router 按"每条消息"选模型，每次切换都会丢掉缓存的对话，于是要按全价让新模型把整段历史重读一遍；而且它们通常按任务类型而非难度路由，简单和困难的 coding 任务会被分到同一档模型。Jev Router 的策略是：为一个 session 保留一个"能干活"的模型，能不换模型就只升降 effort；只有当预期收益大于成本（成本中包含会丢失的缓存）才真正切换。另一个工程细节值得注意——Jev 调用超时或返回非法输出时，请求直接失败，而不是 fallback 到别的 router，以保证路由决策的可预测性。实测数据：4 个 agent benchmark 上比 OpenRouter 自家 Auto Router 多解 82% 任务（237 vs 130，共 423）；5 个 benchmark 上 median TTFT 快于所有被测 router。隐私方面 Jev 运行在零数据保留（ZDR）条款下，附件从不发给 Jev。

02 / 深度技术解读

① "Plan Mode 已死"？极简 Harness 与人类审批点的拉锯

今天有两条独立线索同时指向"Harness 应该更简单"，也有第三条线索明确唱反调。

正方线索一：Hacker News 上今天传播很广的文章《Plan Mode 已死》（aymannadeem.com，经 Viking 转述）。核心论点很直接——大模型能力在飞跃，写一份"给人看的冗长 plan"的需求已经大幅下降。它提倡的流程是 understand → act → inspect → clarify → adjust → act again：不再先产出一份要人批准的 spec，而是一边做一边改。Viking 的补充更尖锐：很多 skills 也已经过时，在不少场景下 skills 只会限制强模型的行为方式，不如让它自由发挥——尤其对于最新的 Opus 5.5，他说自己已经卸载了非常多 skills，也很久没用过 plan 模式。

正方线索二：热榜里的 Pi（只给一个 bash）与 MIT CSAIL 的 JAZ（只有 invoke 一个原语、连记忆系统都不要）。两者的共同结论是：把复杂度花在"替模型写 spec、替模型记东西"上，收益可能是负的；模型自己写代码、自己管理状态，反而更强也更便宜。

反方线索：同一天 Google Antigravity 2.0 专门上线了 planning mode。输入 /plan 后 agent 会退后一步思考任务、做大量调研，再生成一份 implementation plan 供你 review，并请求批准后才开始执行；你也可以在 prompt 里自然语言要一个更轻量的 plan。

把三方放在一起看，冲突其实是表面的。真正的分界线不是"要不要 plan"，而是plan 的定位：

定位形态今天的价值
交付物（给人读的 spec）冗长文档，先批准后动手随模型能力提升而下降——模型自己能在执行中修正，写死 spec 反而制造返工
检查点（人类审批 / 成本控制）轻量、聚焦风险与不可逆操作上升——高风险或不可逆任务仍需显式的人工介入点

可落地的判断规则：任务是否可自动验证？如果存在确定性的 verifier（测试、grader、编译通过、benchmark 分数），就把 loop 交给模型、把复杂度花在 verifier 上；如果不可逆或没有可靠 verifier（线上变更、对外发布、数据迁移），就保留一个轻量的人类检查点。Antigravity 的 /plan 与 Pi 的一个 bash，服务的是两类不同任务，不构成矛盾。

给一线的直接建议：先审计你当前的 harness/skills 集合，把"限制模型自由的"和"提供模型无法自行获得的信号的"分开——前者大概率可以删，后者才是护城河。这与昨天讨论过的"判断层拆出生成层"是同一件事的两面。
📎 来源：[Viking @vikingmute] Plan Mode 已死 · [InfoQ] Pi 爆火真相 · [elvis @omarsar0] JAZ · [Google Antigravity] Antigravity 2.0 planning mode

② Agent 的成本结构：缓存、路由与 effort 档位，比"换便宜模型"更重要

热榜 05 的 Jev Router 之所以要"缓存感知"，是因为它触碰到了 Agent 账单的真正大头：每跑一轮，都要把之前累积的整段对话重新发给模型一遍。

宝玉对 Anthropic 官方文章的解读把这件事量化了。Opus 5.5 的 API 单价看起来降了 20%（缓存读取降了 60%），但账单高低其实取决于任务跑了多少轮——轮数一多，重发的历史就吃掉全部差价。算下来平均一个会话能便宜约 31%；Anthropic 内部用 44 张客服工单测试，从 Opus 4.8 换到 Opus 5.5 成本降约 18%，再做一次提示词审查后总共比原来低约 25%。订阅用户（Pro / Max / Team）的额度按新价折算，能比用 Opus 5 时多撑 25% 左右。

缓存的边界条件是最容易被忽略、也最贵的一环：

  • 保留时长不同：订阅用户的缓存保留 1 小时，而 API 只保留 5 分钟——离开 6 分钟，12 万 token 上下文的下一次请求会从 $0.02 涨到 $0.60。
  • 前缀必须完全一致：缓存只复用和上一轮开头完全相同的部分。
  • 这些动作会让缓存失效：中途切换模型、接入或断开 MCP 服务器、第一次打开快速模式——下一轮都要按更贵的写入价重新付费。
  • 清理方式要选对：换到不相关的任务用 /clear 清空对话；想保留前情用 /compact 压缩，但必须在缓存失效之前做，否则更贵。

另一半是 effort 档位。Anthropic Claude Code 团队的 Thariq Shihipar 给出了一个精准的类比：同样是做一件事，别人给你 12 小时，你会理解为"尽全力做好"；只给你 1 小时，你会先交付一个满足要求的版本，等反馈再迭代。effort 就是这个"时间预算"：高 effort 意味着模型做更多自主判断和验证，低 effort 意味着快速给一个可迭代的起点。他基于 Terminal-Bench 3.0 的失败数据得出全文最有洞察力的结论：提高 effort 主要减少"遗漏边界情况"导致的失败，但无法修复"方向/思路错误"导致的失败——它不会让一个想错方案的模型变对，只会把同一个方案打磨得更严密。典型证据是一个 HTML 安全检查任务（要求封堵所有向页面走私 JavaScript 的方式）：Fable 5.1 在低 effort 下只有 1/5，在超高 effort 下达到 5/5；低 effort 约 2 分钟一遍写完、只用手写页面测一下，高 effort 约 33 分钟，会对抗性审查自己的初稿、读解析器源码找 bug、跑标准 XSS 测试套件，甚至写一个随机文档模糊测试器。

由此得到的成本优化顺序是：先把 cache 命中率做对，再把 effort 档位选对，最后才考虑换更便宜的模型——前两项是无损的，换模型是有损的。

04 / 实践指南

4.1 effort 档位：调的是"验证强度"，不是"能力上限"

理解了 effort 的本质（见深度解读 ②），档位选择就有了原则而非玄学——按任务需要的验证强度选，而不是按任务"看起来难不难"选。Thariq 基于实测给出的对应关系：

档位适用场景心智模型
low头脑风暴、画草图、小改动要的是快，随时能插手
medium大部分日常开发，如实现新功能给 1 小时：先交可迭代的版本
high需要验证、边界情况多的活，如老代码库修 bug给 12 小时：自己反复打磨、检查
max完全自主攻克难题，如从零搭 App 并验证、给关键软件找安全漏洞给足时间，允许它自己拿主意

在 Claude Code 里输入 /effort 即可切换，对话中途也能换。两个关键提醒：只有最新的 Opus 5.5 和 Fable 5.1 中途切换 effort 不会破坏 prompt cache，早期模型会让缓存失效；另外 Opus 5.5 默认推理强度是 medium，比 Opus 5 的默认 high 低一档，但同一档位下 Opus 5.5 想得更多，给 Opus 5 调好的档位不要照搬。日常活用 medium，卡住了调 high，批量重命名这类机械活用 low。模型分工上：日常用 Opus 5.5；开到 xhigh 还在同一个问题上连卡两次，再换更贵的模型，解决完立刻切回来；搜代码、读日志的 subagent 交给 Sonnet 或 Haiku，写代码留在 Opus 5.5。

4.2 缓存友好的 Claude Code 使用清单

把深度解读 ② 里的规则落成一张可执行清单，按此顺序检查，通常能省下两位数百分比的账单，且不损失任何能力：

# 1. 会话边界要清晰
换到不相关任务 → /clear            # 别在同一会话里不断切换主题
想保留前情     → /compact          # 但必须在缓存失效之前执行

# 2. 别打断缓存前缀
中途切模型 / 接或断 MCP / 第一次开快速模式
  → 下一轮按更贵的写入价重付

# 3. 注意保留时长的差异
订阅用户缓存保留 1 小时；API 仅 5 分钟
API 场景离开 6 分钟：12 万 token 的下一轮 $0.02 → $0.60

# 4. 长任务不要挂着离开
撞上 5 小时限额时，Claude Code 会先找一个合适的位置停下，
用一笔固定额度收尾（从每周额度里扣），而不是把多文件改动改到一半硬断

最后一条是今天新上线的行为，值得单独说明：Claude 的付费订阅本来有两道限额——滚动计算的 5 小时窗口和每周总量上限，网页版、桌面端、Claude Code 共用一个额度池。以前 5 小时额度一用完，Claude Code 当场就停，如果它正在做跨多文件的改动，停下时可能 5 个文件只改了 3 个，代码连编译都过不了；几个小时后额度恢复，你还得先弄清楚它停在哪、改了哪些。现在它会尽量把手头能收尾的部分收掉，停在一个方便接着干的位置。规则是：Pro 用户每周能用一次收尾额度，Max 和 Team 高级席位每次撞上 5 小时限额都能用；收尾后还想继续，可开启额外用量按 API 标准价计费。

4.3 让 Agent 主动"搞破坏"：worst-case 布局审查与 i18n 审核

一个成本极低、立刻能用的实践：让 agent 往界面里塞各种 edge case，然后对着截图做 UI review，再按问题清单修。Emil Kowalski 的做法是让 AI 尝试"弄坏"自己刚做的东西——塞入大量数据、超长名字、异常邮箱、极端数字，构造最坏情况的布局。Viking 指出这个技巧在 i18n 审核上尤其好使：不同语言字符长度差异极大，中文和英文的长度差非常容易把界面搞乱，靠人肉切换语言逐个目测效率很低。

更值得抄的是协作方式：让一个 agent 只负责 audit 并截图，把结果交给另一个 agent 去修，而不是在同一条对话里又找问题又改代码——Viking 的经验是后者模型容易"自我开脱"，把自己写的代码判为没问题。这本质上是把 code review 的"作者与审查者分离"原则搬到了 Agent 工作流里。类似的思路在纯后端场景也适用：让一个 agent 写对抗性测试，另一个 agent 修。

📎 来源：[Viking @vikingmute] worst-case 布局审查 · [Viking @vikingmute] 用这个技巧做 i18n 审核

4.4 PostgreSQL 选型：JSON 还是 JSONB，按"读多还是写多"决策

基于 100 万行实测数据（见热榜 04），决策树其实很短：

  • 要对 JSON 内部字段做查询、过滤、聚合，或需要索引 → 一律用 JSONB。它独占 GIN 索引与 @> / ? / ?& 运算符，查询性能优势是 7 倍量级，这个差距不是靠加机器能补回来的。
  • 只是当作不透明载荷存储、写入吞吐是唯一瓶颈 → 才可以考虑 JSON，省下约 31% 的写入时间。
  • 需要保真原样（保留空格、键顺序、重复键，例如做审计留档或需原样回放） → 必须用 JSON，因为 JSONB 会去空格、不保证键顺序、并去掉重复键。这一条是文档里最容易被忽略的坑，且无法通过后续配置挽回。
  • 存储空间敏感 → JSONB 反而更省，实测小约 26%。

一句话原则：把 31% 的写入收益和 7 倍的查询代价放在一起比较，绝大多数业务表都该选 JSONB；真正需要 JSON 的场景是"保真"而不是"性能"。

📎 来源：[dbaplus社群] 100 万行数据实测：PostgreSQL 用 JSON 还是 JSONB

4.5 用 GitHub issue intents 自动做 issue 分诊

维护者最枯燥的工作之一是保持 issue 元数据最新。GitHub 的 issue intents 让这件事可以自动化，同时保留对人的完全控制权：为意图建议设置置信度阈值、审查 agent 的推理过程、再让日常性的变更自动应用。整个流程跑在 GitHub 的 agentic workflow 上，agent 的产出（safe outputs）与日志都可以在 GitHub Actions 里逐条检查。

落地路径（官方教程章节顺序）：先理解 issue 元数据分诊的痛点 → 了解意图建议与理由（rationale）的生成方式 → 在仓库设置里调整自动化级别 → 测试自动打标签与设置优先级 → 配置 issue intent agentic workflow → 检查 safe outputs 与 agent 日志 → 最后用 Copilot 与 API 自定义 issue intents。对 issue 量大的项目，先用高置信度阈值 + 人工复核跑一段时间，观察 agent 的推理质量，再逐步放宽自动化级别，是风险最低的引入方式。

📎 来源：[GitHub] How to automate issue metadata with GitHub issue intents

4.6 给初级工程师的建议：别恐慌 AI，但也别把判断力外包出去

seangoedecke 的《Advice to a beginning software engineer》开场就很清醒：一般来说，你应该怀疑那些试图给你建议的工程师——这个行业既宽又变化极快，没人真正知道确定答案，而"我们并不处在平常时期"：LLM 与 AI agent 的到来是他职业生涯中软件工程最大的变化，甚至可能是有史以来最大的。他的核心建议可以压缩成三条：

  • 别玩游戏，把注意力放在真正理解你在做什么——保持尽责、努力弄懂手头的系统，而不是参与政治斗争。
  • 不要为 AI 恐慌，也不要避开它——继续思考，把 AI 当作工具而不是判断力的替代品。
  • 不要信 ZIRP 时代的建议——过去十年"扩张、融资、抢人"的经验，在今天的约束下往往是有害的。

把这套标准反过来用在自己身上同样成立：当 Agent 给出一个看起来合理的方案时，"它说得头头是道"和"它是对的"是两件事，尤其在没有确定性 verifier 的场景下。

4.7 花絮：1 分钟、约 2 美元，做出一支产品发布视频

一条给前端/全栈工程师的开胃菜。有人为一家 AI 推理初创公司做的发布视频，只用了 1 分钟、花费约 2 美元；过去同类视频往往需要数周甚至数月，还要协调代理商。更值得关注的是技术路线：整个过程没有使用任何视频生成模型，也没有使用额外的库，只用了 JavaScript、Playwright 和 FFmpeg——Claude 编写网页动画，再用 Playwright 把它录制下来、FFmpeg 合成视频。（同一天的另一个复现案例用的是 Remotion（React/JS 视频框架）+ KaTeX 渲染公式，TTS 则用了微软免费的 EdgeTTS。）对开发者而言，这条路径的启发在于："视频"未必需要视频模型，把已有的浏览器渲染与录制能力串起来就够了，而且产物是代码，完全可版本化、可参数化。
