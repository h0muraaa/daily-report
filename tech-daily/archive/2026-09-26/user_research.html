今日要点

5 条最值得用户体验从业者停下来想一想的信号。

01AI 助手正在取代搜索引擎，成为产品被发现的第一入口

Notion 联合创始人 Akshay Kothari 披露了一个值得所有用户研究者警惕的数据：在 Notion 经典的获客归因问题「你是如何听说我们的？」里，ChatGPT、Claude 等 AI 工具已经超过所有传统渠道，成为第一大来源。他用「Gradually, then suddenly」（先是缓慢地，然后突然地）形容这次转变——这不是一次渠道波动，而是用户旅程起点的结构性位移。

对研究的冲击是双重的。一方面，传统「发现渠道」问卷选项正在失效：受访者很难回忆起自己是被哪一次 AI 对话说服的，归因链条从「一次点击」变成了「一段多轮对话」。另一方面，围绕「AI 答案里如何呈现自己」的 GEO（生成式引擎优化）正在成为独立学科——向阳乔木的公开课把它拆成入口层、信源层、数据层、技术层、执行层、交易层、治理层七个层次，并提出「AI 可见度监测 → AI 效果归因 → AI 内容与知识工程」的方法进阶路径。

行动提示：如果你的用户旅程地图仍以「搜索 / 社交 / 口碑」为起点，现在需要补一条「与 AI 对话」的主干道，并重新设计捕捉它的方法——问卷问不出来，得靠对话回放与行为日志。

02Anthropic 用两周把 claude.ai 与 Claude 桌面端核心体验提速约 3 倍

花叔复盘了 Anthropic 三位工程师在 claude.dev 上发布的性能冲刺报告，数字很具体：打开 claude.ai 到可以打字，从 3.1 秒降到 0.55 秒；桌面端新开 Claude Code 会话，从 0.8 秒降到 0.3 秒；加载 Cowork 云端会话，从 2.6 秒降到 0.73 秒（均按 P75 计）。四类核心操作共 13 项指标的几何平均提速 3.1 倍，团队估算每天为用户省下数万小时的等待。

执行方式本身也值得研究者注意：整个冲刺跑在一个 Slack 频道里，每个讨论串里都有 Claude 参与——它负责找瓶颈、搭 benchmark、写代码提 PR、盯每一次部署；人只负责定目标、做取舍、审批每一个改动。两周合入 3000 多个改动，零线上事故和回滚。

研究视角：这份报告最有价值的一句话是「只要 Claude 能把一件事衡量出来，它就能把这件事变快」。感知性能是可以被拆解成可测指标的。而像「打开就能打字」这种没有页面跳转的等待，恰恰是用户最容易抱怨、产品团队最容易忽略的体验债务——它不出现在任何一次功能评审里，却每天发生几十次。

来源: 花叔

03Notion 同一天动了两处「看起来简单」的地方：移动端评论与行列级权限

移动端评论正在被原生重构。此前打开评论的体验「更像一个表单」（网页弹层），新版改用更多移动端设计语言、速度更快，目标是「感觉更像在发消息」。这件事的价值不在视觉改版，而在于把「评论」从一个页面级功能还原为一种即时沟通行为——用户在手机上只是想回一句话，不是想填一张表。

另一处是呼声第一的功能：数据库行 / 列级权限终于上线，可以精确控制谁能查看和编辑每一个属性。Notion 产品负责人 Akshay Kothari 的表述很坦诚：「这件事表面上看起来简单，但花了好几年反复推敲和迭代。」

设计命题：权限模型的真正难点从来不是能力，而是如何把「谁能看哪一列」这种矩阵式的复杂关系，包装成用户不用读文档就敢点下去的控件。两个案例合起来说的是同一件事——把复杂性留在系统里，把确定性交给用户。

来源: Notion · 移动端评论 来源: Notion · 行列权限 来源: Akshay Kothari

04被专业用户点名「精心设计」：Meta Muse 的授权与连接器流程

多位重度用户拆解了 Meta Muse 的连接器体验，评价出奇一致。歸藏认为它的上下文获取流程「一定是精心设计过的」：Steam 给一个选项、一个按钮，填一下 token 就好；DeepSeek 给一个输入框填 key，而且模型不会直接读到 key；B 站直接给一张二维码。向阳乔木补充，自定义连接器只需对话就能创建，背后复杂度都被藏起来，「最多让用户提供个 API」；没有 API 时，它甚至会用浏览器读取 cookie 来获取数据。

为什么值得研究：授权是整条 agent 链路里最让用户焦虑的一步——既怕麻烦，也怕交出去的东西被滥用。Muse 的做法把认知负荷压到最低，同时用「模型读不到你的 key」这种明确承诺来交换信任。这是把「信任」当作一等设计目标，而不是安全团队的合规附注。

来源: 歸藏(guizang.ai) 来源: 向阳乔木

05Claude Code 为「额度用尽」重新设计了失败体验

Claude Code 上线了一个细节改动：当任务执行到一半撞上 5 小时限额时，它不再当场硬停，而是先找一个合适的收尾点停下，把能收的部分收掉，停在一个方便接着干的位置；收尾动用一小笔固定额度，从每周额度里扣。

这个改动针对的痛点非常具体——以前如果它正在做跨多文件的改动，停下来时可能 5 个文件只改了 3 个，代码连编译都过不了；几小时后额度恢复，用户还得先弄清它停在哪、改了哪些，才能继续。

这是典型的「失败路径设计」。系统一定会遇到资源耗尽、网络中断、权限失效，而绝大多数产品只优化成功路径。把中断点包装成可预期的状态、并把恢复成本降到最低，是 agent 类产品必须补上的一课——对长时间自主任务尤其如此，用户的信任往往正是在「出问题时它表现如何」这一刻建立或崩塌的。

设计趋势洞察

两个正在成形的方向，各配一条可落地的设计判断。

Trend 01

Agent 的「信任界面」正在成为新的设计战场

三条互不相干的信号，指向同一件事。

① 授权流程的重新设计

Muse 把 OAuth、API key、扫码、cookie 抽取这些技术动作，统一降维成「一个按钮 / 一个输入框 / 一张二维码」，并明确告知「模型读不到你的 key」。这不是某个组件的优化，而是把信任当作一等设计目标。

② 决策过程的可解释化

OpenRouter 发布 Jev Router 时，专门做了一个 routing insights panel，展示它在每一轮对话里选了哪个模型、以及背后的评分维度——任务类型、难度、精度需求、换更大模型能带来多少收益。也就是说，当系统替用户做决定时，产品要把「为什么这么选」摊开给用户看，而不是黑箱输出结果。反面的教材同样清晰：Peter Yang 让 Grok Bot 和 Muse 追踪同一段日本行程，Muse 报出的价格高出 1000 多美元，追问原因时它才说自己搜的是 Duffel 而不是 Google Flights——用户无法理解它的信息源选择，信任瞬间打折。

③ 人在环的确认机制

傅盛记录了他让 GPT-6 接管微信、连续几小时给 50 位公司骨干写专属祝福、并逐条回复 70 多条收到的祝福（120 多条消息零失误）的过程。最值得注意的不是自动化程度，而是他刻意保留的机制：「它找到一个人，先问我：他做什么？我对他有什么期待？我随口讲，它整理成文字给我看。我说『发』，它才发。发完核对、存档，再找下一个。」他还在朋友圈坦白这不是自己逐字敲的、但确实是自己一点一点描述的，结果接近一半同事回复说感动。

设计洞察：Agent 的能力越强，「我不知道它会做什么」的焦虑就越强。可解释性、授权边界、确认节点——这三者正在从「加分项」变成「入场券」。设计目标不是让 agent 显得更聪明，而是让用户始终觉得「它在我的控制之内」。山行AI 对 Anthropic 金融 Agent 参考架构的分析给出了一个精炼的说法：能力可以自动化，责任不能自动转移——工作底稿由 Agent 准备，最终结果必须由专业人员签核。这条边界如何呈现给用户，本质上就是界面设计问题。
来源: 歸藏(guizang.ai) · Muse 连接器 来源: OpenRouter · Jev Router 来源: OpenRouter · routing insights 来源: Peter Yang · Muse 比价 来源: 傅盛 来源: 山行AI · 金融 Agent 签核
Trend 02

C 端 Agent 正从「效率工具」转向「关系与闲暇」

小扎近期访谈里谈了 Muse 的三个差异化，最值得玩味的是第二条：Meta 擅长连接人，Muse 不只替人干活，还要帮人照顾家人、维系朋友关系。访谈里出现了一个词「fleet」（舰队），指所有用户的 Muse agent 组成的群体——思路是让 agent 从群体中学习匿名经验，再结合各自用户的需求提出新建议。

与此同时，Frank Wang 提出了一个更激进的产品判断：「人类正在从需要勤奋才能生存的时代，进入到一个需要认真面对闲暇的时代。勤奋时代，提效就是生产力；闲暇时代，人最多的就是时间。」因此他认为创业者太忙反而容易错失大机会——该做的是帮人消磨时间（旅游、麻将、抖音、X），而不是帮人提效。

这个转向在傅盛的案例里已经有了真实的落地形态：AI 代写祝福之所以让人感动，不是因为省了时间，而是因为它完成了关系维系这个动作——「以前那些搁着没回的祝福，这次每个人都收到了回复。」

设计洞察与张力：Peter Yang 提出了一个不能不面对的问题——「Muse 的 UI 和吉祥物非常出色，但底层模型有多聪明值得怀疑；如果它不够聪明，倒也说得通，因为这东西是要 scale 到十亿人的。」这提醒我们：面向十亿级用户的 agent，交互深度与模型能力必然要做取舍。你不可能指望每个用户都学会写复杂 prompt，所以界面必须比模型更宽容。做 C 端 agent 的用户研究者，恐怕需要重新定义成功指标——不是任务完成率或提效比，而是「关系是否被维持住、用户是否感到被理解」。
来源: Frank Wang 玉伯 · 小扎谈 Muse 来源: Frank Wang 玉伯 · 闲暇时代 来源: Peter Yang · Muse 的取舍 来源: 傅盛

产品体验点评

两个可复用的产品设计案例，含设计决策的动机与代价。

点评一 · Codex 的导航重构：当「内容越来越多」，信息架构必须重做

Codex 这次更新把界面导航大改：左侧新增导航栏，把插件、定时任务、站点、项目、地图、PR 都收进左栏，并新增「资源库」和「图像」两个页面。资源库汇总用户创建的图像、图片、文件夹、收藏，以及自己创作的文档和 AI 生成的图像文档；图像页承接 ChatGPT 原有的图片页，包含 GPT-Image 的模板和提示词。

用户的评价给出了最朴素也最准确的理由：「不然之前全放在顶部，随着项目和聊天越来越多，每次找顶部那几个入口都得往回滚，挺烦的。」——顶栏导航在内容量小的时候没问题，一旦规模上去就会失效，因为它的容量是固定的，而用户的资产是增长的。

一个值得记的细节

评论者指出，藏师傅的 CodePilot 几个月前就加了资源库，并且做到了「从资源库的结果直接跳回聊天里看具体是怎么做的」，方便复用素材给其他模型调用。资产页不只是收纳，它应该能反向追溯到生成过程——这是 AI 时代素材管理新增的一条设计原则：AI 生成物的价值不只在结果，也在可复现的上下文。

如实记录反面

也有很多人觉得不方便、看着不习惯。这种大改必然带来迁移成本：用户已经形成的空间记忆（「东西在那个角落」）会被一次性清零。

实践建议：导航重构前先量化两件事——目标入口的平均到达步数，以及旧版用户肌肉记忆的深度。对后者，过渡期「双入口并存」往往比「一次到位」的干净利落更划算；把迁移成本当作设计变量，而不是上线后再看的后验数据。
来源: 歸藏(guizang.ai) @op7418

点评二 · Time Atlas 的冷启动困境：自动记录类产品的价值延迟与权限门槛

少数派介绍了 Time Atlas：它在后台持续记录你去过的地方、走过的路线、参与的活动，并结合照片、地图、Apple 健康和文字笔记，把一天自动整理成可回看的生活档案。内容呈现做得相当细致——时间线串起地图、天气、照片、轨迹和统计；多张照片会自动堆叠成相册并把最新的一张置顶；可以连接 Apple Health，把运动（锻炼、步数、步行距离）和健康（睡眠时长、睡眠图表、心率）数据放进时间线，为记录补充上下文；分享时可生成包含标题、时间轴、地点的卡片；摘要区最多四格，可自定义排列、加笔记和标题。

但作者也点出了一个结构性难题：首次打开 Time Atlas 时会申请一长串权限（地理位置、照片、运动与健康），而刚上手时内容几乎全是空白，必须使用一段时间、积累足够数据后，才能呈现丰富的视觉数据。

这几乎是所有「自动记录 / 自动整理」类产品的宿命：价值必须在数据积累之后才出现，但信任成本——以及被劝退的风险——却在第一分钟就要用户支付。同类产品（健康追踪、屏幕时间、自动记账）反复栽在同一个坎上。

实践建议：把权限申请拆成「按需触发」而不是「首屏打包」；用合成的示例档案（demo timeline）先让用户看到最终形态；再用一次真实的、即时的小价值（比如「今天你去了 3 个地方」）去换取下一层权限。让用户先看到回报，再付出信任——顺序反过来，再好的自动整理能力也没有机会被体验到。

研究方法论

两条可直接进入日常工作流的方法：一条偏量化走查，一条偏定性访谈。

方法一 · 让 AI 主动「弄坏」你的界面：worst-case 布局审计法

Emil Kowalski 分享了他最近最喜欢的一个 AI 用法：让模型试着弄坏你做的东西——塞进大量数据、超长名字、奇怪邮箱、极端标签，把所有最坏情况都构造出来。Viking 认为这个技巧「超级实用，任何模型都可以做」，并补了两条实战经验。

① 这是 i18n 审核的利器

不同语言由于字符长度差异极大（尤其是中英文），非常容易把界面搞乱。让 agent 批量注入各语言真实长度的文案，比人工逐条检查高效得多——本地化布局问题通常不是翻译错误，而是长度溢出与断行失控。

② 采用双 agent 分工，避免模型自我开脱

「可以让一个 agent audit 然后截图交给另外一个修复，和 code review 一样……同一条对话里又找问题又改代码，模型容易自我开脱。」另一位参与者建议：对着截图做 UI review，再按问题清单逐条修。

对用户研究的价值：这在方法论上等价于把「极端样本走查」自动化了。传统可用性测试受限于能招募到的人数、以及他们带来的真实数据形态；而这种做法可以穷举边界条件。它当然不能替代真实用户的行为洞察，但非常适合在正式用户测试之前，把那些「一定会被真实数据踩到」的布局问题先清干净——把有限的受访者时间，留给真正需要人来看的问题。
来源: Viking @vikingmute 来源: Viking · i18n 审核

方法二 · 把「主持人」当作一项专业工作来设计

meng shao 推荐了 swyx 关于如何做好炉边谈话 / 圆桌主持的高密度指南。它对做深度访谈、可用性访谈的研究者同样适用，核心论点是：会议质量的核心瓶颈往往不是嘉宾不够强，而是主持没有被当作一项专业工作来设计。主持人不是轮流念问题的人，而是现场的「信息编辑、体验导演与价值翻译者」。

主持任务压缩成三件事

  • 翻译——嘉宾讲的是「我当年怎么做」，主持人要追问并归纳成「你在类似阶段该如何判断、采取什么动作、避开什么坑」。原始经历只是原材料，听众能带走的可迁移判断才是最终产品。
  • 制造张力与参与——「娱乐」不是追求热闹，而是维持注意力、推动认知冲突。要揭示不同立场、追问含糊之处、阻止嘉宾陷入彼此认同的安全对话。所有人都同意、却没有新信息产生的对谈，是最差的呈现。
  • 简洁复述并掌控节奏——主持人自身发言应很少但必须高密度，价值不在「说得多」，而在于及时总结、切换议题、澄清概念。

两条最值得借鉴的设计思想

其一，以听众为中心，而非以嘉宾为中心。原文要求主持人先界定听众：融资后期的创始人、与 A 轮早期公司的团队负责人，面临的流程、招聘、销售、市场问题完全不同。主持人要持续校准——这段经历对现场哪类人有用？他们能据此做什么具体决策？嘉宾的成功是否可复制、适用前提是什么？

其二，「能量」是一种信息传递能力。人们在投入时保留更多信息。这里的能量不是浮夸，而是节奏紧凑、问题有明确目的、能识别值得深挖的回答、敢于打断低价值的铺陈。

映射到用户研究：访谈提纲不是问题清单，而是一份「听众画像 + 可迁移输出」的设计文档。如果你的受访者说的每句话你都点头认同，那场访谈大概没有产出；如果结束后你只记得热闹、记不住可执行的判断，说明翻译这一步没做。这套框架和可用性访谈中的 think-aloud 追问技术高度同源——两者的共同敌人都是「友善的空转」。
来源: meng shao @shao__meng（引 swyx 指南）

UX 雷达

还不足以成为趋势、但值得放进观察清单的早期设计信号。

Jev Router 的 routing insights panel：把「选型理由」做成界面

OpenRouter 在聊天界面中展示每轮选择的模型及评分依据（任务、难度、精度、换更大模型的收益）。这是「AI 替你做决定」场景下可解释性 UI 的一个具体范式——不是事后解释，而是过程中可见。值得注意的是它同时保留会话内模型的连续性（不轻易切换，因为切换会丢失缓存）：稳定性本身也是一种体验，频繁切换的成本最终会转嫁成用户的等待与账单。

「规划模式」同时出现了两种对立主张

Google Antigravity 2.0 新增 /plan 规划模式：agent 先退一步思考、做广泛调研，再生成供你审阅的实施计划。而 HackerNews 上《Plan Mode 已死》主张相反的流程——understand → act → inspect → clarify → adjust → act again，一边做一边改，不再先写一份要人批准的 spec；Viking 也认同「很多 skills 只会限制强大的大模型」。两个信号并列说明：「给用户一个可审阅的计划」究竟是安全垫还是瓶颈，取决于模型可靠度与任务风险等级——这正是需要按场景做用户研究的问题，而不是可以一刀切的规范。

微信把「元宝总结」换成「问 AI」

据人人都是产品经理观察，微信 PC 版公众号文章右上角原来的「元宝总结」已陆续替换为「问 AI」，背后接入的是腾讯「小微」；聊天消息、朋友圈发布、照片编辑、扫一扫、文件等场景也开始出现小微入口（仍在测试）。这是内容消费场景里 AI 入口的一次重构：从「给我摘要」变成「可以继续问」。对阅读类产品的启示是——AI 的落点不该只是一个功能按钮，而应是内容的延续对话层。

Notion 的组件语义之争：toggle 还是 database？

Sam Seely 发了一张 toggle 组件的图，配文「这个小家伙是 Notion 的骨架」，Notion 官方转发问：你是 toggle 派还是 database 派？这个看似玩梗的讨论指向一个真实的设计问题：同一个用户意图（收纳与折叠），应该由「组件」还是「数据表」来承载？组件的语义边界，直接决定了用户的学习成本与心智模型的一致性。

HeyGen 的 Custom Looks：数字人的个性化与身份一致性

可以为数字人更换任意服装而不丢失「像本人」的特征。当 AI 生成的形象开始承载个人身份时，「相似度」就从视觉参数变成了信任资产。个性化与身份一致性如何兼得，会成为数字人产品一类新的设计约束——用户要的是「我穿了这件衣服」，而不是「一个穿这件衣服的人」。

Whiteboard：人和 agent 共享一块画布

HackerNews 上出现开源桌面应用 Whiteboard，为人类与 AI agent 提供协作做软件架构设计的工作空间。值得关注的不是功能，而是「人和 agent 共享一块画布」这种交互隐喻——当协作者从人变成 agent，白板、文档、代码评审这些协作界面的设计假设都需要重写：它如何表达「这里我改过」、如何让人一眼看出 agent 的意图、如何保留人的最终决定权。

把模型参数翻译成用户心智模型：Claude Code 的 effort 档位指南

Anthropic 的 Thariq 给出了 effort（投入档位）使用指南，并给了一个精准类比：同样是做一个任务，别人给你 12 小时，你会理解为「尽全力做好」；只给你 1 小时，你会先交付一个满足要求的版本，等对方反馈再迭代——effort 就是这个「时间预算」。low 用于头脑风暴和小改动，medium 用于日常开发，high 用于验证多、边界情况多的活。另外 Anthropic 上线了插件提交 / 审核 / 用量查看门户。这类「把抽象参数翻译成用户已有心智模型」的说明文档，本身就是一种界面设计。

轻量高频的用户调研正在成为日常动作

Tw93 为 Mole 的 Windows 版做小调研，直接问「你日常用的电脑是什么、各自系统使用场景是什么」。当 agent 让产品迭代节奏加快，这种轻量、高频、贴近真实用户的反馈循环，可能比一年一度的正式调研更能跟上产品节奏。值得研究者思考的是如何把这类「随手一问」纳入正式的数据采集流程，而不是让它们散落在社交媒体的评论里。
