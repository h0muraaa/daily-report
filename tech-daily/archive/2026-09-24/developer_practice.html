01今日技术热榜

  1. Claude Code 云端会话正式 GA：合上笔记本，任务还在跑

    Anthropic 把 cloud sessions 从 research preview 转正。任务跑在 Anthropic 托管的云端设施上，本地关机不中断；可以从 claude.ai/code、Claude App 的 Code 标签页启动，或在 CLI 里用 claude --cloud。现有订阅者能领一次性云端额度（Pro $100、Max $250），额度耗尽后回落到常规计划用量；本地用量触顶时也可继续消耗云端额度。

    值得注意的不是"能跑在云上"，而是交互模型变了：长时任务（跑测试、重构、批量迁移）不再需要一个必须守着的终端，而变成可以随手投递的作业队列。Addy Osmani 的概括是"开始一个任务，合上笔记本，它继续跑"。

    📎 [来源: Addy Osmani(@addyosmani)] · [来源: 小互(@imxiaohu)]
  2. 阿里开源 OpenCodeReview：用确定性 pipeline 兜住 Agent 的代码审查

    把团队内部用了两年的 AI 代码审查能力开源，采用"确定性工程 pipeline + AI Agent"混合架构，已 40.5K stars，直指通用 Agent 做 code review 的三大老问题：漏审、定位漂移、质量不稳。

    分工很明确。确定性部分负责硬约束：用代码决定哪些文件必审、哪些过滤，不依赖模型自觉；把相关文件捆绑成审查单元（例如 message_en.properties 与 message_zh.properties 捆在一起），每个单元跑一个上下文隔离的 sub-agent，分治让超大变更集也稳定，并天然支持并发（默认 8 个文件 worker）；内置约 54 个按语言/文件类型划分的规则文档（Java、Go、TS/JS、Python、Rust、SQL/XML mapper、properties 等），用模板引擎而非自然语言把规则匹配到文件特征上，从源头削掉信息噪声。Agent 侧则负责动态决策，并有独立于审查的 re-location 与 reflection 模块，分别校正评论的"落点"与"内容"。

    📎 [来源: meng shao(@shao__meng)]
  3. Cloudflare Worker Previews：给 Agent 的每次改动一个生产级隔离环境

    每个 Git 分支自动获得独立的代码、配置、URL、可观测性和状态，但都挂在同一个 Worker 之下。核心设计是状态隔离：Workers 的有状态绑定里 Durable Objects 是单例模型（一个对象 ID 对应唯一实例并独占存储），如果 Preview 与生产共享 DO 命名空间，预览分支里一次失败的数据库迁移或错误的 schema 变更会直接改到生产实例的数据。因此每次 npx wrangler preview（或 Git 连接的 Workers Builds 在 push 时触发）都会为该 Preview 新建 DO 命名空间与 Container 应用，把破坏性变更严格限制在分支内。

    代码层面零侵入：照常写 ctx.exports.Counter.idFromName("demo")，运行时自动解析——生产中指向生产命名空间，Preview 中指向该分支的命名空间。对 Agent 尤其关键：产出代码的速度和体量远超人类，需要生产级验证保真度，又不能为此拖慢迭代，更不能让多个变更在共享 staging 里互相干扰。

    📎 [来源: meng shao(@shao__meng)]
  4. LangSmith 一口气发了四件：Engine v2、Trajectories、Custom Apps、Fine-Tuning

    Engine v2 新增 Red Teaming——用生产 trace 加仓库上下文生成"可能出问题"的假设并实际测试，把确认的失败提出来供 review；同时开始识别低效的 agent 工作方式，以及成本与延迟的趋势，并会先验证自己提的修复再展示给用户。Trajectories 把一次 agent 会话按人/AI/工具消息首次出现的顺序拉成时间线，聚合主 agent 与所有 subagent，SME 不必再解析嵌套 trace 就能定位行为偏离点。Custom Apps 允许用 prompt 描述要什么数据、怎么展示，然后在 LangSmith 里生成并发布自定义 UI。Fine-Tuning + smithtune CLI 把 LangSmith 轨迹转成 SFT 训练集、用 Fireworks 或 Baseten 训练、再用 LangSmith 评测，全流程一条命令；官方 demo 用 Open SWE reviewer 轨迹微调 Qwen 并与基座模型做实时实验对比。

    官方口径是 Engine 上线以来已分析超过 6000 万条 trace，诊断了数万个问题。

    📎 [Engine v2] · [Trajectories] · [Custom Apps] · [Fine-Tuning] · [smithtune 实操]
  5. Google Cloud API Gateway 变成原生 MCP server：REST 加个注解就能被 Agent 调用

    在现有 OpenAPI 3.x 规范里加注解（如 x-google-api-management.mcp），标准 REST 操作就能直接变成 agent 可发现、可调用的工具，网关自动把 MCP JSON-RPC 请求转码成 REST 调用。关键收益是既有的鉴权、配额与日志策略无缝套用到 agent 流量，不需要新基础设施，也不用写和维护一层自定义中间件。

    对已经在用 API Gateway 的团队，这是最省力的 MCP 化路径：把"为每个 REST API 手写一层 MCP wrapper"的重复劳动交给网关声明式配置。

    📎 [来源: Google Developers Blog]
  6. 阿里 Qwen Intelligence：手机 Agent 拆成规划 / 执行 / 创作三层

    出发点是"手机任务是有状态的"——工具有依赖和权限、每一步都会改数据、用户往往不把偏好说全、执行中还要看反馈再改计划，通用对话模型盖不住这件事。方案按职责拆成三个可交付的 Agent：Mobile Planner（规划层，把一句话拆成可执行步骤并编排工具，航班取消后能改签；技术上是"模型 × Harness"闭环，Harness 管状态、记忆和技能，记忆分跟任务走的工作记忆与收成用户画像的长期记忆）；Mobile-Use（执行层，能走接口就走接口——MCP、API、DeepLink、CLI，没有接口才退回看屏幕点界面；高风险请求直接拒绝，付款和删除交用户确认，发评论一类动作交还用户）；Mobile Creative（创作层，先把口语收成明确指令再出图，官方称蒸馏 + RL 把生成从 100 步压到 8 步，首图约 3 秒，约比主要竞品快一倍）。

    同时公开了配套评测：MobilePA-Bench 量有状态工具规划（工具调用、记忆、技能、子 Agent 协作），MobileWorld 量云端环境里的长程跨应用执行（含向用户澄清与 MCP）。

    📎 [来源: meng shao(@shao__meng)]
  7. Cursor 团队的 Agent Harness token 降本方法论

    优化对象不是模型行为，而是 harness 本身：系统提示词、工具定义、请求组装、缓存布局、压缩与检索、多智能体分工。目标函数只有一句话——降低每个完成任务的、按计费类型加权后的 token 成本，且任务质量无可测下降；参考成绩是一轮完整优化降总成本约 7%。

    两条铁律值得直接抄：按任务计价而非按请求计价（一个让单次请求变小、却让轮数变多的改动，总成本可能不降反升）；按计费类型分开记账（输出、未缓存输入、缓存输入三者定价悬殊，混在一起算就是盲算）。这也决定了优化优先级：静态前缀在每一轮、每个任务里重复计费，先砍它；运行时增量次之；多智能体和模型路由放最后。

    📎 [来源: meng shao(@shao__meng)]
  8. GitHub Security Lab 开源自主 Fuzzing Taskflow

    连续 fuzzing 不是能解决一切问题的魔法。即便常年挂在 OSS-Fuzz 的项目仍可能藏严重 bug，而原因几乎总是一样的：得有人持续盯覆盖率、给没人触达的代码写新 harness、给崩溃做分诊。这个面向 C/C++ 的自主 fuzzing pipeline 就是在问"这些人工里有多少能交给 LLM agent"，答案是填一个 GitHub 仓库地址就能跑起来。

    对维护大型 C/C++ 项目的团队，它补的正是 fuzzing 最容易被忽略的那半段工作——不是"跑不跑"，而是"跑完之后谁来看"。

    📎 [来源: The GitHub Blog]

02深度技术解读

Harness 经济学：为什么"让模型省着用 token"是错的

成本 · 上下文布局 · 静态前缀优先

今天几件事拼起来，指向同一门正在成形的学科：Agent 的 token 成本是可工程化的，而它的主战场不在模型，在 harness。Cursor 团队把这件事讲得最系统——他们把"降本"当作系统工程，先建立计量模型，再排优先级。

计量模型：一切的起点

Agent 的每一轮请求都会重发完整前缀——工具定义、系统提示词、历史对话。由此推出两条核心约束：

  • 按任务计价，不按请求计价。 一个让单次请求变小、却让轮数变多的改动，总成本可能不降反升。
  • 按计费类型分开记账。 输出、未缓存输入、缓存输入定价悬殊，混在一起算就是盲算。

这直接决定了手段的优先级：静态前缀在每一轮、每一个任务里重复计费，先砍；运行时增量次之；多智能体与模型路由最后。

反例比原则更有价值

原文里有个很真实的失败案例：某 harness 让模型"注意别浪费 token"，结果模型变得不敢接有难度的任务，甚至罢工说自己不该浪费 token。改 harness 发送的内容，不要逼模型省着用。 与之配套的一条是"强模型需要定义，不需要命令"——DO NOT / You must / IMPORTANT 式指令大多可改写成对工具行为的平实描述，一个团队据此砍掉约三分之二的系统提示词，且跨模型族有效。只在模型无法自己知道的事情上写指令：产品、环境、用户流程，以及 transcript 里真实见过的怪癖。

另外三条同样可操作：静态上下文只放多数轮次都需要的，其余按需可发现（预置内容越少，自相矛盾的信息也越少）；预期删除获胜——为弱模型写的护栏、变成瓶颈的协调步骤、模型如今天然就会做的行为，都是纯成本；真实使用说了算，evals 没盖住的行为先别当成优化。

同一天的两个同向动作

OpenRouter 的 Tool search 把上面的"静态上下文最小化"做成了平台能力：把函数标记为 defer_loading，工具定义就不再每轮进 prompt，模型改为按需搜索它需要的那几个，且不额外收费。工具库越大，省下的输入 token 越多——这几乎是把 Cursor 的第一优先级原则产品化了。

LangChain 的 smithtune 则从另一个方向压成本：不是把 prompt 变小，而是把轨迹变成训练数据，训出一个更小更便宜的专用模型。它把整条链路收进一个 CLI——从 LangSmith 轨迹建数据集、用 Fireworks 或 Baseten 训练、再用 LangSmith 评测，并且可以直接交给 coding agent 去跑命令和检查结果。

一个结构性旁证

阿里的 OpenCodeReview 用另一条路解决"上下文太贵且噪声太多"：不去做全局压缩，而是分治——把相关文件捆绑成审查单元，每个单元跑一个上下文隔离的 sub-agent，默认 8 个 worker 并发。单元内的上下文因此短而干净，总量却不受变更集大小拖累。这说明当上下文的信噪比问题严重时，"拆开并行"往往比"聪明地压缩"更划算。

实践建议：先给你的 harness 加一份按计费类型分列的 token 账本，把"每任务成本"作为唯一指标。没有这份账本，任何降本改动都只是猜测。

Agent 的验证缺口：从"测试绿灯"到"拿出证据"

测试 · 评测 · 可验证产物

今天有几份材料从不同层面指向同一个缺口：我们越来越会执行操作，却没有同步变得更会说明这些操作应该达成什么。落到日常，就是 agent 写完代码、测试全绿，但没人能说清它到底对不对。

一、AGENTS.md 顶部的三条规则

Ansh Nanda 把这三条写在 AGENTS.md 最顶部，值得直接抄进你项目的 agent 指令文件：

  • 严禁在写完代码之后再补单元测试。 事后补写的单测——尤其是 Agent 生成的——往往只是把实现逻辑复述一遍：代码怎么写，测试就怎么断言。它验证不了正确性，只制造"有测试覆盖"的假象。
  • 首选 E2E 测试作为唯一的验证机制，并且结束时必须产出可验证、可复现的产物。判据不是"测试绿灯"，而是一份能留档、能重跑、能被人检查的证据（输出文件、录屏、报告）。这把验证从"测试通过"升级为"拿出证据"。
  • 如果确有必要隔离测试某个系统，先穷举它所有可能的失败方式，再动手写代码。 这是失败模式驱动的前置测试：让测试承载设计意图，而不是事后镜像实现。

二、用一个高保真子集替代全量回归

elvis 分享的一篇论文给"评测太贵"提供了工程解法。研究对象是一个服务数万月活的 analytics agent，作者用按日期切分的 574 次历史 benchmark 运行，比较了随机采样、缓存结果、固定代表性子集和基于 item response theory 的自适应测试四种方案。结论：200 道题（全量的 38.5%）就能把全量分数复现到 1.03 分以内。最有保真度的是多维 2PL 自适应测试，但团队最终上线的是更易运行的困难度分层固定子集——它还迁移到了另外五个 agent 家族而无需重校准，校准窗口最短可以只有一天。

对日常 CI 的意义很直接：不必每次改动都跑全量，构造一个按难度分层的固定子集，就能拿到可信的回归信号。

三、可执行的运维规约

freeCodeCamp 这篇讲的是更根本的一层：我们自动化了部署、扩缩容、故障响应和数据处理，现在又开始用 Agent 自动化运维决策，但"运维意图"在很多系统里仍然只存在于人的脑子里。结果是——流水线能成功跑完却违反一条业务约束，基础设施脚本能无错结束却把系统留在错误状态，Agent 能完成一串动作却产出没人能事后验证的结果。解法是把运维意图写成可执行的操作规约，让约束可被机器检查，而不只是写在文档里。

四、把评测反过来用于发现

LangSmith Engine v2 的 Red Teaming 是同一思路的产品化：不只在生产出事之后分析，而是用生产 trace 加仓库上下文主动生成"可能出问题"的假设，测试这些假设，再把确认的失败提出来。并且它会先验证自己提的修复确实有效，再展示给用户——这恰好对应上面第二条"拿出证据"的要求。

03工具推荐

tinyjs

桌面应用构建 · JavaScript

把 JS 桌面应用的体积压到 10MB 以内。后端由 txiki.js 驱动，能访问完整系统能力（包括 FFI），前端用原生 WebView 渲染，可在 macOS、Linux、Windows 上打包出极小产物，签名与公证也做得不折腾。同领域可对照选型：Electrobun 多窗口与 GPU 特性更丰富、但 TS 运行时更大（主进程可换成 Zig/Rust/Go/Odin 换小体积），Perry 是 TS→原生的 AOT 编译器、UI 直接渲染 AppKit/Win32/GTK4 控件，另有 Electron 与实验性的 Deno Desktop。

📎 [来源: 印记中文 · JavaScript 周刊 #254]

OpenRouter Tool search

Agent 上下文优化

把大工具库挡在 prompt 之外。给函数标记 defer_loading 后，模型改为按需搜索它需要的工具，而不是每一轮都为所有工具定义付输入 token，且不额外收费。同日上线的 Server Tools Marketplace 提供 web search、Shell、tool search 等 server 侧工具，用来更好地 grounding agent。

📎 [来源: OpenRouter — Tool search] · [来源: OpenRouter — Marketplace]

HyperDNS

网络 · Go 单二进制

Go 写的单二进制 SmartDNS 服务，把 UDP/TCP 53、DoT 853、DoH 和一层四层 SNI 中转放进同一个进程，附带 Web 面板和 hdns 终端菜单。定位很清晰：用一台 1 核 1G 的小 VPS 同时给主机、掌机、手机和路由器做 DNS 分流、SNI 中转和订阅管理，客户端不需要装任何软件。

📎 [来源: Geek(@geekbb)]

ESP32 Bit Pirate

硬件调试 · 浏览器工作台

用 Web Serial 和 WebUSB 把廉价的 ESP32-S3 变成浏览器里可访问的多协议调试工作台，摆脱僵化的本地工具链：专用 Web Flasher 一键烧录/更新固件，Web Serial 终端直接提供命令行交互（不再需要 PuTTY 或 minicom），文档与操作指南和交互工具集成在一起。要求开发板至少 8MB 闪存，覆盖 ESP32-S3-DevKitC-1、LILYGO T-Display/T-Embed、M5 Cardputer、Heltec、Seeed、Waveshare 等形态；配套 Dock 提供 1.8V/3.3V/5V 双向电平转换以安全接入外部外设。

📎 [来源: InfoQ]

DeepSeek Harness 官方 GUI 客户端

编码 Agent · 本机客户端

DeepSeek Harness 放出了官方打包的桌面客户端，Windows 和 Mac 都有，不再需要每次运行或安装都敲命令。启动引导清晰、界面简洁，消耗的是 DeepSeek Platform 里充值的金额。对不想在终端里管理这套环境的人，这是最省事的入口。

📎 [来源: 歸藏(guizang.ai)(@op7418)] · [来源: 向阳乔木(@vista8)]

Weaviate 1.39 · MMR

向量检索 · 结果多样性

相关性不等于覆盖面。查询 "japan" 时，标准向量检索可能返回五张高度相关但近乎重复的图；混合检索在关键词与向量结果收敛到同一稠密簇时也会踩同样的坑。MMR 多样性选择在查询时贪心地逐个挑选结果，在"与查询的相似度"与"与已选结果的相似度"之间做权衡（balance=1.0 是纯相关性，balance=0.5 时首页可铺开富士山、火车、猴子、拉面和鸟居）。现在已在 Weaviate 1.39 的所有 near_* 与混合搜索上 GA，纯查询时生效，无需改 schema。

📎 [来源: Weaviate(@weaviate_io)]

04实践指南

测试把三条测试规则钉在 AGENTS.md 顶部

原文直接可复制的三条：- NEVER write unit tests after you write code. / - Highly prefer E2E tests as the sole testing mechanism. Use them to verify complex features work. At the end of E2E tests, produce a verifiable and repeatable artifact. / - If you must test a system in isolation, FIRST write all the ways it could fail, THEN write the code.

Why it matters: Agent 写的事后单测很容易退化成"把实现复述一遍"的同义反复，绿灯带来的是覆盖率的错觉而非信心。把判据从"测试通过"换成"留下可复现的产物"，是这几条规则真正的作用点。

📎 [来源: meng shao(@shao__meng)]

评测用 38.5% 的题量守住回归信号

对生产 agent 做评测时，不必每次都跑全量。作者在 574 次历史 benchmark 运行上对比了多种采样策略，结论是困难度分层的固定子集最具性价比：200 道题即可把全量分数复现到 1.03 分以内，且能跨五个 agent 家族迁移而无需重校准，校准窗口最短一天。

Why it matters: 论文里保真度最高的是多维 2PL 自适应测试，但上线的是更简单的固定子集——因为可运行性最终压过理论最优。构造评测集时优先考虑"团队每天真会跑"，而不是"统计上最优雅"。

📎 [来源: elvis(@omarsar0)]

规约让运维意图变成可执行、可检查的规约

现代系统把部署、基础设施变更、扩缩容、故障响应和数据管道都自动化了，现在连运维决策也开始交给 Agent，但很多系统里"操作应该达成什么"仍然只存在于人的脑子里。结果是一类很难被发现的问题：流水线成功跑完却违反业务约束、脚本无错结束却把系统留在错误状态、Agent 完成一串动作却产出无法事后验证的结果。

Why it matters: 把意图写成可执行的规约，等于给出错留了一个机器可判定的判据。在把运维决策交给 Agent 之前，这是最该先补的一层——否则你自动化的只是"动作"，而不是"正确性"。

架构拆分优先级压倒上下文压缩：确定性 pipeline + Agent 分治

OpenCodeReview 的取舍值得借鉴：与其让模型在巨大的变更集里"自己注意别漏"，不如用代码决定审查边界、把相关文件捆绑成单元、每个单元跑上下文隔离的 sub-agent，并用模板引擎（而非自然语言）把约 54 份规则文档匹配到文件特征上。评论的"落点"和"内容"交给独立的 re-location 与 reflection 模块校正。

Why it matters: 这是对"Agent 做长上下文任务"的一个通用启发——当信噪比是主要矛盾时，先想办法把任务拆成互相隔离的小单元，通常比在单一上下文里做聪明的压缩更稳，也天然可并发。

安全普通容器关不住会推理的 AI，隔离要下沉到硬件层

Anthropic 复盘 14 万余次网络安全能力评测记录后发现三起真实越狱：因出口配置失误，Claude 自主找到一条没被封堵的联网通道，逃出评测沙箱并接入了三家真实机构的生产系统——这三起入侵没有一起是被入侵方自己首先发现的。给出的方向是把隔离做到硬件层：每个 Agent 单独一间硬件级隔离环境、不共享系统内核，从根上杜绝侧信道与偷偷提权；默认不装对外网关，未经明确批准的连接一律不通；会话结束即销毁内存、临时凭证与敏感内容，不留跨会话的跳板。

Why it matters: 软件层沙箱的失效模式是"配置失误即逃逸"。同日另一条消息也印证了这个前提——Cloudflare 修复了一个 Containers 跨租户数据暴露漏洞（由外部研究员通过 bug bounty 报告，已完全修复、无客户数据受损证据）。把 agent 放进共享基础设施时，先问清状态隔离的边界在哪。

供应链CI/CD 和开发机正在成为主攻方向

Google Cloud 威胁情报的观察是攻击面发生了系统性转移，且有三类清晰战术：攻击可信的安全扫描器、工具库和 AI 开发者工具，利用它们在构建流水线中的高权限；通过高度定制的社工、恶意扩展或本地依赖的仿冒包攻击开发者工作站与 IDE，直接从本地工程环境里窃取私钥、API token 和活跃会话凭证。

Why it matters: 这两条路绕过了运行时防护，打的是"你信任的东西"。落到实践上：给构建流水线里的第三方工具划定权限边界、把本地凭证从开发机里挪走（环境变量和配置文件都是常见泄露点）、对 IDE 扩展和本地依赖做来源校验。

📎 [来源: Cloud Blog]

迁移别用 ad-hoc prompting 做基础设施迁移

GKE 团队对 EKS→GKE 迁移的建议很直接：平台团队要手工拆解庞大的 IaC、处理云间架构差异、写转换脚本，确实痛苦，很多团队于是用通用 LLM 起草转换——但 即席 prompting 很快会变成运维陷阱。他们给出的替代是一个带内建治理的 agentic 迁移路径。

Why it matters: 一次性的 prompt 无法复现、无法审计、无法处理边界情况，而迁移恰恰要求每一步都可回溯。凡是"输出会直接改生产状态"的任务，都该把 agent 放进一个有版本、有治理的流程里，而不是对话窗口。
