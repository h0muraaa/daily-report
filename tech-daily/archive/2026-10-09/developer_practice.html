#01 迁移Rust

GitHub 用 AI 辅助把 Copilot 运行时从 TypeScript 迁到 Rust：80 万行，14.5 周

GitHub 完成了 Copilot 运行时的一次大规模重写——把 超过 80 万行的 TypeScript / Node.js 代码迁移到 Rust，整个过程只用了约 14.5 周，并拆成 128 个 PR 增量合入，期间 Copilot 版本照常发布。

关键工程手法有三点：通过 N-API 互操作让 Rust 与老 Node 代码并存，避免一次性大爆炸式替换；用自动化测试 + 人工 review 兜底 AI 生成的代码；以“小步增量 + 持续发版”控制风险。这是一个可直接借鉴的大型迁移范式。

对需要做跨语言迁移或性能重写的团队，这是“AI 辅助 + 增量交付”最完整的一份公开案例。

深度技术解读

解读一：Harness 工程 —— 决定 Agent 上限的，是模型外面那层壳

Deep Dive

今天多条资讯指向同一个结论：同一个模型，换一套 harness，能力可以差好几倍。

elvis 引用的一篇论文给出了最直白的数字：在整仓库迁移（whole-repository migration）任务上，把 Codex 换成 HERMES harness 后，GPT-5.6 Sol 的成绩从 6.5% 直接跳到 31.0%。模型没变，外面那层“壳”——工具集、上下文组织、循环控制——让成功率翻了将近五倍。他的结论很直接：harness engineering 还远未被充分探索，值得自己动手造。

行业里几条实践路线可以拼出一张地图：

  • 用现成的 harness 起步：OpenAI 的 Dominik Kundel 讲解 Codex App Server——一套开源 JSON-RPC 协议，把驱动 Codex 的 harness 封装出来，让你不必从零自研就能接上成熟能力。
  • 为 Agent 而非为人设计接口：Airbyte 的 Pedro Lopez 对比了同一份公司数据接入 Agent 的两种方式——MCP server vs CLI，讲清各自真正擅长的场景，而不是谁替代谁。
  • 让模型跟着 harness 一起进化：淘宝直播提出 Harness-Aware Training（HAT），把动态执行环境（harness）的状态显式纳入训练分布，三阶段训练（HSA-SFT 提升工具调用 → OPD 蒸馏恢复通用能力 → HSA-RL 在模拟环境学真实交互），让小模型能随频繁变化的业务规则一起适配。
  • 把 harness 反馈喂回模型：微软 Agent Lightning v1.0（见热榜 #06）就是“保留现有 harness、只训底层模型”的工具化落地。
实践建议：不要把所有精力押在“换更强的模型”上。先把你自己的 harness 显式化——工具集怎么定义、每轮给模型看什么上下文、失败后如何回灌——这些变量对最终成功率的影响，往往比换模型更大。

解读二：Agent 真正进生产，要过四道工程关

Deep Dive

“能跑 demo”和“能上生产”之间隔着一整套工程问题。今天的多条分享几乎可以拼成一份清单：

  • 记忆关：Oracle 的 Anders Swanson 把 agent memory 当成系统问题来处理——上下文窗口不是记忆，把窗口开更大也不是解法；agent 每次会话都重读同样的文件，是因为学到的东西根本没被存下来。需要一层真正的记忆层。
  • 验证关：Sonar 的 Ali-Reza Adl-Tabatabai 指出 AI 带来的是更多 PR、更大的 PR、更多 bug；摆在面前的选择只有两个——拖慢速度，或者走形式地盖章。出路是把验证也自动化，因为 CI 与 code review 正是决定质量的关口。
  • 可靠性关：Amazon AGI Lab 的 Felipe Blanes 讲了 Nova Act 从研究预览到 GA 的历程，一句话总结：benchmark 分数好看，真实客户一用就崩——80% 的可靠性根本不够。
  • 权限关：Orkes 的 Viren Baraiya（Netflix Conductor 原作者）给出生产级心法：让模型决定“接下来做什么”，但绝不让它即兴决定“生产集群怎么重启”——真正的决定权留在确定性代码里，模型只在安全边界内选择。

配套方法论也在同一天出现：Jerry Liu 与 Harrison Chase 力推 eval-driven development——“定义一个 eval，然后在其上爬坡”，往往比直接手写确定性的工作流更能解决问题；Greg Pstrucha（Sentry Seer）则提出 Stop Prompting：你纠正 agent、它回“你说得对”，五分钟压缩（compaction）后又犯同样的错——反复重写 prompt 治标不治本。LangChain 也把“agent 工程师必须能回答的三个问题”归纳为：它在哪里失败、如何可靠复现、怎么让它停下来。

把这几条串起来就是一句话：可观测性（知道它在哪失败）+ 评估（能复现地量出来）+ 记忆（不在同一处反复栽跟头）+ 权限边界（坏的时候炸不了），才是 Agent 上生产的四件套。

CLI安全

mxc（Microsoft eXecution Container）—— 隔离不可信代码的操作系统级沙箱

微软开源的跨平台沙箱化代码执行系统（MIT 协议），定位就是隔离“不可信代码：模型输出、插件和工具”。设计上有两大特点：统一抽象、多后端——应用通过 SDK（Rust / .NET / Node）声明容器类型、隔离规则和工作负载，mxc 校验后选择后端启动（Windows 默认 ProcessContainer，另有 Windows Sandbox、WSL 容器，以及实验性的 Hyperlight microVM 等）；策略驱动——文件系统（只读 / 读写 / 拒绝路径列表）、网络（代理）等规则可精细声明。Unsloth 已与 Windows 团队合作把它集成为 Windows 上的 OS 级沙箱；OpenAI 的 Codex on Windows 也基于 MXC 做沙箱模式，实现更快的初始化与更严格的网络控制。

让 Agent 执行任意代码，隔离层是底线。这是目前少见的、同时覆盖 Rust/.NET/Node 的跨平台方案。

实践指南

工作流

① 按改动规模匹配流程重量：Matt Pocock 的 Agent 流程决策框架

「Skills For Real Engineers」（281K ⭐️）作者 Matt Pocock 分享了一套“AI Coding Agent 该用多重流程”的决策框架：小改动直接写；中大型改动先澄清需求；只有当规划失控时才升级到重型规划。落到两个斜杠命令的时机上：/grill-with-docs 是轻量澄清流程——让 agent 在动手前先“拷问”你、结合文档把需求问清楚，而不是一上来就堆规划。

可落地要点：先按改动大小选流程档位，别对所有任务都套同一套重流程——那正是效率被拖垮的常见原因。

📎 来源：meng shao(@shao__meng)
方法论

② eval-driven development：先定义 eval，再在其上爬坡

Jerry Liu 的观点正在成为共识：与其直接手写确定性的 agentic 工作流，不如先定义一个 eval，然后在其上做爬山优化。Harrison Chase 补充了一个重要边界——Goodhart 定律下“度量变成目标就不再是好度量”，eval 驱动开发更适合范围收窄的任务；他还提出把轨迹标注拆成“难度 / 正确性”两个独立维度，而不是一次 pass/fail。

可落地要点：给核心任务先写一个可自动跑的 eval 当优化信号；同时警惕把 eval 分数当成唯一目标导致过拟合。

📎 来源：Jerry Liu(@jerryjliu0) ｜ Harrison Chase(@hwchase17)
架构

③ 给 Agent 建独立的记忆层，而不是继续加大上下文

Oracle 的 Anders Swanson 把 agent memory 当作系统问题：上下文窗口不是记忆，把窗口开得更大也不是解法；agent 每次会话重读同样的文件，根因是学到的东西从未被持久化。正确做法是引入独立的记忆层，让跨会话的累积真正沉淀下来，而不是靠 markdown 文件或超大 context 硬撑。

📎 来源：AI Engineer · From Context to Memory
安全

④ 用系统级沙箱隔离 Agent 的代码执行，而不是靠信任

把 Agent 生成的代码直接放到开发机上执行是高风险操作。可落地的做法是操作系统级沙箱：如微软开源的 mxc（见工具推荐），通过策略声明文件系统读写范围与网络代理规则，并由 SDK（Rust/.NET/Node）统一声明容器类型。Codex on Windows 已基于 MXC 做沙箱模式，Unsloth 也在 Windows 上做了集成。

要点：让“不可信代码”（模型输出、插件、第三方工具）跑在受控容器里，权限边界用配置声明，而不是靠人肉审查每一行生成代码。

📎 来源：meng shao(@shao__meng)
调试

⑤ 插件 / 应用卡顿：抓一份 thread dump 再排查

JetBrains Marketplace 上线了 UI freeze reports：当用户报告 IDE 无响应、怀疑是你的插件时，重复同样的操作往往复现不出来。现在可以不靠“猜”，而是拿到卡顿期间捕获的 thread dump，直接看到卡在哪个线程、哪段代码——把偶发卡顿的排查从盲区变成有据可查。

📎 来源：The JetBrains Blog
