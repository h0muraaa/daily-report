02 深度技术解读

深度一：把 Agent 做「无聊」——确定性层、Evals 门禁与置信层

Stack Overflow 同一天连发三篇（Part 1/2/3），讲的其实是同一件事：让 Agent 从「聪明但不可靠」变成「无聊但可预期」。这三层正好构成一个自下而上的可靠性栈：

  • 确定性层（Part 1 · determinism）：把能确定的都从模型手里拿走。凡是能写成代码规则、状态机、schema 校验的部分，就别交给模型即兴发挥——让模型的输出空间收窄到「只在真正需要判断的地方做选择」。
  • Evals 作为部署门禁（Part 2 · evals as a gate）：把评测当成发布流水线的关卡，而不是上线后的监控。关键在「知道它们何时漂移」——模型、prompt、数据任一变动都可能让指标悄悄走样，所以要有办法检测漂移。
  • 置信层（Part 3 · confidence）：让 Agent 知道自己不知道。当模型对某个判断没有把握时，应主动降级、追问或转人工，而不是自信地编一个答案。

这套思路在实战里能长成什么样，同一天另一条来自 @shao__meng 的分享给了很好的样本——一个「自然语言问数据库」的数据分析 Agent，把职责硬拆成三层：

# 三层职责分离：模型只做它擅长的事
1. 生成层  Qwen 理解问题 → 写只读 SELECT → 解释结果
            模型从不直接接触数据库
2. 守卫层  纯代码硬规则：仅允许单条 SELECT / SQLite 只读模式
            查询超 200 行拒绝 / 无 WHERE 需人工批准
3. 审查层  独立模型在三个点介入：
            ① 问题清晰度（执行前）——"谁是我们最好的客户"定义含糊 → 93% 置信度要求澄清
            ② SQL 相关性（执行前）——问题/schema/SQL 是否匹配，不匹配给主模型一次修改机会
            ③ 答案接地性（执行后）——解释是否真基于返回行，否则降级标记"未验证草稿"

实践建议：不要指望一个模型同时当运动员和裁判员。把「生成」和「审查」拆成两次独立调用，中间夹一层纯代码的确定性守卫——这一步几乎不花算力，却挡掉了绝大多数危险操作。这也是 Stack Overflow 三篇里最务实、最可迁移的一条经验。

📎 来源：Stack Overflow — Part 1: determinism layer · Part 2: evals as a gate · Part 3: confidence layer · meng shao (@shao__meng)

深度二：投机解码（Speculative Decoding）到底值不值？vLLM 在 Blackwell 上实测

Akamai 的开发者布道师用一场 talk 把「该不该开投机解码」讲成了可量化的工程题。原理不复杂：一个小 draft 模型先猜出接下来的几个 token，大模型在一次前向里批量核验——核验通过就白赚吞吐。真正的问题在于什么场景才划算。她在单张 NVIDIA Blackwell GPU 上用 vLLM 跑了两组对照：

  • 结构化输出：提速 1.6×，因为这类任务下一个 token 高度可预测，draft 命中率（acceptance rate）高。
  • 创意写作：命中率明显更低，收益大幅缩水。

结论背后是两条常被忽视的成本：其一，多托管一个 draft 模型要额外占显存（还有它自己的 KV cache）；其二，长上下文和高并发负载收益更少——因为此时瓶颈从 decode 阶段转移到了别处，投机解码省下的那点时间占比变小。她在 talk 里也讲了推理的 prefill / decode 两阶段拆分和 draft 模型选型方法。

实践建议：不要默认给所有推理都开投机解码。把它当成一个针对特定负载的开关——先用真实流量的 acceptance rate 做判断，结构化输出、模板化生成、代码补全这类任务优先试；创意生成、长上下文场景先别急着上。

📎 来源：AI Engineer — Is Speculative Decoding Worth It? Profiling vLLM on NVIDIA Blackwell (Akamai)

Google Developer Knowledge API + MCP Server（公开预览）

一个很实用的「给 AI 喂权威文档」的工具：Google 推出 Developer Knowledge API 与官方 MCP Server，提供机器可读的方式检索 Firebase、Google Cloud、Android 等最新官方文档。通过官方 MCP server 把你的工具直连到 Google 的文档语料库，可以让 AI 生成的代码和建议基于实时、权威的上下文，而不是训练数据里的过时快照。对经常被「模型给出过时 API」坑到的团队，这是对症的一味药。

📎 来源：Google Developers Blog

llm-openai-decisions  /  Vercel AI Gateway 的 /v1/decisions

OpenAI 的 Decisions API 是 DevDay 上「Jev 风格」的决策模型接口：不生成文本，而是对同一份输入回答有类型的判断题——predicate（是/否）、choice（多选一）、score（打分），返回概率、选项和分数，天然适合路由、分流、护栏、评分。Simon Willison 已放出 llm-openai-decisions 插件（llm install llm-openai-decisions），有趣的细节是他让 GPT-6 Astra 读了新 API 文档后照着他原有的 llm-typesafe 插件现写了一个。Vercel 也在 AI Gateway 上提供了兼容的 /v1/decisions 端点，注意 gpt-6-luna-decisions 与 gpt-6-luna 是不同的 model ID，计费按 Decisions API 走。想用「决策模型」替代一堆 if-else 路由的实验，可以低成本试水。

📎 来源：Simon Willison's Weblog — llm-openai-decisions 0.1a0 · Vercel News — Decisions API on AI Gateway

html-plan：让 Claude Code 生成「一分钟读完」的 HTML 计划文档

来自 Claude Code 团队 @trq212 的插件，解决的是真实痛点：模型给的计划文档冗长平铺，人类很难快速审阅和反馈。运行 /html-plan 后生成的不是 Markdown，而是一个自包含单文件 HTML，把计划组织成四层「声明树」——标题（这是什么）、第 1 层（用户届时能做什么/看到什么，配 UI 草图或状态机）、第 2 层（如何实现，调用栈、数据 schema、代码片段）、第 3 层（代码在哪里）。三个设计很巧：渐进披露（折叠态即摘要）、编号决策点（底部按钮逐个跳未决项）、原地反馈闭环（页面上直接选项、改 schema、对某行代码评论，一键生成答复粘回 Claude Code）。安装：claude plugin marketplace add anthropics/claude-plugins-community 后 claude plugin install html-plan@claude-community。

📎 来源：meng shao (@shao__meng)

OpenDocRouter：把 4000 个 OCR 模型的选型做成「一行切换」

LlamaIndex 发布 OpenDocRouter，用统一 API 收敛文档解析（转 Markdown）这件麻烦事。出发点很实在：Hugging Face 上约 4000 个 OCR 模型、前沿实验室几乎每月上新，今天最好的模型到明年 Q1 就未必——所以「用哪个模型」是伪命题，「多快能换」才是真的。它让同一请求、同一 Markdown 输出，一行代码换模型，无需改 prompt 或集成；首发 10 个前沿与开源模型（含 Claude Opus 5.5、Gemini 3.8 Flash、GPT-6 Luna、MinerU2.5-Pro、PaddleOCR-VL-1.6 等），每个都在 ParseBench 上标了质量与成本，并提供 layout: true 的 grounded bounding box。官方也坦言自研 LlamaParse 并非覆盖所有价位段，故用路由器补齐长尾。

📎 来源：LlamaIndex 🦙 (@llama_index) · Jerry Liu (@jerryjliu0)

04 实践指南

① 写 Skill 时，description 不是摘要，是触发器

很多人写 skill 把精力全砸在正文，却忽略 description，结果 skill 根本没有机会被触发。引用 Claude Code 团队的原话："The description field is not a summary, it's a description of when to trigger this skill." 视角要切换——人类在界面看到的是 display_name 和图标，而模型只拿着 description 去和用户消息做语义匹配，所以你写的其实是一段「给模型的路由规则」。官方规范建议至少包含三项：具体能力清单 + 具体场景 + 用户触发关键词。

# 反例：只描述"是什么"
description: 这个 skill 能帮你写周报，输出的周报很适合老板阅读

# 正例：描述"何时触发"（能力 + 场景 + 关键词）
description: 从任务清单生成结构化周报。当用户要求"写周报""周报助手"
             "整理本周工作"时调用。
📎 来源：架构师之路

② 生产级 Agentic Harness 的六根支柱

Resolve AI 的观点一针见血：AI 写代码很强，但 70% 的工程时间花在「运行和修」上，而 AI 恰恰在这里吃力。原因在于代码是自文档、模块化、单一领域的「简单」问题，而生产横跨代码、基础设施、遥测和多个团队，且只认一个正确答案。Agent 规模化后会暴露这些问题：锚定偏差与模型跑步机、上下文给多给少、看似连贯但不因果的答案、缺护栏、调查之间不学习。对应的六根支柱是：模型编排、上下文工程、因果推理、受治理的动作、学习系统、评测。

📎 来源：AI Engineer — The 6 Pillars of an Agentic Harness for Production (Resolve AI)

③ 读代码不是在读书：别从头顺读

Sean Goedecke 的 How to read code 指出一个常见误区：把读代码当成读书，从第一行顺序读到末行。但英文文本的排列顺序由作者为读者服务，代码的顺序却主要由机器执行的约束决定——你不能因为「放前面更便于理解」就随便把一行挪到文件顶部。这个差异决定了读代码应该用跳跃式、假设驱动的策略（先找入口、追调用链、按需展开），而不是线性阅读。文章从这一点展开到具体的读码方法，适合刚接手陌生代码库时对照自省。

📎 来源：seangoedecke.com

④ 警惕 AI 生成代码带来「调试与理解鸿沟」

独立研究机构 Coleman Parkes 为 Undo 做的调查给出一个务实警示：AI 编码 agent 确实加速了代码生成，但瓶颈并没有消失，只是转移到了调试、代码理解和维护上，形成一道「comprehension gap」。同期 GitHub 的观点也指向同一方向：如今 GitHub 上每 3 个 PR 就有 1 个涉及 AI agent（一年前不到 1/10），照此速度两年内推上 GitHub 的代码大部分可能由 agent 写就，且很多永远不会被人类通读——因此密钥泄露等防护必须跟上代码生成的速度。对团队的启示是：把评审、调试、文档、测试这些「生成之后」的环节当成真正的主战场来投入。

📎 来源：InfoQ — AI-Generated Code Increases Debugging and Failure Rates · The GitHub Blog — Secret protection must scale with software

⑤ 存算迁移可复用的方法论：Grab 与 Kafka 的两个案例

InfoQ 的两篇工程实录都值得当模板看。Grab 的 Counter Service从宽列数据库迁到 Aerospike，靠的是存储抽象层、影子流量、数据一致性校验、灰度迁移这一套组合拳；数据模型重构把时间桶合并成基于 map 的记录，最终生产环境 p99 读延迟降约 50%，磁盘从 3TB 降到 1TB，单节点成本降低 45%–50%。另一篇讲在 Go 里构建「会话有序」的 Kafka 流水线：在 Kafka 分区之上自建应用层路由、一致性哈希、重试与「连续水位线提交」，实现跨数千个独立 channel 的严格消息有序——这个「有序 + 重试 + watermark」的模式，任何需要保证顺序的消息系统都能借鉴。
