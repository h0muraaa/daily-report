Kubernetes 力推 KYAML：更严格、更可预测的清单方言

Kubernetes 官方正在推广 KYAML——一种更严格的 YAML 方言，目标是让 K8s 配置更明确、更可预测，减少常见 YAML 陷阱。关键点是它并非新语言，而是 YAML 的严格子集，现有解析器和 K8s 工具链依旧能处理，只是减少了开发者需要做的语法选择。

写法上对象用 {}、数组用 []、字符串值统一加双引号，保留注释与尾随逗号，因此视觉上更接近 JSON。它解决的是缩进决定结构、未加引号值被误判类型这类歧义——在 Helm 等模板系统生成/处理清单时尤其容易踩坑。该特性 v1.34 引入为 Alpha，v1.35 升级为 Beta 并默认开启。

Amazon Linux 2027 公测：SELinux 默认进入 enforcing 模式

AWS 放出 Amazon Linux 2027 公开预览版，基于 AL2023 基线、内核 7.1，最大的破坏性变化是 SELinux 默认以 enforcing 模式运行。官方明确提醒：在 AL2023 的 permissive 模式下能跑通的应用，切到 enforcing 后可能会失败。

更需要注意的是信息缺失：公告没有给出 AL2023 的停止支持日期、没有 GA 时间、也没有原地迁移路径。对计划升级的团队，建议先在测试镜像里把 SELinux 设为 enforcing 跑一遍全链路，提前暴露 AVC 拒绝，而不是等到被迫迁移时才发现。

Agent Substrate 登陆 GKE：为百万级 Agent 沙箱设计的执行运行时

深度技术解读

▍深度一：AI 写得越快，"验证"越贵——当代码产出速度超过测试能力

今天有两组互相印证的事实，把"AI 编码的瓶颈已经转移到验证环节"这件事摆到了台面上。

场景：Bug 被找出来的速度，超过了修得过来的速度

微软 Exchange 团队在解释 Exchange SE 累积更新 CU1 为何一再延期时，给出的理由颇为意外：AI 工具找到了太多 Bug。找到 Bug 不是终点，而是一长串工作的起点——工程师需要逐个确认、分级、修复、验证、回填。同一时期，Edge 团队也承认 AI 生成的浏览器扩展多到根本审核不过来。不到一个月，微软两度"自曝家丑"，主角都是 AI：AI 编码 ≠ 代码安全。

另一侧的极端案例是 Anthropic：工程师每季度交付的代码量是几年前的 8 倍，其中 80% 由 Claude 编写；六个月内 CI 任务量涨了 25 倍，测试系统接连打了三个补丁（70 天 → 29 天 → 1 天），最终靠一名工程师用三周完成重构才把影响分析规模化。规模上去之后，测试与 CI 才是真正的瓶颈。

一线视角：想法不是瓶颈，验证才是

宝玉的观察很直接："Vibe Coding 到后来，想法都不是瓶颈，验证才是。"AI 让功能快速堆叠，但根本来不及逐个功能测试；产出速度不再是手工编码的节奏，"测得过来"这个隐性前提失效了。他试过用 Computer Use 辅助测试，效果并不理想——要覆盖各种场景，工作量一点不少。结论是：测试不会因为 AI 而被替代，反而需要被测的更多。

他还记录了一个非常具体的踩坑：Agent 显示任务"已完成"，隔天测试却发现没生效——原因是它开了 worktree、在分支上改，压根没合并到 main。清理时发现积压了不止一个。

工程应对：把"意图"和"收尾规则"写进 Agent 上下文

《Tell agents the why, not just the how》指出了一个关键转变：早期 Agent 是"热情的白痴"，必须逐步精确指令；而今天的前沿模型做错事，往往不是"没懂"，而是对你的目标或优先级做了错误假设。例证是当 GPT-6-Astra 以为在给"自己"写代码时，会输出压缩过的代码——它完全有能力写人类可读的代码，只是缺少明确的意图约束。所以与其规定每一步怎么写，不如在规则文件里说明为什么。

把这两点合起来，可以得到一组可落地的实践信号：

  • 把验证预算当成一等公民：既然产出速度上去了，测试与 CI 容量需要同步扩容，否则质量缺口会以"小 bug 遍布产品"的形式外溢。
  • 用 AGENTS.md 约束收尾语义：worktree 不遗留、完成即合并或打 tag 存档，编排 subagent 的会话负责收尾它派生的 worktree。
  • 规则里写 why：说明代码是给人读的、面向哪个使用方，比逐条规定写法更省 token 也更稳。

▍深度二：Agent 权限最小化——从"一把钥匙开所有锁"到细粒度授权

今天多个产品线同时指向同一件事：给 Agent 的能力边界，正在从"给个 API Key 自己看着办"演进为可声明、可收窄、可审计的授权模型。

问题：一个 Key 的权限，往往远超当前任务所需

mem0 在发布 Gateway 时的描述非常典型：Agent 要查一笔支付，你给它的 Key 却同时能退款；要起草一个页面，那把 Key 也能归档所有页面。它给出的方案是——每个 Agent 一把 Key，只授予你显式放行的工具，MCP server 和自家 API 共用同一把 Key，任务变化时改授权即可，Agent 永远看不到真实凭证。这本质上是把"能力"从凭证里解耦出来，等价于一套面向 Agent 的 capability 模型。

平台侧：把治理从构建期推到运行期

Google 在《Build zero-trust AI agents that judge intent, not just syntax》中提出，Agent 安全应从静态的构建期控制转向运行时治理，并给出三层托管防御：Model Armor 在边缘筛查提示词，Semantic Governance Policies 依据业务规则评估工具调用的意图，Agent Anomaly Detection 捕捉多轮组合攻击。要点是把这些能力下沉到平台层，安全管理员可以动态执行策略、中和复杂攻击，而无需修改或重新部署 Agent 自身代码——这一点对迭代频繁的 Agent 系统尤为重要。

AWS 则从另一个角度补齐了链路：Bedrock AgentCore Identity 现在提供托管的 Consent portal，解决"会话绑定"问题。此前客户用授权码模式时，需要自己呈现授权 URL、托管公网 HTTPS 回调、认证回访用户、管理浏览器会话，再调用 CompleteResourceTokenAuth 收尾；现在这些环节可交给托管门户。而 Cloudflare 的思路是把授权收窄到资源维度：一个 Agent 只拿到某个 Worker 的权限。Cloudflare 官方理由说得很直白——最不想看到的就是 Agent 仅仅因为权限给多了，就改动了生产。

实现要点与实践建议

  • 凭证不落 Agent：用网关/代理持有真实凭证，Agent 只持作用域令牌，任务结束即回收或改授权。
  • 按"任务"而非按"人"授权：授权粒度对齐当前任务所需的最小工具集，而非角色或长期身份。
  • 运行期可撤销：策略在平台层执行、可动态更新，避免每次收紧权限都要重新部署 Agent。
  • 为多轮攻击留检测位：单条请求看起来合规不代表组合起来合规，需要跨轮次的异常检测。
  • 容错分层：Anthropic CEO Dario Amodei 提醒"关机键"并不可靠，足够强的模型可能尝试绕过关闭指令，控制手段要按"瑞士奶酪"多层错开设计，别把希望压在单一开关上。

实践指南

A

在 AGENTS.md 里规定 worktree 的收尾语义

场景：Agent 用 worktree 隔离任务，但完成后没有合并，导致"显示已完成、实际未生效"。做法是在 AGENTS.md 里写明收尾规则，而不是逐个任务口头交代。

# AGENTS.md · Git 纪律
worktree 不遗留：
  在 worktree 里做的任务，完成时必须删除该 worktree 及其分支。
  删除前二选一：
    a) 合并进 main；
    b) 不合并时，先把未提交改动提交到该分支，
       打 archive/<worktree 名> tag 存档，
       再 git worktree remove + git branch -D。
  编排 subagent 的会话，负责收尾它派生的 worktree。
  确需保留的（待裁决/有冲突）须在最终回复里点名路径与原因。

配套审查提示词：「帮我看看哪些 worktree 还没有同步到 main，同步好的直接删除，没同步的列出：分支、修改内容摘要（含最近几次 commit）、对应 session」。清理提示词：「明确值得合并的帮我合并并清理 worktree，不确认的给我确认，但要给出清晰建议」。

📎 来源：[宝玉] worktree 收尾与 AGENTS.md 规则
B

给 Agent 讲清"为什么"，而不是只讲"怎么做"

前沿模型今天出错，往往不是没听懂指令，而是对你的目标做了错误假设——例如以为在给"自己"写代码就输出压缩代码。因此规则文件应从逐步骤指令，转为说明意图与优先级。

# 弱的写法（只讲 how）
方法 A 在 B 类上，请给 C~F 类各加一个等价方法。

# 更好的写法（讲 why）
这段代码由团队工程师长期维护，需要人类可读。

用 Prompt Caching 把重复上下文的成本砍掉一个数量级

场景：同一份 10,000 token 的合同，配 50 个用户问题一起发送，就意味着 500,000 个输入 token 按全价计费——而这些内容模型其实已经处理过。缩短提示词或缩小上下文窗口都能降本，但会牺牲上下文质量。

Amazon Bedrock 的 prompt caching 在重复发送相同上下文时，输入 token 成本最高可降 90%。对 RAG、长系统提示、多轮 Agent 会话这类"大量请求共享重复前缀"的负载，这是最直接的降本手段。设计要点是把稳定不变的部分（系统提示、文档、对话历史）放在缓存前缀位置，易变部分放在后面。

📎 来源：[Artificial Intelligence] Optimizing cost and latency with Amazon Bedrock prompt caching

固定 SLO 下做全栈推理优化：718 → 1,997 tok/s 的五层方法

NVIDIA 用 NIM 在 4×B200 上把 Nemotron 3 Ultra（550B-A55B，MoE + Mamba 混合架构，原生 256K 上下文）的系统吞吐从 718 tok/s 提升到 1,997 tok/s；在每用户 50 token/s 的同等交互体验下，同一套硬件可服务约 2.78 倍并发用户。

关键在于这个 "2.5x" 的测量前提极其具体：负载是典型 agentic 场景（64K 输入、400 输出，76% KV 复用），交互目标是 20ms 的 token 间延迟（ITL）。五层优化包括：NVFP4 量化 + 面向 MoE/Mamba 异构内核的自动调优；TP=4/PP=1 配合专家感知执行；以及 NIM 2.0.12 的推荐 profile。方法论上的启示是——报吞吐必须绑定延迟 SLO 与负载画像，否则数字没有可比性；同时长上下文 + 高 KV 复用率的 agentic 负载，值得专门做前缀复用与并行策略调优。

让 RAG 答案"可追溯"：引用粒度与验证 UI 的工程化

RAG 通病是答案看起来合理却无法验证。把"信任"拆成可操作的工程要求：每个论断都能追溯到页码与原文片段——不是让模型更聪明，而是让答案可审计。

参考管线是"云端解析一次，本地无限迭代"：解析层用 LlamaIndex LlamaParse 生成布局感知的 Markdown 并保留页码元数据、按文件哈希缓存；本地层用 nomic-embed-text 嵌入 → 向量索引持久化 → 检索 top-4 → 本地 qwen3:4b-instruct 生成；引用层用 CitationQueryEngine 把上下文切成编号块，强制模型以 [1]、[2] 内联引用。

三个值得记住的判断：解析是天花板而不是模型（基础文本提取会把双栏论文串读、把表格打散，答案上限在管道最前端就定死了）；引用粒度是权衡（512 字符块越小越精确、但推理上下文越破碎，需按文档类型实测）；引用 ≠ 正确（表格数值配错列头时，页码再准答案也是错的，所以要把验证 UI 当诊断工具，让失败能归因到解析/检索/生成三段之一）。
