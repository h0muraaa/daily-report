Vercel 把 Data Cache 收编进 Runtime Cache，统一为跨框架、跨 API 的数据缓存产品。使用 Next.js fetch 缓存或 unstable_cache 的项目无需改代码即可切换。容量上，Pro 每个项目、每个环境独享一份 Runtime Cache 存储，是过去团队共享池的 8 倍；Enterprise 是此前的 10 倍。迁移后，原先不计费的 Data Cache 读写将按 Runtime Cache 价格收费：每百万读单元 0.40 美元、每百万写单元 4.00 美元，并按区域浮动；Hobby 每月免费 100 万读 / 20 万写，Pro 从每月 20 美元基础设施额度中抵扣。

Vercel Daemons 新增 Service Bindings 与存活探针

Daemons 现在可以通过 service bindings 调用同一部署内的服务：在 Daemon 上声明绑定，指定目标服务与接收 URL 的环境变量，之后像普通 HTTP 端点一样调用，内部路由、认证与 TLS 由 Vercel 处理，目标服务保持私有。绑定是单向的，服务不能反向绑定 Daemon；每个实例始终调用启动它的那次部署，即使发生 promotion 或 rollback 也不漂移。同时上线的 livenessProbe 支持配置 HTTP 存活检查，Vercel 会周期性请求该端点，失败时重启容器——用来抓「进程还活着但已经不健康」的 Daemon。

这相当于把 Kubernetes 里最基本的两个原语搬到了边缘运行时。给 Daemon 加一个轻量 /healthz，成本很低，收益是能自动收敛卡死实例。

DoorDash 把杂货复购延迟从 16 秒降到 2 秒：批处理推理 + 确定性校验

DoorDash 通过预计算解决复购场景的延迟问题：用批量 LLM 推理提前算出用户的周期性采购需求，再用确定性逻辑做校验，而不是在用户点击时现场调用模型。实时商品目录解析保证选品不过期，可编辑的购物清单界面则避免了不必要的模型调用。结果是购物清单浏览量翻倍，该流程下单率提升约 34%。

Netflix 平台工程两则：Titus 单租户隔离，GPU 可靠性按分布式系统治理

Netflix 为 Titus 容器平台增加了单租户模式：一个任务独占一台规格匹配的 EC2 实例，由 Compute/Platform 团队继续负责主机维护与补丁，应用团队保持相同的 API 与部署路径。这为有强隔离需求的负载提供了介于普通容器与完整 VM 编排之间的选项。另一条线是 GPU 可靠性：Netflix 把大规模 GPU 训练与推理的故障当作分布式系统问题处理，采用分层健康检查、自动修复与容错训练，让作业在硬件故障下继续运行，而不是依赖单机稳定。

两条实践的共同点是「不假设硬件可靠」：隔离解决的是安全与噪声邻居，容错解决的是故障率。做大模型基础设施的团队可以重点看它的健康检查分层设计。

深度技术解读

两个值得写进团队技术雷达的话题

一、同一个模型，ARC-AGI 从 30 分到 95 分：差距在 Harness，不在权重

素材：YC Paper Club「Harness Night」· InfoQ 编译 · 阿里云《AI Agent Handbook》

Reddit 上每隔几天就会出现「Harness 不过是提示工程的包装纸」的论调。YC Paper Club 的 Harness Night 用一个反例开场：同一个权重文件，换一套 Harness，ARC-AGI 成绩可以从 30% 直接拉到 95% 甚至 100%。如果差距主要来自外层工程，那么「等下一个模型」就不该是唯一的优化路径。

Harness 到底是什么：三层上下文模型

Prime Agent 作者 Seth Karten 给出的拆解是：上下文分为三层——L1 模型权重；L2 活跃上下文加 REPL；L3 文件系统这类可调度的外部状态。Harness 的工作就是在层与层之间做压缩、增删改查与精炼，本质上是「缓存 + 垃圾回收」。

他给了一个很形象的类比：裸 LLM 像图灵机，Harness 像冯·诺依曼计算机——因为后者能在外部存储上读写，表达力高出一个量级。由此得出的判断标准也很直接：Harness 的价值在于表达力。ReAct 那种固定循环模型已经原生会了，不必再显式强加；真正需要工程化的是压缩、Python 执行、文件读写这类能力。另两位讲者分别补上了硬件边界与组织落地：Harness 能跑在什么设备上，以及放进真实团队后，权限、信任和协作往往先出问题。

企业视角：从试点到可治理生产

阿里云开源的《AI Agent Handbook》把 Harness、Runtime、Agent、Workflow 等术语统一了一遍，避免「同一个词各说各话」被模型放大成混乱。其中的调研数据对做技术规划很有参考价值：

  • 已开发完成或开发中的企业 Agent 合计约 46%，但真正部署到生产约 18%，持续迭代的更低；
  • 单 Agent 约 40%、多 Agent 约 42%、以 HITL 为主要架构约 15%——自主度是可调参数，不是新旧替代；
  • 构建后的真正难点：上下文/记忆需求约 90%，多模型路由与成本治理约 63%；
  • 评估上人工抽查约 55%，基于轨迹的自动评估不足 8%；成功率 90% 以上的团队约一成，约 16% 根本没量化过成功率；
  • MCP 关注或落地约 37%，企业内私有部署仅约 9%——缺的是注册中心、身份鉴权、版本灰度、审计与网关，不是协议本身。
实践建议：把预算从「换更强的模型」分一部分到 Harness 与评测体系。最小可行路径是：先给 Agent 建轨迹采集（每一步的输入、工具调用、产物），再做基于轨迹的自动判分，最后用 A/B 对照验证改动是否真的提升成功率与成本效率。没有轨迹数据，调优只能靠人肉翻日志。

同一天还有两个可对照的工程案例：字节火山引擎 AgentKit 的技能评测用「Agent as a Judge」查轨迹、读产物、跑脚本，并给出要改的文件与行号；小红书的 QE Agent 用上下文工程加多端质量知识图谱，支撑 Agent 自主设计用例、动态执行 DAG 与联合断言，每月完成 150 余次完整测试。方向一致——把「判断对不对」也工程化。

来源: InfoQ · meng shao (@shao__meng) · 字节跳动技术团队 · 小红书技术 REDtech

二、AI 写代码变快了，交付为什么没变快：三份一线账单

素材：Revolut 2000 人工程实践 · Cursor 工程师 Token 账单 · 腾讯云「AI Coding 隐性账单」· Spotify 变更量翻倍

Revolut 的 AI 运营负责人 David Abitbol 展示了一张覆盖约 2000 名工程师的内部曲线：一条是编码时间，另一条是交付周期（从接到需求到代码合并、可部署）。他们真正关心的是后者有没有缩短。现实是早期有工程师每月在 AI 上花 1000 美元，也有人花到 1 万美元，额度很快成了瓶颈。Revolut 的解法不是继续压额度，而是把日常编程任务迁到自托管 GLM，Claude Code 与 Codex 仍然可用但不再是默认选项：56 张 B200，混合 Token 成本约每百万 0.30 美元，在 GPU 没有增加的前提下首 Token 等待从 14.26 秒降到 1.68 秒，账单约为过去付给 Anthropic 和 OpenAI 的十分之一。

另一端是极值案例。Cursor 一位工程师的公开用量显示过去 30 天消耗 1.5 万亿 Token。按每百万 8 美元估算，日均约 38.4 万美元、年化 1.32 亿美元；即便按大客户一折计算，年成本仍有约 1300 万美元。作为对照，Jellyfish 对 1.2 万名开发者的统计显示，典型用户（P50）每月约 5100 万 Token，P90 约 3.8 亿——也就是说这位工程师的用量约为典型用户的 2.9 万倍。数字有营销成分，但它揭示了一个真实问题：Token 消耗与产出之间没有天然的比例关系。

瓶颈在哪里：从信息论看「隐性账单」

腾讯云开发者团队把问题拆得很清楚：一份需求通常只说明要解决什么问题，真正实现时还要确认业务规则、现有系统限制、异常处理方式和验收标准。这些内容如果没有在上下文里告诉 AI、AI 也没从代码里查到，模型就只能按常见做法猜测，并把猜测写进代码。需求在 chat 中、在产品/架构/开发/测试之间反复转述时，依赖经验与具体场景的细节最容易丢失。随着生成代码变多，人的检查能力、系统集成速度和运行反馈会逐渐跟不上，返工、维护负担与代码腐化随之上升。

所以 AI Coding 的收益高度依赖任务类型：规格明确、容易验收的「日抛型」应用，生成速度能转化为交付速度；规则复杂、系统耦合多、需要长期维护的应用，收益提升有限，因为瓶颈从「写」转移到了「验证与集成」。

Spotify 的样本：变更量翻倍后，控制体系先升级

Spotify 8 月合并变更量同比增长一倍以上，从约 8100 个增至 17000 个。它运营着近 3000 个生产服务、7.77 亿月活、每秒 1100 万至 1200 万次后端请求，因此把重点放在质量与可靠性控制：强化监控、测试、发布防护、回滚能力、容量规划与质量度量。一次内容处理流水线事故中，计划内批处理任务与新节目内容抢资源、一项质量优化抬高资源需求、一个调度错误又使吞吐量降低约 10%，叠加导致原本几分钟上线的节目延迟数小时；事后补了端到端监控、修复调度器、调整任务优先级并扩容。集群自动化方面，其系统已合并超过 250 万个自动化维护 PR，并引入在 Kubernetes Pod 里通过 Agent SDK 运行 Claude 的后台编码智能体 Honk，由 Fleetshift 负责目标选择、调度与进度跟踪——最近一次后端 Java 迁移只用了三天。

实践建议：用「交付周期」而不是「代码行数/生成速度」做 AI 编程的 KPI；在交给 AI 之前，把业务规则、异常路径、验收标准显式写进任务描述；为验证环节预留人力与自动化容量（CI 时长、评审队列、灰度与回滚）；对高频日常任务做成本分层，默认模型不必是最贵的那个。

02

给 AI 编程任务补全「规格四要素」

腾讯云实践指出，AI 写码快但交付慢，根因常是上下文缺失导致的猜测与返工。任务下发前，至少补齐：

  • 业务规则：边界条件、例外场景、与现有系统的约束；
  • 验收标准：可执行的测试或明确的判定条件；
  • 上下文入口：让 AI 能查到的代码路径、配置、历史 issue；
  • 验证预算：CI 时长、评审队列、灰度与回滚方案。

然后用交付周期（需求到可部署）衡量效果，而不是代码生成速度。

03

为 Agent 建轨迹级评测，而不是只看最终答案

阿里《AI Agent Handbook》的数据显示，基于轨迹的自动评估占比不足 8%，而人工抽查约 55%——这是规模化的最大瓶颈之一。可参考的三个现成做法：

  • AgentKit 的「Agent as a Judge」：裁判 Agent 查轨迹、读产物、跑脚本，并给出要改的文件与行号；
  • 小红书 QE Agent：上下文工程 + 多端质量知识图谱 + 动态执行 DAG + 联合断言；
  • Sonar 的 Gitar 演示：通过项目配置执行业务规则，甚至能抓到不在 diff 里的跨 PR 缺陷。
04

把缓存计费与模型成本纳入架构评审

Vercel Runtime Cache 的迁移是「代码零改动、账单有变化」的典型。建议：

  • 统计现有 Data Cache 的读写量，按每百万读 0.40 美元 / 写 4.00 美元估算月成本；
  • 检查是否有高频 revalidate 或缓存键爆炸；
  • 模型侧做分层：日常任务用自托管或低成本模型，难题再升级到旗舰模型（参考 Revolut 的默认项调整）。
05

复杂故障排查：先承认「可能是多层同时出问题」

Google Cloud 记录的一起事故里，约 800 名开发者连续数周无法部署到生产，表面症状只有「Pod 间歇性连不上 Kubernetes API」。最终发现是三层网络中三个独立 bug 同时作用，制造了同一个超时表象。方法论上的启示：

  • 不要假设单一根因，先列分层假设（应用 / 容器网络 / 主机网络 / 控制面）；
  • 每个假设都要有独立的可观测证据，而不是靠症状相关性；
  • 可观测性优先放在 Mesh 层：统一的 Trace Context 传播、RED 指标与带 Trace ID 的访问日志，能减少业务侧埋点侵入（见掘金《Service Mesh 可观测性》）。
  • 架构迁移同理：淘宝直播用「统一物料 + 声明式编排 + 受约束流程语义 + 结构化执行诊断」把 362 万行代码的生产方式重构，再把迁移经验沉淀成 Skill 交给 AI 复用。
