06Agent Harness 不是固定属性：南洋理工《Finding the Right Fit》

新加坡南洋理工大学安波团队发布报告《Finding the Right Fit: Model–Harness Interactions across Agent Tasks》，把模型与 Harness 视为一个整体来比较，而不是做一张简单的 Harness 排行榜。实验覆盖 OpenHands、DSH、PI、openJiuwen 四套可配置 Harness，并以 Codex–GPT、Claude Code–Claude 两组原生搭配作为参照。核心结论：Harness 的好坏并非固定属性，而取决于它与模型、任务之间的具体组合——同一套 Harness 换到另一类任务未必仍是最佳，厂商原生 Harness 也不一定最适合自家模型。与其找「放之四海皆准」的通解，不如围绕真实任务对模型与 Harness 做联合评估。

##

深度技术解读

02 / 06

① Agent Harness 正在成为新的工程层：改 harness，而不是改权重

// 三篇新论文 + 一个观察：把 harness 当作可迭代、可评测、可版本化的代码资产

过去一年，"提升 Agent 能力"的默认路径是等更强的模型。但今天这一批研究指向了另一条路：把 harness（工具调用、上下文管理、错误恢复那一层）当作可编辑的代码来优化，而且模型权重保持不变。

  • CMU 的 harness learning：作者用 RL 训练一个 proposer 模型，让它读任务、当前 harness 和执行报告，然后直接写一段修改 harness 代码的编辑，奖励就是修改后 harness 的得分——solver 模型全程不动。结果很反直觉：训练后的 4B proposer 在 Reasoning Gym 的单步修订上击败了它的 35B 教师模型，甚至包括训练中从未见过的任务族；在 HotpotQA 上训练的 proposer，还能持续改进 MuSiQue、2WikiMultihopQA 上的 harness。作者直接把"通过编辑 harness 代码而非权重来改进 Agent"称为一项新的 AI 工程技能。
  • Microsoft 的 ScholarEvolve：把 harness 拆成工具使用、记忆管理、任务执行三个模块，然后从已发表的 Agent 研究（而非自己的失败日志）里用主题建模提取改进策略，实现并测试各种组合，并且新论文可以持续加入。模型固定为 Qwen3.5-27B 时，AppWorld Challenge 的目标完成率从 49.6% 升到 63.6%；GPT-5.4-mini 在 Tau2-Bench Telecom 上从 72.7% 升到 81.9%。
  • Google 的 VeriHarness：针对"采样多次、信任多数一致答案"这一常见做法，论文指出一致可能掩盖共享错误，而分歧往往指向正确答案的替代项。VeriHarness 把同一个基座模型变成"智能体验证器"，做两件事：对分歧答案核查工作区证据来裁决；对全体一致的结论主动挑刺，找它们都漏掉的需求。五个长时程 benchmark 上取得最优选择分数，配合证据驱动的修订，Gemini 3.5 Flash 提升 6.2 分、Claude Opus 4.8 提升 6.4 分，并开源约 26,000 条 rollout。

把这三篇和 @李继刚 的观察放在一起看会更清楚：Agent 的发展"基本是一路补短板"——缺事实就加检索、长任务丢信息就加状态保存、工具会失败就加重试恢复、可能越权就加权限审批、结果不达标就加测试验收。但每一层支撑都自带代价（延迟、维护成本、错误传播、协调开销）；同时模型进步又会把其中一部分能力吸收进模型内部，让结构重新变简单。

落地建议：别再问"该选哪套 harness"就完事。把 harness 当成有版本、有评测、有回归测试的代码资产，围绕你真实的任务集做模型×harness 的联合 A/B；用"编辑 harness"作为第一优化手段，权重微调留到最后。
📎 来源：CMU harness learning (elvis/@omarsar0) ｜ Microsoft ScholarEvolve (@omarsar0) ｜ Google VeriHarness (@omarsar0) ｜ 李继刚 (@lijigang_com)

② 让 Agent 在生产里"活着"：异步人机协作、预算硬上限与沙箱隔离

// 一篇 Temporal 演讲 + 一个呼吁 + 一份沙箱选型清单 + 两则故障自愈实践

Agent 从 demo 走向生产，绕不开三个"活下来"的问题：等人类怎么办、失控烧钱怎么办、跑到别人的机器上怎么办。

  • 人类是异步 API。Temporal 的 Melanie Warrick 指出，阻塞式的 "ask the human" 调用在生产必然出问题——人类不会 200ms 返回。她用 wait condition + signal 两个原语，让 Agent 为一个人类审批暂停几分钟甚至几周，并现场演示在审批中途 kill 掉 worker 再拉起来、不丢任何工作。结论是 durability（持久化状态）应该属于 agent harness：由 workers / workflows / activities 追踪状态，而不是靠代码里的 sleep 和内存变量。
  • 默认硬预算上限。Simon Willison 呼吁：pay-by-usage 服务和 API 需要"花到 $X 就切断并返回错误"的硬上限，而不是"发警告邮件"的软上限。理由是 coding agent 和个人 agent 让"起一个会花钱的东西"的摩擦急剧降低——调用付费 API、起托管 Web 应用、自动扩容存储和算力——没人想睡醒发现账户被刷爆。
  • 成本治理三步。LangChain 的 Harrison Chase 分享：编码 agent 成本连续两个月显著下降，靠的是 ①成本可见性——把所有调用 trace 到 LangSmith，看清谁在用什么、怎么用；②成本控制——在 LLM gateway 上设用户级费用上限；③优化 harness——越来越多编码走自研开源云 agent OpenSWE。
  • 沙箱选型。@meng shao 结合阿里《AI Native 研发范式实践手册》整理了一份开源 Agent Sandbox 清单：腾讯云 CubeSandbox（基于 KVM MicroVM，带控制面/调度/网络与凭据策略/快照，兼容 E2B SDK，适合国内生产级自建）、阿里 OpenSandbox（Docker/K8s、多语言 SDK、MCP、浏览器与桌面执行环境）、字节 AIO Sandbox（browser/Shell/文件系统/VS Code/Jupyter/MCP 一体化，Docker 形态）与 SandboxFusion（面向 LLM 代码执行、Online Judge、代码评测与 RL 数据集，支持多语言与部分 GPU）、AWS Firecracker（高隔离多租户 MicroVM 底座，上层需自建）、Google gVisor（用户态容器安全运行时）。
  • 训练也要自愈。Crusoe 分享在 Kubernetes 之上自建 Managed Slurm：千卡规模硬件故障是必然，AutoClusters 能对 XID 79 GPU 故障做全自动修复，并现场在训练中途 kill 掉一块 GPU，15 分钟内从 checkpoint 恢复、无人干预。
  • 可观测性要能喂给编码 agent。LiteLLM 推出 LiteLLM Lens：当 Agent 蜂群并行跑到 20 万+ 条轨迹，人工审查已不可能。Lens 让 Agent 自动审查轨迹、聚类问题、产出"带证据的改进建议"，且数据自托管在用户自己的 ClickHouse 中，通过无速率限制的 SQL/API 直接供 Codex、Claude Code 消费——卖点是数据主权：不再被 tracing 平台锁死。详见下方工具推荐。
落地建议：为长任务的人机交互补上持久化等待（别用阻塞轮询）；上线前先给所有付费调用装"硬熔断"；给 Agent 一个隔离沙箱并明确凭据策略；把生产轨迹导进自己的存储，让编码 agent 能直接消费。

2

Prompt / Memory / Weights 不是阶梯，而是三种工具

Oracle 的 Anant Srivastava 用一个"微调之后开始编造产品名"的支持助手案例说明：架构常常是"正常产品迭代六个月"意外堆出来的，而不是设计出来的。一套简单诊断法：prompt 管小而稳定的行为；memory 管需要最新、体量大、可引用或访问受控的知识；weights 只留给那些已经不再变化的"反射"。别再靠微调去解决检索问题。

📎 来源：Anant Srivastava · Stop Fine-Tuning (AI Engineer)
3

批量生成的核心是幂等，不是并发

《AI 短剧批量生产实战》把异步生产的坑拆得很透：几十个镜头、异步接口、网络超时、下载中断、Key 轮换，某个请求到底有没有创建成功都不一定知道——简单"再试一次"就会重复生成、重复扣费，甚至把同一集生成两遍。要点是让每个任务都有可恢复的身份（Task ID）、明确的状态、以及不会重复扣费的失败路径，用 Excel/CSV 当任务规格，配断点续跑。这个模式对任何"批量调异步 API"的任务都适用。

📎 来源：山行AI
4

AI 时代的 PR Review：可以少 Review，但不能没有验证

关于"不逐个 Review PR"的讨论越来越主流——在 SpaceXAI 做 Grok Bot 的 Lauren Tan 一个月合并 2500 个 PR，晚上让 AI 自查自合、第二天抽查。宝玉提醒的要点是：先弄明白"她凭什么能这么做"，再决定要不要学——靠的是让 AI 能像真人用户一样把程序用一遍自己发现问题，以及给代码定下足够多的规矩让 AI 很难写烂代码（她把做法开源为 pstack）。另一面，马东锡提醒警惕把 AI review 当作办公室政治工具：恶意会在不知不觉中耗尽被攻击者的 token 和正向情绪。

📎 来源：马东锡 NLP (@dongxi_nlp) ｜ 宝玉 (@dotey)
5

分离「操作意图」与「执行器」

freeCodeCamp 的文章主张：软件自动化需要在 operational intent 与 execution 之间加一层——规格只描述"成功是什么"，执行器决定"怎么做"。这样带来的可能性是：如果操作规格独立于执行机制，那么多个执行器都应该能满足同一份规格。但随之而来的问题很硬：两个不同执行器能否达成同一结果？如何比较？执行器变化时什么必须保持稳定？哪些差异可接受？每个执行器该产出什么证据？

📎 来源：freeCodeCamp
6

让模型的输出"讲透"：Karpathy 的四级递进

Karpathy 公开了他让大模型把内容讲透的四套技巧，从文字到视频递进：①写作——用 ASD-STE100 受控语言规范（源自航空维护文档，词汇受限、规则严格，也可要求只达到 80% 标准）生成干净好读的文本；②图表——让模型直接出图，图形比纯文本更易吸收；③可交互 HTML——直接要求输出 HTML，模型前端能力强，这在 Claude Code 团队内部几乎已是默认输出形态；④定制解说视频——他目前最看好的形态。

📎 来源：AI寒武纪
