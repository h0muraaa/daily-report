补丁日警报：Ruby / PHP / Java / nginx 多个可 RCE 的严重漏洞同日修复

CRITICAL

一夜之间四条高危线并行，建议今天就把依赖体检排上：ruby2shell（CVE-2026-132825）是 Ruby 字符串大小写转换中的堆缓冲区溢出，Ruby 官方评为 Critical 且已有 RCE PoC，Rails 与经典 Sinatra 在默认配置下、未认证即可触达，GitLab、GitHub Enterprise Server、Mastodon、OpenProject、Discourse、Chatwoot 等自带 Ruby 的产品均受影响，已修复于 3.3.14 / 3.4.13 / 4.0.10。

phpAfterShell（CVE-2026-126714，CVSS 4.0 达 9.2）出在 PHP 默认的文件型 session handler，可导致远程代码执行，同日修复于 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 / 8.6.0，且一并修了另外 16 个安全问题（含 6 个 critical）。

Java4Shell（CVE-2026-114938）是部分 Java 运行时硬件加速 Base64 解码器的内存破坏，恶意 Base64 输入可污染 JVM 进程内存，导致崩溃或 RCE；这不是 TeamCity/YouTrack 自身的问题，但它们的 server 与 agent 跑在受影响 JVM 上，JetBrains 已发修复运行时（如 YouTrack Server 2026.2.19884 等）。此外 nginx2root 披露了 5 个未认证可触发的内存破坏漏洞，配合一个 Linux 内核 bug 甚至能从 Docker 容器内拿到宿主机 root。Cloudflare WAF 已对包括免费版在内的客户提供拦截。

Vercel Functions 请求体上限从 4.5MB 提到 20MiB（Public Beta）

BETA

此前 Vercel Functions 的入口请求体上限是 4.5MB，常逼着开发者外挂对象存储做上传中转。现在可通过环境变量 VERCEL_SUPPORT_LARGE_REQUEST_BODY=1 开启 20MiB 上限，按“环境”生效，因此可以只在 Preview 打开试跑再推到 Production。两个硬约束要注意：函数需使用 4GB 内存档；且仅适用于 Node.js / Python / Bun 运行时与 Routing Middleware，Edge 运行时仍维持 4.5MB 并对超限返回 413——想用大包体就得从 Edge 迁到 Node 运行时（Next.js 用 runtime: 'nodejs' 或 proxy.ts）。

📎 来源：Vercel Changelog

Modern Web Guidance：给 Agent 装上“现代 Web 大脑”

为什么 AI 写前端总爱用 2020 年的写法？

Chrome 联合 Firefox、Edge（以及 MDN 与社区贡献者）发布了 Modern Web Guidance，上线 1.0 后 48 小时就冲上 GitHub trending 第一。它要解决的问题是：大模型预训练时看过大量旧代码和旧教程，遇到类似需求容易沿用老写法，而不知道浏览器已经有了更简洁的原生能力。

它到底解决什么问题

举个原文里的例子：聊天输入框文字换行时，老办法是每次输入后用 JavaScript 重新计算并设置高度；现代做法是固定宽度、让高度自适应即可。但 Agent 往往不知道这个特性存在，于是继续写一堆 JS。Modern Web Guidance 把这些“专家审过的写法”按场景整理成指南，并通过 Skill 注入 Codex、Claude Code 等 Agent。

怎么用

# 给 agent 安装 skills
npx modern-web-guidance@latest install

# 扫描现有代码库里的“遗留写法”
npx modern-web-guidance@latest legacy-scan .

装好后，Agent 在接到 Web 任务时会先用命令行工具在本地检索：既可以点名某个浏览器特性，也可以只描述想要的效果——检索会同时匹配关键词与语义。找到指南后，Agent 能读到具体写法、容易漏的细节，以及如何兼容项目需要支持的浏览器。

另一个细节：回车键与输入法

很多聊天框用回车发送、而拼音输入法也用回车确认候选词。如果一收到回车就发送，正在编辑的半句话可能被误发出去。正确的做法是先检查按键事件里的输入法组合状态（如 isComposing）再决定是否发送——这类“反直觉但真实”的坑，正是 Modern Web Guidance 想让 Agent 提前知道的。

📎 来源：Ding(@dingyi) ／ 逛逛GitHub 详解

淘宝直播 LiveX Wiki：用 LLM Wiki + OKF + Git 给 Coding Agent 建知识库

当 RAG 不够用，业务知识该怎么“喂”给 Agent？

淘宝直播互动团队在 AI 生码实践中发现：传统 RAG 向量库在复杂业务编码里有明显瓶颈——知识碎片化、相关性低，召回片段还得人工补齐场景边界、依赖关系和“当前事实”。他们把建设重点从“材料检索”推进到“结构化组织 + 按需消费 + 持续维护”，做出面向 Coding Agent 的 LiveX Wiki。

三层结构

  • LLM Wiki 编纂业务理解：用大模型把跨端跨仓的业务经验写成可读的业务知识。
  • OKF 组织知识表达：借鉴这种思想表达知识的“身份与关系”，让知识可被机器解析。
  • Git 管理版本迭代：知识随代码一起版本化，用 LLM + Git 完成自动更新与工程治理。

整体按“域 → 场景 → 知识”三层组织，把跨端、跨仓的业务经验显式沉淀为机器可解析的上下文，而不是丢进向量库等运气。消费侧则用层次索引 + Agentic Search 实现按需取用与“回源核验”，避免一次性灌入过量上下文。

效果数据

  • 端到端生码平均得分较“无知识库”提升 39.15%。
  • 较 RAG 方案提升 30.1%。
  • 线上仓库定位准确率从 60% → 90%。

这条路径的价值在于：通用 Coding Agent 与真实业务需求之间的“认知鸿沟”，靠的不是更大的模型，而是可核验、可维护、可版本化的业务上下文供给。对正在给内部代码库接 Agent 的团队，这是一份可直接对照的架构样板。

📎 来源：大淘宝技术 · LiveX Wiki

实践指南

PLAYBOOK

“健康代码”能让 Agent 审查成本降低 22–35%

Martin Fowler 转述 Marcus Borg 的一项实验：用 CodeScene 的 CodeHealth 指标，在 3 个模型、465 个 PR、246 个开源仓库上，用 5 个 agent 串成 review + fix 流水线。结论是——健康代码（CodeHealth 9.7）比典型不健康代码（2.8）的 agent 审查成本低 22%–35%。导致成本上升的主要 code smell 是 Complex Method 和 Complex Conditional。

实践含义：在 agentic engineering 时代，“代码质量”不再只是给人看的整洁度，而是直接变成 token/时间的账单。重构长方法和复杂条件分支，等于直接给 Agent 降本。

📎 来源：Martin Fowler · Fragments 2026-11-20

用“规格 → 计划 → 实现 → 验证”闭环压住 Agent 漂移

Coding agent 的通病是“漂移”：多写代码、跳过边界情况、忽略规则。JetBrains 的 Paul Everitt 与 Konstantin Chaika 用一条 spec → plan → implement → validate 的实时循环把 agent 拉回轨道。落到工程上，可以把 AI 编程成熟度拆成三层：第一层是流程（规格驱动，如 OpenSpec + Superpowers，一次变更自动产出提案/规格/设计/任务并走完探索→归档六阶段）；第二层是 Loop 工程（给一个可量化、可验证的目标，让 agent 执行→验证→反馈→修正，连续几轮无提升则回退）；第三层是多 Agent 统筹。

原文点破的关键：多数人把 AI 当聊天工具用，而高效的人把它当“生产系统”来驾驭——差距就在“有没有把验收标准和回退机制写进去”。

📎 来源：DeepLearning.AI · JetBrains 工作坊 ／ 架构师之路 · 三层差距

别编辑历史消息：OpenAI Responses API 的缓存与推理复用

OpenAI 明确提示：用 GPT-6.2 Astra / Sol 走 Responses API 时，保持对话历史不变、只追加新轮次，不要回头修改早期消息。原因是新模型开始把每个 reasoning item 绑定到它之前的对话历史；一旦编辑早期消息，API 会丢弃该改动之后的所有推理。正确做法能带来更少 token、更高缓存命中，并让 agent 复用先前推理而不是重复计算。这正好对上社区反馈里反复出现的“缓存命中率低”问题——很多时候不是模型慢，是调用姿势把缓存打没了。

📎 来源：OpenAI Developers ／ 使用建议 ／ Gemini 反馈中的同类问题
