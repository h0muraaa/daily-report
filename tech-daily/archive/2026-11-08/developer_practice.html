Cloudflare 开源的 AI 代码安全审计技能：6.6 万 Star，六步审计流程

安全Agent

这是 Cloudflare 官方出品的开源免费「security audit」技能，装进编程智能体后即可变成一支审计小队：先摸清架构，再按覆盖账本分头找漏洞，每个可疑点交给另一个智能体尝试推翻，最后输出带证据的报告。它的核心约束只有一条——检查漏洞的永远不是发现漏洞的那一个。流程分为侦察 → 按覆盖账本狩猎 → 独立验证 → 结构化输出 → 回源码复核 → 生成报告，并针对内存安全、大模型、Web 协议、供应链、云部署等 10 个领域各配一份攻击清单。官方自测显示单次运行大约只能找到多次运行总数的一半，因此设计成可反复跑、接续账本补漏。安装方式：npx skills add github.com/cloudflare/... --skill security-audit。

开源Agent

新开源项目 terminal-mac 利用苹果虚拟化技术，在你的 Mac 里再运行一套真正的 macOS，并把桌面画面显示在终端中。价值不在于炫技，而在于把 Agent 和你自己的桌面隔离开：Agent 在虚拟机里点击、输入、跑应用，不会抢你的鼠标键盘，也不会动主机的剪贴板。接上 Claude Code、Codex 后，Agent 可以先截图看当前界面，再执行操作，完成后再截图核对变化，很适合让 Agent 自测 Mac 应用。项目开源不久已获 2000+ Star。

深度技术解读

两个今天最值得开发者细读的工程话题：Agent 的记忆架构，以及 Agent 的自验证与可回滚能力。

深读一：Agent 记忆不是「存得越多越好」——Anthropic 的四层记忆与「做梦」机制

关键词：分层记忆 / 后台整理 / 纠错比新增更重要

Anthropic 工程团队拆解了给 Claude 设计跨会话记忆的方法。难点很实际：模型必须在当下决定什么值得记，可它并不知道以后会用到什么。他们的解法是在会话结束后加一个后台步骤，称为「做梦」（dreaming）——让 Claude 回头翻原始对话，改掉记错的笔记，把零散信息整理成更好检索的结构。思路类比人脑睡眠时的记忆固化。

更值得记住的是它的分层设计，从下到上共四层：

  • 原始会话记录：可搜索的原始日志，作为事实来源；
  • 记忆笔记：Claude 自己写的摘要与结论；
  • 结构化整理：例如互相链接的 wiki，便于跨条目检索；
  • 上下文注入：每次开新会话自动塞进上下文的顶层内容。

「做梦」负责把下层内容核对、提炼后往上送。效果用数据说话：在查数据库答题的测试里，Opus 5 有记忆后从 0.564 提升到 0.828（满分 1）；在 Stainless 约 35 万个文件、4.2 亿 token 的内部资料上出 25 道题，让 Opus 5 一轮轮「做梦」把资料整理成互相链接的 wiki，轮次从 2 加到 128，仅靠 wiki 答题的得分从 13% 涨到 48%；wiki 与搜索合用则从 54% 升到 61%，每道题还省下约 2 万 token。

最反直觉的结论来自宝可梦实验：一条记错的笔记，比什么都不记更糟。Claude 把关键地点记错后反复绕回原路，做了「梦」、逐条对照原始记录改正后才走出山洞。另一种失败模式是「什么都想记」——Sonnet 3.7 写了 413 个记忆文件只拿到 1 枚徽章，而只写 10 个文件的版本拿到 4 枚。对工程实践的启示很直接：记忆系统的重点不是存储容量，而是写入筛选、定期复核与结构化的检索层。

📎 来源：Berryxia.AI(@berryxia) · 宝玉(@dotey)

深读二：Agent 说「完成了」之后——自验证、可回滚与自我改进的闭环

关键词：证据交付 / 失败复盘 / 不可逆副作用

今天多条内容指向同一个工程痛点：Agent 汇报「完成」不等于过程正确。Ramp、Warp 与 UndoBench 的研究分别从验收、复盘、回滚三个角度补齐这个问题。

1）先让 Agent 能检查自己。Addy Osmani 的观点是，每项任务都应提供可执行的检查——测试、构建、类型检查，界面改动则用截图验证。Agent 应先执行、检查、修正失败，再带着证据提交结果，而不是丢一句「完成了」把所有验证留给人。必要时再让一个没有参与原对话的新 Agent 独立审查，避免沿着同一思路自我认可。宝玉的实践也印证了这点：把 Issue 直接交给 Agent 修，要求它提交修复后的截图，很多时候它自己截图时就发现了问题并顺手修掉。

2）复盘要看过程，不只看结果。Warp 的 Ben Holmes 举了一个典型案例：测试 Skills 里的端口指令已经过时，Agent 不断试错、最后仍然完成了任务，团队只看到「慢了一点」，没有意识到真正该修的是 Skills 说明。更合理的流程是：团队先定义评分标准（是否重复测试、工具调用是否高效、表达是否冗长），让评审 Agent 检查任务记录并解释扣分原因，再由另一个 Agent 汇总反复出现的问题，把修复建议变成技能或配置的修改 PR。

3）别忘了 Agent 可能「回不去」。UndoBench / EvoUndo 的研究指出，能完成任务的 Agent 未必能在出错时把状态还原：Git 覆盖不到外部 API 调用、运行时配置和通知，而重试也无法逆转已经产生的副作用。更麻烦的是，在 478 项让 Agent 变强的改动中，有 197 项（约 42%）同时破坏了它的恢复能力。论文提出的做法是先捕获原始状态，再按情况选择重试、恢复、补偿或升级人工，并独立验证结果。

把三点合起来，就是一条可落地的 Agent 工程原则：能力提升必须与验证能力、恢复能力同步演进，否则「更会干活」可能只是「更会制造不可逆状态」。

📎 来源：meng shao(@shao__meng) · meng shao(@shao__meng) · AI Engineer

实践指南

从今天的案例里提炼出可直接落地的做法。

把「结果验证」变成任务的一部分，而不是最后一道人工关卡

Addy Osmani 的建议可以整理成三条：其一，每个任务附上可执行检查（测试/构建/类型检查/截图），Agent 先自检再交付；其二，任务说明重点写仓库里看不到的信息——为什么做、业务约束、哪些不要做、怎样才算成功，而不是重复代码已有的内容；其三，并行的上限往往是人的注意力，无人值守任务开始前要明确完成条件、验证方式、权限、运行上限、交付产物与审批人。成效应看交付周期、返工与回退，而不是 Agent 写了多少行代码。

📎 来源：meng shao(@shao__meng) · Viking(@vikingmute)

给 Agent 建基准：先拆任务，再造「合成数据」反复回测

Ramp 的 AI 记账 Agent 经验值得借鉴：先拆解会计的实际工作（对账、差异分析），再构造带有完整账本的合成企业，让 Agent 能在同一批数据上反复回测。他们区分 accuracy 与 pass@k，指出当前模型仍主要败在推理环节；失败的实验包括自动调 prompt，有效的实验包括删掉不需要的技能、跨两个时间段测试记忆、以及把回归测试定时跑起来并把问题报告到 Slack。对内部 Agent 来说，一套可重复的评测集往往比再多调几版 prompt 更有价值。

📎 来源：AI Engineer · Ryan Stevens, Ramp

结构化数据先行：别让 Agent 直接「看」非结构化输入

AlixPartners 让 Claude Code 处理一笔真实并购后的采购分析：数百家供应商、4 万多份合同。第一版答案看起来完整，但一个总额差了约 80 万美元，一个关键续约截止日迟了一个月。原因包括超长合同被静默漏处理、修订条款没有关联到母合同、费率表跨页被切断。他们最终用一个五阶段流水线先把数据结构化，再配内置业务规则的自定义工具，使每个答案都能追溯到来源。结论：在合同、财报、法规这类长文档场景，先把数据整理成可追溯结构，再让模型推理，比直接丢给模型可靠得多。

📎 来源：AI Engineer · Natalia Connolly & Kevin Madura, AlixPartners

让 Agent 交付「给人看的证据」，而不只是结论

宝玉的做法是把 PR 要求带到 Agent 上：任务完成后让 Agent 自行测试、生成效果截图。关键在于截图或录屏是给验收的人类证明它确实把活干完了；对用户来说 Agent 的自测过程仍是黑盒，只有看到可核对的证据才能确认没被糊弄。对前端与 UI 改动尤其有效，因为 Agent 截图时常常自己就能发现问题。

📎 来源：宝玉(@dotey)

给回滚能力单独做测试：能完成任务，不代表能恢复现场

UndoBench / EvoUndo 的结论提醒团队在评估 Agent 时增加一个维度：出错后能否把状态还原。由于 Git 覆盖不到外部 API 调用、运行时配置与已发送通知，重试也无法撤销副作用，建议在关键 Agent 流程中显式设计「捕获原始状态 → 选择重试/恢复/补偿/升级人工 → 独立验证结果」的路径，并把恢复能力纳入回归测试。否则一次能力升级就可能在不知不觉中削弱可恢复性（研究中约 42% 的能力改动伴随恢复能力下降）。

📎 来源：AI Engineer · Tanmay Sah & Dolly Sah
