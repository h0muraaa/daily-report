01

科学家最看重的两件事，恰恰是 AI 用得最少的

Anthropic 11 月 4 日发布了一份科研场景报告，统计 2026 年 8 月 2 日到 9 月 30 日约 20.7 万次科研相关会话，其中聊天与 Cowork 12.9 万次、Claude Code 7.8 万次。分析数据是第一大用途，占聊天会话的 33.7%、Claude Code 的 48.1%；写作占聊天会话 32%，单项最多的任务是起草论文。但如果对照科学家实际投入的时间，答案会变得微妙：分析数据约占科研时间 28%，写作只占 16%，而收集数据占 28.6%，在 Claude 上却只有约 12%；提出想法和假设占科研时间 7.1%，在 Claude 上只有 4.2%，Claude Code 上仅 2.1%。研究团队还调查了 528 位科学家，请他们给四类工作的重要性分配 100 分，提出想法以 35.6 分排第一。也就是说，用户最看重的能力，使用率反而最低。

这正是用户研究最该盯住的「重要性—使用率落差」。它可能来自信任不足、输入成本太高，也可能来自产品根本没有为「想点子」设计入口。报告估算，现有 AI 能力若普及，部分领域科研产出最多翻一倍；若能包揽所有不用动手的工作，计算机、统计可快约 15 倍，化学、生物只能快 3 到 4 倍，因为实验还得有人在实验室做。

02

姚顺雨：用户黏性来自私有上下文和信任，不是模型分数

在清华讲席教授张亚勤与腾讯首席 AI 科学家姚顺雨的对谈中，张亚勤直接发问：DeepSeek、腾讯、Anthropic、OpenAI，各家用户黏性何在？姚顺雨的回答把护城河拉回产品层：第一是数据和上下文，第二是信任。他举了微信里的 AI 作例子——它不必是最聪明的 AI，但它知道你的日程、朋友和活动，这就很难被取代；一个更聪明的模型，却并不了解你是谁。第二道护城河是信任：用户是否放心让 AI 了解自己的数据和上下文，并替自己采取行动。

这两点都不是模型榜单能回答的问题，而是典型的体验问题。上下文意味着产品要在长期使用中积累可用的「关于你」的信息；信任则要求可见、可控、可撤回的权限设计。对研究团队来说，用户信任不该只用满意度量表测量，还要看用户是否愿意授权、是否检查 AI 的动作、出错后是否继续使用。

记忆不是越多越好：会挑、会改，比记得多更重要

Anthropic 工程团队 11 月 6 日拆解了 Claude 的跨会话记忆。难点在于：Claude 必须在当下判断什么值得记，但它并不知道以后会用到什么。他们的办法是加一个后台步骤「做梦」（dreaming）：会话结束后回头翻原始记录，改掉记错的笔记，把零散笔记整理成更好检索的结构。宝可梦实验很能说明问题：Sonnet 3.7 写了 413 个记忆文件，只拿到 1 枚徽章；Fable 5 只写了 10 个文件，却拿到 4 枚。更关键的教训是「记错一条，比什么都不记还糟」——Claude 把月见山的位置记错后，反复绕回原路，做了一次「梦」、逐条对照原始记录改正，才走出山洞。

规模化实验同样硬核：约 35 万个文件、4.2 亿个 token、25 道题，让 Opus 5 一轮轮「做梦」整理成互相链接的 wiki。做梦从 2 轮加到 128 轮，只靠 wiki 答题的得分从 13% 涨到 48%；wiki 和搜索一起用，从 54% 升到 61%，每道题还省下约 2 万个 token。对产品设计的启示很直接：记忆需要「可查看、可纠正、可遗忘」的界面，否则用户无法判断助手到底记住了什么，也无法修复一条错误认知带来的连锁反应。

04

Personal Agent 的下限：懂用户没说出口的偏好

InfoQ 访谈阿里千问事业部 AI 算法负责人蒋冠军，给出了一个克制但重要的判断：Personal Agent 已经渡过早期验证，进入「长期稳定地替用户做事」的竞争阶段，但「今天的 AI 依旧不好用」。从能调用工具完成任务，到真正理解用户、稳定完成任务，对产品可靠性的要求完全不同。他把更广阔的市场放在生活场景，理由是生活里充满大量「用户自己知道、却没有明确表达」的偏好；真正的 Personal Agent 要在长期使用中逐渐知道这些答案，并判断它们什么时候发生了变化、什么值得提醒、什么时候必须停下来。

他还提到，各家实现框架差不多，基础模型的核心能力差别没有想象中那么大，最核心的差异来自「怎样理解用户需求」以及选择哪些重点方向。执行稳定、个人 Context、生态开放、权限边界和商业模式都还没有定型。这段判断把 Personal Agent 的体验难点说得很清楚：不是演示时能不能完成一次任务，而是第 100 次使用时是否仍然可靠、是否懂得在该停的时候停。

Agent 说「完成了」，不代表过程没问题

Warp 的 Ben Holmes 在 AI Engineer 演讲里提醒：Agent 可能在绕过错误指令、反复尝试之后完成任务，却只向你汇报最终结果。他举的例子很典型——Skills 里的端口说明已经过时，Agent 不断试错，最后还是完成了任务；团队只看到「慢了一点」，却没发现真正该修的是那份说明。因此复盘不能只看最终答案或代码，还要结合对话、工具调用和代码改动，否则每次任务看似成功，下一次仍要重新摸索同一个问题。

他给出的流程是：团队先定义明确的评分标准，比如是否重复测试、工具调用是否高效、表达是否冗长；让评审 Agent 检查任务记录并解释扣分原因；再由另一个 Agent 汇总记录、寻找反复出现的问题，把修复建议变成技能或配置的修改 PR，交给团队审查。重点不是让每个 Agent 临时变聪明，而是修掉让所有 Agent 反复踩坑的共同原因。对体验设计的启发是：验收界面不该只显示「完成」，而应展示「怎么做的、验证了什么、哪里绕了路、还有什么没确认」。

设计趋势洞察

Design Signals
趋势 01

可信交付：Agent 体验从「能完成」走向「能证明」

a16z 与 OpenAI Computer Use 产品负责人 Ari Weinstein、James Sun 的对谈里，最值得产品团队细看的不是宏大叙事，而是那点「难以察觉」的增量。两人判断，自 Astra 出现之后，Computer Use Agent 已能完成一个人用电脑能做的任何事情，速度上超过普通人，正逼近「超人类」水平；但真正决定体验的，是 99% 与 97% 可靠性之间那微小却关键的差别，是它在抵抗 prompt injection 上的对齐提升，是 dots 会主动发现你漏掉的外部会议邀请、登录 Sentry 提取日志再给出分析。企业端的落地反而朴素：ERP、采购、财务对账、市场调研，全是没人愿意亲手做的苦差事。

Addy Osmani 那篇《Your Coding agents made you a manager》把这种转变讲得更具体。他把「自验证」放在首位：每项任务都应提供可执行的检查，例如测试、构建、类型检查，界面改动还可以用截图验证；Agent 应先执行、检查、修正失败，再提交结果与证据，而不是说一句「完成了」，把所有验证留给人。必要时，让没有参与原对话的新 Agent 独立审查，减少沿着同一思路自我认可。任务说明也不必重复代码已有的内容，更重要的是：为什么做、业务约束是什么、哪些事情不要做、怎样才算成功。

Ben Holmes 的过程复盘补上了第三块拼图：结果正确不等于过程健康。千问蒋冠军所说的「下限比上限更重要」，则从产品侧给出同一个结论。四件事放在一起，指向一个清晰的设计命题：Agent 产品需要一层「证据界面」——把结果、验证方式、失败与绕行、待确认项组织成可抽查的证据链，而不是只给一个完成状态。默认折叠、异常展开，让人保留最终判断权，同时不必逐条审查。

设计启示：信任不是靠一句「已为你完成」建立的，而是靠可验证的证据逐步校准。过度信任会放大错误，一次失败就弃用则是另一种校准失败。评估 Agent 体验时，除了任务成功率，还应测量用户检查证据的成本、发现错误的路径，以及错误发生后的恢复体验。

趋势 02

自然语言不是万能接口：从「说出需求」到「共同理解」

poteto 的 AI 音乐项目给出了一个很贴近真实用户的场景。她没有音乐制作经验，起初只能这样描述：想要 Game Boy 风格，同一主旋律的不同变奏能无缝衔接，类似玩《原神》时的体验。她直接告诉 Grok Bot：「我缺少描述自己想法的词汇。」随后用 /sharpen 深化需求，再用 /in-your-own-words 让 Agent 复述目标，检查双方理解是否一致。这两个 skills 不是作曲工具，而是在补齐创作前的沟通。制作解释视频时，她也先确认分镜和动态分镜草稿，再制作完整版本。

更有价值的是，需求最终如何落地。声音通过浏览器的 AudioWorklet 实时合成，包含 Game Boy 风格声部、低音、铺底和鼓，并加入延迟与混响；曲目统一为 128 BPM，不同区域和首个 Boss 的配乐围绕同一主题变化，随游戏强度逐层加入声部。所谓「无缝衔接」，最终变成具体规则：两个播放通道，按小节和乐句安排切换，旋律与伴奏分别处理；同主题变奏可以叠加，其他组合则采用保留旧旋律、先换新伴奏的方式。一个模糊的审美要求，只有在变成节奏、声部和切换规则之后，才能被稳定执行。

这和 Addy Osmani 所说的「仓库里看不到的信息」、千问所说的「用户自己知道却没明确表达的偏好」，其实是同一个问题：用户能说出的往往只是方向，不是规格。自然语言降低了表达门槛，却没有消除理解偏差。界面需要为「对齐」留出专门环节：复述确认、给词汇脚手架、用例子和对照帮助用户指认想要的东西，再把模糊偏好翻译成可执行约束。

研究启示：访谈里要区分「用户说的」「用户做的」和「用户真正在意的」。当用户说「我想要那种感觉」时，研究员的活儿不是追问一个更专业的词，而是帮他找到可指认的参照、可比较的选项，并复述回去确认。AI 产品的需求澄清流程，本质上就是把这段研究对话产品化。

产品体验点评

Product Experience
案例 01

纯纯写作 iOS：把「永不丢失」落到光标和双引号上

用户场景

Android 平台知名写作应用纯纯写作一周前正式在国区 App Store 上架 iOS 版。它长期主打「永不丢失」的写作体验，此前已在 Android 持续更新数年，并扩展桌面版改善编辑体验，这次 iOS 版补足了主流平台支持。对高频写作者来说，换平台最大的顾虑不是功能多少，而是文档会不会丢、会员要不要重买、编辑手感能不能延续。

设计动作

iOS 版完全拥抱了液态玻璃设计，主界面常见功能按钮都以液态玻璃呈现，平台适配度高；支持 iCloud 同步，后续还计划让 Android 也用上；会员可直接登录同步状态，无需二次付费。功能上率先支持双栏模式，可以左右对照编辑，对 iPad 或 iPhone Duo 用户是利好，但在常规 iPhone 上略显局促。最见功力的是快捷输入栏自定义：支持自定义光标位置，输入完成后按回车把光标直接移到符号末尾，输入双引号不必分两次或再挪光标。时光机与 AI 功能暂未提供。

体验启示

「永不丢失」不是一句口号，而是一组连续性的设计：跨端同步、会员权益延续、编辑习惯可迁移。液态玻璃让 iOS 用户获得熟悉的原生感，而不是把 Android 界面照搬过来——平台一致性和平台原生并不矛盾，关键是让用户不用重新学习。双栏模式也提醒我们，自适应布局要按场景判断：同一个功能在 iPad 上成立，在小屏手机上可能只是把局促放大。最后，明确标注「时光机与 AI 暂未提供」，比假装功能完整更能积累信任。

来源：少数派
案例 02

iPhone Duo 换回 Air：当设备开始抢走内容的注意力

体验观察

歸藏记录了一次很真实的换机复盘：用了一周 iPhone Duo 后卖掉，换回 iPhone Air，「感觉终于回到了用手机的感觉」。他承认 Duo 质感非常好，在一些适配好的应用里体验也挺好；问题在于，折叠屏会让他太在意手机本身。日常用手机时，注意力本应在内容上，而 Duo 又重、国产主流 App 适配又差，导致心思全花在设备上，注意力被手机分散，落不到内容里。换回 Air 后机身很轻，几乎感知不到它的存在，屏幕素质甚至更好；单扬声器、单摄像头因为有备用机影响不大，电池则靠随身充电宝兜底。

设计洞察

这是一条很典型的「注意力税」：设备越重、适配越差，用户越需要持续为它分心。好的硬件和界面应该趋于「消失」，让用户直接抵达内容；当用户开始频繁注意设备本身——重量、折痕、应用有没有铺满屏幕——体验就已经在漏损。另一边，极客公园的日报提到「超 10 万款应用已适配 iPhone Duo」，创业邦也报道苹果、三星计划在 2028 年前推出采用蚀刻超薄玻璃的可折叠显示屏。生态数字在增长，但它衡量的是「能不能打开」，不是「用起来是否不打断」。

体验启示

评估新形态设备时，除了功能可用性，应该加一条「设备是否抢走了内容注意力」。可以观察用户是否频繁调整握姿、是否因为布局局促而放弃某个任务、是否在适配不良的应用里反复缩放。生态适配也别只看数量，任务完成率、切换成本、单手握持下的可达性、注意力自评，才是更接近真实体验的指标。对做自适应布局的团队来说，双栏在 iPad 上是效率，在常规 iPhone 上可能就是负担——形态适配要跟着使用情境走，而不是跟着屏幕数量走。

研究方法论

Research Methods
方法 01

用量—价值落差分析：从「用得多」里找商品化，从「用得少」里找机会

Anthropic 的科研报告提供了一套可直接迁移的分析框架：先给每段会话打上任务标签，统计各类工作的 AI 使用占比；再通过问卷让用户分配重要性分数；最后把「使用占比」「时间占比」「重要性评分」三者放在一起看。结果显示，分析数据和写作被 AI 明显放大，而收集数据、提出想法这两件科学家最看重的事，使用率反而低于时间占比。这种落差比单看使用量更有解释力：使用率高的环节往往已经商品化，落差大的环节则可能卡在信任、输入成本或产品缺位上。

怎么做：在团队里建一张任务分类表，覆盖用户完成目标的关键环节；用埋点或日志估算各环节的实际使用，用短问卷收集「哪一步最影响结果」的重要性排序；画出落差矩阵。对「重要性高、使用低」的格子做访谈，问清楚是不知道、不敢用、不好用，还是不需要。注意原研究的样本来自个人订阅用户，标签由模型生成，且不保留研究内容，结论要结合访谈与日记法三角验证。
来源：宝玉 (@dotey)
方法 02

让 Agent 复盘过程，而不是只验收结果

Ben Holmes 的实践可以原样搬到研究运营：先由人定义评分标准，例如是否重复测试、工具调用是否高效、表达是否冗长；再让一个评审 Agent 检查完整任务记录，并解释每一处扣分的原因；随后让另一个 Agent 汇总多次记录，寻找反复出现的问题，把修复建议变成技能或配置的修改 PR。Skill Doctor 用于一次性检查本地历史，Warp Factories 则展示持续评分、定期提出修复建议的工作流。关键设计是把「生产者」和「评审者」分开，避免同一个上下文自我认可。

迁移到研究：给访谈记录和洞察报告定一份质量 rubric，比如证据是否可追溯、结论是否过度外推、是否区分了用户原话与研究员的解释、是否遗漏反例。让 Agent 先按 rubric 审计，再由人裁决是否采纳。反复出现的问题不要每次手工修，而应回写到访谈提纲、编码手册或综合模板里。注意 rubric 会被「应试」优化，保留人工抽检和定期校准，别把评分当成洞察本身。
来源：meng shao (@shao__meng)
方法 03

在隔离环境里做 Agent 可用性测试

两组新工具让「让 Agent 替你走一遍界面」变得可行。terminal-mac 在终端里跑一台虚拟 macOS，有自己的应用、文件和登录账号，Agent 可以先截图查看当前界面，再点击、输入或按快捷键，完成后再截一张图检查变化；因为跑在独立系统里，不会和用户争鼠标、键盘或剪贴板，刚开源就有 2000 多人 Star，适合把待测应用装进去让 Agent 自己测试。Pinky 则把 Claude Code、Codex、Cursor 这类 Agent 接到真实 iPhone 和 Android 手机上，读屏、点按、打字都走 MCP；付款前会停下来等用户点头，发消息、删除可以设成先问，随时能接管，每一步都有录屏。

怎么做：用测试账号和隔离设备搭一个沙箱，写清任务脚本、成功标准与停止条件；让 Agent 跑关键流程并保留逐步截图、点击坐标和失败重试记录；把反复卡住的位置当作可用性缺陷线索，再回到真人测试确认。这类方法擅长发现断裂、回归和无障碍问题，但不能替代真人——Agent 不会像用户那样犹豫、误解或放弃。涉及真实设备时，必须处理知情同意、数据脱敏和权限边界。
