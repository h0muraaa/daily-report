今日技术热榜

01 Claude Code 开放 Mod：用几行 TypeScript 魔改你的 Coding Agent

Anthropic 给 Claude Code 上线了 Mods：一个 Mod 就是一小段 JS/TS 文件，在当前会话内运行，可以监听 agent 生命周期事件、改写行为、甚至自己绘制 UI，保存代码即热重载，通过 /plugin 安装分享。官方把自带的 /diff 和 AGENTS.md 支持都改成了 Mod 实现，意味着"精简内核 + 按需插件"正在成为默认形态。

官方三个示例很能说明能力边界：Token Weather 在输入框上方实时画出上下文占用（18%→67%→81%，超过阈值变"暴风雨"）；Blast Radius 拦截 rm -rf、git reset --hard、强制推送等高危命令并列出受影响文件等你确认；Replay Theater 逐项回放本轮多文件编辑的 diff。它还支持改名、换主题、加按钮等界面级定制，全部可以让 Claude 自己写出来。

值得一提的是 DeepSeek Harness 负责人 Tianyi Cui 的回应：他认为两边是"思路的汇合"，但深度不同——Claude Code 把部分内建功能开放为 Mod，而 DeepSeek Harness 从架构层面把模型、工具、会话、沙箱、Agent 循环和界面都做成了插件。对开发者而言，agent harness 的可扩展性正成为新的竞争维度。

📎 来源: 宝玉 (@dotey) · 小互 (@imxiaohu) · Addy Osmani · AINLP

02 Pi 1.0 发布：延迟工具加载、虚拟模型编排与缓存预热

Earendil 团队的极简 harness Pi 1.0 正式发布，同时推出实验性姊妹项目 Pi Durable。团队的核心主张是"harness 的长期竞争力来自可靠性和可扩展性，而非功能清单的长度"，设计上向 Unix 与 SQLite 那种"小而硬"的传统靠拢。Codemode 原生支持了 MCP，还支持非 LLM 模型（Jev、图像模型），可让 agent 总结一周的 git 提交历史。

技术上最值得抄作业的有四点：延迟工具加载——工具定义不再在会话开始时全量注入上下文，而是按需加载，直接缓解长会话中工具定义挤爆上下文窗口的痛点；虚拟模型——把多个模型组合成一个可编程对象，例如 Claude Opus 负责规划、GPT 负责实现、由 Jev 决定切换时机；Anthropic 模型缓存预热——配合 /session 命令汇报每个模型的成本与缓存使用情况，认真对待成本工程；以及会话中系统消息——支持在对话进行中修改提示词和工具集，且感知已有转录内容。

Pi Durable 把 Pi 移植到 TypeScript 并外置所有有状态逻辑，支持多地点长跑、多会话并发、每步 checkpoint（崩溃可续）、多人 steer，可跑在 Bun 或 Cloudflare Durable Object 上。这套设计对想自建长时任务平台的团队有直接参考价值。

📎 来源: Viking (@vikingmute) · meng shao · Latent.Space

03 GitHub Copilot 的 Project HydraFusion：让 CLI 自己决定用哪个模型

GitHub 在 Copilot CLI 中上线实验性的 Project HydraFusion，定位是"多模型编排"。它会理解你的意图，然后自动在三种执行模式中选择：single（单模型直出）、cascade（级联，一个模型的结果喂给下一个）、critique（批判，让模型互查）。这解决了"到底该用哪个模型写这段代码"的持续困惑，也不同于此前的 Auto Model Select 单点选择。

开启方式：在 Copilot CLI、Copilot App 或 VS Code 中输入 /experimental 打开实验模式即可试用。对团队来说，这意味着模型路由逻辑正在从"人工配置"下沉到工具内部。

📎 来源: GitHub Checkout (YouTube) · GitHub (@github)

04 Cloudflare 把日志、链路、指标合成一个可观测性平台

Cloudflare 一次发布 8 项可观测性更新：跨产品的统一日志探索、从边缘到源站的端到端 tracing、一个统一的 SQL API 查询 Cloudflare 数据、统一计费模型、自定义告警、30 天数据保留的分析、自定义 dashboard，以及 Logpush 导出向自助套餐开放。以前排查一个问题要在多个产品间跳转，现在收敛到一处。

同批还发布了 Cloudflare Traces（open beta）：把自动 tracing 从 Workers 扩展到整条请求路径，一条 trace 里能看到安全规则、转换、缓存决策、路由、Worker 执行和源站处理，并基于 OpenTelemetry 继续向下游传递 trace context。可设置基线采样率，再用 Trace Rules 对特定流量覆盖。

📎 来源: The Cloudflare Blog · The Cloudflare Blog

05 Cloudflare Web Search API：别再让 agent 靠猜 URL 抓网页

Cloudflare 指出了一个普遍的工程问题：agent 需要实时网页时，往往是"猜一个 URL 然后 curl"，猜错就返回 404，既低效又不可靠。新发布的 Web Search API（通过 AI Gateway 提供）让 agent 像人一样先做搜索查询，再基于实时结果 grounding 回答，而不是随机猜地址。对构建 RAG 或浏览型 agent 的团队来说，这补上了"检索入口"这一环。

📎 来源: The Cloudflare Blog

06 Perplexity 开源决策模型 pplx-decider-27b 并推出 Decisions API

Perplexity 开源了多模态决策模型 pplx-decider-27b：它不输出文本，而是对固定答案集合输出概率分布，适合做 harness 内部的"小决策"——路由、审批、评判。新的 Decisions API 定价为 $0.04 / 百万输入 token、输出 token 免费，官方称基准平均得分 85.71%，并计划继续降价。

LangChain 的 Harrison Chase 点评了它的典型用法：用便宜的强类型输出来处理 harness 里的小调用（routing、approvals、judging），把大模型留给其余部分。这种"决策模型 + 通用模型"的分工，是当前 agent 成本工程里一个很务实的方向。

📎 来源: Aravind Srinivas (@AravSrinivas) · Harrison Chase (@hwchase17)

深度技术解读

🔬 同一份权重，换一个 harness 从 62% 掉到 33%——多 harness 强化学习怎么做

问题场景：Hugging Face 团队指出一个扎心的事实——同一模型、同一权重，在一个 agent harness 里能拿 62%，换到另一个 harness 只有 33%。也就是说你辛苦调出来的能力，可能被 harness 的实现细节吃掉一半。而针对某个 harness 去做微调，又容易过拟合到那一个客户端。

方案与实现：他们的做法很巧妙——不动 harness，而是把 harness 指向一个 proxy 而不是真正的模型。这个 proxy 同时支持编程 agent 使用的主流四种 API 格式（OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini），记录下 vLLM 采样出的精确 token ids 和 logprobs，再用这些数据训练。整个过程不需要改动 Claude Code、Codex 或 OpenCode 的一行代码，因此可以同时在 4 个 harness 上训练。

结果与实践建议：LFM2.5-2.6B（Liquid AI）从 42% 提升到 54%，工具调用次数减少 31%（对"用更少步骤解决问题"给了小幅奖励）。如果你在做 coding agent 的 RL 或评测，这篇指南的启示是：评测报告必须写明 harness 版本，否则数字不可复现；而能力提升的一个高杠杆点是让模型学会在多种 harness 下都稳定发挥，而不是绑定单一客户端。

📎 来源: Hugging Face (@huggingface)

🔬 "MCP 不烂，烂的是你的 Agent"：上下文膨胀的真正来源

问题场景：过去一段时间"MCP 已死"的声音不小，主要抱怨是上下文膨胀和 token 消耗。Apify 创始人 Jan Čurn 在 AI Engineer 的分享里给出反直觉的结论：问题出在天真的客户端实现，而不是协议本身。很多 harness 在会话开始就把所有 MCP 工具定义全量塞进上下文——这其实是 harness 的 bug。

三个已被验证的修法：①sub-agents，把工具调用隔离到子 agent 的独立上下文；②progressive tool discovery（渐进式工具发现），按需加载工具定义（与 Pi 1.0 的延迟工具加载是同一思路）；③Code Mode，让模型写代码来调用工具而不是逐个 JSON schema 调用。他也解释了为什么 CLI 对 agent 来说"手感更好"，并主张远程访问用 MCP、本地访问用 CLI。

实践建议：如果你自建 agent，先审计"会话初始化时注入了多少工具定义"，能延迟加载的绝不全量注入。他还演示了 Apify 开源的通用 MCP CLI 客户端 mcpc，并给出对比 raw MCP、纯 CLI、mcpc 三者的 Connector Evals 早期结果，可作为选型参考。

📎 来源: AI Engineer (YouTube)

实践指南

⚙️ Uber Eats 搜索端到端延迟砍半：可复用的 6 个手段

Uber 重建了 Uber Eats 搜索流水线的大部分组件，报告端到端延迟下降 50%。可以借鉴的具体做法：

  1. Above-the-Fold 度量——只优化用户首屏可见内容的加载时间，而不是整页，指标更贴近真实体验。
  2. 减少检索工作量——压缩每次查询实际触发的候选检索规模。
  3. 并行 hydration——把原本串行的结果补全步骤并行化。
  4. 广告数据重构——重排广告数据的取用路径，减少对主链路的拖累。
  5. 基础设施优化——底层资源与拓扑层面的调优。
  6. agentic coding 工作流——把 agent 编码纳入日常研发流程。

此外他们还在探索 microbatching、基于商品的检索（product-based retrieval）和 HTTP multipart streaming。如果你在做搜索/推荐链路，这份清单可以直接对照排查。

⚙️ Notion 用 Postgres 扩展查询协议流水线，读查询快约 50%

Notion 工程师实现了 Postgres extended query protocol 的流水线（pipelining），让查询速度提升约 50%。背景是 Notion 在事务里跑很多查询，因此可以搭配 pgbouncer 的事务级连接池 + SET LOCAL，典型的读事务形如 BEGIN; SET LOCAL search_path=...; SELECT ...; COMMIT;。

问题在于这些语句原本各自占一个网络往返。流水线把多个语句打包成一次往返：读操作从 N 次往返降到 1 次，写操作降到 2 次（即把 BEGIN / SET LOCAL / SELECT / COMMIT 合入一个 ExtendedQueryPipeline）。这是一个低改动、高收益的网络层优化，对高并发事务型服务很有参考价值。

📎 来源: Akshay Kothari / Jake (@akothari)

⚙️ 用 Spanner queues 解决 agentic 工作流的"双系统一致性问题"

AI agent 会自主发起退款、管理库存、执行多步交接、编排子 agent。这类流程常需要在运营数据库里维护状态，同时通过独立的消息/事件队列派发异步动作——而两套系统提交点不一致，会直接破坏事务一致性。

Google 宣布 Spanner queues 正式 GA：把原生事务消息直接内嵌进 Spanner，创建一条消息就只是事务里的又一次操作，从而让"改状态"和"发消息"落在同一个提交点。如果你在构建需要可靠异步执行的 agent 后端，这是把一致性从应用层下沉到数据库层的一种思路。

📎 来源: Google Cloud Blog
