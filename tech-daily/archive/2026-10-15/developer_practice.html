让代码库对 Agent “好读”：代码智能层正在变成 AI 编码的基础设施

今天有三条新闻其实指向同一个趋势：当写代码的主体从人变成 Agent，代码库的“可被机器理解程度”本身成了一种性能指标。

案例一：Netflix × JetBrains（把语义智能喂给 Agent）。Netflix 把 JetBrains 的无头代码智能引擎（IntelliJ IDEA 背后那套）接进 Claude Code 和 Codex，并做了基准测试。为什么有效？因为 AI 编码 Agent 的传统工作方式是“猜 + grep”：靠文本搜索找符号，靠上下文拼出跨文件引用，一旦项目大了，token 花在“找”上的比例迅速上升，还容易改错。给它一个真正的语义层——符号解析、类型信息、跨文件引用——等于把“猜测”换成“查询”。这是一个可以直接抄的架构模式。

案例二：Instagram 的 Jetpack Compose 迁移（让代码本身对 Agent 好读）。InfoQ 报道 Instagram Direct 把 Android UI 从 Android View 迁到 Jetpack Compose，明确目标就是建立对 AI Agent 更友好的代码库。结果：UI 代码量 -50%，Token 成本峰值 -33%。为什么量减少了 Token 就减少？因为 Agent 要读的“代码表面积”直接变小了；声明式 UI 把散落在多个文件和生命周期回调里的状态逻辑收敛到可预测的结构里，模型不需要跨文件脑补状态流。

案例三：IntelliJ 的 JVM 智能走向任何编辑器（代码智能服务化）。JetBrains 把 Java/Kotlin 的 LSP 扩展做到 1.0，让 VS Code 和 Cursor 也能拿到 IDEA 级智能，并明说这是“把 JVM 智能搬到用户所在的地方，不论他用什么编辑器或 Agent”。这三件事合起来说明：代码智能正在从“某个 IDE 的独占功能”变成一个“可被任意客户端（包括 Agent）调用的服务”。

# 可复用的三个动作
1. 给 Agent 语义工具：暴露 LSP / 编译器的符号、类型、引用查询
   —— 别只给 ripgrep 式文本搜索，Agent 会用它猜
2. 压缩 代码表面积：迁移到声明式、结构规整的写法
   —— 少一半代码 ≈ 少三分之一的 Token 与出错面
3. 按 Token 成本评估重构收益：把「可读性」量化成「推理成本」
   —— 团队通用指标：UI 代码量、平均文件体积、跨文件依赖数

实践建议：(a) 先量出你的 Agent 在一次任务里“搜索/定位”和“实际修改”花的 token 比例，如果前者偏高，优先补代码智能层而非换更强的模型；(b) 把“减少代码量/收敛副作用”这类重构在 Agent 时代重新定价——它不只是可维护性，而是直接省钱；(c) 若你在自建 Agent 平台，把 LSP/编译器信息做成 MCP 工具或结构化 tool call 暴露出去。

// deep dive 02

Agent 沙箱的两条正道：可复现评测（Docker/Harbor）与加密身份（Perplexity SPACE）

今天两条新闻从不同角度回答同一个问题：当 Agent 能执行代码、调工具、跑很久，你怎么既放开它的手脚，又守住边界？

问题定义（Docker）。Docker 把风险说得很准：让 Agent 有用的“自由行动”恰恰是风险来源。它不只是回答问题，还浏览网页、执行代码、调用工具，所以一条被污染或错误的指令会变成“真实损害”，而不只是一个错误答案。因此隔离不是可选项，是前提。

解法 A：可复现的评测（Docker Sandboxes + Harbor）。Harbor 现在能把每个评测任务跑在 Docker Sandboxes 里；Sandboxes 是基于 MicroVM 的环境，安全运行 Claude Code、Codex、Cursor 等 Agent。两个关键点：① 你可以为沙箱定义自定义网络策略——限制 Agent 能访问什么，从而得到“公平、可复现”的评测（否则一次联网差异就会让结果不可比）；② 评测可本地也可上云。做 Agent 红队/基准的人，这套“MicroVM 隔离 + 网络策略 + 可复现”基本是标准答案。

解法 B：加密身份绑定（Perplexity 开源 SPACE）。Perplexity 开源了其沙箱平台 SPACE（Agentic Runtime Platform 的第一个组件），并公布了安全测试：Escaping SPACE: Part I 中，9 种拥有 VM 内 root 权限的模型配置发起了 108 次逃逸尝试，无一触达宿主机。它的机制是“请求 ↔ 执行身份”的绑定：每个请求携带短时、签名的凭证，声明“哪个执行可以处理它、允许什么访问”。难点在于沙箱会暂停、恢复、迁移——终端与文件监听可能活得比发起它的请求更久；一旦接收方安装了新的执行身份，SPACE 会立即停掉旧数据流，只允许符合条件的操作凭身份重连一次。这与 Perplexity 此前披露的“日均数百万次执行、错误率低于 0.0002%”是同一套体系。

# Agent 沙箱的两个正交维度
隔离强度 : MicroVM(Docker Sandboxes) —— 硬边界,防逃逸
权限收敛 : 自定义网络策略 —— 能访问什么,可审计
身份绑定 : 短时签名凭证(SPACE) —— 请求只能落到"该执行"上
状态迁移 : 暂停/恢复/迁移时主动吊销旧身份与数据流
可复现  : 固定隔离 + 固定网络 → 评测结果可比

实践建议：(a) 任何“Agent 能执行代码或调外部工具”的场景，默认跑在 MicroVM 级隔离里，不要用同一进程/容器混跑；(b) 为沙箱定义显式网络白名单——既降风险，也让评测可复现；(c) 若你的平台允许长连接会话，务必实现“执行身份迁移时必须吊销旧流”的逻辑，这是最容易出安全洞的角落。
