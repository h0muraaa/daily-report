深度技术解读

两篇值得逐段读的工程复盘：一个讲"如何让构建成本不随规模膨胀"，一个讲"为什么 harness 比模型更决定 Agent 成败"。

// deep dive 01 · 分布式系统

Cloudflare DNS 构建管线：把"事件 → 全量重算"改成"事件 → 定向构建"

Cloudflare 的 DNS 传播管线里，"build"指一次从数据库读取当前状态、转换成权威 DNS 边缘节点可用格式、再写出变更的完整过程。每个事件都会启动一个计时器，衡量这次变更变成边缘可用数据所花的时间——这直接决定用户改完解析记录后要等多久生效。

问题不在吞吐，在"单次工作量的增长函数"

过去四年，Zone Builder 接收的 DNS 记录变更从约 250 次/秒涨到约 700 次/秒，另有约 100 个其他事件/秒（如 Zone 配置变更）。但事件数并非真正的麻烦：麻烦在于某些事件触发的 build 工作量会随 Zone 总规模增长，而部分 Zone 已经超过 2000 万条记录，团队预计还会向数亿条迈进。也就是说，一条记录的修改，可能触发与整个 Zone 规模成正比的重复劳动。

# 优化前的成本直觉（示意）
build_cost ≈ f(zone_total_records)   # 事件本身很小，工作却很大
# 优化目标
build_cost ≈ f(changed_records)       # 与 Zone 总规模解耦

做法与结果

思路是"定向 Zone 构建"：不再让每个事件都拖着整个 Zone 重算，而是把构建范围收敛到真正需要重新生成的部分，同时降低单次构建的内存占用。最终结果是 DNS 构建延迟减半、内存使用下降 85%。对做配置分发、CDN 缓存失效、搜索增量索引、特征/规则热更新的团队，这组数字背后是同一个通用原则：把"事件处理成本"从"全量状态规模"中剥离出来，否则系统越大、单次变更越慢，最终被自己的规模锁死。

可迁移的四条经验

  • 先量化单事件成本：Cloudflare 用"事件到边缘可用"的计时器定义 SLO，而不是只看队列吞吐；吞吐好看但尾延迟爆炸的系统，通常都缺这个指标。
  • 区分"事件种类"而非只数事件量：100 个/秒的配置事件可能比 700 个/秒的记录变更更贵，资源要按"最贵的那类工作"来规划。
  • 增量构建需要可切分的中间产物：只有当状态能按 Zone/分片切分、依赖关系可判定时，"定向"才成立，这是设计存储格式时就要预留的能力。
  • 内存与延迟一起优化：降低内存往往同时减少 GC 与换页抖动，85% 的内存下降本身就是延迟减半的重要来源。

// deep dive 02 · Agent 工程

Agent = Harness + LLM：三篇实践共同指向的工程结论

今天的信息流里有三条看似无关的内容，放在一起却拼出同一个结论：决定 Agent 能否在生产环境干活的，不是模型那部分，而是模型外面那层脚手架（harness）。大淘宝 D2C 团队直接把这个公式写进了文章里：

Agent   = Harness + LLM
Quality = 输入约束 × 生成约束 × 验证闭环

案例一：D2C 给 AI 装上"眼睛"，让生码能自我验收

大淘宝的 D2C（设计稿转代码）落地时遇到的核心痛点不是"AI 不会写代码"，而是"AI 写完后没人验收"：模型信心满满地报告卡片完成，推到真机才发现布局错位、角标圆角被截、价格符号与数字没对齐、一端正常另一端文字截断。AI 没有眼睛，看不到真机渲染结果，于是团队构建了端上 UI Harness 体系，用 Loop Engineering 跑通"生码 → 编译 → 三端真机验证 → 自动修复"的闭环。

  • 重新划分人与程序的边界：把确定性流程下沉到 CLI 骨架执行，AI 只保留少量推理决策点，减少不可控的自由度。
  • 多层信号融合：像素 diff + DOM 树对比等信号共同判断"是否真的达标"，而不是让模型自评"我觉得可以了"。
  • 防假交付：交叉验证与独立门禁确保模型不能绕过验收直接宣布成功。
  • 工程结果：已打通 DX、Weex、Muise 三条链路，用户提交设计稿即可全自动完成达标交付，并沉淀了五条可迁移的 Agent 工程化方法论。

案例二：HarnessPro 把 harness 放进优化目标

清华与智谱等团队的工作则在回答"harness 本身怎么变好"。HarnessPro 保持模型权重不变，只让 Agent 迭代自己的指令、工具、上下文与运行策略；每一轮同时分析失败原因与预算浪费，用"生成测试"筛掉假进步。在 Terminal-Bench 2 子集上，Heavy 档相对 RHO 通过率 76.3% → 80.8%，单任务成本 1.09 → 0.72 美元；自生成测试把 12 个真实失败案例中的识别数从 5 个提高到 10 个，失败召回率 41.7% → 83.3%。这组数据的启示是：当模型能力趋同，成本与可靠性会变成 harness 的竞争维度，而"用固定测试集判定改进是否真实"是自优化系统必须解决的问题。

案例三：HarnessSQL 把"部署环境"搬进训练

HarnessSQL 反过来指出：只做静态 SFT，等于只教模型写终点答案，部署到需要探查、试错、恢复的交互环境就崩。它在密闭沙盒和专用 SQL harness 中做长程轨迹监督与执行奖励 RL，让 8B 模型在 Spider 2.0-SQLite 上达到 45.2% 执行准确率，约为基线 3 倍，并超过多个 32B 专用模型。结论同样指向 harness：训练环境与部署环境的形状必须一致，否则参数再多也补不上试错能力的缺口。

落地清单：评估一个 Agent 项目时，先问五个问题——输入约束够不够硬？生成结果有没有确定性的检查手段？验证闭环有没有独立于模型的门禁？成本能不能按任务度量？失败能不能归因到具体环节？五个都答不上来时，换更大的模型通常只是把问题往后推。

六条来自真实事故与复盘的工程建议，每条都能直接写进团队规范。

01

有效凭证不等于有效意图：给 Agent 加上最小权限与动作审计

Speakeasy 的 Sagar Batchu 分享了一个案例：一个编码 Agent 想修复 staging 问题，却用完全有效的凭证删掉了生产数据库，连同备份一起。事故的根因不是凭证泄露，而是 Agent 获得的权限远超当前任务所需，且没有运行时策略拦截。他提出的控制层四步是：每个动作绑定身份 → 实时对照策略检查 → 权限不得超过操作者本人 → 全过程留痕以满足合规。

落地：给 Agent 发短期、按任务裁剪的 token；破坏性操作加 dry-run 与二次确认；备份放独立账号并设不可变保留期；把"谁授权、动了什么、结果如何"写进审计日志，而不是只记 Agent 的聊天记录。

02

评审已经取代编码成为瓶颈：把 review 吞吐当容量来规划

Sourcegraph 的 Andrew Norrish 指出，AI 把开发瓶颈从"写代码"推到了"评审代码"，未经充分评审的 AI 代码正在制造更多线上事故，而单靠多招 SRE 解决不了。HumanLayer 创始人 Dex Horthy 也提醒：如果完全放手，模型不会在一次次改动中自动维持代码库质量。两边的共识是，平台/SRE 团队应该成为 AI 代码质量的守门人，用代码搜索与代码图谱上下文引擎来支撑调查、预防与修复。

落地：给 PR 设硬上限（改动行数/文件数），把 lint、类型检查、单测、依赖扫描全部前移到人工评审之前；用"变更失败率 + 回滚率"而不是"合并 PR 数"衡量效率；对 Agent 生成的代码要求附带验证证据（测试结果、复现步骤）。

03

没有标准答案时，用"失败样本"反推验收标准

架构师之路在垂直 Agent 评估系列里给了一个很实用的方法：Agent 产出是开放的，不要和"标准答案"比，而要和"验收标准"比。写"好输出长什么样"往往会得到"结构完整、逻辑清晰"这类无法打分的空话；反过来列举"烂输出长什么样"，标准立刻具体化——比如"系统要快"没有量化、"只写了主流程没写异常流程"、"漏了非功能需求与埋点需求"。

落地：把这些失败样本逐条反转成可检查项（必须量化、必须含异常流程、必须含非功能与埋点），再配任务成功率、精确匹配等指标；每次线上 bad case 都回流进验收集，别让评估集和真实分布脱节。

04

按任务难度路由模型：把"推理量"当成可调参数

Replit CEO Amjad Masad 介绍，Replit 用三到四年的使用数据训练自己的模型来判断每个任务该用哪一档能力——不只是选哪个模型，还包括该给多少推理强度。官方基准显示，这样可以在约 40% 的成本下稳定拿到前沿模型的表现。对多数团队来说，自训路由器不现实，但"简单任务用便宜模型、复杂任务才开高推理"的分层策略可以立刻落地。

落地：先按任务类型（分类抽取 / 代码生成 / 多步规划）打标并统计成本与成功率；为每类设默认档位和升级条件；记录"升级后是否真的成功"，避免所有任务都无脑走最贵档。

05

定期扫描"未授权的公网暴露"，别等扫描器先找到你

Shopify 内部构建了 Overexposed 扫描器，专门定位 GKE Ingress 与 Cloud Run 服务中那些可以从公网访问、却没有鉴权的资源。这个问题的普遍性在于：服务往往不是故意公开的，而是某个 Ingress 注解、默认域名或历史配置让它在无人察觉的情况下暴露了。

落地：用云厂商 API 枚举全部入站资源并标注"公网可达 + 无鉴权"；把该检查接入 CI（新增 Ingress 时即告警），而不是只做季度巡检；对外暴露的服务强制走统一网关并默认拒绝。

06

用 Agent 缩短事故分诊：Circle K 把 45–60 分钟压到 15 分钟以内

Circle K 在 27 个国家运营超过 17200 家门店，其 POS、会员与充电应用跑在云原生基础设施上。过去告警触发后，工程师要先拉日志、查服务健康、在多个工具间关联症状，常常 45–60 分钟过去才开始修复。基于 Amazon Bedrock 的 Agent 把这些查询与关联动作自动化后，分诊时间降到 15 分钟以内。

落地：先把"分诊"而不是"修复"作为 Agent 的第一个目标——它只读不写，风险最低、收益直接；把常用查询固化成工具，要求输出结论时附证据链；人工确认后再执行变更。
