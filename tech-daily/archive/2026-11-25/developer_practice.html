模型架构 · 深度解读

不堆参数，用「循环计算」换推理深度：拆解 GLM-5.4 的 Loop Transformer

问题：参数越来越多，边际收益却在下降

传统 Transformer 里，每一层权重在一条序列上前向只过一遍。想提升推理能力，业界最直接的做法是「加参数、加层数」，但成本随规模线性甚至超线性上涨。Loop Transformer 换了个思路：让同一组网络层循环执行多轮，在不增加参数的前提下增加「计算深度」——同一份权重被复用多次，等价于加厚了等效层数。这个想法谷歌 2018 年就提过，但当年从零训练时打不过传统 Transformer，长期只停留在论文里。

GLM-5.4 怎么做的

智谱没有从零重训，而是在约 750B 的已训基座上，挑出 28 层做两轮循环。循环带来的最大工程难题是训练稳定性：同一组层多跑几轮容易发散，智谱通过门控机制等设计保证多轮循环仍能稳定收敛。官方口径是这套 750B 基座在 Loop 加持后，达到了 2T–3T 级模型的效果——也就是用「计算」换「参数」。

配套的推理 Infra 优化才是落地关键

循环计算会抬高推理成本与显存占用，所以模型架构与推理 Infra 必须协同设计：GLM-5.4 通过 KV Cache 共享与稀疏注意力索引复用来控制额外开销。这部分对做模型部署的工程师尤其有普适借鉴意义——当模型侧引入「重复计算」时，Infra 侧要靠缓存与索引复用来把成本压回去。

为什么值得关注

它是目前第一个公开技术细节的大尺寸 Loop 模型，把「参数效率 vs 计算效率」的权衡摆上了台面；同时补齐 24 层 ViT 原生视觉后，「泛 Coding」（3D 建模、Code to Video、操作专业软件）才真正跑通。如果后续 Loop 路线在大尺寸上被验证，模型训练与推理的成本模型都会被重新定义。

📎 来源: Datawhale · AI产品阿颖 · Latent.Space
性能优化 · 深度解读

一次「少拷贝却更慢」的性能复盘：小红书 RedKV Proxy 优化实战

背景与链路

RedKV Proxy 为客户端提供 Redis 协议入口，V3 路径经 InternalSDK 访问 KVServer；InternalSDK 的数据收发复用 Proxy 工作线程的事件循环，统一管理连接、请求队列与完成回调。优化的是这条「代理 + InternalSDK」链路，后端执行成本单独评估。

关键洞察：不同负载的瓶颈完全不同

团队发现不能一刀切地优化：小 GET 更容易受对象构造、解析和状态登记影响；大 GET/SET 更容易受内存搬运与收发批量影响；而大 MGET 可能长时间占用事件循环，让其他请求一起排队等待。对应的手段是请求复用与有界批处理——但批处理必须「有界」，否则大请求会饿死小请求。

踩坑点：「少拷贝」不等于「更快」

文中复盘了一次「少拷贝却更慢」的实验：减少一次数据拷贝，反而引入了额外的调度/批处理成本，整体更慢。结论是不能凭直觉去减少拷贝，必须结合采样、反汇编和 I/O 计数，定位「到底多做了什么」，而不是只看表面上的拷贝次数。

一套可复用的验证方法论

他们在验证收益时：关闭探针以隔离编译与测试负载；让优化前后版本交替运行；同时观察吞吐、每请求 CPU 时间、P99 与错误计数；结果波动时补预热、交换端口，并保留不利窗口；对照配置（例如 V2 的静态路由 vs V3）也逐项核实。这套方法论比单次跑分可靠得多，值得直接抄进自己的压测流程。

📎 来源: 小红书技术REDtech

//实践指南 可落地的最佳实践

把 Agent 评测当成一门「测试学科」，而不是跑分

评测本质上是测试：传统软件测试服务于「验证迭代后系统行为符合预期」，而 Agent 的不确定性更强——既来自模型输出的不可预期，也来自人类操控 Agent 时的随机性。因此必须建立 golden dataset、回归测试与发布门禁，而不是看一两个样例就下结论。

EMNLP 2026 Oral 的 RDQA 基准很能说明问题：它不给预置检索索引、也不把源文件预先交给模型，每题都要求 Agent 自己找到原始文件、调用解析工具、定位到某一页/格/秒再作答，并对「答案已出现在公开网页上」的题做改写。结果 12 个通用 Agent 经参数泄漏率调整后的准确率最高仅 24.0%——大量「答对」其实是背出来的、只是假装在搜索。设计评测时要专门防这种参数泄漏。

InfoQ 给出的生产蓝图也值得抄：知识图谱 + 双层 eval 评判 + CI/CD 发布门禁 + 对 golden dataset 做回归，把非确定性当工程问题治理；OpenAI 用 Codex 六周做出 $100M 产品时，靠的同样是分层测试、沙箱与批量 PR 评审，并把「code slop」和 Agent 不安全操作列为明确失败模式。

📎 来源: 硅星人Pro · 新智元 · InfoQ · InfoQ

把 Agent 系统当作分布式系统：幂等、重试与最终一致

当 Agent 开始并行、跨服务、跨多次重试地执行动作，「调用一次」的假设就不成立了。Stack Overflow 同日三篇短文正好从不同角度点题：《Idempotency when you don't control the other end》讲对端不可控时如何做到幂等、《A Reboot Is Still a Deployment》提醒重启本身就是一次部署、《Agent swarms need more than a message board》则指出 Agent 群组协调本质上是分布式系统问题，光有消息板远远不够。

一个具体的正面样板是 Cloudflare D1 的控制平面：重试 + 幂等保障 + 最终一致性 + 30 秒心跳与 Postgres 对账，专门修复创建/删除失败后留下的孤立状态。做多 Agent 编排时，先把「重复执行会怎样」「部分失败如何收敛」「谁是对账的事实来源」想清楚，再谈并行度。

给非确定性上「发布门禁」：Prompt Injection 也要回归测试

Prompt Injection 的修复往往是「打补丁」，今天堵住、明天换个措辞又复发——Stack Overflow 因此主张 Prompt Injection 的修复必须配回归测试，把每个已知攻击样本固化成用例，防止安全修复被后续改动悄悄破坏。这与 InfoQ 的「非确定性发布门禁」是同一套思路：把 prompt/agent 的改动纳入 CI，挂上 eval 与回归，让每次发布都过同一道质量闸，而不是靠人肉在聊天窗口里试。

团队级 AI 编程治理：网关收口、标配、门禁、知识库、协作

个人提效容易、团队提效难，根源是五个结构性问题：谁在调模型花了多少说不清、水平参差导致下限决定交付、产码太快 Review 追不上、同一个坑每人轮流踩、PR 满天飞分支天天撞车。对应的五件治理事：①网关收口（所有大模型调用走同一网关，做鉴权/限流/计费/路由，按任务难度把架构评审打高端模型、日常编码打 flash 版，省钱又高可用）；②团队标配（把验证过的好做法固化成标准，拉高下限）；③质量门禁（质量检查挂进 CI/CD，AI 写的代码更要过）；④项目知识库（决策、业务、坑记下来给下一轮当上下文）；⑤团队协作（AI 时代的新瓶颈是沟通带宽与并行度）。

核心判断是：研发重心正从「代码资产」转向「AI 调用治理 + 能力沉淀」，代码反而成了中间产物。

📎 来源: 架构师之路

少造 Agent、多沉淀 Skills；Harness 保持 model-neutral

Anthropic 工程师的做法值得借鉴：不再为每个任务单独搭一个 Agent，而是用一个能力较通用的助手 + 可复用的 Skills（通常是一个含 SKILL.md 的文件夹）来积累「工作经验」。要点是「先把工作做一遍，再把它变成技能」，并注意技能不是写得越多、规定得越细就越好——要能测试「不使用技能」时的效果作为对照。

另一条是别把 Agent Harness 锁死在单一模型供应商：LangChain 强调 harness 应保持 model-neutral（LangGraph、Deep Agents 均开源），这样新模型一出来就能切过去，也不会被单一供应商涨价卡脖子。在路由这类高频判断上，可把额外的 LLM 调用换成更轻的「决策模型」（如 Jev）——先用便宜模型兜底，低置信度时再升级到前沿模型，Browserbase 迁移后网页导航快了 4 倍。
