02深度技术解读

深度一 · Context 即代码：瓶颈已从"写代码"转移到"管理上下文与验证结果"

今天几条互不相干的数据，拼出了同一张图景：AI 编码的瓶颈不在生成，而在定义意图、拆分任务、管理上下文、验证结果这四件"工程基本功"上。

  • 上下文越长，模型越差。Total TypeScript 作者 Matt Pocock 在 The Pragmatic Engineer 访谈中直言："你给 Agent 的上下文越多，它的表现反而越差。"同样一个改造任务，把需求文档、代码、日志、报错一次性塞进去，几回合后会话里全是过期信息，模型还在输出但改动已偏离原要求；正确做法是拆成独立工单，一次会话只处理一张，先定位、再补测试、再开干净会话改代码。（51CTO技术栈）
  • 把上下文当作代码来管。Patrick Debois 在 InfoQ 演讲《Context Is the New Code》中提出：用成熟的软件工程实践来管理、评估、分发和观测上下文——测试、CI/CD、包管理、安全扫描一应俱全。这样才能在规模化运行 AI 编码 Agent 时，对非确定性输出保持控制，并把经验沉淀为组织资产。（InfoQ）
  • 代码正在变得"只写且可丢弃"。Phillip Mortimer 在 QCon London 指出：AI 让所有代码趋向"只写且不可读"，测试成为行为定义与文档，重写往往比调试更划算；而人工无法规模化审查 AI 生成的代码，应转向自动化审查 + Agent 通过可观测性自我修复，并把"意图"与"实现"解耦。（InfoQ）
  • 审查才是真瓶颈。Laurie Voss（Arize AI，npm 联合创始人）给出的数据：用自主 Agent 的开发者写了 741% 更多的代码，却只多交付 30% 的软件；审查有效性在约 400 行之后急剧崩塌，而 Agent 已开始提交上万行的 PR。他引述 METR 的发现——约一半通过 SWE-bench 的 PR 实际不会被合并，以及 Cognition FrontierCode 在 SWE-bench Pro 上 88%、真实可合并率仅 29% 的落差。（AI Engineer）
  • 度量数据印证。DX 的 Justin Reock 基于约 20 万名工程师的数据：部署频率上升，但变更失败率波动更大；可维护性上升，变更信心反而下降；PR 从约 44 行涨到 72 行；初级工程师用 AI 最多，staff+ 用更少 token 达到同样的时间节省；PR 吞吐中位提升约 7.7%，顶尖选手也未到 2x——因为代码生成从来不是瓶颈。（AI Engineer）
实践含义：把投资从"更长的提示词"转向"更小的任务单元 + 更可控的上下文 + 更强的自动化验证"。Agent 把错误答案写成代码的速度和写对答案一样快——开发者判断错一次，它可能沿着错误方向改完整个仓库。

深度二 · 长程任务 Harness：让 Agent 跨昼夜可靠交付

当 Agent 任务从"一次会话"变成"跨小时、跨天、甚至跨真实流量验证"的项目，新的工程问题出现了：状态怎么延续、失败怎么恢复、代价怎么归属。

  • 小红书推荐系统的跨昼夜发布。其推荐核心服务一次发布横跨十几个部署组、数千个 Pod，平均持续 10 多个小时，还要等次日真实流量验证。团队把发布知识、操作步骤和异常处置沉淀为近 20 万字的 SKILL；但"知识完备 ≠ 执行可靠"，跨会话状态延续、故障恢复与动态变化仍需系统保障。于是他们构建长程任务 Harness：以任务保存状态、以模板固化约束、由引擎推进并核验结果。（小红书技术 REDtech）
  • Cloudflare Issues：把"串联步骤"自动化。Workers 内建错误监控（开放公测），可自动分组重复失败、把日志与 trace 上下文打包交给 Agent、并检查修复是否生效。此前这些环节全靠人肉衔接——识别同一 bug、收集上下文、发给 Agent、验证修复。（The Cloudflare Blog）
  • 一个忘关的开关，烧掉三倍预算。InfoQ 记录的真实案例：某企业上月上线的 AI 应用预估 token 费约 1 万元，结算却花了 3 万元，只因为一个开关忘了关，应用在后台默默烧钱。企业因此需要"身份可传递、状态可恢复、费用可归属、异常可发现"的全栈协同。IDC 预测到 2029 年全球部署的 AI 智能体将超过 10 亿个，约为 2025 年的 40 倍。（InfoQ）
  • Harness 的角色在变。Replit 的观点值得记下："模型越来越聪明，但 harness 不会消失，它的工作从替模型做决定，变成给模型提供选项。"主 Agent 决定何时更用力思考、何时移交子 Agent、子 Agent 花多少力气。这正是 Sutton "苦涩的教训"在 harness 设计上的体现——明天的模型不该继承昨天为它打的所有补丁。（Replit）
实践含义：把长程 Agent 当成分布式系统来设计——需要实时有序传输、持久化与再水化、运行时协调，而 MCP / A2A 这类"无状态调用、单向 client/server、无发现机制"的协议还远不够用（见 AI Engineer《Your Agents Are in Solitary Confinement》）。

04实践指南

  1. 别把整个需求塞给 Agent：拆工单，一次会话只做一件事 把规格拆成一张张独立工单：这一轮只定位问题，下一轮补测试，再开一个干净会话修改代码。每一步有明确范围，也知道怎样才算完成。判断上下文是否已经"污染"——当模型还在输出但改动开始偏离最初的约束时，就该重开会话而不是继续追加消息。（来源：51CTO技术栈）
  2. 把上下文版本化、可测试、可分发 把 prompts、skills、工具定义、环境说明当成代码管理：进版本控制、写测试、走 CI/CD、做安全扫描。这样面对非确定性输出时才留得住控制权，也才能把个人的"调参经验"变成团队可复用的资产。（来源：InfoQ · Patrick Debois）
  3. 控制 PR 规模，把审查从"更努力"改成"更结构化" 审查有效性在约 400 行之后明显下降，而 Agent 会开上万行的 PR。应对方向是限制单次提交规模、多轮审查、把机械性检查交给自动化，并让 Agent 借助可观测性自我修复。别指望"审查得更狠"能线性扩展。（来源：AI Engineer · Laurie Voss）
  4. Vercel 缓存排查手册：Vary: Cookie 让 CDN 不再缓存 Vercel CDN 现在不再缓存 Vary 含 Cookie 的 origin 响应。定位方式：x-vercel-cache 返回 MISS，且 Runtime Logs 出现 vary_key_denied:cookie。修复方式：若响应与 Cookie 无关，从 Vary 中移除 Cookie，CDN 即可在其他条件满足时正常缓存。（来源：Vercel News）
  5. K8s 上诊断 AI 推理延迟：指标全绿 ≠ 服务健康 freeCodeCamp 的实战案例：节点就绪、Pod 运行、CPU 仅 20%、无重启无告警，但用户首字延迟已 11 秒。这类"慢而健康"的问题要从排队、批处理策略、KV cache 命中、tokenizer、连接复用等推理路径环节排查，而不是只看集群层面的红绿灯。（来源：freeCodeCamp）
  6. 内核优化要落到硬件 tile 执行才算数 Google Developers Blog 的高分辨率视频扩散优化案例：为把 Sparse VideoGen 的算法稀疏性转成 TPU 上的真实加速，团队跳过空内存块、只对边界 tile 做精确坐标掩码、并把 token 内存布局重排为 temporal-major 以获得连续访问，最终取得最高 1.69x 端到端推理加速。教训：算法层面的"省"必须对齐硬件的实际执行粒度，否则只是账面上的稀疏。（来源：Google Developers Blog）
  7. 长程任务要显式设计状态、约束与核验 参考小红书推荐发布的 Harness 三件套：任务保存状态（抗跨会话中断）、模板固化约束（防止 Agent 自由发挥）、引擎推进并核验结果（不把"跑完了"当"做对了"）。同时给企业级 Agent 预留成本归属与预算约束——一个忘关的开关就足以让账单翻三倍。（来源：小红书技术 · InfoQ）
  8. 容灾演练要拉长到"小时/天"级别才有效 AWS 架构博客的 ARC Zonal Shift 多天 AZ 撤离演练：传统 DR 测试几分钟内切换流量就回滚，只能验证 failover 机制；而时变行为（比如没为持续 N-1 调优的 Auto Scaling 策略）只有在数小时到数天里才会暴露。把演练时长拉到与真实故障同量级，才能逼出短测看不见的失效模式。（来源：AWS Architecture Blog）
