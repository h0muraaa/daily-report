01Spring Boot 4.2.0-M2 与 Spring AI 2.1.0-M1 同日发布，Java 生态补齐 OpenTelemetry 与多模态消息

FRAMEWORKJava 后端一天内连收两个里程碑版本。Spring Boot 4.2.0-M2 包含 141 项增强、文档改进、依赖升级与缺陷修复，其中两个值得关注的新特性是：LDAP 的 SSL bundle 支持（含内嵌 LDAP 服务器的 LDAPS），以及对 OpenTelemetry 语义约定的原生支持，同时提供统一的 OTLP endpoint、header 与压缩配置——这意味着接入可观测性后端的样板配置可以大幅精简。

02Vercel Labs 开源 scriptc：把 TypeScript 编译成原生可执行文件，彻底甩掉 JS 引擎

COMPILERVercel Labs 推出实验性编译器 scriptc，可将 TypeScript 直接编译为体积很小的原生可执行文件，运行时不依赖 Node、V8 或任何 JavaScript 引擎。其实现路径是复用 TypeScript 编译器做类型检查与语义分析，再输出 C 或 WebAssembly 代码，交给宿主工具链生成机器码。

初步基准测试显示，scriptc 产物的启动时间与内存占用显著优于 Node，但纯执行速度反而更慢——这符合"冷启动优先"的取舍：牺牲峰值性能换取毫秒级启动和极小内存足迹。对于 CLI 工具、Serverless 冷启动敏感场景、边缘函数，这个权衡很有吸引力；对计算密集型长驻服务则不划算。项目目前处于实验阶段，适合先做技术预研而非生产替换。

03无状态 MCP 规范落地：远程 MCP Server 不再需要会话粘性

PROTOCOLAWS 详解了最新版 Model Context Protocol 规范的关键变更：移除协议层会话（protocol-level sessions）、粘性会话要求以及远程 MCP 服务器的会话存储。此前远程 MCP 部署必须依赖负载均衡的会话亲和性，把请求固定到同一实例，这让水平扩展变得别扭且脆弱。

新规范让请求可以独立路由到任意实例，架构上更接近标准的无状态 HTTP 服务，部署模型大幅简化。代价是应用状态、重试、可观测性与幂等性的责任被明确上移到应用层：以前协议帮你兜住的会话连续性，现在需要自己在业务代码里设计和实现。对正在把 MCP 工具服务容器化、跑在 K8s 上的团队，这是一次值得尽快评估的架构简化。

04Perplexity 自研 CobbleDB 替换 DynamoDB：Rust 键值存储把查询延迟砍到 1/5

DATABASEPerplexity 把搜索基础设施从 Amazon DynamoDB 迁移到自研的 CobbleDB——一个用 Rust 实现的键值存储。迁移后查询延迟降至原来的 1/5，云存储成本同步下降，新架构在承载可观生产流量的前提下，更高效地支撑高查询量场景。

这条新闻的价值不在"自研替换托管服务"这个结论本身（对多数团队并不适用），而在于它印证了一个常见规律：当访问模式足够明确、且批量文档处理成为主要瓶颈时，通用托管 KV 的抽象成本会变得难以接受。值得学习的是 Perplexity 的决策方法——先量化延迟与存储成本的具体损耗点，再判断是调优现有方案还是重写。Rust 的选择也延续了"数据面重写用 Rust"这一近年主流路径。

05Docker 发布 Sandbox Kit 规范 v3，联合 Linux Foundation / CNCF 推动成为中立标准

SECURITYDocker 发布 Sandbox Kit 规范 v3，并联合 Linux Foundation 与 CNCF 将其推为中立开放标准。核心思路是把 AI Agent 运行所需的全部权限声明——网络规则、凭据、卷、工具、指令——打包成一个普通 OCI 镜像，让"Agent 被允许做什么"第一次变得可版本化、可审查、可复现、可跨运行时移植。

该规范针对的是一个真实的工程痛点：Agent 权限是"隐形积累"的。每个 bind mount、每个范围过宽的 token、每条为图省事开大的防火墙规则，单独看都合理，叠加起来就摧毁了隔离，而且不需要任何漏洞利用——配置本身就是漏洞。更麻烦的是这些授权散落在 shell 历史、控制台和人的记忆里，无法交接、无法 diff。规范的关键设计取舍是：容器共享宿主内核、边界恰好是 Agent 正在探测的同一个内核，因此改用 microVM 提供独立内核，从而能在沙箱内放心给 root，破坏止步于沙箱边界。任何跑 coding agent 或自主 Agent 的团队都应关注这套声明式权限模型。

07Google 开源 AX：给 Agent 工作负载做的"Kubernetes"

ORCHESTRATIONGoogle 开源了声明式 Agent 编排运行时 AX，用 YAML 声明一个 Agent 任务，AX 负责在集群中沙箱化、配置环境、管控网络并大规模运行它。项目的立论清晰：Agent 是一种既有编排体系都不匹配的新型工作负载——它不像微服务（无状态、常驻），会持续积累对话记忆、工作区文件、工具会话等状态；也不像批处理作业（跑完即弃），大部分时间在等模型响应、等工具返回、等人类审批，沙箱空转烧钱。

架构上是四个二进制 + Redis：ax（开发者 CLI）、ax-server（无状态 gRPC API）、ax-controller（调和循环）、ax-task-runner（每个任务容器内的 PID 1）。核心原语有三个：Task 是最小执行单元，带 CPU/内存限制的隔离沙箱，生命周期用 status.phase + Conditions 表达并支持挂起/恢复；Workspace 把"环境准备"声明化，列出所需 Git 仓库、MCP 服务器、技能包，runner 在命令启动前物化；更激进的是 generative workspace——只写一句自然语言目标（如"搭一个 Python 3 开发环境"），首次启动时派一个引导 Agent 现场生成环境。这是目前对"Agent 编排层应该长什么样"最完整的开源回答。

02 / 深度技术解读

① Agent Harness：把"智能"和"让智能干活的基础设施"拆开看

今天有至少四条独立线索指向同一个概念——Agent Harness。Google Cloud 的 Ryan Lopopolo（该术语的提出者）在 The Agent Factory 中给出的定义很直接：一个 AI Agent = 一个 LLM + 一个 agent harness。Harness 是包裹在 LLM 外面的一切：工具调用协议、上下文拼装、记忆管理、权限控制、失败重试、可观测性。用他的话说，把模型"锚定（grounding）在丰富上下文中"、并把干预点左移，才能解锁高水平的 Agent 自主性。

InfoQ 的文章《The Agent Harness: What It Is and Two Ways to Build One》则用同一个财务助手的两个实现做了对照——AWS AgentCore Harness 与 LangChain + Envoy AI Gateway——比较它们在工具、记忆、模型访问、成本控制和可观测性五个维度上的处理方式与取舍。两者的核心分野在于：运维归属权、可移植性与工程量。托管方案（AgentCore）把你从基础设施里解放出来，但绑定云厂商；自建方案（LangChain + Envoy）可移植性强、控制粒度细，但你需要自己维护网关、限流、密钥与 tracing。选型时先回答一个问题：你希望 harness 是产品还是基础设施？

// 一个 harness 需要覆盖的横切关注点（按重要性排序）
1. Context assembly   // 给模型看什么、以什么顺序看
2. Tool protocol      // MCP / function calling / schema 校验
3. State & memory     // 持久化、压缩、召回（见下方"判断层"）
4. Permissions        // 沙箱、凭据、网络白名单（见 Docker Sandbox Kit）
5. Observability      // trace 每一次工具调用与 token 消耗
6. Cost control       // 预算、熔断、模型降级路由
7. Retry/idempotency  // 无状态 MCP 之后责任上移到应用层

与之呼应的还有两条消息。一是 Zuse，一个开源的"Devin 替代品"：它自己不实现智能体，而是做 CLI Coding Agent 的宿主、编排器和记忆系统，把 Claude Code、Codex、Grok、Gemini、Cursor、OpenCode 统一到一个持久化、项目感知的 GUI 里。其架构细节很值得抄：用 SQLite 事件溯源持久化会话、消息、轮次，重开应用完整恢复；每个聊天会话绑定独立的 Git worktree，多个会话可并行改同一仓库互不干扰；Provider 进程生命周期被拆成两个隔离平面——管理平面（只读查询，走共享资源池）与会话平面（默认每会话独占一个进程），直接回应了多 Agent CLI 混跑时最脏的并发问题。二是"判断层"正在被拆出来：TypeSafe 的 Jev、TierFlow 的 TierSense-1「枢衡」这类专用轻量模型，把难度评估、历史压缩、记忆召回的判断从生成中剥离，返回评分或结构化建议供程序直接使用，TierSense 单次 API 请求约 30ms。Jev 创始人 Diogo Almeida 的判断是："下一个时代并不是 Claude Code 时代"，AI 会像数据库、正则表达式一样退到软件背景中。

对开发者的直接启示：不要把 harness 的能力假设成模型能力。当你发现 Agent"不够聪明"时，先检查是不是上下文拼装、工具 schema 或记忆压缩这些 harness 层的活儿没做好——这三处的收益通常远大于换一个更强的模型。

② 删掉 40 万行测试代码，覆盖率几乎没掉：AI 写测试的"通胀"与治理

今天最扎心的一条开发者实践：OpenClaw 删除了大约 40 万行自己的测试代码，代码覆盖率几乎没有变化。原因并不复杂——现代模型特别爱写没用的单元测试，为了测试而测试，比如写十个 case 去判断一个常量里的字符串。这类测试在评审时很容易被"覆盖率上升"这个指标掩盖过去，实质上只增加了维护面、拖慢 CI、并在重构时制造虚假的失败信号。

更值得注意的是操作手法。项目作者指出：如果只跟 Agent 说"清理一下"，它会很早就停下来不干了；必须给它一个更狠、更可量化的目标，比如"删掉最没用的 20% 测试，同时覆盖率波动控制在 2% 以内"。这是一个可迁移的 Agent 指令设计模式：把模糊的意图翻译成带约束的、有明确终止条件的量化目标，Agent 的执行深度会显著不同。

OpenClaw 同时开源了他们使用的 test audit skill，其做法是在动手写测试之前先做拦截：要求 Agent 先回答四个问题，判断"是否有必要加测试"，通过判断才允许新增。这与 Stack Overflow 播客中 David Burns 的观点形成呼应——在 AI 驱动的环境里，职业性的怀疑精神（professional skepticism）才是开发者最好的技能，包括把 TDD 应用到 agentic engineering，以及认识到修 flaky test 的本质是管理应用状态而非重试。

# 可直接抄的 test audit 拦截式 prompt 模板
在为本改动新增任何测试之前，先逐条回答：
1. 这段逻辑是否包含分支 / 边界 / 状态机？（纯常量断言 → 不加）
2. 该行为是否已被现有测试覆盖？（重复覆盖 → 不加）
3. 这条测试失败时，能否指向一个真实的用户可见回归？
4. 若未来重构实现（而非行为），这条测试是否会误报？（会 → 不加）
# 四条全过才写。同时给清理任务设定量化目标与约束边界。

配套的工程实践是把测试结果本身变成可观测数据：Grafana Labs 公开了一套实用方法，把 Cypress 测试结果转换成 Prometheus 指标并推送到 Grafana Cloud，让测试套件的健康度（通过率趋势、flaky 率、耗时分布）进入与线上服务同一套监控与告警体系。测试不该是"跑完就丢"的 CI 日志，而应当是持续可查询的时序数据——这样才能在测试膨胀的早期就发现它。

03 / 工具推荐

mdxcn — 纯文本图表驱动的 MDX 文档组件集

DOCS一套免费开源的 MDX 文档组件集，包含提示框、步骤、终端、图表和时间线等 Markdown 友好型组件，可通过 shadcn CLI 一条命令复制进项目：

pnpm dlx shadcn@latest add mdxcn.dev/r/all.json

它最巧妙的设计是用纯字符（█ ░ - = + ├ └）画出带虚线边框、左上角 + 包角、顶边标注 [ TITLE ] 的图表，而非引入 Mermaid、SVG 或 canvas。这带来一个关键优势：图表就是纯文本——重新打开 MDX 文件时标签和数值依然可读，Agent 也能像当初写它一样直接编辑那帧图，不依赖渲染器、不产生二进制资产。视觉语法是强约束的：字体固定 Geist Mono、边框一律虚线、明确禁用 SVG/Mermaid/Recharts/canvas、动效仅限 opacity/transform 约 220ms。另一个独特之处是双轨交付——它同时是"给人用的组件包"和"给 Agent 用的 Skill"，装好 skill 后直接说"要一份 write-up"，内置的 chooser 决策表会按写作目的和数据形态自动挑选图表类型。写重构方案、事故复盘、PR 说明时非常合适。

MOBILEGitHub 上近 7K Star 的开源项目，接入设备后 AI 可以读取屏幕内容、点击按钮、滑动页面、往输入框填文字。支持安卓和 iOS，真机与模拟器均可，能接入 Claude Code、Codex 等支持 MCP 的工具。技术上的关键取舍是优先利用系统无障碍（accessibility）信息：App 给页面元素附带的、原本用于帮助视障用户的说明，能告诉 Agent 页面上有哪些文字、按钮、输入框及其位置，很多操作可直接依据信息完成；当信息不完整或控件难以识别时，再降级为截图 + 图像理解 + 坐标操作，两种方式结合以覆盖不同 App 的界面结构。对独立开发者的实用场景是页面检查自动化：改完一个页面，让 AI 打开设备检查按钮位置和页面跳转，替代手工点测。运行环境需要 Node.js 22+。

Zuse — CLI Coding Agent 的开源宿主与编排层

AGENT被称为"开源版 Devin"，把 Claude Code、Codex、Grok、Gemini、Cursor、OpenCode 等 CLI Coding Agent 封装进统一、持久化、项目感知的图形界面。它解决三个具体问题：工具碎片化（每个 CLI 各有终端界面、会话管理和配置方式，Zuse 提供统一外壳：流式聊天时间线含工具调用/思考块/diff/错误气泡、斜杠命令、@ 文件引用、图片 PDF 附件、Plan 模式、会话级权限覆盖）、上下文丢失（SQLite 事件溯源持久化，重开完整恢复；每会话独立 Git worktree 支持并行改同一仓库）、人力瓶颈（云端工作区跑在托管沙箱，桌面端关掉后继续执行，通过手机 Expo 推送审批权限、查看结果）。想自己搭多 Agent 编排的团队，它的 Provider 进程双平面设计是最值得研读的部分。

04 / 实践指南

4.1 给 Agent 的指令要带量化目标与约束边界

来自 OpenClaw 的实战经验：模糊指令会让 Agent 提早收工。只说"清理一下"，它会很早就停下来；改为"删掉最没用的 20% 测试，同时覆盖率波动控制在 2% 以内"，执行深度完全不同。原因是 Agent 需要一个可判定的终止条件来自我评估完成度，而模糊目标无法被判定。可落地的模板：

# 差的写法
清理一下这个模块的重复代码

# 好的写法：目标 + 量化指标 + 约束边界
重构 src/parser/ 下的重复逻辑：
- 目标：减少重复实现，消除最近 3 次 commit 中的复制粘贴
- 约束：公开 API 签名不得变更；现有测试全部通过
- 量化：重复代码块（≥8 行完全相同）数量从当前值降到 0
- 停止条件：达成量化目标后立即停止，不要顺手做无关重构

配套的是把生成权从模型手里拿回来——test audit 模式（先回答四个必要性问题再动手）本质上是在生成前插入一个显式决策点，比事后审查更省成本。

📎 来源：[Viking @vikingmute] OpenClaw 测试清理经验 · [Viking @vikingmute] test audit skill

4.2 无状态 MCP 迁移清单：把状态责任接回应用层

新版 MCP 规范移除协议级会话后，原先由协议兜底的连续性、重试与幂等责任上移。迁移到无状态远程 MCP 前，逐项确认：

  • 会话状态外置：把原先隐式依赖"同一实例"的内存态（对话上下文、临时文件、游标）迁移到外部存储（Redis / DB），或改为随请求传递。
  • 幂等键：为写操作定义 Idempotency-Key 语义，避免负载均衡重试造成重复副作用。
  • 可观测性补位：粘性会话消失后，跨实例的 tracing 必须依靠 trace context 传播，确认 OTLP 链路已打通（Spring Boot 4.2 的 OTel 语义约定支持正好可以简化这块配置）。
  • 重试策略：从"依赖会话亲和性避免重试"改为显式的指数退避 + 熔断，并区分可重试与不可重试错误。

收益是部署模型回归标准无状态 HTTP 服务，K8s 里不再需要配置会话亲和性，水平扩展与滚动更新都变得简单。

📎 来源：[InfoQ] Stateless MCP Removes Session Affinity Requirements

4.3 用声明式方式管理 Agent 权限，别让它"隐形积累"

Docker Sandbox Kit v3 的核心洞察值得变成日常习惯：Agent 权限的失控不需要漏洞利用，配置本身就是漏洞。每个 bind mount、每个范围过宽的 token、每条图省事的防火墙规则单独看都合理，叠加起来就摧毁了隔离，而且没有落盘记录——散落在 shell 历史、控制台和人的记忆里，无法交接、无法 diff。实践建议：

  • 把 Agent 的网络规则、凭据、卷、工具、指令统一声明到一个可版本化的文件里，纳入代码评审。
  • 隔离边界选在模型能触及或改写的一切之下——容器共享宿主内核，而 Agent 恰恰在探测同一个内核；microVM 的独立内核才提供真正的边界。边界之内可以放心给 root。
  • 对"空沙箱不是环境"这一点保持清醒：还需要声明跑哪个 Agent、配哪些工具和 MCP 服务器、哪些技能和指令塑造它。

如果团队已经在用 Google AX 这类运行时，其 Workspace 原语正是把"环境准备"声明化的实践：列出所需 Git 仓库、MCP 服务器、技能包，runner 在命令启动前物化好，甚至支持用一句自然语言目标生成环境（generative workspace）。

4.7 花絮：为什么网址要以 www 开头？

一条适合放进团队知识库的经典科普。www 全称 World Wide Web，本质只是一个子域名，www.example.com 可拆为主域名 example.com + 子域名 www，与 mail.example.com、ftp.example.com、api.example.com 属于同一类。它从来不是必须存在的东西，只是早期命名习惯的残留：九十年代一个域名下常同时运行网站、邮件、FTP、BBS、新闻组等多种服务，前缀用于标识服务类型；而当年 DNS 解析能力有限、虚拟主机不成熟、HTTPS 未普及、CDN 几乎不存在、服务器软件兼容性差，工程师发现把网站统一放到 www.xxx.com 最稳定省事。如今的裸域名（google.com、github.com）已完全可用。理解这段历史有助于正确理解 DNS、虚拟主机与 TLS 证书（SAN/通配符）的配置边界。
