DEEP DIVE / 01

Jev 决策模型：把"判断"从生成里拆出来，为什么它能便宜 400 倍

它要解决的问题：Agent 循环里最贵的一步其实不需要生成

典型 agent loop 长得像这样：每一步都调用一次 llm(context)，让模型逐字生成一段文本，再用代码去解析 JSON，格式错了还得重试。可是循环里绝大多数步骤要的并不是一篇长文，而是一个极小的确定性判断：这封工单紧不紧急？这个指令该分发给哪个下游模型？刚检索出的这段知识能不能回答用户问题？这个终端命令有没有删库风险？用自回归生成来做选择题，代价是双重的——又慢又贵，而且结果还得靠解析器猜。

形态与计费：为什么"输出免费"是机制而不是折扣

Jev 的接口很窄：输入文本或可序列化的 state，再加一个或多个带类型的问题；输出是 choice / score / yes-no 以及对应的概率。TypeSafe 的官方描述是 "unstructured state in, typed probabilistic decisions out"，把它称作"前沿智能的函数调用"。

关键在计费口径：普通 LLM 按输入 和 输出 token 计费，输出单价通常高得多；Jev 只对输入计费、输出免费。这不是营销折扣，而是输出形态决定的——输出不是 token 序列，而是几个浮点数，没有自回归解码这一步，因此速度是百倍量级的差。理解了这一点，就能判断它适合什么：凡是"能写成选择题"的位置都适合，凡是需要生成长文本的位置都不适合。

边界：它不是 Agent，也不做执行

  • 接收 state 与类型化问题，返回 choice / score / yes-no 及概率；
  • 是否执行、调用哪个工具、风险阈值是多少，仍然由应用代码决定；
  • 它不打开浏览器、不删文件、不下单。把"判断"和"执行"分开，好处是判断这一步变得可解析、带概率、可弃权——低于阈值就直接不走自动路径。

动手接入：三条命令先在命令行跑通

# 1. 安装 Simon Willison 写的 LLM 插件
llm install llm-typesafe
llm keys set typesafe

# 2. yes/no 判断（noul=0.99 表示"是"的置信度 0.99）
llm -m jev 'Please refund my last payment.' \
  -s 'Does this message explicitly request a refund?'
# → {"type": "noul", "noul": 0.99}

# 3. 多分类（带类型化候选与判定标准）
cat message.txt | llm -m jev \
  -s 'Which team should handle this message? If billing and technical issues both occur, choose billing.' \
  -o answer_type choice \
  -o criteria '{"billing":"Charges, invoices, payments, or refunds","technical":"Problems installing or using the product","other":"Neither"}'

要在服务里用，Vercel AI Gateway 提供两种调用方式：TypeSafe 兼容的 API（与 AI SDK 的 type-safe 风格一致）以及纯 HTTP API，所以任何语言、任何框架都能接，不必绑 JS 生态；AI SDK 内 9/25 前免费，正好用来做小规模验证。

为什么值得跟这条线

  • 它把"校准过的置信度"推成共识接口。对工程的价值不是准确率数字，而是"可以设阈值"这件事本身——高置信自动处理、低置信转人工，这是把 AI 输出接入既有业务流的通用形状。Jerry Liu 把同一思路延伸到 schema 化文档抽取：每个抽出的值都带置信度，还带指回原文的 bounding box，人审时可以直接定位。
  • 它天然是路由器。如果"选哪个模型、走哪条分支"被建模成一个可校准的离散决策，那它正好是前面 Fireworks 实验里最缺的那一环——实验结论是"真正的难题是预测哪个模型合适"。决策模型给这种小分类任务提供了一个便宜且可校准的执行体。
  • 训练范式上的取舍值得理解。作者 Diogo Almeida 的核心论点不是"模型不够聪明"，而是过去的模型没有为软件世界设计：RLHF 的本质是优化人类偏好，循环的终点是"让人满意"，那就必须有人在环里，于是 AI 永远无法完全自动化，还会附带谄媚与幻觉。他们改为以 RLCD（程序在环）为北极星，做"机器原生、能被代码直接消费"的模型。对一线开发者的含义是：不要指望"更聪明的聊天模型"解决可靠性问题，把可验证的决策抽出来单独做，才是有产出比的路径。
风险提示：决策模型同样会校准失真，"置信度 0.99"不等于"这条判断对"。上线前仍需针对自己的分布做 eval，并且不要把高风险动作（转账、删数据、改权限）的最后一票交给单一阈值——阈值应该触发人工，而不是放行。

MiMo-V2.6 的 RL 施工记录：MixRL 与 MOPD 为什么必须并存

这轮发布真正少见的地方不是模型，而是把施工过程放了出来：6 天里训练中断过、模型钻过奖励的空子、有些任务适合一起练、有些必须分开——这些都写进了 44 页技术报告，团队还开了一个在线面板直播训练进度与花费。下面是能直接迁移到自家 RL 流程的几条。

先把规模账算清楚

  • Pro 与 Flash 各跑 30 个训练步骤，Pro 覆盖约 75 万条轨迹、每条平均 11 万–15 万 token；
  • 成本：Flash 约 85 万美元，Pro 约 262 万美元，合计约 347 万美元；
  • 峰值配置：约 每步 20 亿 token、1568 prompts × 16 rollouts、全异步、跨多个 harness 的多任务 agentic RL；
  • 奖励侧：用 test-case 与 rubric 构造，并做组内（in-group）credit assignment。

注意最后两条的因果：全异步带来吞吐，也带来 rollout staleness——旧策略采出来的轨迹还没跑完，中心策略已经更新了好几版，梯度信号就失真了。这并不是实现瑕疵，而是规模化的固有代价，也正是下面两条管线要分开的原因。

管线一 MixRL：把可验证的中等难度任务混在一起练

把编程及相关 agentic 任务放进同一个 RL run 联合训练，团队的实证结论是跨域混合的泛化"出奇地好"。他们被问"为什么你们能做 MixRL"时给了三个答案，前两个是技术性的，第三个是组织性的——团队扁平、没有部门墙，跨域联合训练"对我们不难"。这条信息对 RL 团队比任何超参都重要：能不能做联合训练，往往取决于组织边界而不是算法可行性。

管线二 MOPD：难验证的任务单独训教师，再蒸馏合并

游戏、3D 这类任务有三个特点叠加：难验证、超长时程、评价信号主观。它们的 rollout 又慢又长，混进联合 run 会拉垮吞吐，或者造成严重的 rollout staleness。所以做法是分两步：

  • 各领域单独跑 RL，训出领域专家教师；
  • 再让主模型在自己的 rollout 上接受多个教师的稠密 token 级信号，把能力蒸馏合并回来（Multi-Teacher On-Policy Distillation）。

MOPD 不是临时凑的办法：它此前在 MiMo-V2-Flash 的后训练中提出，有独立论文，并在 Qwen3-30B-A3B 上系统对比过 Mix-RL、Cascade RL、参数合并等基线且胜出。所以"两条管线"不是二选一，而是同一系统里的两条通路：可验证的中等难度任务走联合训练吃吞吐，难验证的长时程任务走"专家教师 + 蒸馏"保信号质量。

配套的推理侧优化：KV Cache 上的 NVFP4

同一批新闻里还有一篇 SGLang × Qwen × NVIDIA 的三方工作，解决的是长上下文与 agentic 场景下推理系统的最大内存压力源——KV Cache。FP8 已把占用相对 BF16 砍半，再往下压到 4-bit 时量化误差会明显放大，一直是难点；这篇把 NVIDIA 在 Blackwell 上推出的 NVFP4 格式落到了 SGLang 的分页 KV Cache 里。

NVFP4 的关键是两级缩放：数值本身用 4-bit E2M1（1 符号 + 2 指数 + 1 尾数）；每 16 个值配一个 FP8 (E4M3) 的块级缩放；整个张量再配一个 FP32 全局缩放。存储账很直观：16 个值打包占 8 字节，加 1 字节块缩放共 9 字节，而 FP8 同样 16 个值要 16 字节，即 约为 FP8 的 56.25%、容量比约 1.78×——注意这不是 4-bit 理论上的 2×，那 1 字节块缩放就是为精度交的税，账算得很诚实。实现上按阶段分三条注意力路径：初始 prefill 用 BF16 Q × FP8 K/V 计算（不牺牲算力）同时把 KV 量化成 NVFP4 写入持久缓存，这个阶段不读缓存所以没有反量化开销；分块 prefill / extend 走另一条；decode 再一条。

04实践指南

兼容性升级到 Opus 5.5 前，先 grep 两个会让请求变成 400 的变更

① 思考模式改为始终 adaptive：请求里禁用 thinking 或指定固定 thinking budget 会被拒绝；② forced tool use 下线。做法是在代码库搜 budget_tokens、thinking、tool_choice（特别是 {"type":"tool"} 形式的强制调用），把控制权交回模型自适应；再在 CI 里加一条"对生产 prompt 做一次真实冒烟调用"的检查，比等到线上出现 400 便宜得多。

为什么值得单独做：这两条改的是"原本合法的请求变非法"，不会在类型系统或编译期报错，只会运行时炸——属于典型的静默破坏性变更。

流程把三条测试规则写进 AGENTS.md，压住 agent 的"表演型测试"

① 禁止先写实现、后补 unit test——否则 agent 会陷入"为了通过而通过"，写出"补 10 个单测去断言一个常量字符串里有没有某段子串"这种测试，各种模型都有这个倾向；② 优先把 E2E 作为唯一测试手段，用 E2E 验证复杂功能真的能跑通，并让 E2E 结束时产出一个可验证、可复现的 artifact；开发阶段只跑与本次改动相关的几条，开 PR 后本地跑全量、CI 上只跑关键路径；③ 如果必须单独测某块系统，先列出它所有可能的失败方式，再写代码。

为什么有效：这三条针对的是倾向性问题而不是能力问题，放在 AGENTS.md 顶部对各类 harness 都生效，比事后人工 review 测试质量高效得多。第三条本质是 TDD 的变种，但更适合 agent——先约束"怎么算失败"，比先约束"怎么算通过"更容易验证。

📎 [来源: Viking(@vikingmute)]

成本模型选型先算"路由上界"，再决定要不要固定用一个贵模型

把 Fireworks 的实验当成决策模板：取自己 20–50 个代表性任务，跨 2–3 个价位档的模型各跑几次，然后观察"如果每个任务都能选到最合适的那个，能提升多少"。经验值很明确——从 1 个模型换到 2 个模型的跃升最大（+13.1 个百分点），三模型组合已达 91.2%，从 3 个扩到 18 个只再涨 6.4 个点；同时 113 个任务里 94 个的最优选择是单价低于 $3 的模型。所以不要一开始就搭复杂路由器，先做一个"两个模型 + 一个简单判别"的版本，收益就已经拿到大头。

为什么：固定用一个贵模型，是在为每一项任务支付"通用能力"的保险费，而多数任务只需要其中一小部分能力。长期看，真正值得投入的是"预测哪个模型合适"的分类器——这正好可以交给深度解读 01 里那类便宜的决策模型。另外比价时别忘了 token 效率：同一档单价下，p99 请求多耗 20–30% token 就是实打实的成本差。

📎 [来源: Fireworks AI(@FireworksAI_HQ)] · [来源: meng shao(@shao__meng)]

架构用 Worker Previews 做按分支隔离验证，但先确认存储绑定

每个分支能拿到独立的 vars / secrets / bindings、稳定 URL、独立的 Durable Objects / Containers / 日志 / trace，这让"agent 推分支 → 自动起环境 → 自动验证"的流水线变得很自然。但上线前必须做一件事：逐项确认 KV / D1 / R2 的绑定指向测试资源而不是生产资源——它们不做自动隔离。

为什么：隔离环境的收益是否成立，取决于最容易出事的那部分有没有真正隔离。计算和配置隔离了、状态存储没隔离，等于给了一个"看起来安全"的假象，分支上的实验会静默写进生产数据。

📎 [来源: The Cloudflare Blog] · [来源: Viking(@vikingmute)]

流程大重构别只优化"AI 写代码"，先把验证闭环建起来

两条来自一线的对照实践值得放在一起读。去哪儿网用 AI Coding 驱动一次 15 万行高并发核心系统重构：总工时约 100PD → 30PD、搜索主流程 P50/P90 耗时下降约 70%、机器资源成本节省约 45%，最终无 QA 介入上线且无故障；他们的方法论不是提示词技巧，而是先把重构拆成"目标可拆解、边界可约束、过程可验证、风险可回滚"的执行系统。腾讯云做登录系统替换时遇到的阻塞点也不是生成代码，而是验证：公共环境不敢停 Redis / 断 DB，预发路径从发起到可验证要 30 分钟到 1 小时，于是改为给每位开发者一套低成本、可控、隔离的验证环境，在其中自主完成故障场景验证（Redis 不可用、DB 不可用下的降级行为）。

为什么：代码生成已经不难，真正的阻塞点在评审、验证与回滚。同一件事在 eval 上也有对照数字——Ramp 的收据采集准确率从 35% 提到 83%，Shopify 用 evals 调出来的工作流比它替换掉的前沿模型方案快 2.2× 且便宜 68%。先把验证环境和 eval 建起来，AI 的吞吐才真正落到交付上。
