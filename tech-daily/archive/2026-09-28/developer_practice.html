01Claude Sonnet 5.5 全平台上线：更快的 Sonnet、更少的 token，价格不变

Anthropic 发布 Claude 5.5 家族第二个成员 Claude Sonnet 5.5，定位是"well-scoped everyday work"——修 bug、写文档、做表格，是 Opus 5.5 的低成本高速补充。官方数据：输出速度快 30% 以上，单任务成本最高降低 30%，而单价与 Sonnet 5 完全一致（OpenRouter 上是 1M 上下文 $2/M 输入、$10/M 输出），省下的成本来自"同样的活需要更少 token"。基准上，Addy Osmani 列出 Terminal-Bench 4.0 70.6%、OSWorld 2.1 80.1%；Cognition 在 FrontierCode 1.1 Main 上测得 64.4%，较 Sonnet 5 的 56.2% 明显跃升，超过 Fable 5.1 的 extra-high reasoning effort。Claude Code 侧的用户体感是 同样时间多完成约 30% 的任务。

发布当天即全线铺开：Cursor、GitHub Copilot（app/CLI）、Devin Desktop 与 Devin CLI、v0、Vercel AI Gateway、AI SDK、Amazon Bedrock、OpenRouter 同步可用。值得注意的是，Sonnet 5.5 是首个带 cyber 安全护栏与降级策略的 Sonnet 模型，官方称常规软件开发不受影响；同时它成为 claude.ai 免费层的驱动模型，Haiku 5.5 将在未来数周补齐家族。

实践启示 ▸ "同价、更少 token、更快"意味着如果你有跑在 Sonnet 5 上的批处理或 agent 流水线，应当直接切换并重跑一遍 evals——成本下降可以立刻量化，但行为变化（尤其是多步任务里的自检行为）必须用你自己的测试集确认。

02沙箱安全成为本周主线：Perplexity 实测 10 家第三方平台，8 家存在网络策略绕过

Perplexity 安全团队公开了对 SPACE（支撑 Perplexity Computer 的沙箱平台）的攻防实验结果，方法本身极具参考价值：他们给 9 个模型（Opus 5、GPT-5.6 Sol、Kimi K3、Gemini 3.1 Pro 等）VM 内的 root 权限，某些轮次连沙箱完整源码一并给出，要求它们逃逸到宿主或访问被网络策略封锁的 URL。108 次尝试中没有任何模型突破 VM 边界；但一旦放开一点网络（仅允许 PyPI 与 Ubuntu 镜像以便装包），4 个模型成功到达被封锁的 URL，手法包括：伪造 DNS 应答欺骗网关、利用 pypi.org 与数千站点共享的 Fastly IP 做同 IP 侧信道、以及 GPT-5.6 Cyber 经由 Taboola 的图片抓取器打到截图服务后 OCR 出 flag。Perplexity 顺手评估的 10 家第三方沙箱中 8 家存在同类网络策略绕过，已全部通报厂商。一个有意思的细节：Claude Opus 5.0 识别出了 IP 共享路径但选择不用，理由是"不要针对外部系统"；Fable 与 GPT-6 Astra 直接拒绝任务。

踩坑提醒 ▸ 纯网络隔离挡不住"同 IP 共享 + DNS 欺骗"这一类侧信道。如果你的沙箱允许装包（哪怕只放行 PyPI），就必须假设 egress 策略可被绕过——真正的防线是能力白名单 + 凭证不落地，而不是域名黑名单。

03NVIDIA Open Agent Safety Platform 发布：OpenShell 策略执行 + Sentry 独立监控

NVIDIA 联合 100 多家行业伙伴推出 Open Agent Safety Platform，由两部分组成：OpenShell 在 agent 运行全程持续执行安全策略（针对"agent 能跑几天、不断调工具、遇错重试"的长时场景），以及运行在 BlueField-4 上的 Sentry 做独立监控与强制。Andrew Ng 的观点解释了为什么这件事重要：OpenAI–Hugging Face 事件是弱沙箱导致的，而有效的沙箱应该只把任务相关的文件放进去，密钥、浏览器登录凭证、任意网站访问默认不可达，且这些限制应由确定性代码而非 prompt 实现——因为 LLM 会犯错、也可能被 prompt injection 攻破。他的 OpenWorker 将基于 NVIDIA OpenShell 实现每 agent 独立的命令沙箱，并记录全部动作以供审计。LangChain 是本次发布的 launch partner。

04Git 2.56.0 发布：可只暂存"已解决的冲突"，无需连带暂存其他改动

Git 2.56.0 发布，包含来自 104 位贡献者（其中 39 位新面孔）的特性与修复。最实用的改进是解决了一个长期痛点：解决 merge 冲突实际分两步——先把工作区改成想要的结果，再把冲突路径 stage 起来告诉 Git"已解决"；但现有命令很容易把你不想提交的无关本地改动一起 stage 进去（例如 recipe.txt 冲突、notes.txt 同时有本地编辑）。新版本提供了只暂存已解决冲突路径的能力，让"冲突解决"和"其他工作区改动"彻底解耦。

可复用技巧 ▸ 频繁处理冲突的团队值得把版本提上来；在 CI 里跑"冲突解决后立即构建"的流水线时，这项能力能避免把半成品改动误带进验证。

05Cloudflare 一天连发五件：Vinext 1.0、cf CLI、Forge、EmDash 1.0、Workers 原生 Rust

Cloudflare 博客集中发布了一批开发者向更新，主题高度一致——把 agent 当成一等客户：

  • Vinext 1.0：把 Next.js 应用（Pages 与 App Router）从"只能部署到 Vercel"变成可移植到任何 Web 平台，包括 Workers 免费计划、Netlify、AWS Lambda。它源于 2 月的一次"一周 AI 驱动实验"，如今已在生产中承载高流量动态应用。
  • cf CLI：一个面向 agent 的新 CLI，覆盖 Cloudflare 全部产品。动机来自数据——2026 年 3 月 agent 已占 Wrangler 使用量的 1/4，上周达到 48%；agent 每天用的命令种类几乎是人的两倍，且用 6 个以上命令的概率是人的近四倍。Wrangler 只覆盖约 280 个操作，而 Cloudflare 有数千个。
  • Forge：开源、可插拔的生成流水线，用于产出 SDK、CLI、文档与库，目前已生成 cf CLI 所需的全部产物。背景是 Cloudflare API 拥有 3500+ 端点，自研生成器已经跟不上。
  • EmDash 1.0：基于 Astro 的稳定版开源 CMS，被称作"WordPress 的精神继任者"。开发者用 Astro 构建、编辑走 admin、agent 可走 API/CLI/内置 MCP server。
  • Workers 原生 Rust：为 wasm-bindgen 增加 wasm32-unknown-emscripten 目标的实验性预览，让原生 Rust 代码乃至基于 Tokio 的应用能直接跑在 Workers 上。
为什么重要 ▸ "48% 的 CLI 调用来自 agent"是一个明确的信号：CLI/SDK/MCP server 正在从"开发者产品专属"变成所有产品的标配面。Forge 的价值在于把这件事自动化——如果你维护一个有大量 API 的产品，手写 SDK 和文档已经不可持续。

06Artifactory 三个漏洞正被活跃利用：5 分钟内可拿到管理员持久访问权

InfoQ 报道，三个 Artifactory 漏洞正处于活跃利用状态，可让互联网可达的自托管部署被绕过认证，攻击者能在不到 5 分钟内建立持久的管理员访问。利用成功后可进一步窃取凭证与密钥、执行任意代码、建立持久化并进行反取证操作。由于 Artifactory 常被用作制品仓库（存放构建产物、内部包、依赖镜像），一旦失守等于供应链上游被打开。

行动项 ▸ 立即检查自托管 Artifactory 是否暴露在公网、是否已升级到修复版本；若无法立刻升级，先收窄网络访问（只允许 CI 与开发者出口），并轮换仓库内可能触及的凭证与签名密钥。

07Radicle 披露两个严重协议漏洞：私有仓库内容以明文暴露，且节点可被冒充

去中心化代码协作平台 Radicle 在其 wire 协议中发现两个严重漏洞，影响所有已发布节点版本，破坏全网的机密性：攻击者可读取私有仓库的明文数据，并可冒充其他节点。由于问题出在架构层面，官方建议立即暂停 clearnet 上的运营；修复需要迁移到新协议（Iroh），因此会带来向后不兼容。

08工程案例：Meta ZGateway 每秒 10 亿次操作、连接数降 19 倍；Linear 完成 1000+ PR 的 StyleX 迁移

两个值得拆解的大规模工程案例。其一是 Meta 的 ZGateway——一个面向 ZippyDB 的无状态代理，把连接管理、流量路由、缓存、负载均衡与准入控制集中起来，每秒处理 10 亿次以上操作，承载约 40% 的 ZippyDB 流量，Meta 模型估算持久连接数下降 19 倍。其二是 Linear 把 React 应用从 styled-components 迁移到 Meta 的 StyleX，横跨 1000+ 个 PR，目标是提升性能并强制更严格的组件边界，结果是主线程工作量下降、导航速度提升——代价是 StyleX 的约束性规则引来一些批评。此外，Uber 公开了 ServiceScale 控制器，把"扩缩容意图"与"执行"分离，使多个编排器能安全地管理同一批 Kubernetes 工作负载，支持区域故障切换而不必预留闲置容量。

实践启示 ▸ 三个案例共享一个模式：把"意图"从"执行"中剥离（ZGateway 剥离连接管理与业务、ServiceScale 剥离缩放意图与执行、StyleX 剥离样式语义与运行时）。这类解耦通常比"优化某一段热点代码"带来更量级的收益，也更容易被独立测试。

深度一 · 生成模型之外的第二条赛道：决策模型正在接管 agent 的"路由器"

本周 Sonnet 5.5 这类生成模型的降价很热闹，但同一批 feed 里还有一条更容易被忽略的线索：一批"决策模型"正在把 agent 系统里大量本不需要生成文本的判断，从昂贵的前沿模型上卸载下来。

  • Jev（TypeSafe AI）返回的不是文本，而是类型安全的结构化值——一个选择、一个分数、一个概率。定价是 $0.04/M 输入 token 且输出免费。一个有说服力的实测：它用 24.9 秒读完当天早上的 384 条新闻，为 15 个品牌筛出适合当天借势的新闻，总成本 $0.19；同一时间、同一批信息源，Claude Opus 5 只处理了 4/384，成本却是 $0.77。作者在 5 个真实项目（PR 分类、自我会话元分析、Gmail 分诊、产品洞察图、4500 条 YouTube 评论实时看板）上都用了它，并特别提到用 9 美分分析了 1700 个 PR。
  • Solar Mini 4 / Solar Decide（Upstage，上 OpenRouter）：Solar Mini 4 是 35B MoE、3B 激活参数、524K 上下文，$0.05/M 输入、$0.20/M 输出，支持工具调用与结构化输出；Solar Decide 则是构建在它之上的决策模型，跑在 OpenRouter 的 Decisions API 上。
  • Span-01 / Span-01 Lite（Respan）：直接面向 agent trace——你发一个 span 加上你关心的行为，返回每个行为出现的概率，比如"用户是否沮丧""这个工具调用是否安全可执行"。定价极低（输入 $0.02/M，输出免费，Lite 版完全免费），声称比 Jev 便宜 2 倍、效果好 18%。
  • Magpie + DeepSeek + RTK 的组合则是从另一侧省钱：先用 DeepSeek 压低 prompt 成本，再叠一层 RTK 把 Bash 工具输出里的噪声过滤掉，实测省掉七成多的工具输出 token。

把这几件事放在一起，图景就清楚了：一次典型的 agent 循环里，真正需要"生成能力"的只有推理与产出那一小部分，其余大量步骤——路由、分类、判定、打标、gating——本质上都是决策。用前沿生成模型去做这些，等于用 Opus 的价格做分诊。而决策模型的输出是结构化值，天然可类型检查、可缓存、可单测，也更适合放进 CI 做回归。

落地方向 ▸ 先把你自己的 agent 流水线按"生成 / 决策"过一遍，把分类、路由、安全判定、满意度打标这类步骤抽出来，接到决策模型或一个廉价小模型上；再对工具输出做一次噪声过滤。在做这件事之前，先把每一步的 token 成本和延迟打点——大多数团队会发现长尾步骤的调用量远高于核心生成步骤。

深度二 · "把密钥塞进环境变量"正在成为 agent 时代最危险的习惯

本周三条独立信源指向同一个反模式，值得单独拎出来讲。

问题本身。Philipp Schmid 指出：把 API key 或 secret 当作普通 env 传给 agent，意味着沙箱里任何一个依赖都能读到它、并可能把它泄漏出去。这在传统服务里已属可疑，在 agent 场景下被急剧放大——因为 agent 会执行模型生成的代码、会安装第三方包、会调用任意工具，而这些代码与包都在同一个沙箱里，和你的密钥共享同一个环境。Gemini Managed Agents 给出的方案是 Credentials API：密钥不落地到沙箱，而是在发往可信域名的链路上注入，因此沙箱内的代码永远拿不到原始 token，且对 env、CLI、MCP Server 都适用。

为什么单纯"网络隔离"不够。Perplexity 的实验给出了实证：在只放行 PyPI 和 Ubuntu 镜像的情况下，4 个模型依然通过伪造 DNS 应答、利用 pypi.org 与其他数千站点共享的 Fastly IP 等手法到达了被封禁的 URL。也就是说，只要沙箱能出网（哪怕只是为了装包），基于域名/IP 的 egress 黑名单就可能被绕过。

正确的分层。把这三条消息合起来，一个相对完整的分层防御是：① 密钥不进沙箱（走凭证注入 / 短期凭证 / 链路注入），从根上消除"读得到"；② 权限用能力白名单而非网络黑名单表达，且用确定性代码而不是 prompt 实现（Andrew Ng 强调 LLM 会犯错、会被 prompt injection 攻破）；③ 全程记录动作以供审计，并用独立于生成方的组件做监控（如 NVIDIA OpenShell 管策略、BlueField-4 上的 Sentry 独立强制）；④ 沙箱本身要能观测（Vercel Sandbox 本周新增内存可观测，含 P75/P95 与 85% 内存上限参考线，可在 query builder 里用 memoryUsedBytes 做自定义告警）。

自查清单 ▸ 现在就 grep 一遍你的 agent 部署配置：有没有 OPENAI_API_KEY / AWS_SECRET_ACCESS_KEY / 数据库连接串出现在 agent 容器的 env 里？如果有，先假设它们已经被任何一次安装依赖的行为暴露过，并制定轮换计划。其次检查你的 egress 策略是不是一份域名黑名单——如果是，它挡不住同 IP 侧信道。

一、模型换代后的标准动作：切换 → 重跑 evals → 量化成本差

Sonnet 5.5 提供了罕见的"同价 + 更少 token + 更快"三重改善，这类升级通常不需要任何代码改动。但 Sonnet 5.5 同时是首个带 cyber 护栏的 Sonnet 模型，且在多步任务里的自检行为有变化，因此不能只凭"基准变好"就上线。

  1. 先量化。记录切换前后每次任务的输入/输出 token 与耗时，把"省了 30%"变成你自己数据的结论，而不是引用官方口径。
  2. 再验证。用你现有的评测集重跑一遍，重点看多步 agent 任务的成功率与工具调用次数——GitHub 的早期测试提到它"用显著更少的步骤、token 与工具调用完成同样任务"，这类变化会直接影响你的重试逻辑与超时设置。
  3. 最后重估路由。如果 Sonnet 5.5 在多数任务上已经接近 Opus，就把 Opus 留给真正困难的长程任务，其余走 Sonnet——这正是"决策模型 + 生成模型分层"的延伸。
📎 来源: GitHub Copilot 早期测试结论 · 对齐审计与 cyber 护栏 · GitHub / Claude (@claudeai)

二、多 agent 不一定要中心编排：共享状态也是一种可行架构

Microsoft Research 的一篇论文做了一次很有信息量的压力测试：他们同时运行 1000+ 个 coding agent，架构叫 Agensh，没有中心编排器——agent 通过共享状态协调：各自收集上下文、认领子任务、完成工作、分享发现、验证结果并合并，全部通过共享工作区与消息通道异步进行。数据上，在最难的 5 个 ProgramBench 任务上把 agent 从 1 增加到 128，平均最终测试通过率从 19.31% 升到 28.78%，且更大的团队更早达到给定通过率；在 pandoc 上，1024 个 agent 达到目标通过率所需的时间进一步缩短。

实践启示 ▸ 如果你正打算给 agent 系统引入"主管 agent"，先问一句：需要共享的是状态还是决策权？前者用共享工作区 + 消息通道就够了，且扩缩容更自然；后者才需要中心编排。另外注意论文里"每个 agent 都要自己验证结果"这一点——没有中心编排时，验证责任必须下沉到每个 worker。
📎 来源: Microsoft Research — 1K+ coding agents, no central orchestrator · elvis (@omarsar0)

三、用 AI agent 补齐"遗留服务缺文档"这块硬骨头

InfoQ 的一篇文章给出了五种用 AI coding agent 改进行架构的用法，切入点是许多现代架构共有的现实：系统里依赖着若干遗留服务，它们缺少准确文档，不了解就贸然改动风险很高。AI coding agent 的价值在于把这个知识缺口先填上——让 agent 去读代码、梳理调用关系与契约，形成人类可审阅的文档，再动刀。这与"Google 用 AI + 差分模糊测试重写 giflib、但仍需持续人工审查"是同一条经验的两面。

可复用技巧 ▸ 给 agent 的任务不要写成"改进这个服务"，而应写成"先产出这个服务的合约文档（输入/输出/边界条件/失败模式），等我确认后再改"。把产出物定义成可评审的中间物，既拿到了知识沉淀，也把风险控制在动手之前。
📎 来源: Five Ways To Use AI Coding Agents to Improve Your Software Architecture · InfoQ

四、让 CI 自己修 CI：agent 从"写完代码"延伸到"护送到合并"

GitHub 展示了 Copilot app 的一个实用形态：打开 PR 之后它仍然留在流程里，自动修复 CI 失败、响应评审意见，一路把代码护送到合并，而不是写完就撒手。对开发者而言，这解决的是"本地通过、CI 挂掉"这一高频上下文切换。

注意 ▸ 让 agent 自动修 CI 失败有一个前置条件：CI 必须给出可行动的失败信息。如果你的流水线只吐出"exit code 1"，agent 只能瞎猜。先把构建与测试的失败输出做成结构化、可定位到文件与断言的格式，再考虑把修复权交给它。
📎 来源: How GitHub Copilot app fixes CI failures automatically · GitHub

五、Rider 2026.2.3 与 Kotlin Multiplatform 的"独立编译"

JetBrains 本周两则工具链更新值得关注。Rider 2026.2.3 把 AI 性能分析接进了 Monitoring 工具窗口：Monitoring 每次运行应用都会采集运行时数据，现在可以直接用 Analyze with AI 基于最近一次会话让 agent 排查瓶颈并定位到代码，同时修复了 Windows 上 AI Agent Setup 组件的问题。另Kotlin 2.5.0-Beta1 引入了可选的 KMP "separate compilation"，解决了两类长期困扰多平台开发的问题：IDE 分析与编译器结论不一致（IDE 比编译器更严格）导致的困惑，以及 commonTest 意外调用到平台 source set 里代码的情况；额外收益是使 common source set 的增量编译成为可能。
