01Google Antigravity 用 93 个子代理、12 小时、20 亿 token 造出能跑 Doom 的操作系统内核

Google DeepMind 的 agentic coding 产品 Antigravity 负责人 Kevin Hou 披露，团队用 93 个 subagent、12 小时、约 20 亿 token、成本不到 1000 美元从零构建了一个能运行 Doom 的 OS 内核。他的核心原则是"把球传给梅西然后让开"——产品应当在模型每次升级时自动变好，而不是靠产品侧打补丁。演讲还梳理了编码工具的演进路径：2022 年补全、2024 年 agent、2025 年 agent 管理器、2026 年 agent 团队，并介绍了 Antigravity 2.0 的三大构建块，包括由 Gemini 3.5 Flash 领队的动态 subagent 协作机制。

实践启示 ▸ "agent 团队 + 动态 subagent"正在成为 2026 年编码代理的主流形态。如果你还在单 agent + 长 prompt 的模式里挣扎，可以开始把任务拆成"领队 + 专员"的分层结构，让每个子代理拿到干净的上下文。
📎 来源: Agents Built an OS Kernel That Runs Doom — Kevin Hou, Google DeepMind · AI Engineer

02Z.ai 发布 GLM-5.2 开放权重：长程编码/代理基准介于 Opus 4.7 与 4.8 之间

Z.ai 负责人 Zixuan Li 发布 GLM-5.2，在最难的长程编码与 agentic 基准上落在 Claude Opus 4.7 与 4.8 之间；其非思考模式甚至超过了开启思考的 GLM-5.1，并在 Artificial Analysis Intelligence Index 上领先其他开放权重模型。Z.ai 明确解释了为何坚持开源接近前沿的模型：让企业和政府能在自有服务器上运行、允许在法律/金融/安全等垂直领域微调、并让客户共同决定模型演进方向。同场还发布了自研编码 harness Z Code，为 GLM-5.2 专门调优。

为什么重要 ▸ 开放权重模型已经逼近闭源前沿，意味着大量"必须走公网 API"的合规/隐私场景现在有了可自托管的可行选项。
📎 来源: GLM-5.2: Open Weights, Near-Frontier Intelligence — Zixuan Li, Z.ai · AI Engineer

03Google 用 AI + 差分模糊测试把 giflib 的 C 代码重写为 Rust

Google 安全团队公开了一套把遗留 C 代码迁移到 Rust 的方法，并以图像处理库 giflib 为试点，目标是消除内存安全类漏洞。流程采用自动化迁移 + differential fuzzing（差分模糊测试）保证行为兼容，项目在维持运行时性能的同时实现了零日漏洞缓解。InfoQ 的结论很关键：AI 翻译出的代码仍需要持续的人工审查，不能当作一次性自动转换。

可复用技巧 ▸ 迁移遗留代码时，"AI 生成 + 差分模糊测试比对旧实现"是能兼顾速度与正确性的组合拳。差分测试同样适用于任何重写/优化场景：把新旧实现喂同样的输入，逐字节比对输出。
📎 来源: Google Rewrites Critical C Dependencies to Rust Using AI and Differential Fuzzing · InfoQ

06Claude Code 新增 claude plugin eval：用测试用例给插件打分

08Google 发布 Dream-RSI：让 coding agent 的"探索策略"自我改进

Google DeepMind 联合马里兰大学、弗吉尼亚大学提交 Dream-RSI 预印本，研究长时间工作的 coding agent 该如何安排一次次尝试——何时另开方向、何时沿现有方案深挖、并行几路、何时停止。方法的关键是：用真实探索留下的历史树做回放，由"策略开发代理"改写探索策略代码，让不同版本在已记录的树上试跑比较，胜出者再进入下一轮真实搜索。在 Lasso 路径求解任务上，Gemini-3.1 Pro 组累计 agent 调用从 550 次降到 317 次，Gemini-3.7 Flash 组从 3200 次降到 1879 次，且最终求解器在六个下游数据集上平均耗时更低。

02深度技术解读

// 两个本周讨论密度最高、且直接影响工程组织方式的话题

深度一 · "软件工厂"是同一个词，五种互相打架的做法

本周 AI Engineer 大会上，"software factory"成了一个被反复争论的标签，几场演讲恰好构成了一次难得的观点对撞，值得完整读完再决定自己站哪边。

  • Warp（Zach Lloyd）的"工厂工程"论：他认为软件工程正在变成"工厂工程"，每个严肃项目最终都会像今天标配 CI/CD 一样标配一条软件工厂流水线。Warp 在闭源五年后开源，拿到 6 万多 Star、80 万+ 活跃开发者；理由是当软件变得廉价且易被克隆时，"好产品"不再足够，公开构建才能长出生态，而自动化已经能消化嘈杂 issue 和粗制 PR 的常规痛点。工厂流水线被他拆为：输入 → 分诊 → 产品/技术规格 → 实现 → 评审 → 验证 → 监控。
  • Conductor（Charlie Holtz）的"管弦乐团"论：他直言"我其实挺讨厌 software factory 这个词"。总结顶尖构建者的共性：贴近前沿但别试图战胜市场（凡是人人可用的工作流，大厂会直接内置）；划出"无 slop 区域"（迁移、文档、skill 文件必须人工仔细评审）；把 Slack、bug 报告、会议纪要全部灌进一个 agent 可查询的数据库；给 agent 自由活动空间，用云沙箱让它们在你合上笔记本后继续跑。
  • WorkOS（Ryan Cooke）的"别自欺"论：标准软件工厂把 agent 塞进沙箱、prompt 一下、合并 PR，结果和工程师在自己笔记本上跑 Claude Code 难以区分。他反对用 PR 数或 AI 代码行数当指标，唯一有效的度量是是否真的给客户交付了更多。WorkOS 的做法是把工程流程本身内建进工厂——agent TARS 常驻 Slack/Linear/GitHub，用 webhook 自己认领下一张工单；PM agent 起草产品文档并把已批准工作拆成工单，解决"空白页问题"。
  • Factory（Tereza Tížková）的"全生命周期"论：她给企业（EY、Adobe）跑工厂，定义为"整个软件生命周期自主运行"——收集信号、排优先级、构建、验证、改进。三条原则：保持 agnostic（适配团队原本工作方式，自动路由模型，保守基准下约省 25% 成本）；保持 autonomous（Mission 可运行数小时甚至数周，真实客户案例跑了 16 小时）；worker agent 串行而非蜂群，每个都从干净上下文开始，验证者只检查不是自己写的代码。
  • Warp（Suraj Gupta）的"工厂如何自我改进"论：三条可落地做法——自我改进的 skills（外层 agent 观察分诊 agent 的运行与反馈，开 PR 更新其 skill，改动进 Git 并有人工评审）；持久记忆（版本化、可追溯的事实库，Sentry agent 不必重新发现已找到的根因，兼容 Claude Code/Codex 等任意 harness）；模型路由（别用 Opus 的价格去做分诊或简单 CI 修复）。
读后判断 ▸ 五场演讲的分歧点其实很清晰：要不要把"判断力"也外包给 agent。WorkOS 和 Conductor 都强调人工评审与"无 slop 区域"，Factory 用"验证者不审自己代码"来制衡，而纯 PR 数派最容易被自己的指标骗。选型时先问自己：我的验证环节是不是独立于生成环节？
📎 来源: Warp — Factory Engineering · Conductor — Orchestras, Not Factories · WorkOS — No, That's Not a Software Factory · Factory — What It Actually Takes · Warp — How Factories Improve Themselves · AI Engineer

深度二 · Context 管理：从 Pi Agent 的构建原则，到"把判断力写进 repo"

先厘清概念。一篇 14000+ 字的长文以 Pi Agent 为例拆解了 context 管理：作者把 Prompt 理解为相对静态的指令设计，Context 理解为 Agent 运行过程中动态形成的信息环境——Prompt 提前定义"应该怎么做"，Context 决定模型"此刻基于哪些信息来做"。从单次 LLM 调用看，Context 通常由五部分构成：System Prompt、Skill、Tool Result、Message 等，而 agent 的真正难点在于这些信息如何被组织、并在执行过程中逐步收敛成模型实际看到的那一份视野。这也顺带回答了"Skill 到底算 Prompt 还是 Context"这个热门争论。

再看判断力。Reddit 高级 Android 工程师 Andrew Orobator 的观点恰好与之互补：换更强的模型只得到略好的答案，抽掉测试、门禁和评审，一切立刻崩坏——模型从来不是瓶颈，模型周边的判断力才是。人类可以隐式吸收判断力，agent 却需要被显式写出来。他的落地方式包括：把 Skills 当作"机构判断力的可执行形式"；用 work log 让一个全新的 agent 从 9 个里程碑中的第 7 个无缝接手（该演讲本身就是这样构建的）；用 Persona 借用安全评审或设计师的视角；用验证阶梯（verification ladder）控制放行条件。他的 feature-flag 清理 agent 在绿 CI 的 PR 上做到了 7 发 7 中，每个成本 1.26 美元。

实践启示 ▸ 把两者合起来看，可落地的顺序是：先用最小可运行 context（别塞模板，给目标和规范）→ 再把团队隐性判断固化成 skills / personas / work logs → 最后用独立的验证阶梯卡住放行。这套组合正对应本周另一个观点：给模型"目标、规范"而不是"模板"，让它按自己熟悉的方式发挥，效果往往更好。
📎 来源: 到底什么是 Context？万字长文谈 Pi Agent context 管理 · Scale the Judgment, Not the Model — Andrew Orobator, Reddit · 大模型智能 / AI Engineer

04实践指南

// 可以直接抄进自己工作流的做法

① 按官方建议调优 Opus 5.5 + Claude Code

Anthropic 官方给出的几条建议，几乎都是"做减法"：

  1. 给出清晰的"完成"定义，明确期望实现并验证的行为；
  2. 删掉"认真思考"这类通用指令——Opus 5.5 使用自适应思考与可配置 effort，泛化指令只会干扰它；
  3. 用 CLAUDE.md 指示 Claude Code 完成常规工作、只在遇到真实阻塞时上报；
  4. 长任务维护一份 tasks.md，让进度、已完成的检查项与阻塞项保持可读。
经验值 ▸ 社区建议日常默认用 Opus 5.5 Medium：99% 的场景没必要开 High，effort 档位带来的收益递减明显。
📎 来源: Opus 5.5 OFFICIAL Super Mode · AICodeKing · Peter Yang

② 用 /checkup prompt-audit 清理你的 CLAUDE.md 与技能

随着模型换代，旧 prompt 里的"拐杖指令"会变成阻力。该命令会检查你的 CLAUDE.md、技能与 Agent，找出当前模型已不再需要的指令、以及阻碍其发挥能力的提示内容，并给出修复建议。配合 Claude Code 新的 plugin eval（有/无插件对照打分），可以形成一套"定期体检"机制。

📎 来源: 小互 (@imxiaohu) · Ado (@adocomplete)

③ 让 agent 干长活：串行 worker + 独立验证者 + 模型路由

综合 Factory 与 Warp 两个团队的一手经验，运行长周期 agent 任务时：worker agent 串行执行而非蜂群（每个从干净上下文起步，避免上下文污染）；验证者只检查不是自己写的代码；在分诊、简单 CI 修复等环节路由到更便宜的模型，别用 Opus 的价格做所有事（Factory 保守基准下约省 25% 成本）；用持久记忆避免 agent 重新发现已知根因。

📎 来源: Factory — What It Actually Takes · Warp — How Factories Improve Themselves · AI Engineer

④ 重构"屎山"的新思路：先蒸馏成功能文档，再原地重写

社区里流传的一个务实做法引发大量共鸣：与其硬啃遗留代码做增量重构，不如把源项目库蒸馏成一份功能文档，然后用最新模型原地重写。这与本周 Warp 讨论的"迁移属于必须人工细审的无 slop 区域"并不矛盾——重写省力，但验证（差分测试、回归用例）仍需人工把关。

📎 来源: 数字生命卡兹克 (@Khazix0918)

⑤ 在 Windows 上用 WSL 跑编码 agent（GitHub Copilot 官方演示）

GitHub 展示了如何把 Copilot 应用连接到 WSL、直接在 Ubuntu 内运行编码 agent：用 worktree 并行处理多个 feature 请求、在应用内置浏览器里预览改动、并验证代码 diff，全程不离开应用。前置条件与资源（Agent automation controls、GitHub Agentic Workflows 文档）在视频说明中给出。

📎 来源: How to use GitHub Copilot with WSL on Windows · GitHub

⑥ 重新审视"人机协作"的定位

一篇被广泛转发的分析给热闹的 agent 叙事泼了盆冷水：国际象棋的"半人马"时期之所以成立，是因为人机组合在棋力上确实超越了单独的人和 AI；而在软件工程里，AI 辅助的工程师并不真的"更擅长编程"，只是产出更快——人机协作的价值在 alignment（对齐与把关），而非 capability（能力叠加）。把这个框架记在心里，有助于你判断哪些环节该交出去、哪些必须自己守住。
