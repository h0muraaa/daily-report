同一批开源模型，换 Harness 成绩翻倍：28,849 次实验的 Harness Leaderboard

开发者 Joël Niklaus 做了一件很“烧钱但有用”的事：固定模型、Provider 和 reasoning effort，只更换 coding-agent Harness，在 Terminal-Bench 2.1 和 DeepSWE 上跑了 28,849 次试验，推理成本约 4,746 美元。结论非常直白——在 GLM-5.3-Flash、DeepSeek-V4.1-Flash、Flint 三个开源模型上取平均，仅靠 bash 的 mini-swe-agent 能解出 51.4% 的任务，而 openclaw 只有 27.3%，差距接近一倍。这说明对开源模型来说，“选对脚手架”带来的收益可能比换模型更大，评估模型能力时不能脱离 Harness 谈分数。

Browser Agent 省 token 技巧：别截图找按钮，直接读 Chrome 无障碍树

browser-use 分享了一个很实用的优化：与其不断截图让视觉模型定位按钮，不如调用 CDP 的 Accessibility.getFullAXTree，拿到每个元素的 role、name 和 node id，过滤出链接/按钮/输入框，再用 DOM.getBoxModel 算出中心点执行点击。在 Hacker News 首页上的实测是 1,764 个节点里筛出 227 个可点击元素，视觉 token 消耗为零。对于 DOM 结构清晰的站点，这条路比视觉方案更快、更便宜，也更容易调试。

02深度技术解读// 2 个话题

话题一：Harness 正在成为比模型更关键的变量

从“链式提示词”到“可执行代码”，再到可量化的 Harness 排行榜

过去一年，围绕大模型搭出来的那层“脚手架”经历了三代演进：最早是链式编排——把提示词串成一串，上一步输出喂给下一步，LangChain 式的 RAG 三步走是典型代表；随后是图式工作流，用节点和边表达分支、路由和重试；现在则转向代码化 Harness，也就是用可执行代码去约束、校验、观测模型输出，而不是靠自然语言描述流程。

为什么这个变化重要

因为模型本身是概率性的，Harness 的职责就是把它“压”成确定性系统的一部分。AI 前线总结的三代范式中，一个共识是：对模型输出要做校验，并且选用能满足可靠性、速度和成本要求的最简单的方案——不是越复杂的图越好，很多场景一条带校验的链就够了。

现在有了量化证据

刚发布的 Harness Leaderboard 把这件事从经验变成了数据。实验设计很干净：只变 Harness，模型（GLM-5.3-Flash / DeepSeek-V4.1-Flash / Flint）、Provider、reasoning effort 全部固定，每个任务跑三次取结果。28,849 次试验、约 4,746 美元推理成本之后，得到的结论是：

  • mini-swe-agent（仅靠 bash 的最小化 Agent）平均解决 51.4% 任务；
  • openclaw 只有 27.3%——同样的模型，成绩相差接近 2 倍。

对一线开发的直接含义

第一，评估模型时不能脱离 Harness 谈 benchmark 分数，报告里的“某模型能解 X%”往往只对特定的脚手架成立。第二，优化方向上，与其升级模型，不如先把你自己的 Agent 循环打磨好——工具描述、错误回传、上下文裁剪、重试策略，这些构成的边际收益可能更大。第三，这也是 Baseten 那句 “Keep the harness. Choose the model.” 的底层逻辑：Harness 是可复用资产，模型是可替换件。

# 一个最小化 harness 的骨架：循环 + 校验 + 可观测
while not done:
    action = model.step(state, tools)          # 模型只负责决策
    result = execute(action)                     # 代码负责执行
    if not validate(result):                   # 代码负责校验
        state.push_error(result.error)          # 错误回传，而不是静默重试
    record_trace(state, action, result)       # Agent 自己能读的观测数据

话题二：Agent 记忆的正确打开方式——记录、整理、检索三件套

Anthropic 的 dreaming 机制，以及为什么“多存”不等于“记得住”

几乎所有做 Agent 的团队都会撞上同一个问题：会话一长，历史记录就沦为噪音。Anthropic 公开的记忆架构给出了一个分层的答案，并且用实验数据支撑了几个反直觉的结论。

记忆由四个环节组成

  • 保留原始记录：用于事后追溯证据，不做过早压缩；
  • 任务中写笔记：把目标、计划和已验证的结论写下来；
  • 后台整理（dreaming）：离线回看记录，纠错、去重、补链接，必要时建知识库；
  • 按需检索：读取时只预加载少量高价值内容，其余现查。

实验里的三个关键数字

在 CL-Bench 数据库任务中，每道题都开新会话、只保留记忆目录，较强模型会自动保存“经过验证的规则和依据”，而不仅仅是记录错题；实验还发现，限定“只记失败”反而削弱收益。在约 35 万份文件、4.2 亿 token、25 个评测问题的内部语料上，纯搜索的评分标准覆盖率是 53%；知识库结合搜索后，随整理轮次增加从 54% 提升到 61%，并且每题少用约一部分 token（整理成本需要计入总账）。

落到工程上怎么用

不要把“记忆”等同于“把聊天记录塞进上下文”。更划算的结构是：原始日志落盘可查，任务态写结构化笔记，离线跑一个整理任务，检索层做渐进披露（progressive disclosure）——新会话启动时只加载一个很小的索引。开源实现里，Claude-Mem 就是用 lifecycle hooks + 本地 worker + observer model 做这套流程，并用渐进披露索引把新会话的启动上下文压到很小。

另一个相关的工程点是：Agent 会“悄悄绕过坏掉的指令”而不告诉你。Warp 的做法是把每次对话连同工具调用和输出收集到一处，用 LLM-as-judge 按冗余测试、啰嗦度、效率打分，再跑一个每日 Agent 找失败模式并自动提 PR 修 skills 和 config。这本质上是把记忆整理从“被动存储”变成了“主动的自检回路”。

📎 来源：Anthropic 工程博客 · meng shao 研究解读 · AICodeKing（Claude-Mem 实测） · AI Engineer / Warp

03工具推荐// 7 个

Kiri Rust · Docker 平替

用 Rust 写的轻量容器运行时，覆盖 macOS / Windows / Linux，兼容现有 docker CLI、Compose 和 buildx，把容器跑在一个小型 Linux VM 里。定位是 Docker Desktop / OrbStack 的轻量替代，适合嫌 Docker Desktop 重、又不想换工作流的开发者。

📎 来源：Geek (@geekbb) · github.com/libracoder/kiri
Rune Rust · 跨平台 UI

来自 OpenCode 团队的 UI 库，用 wgpu 自己 GPU 绘制，颜值在线。最值得关注的是 headless 模式：不打开界面也能运行，并提供截图模式和元素树，专门方便 Agent 调试和观察 UI。同期冒出的还有 NSH（Rust + 原生控件）、MyGo（Go，Web/原生双模式）、BUI（C + 移植 Blender 控件），跨平台 UI 方案明显在百花齐放。

📎 来源：Viking (@vikingmute)
Craft Anything 逆向研究 · MCP

由开源过 Photoshop / Office 替代品的团队放出的“先研究、再构建”工具：先收集目标产品的外观、布局和行为，再交给编码 Agent 构建自己的版本，网页检查会覆盖三种屏幕宽度以发现差异。内置 300+ 工具，同时提供 CLI 和 MCP 接口，可作为其他 Agent 的研究工具箱。默认“净室模式”只用外部可见信息并设工具白名单，“深度模式”才分析代码与脚本——注意技术分界不等于解决版权授权问题。

📎 来源：meng shao (@shao__meng)
Bumpy TypeScript · Monorepo 版本管理

MIT 许可的版本管理与 changelog 工具，跟随 changesets 的 markdown bump 文件工作流，额外支持 workspace / catalog 协议、自定义发布命令和基于分支的预发布。Changesets v3（2026 年 8 月发布）已补上不少历史缺口，但两者仍有差异，迁移前值得对比。

📎 来源：InfoQ
pg_vectorsearch PostgreSQL · 向量检索

开源的 Postgres 向量检索扩展，用 PRISM 索引（数据分区 + 压缩）替代 pgvector 的 HNSW 图索引，目标是降低内存占用和索引构建时间。目前是 alpha，适合在测试环境评估召回与资源开销的权衡。

📎 来源：InfoQ
Vercel json-render AI SDK · 生成式 UI

把 AI SDK + Chat SDK 与 json-render 组合，可以从 LLM 直接产出 UI，并落到 Slack、Teams 这类平台上，实现“对话式 Agent 的生成式界面”。Guillermo Rauch 认为这会成为人机交互（HAI）的主流形态，适合做内部工具和 IM 场景的团队先试水。

📎 来源：Guillermo Rauch (@rauchg) · AI SDK
Claude Code · Concise 输出风格 配置技巧

Addy Osmani 提示：把 Claude Code 的输出风格切到 Concise，可以得到更短、更直给的结果。开启方式是在 /config → Output style 中切换，或直接在 settings.json 里写 "outputStyle": "Concise"；需要细节时仍然可以追问。对每天几十次交互的开发者，这是零成本的 token 与注意力节省。

04实践指南// 6 条可落地

✓把“AI 代码放量”当成系统性风险，用分层防御而不是 review 兜底

Grab 的做法值得直接借鉴：在生命周期各阶段分别做预防（提交前检查）、检测（发布前发现异常）和收敛（线上快速止血）。AI 生成的代码让每次发布的变更密度显著上升，仅靠人工 review 无法线性扩展——必须把防线前移并自动化。

📎 参考：InfoQ

✓Agent 安全不能只查“有没有权限”，还要查“为什么执行”

Uber 的内部体系 Secure AI 提供了一个清晰的三层模型：上线前用 registry 登记用途/负责人/允许行为/风险等级，并用静态分析对照“申报用途 vs 实际能力”；运行时检查具体动作是否符合用户请求、是否来自不可信内容，把高权限动作追溯到用户的实际请求；上线后用历史交互回放测试新规则并做红队。为控制延迟，Uber 用本地小型专用模型并行执行多项检查。核心难点不是检测，而是规则取舍。

📎 参考：meng shao 解读 @UberEng

✓高流量、任务明确的场景，先算小模型的账

Airbnb 在内容审核任务上微调了约 20 亿有效参数的 Gemma4-E2B，F1 从 0.563 提升到 0.902，接近最好的专有模型；延迟中位数 35ms、p99 约 85ms，而前沿 API 低思考模式下中位延迟约 900ms，高流量下自托管成本约为前沿 API 的 1%。成立的前提很硬：任务边界清晰、有数十万条领域样本、调用量大。反过来，如果任务模糊或流量小，微调不划算。

📎 参考：meng shao 解读 @AirbnbEng

✓Agent 团队不等于 Agent 越多越好：把额外 worker 花在“卡住”的阶段

Cohere 在 ProgramBench 和 Commit0 上做了数百次实验：让 lead 拆分任务、worker 并行探索与验证，团队在长任务上确实能超过单 Agent，但成本会翻数倍。经验是——只在任务卡住的那个阶段委派，让 lead 等待 worker 而不是抢跑，并用“强 lead + 便宜 worker 做规划”组合，能以约低 70% 的成本接近全前沿模型团队的水平。

📎 参考：AI Engineer / Cohere

✓技术文档不要整篇重写，先定位“易失效断言”再逐条核对

一个很实用的文档 Agent 模式：先把 PDF 转成保留结构的 Markdown，抽取版本号、API 路径、配置项、弃用提示和依赖等易过期信息并去重，再把每条断言连同上下文交给带实时网页检索的决策接口，输出“仍有效 / 已过时 / 需复核”并附引用来源；证据不足时归入“需复核”而不是强行判定。用一份旧 OpenAI API 文档实测，抽出 12 条断言：7 条过时、1 条仍有效、4 条需复核。

📎 参考：meng shao 分享 @Sumanth_077

✓AI 写代码越多，工程基本功越重要——但重点不是框架 API

GitHub 的数据给出了一个提醒：2026 年 10 月单周提交量超过 12 亿次，同比增长 400%以上；但 Faros AI 的研究发现，团队从低 AI 使用率转向高使用率时，PR 在 review 阶段停留的时间长了 441%。也就是说，瓶颈已经从“写”转移到“理解、审查和验证”。Matt Pocock 那场《Why Software Fundamentals Still Matter》的落点也类似：真正更值钱的是设计原则与实践，因为坏代码更容易破坏整个系统，而不是记住某个框架的内部实现。

📎 参考：The GitHub Blog · Viking 分享 Matt Pocock 演讲
