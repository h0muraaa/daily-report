#02 LLM 内核论文

字节联合普林斯顿 / 斯坦福 / 伯克利：DeepSeek-V4 分块 KV Cache 存在"周期性盲区"

论文《Periodic Weak Spots: Phase Sensitivity from Chunked KV-Cache Compression》（arXiv 2609.36322）指出，分块 KV Cache 压缩把长上下文切块处理，导致"位置决定命运"：当关键信息恰好落在切块交界的"信息盲区"，模型会直接无视它。最直观的证据来自让 DeepSeek-V4-Flash-Base 补全一段 FP8 推理内核代码——正确答案是 8，仅仅在注释里逐个添加装饰性等号 =，输出就在 8 与 32 之间翻转，且与等号数量 mod 4 强相关（余数 0/1 时错误率高达 71.3%）。在 128K 长上下文检索实验里，目标信息所处 Token 位置不同，准确率可暴跌约 40%。

这不是 DeepSeek 独有——任何采用分块压缩 / 稀疏化注意力的模型（论文点名 Llama 3 系列）都可能有类似短板。做长文档、长代码库检索的团队，务必把"位置不变性"纳入测试，而不是默认检索结果稳定。

#03 Agent编排

Claude Managed Agents 上线"动态工作流"：单次最多调度 1000 个 Agent

Anthropic 把动态工作流（dynamic workflows）带进面向开发者的托管 Agent 平台：主智能体先写一段程序把任务拆成阶段，交给一批 Agent 并行执行，再由服务端按程序在后台传递上下文与结果汇总。单次运行最多累计启动 1000 个 Agent，同时工作线程上限 64。官方给出的对照数据很有说服力：在一个 11.6 万行代码库里埋 70 个 bug，单 Agent 跑 3 次分别找到 14 / 15 / 27 个、波动很大；用工作流跑 3 次每次都找到 66 个。适合的大批量可切分任务包括审计大代码库、批量迁移、读几百份合同。

用法是在 Agent 配置里把 multiagent 类型设为 multiagent_20261001（该类型下工作流默认开启）；在 Claude Code 里可直接跑 /claude-api managed-agents-onboard bug-hunter 上手。

深度技术解读

解读一：LLM 推理的"读"与"写"——为什么所有优化都从这两个阶段出发

Deep Dive

今天头条里的 DeepSeek-V4"周期性盲区"（热榜 #02），本质是 KV Cache 压缩引入的副作用。要理解它为什么危险，得先掌握一个比任何具体优化技巧都更基础的心智模型：一次推理由两种工作负载组成，瓶颈完全不同。

  • Prefill（预填充）：并行读入整个 prompt，逐层计算并写入 KV 缓存，产出第一个 token。整个序列并行、矩阵乘法饱满，瓶颈在算力（FLOPS），优化方向是更强的 GPU 与更好的 kernel。
  • Decode（解码）：自回归循环，一次只算一个 token——读权重、读全部历史 KV、算出下一个 token、追加新 KV。单 token 逐次访存，瓶颈在内存带宽，优化方向是更快的显存与更小的权重 / KV。

关键差异是算术强度（每个字节能做多少次浮点运算）。直观理解：prefill 像"一次搬完全部货物，路不是问题、装卸能力才是问题"；decode 像"每次只搬一件，但每次都要跑全程，路的通行速度决定一切"。这也解释了两个常见现象：批处理会改变瓶颈——把多条请求拼成 batch 后权重只需读一次、计算量翻 N 倍，瓶颈从带宽滑向算力，这正是吞吐与时延的取舍；以及为什么 llama bench 要把 pp128（prefill） 和 tg64（decode） 分开测——两个数字受完全不同的因素支配。

回到那个 Bug：为了把长文本成本打下来，业界用分块压缩 / 稀疏化来减小 KV Cache，于是"读历史 KV"变便宜了，但也切出了"信息盲区"。KV Cache 不只是性能手段，它同时是模型正确性的一部分。

实践建议：调推理性能时，先问"我在优化 prefill 还是 decode"——量化、批处理、投机解码针对的瓶颈各不相同，混为一谈就会优化错方向；采用压缩 / 稀疏 KV 的模型时，把"长上下文位置不变性"写进你的评测集。

解读二：从 RAG 失败到 91% 准确率——Uber 法务 Agent 的四次架构演进

Deep Dive

Uber 每年谈判数千份合同，法务审核是交易与供应商入驻的瓶颈。团队发现这份看似高度专业的工作里藏着大量结构性模式（相似条款反复出现、红线修改可复用、法律立场长期稳定），与代码审查同构、只是知识壁垒更高。项目最终达到平均审核时间下降 20%+、AI 生成决策准确率 91%，并拿下 2026 年 ALM Legalweek"年度最具创新力法务部"奖。它的价值在于把一条经典的 "从 RAG 到 Agent" 演进路径完整记录下来：

  • 第 1 版 · 朴素 RAG——失败：把谈判 playbook 灌进 RAG 管道，暴露三个典型问题：做嵌入的"关键句"与实际要检索的内容粒度错位，语义检索失准；生成注释的语气要么过度防御要么过度让步（而法律文书的语气本身就是立场）；没见过的场景直接失效。核心教训：文档不等于决策数据，playbook 里的静态知识与律师动态偏好之间有巨大鸿沟。
  • 第 2 版 · 反馈闭环——转折点：放弃"从文档学"，改为"从决策学"——捕获每一次真实谈判的完整轨迹（对方原始措辞 → 律师的红线 → 期望动作）。
  • 第 3、4 版：围绕"在律师工作的地方交付"（做成 Microsoft Word 插件而非新工具）、"增强而非替代"（AI 只给 accept / reject / modify + 理由注释，决策权留给人）持续迭代。

同一天的另一条资讯从侧面印证了"上下文质量 > 检索量"：Unblocked 工程团队指出，向量检索答不了"我上周合了哪些 PR"这类问题，编码 Agent 需要的不止是代码搜索，还有 PR、Slack 线程与事故历史这类解释"代码为什么长这样"的上下文——他们用一个关系型上下文引擎替代纯向量检索，某些 Claude 会话的成本下降约 50%，还有一次据此把一次回归定位到了"切换模型"这个动作上。

共同结论：RAG 的天花板往往不在检索算法，而在"你检的东西对不对、够不够接近真实决策"。把真实决策轨迹沉淀成可检索的数据，再让 Agent 在其上做判断，比堆文档、堆向量库更有效。

配置Claude Code

① 约束 Claude Code 的自动压缩长度到 300–400K，并删掉过时的禁用项

宝玉给出一条具体的 Claude Code 调优建议：用 /autocompact 400k 约束自动压缩的上下文长度（他本人设 300K，认为足够），400K 左右是比较合理的值。同时提醒——如果你此前按旧建议在 ~/.claude/settings.json 里设过 CLAUDE_CODE_DISABLE_1M_CONTEXT，现在应该删掉，否则上下文最多只能到 200K。

可落地：把 autocompact 设到略低于上限的"甜点位"，既避免过早压缩丢上下文，又防止上下文膨胀拖慢速度、烧 token。

性能迁移

② 给 Node 服务降本：把进程级集群换成 worker threads，再调 GC 与负载均衡

Booking.com 的迁移是一条可复制的降本路线：把最大的 React SSR 服务从 PM2 基于进程的集群方案迁移到 Platformatic 的 Watt + worker threads，再配合负载均衡策略与 V8 GC 调参，最终把成本压低 38%。进程级集群的内存与启动开销更大，worker threads 在同一进程内共享内存、切换更快，适合 I/O 与渲染混合的 SSR 负载。

可落地：先量化当前方案的进程数 / 内存占用 / GC 停顿，再评估 worker threads 的改造成本——大型 Node 服务的降本很多时候来自运行时模型，而不只是加机器。

安全CI

③ 在 CI 里固定 MCP 工具 Manifest，用差异评审替代人工放行

把 MCP 用到生产的关键是把安全做成可自动化的门控，而不是靠网关或人工审批兜底：在注册时对工具 Manifest 固定（pin），CI 里对 Manifest 做基于差异的评审——一旦 schema 发生变化就报警并要求复核，从而防住批准之后的"rug-pull"式篡改；对工具执行做隔离、对出站流量加出口控制与作用域令牌，并建立行为基线。

可落地：MCP 服务器生态良莠不齐（扫描显示 38% 关键端点无认证），把"schema 变了没有"变成一条会自动失败的 CI 检查，是最省人力的第一道防线。

工作流Agent

④ 把开发变成快速循环：定义问题 → 原型 → 实现 → 验证，重点押在两头

宝玉把自己的开发方法论总结成一个"转得很快的 loop"：每个功能开发、bug 修复的每个环节，无论 Agent 还是他自己都能很快拿到反馈，loop 转得越快效率越高。具体顺序是——先写技术方案文档并反复定稿；再做高保真原型（原型实现成本低、改起来容易，Agent 能快速拿到反馈，避免直接在最终代码上返工）；方案与 UI 定了才去实现代码；最后验证。当 loop 跑起来后可并行多个任务，因为大部分时间 Agent 在生成和验证，人应把重点放在定义问题和验证上；他坦言当前瓶颈是设备和 Token 不够，下一步要更多在云端开任务。对于以 UI 为主的改动，甚至可以不写技术方案，直接从原型起步，用 Agent 内置浏览器的"标记"工具在要改的地方标注意见。

可落地：把"定义问题"和"验证"当成你不可替代的两端，中间的编码 / 原型尽量交给 Agent；用高保真原型压低返工成本。

验收Agent

⑤ 重新定义"任务完成"：让 Agent 自己打开软件验收，而不止是测试变绿

OpenAI 电脑操作 Agent 产品与工程负责人 Ari Weinstein 提出：过去一项开发任务常在 PR 合并时结束——代码能跑、测试变绿就算交付；现在 Agent 写完功能还要自己打开软件，像用户一样点击页面、填表、检查结果：按钮没反应就查原因、页面报错就回代码改。他举例，一个原本需要自己操作 2 小时的任务，Computer Use 用了约 15 分钟；代码生成、软件操作、排错与功能验收正被接进同一条工作流。

可落地：在定义"完成"时，除了单测 / 集成测试，加上一条"Agent 能端到端走通用户路径"的验收——尤其适合 UI 与交互类改动。

训练RL

⑥ 小模型也能打赢大模型：用不到 $500 的 RL 训练，4B 在金融问答上超过 235B

Snorkel AI 与 UC Berkeley Sky Computing Lab 做了一件很有启发的事：基于 SEC 10-K 财报数据构建了专家验证的金融问答数据集 FinQA，发现即使前沿模型也会编造表结构、把上下文撑爆、重复失败的策略；随后用开源 rLLM 框架 + 简单的通过 / 失败奖励做强化学习，花不到 500 美元训练 Qwen3 4B，在真实金融问题上达到约 60%，超过 235B 大模型的 51%，且技能能迁移到更难的多表问答而不损通用能力。

可落地：领域任务上，与其堆大模型的 prompt，不如构建一份专家验证的小数据集 + 简单奖励信号做 RL 后训练——成本可控、效果往往更集中。
