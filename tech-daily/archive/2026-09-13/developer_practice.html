01阿里开源 Open Code Review：把「AI 代码审查」做成可复现的工程流水线

阿里巴巴把内部打磨两年的 AI 代码审查助手开源了，项目 alibaba/open-code-review 是一个用 Go 编写的 CLI 工具（命令名 ocr），读取 Git diff，让 LLM Agent 带着专用工具去审查代码，并输出行级精确定位的审查意见——定位很明确，它不是通用 coding agent，而是一个专门做 review 的 harness，支持 BYOK，也支持 Delegation Mode（自己不需要 key，只负责选文件、匹配规则、准备 diff，把审查交给别的 agent）。

这件事值得关注的原因在于它正面回应了通用 Agent 做 code review 的三大顽疾：大变更集下 Agent「偷懒」只挑部分文件看（漏审）、报出的问题和实际代码行对不上（位置漂移）、纯自然语言驱动导致质量随 prompt 微调而波动。项目把根因诊断为「纯语言驱动的架构对审查过程缺少硬约束」，因此用确定性工程把流程切成多阶段流水线来兜底。

02GitHub Copilot 的 Project HydraFusion：运行时多模型路由

GitHub 为 Copilot 推出研究预览项目 HydraFusion，核心思路是在运行时动态编排多个厂商的模型，根据任务复杂度即时组装执行计划，而不是把所有请求都丢给同一个模型。系统内置三种执行模式（execution patterns），按任务难度分流。

03Shopify Gisting：把系统提示词压缩成「主旨词元」，TTFT 直降 84ms

Shopify 工程团队提出 Gisting 技术，把冗长的 LLM 提示词压缩为精简的 Gist 词元集合，从而提升吞吐、降低推理开销，且无需修改模型核心权重。方法源自 2022 年的一篇论文，用两步流程（教师阶段产出对数概率 → 学生阶段用 Gist 词元对齐）训练出压缩嵌入向量。

实测把 Sidekick GraphQL 智能体的系统提示词从约 6000 token 压到 1500 token（4:1 压缩），且没有牺牲预测质量。在 350 RPM 负载下：TTFT 中位数 438ms → 354ms，端到端延迟中位数 6.8s → 4.2s，吞吐 20.2 → 23.4 QPS，最终直接减少了分配的 GPU 数量。

04Cloudflare Cache Transcoding：用 Zstandard 换 petabytes 级缓存容量

05PyroDash：让小模型自己决定何时「呼叫」大模型，成本降到 1/30

火思动力开源的 PyroDash 给出一个反直觉的答案：不做简单的模型路由，而是在 token 级别让小模型自主决定何时向大模型求助。论文题为 PyroDash: Cost-Efficient Token-Level Small-Large Language Model Collaborative Inference（arXiv:2607.20327）。

在五个数学推理基准上：偏省成本时，小模型平均每 100 道题才叫一次大模型，估算总成本从纯大模型的 $49.36 降到 $1.78（不到 1/30），准确率几乎不掉；偏准确率时，小 + 大组合平均准确率 64.04%，反而比纯大模型的 57.68% 高 6.36 个百分点，成本还低两成。准确率均高于 RouteLLM、GlimpRouter 等基线。

深度技术解读

一、为什么「确定性工程 × Agent 混合」是 AI Code Review 的正确答案

阿里 Open Code Review 的设计几乎可以当作一份「如何让 LLM 稳定干工程活」的教科书案例。它的多阶段流水线把一件模糊的任务拆成了六个职责单一、prompt 独立且短的阶段：

Grouping → 按语义把变更文件聚成审查组（接口 / 实现、中英文 properties 等打包），每组 ≤ 10 文件
Plan → 规划风险点与工具调用策略
Main Review → Agent 挂载工具实际审查，产出意见
Re-location → 独立定位模块，从 diff 反向提取意见对应的确切代码片段 ← 位置不漂移
Review Filter → 事实核查，只删除被 diff 证实有误的意见
Memory Compression → 超长会话压缩对话历史，配合 session 复用

三个值得抄走的设计决策

  • 用「独立阶段」对抗「偷懒」：Grouping 强制每组最多 10 个文件，等于给 Agent 的注意力划了上限，从结构上杜绝大 diff 下的漏审，而不是靠 prompt 求它认真。
  • 把定位从生成里剥离：Re-location 是一个独立的、不产生新内容的模块，只负责把自然语言意见映射回 diff 行。这直接消灭了「报错行号对不上」这一通用 Agent 的老毛病——位置精度由独立模块保证，而不是由生成模型「记得住行号」保证。
  • 审查过滤器的偏置声明：Review Filter 的 prompt 里有一段很精彩的取舍原则——「保留错误意见只浪费审阅者几秒钟，删掉正确意见则永远无人知晓」，因此采取「宁可漏删，不可误删」的保守策略。这种把业务风险量化写进 prompt 的写法，比笼统地要求「准确」有效得多。

实践建议

如果你在团队里做 AI 审查 / 巡检类 agent，可以照搬这条原则：凡是有「客观正确答案」的环节（定位、去重、引用核对），都不要交给生成模型自由发挥，而是拆成独立的、可验证的模块。生成模型只负责它擅长的部分——提出问题、给判断依据。

二、把 LLM 推理指标算清楚：TTFT / ITL / e2e，以及 Prefill、KV Cache、Prefix Caching

NVIDIA NIM LLMs Benchmarking 2.0.0 围绕 prefill / decode 两阶段执行模型构建了一整套指标体系，值得每个要调 LLM 服务端性能的人过一遍。

延迟类指标的三个层次

  • TTFT（Time to First Token）：从提交请求到收到第一个输出 token，包含排队 + prefill 计算 + 网络延迟。主要由 prefill 阶段决定——注意力必须处理完整个输入序列、建好 KV cache 才能开始生成，所以输入越长 TTFT 越长，这是平方复杂度注意力的固有代价。测量细节：响应为空时 TTFT 无意义，AIPerf 会忽略空的首响应。
  • e2e Request Latency = TTFT + Generation_time，涵盖排队、批处理调度、网络在内的全部时间。一个容易忽略的成本点：流式模式下 de-tokenization（解码回文本）会随 partial result 反复执行，而 TTFT 也包含 tokenization，文本处理开销其实藏在端到端时间里。
  • ITL（Inter-Token Latency）：衡量 decode 阶段逐 token 的输出节奏，是「体感流畅度」的直接来源。

生产环境最关键的一条洞察：一个请求的 prefill 可以与其他请求的 decode 阶段重叠执行（continuous batching），因此并发场景下 TTFT 的表现和单请求串行测试差别很大——用单流压测出来的 TTFT 去估容量，会严重失真。

三个必须分清的缓存概念

文档 + “帮我看看，有哪些风险？” → A
文档 + “预算减半，帮我调整一下。” → B
修改后文档 + “再看看，预算够不够？” → C
  • Prefill：处理 input（把整段 prompt 过一遍注意力并建 KV）。
  • KV cache：保存 prefill 算出来的 K / V，供后续生成复用，避免每步重算历史。
  • Prefix caching：当 C 的输入已被修改，只能复用「首次 token 变化之前的共同 prefix」。前缀里任何一处变动都会让后续缓存全部失效——这正是为什么把易变内容（时间戳、用户输入）尽量放到 prompt 尾部的实践如此重要。

把这两组知识串起来看今天热榜的 Shopify Gisting 和 PyroDash 就更好理解了：Gisting 压的是 prefix token 数（直接减 prefill 成本、降 TTFT），PyroDash 调的是 decode 阶段用哪个模型（控制生成成本）。优化 LLM 成本，本质就是分别优化 prefill 侧和 decode 侧。

实践指南

⚠️必读安全实践：从 Anthropic 154 页威胁报告中学到的三件事

Anthropic 9 月 10 日发布的 AI 威胁报告（154 页）核心结论只有一句：「Sophisticated attacks no longer require sophisticated attackers」——高端攻击不再需要高端攻击者。攻击技术一点没变（偷凭证、钓鱼、SQL 注入、未打补丁设备），变的是 AI 在其中的角色：侦察、漏洞利用、数据处理、外传，以前需要一个团队的活，现在一个人加一堆 agent 并行就能干，AI 从「助手」变成了「指挥官」。

两个真实案例

  • 酒店 WiFi 入侵（GTG-20006）：AI 先黑掉至少 3 家酒店 WiFi 供应商并篡改 DNS，客人一连 WiFi，Windows / 安卓 / iOS 全中招，30 多万条身份记录被窃。AI 自带「自动重写」循环，跑了 130 天不断变种躲检测。
  • AI 厂商供应链入侵（GTG-50020）：攻击者往一家 AI 厂商的自动化评测沙箱里注入恶意指令，沙箱乖乖交出了手里的生产环境 API key（其中含多家厂商的 key）；拿到 key 后 4 天打了约 30 家 AI 公司，同一条攻击路径复制 30 遍。两起攻击烧的算力，用的都是偷来的 API key。

可落地的行动项

  • 把 API key 当硬通货看待：会话 / 沙箱环境里绝不放生产 key，评测、CI、demo 环境一律使用最小权限的临时凭证，并设置额度上限与异常调用告警。
  • 重新审视 eval sandbox 的权限边界：让 agent 执行代码做评测时，默认假设它会执行任意代码——沙箱必须无网络或严格白名单、无宿主机凭证、文件系统隔离。
  • 警惕文档与网页里的间接 prompt injection：agent 读取的 README、issue、网页都可能携带指令。对外部内容一律按不可信输入处理，工具调用前做白名单校验。

🛠️分库分表后的查库噩梦，用一个订单号解决

某大型 OTA 平台订单系统的真实案例：单库时代用 Snowflake 生成 64 位 orderId，全局唯一、趋势递增，查询就是 SELECT * FROM t_order WHERE order_id = ?，简单高效。分库分表后按 channel + orderId % 4 拆分，问题来了——订单号里不包含路由信息，拿到 orderId 也不知道属于哪个渠道，必须先查订单索引表拿到渠道，再定位具体分片。查询耗时从几十毫秒涨到数百毫秒，P99 超过 1 秒。

解决思路借鉴身份证号：身份证前 6 位就知道是哪个地区，无需查库。于是改造 ID 生成逻辑，在 64 位订单号中嵌入 4 位 routeKey，查询时直接解析出路由信息，跳过索引表。核心收益：约 95% 的查询命中该优化路径。

可以带走的经验

  • 分片键信息「外置」成索引表，等于给每次查询加一跳，且索引表本身会成为新的单点。能编码进 ID 的路由信息就编码进 ID。
  • ID 编码方案一旦上线就极难回滚（存量数据要迁移），因此必须在分库分表设计阶段就定好，而不是等性能出问题再改。
  • 代价要一并评估：嵌入 routeKey 会挤占 ID 的随机位，需要权衡 Snowflake 的并发上限与可读性。

🛠️Agent 协作技巧三则：/goal vs /loop、Step back、worktree 验证

1. Claude Code 里 /goal 和 /loop 回答的是不同问题（Addy Osmani）：/goal <cond> 是「干到终点线」——给它一个检查条件和一个上限，例如「测试通过，或 20 轮后停止」；/loop <prompt> 是「反复处理变化中的输入」（CI、review）；单独 /loop 是「照看 PR」；/usage 看每个 loop 的成本。把这两个命令用混，是很多人 agent 用得不顺的根源。

2. 「Step back」是一个高性价比的提示词关键词（宝玉）：当看到 Agent 在原地打转没有实质进展时，一句「Step back」让它重新看目标是什么、当前路径是否有问题，常常有效。同源技巧是「如果跳出当前架构，基于功能重新设计这个流程，你会有什么不一样的做法」——但要让 Agent 用数据验证，而不是空谈。

3. 用 worktree 而非分支来并行验证方案：宝玉让 Agent 开一个 worktree 去验证新方案（因为还有别的任务在跑，不方便切分支），对比当前方案在「不牺牲质量的前提下是否有更好性能」。结论是并没有预期那么好，但有部分可借鉴之处。另外用 sidechat（/btw） 让它解释方案，可以避免把冗长的解释塞进主上下文。

🛠️架构选型：WebView / RN 还是原生？从 SwiftUI 的「桥接 bug」说起

近期多个团队在做 app 技术路线的切换，背后是一个正在发生的结构性变化：agent 颠覆了「web 开发 vs 原生开发」的成本经济学，手写原生 app 的门槛被大幅拉低，于是原本因成本而选 WebView / RN 的产品开始考虑回归原生。

但回归原生不是没有代价。SwiftUI 联合创造者 Kyle Macomber 的点评很值得一读：在 Apple 内部做 SwiftUI 时，团队有个常见笑话——「所有 bug 都是桥接 bug」。SwiftUI 本质是在 UIKit 之上搭了一层声明式抽象，两层之间的衔接充满未定义行为，尤其是更新周期的微妙时序问题，而且底层还在不断变化；即便两个团队办公地点很近、有明确目标保持同步，也做不到完美。可以想见 React Native 团队有多难。

选型建议

  • 抽象层必然带来桥接成本，这是结构性的，不是某个框架的实现质量问题。做跨端方案选型时，要按「桥接面有多大」来估算长期维护成本。
  • Notion 移动端原本是 webview 套壳（与 mac 端 electron 思路一致），近年在陆续改造为 Swift 原生——这类「先套壳上量、再逐步原生化」的渐进路径，可能是比「一步到位重写」更稳的选择。
