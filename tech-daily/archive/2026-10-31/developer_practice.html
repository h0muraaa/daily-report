DeepSeek Super-agent：当「会话」变成实现细节

// 单任务 Agent 已经够强，下一个瓶颈是人类注意力

DeepSeek Harness 团队发布技术文章《Super-agent 设计探索：迈向更自主的 Agent 系统》，核心判断很直接：单任务 Agent 的能力已经不再是瓶颈，真正的上限变成了「一个人能同时盯住几个 Session」。主流设计仍以单一 Session 为基本单位，并行几件事就要人手动切换、自己记上下文，一个人通常只能跟住大约 3–5 个活跃会话——于是单任务上限看模型，多任务上限看人的注意力。

团队提出 Super-agent 应具备四个基础特征，并据此把单个 ReAct Loop 拆解成多个模块：

  • 连续：IM、GitHub 评论像同一个 Agent，不需要问「Session X 里有没有 Y」；
  • 高效：可并行多任务，不必等上一条做完才能说下一条；
  • 主动：持续观察环境，该出手才出手；
  • 持久：始终在线，异常能自愈。

五个工程模块

  • 双层 Router / Worker：解决连续性与吞吐的张力——全进一个 Session 上下文最连但串行慢、细节互相污染；每条事件新开 Session 吞吐高但缺全局上下文，于是用 Router 分发、Worker 执行。
  • 事件过滤与直通：只让真正需要处理的事件进入推理循环，避免噪声淹没注意力。
  • 异步 ReAct：把同步阻塞的推理循环改为事件驱动，任务之间不再互相卡死。
  • 存算分离 + 端侧 daemon：状态持久化，设备离线也不中断。
  • 外部 Watchdog：监控异常并触发自愈。

更值得关注的是它已经跑在内部研发协作里：当团队成员在群聊中反馈问题时，即使没有人 @ AI，它也能识别潜在缺陷，在后台尝试复现、寻找修复方案，甚至直接提交 GitHub Pull Request 等待审查；同一任务还能在群聊与 GitHub 之间连续推进——群聊定方案、GitHub 改要求，Agent 能理解前后变化并调整方向。需要说明的是，Super-agent 目前仍是面向工程实践的架构探索，部分设计已通过开源原型实现，并非 DeepSeek 正式产品。

📎 来源：meng shao · Super-agent 设计探索·爱范儿 · DeepSeek 全新 Agent 架构

自建 GPU 跑模型，到底什么时候比调 API 划算？

// imec 的上千次基准测试：硬件成本是阶跃的，并发比准确率更重要

比利时半导体研究机构 imec 的 AI 负责人 Steven Latré 团队针对「长时运行的编码类 Agent」做了一项扎实的测算：把开源权重模型与三套编码 harness 放到 SWE-Bench Pro 上跑了成千上万次基准，回答从 API 转向自有 GPU 的真实成本问题。

89% → 15%盈亏平衡 GPU 利用率：小系统约 89%，8×B200 机器约 15%
≈50%选对 harness 可将相同结果的 GPU 时间减半
阶跃硬件成本呈阶梯式跳变，而非平滑曲线

几个反直觉的结论值得记下来：第一，硬件成本是阶跃的，一旦跨过某个显存 / 卡数门槛，成本会突然跳变，规划容量时要按台阶算而不是线性外推；第二，并发比准确率更影响经济性，高吞吐批处理摊薄单任务成本的效果可能强于抠准确率；第三，harness 的选择能砍掉一半 GPU 时间，说明 Agent 框架层的工程优化与模型本身同样关键。对做长时 Agent、且调用量足够大的团队，这就是一张可直接拿来做容量与预算决策的参考表。

📎 来源：AI Engineer · When Running Your Own AI Models Beats Paying for APIs（Steven Latré, imec）

04 实践指南
01

用可达性分析给 Dependabot 告警降噪

Dependabot 告诉你某个依赖有漏洞，但你的应用真的能到达那段脆弱代码吗？GitHub 的 reachability analysis 会沿调用路径判断应用是否可能调用到脆弱代码，把它当作一个优先级信号，与严重度、EPSS 和生产上下文一起使用，而不是见到告警就全量升级。这是把「漏洞数量」转化为「真实风险」的低成本方法。

📎 GitHub · Security in 60 Seconds
02

给 Agent 设计「记忆晋升」策略，而不是无限追加上下文

RAG 让 Agent 能「读」，而记忆让它能「写」，业务价值就在写进去的那部分。Oracle 的 Wojciech Pluta 提出的做法是「记忆晋升」：先判断哪些信息值得保留，再与既有记录比对，最后决定是接受、拒绝还是升级给人类。他演示的按揭 Agent 能跨会话记住操作员偏好，但会拒绝存储「批准所有申请」这类越权规则；同时用 context card 保持提示词精简，并区分短期、长期与共享记忆——用数据库承载记忆是更可控的选择。

📎 AI Engineer · How to Decide What Your AI Agent Should Remember（Oracle）
03

Agentic 负载的 Bedrock 成本，要按「工作负载」而非 token 单价管

对话助手通常每轮一次模型调用，而 Agentic 工作流（如编码助手：规划、读文件、调工具、迭代）每个任务会发起多次调用并携带更大上下文，token 消耗呈量级差异。AWS 的 FinOps playbook 指出，只比较每模型 token 单价、让团队缩短提示词并不足以回答财务关心的三个问题：哪个团队花在哪、花了多少、是否在预算内。需要用标签化的团队 / 工作负载维度做归因与预算控制。

📎 AWS · Managing Amazon Bedrock costs end to end
04

让 AI 报漏洞，但必须由「确定性验证器」复现后才上报

Google 披露其 AI 安全 Agent PageBreak 自今年 1 月全面运行以来，已在自家 Web 应用中挖出 500 多个 XSS 漏洞。它的关键设计不是「让模型直接告警」，而是用 Gemini 自主调查潜在漏洞后，只有确定性验证器在运行中的应用上成功复现 exploit 才上报——这把模型的高召回与验证的低误报结合起来，值得任何做自动化安全扫描的团队借鉴。

📎 InfoQ · Google PageBreak AI Security Agent
05

Agent 上生产的真正卡点是工程配套，不是「要不要做」

阿里云开源的《AI Agent Handbook》所附「2026 Agent 开发者调研报告」显示：近半团队在做 Agent，但真正进入生产约仅 18%，持续迭代的不到 10%；卡点集中在上下文与记忆、多模型路由与成本、评估与可观测这三类工程配套。架构上单 Agent（约 40%）与多 Agent（约 42%）会长期并存，另有约 15% 把人在回路当作生产原则；多 Agent 的典型痛点是状态与上下文在协作中衰减约 60%，还会出现死锁雪崩与成本失控。结论是可迁移的抽象比押注单一厂商更值钱。

AI 功能的 A/B 测试：平均值会掩盖长尾里的坏输出

Bumble 产品经理 Supriya Subudhi 复盘了一个月活超 2000 万的约会 App 中 AI 照片点评功能的五个教训：调查中 78% 用户说想要反馈，实际只有 10–15% 使用；平均指标的提升掩盖了「让微笑的人笑得更多」这类怪异输出；最好的模型成本约 10 倍，换成便宜模型结果也缩水；合规限制导致该功能无法在美国以外上线。上线前建议先问：用户真的会用吗、长尾输出是什么样、成本与效果如何权衡、能否全球发布。
