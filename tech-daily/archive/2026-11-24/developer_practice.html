DEEP DIVE · 01

Loop Transformer：不堆参数，用"循环"换深度

标准 Transformer 里，每一层在前向过程中只运行一次。而 Loop Transformer 让一组权重共享的层循环执行多次，每一轮在上一轮输出的 hidden state 上继续精炼。这样可以在参数量不增加的前提下获得更深的有效网络——本质上是用"每个 token 更多的串行计算"去换取"更少的参数与显存"。

# 概念示意（非真实实现）
def forward(x):
    x = embed(x)
    for layer in layers_before:        # 常规层，各跑一次
        x = layer(x)
    for i in range(loop_iters):        # 同一组共享权重，跑 N 次
        x = shared_block(x)            # 每轮精炼 hidden state
    for layer in layers_after:
        x = layer(x)
    return lm_head(x)

一周内出现两个样本

  • GLM-5.4（智谱 / Z.ai）：首个 Loop Transformer 旗舰，官方称智能水平对标 2-3T 级模型；实测中它会出现"雷霆大思考"式超长思考，但团队认为这种反思与自我修正恰是长程任务所需的能力。
  • Inkling 2 Mini（Thinking Machines Lab，Mira Murati 创办）：总参数 26.4B，对每个 token 把中间层跑三遍；原生低精度权重约 20GB，官方称可在至少 32GB 内存的 Mac 上本地运行，能读图、写代码、搜索和调用工具。
工程视角：Loop 架构把"参数量 / 显存"和"推理算力"解耦开来。对端侧与本地部署尤其友好——Inkling 2 Mini 能塞进个人电脑就是例证；代价是每 token 的串行计算变多，延迟与算力开销上升。选型时先问：你是被显存卡住，还是被吞吐/延迟卡住？

来源：智谱 · Simon Willison · AINLP（Inkling 2 Mini）

DEEP DIVE · 02

Agent 沙箱的"数据恢复"瓶颈：腾讯 EROX 统一数据面

AI Agent 是有状态、长会话的：装依赖、跑任务、等大模型返回，状态要跨会话、跨节点延续。计算资源可以随时重建，数据却必须"随用随到"。腾讯技术工程给出的具体场景很扎心——4000 台 Agent 沙箱，每台挂一个 50GB 工作区，任务结束还要跨节点继续。若每次启动都先把 50GB 从远端搬下来，启动等待就会从秒级拉长到分钟级。

EROX 的做法：把数据面串成一条链

EROX 用一套统一数据面，把内核直挂、按需拉取、P2P、增量快照与节点侧降本串起来，加速镜像启动与快照分发。结果是：50GB 工作区 1 秒就绪、冷启动缩减 50%+，核心价值被概括为"读取即启动、状态可复制"。

配套的 CubeSandbox v0.8.0

  • 新增 JuiceFS 存储后端（预览）：模板跨节点共享，无需逐节点分发；元数据支持 Redis / MySQL / TiKV，对象存储支持 MinIO / 腾讯云 COS。
  • 调度策略插件化，可按业务定制装箱率与碎片率；运行状态统一采集（指标与日志不再散落各节点）。
  • 异常恢复交还给沙箱自身（不再只靠上层心跳拉起），并增强沙箱间通信与 E2B 兼容性。
  • 这一版共 128 个 PR、46 位贡献者、8 项核心特性。
可复用结论：做 agent 沙箱 / 代码执行平台时，瓶颈往往不在"冷启动本身"，而在工作区数据的搬运。优先设计增量快照 + 按需拉取 + P2P 分发，而不是每次全量恢复镜像。

来源：腾讯技术工程 · EROX · CubeSandbox v0.8.0

01供应链安全：5400 个恶意 npm 包说明了什么

Databricks 分析了 5400 个恶意 npm 包，系统梳理 2026 年的供应链威胁态势。配合 freeCodeCamp 的观点：企业 AI 流量难防护，是因为"安全相关信息藏在合法连接内部"——开发者把源码发给 coding assistant、内部应用把检索到的客户数据发给模型 API、agent 通过合规端点执行了业务从未意图的动作。评估 AI 网络防火墙时，要看它能否把一次 AI 交互绑定到足够上下文：用户/负载身份、应用、模型、数据敏感度、目的地、提示意图、工具访问、下游动作。

来源：Databricks · freeCodeCamp

02防"意图劫持"：Semantic governance policies

Google 的方案在每次工具调用执行前，用自然语言约束校验"这是否符合用户意图"，以拦截间接提示注入与意图劫持。在 AgentDojo 基准、Gemini 2.5 Flash agent 上，攻击成功率从 48.7% 降到 0.9%，同时保持较高任务可用性。开发者可在 Gemini 平台通过 Agent Gateway 预览使用。思路值得借鉴：把"用户到底要什么"编码成可在运行时逐次校验的策略，而不是只在输入端做过滤。

来源：Google Developers Blog

03Git 性能：三个"看起来无害"的操作会拖垮仓库

微软给出 Azure Repos 的优化建议，同样适用于任何 Git 仓库：
① 直接提交二进制——二进制版本间差异大、delta 压缩失效，仓库增长更快；
② 生成内容顺序不稳定——每次增删少量数据但顺序不一致，Git 会存下额外数据；
③ 默认 clone 拉全部数据——git clone <url> 默认拉取所有分支，某个开发者分支上的大文件会拖慢所有人。应对：partial clone、sparse-checkout、避免二进制入库。

来源：Microsoft for Developers

04给 agent 写 API：REST 还是 RPC 没那么重要，文档才重要

微软用 6 个模型、2 家厂商、1356 次运行做了对照：在有文档时，REST、POST-only、RPC 风格 API 的成功率、失败调用数和 token 成本几乎一样；在无文档时，REST 大幅领先——因为 agent 能从 HTTP 方法"猜"出意图（PATCH 改、DELETE 删），而 RPC 端点（/updateBin、/deleteBin）必须查文档。结论：想服务 agent，先把文档喂好，再谈风格。

来源：Microsoft for Developers

05为 coding agent 改造 SDLC：三个真实案例

Netflix：为人和 agent 写了 45 份架构决策记录（ADR），加了一个"只贴已验证阻塞项"的 review agent，并通过单一 MCP 工具提供按域的 GraphRAG 上下文。
Agoda：用模块化单体（domain components、Data Mapper、typed builders、ArchUnit 边界测试）在不大重写的前提下降低耦合——框架化改动使代码评审中位时间缩短 64%、初次反馈快 34%。
Slop Code Bench：最强模型仅约 16% 分，说明 agent 长期演进代码库仍很难——所以"评审仍然重要"不是保守，而是数据结论。

来源：InfoQ · Netflix · InfoQ · Agoda · AI Engineer · Slop Bench

06CI 选型：GitHub Actions 的替代选项

JetBrains 调研了 838 个组织实际在用哪些 CI/CD 工具、为什么。2026 年给团队换 CI 的理由变得具体：7 月 9 日托管 runner 故障超 9 小时、5 月 Megalodon 活动一下午把恶意 workflow 推进 5500+ 仓库、以及自托管 runner 收费风波（后因反弹推迟）。"替代"其实有四种含义——从"换一个执行器"到"整套迁移"，先想清楚你要解决哪一层问题。
