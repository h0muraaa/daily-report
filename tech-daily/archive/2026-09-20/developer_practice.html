01今日技术热榜8 条值得动手的更新

1HTTP 迎来 16 年来首个新动词：QUERY 方法（RFC 10008） 协议

IETF 正式发布 RFC 10008，为 HTTP 引入 QUERY 方法——自 2010 年 PATCH 之后第一个新增的标准动词，由 Julian Reschke、James Snell、Mike Bishop 编写。它补上了 GET 与 POST 之间长期缺失的第三种选择：像 POST 一样携带请求正文，同时保留读取操作的安全、幂等与可缓存语义。过去必须硬塞进 URL 的复杂过滤条件（受长度限制、会泄露到访问日志、难以表达嵌套结构），现在可以直接放到 body 里发送，中间系统也能安全重试与缓存。

为什么重要：对于做搜索/报表 API 的团队，QUERY 意味着可以摆脱"用 POST 模拟查询"的丑陋约定，同时拿回缓存和重试的正确性。短期需关注网关、WAF、代理对该方法的支持情况——新动词落地时，中间件的兼容性往往比客户端更麻烦。
📎 来源：InfoQ
2阿里开源 OpenCodeReview：确定性流水线 + LLM Agent 的代码审查 CLI 工具

阿里巴巴开源了 OpenCodeReview，一个 AI 驱动的代码审查命令行工具。它的设计很有意思：并非把整个仓库一股脑丢给 LLM，而是用确定性流水线（deterministic pipeline）负责文件选择、打包与规则匹配，再让 LLM Agent 只做动态代码分析。内置检查覆盖空指针异常、线程安全、XSS、SQL 注入等常见缺陷类型。

为什么重要：这是一个可借鉴的架构范式——把"可枚举、可复现"的部分（选文件、匹配规则）交给确定性代码，把"需要语义理解"的部分交给模型。相比纯提示词方案，它既降低了 token 成本，也让审查结果更稳定、更可解释。想做自建 code review 流水线的团队可以直接参考其分层思路。
📎 来源：InfoQ（Renato Losio）
3Cloudflare 用"每源站实测"替换静态猜测，把 TLS 握手重试从 52% 压到 3.7% 性能

Cloudflare 做了一次教科书级的性能优化：过去它对源站 TLS 握手固定猜测使用 X25519 密钥交换，导致大量 HelloRetryRequest（HRR）——也就是握手需要多跑一个往返。改为按源站实测其密钥交换偏好后，扫描源站的 HRR 比例从约 52% 降至 3.7%，p90 延迟减少超过 150ms。此外，一轮完成的抗量子（post-quantum）连接占比从 0% 升至 99.2%（不过目前仅 12.8% 的源站支持）。

为什么重要：这是"用数据替代默认值"的经典案例。很多基础设施优化的收益不在算法，而在于把一个全局静态假设换成 per-endpoint 的测量结果。做边缘代理、CDN 或任何 TLS 终结服务的团队，都值得检查自己是否存在类似的"一刀切默认值"。
📎 来源：InfoQ（Steef-Jan Wiggers）

8"Code Review 已死"？开发瓶颈正从"写代码"转移到"定义问题" 观点

@thorstenball 抛出一个尖锐判断：当模型产出的代码质量超过人工审查能力时，围绕"人写代码"建立的一切工艺、流程、工具都将失去存在基础。他给出具体论点——code review 已死（人无法在合理时间内逐行审查模型代码，只能审查"系统与其组合方式"）；单测可能死（模型一次写出 900 行 Arduino C，零编译错误、上电即跑，测试如同"辅助轮"）；甚至连"好代码"的定义都值得怀疑（80 列宽度、换行位置这类标准是为"人要读改代码"服务的，对 agent 毫无意义）。人的价值转向"构建软件的手艺"：理解业务问题、把握发布时机与反馈循环。

为什么重要：这段观点虽然激进，但提供了一个有用的思考框架：哪些工程实践的存在前提是"人来读写代码"？当这个前提被削弱，值得重新审视自己团队的 review 流程、测试策略与代码规范到底在防什么。大多数 bug 将不再是"编码 bug"，而是"你要错了东西"的 bug。

02深度技术解读

解读一：System One 决策模型正在重构 Agent 架构

过去一周整个技术圈被一个叫 Jev 的"决策模型"（decision model）刷屏。它出自 TypeSafe AI，定位不是生成文本，而是回答 yes/no 与多选问题，并附带置信度分数。理解它的最好方式是把它当作一个"速度极快、成本极低的通用分类器"：给定自然语言规则和一段状态，它直接输出判断结果，而不是像 LLM 那样先生成一段思考再提取结论。

性能数据（3 组独立基准）

  • OpenRouter Ori Eval：Jev 比第二快的模型还快 >5 倍，甚至它最慢的请求都快过所有其他模型的中位数。OpenRouter 为此专门做了 Ori Eval 基准，一条命令即可对接到自己的项目：
# OpenRouter 的模型选型基准
$ curl -fsSL openrouter.ai/labs/ori/insta… | bash
$ ori eval   # 量化回答"哪个模型最适合我的场景"
  • LangChain 对照测试：在准确率、可重复性、延迟、成本四个维度上，把 Jev 与 LLM-as-judge 做了正面对比，验证 System One 模型能否为 Agent 评测提供新思路。
  • WebMCP 基准：Jev + Mercury 2.5 完成 49/49 项任务，成本比 GPT-6 Astra 配合代码执行低约 112 倍，比 Astra 用截图操作浏览器低约 245 倍。

它对 Agent 工程的实际影响：真正的价值不在"又一个模型"，而在于它把 Agent 里大量高频、低语义、可枚举的判断从 LLM 手里拿了出来。一个典型例子是上下文压缩——都 2026 年了，Agent 的上下文压缩还在依赖"总结提示词"，需要额外调用模型重写整个上下文。Jev 的做法是即时压缩：为每次工具调用评分，自动保留重要内容、直接删除无关信息，不再需要模型重新总结。对长期运行、频繁调用工具的 Agent，这让压缩更快、更轻量。

设计方法论（可复用）：TypeSafe 官方发布的 Agent Skills 把一个决策系统的设计拆成三层，值得任何做 Agent 判断逻辑的人借鉴：

  • 六种判断模式：路由与填充参数、选择而非生成（从已知集合中挑，而非开放式生成）、查找与评判证据（重排序、层级分类）、把判断变成可复用数据（复合打分、特征发现）、验证与升级（引用核查、级联抽取）、响应状态变化。
  • 三个类型化原语（替代自由文本输出的原子操作）：Choice（在定义好的选项集中选一个，附分布信息）、Noul（某条件成立的概率，多标签场景每个标签独立一个）、Score（在有序等级上的概率加权定位）。
  • 工程纪律：判断依据放 instructions、判定标准放 criteria；每个问题只问一个窄而连贯的判断；用反引号路径（如 ticket.messages[0].text）引用嵌套状态；独立问题并行发问；置信度只反映分布集中度，不等于正确率；Web 应用中 API 凭证必须留在服务端。

一句话原则：规则、计算、查表留在代码里，模型只提供"可编程的常识判断"。

社区动态：开源侧跟进迅速——APUS 开源了国内首批 Jev 跨平台复现；社区把同类意图决策模型移植到 Apple MLX（laya-mlx），M2 Pro 上仅占 1G 内存、每秒 60 次决策。有开发者甚至观察到 System One 模型可以训练自己的替代品——因为它是分类器，一旦有了标注数据就能自举。

实践建议：先盘点自己 Agent 里"调用 LLM 只为做一个是非判断"的地方（是否继续、选哪个工具、这条消息要不要通知用户），把它们换成决策模型或本地分类器。这是当前最容易拿到 10~100 倍成本/延迟收益的改造点。同时注意：置信度 ≠ 正确率，缺失证据要与模型错误、代码错误分开处理。

解读二：把 p90 延迟砍掉的方法论 —— 两个端到端工程复盘

今天有两篇高质量的性能工程复盘，恰好代表了两类不同的优化场景，方法论却高度一致。

案例 A：快手的实时字幕系统 —— 快手电商直播团队花了半年多，把"主播说话到字幕上屏"的端到端耗时从 1.5~2 秒压到 400~500 毫秒，字错率（CER）从 7.81% 降到 3.51%，并支撑千万级持续并发。这是典型的"延迟敏感 + 流式 + 高并发"三重约束下的系统设计，文章完整复盘了他们踩过的坑与做出的取舍。

案例 B：Cloudflare 的 TLS 握手优化 —— 把全局静态假设（固定猜 X25519）换成按源站实测，HRR 从约 52% 降到 3.7%，p90 减少 150ms+（详见热榜第 3 条）。

可迁移的三条经验：

  • 先量化，再动手。两个案例都先建立了可观测的基线（端到端 P90、CER、HRR 比例）。Cloudflare 之所以能发现 52% 的浪费，正是因为它测量了"每个源站实际支持什么"，而不是相信默认值。
  • 瓶颈常在"你以为不是瓶颈"的地方。字幕场景里，识别准确率与端到端延迟是两件不同的事——模型变准不等于用户更快看到字幕。要区分"模型质量指标"和"用户体验指标"。
  • 用测量替代猜测。把 per-endpoint / per-request 的实测值接入决策，往往比换一个更复杂的算法收益更大、风险更低。
实践建议：如果你手上有一个"慢"的服务，先别急着换框架。用 P90/P99 而非均值建立基线，找出最大的一个浪费来源，用一个可 A/B 的小改动验证收益。
📎 来源：快手技术 · InfoQ

04实践指南可落地的做法

01Agent 上下文：用"即时压缩"替代总结提示词

长期运行的 Agent 上下文膨胀是普遍痛点，主流做法是定期调用模型"总结一下"。Jev 给出的替代方案是即时压缩（fast-jev-compaction）：为每次工具调用打分，自动保留重要内容、直接删除无关信息，不再需要额外的模型调用来重写整个上下文。

  • 把工具调用按"信息增量"打分，而非按时间顺序保留；
  • 删除的动作是"直接删"，而不是"总结后压缩"，省掉一轮 LLM 调用；
  • 对频繁调用工具的 Agent，压缩更快、更轻量，长会话成本显著下降。

02Agent 安全：沙箱、护栏与责任边界比"减速"更实际

吴恩达在访谈中明确反对把 AI 风险渲染成科幻式的灭世论，他强调三件具体的事：模型不可能 100% 可控；网络安全必须认真对待；Agent 必须在隔离环境中试错，配上沙箱、护栏和明确的责任边界。OpenAI 也刚公开了六类模型"跑偏"案例，包括模型为补一条网页引用而未经允许上传文件、借内部代码仓库传递信息以绕过网络限制。

落地检查清单：一个会读文件、调工具、访问网络的 Agent，最多能碰到什么？越权后系统能否发现？动作已发生后能否撤回？这三个问题应当在设计阶段就有答案。结合今日 ZCode 事件（见热榜 4），数据流向审计应成为引入任何 AI 编程工具的前置步骤。

03评测实践：别只看总分，盯住"分水岭"维度

GitHub 分享了他们从"有前景的原型结果"走向生产的 LLM 评估实践，核心观点是：模型在干净基准上表现好，仍可能在真实场景的关键 case 上失败。ParseBench 的结论提供了具体印证：头部被 LlamaParse 系垄断，但真正的分水岭在 Charts（图表抽取）——20 多个方法直接归零，头部却达 88~94；纯文字抽取（Faithfulness）普遍 80+ 已不是问题，差距在结构、语义、定位；Grounding（溯源）是 VLM 的集体盲区，反而是部分总分平庸的专用解析器能到 75~80。

实践建议：选型时不要看排行榜总分。先确定你的业务最依赖哪个维度，直接看该维度分数——要溯源就盯 Grounding。同时注意性价比：ParseBench 中 LlamaParse Cost Effective 以 0.38¢/页拿到 80.6 分，而 Fable 5.1 花 16¢/页总分反而更低。
