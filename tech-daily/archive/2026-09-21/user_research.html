应用供给翻了四倍，需求纹丝不动：vibe coding 把「谁会用」提前摆上了桌

a16z 最新一期数据周报给「vibe coding 创业潮」泼了一盆冷水。核心事实是供需的严重脱节：2025 年 2 月之后，iOS 每月新增应用从约 3 万～5 万款跃升到约 12 万款，Chrome 插件从约 3000 款增至 2 万款以上，Android 也从低谷回升到约 10 万款；但同期新应用在头三个月获得的下载、评分与参与度持平甚至下降，而「连小规模受众都没能积累起来」的应用占比还在上升。

爱范儿把 MIT 与宾大今年 5 月的论文《Writing Code vs. Shipping Code》串了起来：研究者把 2025 年 2 月标注为「Agentic coding era」（智能体编程时代）的起点，三条平台曲线在那个拐点之后几乎是垂直的。但需求端并没有跟着动——游戏使用时长下降约 3%、收入下降约 15%，生活方式类收入下降约 30%、图书收入下降约 40%。市场呈现的不是「所有 AI 应用一起繁荣」，而是增长集中在少数赢家。同期另一组数据为这个判断补上注脚：愿意自掏腰包购买 AI 的用户比例，从 2023 年一季度的不足 1%，到 2026 年一季度仅升到约 3%——且增长高度集中在年轻人（18～24 岁约 6%，65 岁以上约 1.4%，相差近 4 倍）。

对研究员的启示：这是本季度对用户研究价值最直接的一次背书。当「做出来」的成本趋近于零，稀缺性就整体转移到了「判断该做什么」和「验证有人要用」上，而这两件事恰恰是研究职能的本体。但也要注意数据指向的一个更尖锐的问题：新增应用失败不是因为质量差，而是因为没能找到最初的一批用户——「连小规模受众都没能积累起来」的应用占比上升，说明失败发生在获客与早期留存环节，而不是功能完备度环节。这意味着对独立开发者和小团队而言，最该补的不是设计工具，而是上线前的最小可用性验证：五个真实用户、三个核心任务、一次半小时的观察，成本远低于一次重构。同时，付费转化 3% 与年龄分层 4 倍差距这两个数字值得警惕——如果产品默认面向「愿意为 AI 付费的年轻人」，那么大量沉默的、付费意愿低的、以及老年用户的需求将在设计阶段就被系统性排除，这是典型的取样偏差写进产品定义。

GPT-6 Astra 通过 Figma MCP 做出了「有系统的原型」：AI 补上了 UI 生成最缺的那一环

OpenAI 公布了一段演示：让 GPT-6 Astra 完成一个 moonshot 级别的任务——为新式个人飞行器设计飞行控制界面。关键不在结果好看，而在于过程。Astra 没有直接「画一张界面」，而是先推理受众是谁、要完成哪些任务（jobs to be done）、飞行员与乘客之间的取舍、以及关键界面状态有哪些，然后通过 Figma MCP Server 把这份思考接入真实的设计系统，最终产出一个符合品牌规范的精修原型。OpenAI 自己的判词是：「生成一个界面」和「设计一套系统」之间的差距是巨大的，而 AI 模型过去一直做不到这一点。

同一批演示里还有一条更朴素的证据。Ramp 的工程师给 Astra 提了一行功能需求（为单个 API Key 增加路由控制），Astra 自己找到正确的设置项、完成修改，并主动使用 computer use 检查了自己的成果——在没被要求的情况下验证了移动端体验。实现约 12 分钟，验证又花了 15 分钟。这位工程师对 OpenAI 说的话点出了转折：「给它一个高层级目标，让它推进，然后回来审查改动。」

对研究员的启示：过去两年 AI 生成 UI 最被诟病的问题，不是美感差，而是「一次性」——它产出的是孤立画面，不是能进入团队流程的资产。设计师拿到的是一张无法复用、无法迭代、与设计系统脱节的图，等于把返工成本从设计环节推迟到了交接环节。MCP 接进 Figma 之后，「有系统的生成」这件事第一次成立，对研究工作的直接影响有三个：其一，把「合规性」纳入生成质量的评价维度——产出是否使用了正确的组件、是否遵循间距与状态规范，这类指标从主观评论变成了可自动核对的清单；其二，原型成本骤降会改变测试的时机，过去「等设计稿出来才能测」的节奏，现在可以在概念阶段就产出多个可交互分支做对比测试；其三，Astra 那句「先推理受众与任务，再动手画」值得当作方法论记住——把 jobs to be done 显式写进生成流程，产出质量会有质的差别，这也是研究员可以把研究成果更早注入产品过程的接口。

20,840 条真实 trace 的吐槽分析：用户抱怨的从来不是「不够聪明」，而是「没做完」

Arena.ai 分析了 Agent Arena: Code 上跨 29 个模型的 20,840 条真实交互轨迹，把用户的原话反馈拆成了可统计的失败类型。排名第一的抱怨是代码跑不起来（69.1%）；紧随其后的三类是输出不完整（27.1%）、收尾潦草与可用性差（27.1%）、无视指令（20.3%）。另一个有洞察力的发现是：模型们有共同弱点，但「失望的方式」各不相同——Fable 5.1 收到的「敷衍」与设计类抱怨明显少于 Astra（3.9% vs 5.7%）。趋势上，越新的前沿模型收到的正向反馈显著更多，跨实验室都成立。

对研究员的启示：这份数据的价值不在于排名，而在于它示范了一种把非结构化用户反馈转成产品语言的方法。三个可迁移的点：其一，抱怨的分布本身就是优先级排序。69.1% 集中在「根本不能用」，说明对工具型产品而言，可靠性是压倒一切的第一体验维度，任何在「更聪明的交互」上的投入，都要先扣掉这一项的负债。其二，注意「不完整」和「收尾潦草」并列且都在 27%——这恰恰是用户最难用一句话说清、也最难在传统问卷里问到的东西，因为用户往往只留下「感觉不太行」这类模糊表达，需要靠人工读原话才能解码成「它总是差最后一步」。其三，「不同模型以不同方式让人失望」意味着单一满意度分数会掩盖问题。用研常见的做法是给每个模型打一个平均分，但两个平均分相同的模型，其失败模式可能完全不同——一个偶尔彻底崩坏，一个稳定地每次都差一口气。后者的用户流失更隐蔽也更致命。建议在评估体系里保留失败类型分布，而不只是均值。

Googlebook 发布：把「光标」变成多模态输入点，交互从「命令」转向「意图」

Google 正式发布 Googlebook，9 月 21 日开启预售、10 月 4 日上架。产品定位非常明确：Googlebook 是「你的 Android 手机一直在等的那台笔记本」，把 ChromeOS 与 Android 的能力合起来，做一个对 Android 用户感觉最好的笔记本。Sameer Samat 在发布串里说得直白：「今天很多人严重依赖笔记本完成工作，但我们认为有机会重新思考这个品类。」

对用研最有价值的是体验层的那条线：Googlebook 强调内置智能，通过「多模态光标」（multimodal cursor）、智能听写等工具去「预判你的需求，简化你的一天」。设计层面则主打屏幕素质、处理器与材质质感——是一场软硬件同时发力的发布。

对研究员的启示：「多模态光标」这个命名本身就是一条值得记录的设计信号。光标是图形界面四十年来最稳定的隐喻——它代表「指向」，是一个纯粹的定位工具。一旦它可以承载截图、圈选、语音、上下文，它就从「定位器」变成了意图的发出点：用户在屏幕上的一个动作，可以同时表达「看这里」和「我要对这个做什么」。这对交互设计的挑战在于，同一次点击的语义空间突然变大了，而用户不会知道系统到底理解成了哪一种。这几乎是必然的可用性风险点：当动作的解读方式变多，可预测性就会下降。建议在测试这类界面时固定加入三类任务——「我明确知道想要什么」「我大概知道但不精确」「我只是随便试试」——并重点观察第二类，因为那是歧义最集中的地带。另外，跨端一致性是这次发布的隐含赌注：Googlebook 的全部体验设计都建立在「使用者的数据与习惯已经在 Android 手机上」这个前提上，这意味着它对非 Android 用户天然次优，是一个明确的、被主动选择的用户分层，而不是疏漏。

理想 i9 在「停车让行」路口没停车：拟人化学习把用户的坏习惯也学走了

理想在 i9 发布会上播放了一段媒体实测的智驾演示，本意是展示系统的防御性驾驶能力：在一个无信号灯的窄路口，i9 提前减速、确认安全后顺畅通过。但爱范儿指出了一个尴尬的事实——那个路口立着「停车让行」标牌，严格来说，这段被用来炫耀的演示，是一段智驾违规的典型案例。按现行规范，八角形「停」要求车辆在停止线前将速度绝对归零、充分瞭望后再起步，i9 并未执行。

文章的分析比批评更有价值：这不能全赖理想。国内道路上的多数司机面对视野开阔、无横向来车的停车标志，习惯降速观察、滚动滑行；真正停稳再起步的车辆反而容易招致后车鸣笛甚至追尾。而端到端大模型的行为范式，正是被真实驾驶视频片段与用户反馈共同塑造的——训练集里沉淀着老司机的预判与博弈经验，系统在变得更「拟人」的同时，也学会了部分驾驶者的「臭毛病」。同样的现象并非中国独有：美国研究数据显示，在有停车标识的路口，真正完全停稳的驾驶员同样只占少数。

对研究员的启示：这是一个把「拟人化」的设计伦理问题摆到明面上的案例，而且它适用于所有以人类行为数据为学习对象的产品。核心矛盾是：当系统用「像人一样」作为体验标准时，它同时继承的是人类行为的均值，而均值里包含大量「人们明知不该做、但因为环境压力还是会做」的部分。这里存在两条互斥的评价标准——法规合规性与社会习惯合规性——而真实用户对系统的期待往往同时包含两者。落到研究方法上，有三点建议：其一，在类似场景的测试中不要只收集用户「觉得对不对」的反馈，还要单独记录行为本身的规范符合度，因为用户很可能因为「大家都这么开」而对违规行为毫无异议，这类沉默的接受同样需要被记录下来作为决策依据。其二，警惕用户反馈作为训练信号时的自我强化循环：如果用户长期习惯滚动通过，系统学到「滚动通过是正常行为」，用户又因为系统这样做而巩固习惯，形成的稳定均衡可能是所有人都不满意的。其三，这个案例对自动化产品的普适教训是——「模型的期望行为」和「用户的典型行为」是两个必须分开定义的东西，前者需要显式的规则注入，不能指望从数据里自然涌现。做 agent、做推荐的团队都可以直接套用这个提问方式。

设计趋势洞察

Design Trends

趋势一：当 AI 学会「接进设计系统」，UI 生成的评价标准被迫重写

把今天两条独立的信息并起来看，能得到一个清晰的判断。一边是 GPT-6 Astra 通过 Figma MCP Server 把设计推理落进真实设计系统，产出「有系统」的原型；另一边是 Arena.ai 对 20,840 条真实轨迹的统计显示，「收尾潦草与可用性差」是继「代码跑不起来」之后的第二大类抱怨（27.1%），而且不同模型在这类问题上差异明显。

这两件事指向同一个变化：AI 产出物的评审语言正在从「好不好看」转向「和不和规矩」。一个孤立画面无所谓「合规」，但一个进入设计系统的原型可以被逐项核对——字号是否来自 type scale、间距是否命中 8pt 网格、交互态是否用了既有组件、错误态是否被覆盖。这类检查项的好处是客观、可复现、可自动化，而传统 UI 评审里「这个按钮感觉有点奇怪」的表述恰恰相反。

给研究工作的三条具体建议：

  • 把设计系统一致性做成交付门槛而非评分项。既然可以自动核对，就不要让它以「主观分数」的形式混在整体评价里——它应该是一条硬性通过线，先过线再谈创意。
  • 建立「状态覆盖清单」作为评审的固定动作。AI 生成界面时最容易漏的是关键状态：空态、加载中、错误、权限不足、超长文本。这恰好对应数据显示的「不完整」与「收尾潦草」两大抱怨。把这份清单前置到生成指令里，比事后返工便宜得多。
  • 保留人为的「品味判断」空间。合规可以被自动化验证，但「这个设计是否有品味」不能。Arena.ai 的数据显示 Fable 5.1 的「设计类抱怨」显著少于 Astra（3.9% vs 5.7%）——同样的合规程度下，产出依然可以有不同的品味高下。研究者需要守住这块无法量化的判断权，而不是把评审整体交给检查清单。

趋势二：个人 Agent 的「入口形态」之争——独立 App 还是聊天窗口里的一个会话

今天多条信息共同描绘了一场正在发生的入口之争。产品人 Peter Yang 给出了一条基于直接体验的判断：「一旦你用过 Muse 应用，就会意识到让 agent 寄生在 iMessage 这样的既有通讯应用里是没什么道理的。」他把 Meta 的 Muse 列为领跑者，理由是应用本身直觉易用，且 Meta 正在全平台激进推广，他预测它将超过 Threads，成为 Facebook 之后 Meta 最成功的自研应用。但他同时承认 ChatGPT 大概仍是个人 agent 的领导者，因为它已有 10 亿级用户，且模型、computer use 与语音逐项对比都不弱——只是「很难用一个产品同时服务工作与个人场景，更难用同一套 UX 同时服务企业与消费者」。

中文播客《乱翻书》从另一侧补上了完整的行业图景。节目邀请了 Today 创始 PM、前字节 AI PM 与前 TikTok 产品经理，拆解 Town、Instinct、Grok Bot 与 Meta Muse 四款产品。资本信号很密集：Instinct 今年才开始小范围测试，估值便从早期 5000 万美元涨到 25 亿，随后传出以 100 亿美元目标估值融资；Meta 推出 Muse 后迅速登顶美国 App Store 免费榜。节目给出的共识判断是：「Chatbot 只能回答问题，Personal Agent 却可能长期理解一个人，替他处理邮件、订票、购物、预约、退款和家庭事务。」而一旦 AI 开始替人办事、花钱和作出决定，它争夺的就不再是一款工具的使用时长，而是用户意图产生后的第一入口——搜索、推荐、电商、支付和超级 App 原有的位置都可能重新排列。节目也留了一个诚实的追问：上一批 Agent 为什么成了先烈。

设计洞察：这场争论表面上是「独立 App vs IM」，实质是一个关于「context 边界」的设计问题——Agent 需要的上下文究竟横跨多大范围？寄生在通讯应用里，它能天然获得社交上下文，却受限于该应用的交互范式与历史包袱；独立成 App，它能设计专属的信任与授权界面，却必须从零重建用户的习惯入口。Peter Yang 那句「让 agent 住在 iMessage 里没道理」的直觉，本质是在说授权与信任的操作需要专属空间：当 agent 要代替你花钱、发消息、做决定时，用户需要一个能看得见「它代表我做了什么」的地方，而聊天窗口的线性消息流并不适合承载这种可回看的审计视图。

给研究工作的建议：针对 Agent 类产品，把传统「任务成功率」指标换成三组更能反映真实信任的测量——①授权颗粒度（用户能否按任务类型、金额、对象分别授权，而不是一次性全权）；②事后可解释性（「它为什么这么做」能否在三秒内被回答）；③介入频次曲线（随使用时间推移，用户检查 agent 行为的频率是下降还是居高不下）。第三项尤其关键：如果介入频次不随时间下降，说明用户从未真正建立信任，产品实质上退化成了一个更麻烦的手动工具。

案例一：剪映没有再造一个生成平台，而是去「接住」别人生成的素材

9 月 20 日，剪映在「AI 新创作发布会」上集中更新了专业版、移动端与创作者生态。专业版新增一站式创作工作台「剪映 Hub」，由无限画布与多轨编辑器组成：用户可以从一句话、一个参考视频或一份文档开始，在画布上整理思路、生成脚本和分镜，调用即梦、小云雀等平台生成图片、视频和声音，再把初剪结果送入时间线继续修改。智能创作 Agent「剪映助手」则进入具体的剪辑工程，负责整理素材、删减口播、纠正字幕、检索补充画面和包装视频；手机端这个助手叫「小映」，面向生活记录、内容创作与商品营销。此外剪映调整了模板与会员体系：模板可以用自然语言改写内容，成熟创作者可以把自己的工作流沉淀为 Skill；新的 AI Ultra 会员每月含 22100 点 AI 积分，连续包月 199 元（首发期 99 元）。发布会上还意外展示了 AI 互动影游创作平台 ICG Studio，让创作者从一份剧本出发，做出可观看、可选择、可探索的互动故事。

体验点评：这次发布里最值得学的不是功能，而是定位选择。剪映明确没有去做独立的 AI 视频生成平台——生成依然交给即梦、小云雀等产品完成，剪映要做的是接住这些模型产生的素材，把此前分散的构思、素材管理和后期编辑放进一套创作工程。文章的原话很准：「过去两年 AI 视频模型的进步主要体现在生成效果上……但对做过 AI 视频的人来说，真正的痛苦往往在生成之后。」这是一个典型的从用户旅程而非技术能力出发的产品决策：技术把「生成」这一段解决了，剪映去占据上下游那些还没被解决的、更脏更碎的环节。

给研究员的可迁移方法：「无限画布 + 多轨时间线」这个组合值得专门分析，因为它试图同时容纳两种截然不同的思维方式——画布是发散、非线性、允许并置和反复推翻的；时间线是收敛、线性、不可逆的。把它们放进同一个工作台，本质是在用空间布局去承接用户的认知切换：先在画布上想清楚，再在时间线上做出来。这是对创作流程的真实理解，而非功能堆叠。相应地，评价这类工具的方法也要调整：不要用「完成任务需要几步」这类效率指标，而要观察「用户从发散切换到收敛的时机是否被工具支持」——具体来说，用户是否能在画布上保留多个被否决的方案而不被清理，是否能随时把画布上的想法降级/升级为时间线上的片段。另外「创作者把工作流沉淀为 Skill」这一条值得关注：它把专家的隐性经验变成了可复用的产品对象，如果做得好，这会是一种新型的用户研究方法素材——技能本身记录了专家实际的操作序列，比事后访谈更有证据力。

📎 来源：极客公园 · 剪映，杀入 AI 互动影游

案例二：NotebookLM 把语音问答推给全量用户，Claude 让 computer use 退到后台

今天有两款产品在「如何让自动化不打扰用户」这个命题上给出了各自的答案。NotebookLM 宣布 Live Chat 已 100% 推送给移动端所有 Ultra 用户，支持跨约 100 种语言与你的笔记进行实时语音对话，可以就来源提问并获得分步指引，且几乎完全免手动操作。另一边，Claude Code Desktop 应用中的 computer use 现在可以在 Mac 上于后台运行——Claude 在用户已授权的应用里「看」和「操作」，而用户可以继续做自己的事；该功能在 Pro 与 Max 计划上处于 beta。

体验点评：两条消息共享同一个设计方向——把「你需要盯着它」变成「它可以自己去办」。但它们选择了两种不同的实现路径，值得对比。NotebookLM 走的是降低输入摩擦：免手动、实时语音，用户不需要在屏幕上做任何精确操作，说话的节奏就是交互的节奏。这直接服务了一个明确的场景——用户在做饭、通勤、走路时想查自己资料里的某个细节。Claude Code Desktop 走的是降低监督成本：不是让操作变简单，而是让用户不必在场。它承认了一个此前被回避的事实：自动化助手最消耗用户的不是操作本身，而是「我必须看着它做完」。

给研究员的两点提示：第一，这两类设计都把可用性测试的情境真实性门槛提高了。在实验室里测试「后台 computer use」，如果被试全程盯着屏幕，就完全测不到这个功能的核心价值——必须构造「用户去处理别的事情、回来检查结果」的完整循环，并测量回来后的第一反应（能否快速判断它做了什么、是否信任结果）。第二，「几乎完全免手动」这个措辞里的「几乎」值得留意：语音产品的可用性断点通常就藏在那些仍需手动介入的少数场景里（纠正识别错误、在长列表中做选择、确认破坏性操作）。测试时应当专门寻找这些「必须动手」的时刻，因为它们是免手动承诺的兑现边界。

研究方法论

Research Methods

方法一：先做错误分析，再谈评估体系——指标应该「长出来」而不是「设计出来」

AI Agent Evals 实战 FAQ · Hamel Husain & Shreya Shankar · 700+ 工程师教学沉淀

当前行业对 Agent 评估的主流叙事是：搭评估基础设施、接 LLM-as-a-Judge、看仪表盘分数。两位作者基于大量一线教学与实践，认为这条路径恰恰是本末倒置的。他们的核心方法论可以压缩成一句话：先做错误分析，再谈评估体系。评估指标应当从真实失败案例中「生长」出来，而不是预先设计出来。分享者 meng shao 转述的原话更直接——「先手动读 100 条真实 trace，找到失败模式，评估器才会长出来；评估的本质是理解系统在哪里影响了用户，这一步没有自动化捷径。」

为什么这对用户研究员重要：这套方法论几乎是从工程侧重新发现了用研的基本信条。传统的可用性研究之所以强调「观察而非询问」，核心逻辑正是用户报告的失败与用户实际遭遇的失败系统性不一致——而 LLM-as-a-Judge 和仪表盘分数，本质上是把这个错误换了个技术外壳重犯一次：让机器替我们做「什么算失败」的判断，而这个判断本身就是研究中最需要人来做的部分。同时，今天 Arena.ai 那份 20,840 条 trace 的统计提供了一个现成的证据：用户抱怨的分布是 69.1% / 27.1% / 27.1% / 20.3%——这种颗粒度的失败分类，不可能在任何预先设计的评分表里被写出来，只能从阅读真实失败中归纳。

可落地的操作建议：把「手动读 trace」正式列入项目排期，而不是当作工程师的临时救火；读的时候按失败类型而非严重程度聚类，因为严重程度无法指导修复方向；每一类失败都要能被翻译成用户语言（「它总是差最后一步」），而不是工程语言（「第 4 步工具调用超时」）——能被翻译出来的，才是真正影响体验的失败。

📎 来源：meng shao (@shao__meng) · AI Agent Evals 实战 FAQ：先发现失败、再谈评估

方法二：直接用户反馈作为前沿追踪指标——把「点赞点踩」变成可分析的信号

Arena.ai · Agent Arena: Code · 20,840 traces / 29 models

Arena.ai 这次分析的方法论价值，和它给出的结论同样重要。他们没有用基准测试分数，而是把用户在真实使用中主动留下的好评与抱怨当作了追踪前沿的数据源，并明确把这件事称为「直接反馈解锁了追踪前沿的新机会」。在同一次分析里，他们还发现了一个值得产品团队注意的结构性差异：模型们有共同弱点，但「失望的方式」不同——这让「平均满意度」这类聚合指标的局限性暴露无遗。

为什么值得借鉴：传统的满意度量表问的是「你满意吗」，得到的是一个被压缩成一维的信号，而用户真实的反馈里包含指向性明确的问题描述——「它没做完」「它老是删我代码」「它无视我说的话」。这些原话的信息密度远高于任何评分。但要把它们变成可用的指标，需要三个前提：反馈必须绑定具体的使用轨迹（否则无法复盘发生了什么）、必须有足够量才能看出分布（20,840 条才支撑得起 27.1% 这样的细分）、分类体系必须从数据中归纳而非预设（否则会漏掉最意外也最重要的那一类）。

给研究工作的建议：如果你手上已有产品在使用中被反馈（App 商店评论、客服工单、社群吐槽、应用内反馈），它们很可能已经构成一个被低估的研究资产。值得做一次系统性的整理：把最近 500～1000 条原话按失败类型聚类，统计分布，并与团队自认为的问题优先级做一次对照。多数情况下两者会有显著偏差——而这个偏差本身就是最有价值的发现。另需注意：公开反馈天然偏向极端体验（非常满意或非常愤怒的人更愿意说话），所以在解读分布时要结合使用量分母，避免把「抱怨最多的类型」直接等同于「发生最频繁的问题」。

📎 来源：Arena.ai (@lmarena_ai) · 20,840 条 trace 的用户反馈分析
