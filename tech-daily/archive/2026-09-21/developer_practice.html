02深度技术解读

DEEP DIVE / 01

tokenizers v1 是怎么把编码做快 30 倍的：拆解三项核心重构

先说结论：tokenizers v1 没有改变分词算法本身。流水线依旧是四段——归一化（小写化、Unicode NFC/NFKC）→ 预切分（切成 pre-token）→ 模型层（pre-token 映射为 ID，BPE 反复合并优先级最高的相邻 pair，且合并永不跨越 pre-token 边界）→ 后处理（插入 special tokens）。速度提升全部来自实现层面的替换，这也是它敢承诺 token ID 与 API 完全不变的原因。

技术一：bitcannon 用 SIMD 位流替掉正则引擎。预切分阶段用的正则模式其实是模型的固定参数——GPT-2、cl100k、o200k、Tekken、DeepSeek 就那么几种切分规则。既然模式已知，运行时再跑一个通用正则引擎就是纯浪费。bitcannon 把输入字节当作并行位流处理，单条寄存器操作一次吃掉 64 字节（SIMD），思路承自 Parabix 与 simdjson。注意它只覆盖那五种已知模式，遇到不认识的分词器会自动回退到正则——这解释了为什么不同 tokenizer 家族的提速幅度差异那么大，自己训的冷门 BPE 很可能基本吃不到红利。

# 粗略感受一下命中与不命中的差别
from tokenizers import Tokenizer

# 已知家族（cl100k / o200k / ...）→ 走 SIMD 快路径
tok = Tokenizer.from_pretrained("Qwen/Qwen3-Tokenizer")
# 自训词表 → 自动 fallback 到正则，提速有限
tok = Tokenizer.from_file("./my-custom-bpe.json")

技术二：word cache 吃的是 BPE 的确定性。BPE 对同一个 pre-token 的输出是确定的，所以可以维护一个线程本地缓存，把 pre-token 字节直接映射到 token IDs，重复出现的词完全跳过合并计算。代价很直白：输入里重复很少时，查表开销收不回来。反过来说，它在 agent 场景特别划算——真实 agent trace 里系统提示、工具 schema、历史消息大量重复，正是缓存命中率最高的输入形态。

技术三：crate 拆分换更小的包体积与内存占用。把单体库拆成更细的 crate，让不需要完整功能的调用方（例如只做推理、不做训练的路径）只链接自己需要的那部分，从而降低二进制体积和常驻内存。这一项对服务端批量部署的收益往往被低估。

给你的落地建议：(1) 直接升版本，token ID 不变意味着可以放心回归；(2) 升级后跑一遍你线上的真实 trace 做吞吐对比，而不是跑论文里的英文语料——你的收益高度取决于「分词器家族 + 重复率」这两个变量；(3) 如果你的预切分模式不在那五种之内，别指望数量级提升。

📎 [来源: Hugging Face - Blog] · [来源: meng shao(@shao__meng)]
DEEP DIVE / 02

如果 LLM 没有 KV cache：一次对 coding agent 成本结构的反向审计

TypeSafe 的 Diogo 提了一个很锋利的反事实思想实验：假设 LLM 没有 KV cache，你会怎么设计 coding agent？他的论点是，今天 agent 的很多"标准特性"并非来自用户价值，而是为绕开 KV cache 与按 token 计费的成本结构打的补丁。用这个视角审计，才能分清哪些是真设计、哪些是缓存机制的衍生物。

他的前提假设也值得记下：agentic 部分本身出奇地简单（本质是 while 循环加少量工具），创新空间在「非 agent 部分」——状态管理、上下文构造、成本控制；模型、UI、开源实现都可以复用，因此第一方 agent 的成本优势正在缩小。

首个被点名的"怪象"：按难度路由在经济上不成立。把账算一遍（Opus 输入 5 / 输出 25，Sonnet 输入 3 / 输出 15，按每百万 token 计）：令 X = 上下文 token，Y = 生成输出，Z = 输出中额外产生的 token（写命令、读文件内容等）。

全程 Opus：
cost_all_opus = 25*Y + 5*Z

Sonnet 开路 → 回到 Opus：
cost_routed   = 3*X + 20*Y + 8*Z

结论是：只要 X 足够大（长会话）或 Z 超过 Y 的约 1.67 倍，第二条路线反而更贵。按 Diogo 给出的典型比例（X = 0.65、Y = 0.12、Z = 0.23），全程用 Opus 只要路由方案三分之二的钱。直觉盲区在于两点：cache 是按模型隔离的，小模型读大模型的上下文要按全价重新计费；中途产生的每个 token，回到大模型时还要再按输入价付一遍。这条分析对"用便宜模型做前置、贵模型做后置"这类常见架构是直接的反证。

⚠ 但请注意这不是"路由无用"的结论。该模型假设的是同一套上下文在两个模型间来回搬运。如果你把子代理做成上下文隔离的——子代理只拿到任务的窄上下文、返回结论而非全量轨迹——那么它省的正是 X 这块最贵的部分。今日另一条实践恰好是反例：有人在 Codex 里把仓库探索、写实现、跑测试这些高 token 消耗环节外包给 DeepSeek V4.1 Flash 子代理，让昂贵的 Astra 只做规划、架构判断和最终验收，确实压低了单任务成本。两者的差别不在"要不要路由"，而在上下文有没有跨界搬运。

配套读的两篇工程侧材料：大淘宝技术提出的 Loop engineering 把工程师的角色从"逐轮提示 agent"改为"设计包含读取状态、判断任务、执行操作、验证结果、记录状态、判断停止条件的自动化循环"，并拆出六大组件：负责唤醒的自动化机制、隔离并行的 worktrees、沉淀项目知识的 skills、接入外部工具的插件、分离读写职责的子 agent、确保状态持久化的记忆层。作者特别强调 loop engineering 不是盲目追求全自动，而是靠明确输入输出、严格权限分层与成本控制来保证可靠性。
另一篇是 OpenAI 的 Vinoth Govindarajan 关于 Agent Harness 的分享，核心论点很一致：生产环境 agent 的失败大多不在模型幻觉，而在骨架设计——需要明确状态归属、串行化并发的状态变更、限定执行权限范围、在用户可见边界上做动作校验。

04实践指南

SECURITY把依赖升级节奏改成"能当天出补丁"

Spring 团队公布了他们的调整：发布列车从每两周一次改为单日发布——每月第三个周一之后的周四，下一次常规补丁是 10 月 22 日，9 月 24 日会先有一次仅里程碑的列车。驱动这次改变的是漏洞节奏：自 3 月以来，他们平均每月收到近 80 份社区提交的安全报告，再加上用前沿模型做的内部扫描，增速没有任何放缓迹象。

为什么重要：当上游把补丁频率从"两周"压到"一天"，你的下游流程如果还依赖人工排期升级，就等于主动把暴露窗口拉长。今天 Next.js 也宣布 9 月 22 日要发带外安全更新（16.3.6 / 15.5.26），同样是这个趋势的例证。怎么落地：确认锁文件升级路径无阻塞、CI 能在一次构建内跑完回归、并且有一个能在补丁发布当天合并的流程——而不是攒到下个 sprint。

📎 [来源: Spring] · [来源: Next.js Blog]

EVALS先手动读 100 条真实 trace，再谈评估体系

Hamel Husain 与 Shreya 在教过 700+ 工程师之后给出的方法论与主流叙事相反：当前行业的默认路径是"搭评估基础设施 → 接 LLM-as-a-Judge → 看仪表盘分数"，他们认为这是本末倒置。正确顺序是先做错误分析——手动读大量真实 trace、归类失败模式，评估指标应当从真实失败案例中"生长"出来，而不是预先设计出来。

为什么重要：评估的本质是理解系统在哪里伤害了用户，这一步没有自动化捷径；先建平台再找问题，很容易得到一组漂亮的、但和真实痛点无关的分数。怎么落地：把"读 trace"列为固定动作而非一次性任务，失败分类先做成人工标签，等某个类别稳定重复出现再把它固化成自动评估器。

📎 [来源: meng shao(@shao__meng)]

AGENTLoop engineering：把"提示 agent"换成"设计循环"

大淘宝技术把 loop engineering 拆成六个可独立落地的组件：① 自动化唤醒机制；② 隔离并行的 worktrees（避免多个 agent 互相踩文件）；③ 沉淀项目知识的 skills；④ 接入外部工具的插件；⑤ 读写职责分离的子 agent；⑥ 确保状态持久化的记忆层。工程师的角色从"每一轮的操作者"变成"循环机制的设计者与最终责任人"。

为什么重要：当 agent 能自己读代码、改代码、跑测试、开 PR 之后，逐轮提示会成为瓶颈；但作者同时警告别把它做成"另一种自动化幻觉"。怎么落地：从明确的输入输出契约、严格的权限分层和成本上限三条约束开始，先让循环在一个低风险仓库里跑通，再扩大范围。

📎 [来源: 大淘宝技术]

AGENTAgent Harness 的四条不变量

OpenAI 的 Vinoth Govindarajan 基于真实案例（含 OpenClaw）指出：生产环境的 agent 失败大多不在模型幻觉，而在骨架。四条原则分别是——明确状态归属（谁拥有这份状态）、串行化并发的状态变更（避免两个动作同时改同一处）、限定执行权限范围、在用户可见边界上做动作校验。

为什么重要：这四项都是可以在 code review 里检查的工程约束，而不是"换更强的模型"能解决的问题。怎么落地：把它当成 harness 层的 checklist，在写工具调用与新状态字段时逐条对照。

SECURITYAgent 授权：从 token 访问转向有界委托（DPACT）

Sahil Agarwal 提出 DPACT 框架作为构建受控 agentic 系统的蓝图，五个维度：Delegation（委托）、Policy（策略）、Auditability（可审计）、Context（上下文）、Time（时效）。核心主张是放弃简单的 token-based access，改为"有界的、可委托的权限"。

为什么重要：传统 API token 的权限模型是为长期运行的服务设计的，而 agent 的调用链是动态、短时、多层委托的，用静态 token 很容易出现权限放大。怎么落地：给每个 agent 会话的凭证加时效与范围约束，把"这次委托能做什么"与"这个人能做什么"分开建模，并保留可审计的动作日志。

SECURITY多租户 agent 执行沙箱：别让 DNS 成为后门

Benchling 需要在数千个生命科学租户之间运行 AI 生成的科学代码，他们的安全团队发现常规沙箱不够。关键在于：标准网络控制能封 HTTP、限制出站端口、限制外连数量，但 DNS 解析往往仍被放行；即便系统默认有限制，你也可能既看不见也控制不了。为此他们基于 Amazon Bedrock AgentCore 做了更强的网络隔离，目前每天处理 600+ 次代码执行会话、每周覆盖 250+ 租户，零安全事件。

为什么重要："允许 DNS"看起来无害，但它是数据外泄的常见通道。怎么落地：审计你的沙箱出站策略时，把 DNS 显式列入管控项，并确认你对解析目标有可见性与否决权。

COSTGPU 利用率：跨集群路由把推理成本压下来

Google Cloud 描述了他们为 GKE Inference Gateway 构建的分层路由架构。背景很直白：全球加速器短缺意味着团队很难从单个数据中心拿到足够算力，容量散落在隔海相望的多个集群；而今天的 agentic 长任务上下文窗口动辄 100k–800k+ token，吃显存的速度超过以往任何一代流量。目标是把"每美元能买到多少智能"最大化——让闲置的加速器被填满，而不是让请求在别处排队。

为什么重要：超长上下文让推理的显存压力成为常态，单集群规划几乎必然出现峰谷错配。怎么落地：如果你已在多集群跑推理，评估在网关层做全局路由（官方数据是 <1% 开销）；同时把长上下文请求单独打标，因为它们才是真正压垮显存的那部分流量。

RUNTIMECloudflare 的 ADLC：用"软件工厂"替换传统 SDLC

AGENT用户到底在抱怨 coding agent 什么：一份 20,840 条 trace 的统计

Arena.ai 分析了 Agent Arena: Code 上 29 个模型的 20,840 条 trace，结论很有参考价值：代码跑不起来仍是最大的抱怨来源，占 69.1%；其次是输出不完整（27.1%）、收尾与可用性差（27.1%）、忽略指令（20.3%）。跨实验室的新模型整体正面反馈占比更高；模型之间共享一部分弱点，但"失望的方式"各不相同——例如 Fable 5.1 收到的 slop 与设计类抱怨少于 Astra（3.9% vs 5.7%）。

PERF把 LLM 剪枝当物理问题解：块移除作为 Ising 优化
