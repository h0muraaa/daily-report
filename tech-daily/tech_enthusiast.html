当写代码变成“零成本”，审查却成了新瓶颈

以 Ruff 和 uv 闻名的 Charlie Marsh 最近在播客里坦白，自己被 OpenAI 收购后，一度进入“一行代码都不读，全扔给 AI”的模式，结果被同事打醒。这种体验现在越来越常见：AI 生成一个“看起来合理”的 PR 几乎不需要成本，但人类审查它的时间并没有减少。

Charlie 还观察到，Bun 仓库的头号贡献者已经是一个机器人，整个工程世界的工作流正在改变。未来的程序员可能不再以“写代码”为核心，而是变成“指挥 Agent + 逐行审阅输出”。这带来的不仅是效率提升，还有信任危机：当机器能轻易给出合理答案，人类判断什么才是合理的，反而成了更稀缺的能力。

来源：AI前线

提示工程不够了，“上下文工程”正在决定 AI 的上限

很多人都知道“提示工程”——换种问法让 AI 回答得更好。但现在越来越多实践者发现，真正决定大模型表现的，往往不是问题怎么问，而是 AI 在回答前拿到了什么信息。这就是“上下文工程”。

一篇关于 AI 根因分析的文章指出，只要给 LLM 正确关联的日志、指标和链路数据，它就能完成复杂的故障推理；没给上下文，再强的模型也瞎猜。AI Agent 的行为同样如此：提示、评估、反馈、轨迹记录构成一个循环，任何一环缺失都会让表现大打折扣。换句话说，未来拼的不是“谁更会提问”，而是“谁更会给 AI 准备好资料”。

来源：freeCodeCamp、InfoQ

科普小课堂：什么是上下文工程？

一句话解释：上下文工程就是给 AI 准备“它需要知道的一切”，而不是只训练它怎么回答。

你可以把大模型想象成一个聪明但健忘的学生。提示工程相当于教他“考试技巧”，而上下文工程相当于在考前把课本、笔记和例题放到他面前。没有资料，技巧再好也白搭。

常见的上下文工程做法包括：检索相关文档（RAG）、整理代码仓库结构、给 Agent 接入实时搜索、提供历史对话记忆、把日志和监控数据按时间线拼接好。下次你觉得 AI“明明很聪明却总是答错”，不妨先检查一下：是不是该给它的“参考资料”不够完整？

产品推荐：Perplexity CLI

为什么值得关注

Perplexity 最近推出了命令行版本，让你在任何终端里直接调用它的联网搜索能力。对开发者来说，这意味着 coding agent 可以实时查文档、查报错、查最新 API；对普通科技爱好者来说，它也为“AI 搜索引擎”打开了一个更灵活的使用入口。

适合场景：快速调试代码时查最新资料、批量调研某个话题、把搜索结果接入自己的工作流。如果你已经在用 Perplexity，CLI 会让它离你的键盘更近一步。

上手方式：关注 Perplexity 开发者账号公布的 skill 安装说明，把技能配置进你常用的 agent 或终端环境即可。
